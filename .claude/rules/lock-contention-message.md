# The lock-contention message and its recovery command

Rest of the state layer: [layout-state-types.md](layout-state-types.md). Index
of every area: [code-layout.md](code-layout.md).

Split out of `layout-state-types.md` because that file's `paths:` glob covers
all of `src/state/**` and `src/types/**`, so every edit anywhere in either
directory paid for this entry — and the entry is about ONE file. The split is
the remedy `tests/unit/scripts/rule-file-payload.test.ts` names in its own
failure message; nothing here is summarised or dropped.

- **src/state/lock-contention-message.ts** - The message every fail-fast lock-contention site raises, plus `buildForceUnlockCommand` (issues [#2161](https://github.com/go-to-k/cdkd/issues/2161) / [#2170](https://github.com/go-to-k/cdkd/issues/2170)). Nine sites refuse on a held lock — `destroy` / `state destroy`, `import` (top-level + nested child), `orphan`, `state refresh-observed`, `drift --accept` / `--revert`, and `export`'s two — and before this module each spelled its own text, which drifted three ways. **Two of the three findings it closes are only fixable in ONE place, which is why the module exists rather than a shared string constant.** (a) The message asked the user to decide "is another process active?" while printing NONE of the evidence, and the population that reaches it makes that consequential: `acquireLock` reaps an EXPIRED foreign lock and retries, so a `false` return means the lock is LIVE — in practice a running `cdkd deploy` — and a user who follows a bare `cdkd force-unlock <stack>` deletes that owner's lock and reproduces #2161's harm by hand. `buildLockContentionMessage` therefore reads `getLockInfo` best-effort (one GetObject) and names owner / operation / time-to-expiry, degrading to the evidence-free wording on a null or a throw rather than replacing the contention with an S3 error — the caller is already on its way to throwing, and losing the reason it throws is the worse outcome. (b) `cdkd force-unlock` re-resolves the state bucket from the AMBIENT profile (`src/cli/commands/force-unlock.ts`), so a hint carrying only `--stack-region` resolves the DEFAULT profile's account after `cdkd destroy --profile prod` and force-deletes a same-named stack's lock somewhere else entirely; `LockRecoveryContext` carries `profile` / `stateBucket` / `statePrefix` and `buildForceUnlockCommand` emits whichever were set, shell-quoting a value that would otherwise truncate when pasted. (c) `subject` varies only the NOUN (`stack` / `nested stack` / `nested-stack child`), so one grep over CI logs finds every spelling. `heldClause` exists for `export`'s nested children, which call `acquireLockWithRetry` first and must say "held it through the retry window" rather than "holds it"; `suffix` carries that same site's no-changeset note. `destroy-runner.ts`'s FORCE-QUIT hint uses `buildForceUnlockCommand` too and needs the region MORE than the contention sites do — by that point `deleteState` may already have removed the record `force-unlock` would infer it from. Its imports are the `LockManager` TYPE and `DEFAULT_STATE_PREFIX` (from `src/state/state-prefix.ts` -- the constant was MOVED there rather than imported from `src/cli/commands/state-file-keys.ts`, which would have inverted the layering); the parameter is `Pick<LockManager, 'getLockInfo'>` so a caller (and a test) needs nothing else. **Two rules the review round established and a later edit must not undo**: every value that reaches the terminal is sanitized (a class wider than C0+DEL -- U+0085, the C1 range, U+2028/9 and the bidi overrides all reorder or forge lines in a terminal or a JSON log viewer) and THEN shell-quoted, in the PROSE as well as in the command, since `stackName` comes from an S3 key and `region` from a key SEGMENT (the BODY until go-to-k/cdkd#3328 made `getState` adopt the key's; plantable either way); and the command is emitted LAST and UNWRAPPED, because wrapping it in `'...'` composed with `shellQuote`'s own quoting into something unpastable for every `Parent~Child` name. `~` is deliberately NOT in the unquoted class -- it was added for exactly that case and removed again once the wrapper was gone, since a quoted `'Root~Child'` pastes fine while an unquoted leading `~` is tilde expansion on a bucket-plantable value. A value that sanitizes to EMPTY suppresses the whole command rather than emitting `--stack-region ''`, which `force-unlock` reads as "not supplied" and widens to every region holding the stack name.
  - **"Every value that reaches the terminal is sanitized" became literally true only at issue [#3377](https://github.com/go-to-k/cdkd/issues/3377), and ALL THREE `LockRecoveryContext` fragments were the exception, not just the one the issue named.** `--profile`, `--state-bucket` and `--state-prefix` were shell-quoted and never sanitized: quoting makes an injected `\ncurl ... | sh` a literal and does nothing about an ESC, which redraws the terminal from inside `'...'`. ONE of them is third-party PLANTABLE rather than merely operator-supplied, and the first cut of this note over-claimed it for all three (go-to-k/cdkd#3390 round 2): `config-loader.ts` resolves the BUCKET from a repo's `cdk.json` `context.cdkd.stateBucket`, while `--state-prefix` has exactly one source (its commander option -- `context.cdkd` does not expose it and no `CDKD_STATE_PREFIX` exists) and `--profile` likewise comes from argv. All three are sanitized anyway, because argv is untrusted text on a line an operator pastes; what differs is how much reach an attacker needs. They now go through one shared `sanitizeRecoveryValue` (a fourth fragment added later inherits it) giving the same sanitize + EXACTNESS pair `stackName` and `region` take -- a fragment whose rendering CHANGED names a different lock, and for `--profile` a different ACCOUNT. **Two deliberate asymmetries, both argued at the code**: the fragments take the DENYLIST while stack and region take `asciiOnly` (those two have a known ASCII charset, a profile name legitimately does not -- `asciiOnly` there would suppress the whole command for `prod-café`); and there is no empty-string clause beside `safeRegion === ''`, because an absent or empty profile or bucket emits nothing rather than an empty ARGUMENT -- an empty `--state-prefix` IS emitted, as `--state-prefix ''`, since it keys a real key space (go-to-k/cdkd#3363). The rule lives in the exported `recoveryCommandFlags`, shared with `cdkd orphan`'s properties refusal, which prints an inexact fragment as a `<profile>` / `<bucket>` / `<prefix>` hole where this function suppresses. `isPasteableIdent` is NOT used here (it answers the OPTION case, which cannot arise after a flag), unlike the sibling `cdkd local` site in the same issue. Whatever can suppress must also be named in `UNREPRODUCIBLE_LOCK_CLAUSE` and in `buildLockContentionMessage`'s no-command sentence -- both enumerate the values, and the first cut of this change widened the guard without widening either, telling a user their STACK NAME was unrenderable when it was their profile.
  - Issue [#2610](https://github.com/go-to-k/cdkd/issues/2610) added a TENTH caller outside those nine -- `lock-manager.ts`'s `acquireLockWithRetry` exhaustion arm, which had named a `--force-unlock` FLAG existing nowhere. Threading no `LockRecoveryContext`, its hint is region- but not account-qualified. It also EXPORTED `shellQuote` and `UNREPRODUCIBLE_LOCK_CLAUSE`; a second spelling of either drifts. Issue [#3085](https://github.com/go-to-k/cdkd/issues/3085) added `formatLockExpiry(expiresAt)` to that list -- the ONE rendering of a lock's deadline (`expires in 1m23s` / `expired 45s ago` / `expires at an unknown time`), consumed by this module's refusal, `LockManager`'s takeover warning / retry line / `LockError`, and `cdkd state show`'s lock row. It takes the RAW `expiresAt` and tests it with `Number.isFinite`, the same test `isLockExpired` makes, so what a record SAYS agrees with what the check DOES; subtracting first coerced a numeric string into a deadline the check called expired. `tests/unit/state/lock-expiry-renderer-sync.test.ts` refuses the phrases in any other `src/**` file and a consumer that hands the helper a difference; it strips line comments BEFORE block comments and anchors a block to a line start, because a `deployments/*.jsonl` inside a `//` comment in `lock-manager.ts` otherwise opens a phantom block that hides the `LockError` site (review of go-to-k/cdkd#3095).
