# main-tree-git-cwd-detector

Moved verbatim out of [hooks.md](hooks.md) when that file crossed the 120,000 B
per-file payload cap (the go-to-k/cdkd#2236 precedent, repeated for the
go-to-k/cdkd#2363 widening). hooks.md keeps a one-line pointer in the
"Branch / push safety" section.

**`.claude/hooks/main-tree-git-cwd-detector.sh`** — PostToolUse (matcher `Bash`) REACTIVE backstop for the cwd-RACE class documented in memory `feedback_session_resume_resets_cwd.md` (4 hits in a single 2026-07-03 session). The failure shape: during a feature-worktree task the persistent Bash cwd silently resets to the MAIN worktree (session resume / compaction / an earlier convenience `cd`), so the next command that OMITS an explicit `cd <worktree> &&` runs against the MAIN tree instead of the intended `.claude/worktrees/<branch>/` worktree. Complements the OTHER main-tree hooks: `main-tree-dirty-detector.sh` catches variable-indirected FILE writes but not the command-invocation cwd race; `branch-gate.sh` blocks `commit`/`push` only when the target tree is on `main`/`master` and its error is itself easy to misattribute. The hook fires whenever a matched command's EFFECTIVE working dir equals the MAIN worktree WHILE one or more `.claude/worktrees/` feature worktrees are active (= a task in flight) — with the one `vp run build` exemption below — emitting a **non-blocking** `additionalContext` warning that names the active worktrees and the re-run form. When no feature worktree exists it stays silent (ordinary main-tree work, governed by `branch-gate`). Always exit 0.

**It covers THREE command families, which share the mechanism but fail in different ways.** (1) **git mutations** — `git add` / `git commit` / `git push` / `git rebase` / `git merge` / `git cherry-pick` — surfacing as a quiet "nothing to commit" / "non-fast-forward" / wrong-files-captured / silently-fast-forwarded rebase or merge that reads like real git state, not a cwd bug; the warning tells the operator to re-run prefixed with `git -C <feature-worktree>` (the cwd-race-proof form). The rebase/merge/cherry-pick trio joined for issue #2363 (a `git rebase origin/main` intended for a lane worktree ran in the main tree and fast-forwarded silently); `git pull` is deliberately excluded — it is the mandated post-merge main-tree sync step. (2) **verification commands** — `vp run <task>` / `vp test run <path>` and `markgate set|verify <gate>`, including the `mise exec -- markgate …` spelling every marker call in this repo actually uses — where the wrong tree produces **no error at all**. A build / test / typecheck run against unmodified `main` PASSES, so the hazard is a FALSE GREEN whose verdict attests to nothing about the lane, and a `markgate set` from there binds the main tree's content in the main tree's per-worktree store. Unlike family 1 there is no symptom to misread, because there is no symptom; the warning therefore says explicitly not to treat the run as evidence and prints `cd <feature-worktree> && <the same command>`. (3) **`gh pr merge`** (issue #2363) — a marker-consulting command: the merge gates resolve the markgate store and the `.markgate-pr-review-sha` sentinel from the tree the command runs from, so a main-tree `gh pr merge` is judged against the MAIN tree's markers — a block arrives with a misleading diagnosis (the fresh marker sits in the worktree, the measured incident shape) and a pass would attest to the wrong tree; the warning says not to chase the gate's stated reason and prints the `cd <feature-worktree> && <the same gh pr merge command>` re-run. `gh pr create` stays out (same consultation, but it runs moments after the markers are set in the same session, so the mistargeted shape has not been observed there).

**Family 2 was added because the rule was already written down twice and got violated anyway** (2026-08-20). `/work-issues` section 6 states "Start every marker and gate command with an explicit `cd <worktree> &&` … a shell cwd does not reliably persist between tool calls, so the wrong tree is the default outcome rather than a slip", and its "bash cwd silent reset" Gotchas entry names the FALSE GREEN as the worst form. In one run the orchestrator that had just read both violated it three times: `vp run build && vp run test` with no `cd` ran the whole suite against the main checkout (caught only because the tool result echoed the session cwd); a post-rebase `grep` on a relative path ran in the main tree and returned 0 for BOTH markers it was checking, reading exactly like lost content when the real answer was 1 and 1; and `cd "$W" && gh pr merge 2082` — `$W` being a VARIABLE — left `pr-review-gate` unable to resolve the worktree statically, so it fell back to the session cwd, read a DIFFERENT worktree's `.markgate-pr-review-sha`, and refused the merge against a correctly-bound marker. Per this repo's own escalation rule (`/work-issues` section 10-b), a rule already in the text that is violated anyway escalates to a mechanism rather than a restatement.

**Scope is the EVIDENCE-PRODUCING set, deliberately, and there is a real gap it leaves.** Arbitrary read-only commands are NOT matched: a `grep` or a `cat` in the wrong tree is wrong too, but warning on those makes the detector noise, and a noisy detector gets ignored. What earns a warning is a command whose VERDICT is taken as evidence. The concrete cost is that **the second violation above — a bare `grep` on a relative path — is not and will not be caught by this hook**; only the worktree-first process and reading the echoed cwd cover it. `markgate status` (read-only) and a bare `vp run` with no task token are likewise out.

**The MANDATED post-merge `vp run build` is EXEMPT** ([#2094](https://github.com/go-to-k/cdkd/issues/2094)): the verify half goes quiet only when EVERY verification verb is `vp run build` AND the main tree is on `main`/`master`, clean of TRACKED changes, and not ahead of `origin/<branch>`. The discriminator is the TASK — main-tree git state separates NOTHING (in the DANGEROUS shape the tree is ALSO on `main`, clean and at `origin/main`), so those state checks only narrow. **ACCEPTED MISS, a BOUNDARY not one example**: the verify warning drops for ANY riding command `VERIFY_VERB` does not match, the SAME call included; 5 such shapes are pinned QUIET so the concession is FENCED. NOT closed by widening `VERIFY_VERB` — a different change with its own false-positive surface. Full measurement in the hook header.

**Effective-dir resolution** follows every `cd` in command position before the verb (via the shared `cmd_last_cd_target`, so chained relative cds compose and a trailing `cd` cannot hijack the lookup), then — **for the git family only** — an explicit `git -C <dir>` overrides. `git -C` is deliberately NOT honoured for the verification family: `vp` and `markgate` have no `-C` equivalent, so `git -C <wt> add -A && vp run test` runs the test in the cwd regardless, and reading the `-C` there would silence the warning. That is a false NEGATIVE, the one unacceptable direction for a detector, since a missing warning is indistinguishable from nothing being wrong.

**An unresolvable `cd` makes the hook SILENT, and that asymmetry is deliberate.** `cd "$WT" && vp run test` — the spelling `/work-issues` section 6 mandates, written with a variable as it is in practice — is skipped by `cmd_last_cd_target` — the token still holds a `$` or a backtick after unquoting, so it is not a path — and the function returns nothing, exactly as it does when there is no `cd` at all. (Between the convergence and go-to-k/cdkd#2130's review it briefly resolved such a token LITERALLY, to `<cwd>/$WT`, which no `git -C` can read: every affected gate then exited 0. That was a fail-open on the mandated spelling.) Collapsing those two states makes the hook fall back to the payload cwd and assert "this ran in the MAIN worktree" about a command that almost certainly did not; the first revision of this extension did exactly that and false-positived on both families. The hook therefore distinguishes them (a local `has_cd_before_verb` mirrors the library's scan, counting placeholder targets the library skips) and stays quiet on the unresolvable case. The honest reason is that the hook cannot know — it cannot expand `$WT` — and between a false alarm on the mandated spelling and a missed warning on a command that already carried the right prefix, the false alarm costs more, because it trains the reader to skip the warning and so disables the hook for the cases it CAN decide. An UNQUOTED `cd $WT` is quiet by a different route (the literal `$WT` path fails the `-d` check); both mechanisms are pinned by cases so neither can be removed believing the other covers it. A resolvable `cd <main-tree> && …` control keeps "quiet on every `cd`" from passing.

**Moving to the shared matcher COST command positions — a regression that is now REPAIRED** (issue [#2093](https://github.com/go-to-k/cdkd/issues/2093), closed by the #2129 convergence). This hook previously used its own inline anchor `(^|[&;|(])` — including `(`. The shared `lib/command-match.sh` anchors at `(^|[|;&][[:space:]]*)`, with no `(`, so subshell and command-substitution positions were lost. Measured old → new, all warn → quiet: `(git commit -m x)`, `true && (git commit -m x)`, `out=$(git commit -m x)`, plus the shared matcher's unbalanced-apostrophe limit `echo don't; git commit -m y` (a bare `git commit -m x` control stays warn). The gain is real — heredoc bodies and quoted spans mentioning `vp run test` in a commit message or PR body no longer fire — but the loss is stated here rather than implied away. The loss was accepted for a while because the same anchor governs every sourcing hook, several of them BLOCKING gates where a `(git commit -m x)` subshell is a `check-gate` bypass rather than a missed warning. The convergence widened it for all of them at once, with the full re-run that demanded: every hook suite under bash 5.x and macOS system bash 3.2, plus a never-match mutant over all 32 gates that have a suite (zero survivors). Re-measured on `branch-gate.sh` against a checkout on `main`, all four rows are now rc=2. Being non-blocking, this hook **skips** rather than refuses when the library is unloadable, matching `restore-backup.sh` / `post-merge-sync-reminder.sh` — the blocking gates fail CLOSED instead.

Smoke test at `.claude/hooks/main-tree-git-cwd-detector.test.sh` (79 cases, green under bash 5.x and macOS system bash 3.2 — the 8 original git-family cases, verification-family cases covering each verb, the `mise exec -- ` prefix for BOTH `markgate` and `vp` plus the `--`-required negative, the `cd <worktree> &&` and in-worktree quiet forms and the `git -C` non-redirect case above, 5 unresolvable-`cd` cases with their resolvable control, 3 scope-guard cases incl. the documented `grep` non-coverage, 5 quiet cases for no-worktree-active / non-opted-in-repo across the families, the #2094 exemption block — 15 quiet and 10 WARN by verdict — and the two #2363 blocks: 10 rebase/merge/cherry-pick cases incl. the `git pull` stays-quiet control and the read-only `git merge-base` / `git merge-tree` hyphen-boundary controls, and 8 `gh pr merge` cases incl. the non-merge-gh control and the build-exemption-must-not-launder case). The #2094 block's quiet cases fail 15/15 against the pre-change hook while its WARN cases pass there too, so those fence the exemption rather than the fix; the #2363 blocks' 6 WARN cases fail against the pre-#2363 hook while every quiet case passes there, so they fence the widening the same way. Each mutation probe reddens exactly its own cases. Pairs with `main-tree-dirty-detector.sh` + the worktree-first process.
