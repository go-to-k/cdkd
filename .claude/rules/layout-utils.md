# Key Files and Directories - src/utils

`src/utils/ip-protocol.ts` is documented with the drift normalizers: [layout-drift.md](layout-drift.md).

## Important Files

- **src/utils/parameter-types.ts** - `isListParameterType(type)`, the ONE definition of "is this CloudFormation Parameter `Type` LIST-shaped?" (issue [#2347](https://github.com/go-to-k/cdkd/issues/2347)). A LEAF with no imports. cdkd held TWO disagreeing answers: `coerceParameterTypedValue` in `src/deployment/intrinsic-function-resolver.ts` named exactly `List<Number>` and `CommaDelimitedList` in a `switch`, so the nine `List<AWS::...>` types CloudFormation defines fell to `default` and a `Ref` to one resolved to the raw comma-joined STRING -- which `Fn::Select` then refuses outright, failing the deploy -- while `src/synthesis/macro-expander.ts` tested `startsWith('List<')` and held the wider, correct view. It lives HERE rather than in either layer for the same reason `ip-protocol.ts` does: two consumers in different layers, and `src/deployment/**` and `src/synthesis/**` had no imports of each other before, so hosting it in either would have made the other's import the layering statement. **Deliberately NOT `aws-cdk-lib`'s `indexOf('List<') >= 0`**: that also matches the Systems Manager OUTER form `AWS::SSM::Parameter::Value<List<String>>`, whose supplied value is a Parameter Store KEY rather than the resolved list, so splitting it would shred a key. `macro-expander` asks the question of the already-peeled `inner`, so one predicate serves both sites. `List<Number>` keeps its own arm in the resolver, being the only list type whose ELEMENTS are not strings.

- **src/utils/display-safe.ts** - `displaySafe(value, { asciiOnly? })`, the ONE rule for making an untrusted value safe to render in a terminal or persist into a log (issue [#2170](https://github.com/go-to-k/cdkd/issues/2170) review round 3). A LEAF with no imports. It exists because the rule was being widened BY HAND one module at a time and missing an instance every round -- the change sanitized 1 of 5 readers of `LockInfo.owner`, and the review's verdict was "converging on mechanism, not on coverage". The structural answer is that `LockManager.getLockInfo` now sanitizes `owner` / `operation` AT THE SOURCE, so all five readers (a TTY, two `LockError` messages, the contention message, `state orphan`'s warning) inherit it and a reader added later inherits it too. **Two modes, and a caller must pick deliberately** -- the denylist strips every mechanism that forges a LINE or an ESCAPE (C0+DEL, `U+0085` and the C1 range since xterm reads `U+009B` as CSI, `U+2028`/`U+2029` because this text is persisted and re-rendered by JSON viewers, and the Trojan-Source bidi overrides `U+202A`-`U+202E` / `U+2066`-`U+2069` which visually REORDER the command being pasted), while `asciiOnly` is a positive allowlist for a value with a KNOWN charset (a stack name, an AWS region) and therefore has none of the denylist's residual (the invisible formatters `U+200B`-`U+200D` / `U+FEFF` and the bidi MARKS `U+200E` / `U+200F` / `U+061C`, which no denylist reaches). **An ABSENT value renders EMPTY, not `'undefined'`**: every caller keys an "is there anything here?" decision on the result, and `String(undefined)` is a TRUTHY `'undefined'` -- which printed `held by undefined` while certifying the holder as live, and is the defect the round-3 fence caught after the first fix looked correct.

- **src/utils/** - Logger, ANSI color helpers (`colors.ts` — `green` / `yellow` / `red` / `cyan` / `gray` / `bold` / `dim` inline wrappers; kept in a separate module from `logger.ts` so test files that `vi.mock('../../../src/utils/logger.js', ...)` don't accidentally strip color helpers and crash any code path that imports them), per-resource status-line formatter (`resource-line.ts` — `formatResourceLine(op, logicalId, resourceType, verbOverride?)` builds the shared `<glyph> <id> (<type>) <verb>` line printed by `cdkd deploy` / `cdkd destroy` for created / updated / deleted; every successful op renders a check ✓ — never a cross ✗ — and is distinguished by COLOR not glyph (green created / yellow updated / green-check-plus-red-verb deleted), so no success line is ever mistaken for the red ✗ "Failed to delete" failure path; `verbOverride` swaps the verb word, e.g. `'updated (metadata)'`), live progress renderer (multi-line in-flight task display), error handler (incl. `normalizeAwsError` for AWS SDK v3 synthetic UnknownError → actionable HTTP-status-keyed messages), AWS client factory, AWS region resolver (`aws-region-resolver.ts` — caches bucket-region lookups via `GetBucketLocation` so the state-bucket S3 client can be rebuilt for the bucket's actual region. Two things about the probe are decisions, both from issue [#1763](https://github.com/go-to-k/cdkd/issues/1763). Its ENDPOINT is `opts.region` -> `opts.fallbackRegion` -> the AWS SDK's own region chain -> `us-east-1`, never the hardcoded `us-east-1` it used to be: `GetBucketLocation` is answered by ANY regional S3 endpoint for a bucket in the SAME partition (measured 2026-08-13 — a real eu-west-1 bucket resolved identically from us-east-1 / us-west-2 / ap-northeast-1 / eu-west-1 clients), so the probe never needs to know the answer to ask the question, but it does have to REACH the partition — a us-east-1 endpoint is unreachable from `aws-cn` / `us-iso*`, so outside the commercial partition the probe could not run at all and every consumer (state backend, lock manager, exports index, custom-resource response path, `upload-cfn-template`) silently proceeded against the commercial default. No call site needed threading: `rebuildClientForBucketRegion` already passes `fallbackRegion` from the client's own `config.region()`, and `deploy` / `destroy` / `export` / `import` / `orphan` each assign `--region` into `process.env.AWS_REGION` before any work, so the SDK chain covers the rest. And only a SUCCESSFUL lookup is cached, mirroring `write-only-properties.ts` and #1746's `getAccountInfo` — the failure answer is a guess, and caching it pinned every later caller in the process to one transient error's wrong region with no way to heal), S3 bucket endpoint builder (`s3-endpoints.ts` — `s3BucketArn` / `s3BucketDomainName` / `s3BucketRegionalDomainName` / `s3BucketDualStackDomainName` / `s3BucketWebsiteUrl`, the four host-shaped `AWS::S3::Bucket` `Fn::GetAtt` values, each deriving its URL suffix through `derivePartitionAndUrlSuffix`. Shared because BOTH `S3BucketProvider.buildAttributes` (what lands in state) and `IntrinsicFunctionResolver.constructAttribute` (what an uncached cross-resource `Fn::GetAtt` resolves to) construct them; they used to carry independent copies hardcoding `amazonaws.com`, so fixing one side alone would make the resolver's answer disagree with `readCurrentState` — the phantom-drift shape `.claude/rules/providers.md` warns about (issue [#1745](https://github.com/go-to-k/cdkd/issues/1745)). `WebsiteURL` is NOT a mechanical suffix swap: AWS serves the legacy `s3-website-<region>` spelling for exactly nine regions and `s3-website.<region>` everywhere else, so `S3_WEBSITE_ENDPOINT_LEGACY_DASH_REGIONS` is a closed per-REGION set read out of `aws-cdk-lib`'s `region-info` `S3_STATIC_WEBSITE_ENDPOINT` facts — `us-gov-west-1` takes the hyphen while `us-gov-east-1` takes the dot, so the partition cannot decide it — and an unknown region falls back to the dot form, matching CDK. `DomainName` is the one value a suffix swap cannot make correct — S3's partition-GLOBAL endpoint exists only in the commercial partition, so the derived host does not resolve elsewhere; cdkd emits CDK's spelling rather than guessing the regional form, tracked as issue [#1809](https://github.com/go-to-k/cdkd/issues/1809)), RegExp literal escaper (`regexp.ts` — `escapeRegExp(value)`, the four-line helper that was spelled THREE times, in `ecr-uri.ts` / `cli/commands/gc.ts` / `assets/asset-redirect.ts`, each interpolating a user-controlled name (an AWS region, a bootstrap-marker asset bucket / container repo, an ECR host label) into a pattern. Centralized because copies of a security-shaped helper drift: the escaped set is what stops a `.` in an interpolated literal matching ANY character, and in `gc.ts` a widened match decides which live assets read as referenced), ECR image-URI host matcher (`ecr-uri.ts` — `parseEcrRegistryHost(imageUri)` returns the `{accountId, region}` of an ECR registry host, or `undefined` when the host has none of the served shapes or carries a suffix the matched shape does not serve for that region; `looksLikeEcrHostWithForeignSuffix` distinguishes that rejection from a genuinely public image. Since issue [#1793](https://github.com/go-to-k/cdkd/issues/1793) this module owns the ECR registry-host FORM TABLE — `ECR_REGISTRY_HOST_FORMS` plus the `ecrRegistryHostPattern(...)` builder that `src/cli/commands/gc.ts` consumes — because the forms were spelled TWICE and the two already disagreed: gc carried the `-fips` and `on.aws` forms while this module matched only the plain one, so a genuine FIPS or dual-stack registry classified as a public image here (anonymous pull, no `docker login`). **What is shared is the TABLE, not the whole matcher, and the unification is deliberately PARTIAL** — gc is the ONLY consumer of the builder; this module's own `ECR_URI_HOST_REGEX` re-spells the alternation from the table's LABELS column, because it needs the suffix CAPTURED at a FIXED group index to pair it with the region while the builder inlines a `fixedUrlSuffix` uncaptured (so the capturing-group count would vary per alternative, and gc reads its tag / digest groups BY POSITION). The acceptance rules stay separate too (gc matches the suffix against the union over all partitions and never pairs it with the region; this module pairs them — see the `AWS_URL_SUFFIXES` doc for why the two strictnesses are deliberate), and a THIRD, looser spelling still lives outside the table: `isCdkAssetImageUri`'s `host.includes('.dkr.ecr.')` in `src/local/ecs-task-resolver.ts`, which sees only the plain lower-case form and cannot simply call either matcher because it must keep tolerating an UNRESOLVED host (issue [#1846](https://github.com/go-to-k/cdkd/issues/1846), which also tracks the #1764 diagnostic MESSAGE now over-claiming for a form/suffix mispairing). Every verdict issues #1792 / #1793 changed — including the five DIAGNOSTIC-ONLY flips, where the parse result is unchanged but `looksLikeEcrHostWithForeignSuffix` goes `false` -> `true` — is tabulated in `ECR_URI_HOST_REGEX`'s doc comment and pinned by `tests/unit/utils/ecr-uri.test.ts`. The table's four rows are read off the AWS-published `ecr` endpoint list: `dkr.ecr` (every partition), `dkr.ecr-fips` (the six US / GovCloud FIPS regions), and the dual-stack `dkr-ecr` / `dkr-ecr-fips`, whose suffix is the FIXED `on.aws` rather than the region's partition suffix — so a form spelled with the other's suffix is refused, and the fixed literal is the tightest available check for those two (`on.aws` is AWS-owned, so unlike a captured suffix it cannot be substituted). Unifying the two copies is what surfaced `dkr-ecr-fips.<region>.on.aws`, which BOTH had been missing — on gc's side the irreversible direction, since a missed reference reads as unreferenced and the live image is DELETED. Lives in `src/utils/` because it has TWO consumers in different layers — `src/local/ecr-puller.ts`, which needs the `:tag` tail on top of it, and `src/local/ecs-task-resolver.ts`, which classifies an image that may carry a digest or no tag — and because it must stay free of AWS SDK imports, which is the invariant `ecs-task-resolver.ts` documents about itself. Before issue [#1758](https://github.com/go-to-k/cdkd/issues/1758) each site carried its own copy of a hardcoded `amazonaws.com(\.cn)?` pattern, so fixing the pull path alone left `cdkd local run-task` classifying a non-commercial registry as a public image and attempting an anonymous pull. Issue [#1786](https://github.com/go-to-k/cdkd/issues/1786) then made the whole comparison case-INSENSITIVE at ONE module-private boundary (`matchEcrRegistryHost`, which lower-cases the captured region, the captured suffix AND the derived expected suffix): DNS is case-insensitive, but both halves of the #1758 check were case-SENSITIVE in OPPOSITE directions, so an upper-cased region made a LOOK-ALIKE pass the strict check (it falls through to the commercial partition, whose suffix the look-alike carries) while an upper-cased region or suffix made a GENUINE host FAIL it. The returned `region` is consequently the canonical lower-case spelling, which both consumers rely on as an SDK client region. The same boundary refuses a region segment OR a URL suffix that is not `[A-Za-z0-9-]` / `[A-Za-z0-9.-]`, tested against the RAW capture BEFORE folding: case was only one way to defeat the partition helper's `startsWith` classification, the captured segment is not inert (it becomes an `ECRClient` region and is interpolated into the fallback login endpoint), and `toLowerCase()` maps U+212A onto ASCII `k` -- which, once #1764 landed `aws-isoe`'s `cloud.adc-e.uk`, let a folded suffix impersonate a real partition's. Issue [#1792](https://github.com/go-to-k/cdkd/issues/1792) then folded the last case-sensitive piece, the `dkr.ecr` LABELS, via the regex's `i` flag: an upper-cased label named the same host but did not match the SHAPE at all, so BOTH entry points went quiet (`parseEcrRegistryHost` `undefined` AND `looksLikeEcrHostWithForeignSuffix` `false`, i.e. not even the #1764 diagnostic). Widening rather than refusing is right because docker itself accepts an upper-cased registry host — `distribution/reference` spells `domain-component` as `[a-zA-Z0-9]`-based while the repository PATH is `[a-z0-9]+`, and `ParseNormalizedNamed`'s `must be lowercase` error applies to the remote NAME only — so cdkd is not made to `docker login` for a URI docker would reject, and the repository path is never touched. What docker does NOT fold is its credential STORE (keyed on the hostname verbatim, measured in #1801), so the login / pull spelling is reconciled one layer up by `ecr-puller.ts`'s `canonicalizeImageUriHost`; issue [#1817](https://github.com/go-to-k/cdkd/issues/1817) tracks moving that fold in here. That reconciliation covers the CASE fold only, which is why RECOGNIZING the three widened forms is not yet a working `docker pull` for them: `ecrLogin` authenticates against the PLAIN host (`proxyEndpoint`, or a hardcoded `dkr.ecr` fallback) while the pull targets the host the template names, so a FIPS / dual-stack pull fails with `no basic auth credentials` — issue [#1855](https://github.com/go-to-k/cdkd/issues/1855). One bound is recorded in-code rather than fixed there: three `cdkd local` command files still derive `${AWS::URLSuffix}` from the RAW user `--region`, so an upper-cased `--region` synthesizes a host this module then correctly rejects as a look-alike (issue [#1795](https://github.com/go-to-k/cdkd/issues/1795), shipped separately in PR #1818, which added `canonicalizeRegion` INSIDE `derivePartitionAndUrlSuffix` -- that makes the partition LOOKUP case-insensitive for every caller and is complementary to, not a replacement for, these guards, which decide whether the captured segments are a region id and a suffix at all)), AWS partition helper (`aws-partition.ts` — `derivePartitionAndUrlSuffix(region)`, the closed region -> `{partition, urlSuffix}` mapping CloudFormation applies to `${AWS::Partition}` / `${AWS::URLSuffix}`. Moved here from `src/local/ecs-task-resolver.ts` by the issue #1681 PR review — it gained a consumer in the provisioning layer (`AppSyncProvider` rebuilds a child's ARN when AWS reports none) and a provider importing from `src/local/**` would invert the layering; that module re-exports it so every `cdkd local *` call site is unchanged. `getAccountInfo().partition` (`src/deployment/intrinsic-function-resolver.ts`) is no longer a competing answer: it was hardcoded to `'aws'` on BOTH the success and the STS-failure path — which is how the AppSync update path came to overwrite a correct `arn:aws-cn:` ARN with `arn:aws:`, the regression that review caught, and which left the four `CloudControlProvider` enrichment sites (KMS key, ECR repository x2, Kinesis stream) building the same wrong ARN — and since issue [#1730](https://github.com/go-to-k/cdkd/issues/1730) it DERIVES the field through this helper. Issue [#1746](https://github.com/go-to-k/cdkd/issues/1746) then made that derivation PER CALL rather than per cache entry: `partition` is a function of `region`, and `region` is the CALLER's, so caching a whole `AwsAccountInfo` pinned the FIRST caller's region and a later no-override call inherited both it and the partition derived from it — benign while the field was hardcoded `'aws'`, a stale partition once #1730 made it derived. The cache now holds only the genuinely region-independent `CachedAccountIdentity` (`accountId` + the `fabricated` flag), and `accountInfoFor(identity, overrideRegion)` builds each caller's `region` + `partition` on the way out; `resolveAccountIdentity` takes no region at all, so the shared in-flight promise is region-agnostic by construction rather than by convention. Either spelling is now correct; prefer this one where a region is already in hand, since it needs no STS hop. Issue [#1850](https://github.com/go-to-k/cdkd/issues/1850) then folded the REGION the same way the partition already was: `derivePartitionAndUrlSuffix` canonicalizes its own input (#1795), so the PARTITION segment was already right for an upper-cased `--region`, while the REGION segment beside it was folded nowhere -- and `cdkd deploy --region US-EAST-1` is REACHABLE, since DNS is case-insensitive so the SDK endpoint resolves and the deploy SUCCEEDS. cdkd then recorded `arn:aws:appsync:US-EAST-1:...` into `state.json`, a value no IAM policy matches (policy matching IS case-sensitive) and every SDK call taking it rejects. The fold is applied at `AppSyncProvider.buildAppSyncArn`, at the four `CloudControlProvider` enrichment sites, and -- widest -- ONCE at `constructAttribute`'s `const region = canonicalizeRegion(...)` destructure, which feeds every constructed ARN / URI the resolver builds, so an attribute added later inherits it instead of having to remember. Double-folding is a no-op, which is what makes the region fold and the partition derive safe side by side. The same issue stopped caching a `fabricated` answer (the hardcoded `123456789012` fallback) FOR THE PROCESS, mirroring `write-only-properties.ts`'s "only SUCCESSFUL lookups are cached": one transient STS blip used to poison every later caller in the run, and the ARN-building consumers refuse on `fabricated`, so caching one turned a single bad answer into a whole deploy that records no ARNs. It is not cached for ZERO time either, and the distinction is what PR review had to correct: `getAccountInfo` sits on the path of EVERY `Fn::GetAtt` and every `AWS::AccountId` / `AWS::Partition` / `AWS::StackId` pseudo-parameter, so an uncached failure re-issued `GetCallerIdentity` — with the SDK's own 3-attempt retry, plus one warning — dozens of times per stack. A fabricated answer therefore gets a bounded `FABRICATED_ACCOUNT_INFO_TTL_MS` (10s) window (`accountInfoClock` is the test seam) and a shared `accountInfoInFlight` promise so concurrent callers under `--concurrency` collapse onto ONE round trip; a later phase can still heal. Those four `CloudControlProvider` sites now OMIT the attribute when `fabricated` is set (`accountInfoForSynthesizedArn`), mirroring `AppSyncProvider.childImportAttributes` — an ARN built from the placeholder account carries no wildcard, so `isPlaceholderArn` cannot catch it and the value would be recorded into state as the resource's `Fn::GetAtt` answer), state-bucket owner guard (`expected-bucket-owner.ts` — `resolveExpectedBucketOwner(client)` / `expectedOwnerParam(client)`: STS `GetCallerIdentity` on the client's own credentials, spread as `ExpectedBucketOwner` into EVERY state-bucket-family S3 call — S3StateBackend / LockManager / ExportIndexStore / bootstrap / state-migrate / state.ts raw reads / upload-cfn-template — so a predictable-name bucket pre-created in a foreign account is rejected by S3 itself (403) even when its policy ALLOWS this account; asset-storage has carried the same defense since #1002 PR 1; best-effort: test doubles / STS failure omit the header. Memoized in TWO layers (issue #1283): a per-client `WeakMap` fast path, plus the STS call itself keyed by the resolved ACCESS KEY ID — an access key belongs to exactly one account, so the several clients cdkd builds from one credential chain in a deploy preflight (the bucket-existence probe, the shared `AwsClients.s3`, the region-corrected rebuild) share ONE round trip, while an assumed-role session (its own `ASIA…` key) still resolves its own account — which is what keeps the cross-account `Fn::GetStackOutput` `RoleArn` path correct. `recordResolvedAccountId(client, accountId)` seeds that cache from a `GetCallerIdentity` the caller ALREADY issued with the client's own credentials (the default-state-bucket name resolution); it is keyed by the client's credentials, not by a caller-supplied key, so it is a memoization rather than an override and cannot attach an account to credentials the caller does not hold), cdkd-owned-bucket deny policy (`deny-external-access-policy.ts` — `buildDenyExternalAccessPolicy(bucketName, accountId, region)`, the `DenyExternalAccess` document applied to all three buckets cdkd owns: the state bucket (`cdkd bootstrap`), the `cdkd state migrate` destination bucket, and the asset bucket (`ensureAssetStorage`). The three were byte-identical copies, and all three hardcoded `arn:aws:s3:::` — so outside the commercial partition the statement named a resource that does not exist there, matched nothing, and the deny protected NOTHING while `PutBucketPolicy` still succeeded and each command still printed its checkmark (issue [#1794](https://github.com/go-to-k/cdkd/issues/1794), the [#1745](https://github.com/go-to-k/cdkd/issues/1745) residual). Centralized so the partition is derived in ONE place and a fourth copy cannot re-introduce the class. **Every caller passes the region of the CLIENT that writes the policy** (`await client.config.region()`), never a local `region` variable — the rule is uniform so no call site has to judge whether its own variable is authoritative. That is not cosmetic: the first cut passed `bootstrap`'s `region` on the argument that credentials are partition-scoped so it must agree, and the PR review showed the code does not read the credentials' region at all — `region` is `options.region || AWS_REGION || 'us-east-1'`, a hardcoded commercial fallback, while `AwsClients` omits `region` when `--region` is absent and lets the SDK chain resolve the profile's. A non-commercial profile with no `--region` therefore reproduced the very defect on the fix's own path. The same divergence mis-NAMES the asset bucket / ECR repo / marker key, which is a rename-and-migration question tracked as issue [#1820](https://github.com/go-to-k/cdkd/issues/1820)), state-bucket client rebuilder (`bucket-region-client.ts` — `rebuildClientForBucketRegion(client, bucket, opts)`, the single shared helper extracted in issue #827 from the three near-identical `ensureClientForBucket()` copies in `S3StateBackend` / `LockManager` / `ExportIndexStore`; does the cached-region probe + same-region short-circuit (returns `null` = keep the original client) + credential-reusing rebuild that does NOT destroy a shared client by default, with per-store knobs `destroyOldClient` / `reuseClientCredentials` / `profile` / `credentials` / `tolerateNonStandardClient`; kept in its OWN module — not folded into `aws-region-resolver.ts` — so the per-store tests' `vi.mock('aws-region-resolver.js')` of `resolveBucketRegion` is still intercepted cross-module, and each store retains its own `clientResolved` / `resolveInFlight` memoization), stack output buffer (`stack-context.ts` — `AsyncLocalStorage`-backed per-stack log buffer used by `cdkd deploy` when more than one stack is running concurrently; used by `cdkd local invoke` / `local start-api` to close the SIGINT-during-outer-finally race against shared mutable state like `containerId` / `servers[]` / tmpdir sets), docker subprocess helper (`docker-cmd.ts` — `getDockerCmd()` resolves the CLI binary via `CDK_DOCKER` env var for podman / finch / nerdctl parity; `runDockerStreaming` / `spawnStreaming` route every docker subprocess call through streaming spawn so BuildKit's progress output doesn't hit Node's `execFile` `maxBuffer` ceiling, mirror chunks to stdout/stderr when the logger is at debug level (`--verbose`), and reject with a `SpawnError` carrying the captured streams. `dockerSpawnEnvWithSensitive(sensitiveEnv)` / `partitionSensitiveEnv` / `DOCKER_CLIENT_ENV_KEYS` / `isDockerClientEnvKey` (issue [#2183](https://github.com/go-to-k/cdkd/issues/2183)) build the spawn `env` for a `docker run` that forwards value-less `-e KEY` flags — the pattern that keeps a secret VALUE off the argv / `/proc/<pid>/cmdline`, chosen over `--env-file` because docker's `--env-file` truncates a multi-line value (PEM keys) at the first newline while the env channel preserves it. The helper starts from `process.env` and adds only the sensitive keys that do NOT name a var the docker CLIENT (or a credential / connection helper it execs) reads — matched CASE-INSENSITIVELY since Windows env lookups are. `isDockerClientEnvKey` is an EXACT set (`DOCKER_*` connection / TLS / behaviour vars incl. `DOCKER_AUTH_CONFIG`, `PATH` / `PATHEXT` / `HOME` / `USERPROFILE`, the TLS-trust / runtime vars `SSL_CERT_FILE` / `SSL_CERT_DIR` / `GODEBUG`, the non-prefixed loader vars `GLIBC_TUNABLES` / `GCONV_PATH` / `BASH_ENV`, the CLOSED ssh exec/trust set — `SSH_AUTH_SOCK` / `SSH_ASKPASS` / `SSH_ASKPASS_REQUIRE` / `SSH_SK_HELPER` / `SSH_SK_PROVIDER` / `SSH_PKCS11_HELPER` / `SSH_AGENT_PID`, enumerated exactly per the #2186 round-3 blocker since an `SSH_` PREFIX dropped realistic secrets like GitLab CI's `SSH_PRIVATE_KEY` — the AWS credential-helper family the client's `docker-credential-ecr-login` reads (`AWS_ENDPOINT_URL` / `AWS_CA_BUNDLE` / `AWS_PROFILE` / `AWS_CONFIG_FILE` / `AWS_SHARED_CREDENTIALS_FILE` / `AWS_WEB_IDENTITY_TOKEN_FILE` / `AWS_CONTAINER_CREDENTIALS_FULL_URI` / `AWS_ROLE_ARN` / `AWS_EC2_METADATA_SERVICE_ENDPOINT`), and the upper-case proxy vars) PLUS a PREFIX rule for the release-specific families an enumeration is always one release behind on — `LD_` / `DYLD_` (the dynamic loader) and `AWS_ENDPOINT_URL_` (aws-sdk-go-v2's per-service endpoint family, which walks around the exact `AWS_ENDPOINT_URL` entry — #2186 round 4). The prefix families are fail-closed on the whole prefix (issue #2186 review), so an unlisted `LD_*` / `DYLD_*` / `AWS_ENDPOINT_URL_*` secret is dropped (with a rename warning) rather than reaching the client. A sensitive key of a MALFORMED shape (empty, or containing `=` / NUL — `isMalformedEnvKey`, the good-env-name shape defined POSITIVELY as the single pattern `WELL_FORMED_ENV_KEY = /^[^=\0]+$/`, negated (so a further bad spelling needs no further clause)) takes the same fail-closed collision path in BOTH `partitionSensitiveEnv` and `dockerSpawnEnvWithSensitive` (#2186 rounds 4-5): the denylist matches the whole key while the OS parses the environ NAME as everything before the first `=`, so `PATH=/tmp/evil:` would otherwise poison the client's own `PATH` (and an empty key emits an opaque `-e ''`). Case-insensitive Windows env handling is deliberately deferred to issue #2190 (needs the Windows-critical vars on the denylist first + a real Windows execution path; CI is ubuntu-only) — so a user-controlled ECS secret NAME cannot hijack the client (redirect the daemon via `DOCKER_HOST`, inject code via `LD_PRELOAD` / a `SSH_ASKPASS` helper, forge trust via `SSL_CERT_FILE`, pick a different Windows helper via `PATHEXT`). The argv split lives in `partitionSensitiveEnv` for the same reason: a colliding secret gets NO `-e` flag at all — not even the value-less form — because emitting `-e KEY` for a key `dockerSpawnEnvWithSensitive` refuses to set would make docker resolve it against the CLIENT's own env and hand the container the HOST's value (e.g. the host `HTTPS_PROXY` credential, or a macOS `PATH` inside a Linux image — the #2186 review blocker). Dropping the flag is what makes "not passed to the container" literally true; the dropped key is returned in `collisions` and WARNED at the call site. Consumed by `src/local/ecs-task-runner.ts` (`buildDockerRunArgs` returns `{ args, sensitiveEnv, collisions }`; the value goes to the container through the spawn `env`, never argv) and `src/local/ecs-network.ts` (the metadata sidecar's AWS credentials). ALSO adopted by the sibling `-e KEY` path in `docker-runner.ts`'s `runDetached` (the Lambda local-invoke path), which carried the same latent collision — closed by routing that path through the shared `partitionSensitiveEnv` / `dockerSpawnEnvWithSensitive` (issue [#2184](https://github.com/go-to-k/cdkd/issues/2184)), so a template-controlled SecureString NAME from `--from-cfn-stack` can no longer hijack the docker client there either)
