# Key Files and Directories - state, types

Split out of the former `layout-misc.md`, whose six globs made every
`src/synthesis` / `src/state` / `src/assets` / `src/types` edit load all four
areas' notes. Each file here carries a glob as narrow as its content.

## Important Files

- **src/state/** - S3 state backend, lock manager

- **src/state/state-prefix.ts** - `DEFAULT_STATE_PREFIX` (`'cdkd'`), the default S3 key prefix for cdkd state. Homed in the STATE layer and RE-EXPORTED by `src/cli/commands/state-file-keys.ts`, so its four pre-existing importers are unchanged. The move is the layering fix issue [#2170](https://github.com/go-to-k/cdkd/issues/2170)'s review forced: `lock-contention-message.ts` needs the constant to decide whether a recovery hint should spell `--state-prefix` at all, and a `src/state/**` module importing from `src/cli/commands/**` inverts the 7-layer architecture -- the CLI sits ABOVE the state layer, not below it. Note this is only the DEFAULT; commands accept `--state-prefix`, so whole-bucket listings deliberately do not scope to it. It also homes `CUSTOM_RESOURCE_RESPONSE_PREFIX` (issue [#2052](https://github.com/go-to-k/cdkd/issues/2052)); rationale and sync fence in [layout-cli.md](layout-cli.md)'s `gc.ts` entry.

- **src/state/s3-noncurrent-version-purge.ts** / **src/state/s3-replication-purge-gap.ts** - the state-bucket noncurrent-version purge and the S3-replication gap it cannot close (issue [#2447](https://github.com/go-to-k/cdkd/issues/2447)): [state-version-purge.md](state-version-purge.md).

- **src/state/lock-contention-message.ts** - The message every fail-fast lock-contention site raises, plus `buildForceUnlockCommand` (issues [#2161](https://github.com/go-to-k/cdkd/issues/2161) / [#2170](https://github.com/go-to-k/cdkd/issues/2170)). Nine sites refuse on a held lock — `destroy` / `state destroy`, `import` (top-level + nested child), `orphan`, `state refresh-observed`, `drift --accept` / `--revert`, and `export`'s two — and before this module each spelled its own text, which drifted three ways. **Two of the three findings it closes are only fixable in ONE place, which is why the module exists rather than a shared string constant.** (a) The message asked the user to decide "is another process active?" while printing NONE of the evidence, and the population that reaches it makes that consequential: `acquireLock` reaps an EXPIRED foreign lock and retries, so a `false` return means the lock is LIVE — in practice a running `cdkd deploy` — and a user who follows a bare `cdkd force-unlock <stack>` deletes that owner's lock and reproduces #2161's harm by hand. `buildLockContentionMessage` therefore reads `getLockInfo` best-effort (one GetObject) and names owner / operation / time-to-expiry, degrading to the evidence-free wording on a null or a throw rather than replacing the contention with an S3 error — the caller is already on its way to throwing, and losing the reason it throws is the worse outcome. (b) `cdkd force-unlock` re-resolves the state bucket from the AMBIENT profile (`src/cli/commands/force-unlock.ts`), so a hint carrying only `--stack-region` resolves the DEFAULT profile's account after `cdkd destroy --profile prod` and force-deletes a same-named stack's lock somewhere else entirely; `LockRecoveryContext` carries `profile` / `stateBucket` / `statePrefix` and `buildForceUnlockCommand` emits whichever were set, shell-quoting a value that would otherwise truncate when pasted. (c) `subject` varies only the NOUN (`stack` / `nested stack` / `nested-stack child`), so one grep over CI logs finds every spelling. `heldClause` exists for `export`'s nested children, which call `acquireLockWithRetry` first and must say "held it through the retry window" rather than "holds it"; `suffix` carries that same site's no-changeset note. `destroy-runner.ts`'s FORCE-QUIT hint uses `buildForceUnlockCommand` too and needs the region MORE than the contention sites do — by that point `deleteState` may already have removed the record `force-unlock` would infer it from. Its imports are the `LockManager` TYPE and `DEFAULT_STATE_PREFIX` (from `src/state/state-prefix.ts` -- the constant was MOVED there rather than imported from `src/cli/commands/state-file-keys.ts`, which would have inverted the layering); the parameter is `Pick<LockManager, 'getLockInfo'>` so a caller (and a test) needs nothing else. **Two rules the review round established and a later edit must not undo**: every value that reaches the terminal is sanitized (a class wider than C0+DEL -- U+0085, the C1 range, U+2028/9 and the bidi overrides all reorder or forge lines in a terminal or a JSON log viewer) and THEN shell-quoted, in the PROSE as well as in the command, since `region` comes from the state.json BODY and `stackName` from an S3 key; and the command is emitted LAST and UNWRAPPED, because wrapping it in `'...'` composed with `shellQuote`'s own quoting into something unpastable for every `Parent~Child` name. `~` is deliberately NOT in the unquoted class -- it was added for exactly that case and removed again once the wrapper was gone, since a quoted `'Root~Child'` pastes fine while an unquoted leading `~` is tilde expansion on a bucket-plantable value. A value that sanitizes to EMPTY suppresses the whole command rather than emitting `--stack-region ''`, which `force-unlock` reads as "not supplied" and widens to every region holding the stack name.
  - Issue [#2610](https://github.com/go-to-k/cdkd/issues/2610) added a TENTH caller outside those nine -- `lock-manager.ts`'s `acquireLockWithRetry` exhaustion arm, which had named a `--force-unlock` FLAG existing nowhere. Threading no `LockRecoveryContext`, its hint is region- but not account-qualified. It also EXPORTED `shellQuote` and `UNREPRODUCIBLE_LOCK_CLAUSE`; a second spelling of either drifts.

- **src/types/assembly.ts** - Cloud Assembly types (AssemblyManifest, MissingContext, etc.)

- **src/types/rollback-journal.ts** - Rollback-journal types + parser (issue [#1183](https://github.com/go-to-k/cdkd/issues/1183)). Defines `RollbackJournal` / `RollbackJournalSegment` / `RollbackSegmentReason`, the `ROLLBACK_JOURNAL_VERSION` constant, `parseRollbackJournal` (JSON parse + validation), and `UnknownRollbackJournalVersionError`. The journal is a **sibling** of `state.json` (`{prefix}/{stackName}/{region}/rollback-journal.json`), deliberately NOT part of the state schema — its own `journalVersion` (starting at 1), no `StackState.version` bump. Read/written via `S3StateBackend.{load,appendSegment,popSegment,delete}RollbackJournal`; `deleteState` sweeps the key so `cdkd destroy` cleans it up.

- **src/types/** - Type definitions (config, state, resources, assembly, etc.)
