# Key Files and Directories

## Core Directories

- **src/cli/** - CLI command implementations (deploy, destroy, diff, drift, events, gc, synth, list/ls, bootstrap, force-unlock, import, export, publish-assets, state, local), config resolution. `region-options.ts` is the ONE region-normalization point for those handlers (issue [#2065](https://github.com/go-to-k/cdkd/issues/2065)): `foldRegionOption(options)` at each handler's entry canonicalizes `--region` AND the two `AWS_REGION` / `AWS_DEFAULT_REGION` env vars (the env half is what the AWS SDK's own resolution chain reads, which no fold at a cdkd read site can reach), `namedCliRegion(...)` answers "which region did the user NAME" with `undefined` when they named none, and `rawCliRegion(...)` preserves the exact spelling for the bootstrap marker's second probe alone. `tests/unit/cli/cli-region-fold.test.ts` fences the shape across every file in `src/cli/commands/`.

  **Top-level vs `state` subcommand split**: top-level commands (`deploy`, `destroy`, `diff`, `synth`, `list`, `import`, `orphan`) require a CDK app — they synthesize a template to know what they're operating on. The `cdkd state ...` subcommand family (`state info`, `state list`, `state resources`, `state show`, `state orphan`, `state destroy`, `state migrate`) operates on the S3 state bucket only and does NOT need the CDK code; it's the right place to inspect / clean up state when the CDK app is missing or you don't want to synth. `cdkd drift <stack>` is also state-driven (no synth), since it compares state-recorded properties to the AWS-current snapshot returned by each provider's optional `readCurrentState` method — a CC-API fallback covers the majority of resource types out of the box; SDK Providers add their own `readCurrentState` incrementally. The two `orphan` commands operate at **different granularities** (this is the breaking change in PR #92): `cdkd orphan <constructPath>...` is **per-resource** (mirrors upstream `cdk orphan --unstable=orphan`) and rewrites every sibling reference (Ref / Fn::GetAtt / Fn::Sub / dependencies) so the next deploy doesn't re-create the orphan; `cdkd state orphan <stack>...` is **whole-stack** and removes the entire state record without touching siblings. Both orphan variants delete ONLY cdkd state; AWS resources are left intact (use `destroy` / `state destroy` to delete them).

  `cdkd import <stack> --app "..."` adopts AWS-deployed resources into cdkd state. Three modes: (1) **auto** (no flags) — every resource in the template is resolved from its physical-name property, then from a same-named CloudFormation stack's `DescribeStackResources` (issue #1128 / #1130; there is deliberately no `aws:cdk:path` tag lookup — that tag can never exist on a real resource, issue #1134); (2) **selective** (CDK CLI parity, default whenever `--resource <logicalId>=<physicalId>`, `--resource-mapping <file.json>`, or `--resource-mapping-inline '<json>'` is supplied) — ONLY the listed resources are imported, every other template resource is reported as `out of scope` and left out of state for the next deploy to CREATE. Matches `cdk import --resource-mapping` / `--resource-mapping-inline` semantics, including refusing to silently no-op on a typo'd logical ID; `--resource-mapping` and `--resource-mapping-inline` are mutually exclusive (matches upstream); (3) **hybrid** (`--auto` with overrides) — listed resources use the explicit physical id; the rest still go through the same name / CloudFormation auto-resolution as mode (1). `--record-resource-mapping <file>` writes cdkd's resolved `{logicalId: physicalId}` map (covers explicit overrides AND auto / hybrid mode auto-resolution) to disk before the confirmation prompt — emitted even when the user says "no" or under `--dry-run`, so the resolved data can be replayed as `--resource-mapping` in non-interactive CI re-runs (mirrors `cdk import --record-resource-mapping`). **Existing-state semantics**: selective mode is non-destructive — listed resources are merged into the existing state file and unlisted entries are preserved. `--force` is required only when the import would lose data: auto / whole-stack mode against existing state (rebuilds the resource map from the template, dropping any state entry not re-imported), or selective mode where a listed override would overwrite a resource already in state. First-time imports against an empty state never need `--force`. Outputs in the existing state are inherited by both modes (the import flow never derives outputs). `--migrate-from-cloudformation [cfn-stack-name]` (cdkd-specific) extends the import flow with an end-to-end migration path off CloudFormation. The flow: (1) **before** the import loop, `getCloudFormationResourceMapping(...)` (in `src/cli/commands/retire-cfn-stack.ts`) issues a single `DescribeStackResources` against the named CFn stack and merges the resulting `Map<logicalId, physicalId>` into the import overrides (user-supplied `--resource` / `--resource-mapping` entries take precedence). This side-steps cdkd's tag-based auto-lookup — which can't find resources deployed by upstream `cdk deploy` (that flow doesn't propagate `Metadata.aws:cdk:path` as an AWS tag, and AWS reserves the `aws:` tag prefix so cdkd can't add it on the way through either — confirmed empirically in #1128: `TagRole` with an `aws:`-prefixed key returns `InvalidInput: Tag keys beginning with aws: are reserved for system use`, and a `cdk deploy`-deployed resource carries tags `[]` while its template Metadata holds the path. The corollary is that the `aws:cdk:path` tag walk NEVER matches. Auto-mode import therefore resolves ids from the template's physical-name property and — since #1128 — from a same-named CloudFormation stack's `DescribeStackResources`, via the best-effort, never-fatal `tryGetCloudFormationResourceMap`. That lookup is flat (nested children stay `--migrate-from-cloudformation`'s job), never retires the source stack, is skipped in selective mode, and warns-and-falls-through on any failure so a caller lacking `cloudformation:DescribeStackResources` is not blocked) — so a bare `cdkd import MyStack --migrate-from-cloudformation` works for both `cdk deploy`-managed and `cdkd deploy`-managed stacks. The flag also forces `selectiveMode = false` regardless of override count (the CFn-derived overrides shouldn't trigger selective mode, which would mark every other template resource `out of scope` and orphan them after `DeleteStack`). (2) Import runs and writes state. (3) **After** state write, `retireCloudFormationStack(...)` runs the standard `DescribeStacks` (verify stable terminal state, capture existing `Capabilities`) → `GetTemplate` Original-stage (parse JSON, inject `DeletionPolicy: Retain` + `UpdateReplacePolicy: Retain` on every resource) → `UpdateStack` (skipped when the diff is empty or every resource already has both Retain policies) → `DeleteStack` (CFn skips every resource because they're now Retain). Runs inside the import command's lock-protected scope so a concurrent `cdkd deploy` can't race the post-write CFn calls; only runs when state was actually written (zero-imports or "no" at the prompt skip the retirement). The flag accepts an optional value: bare `--migrate-from-cloudformation` uses the cdkd stack name as the CFn stack name (typical for CDK apps where they match); pass `--migrate-from-cloudformation <name>` to override when the names differ. Templates may be JSON or YAML (CFn shorthand intrinsics like `!Ref` / `!GetAtt` / `!Sub` are preserved across parse → mutate → re-serialize via the CFn-aware codec at [src/cli/yaml-cfn.ts](../../src/cli/yaml-cfn.ts) — see the YAML support bullet for details). Templates up to the 51,200-byte inline `TemplateBody` ceiling are submitted directly; larger templates are uploaded to the cdkd state bucket under `cdkd-migrate-tmp/<stack>/<timestamp>.{json,yaml}` and submitted via `TemplateURL` (the transient object is deleted in a `finally` immediately after `UpdateStack`, success or failure). Templates over the 1 MB CloudFormation `TemplateURL` ceiling are structurally unsubmittable and fail with a clear error; cdkd state is already written so the user can re-run or finish manually. Not compatible with `--dry-run` (post-state-write retirement is a real side-effect). For plain (non-CDK) CloudFormation stacks (hand-authored YAML / JSON, Terraform-to-CFn output, Console-created stacks) use the dedicated `cdkd migrate --from-cfn-stack <name>` top-level command, which wraps the same end-to-end flow (upstream `cdk migrate` codegen + 2-pass `(sourceLogicalId, synthLogicalId)` mapping + cdkd state + optional `--retire-cfn-stack`). `cdkd import --migrate-from-cloudformation` is the right tool when a CDK app already exists and you want to take over an existing `cdk deploy`-managed CFn stack without re-generating the CDK code.

  **`provider.import` support coverage**: see [docs/import.md](../../docs/import.md) for the full per-resource-type list (auto-lookup vs override-only vs CC-API fallback vs unsupported). Single source of truth — when adding `import()` support to a provider, update that file. Keep entries one-per-line so parallel PRs don't conflict on rebase.

  **`cdkd import` vs upstream `cdk import` — parity notes** (see [docs/import.md](../../docs/import.md) for the full matrix; this is a quick checklist when working on the import code path):

  - **Mechanism is per-resource SDK calls, not a CloudFormation changeset.** `cdkd import` is therefore **not atomic**. `import.ts` collects per-resource outcomes (`imported` / `skipped-not-found` / `skipped-no-impl` / `skipped-out-of-scope` / `failed`) and only writes state after a final confirmation (`--yes` to skip). A partial import can be backed out with `cdkd state orphan <stack>`.
  - **No interactive prompt for missing IDs.** Upstream's TTY default prompts per resource; cdkd resolves IDs from the template's physical-name property + a same-named CloudFormation stack's `DescribeStackResources` (in `auto` / `hybrid` modes) or treats them as `out of scope` (in selective mode). The only prompt is the final "write state?" gate.
  - **`--resource-mapping <file>`: parity.** Same JSON shape (`{"LogicalId": "physical-id"}`) and same semantics — only listed resources imported, unlisted resources rejected, typo'd logical IDs abort before any AWS call.
  - **`--resource-mapping-inline '<json>'`: parity.** Same JSON shape as `--resource-mapping <file>`, mutually exclusive with it. Useful in non-TTY CI scripts that don't want a separate file.
  - **`--record-resource-mapping <file>`: parity.** cdkd writes the resolved `{logicalId: physicalId}` map to the file before the confirmation prompt (and even when the user says "no" or under `--dry-run`). Covers explicit overrides AND cdkd's auto-resolution (physical-name property, then `DescribeStackResources`), so this is the canonical way to capture an `auto`-mode resolution and replay it as `--resource-mapping` in CI.
  - **`--force` semantics differ.** Upstream: "continue even if the diff has updates/deletions." cdkd: "confirm a destructive write to existing state" — required for auto / whole-stack rebuild on existing state, and for overwriting a listed entry already in state during selective mode; not required for a pure selective merge that only adds new resources, nor for first-time imports. Same flag name, different meaning — do not confuse them when reading PRs / issues.
  - **`auto` and `hybrid` modes are cdkd-specific** (whole-stack adoption via physical-name + CloudFormation `DescribeStackResources` resolution; no `aws:cdk:path` tag lookup — issue #1134). No upstream equivalent. Do not mistake them for parity features.
  - **`--migrate-from-cloudformation [name]` is cdkd-specific.** End-to-end migration off CloudFormation: pre-import `DescribeStackResources` to recover physical IDs (so cdk-deployed stacks work without `--resource`) → import → state write → post-import `UpdateStack` (inject Retain; uploaded to the cdkd state bucket via `TemplateURL` when over the 51,200-byte inline limit, hard-rejected over the 1 MB `TemplateURL` ceiling) → `DeleteStack`. No upstream equivalent — `cdk import` only adopts resources INTO a CFn stack, never out of one. Accepts JSON and YAML templates (CFn shorthand intrinsics preserved end-to-end via the codec at [src/cli/yaml-cfn.ts](../../src/cli/yaml-cfn.ts)); incompatible with `--dry-run` (see the import section above for the full constraint list).
  - **Nested CloudFormation stacks (`AWS::CloudFormation::Stack`):** bare `cdkd import` (auto / selective / hybrid mode) reports each nested-stack row as `unsupported` (`NestedStackProvider` has no `import()`). `cdkd import --migrate-from-cloudformation` IS supported recursively (issue [#464](https://github.com/go-to-k/cdkd/issues/464)): it walks `DescribeStackResources` recursively, writes one v6-keyed state file per nested child (`cdkd/<parent>~<childLogicalId>/<region>/state.json`) with `parentStack` / `parentLogicalId` / `parentRegion` populated, recursively injects `DeletionPolicy: Retain` on every leaf resource (parent + every child template), and retires the whole tree via a single parent-side `DeleteStack` cascade. Children at every level are fetched in parallel. Per-child locks are acquired before each child write and released in reverse on success or failure. The root parent's state entry for each nested-stack row carries the synthesized cdkd-local ARN (matching what `NestedStackProvider.create` writes at deploy time — NOT the real AWS child stack ARN). CDK Stages (separate top-level stacks under one app) work fine.
  - **No CDK bootstrap version requirement.** cdkd uses its own S3 state bucket; the upstream "bootstrap v12+" caveat does not apply.

  `cdkd export <stack>` is the mirror of `cdkd import` in the reverse direction (cdkd → CloudFormation). It synthesizes the CDK app to get the template, reads cdkd state for `(logicalId, physicalId)` mappings, refuses if any template resource is in the never-importable set (`Custom::*` AND `AWS::CloudFormation::CustomResource` — the type CDK emits for `new cdk.CustomResource(...)` without `resourceType`; both are Lambda-backed Custom Resources that CFn cannot adopt) or has no entry in cdkd state. `AWS::CloudFormation::Stack` rows are fully supported as of issue [#464](https://github.com/go-to-k/cdkd/issues/464) PR B2: `buildImportPlan` routes each row into a dedicated `nestedStackRows: NestedStackRow[]` list, the orchestrator invokes `buildCdkdStateStackTree(rootStackName, region, stateBackend)` to recursively load every child state file from `cdkd/<parent>~<childLogicalId>/<region>/state.json` (failing fast on a torn tree), and `runPerStackImportLoop` submits **one CFn IMPORT changeset per cdkd-managed stack in the tree** in leaf-first order. Non-leaf parents adopt their just-imported children as nested references via the AWS-docs "Nest an existing stack" pattern (`DeletionPolicy: Retain` plus `ResourceIdentifier: { StackId: <child arn> }` plus a `TemplateURL` rewritten to point at the child's AWS-canonicalized template fetched via `GetTemplate(Processed)` post-IMPORT). Each child cdkd stack `<parent>~<childLogicalId>` becomes its own CFn stack named `<parent>-<childLogicalId>` by default via `cdkd2cfnStackName` (CFn rejects `~` in stack names); per-child overrides via `--cfn-child-stack-name '<cdkdName>=<cfnName>'` (repeatable). Per-child Parameters are extracted from the parent template's `AWS::CloudFormation::Stack.Properties.Parameters` block by `extractChildImportParameters` (literal string / number / boolean classification) and then intrinsic-resolved by `resolveChildImportParameters` — a root-first pre-pass (`buildResolvedParametersPerStack`, walking `flattenCdkdStateTreeRootFirst`) runs the deploy engine's `IntrinsicFunctionResolver` so `{Ref: <ParentParam>}` / `{Fn::GetAtt: [ParentResource, Attr]}` resolve against the parent's already-resolved Parameters + cdkd state BEFORE each child's standalone IMPORT (CFn's atomic nested create did this implicitly; cdkd's per-stack leaf-first loop must do it explicitly — which is why resolution is root-first while submission is leaf-first). Values the resolver cannot handle degrade to a `logger.warn` + the child template's `Default` (the pre-resolver behavior), so adding resolution never regresses a working export. The original "one atomic `--include-nested-stacks` IMPORT changeset" design was found infeasible by the 2026-05-24 AWS spike (AWS rejects that flag combination with `ValidationError: IncludeNestedStacks is not supported for changeSet type: IMPORT`) — see [design §4.0/§4.3](../../docs/design/464-nested-stacks-export-import.md) for the per-stack-loop redesign. The command resolves each non-nested-stack resource type's primary identifier property via `cloudformation:DescribeType` (with a hardcoded fallback table in `src/cli/commands/export.ts` for ~30 common types — covering S3 / IAM / Lambda / DynamoDB / SQS / SNS / Logs / EC2 / RDS / Events / API Gateway etc.). The SAME schema answers two more questions since issue [#1659](https://github.com/go-to-k/cdkd/issues/1659). **(a)** A type in `COMPOSITE_PHYSICAL_ID_IDENTIFIERS` — cdkd physicalId COMPOSITE, CFn `primaryIdentifier` a SINGLE field — is resolved from cdkd state's recorded `attributes` BEFORE the field-count branch, since the identifier is neither the physicalId nor a split of it: `TableARN` for `AWS::S3Tables::Table`, `DataSourceArn` / `ResolverArn` for the two `AWS::AppSync::*` children (a bare-ARN physicalId is accepted as the second stored shape, which `S3TablesProvider.importTable` records for a CC-routed table), each with an EMPTY `propertiesOverlay` because every one of those fields is `readOnlyProperties`. An unrecorded ARN BLOCKS the resource with a re-deploy-to-heal message rather than shipping the composite, and a `primaryIdentifier` that no longer matches the registered field refuses by name. `AWS::EC2::SecurityGroupIngress` is the fourth member: CFn identifies a rule by the `sgr-...` id AWS mints, which `EC2Provider` records as the `Id` attribute since issue [#1761](https://github.com/go-to-k/cdkd/issues/1761) (read off `AuthorizeSecurityGroupIngress`'s own response, with a best-effort paginated `DescribeSecurityGroupRules` on the idempotent already-exists arm and on the `--resource sgr-...` import path), and `recordedRuleIdIdentifier` resolves from it under the anchored `^sgr-[0-9a-f]+$` predicate. That entry was a pure REFUSAL until #1761 gave it a value to read. A row written by an OLDER cdkd carries no id at all, so issue [#1791](https://github.com/go-to-k/cdkd/issues/1791) adds a live-read BACKFILL reached only when the state-only resolve throws: a paginated `DescribeSecurityGroupRules` on the composite's `<groupId>` (throttle-retried, memoized per group for one `buildImportPlan` call) must match the `<ipProtocol>|<fromPort>|<toPort>` tuple EXACTLY ONCE — zero matches, more than one, or any MATCHING rule AWS reports without a usable `sgr-` id all REFUSE naming what was found, since cdkd's composite identifies a rule only by group + protocol + ports and adopting an ambiguous candidate would record the wrong rule. The `COMPOSITE_ID_SPLITTERS` family gained `AWS::S3Tables::Namespace` in the same change (`<tableBucketARN>|<namespaceName>` -> `[TableBucketARN, Namespace]`, whole-map overlay since the type declares no `readOnlyProperties`) — its absence aborted EVERY S3 Tables export, which made the `AWS::S3Tables::Table` half of (a) unreachable in practice — and `AWS::EC2::VPCCidrBlock` in issue [#1788](https://github.com/go-to-k/cdkd/issues/1788) (`<Id>|<VpcId>` -> `[Id, VpcId]`, overlay narrowed to `VpcId` since `Id` is `readOnlyProperties`; always Cloud-Control-routed, so the physicalId is the primaryIdentifier joined in schema order). That one's absence aborted every export of a VPC carrying a secondary IPv4 CIDR or an Amazon-provided IPv6 CIDR — including every CDK `Vpc` with `ipProtocol: IpProtocol.DUAL_STACK`. Both of its segments start with `vpc-`, but the association id carries the longer, distinct `vpc-cidr-assoc-` prefix, so the two ARE discriminable and the splitter shape-binds BOTH — the way the `AWS::EC2::EIP` entry binds `eipalloc-`, and for the reason that entry gives: validating one side only is not a discriminator. It also accepts the BARE `<Id>` form, recovering `VpcId` from the recorded properties, because CloudFormation reports this type's `PhysicalResourceId` as the association id alone (the shape a `--migrate-from-cloudformation` stack carries).. **(b)** `buildImportPlan` pre-flights types CFn cannot IMPORT at all and blocks EVERY offender in one pass, instead of deferring to a `CreateChangeSet` error that is measurably non-exhaustive (a 3-type probe named 2; a 2-type probe named 1). The verdict needs TWO agreeing fields — no `read` handler AND `ProvisioningType: NON_PROVISIONABLE` — so a partial DescribeType response, or the fallback identifier table, resolves to `unknown` and keeps the old defer-to-AWS behavior; it runs AFTER the `IMPORT_UNSUPPORTED_RECREATABLE_TYPES` branch, since `AWS::IAM::Policy` also lacks a `read` handler and has a real answer there. Because the verdict is a registry HEURISTIC and not AWS's published supported-for-import list, `--skip-import-support-preflight` bypasses it (the counterpart of the neighbouring set's `--no-recreate-import-unsupported`). **Ordering:** `buildImportPlan` and the `blocked` hard-fail now run BEFORE `acquireLock` on the single-stack path — planning performs no AWS write, and the nested path (`runPerStackImportLoop`) had always planned before taking its per-child locks, so the two agree; a stack that cannot be exported no longer locks out a concurrent `cdkd deploy` first. The command then acquires the stack lock, confirms with the user, preprocesses the phase-1 template (strip Outputs; inject `DeletionPolicy: Delete` on resources missing the attribute — matches the CFn type-default for resources without explicit `RemovalPolicy`; overlay each resource's `ResourceIdentifier` onto its `Properties` so CFn IMPORT's identifier-match check passes against cdkd's stack-name-prefixed physical ids — `overlayResourceIdentifierOnProperties`, whose four-way classification of the value the template currently carries is issue [#1787](https://github.com/go-to-k/cdkd/issues/1787): an ABSENT key and a top-level INTRINSIC are left alone (the latter resolves during changeset processing to exactly this resource's identifier, so clobbering it would only dirty the post-export `cdk diff` — issue #319), any LITERAL is overwritten with the scalar identifier (widened past `typeof === 'string'`, because the overlay value comes from the cdkd-recorded physicalId and is the authority on what the resource IS, while the template side is only what CDK happened to synthesize — an `addPropertyOverride('Namespace', ['analytics'])` array used to survive into the phase-1 template and draw an opaque `CreateChangeSet` rejection), and a list carrying an intrinsic / a nested list / an empty list is REFUSED naming the resource, the property and the scalar to declare — preserving any of them reproduces that rejection, while what makes overwriting wrong differs per shape, so the message says which: only a list that actually carries an object element has an intrinsic to discard, an empty one has no value to reconcile, and a nested one simply is not representable as the declared scalar), then issues `CreateChangeSet --change-set-type IMPORT` → wait → `ExecuteChangeSet` → `waitUntilStackImportComplete`, and finally deletes cdkd state for the migrated stack. AWS resources are unchanged across the migration; the stack is then managed by `cdk deploy` / `aws cloudformation`. **Context preservation guard**: refuses by default if CLI `-c key=value` overrides are supplied, because those values are not persisted to `cdk.json` / `cdk.context.json` and a subsequent `cdk deploy` without the same `-c` flags would synthesize a different template (drift / replacement on first post-migration deploy). User moves the values to `cdk.json`'s `context: {}` field (recommended) or passes `--accept-transient-context` to opt in to the risk. On success, prints the exact `cdk diff` / `cdk deploy` command including any captured `-c` flags. MVP scope: JSON and YAML templates supported (via the CFn-aware codec at [src/cli/yaml-cfn.ts](../../src/cli/yaml-cfn.ts) — see the YAML support bullet for details); all-or-nothing (if any resource cannot be imported, the whole command aborts — destroy or accept abandoning those resources first), inline `TemplateBody` only (51,200-byte cap), synth template used verbatim (no `observedProperties` substitution). Caveats: (1) **replacement risk on next `cdk deploy`** if the CDK code does not specify explicit physical names (`bucketName: 'my-bucket-12345'`) — same long-standing UX as upstream `cdk import`; users should set explicit names before exporting or inspect the post-import changeset before executing. (2) **cross-stack `Fn::GetStackOutput` consumers** in other cdkd stacks keep resolving the exported stack's outputs via the CloudFormation fallback (issue [#1697](https://github.com/go-to-k/cdkd/issues/1697) — the resolver reads CFn `DescribeStacks` outputs after the cdkd-state miss; weak reference), so the pre-#1697 leaf-first ordering constraint applies only to consumers deployed with `--no-cfn-fallback`. Implementation in `src/cli/commands/export.ts`.
  `state` is a parent command for inspecting and manipulating cdkd's S3 state bucket: `state info` prints bucket name, region (auto-detected via `GetBucketLocation`), the source that resolved the bucket (`cli-flag` / `env` / `cdk.json` / `default` / `default-legacy`), the schema version, and a stack count (with `--json` for tooling); `state list` (alias `ls`) lists deployed stacks (one row per `(stackName, region)` pair under the new region-prefixed key layout; `--tree` (issue [#555](https://github.com/go-to-k/cdkd/issues/555) A3) loads each state record to read the v6 `parentStack` / `parentRegion` fields and renders a `tree(1)`-style parent → child hierarchy via [src/cli/commands/state-list-tree.ts](../../src/cli/commands/state-list-tree.ts) — flat default is preserved for backward compatibility with scripts that grep the existing one-row-per-stack output, and `--tree --json` emits the nested JSON shape for tooling; orphan children whose parent record is missing surface at root level rather than vanishing); `state resources <stack>` and `state show <stack>` accept `--stack-region <region>` to disambiguate when the same stackName has state in multiple regions; `state show <stack> --show-nested` (issue [#555](https://github.com/go-to-k/cdkd/issues/555) A4) reuses `buildCdkdStateStackTree` (from `src/cli/commands/export.ts`) to recursively walk every `AWS::CloudFormation::Stack` row in the target's state and append each child's full state block after the parent's (DFS order, flat at column 0 with `Nested stack: <name>` headers; `--show-nested --json` emits the recursive `{state, lock, children: [...]}` shape with `children` always present even on leaves so consumers see a stable key set); default (no `--show-nested`) preserves the existing single-stack `{state, lock}` JSON shape verbatim for backward compatibility with tooling consumers; `state orphan <stack>...` removes cdkd's state record for every region by default, or scopes to one with `--stack-region <region>` (does NOT delete AWS resources — name mirrors aws-cdk-cli's new `cdk orphan`); `cdkd orphan <constructPath>...` is the synth-driven, **per-resource** counterpart (mirrors upstream `cdk orphan --unstable=orphan`) — it removes specific resources from a stack's state file by construct path (`MyStack/MyTable`), live-fetching every `Fn::GetAtt` it has to substitute via the resource's `provider.getAttribute()` (cached per `(orphan, attr)`) and rewriting every sibling `Ref` / `Fn::GetAtt` / `Fn::Sub` / `dependencies` reference so the next deploy doesn't try to re-create the orphan or fail on a stale reference. Path matching is **prefix-based** (matches upstream's behavior): the user's input matches every resource whose `aws:cdk:path` is exactly the input OR starts with `<input>/`, so an L2 path like `MyStack/MyConstruct/MyBucket` resolves to the synthesized L1 child `MyStack/MyConstruct/MyBucket/Resource`, and an L2 wrapper that contains multiple CFn resources orphans every child under it. The `aws:cdk:path` index in `src/cli/cdk-path.ts` excludes `AWS::CDK::Metadata` resources so the synthesized `<Stack>/CDKMetadata/Default` sentinel is never offered as an "available path" and cannot be orphaned; unresolvable references hard-fail with a one-shot list of every site, and `--force` falls back to the orphan's `state.attributes` cache (logging a per-case warning) before leaving the original intrinsic untouched if the cache also lacks the attr; `--dry-run` prints the rewrite audit table without acquiring a lock or saving state. The implementation lives in `src/analyzer/orphan-rewriter.ts` (the recursion structure mirrors `IntrinsicFunctionResolver` but in the inverse direction: only orphan references are substituted, every other intrinsic is left alone) and `src/cli/cdk-path.ts` (the shared `aws:cdk:path` index, also used by `cdkd import`). The pre-PR `cdkd orphan <stack>` whole-stack behavior is gone — the command hard-fails with a redirect message that points to `cdkd state orphan <stack>` instead of silently routing. `state destroy <stack>...` deletes AWS resources AND the state record without requiring the CDK app (the CDK-app-free counterpart to `cdkd destroy`). The per-stack destroy logic is hoisted into `src/cli/commands/destroy-runner.ts` and shared by both `cdkd destroy` and `cdkd state destroy`. As of [#555](https://github.com/go-to-k/cdkd/issues/555) A2, `state destroy` is ALSO the documented escape hatch for directly destroying a nested-stack child — `cdkd destroy <child>` is refused with `NestedStackChildDirectDestroyError` (matches CFn's "you can't directly destroy a nested stack" semantic; the parent's `AWS::CloudFormation::Stack` row would otherwise point at gone-from-AWS resources and the parent's next deploy would try to recreate them), but `cdkd state destroy <child>` intentionally bypasses the guard for users who accept leaving the parent's reference dangling. `state migrate` copies all state from the legacy region-suffixed default bucket (`cdkd-state-{accountId}-{region}`) to the new region-free default (`cdkd-state-{accountId}`); refuses to run while any stack has an active lock; verifies object-count parity before any source cleanup; source bucket is kept by default and only deleted with `--remove-legacy`. The bucket-name banner is no longer printed in routine command output (it includes the AWS account id, which would leak via screenshots / public CI logs); pass `--verbose` to surface it in debug logs, or use `state info` for an explicit on-demand answer.

- **src/cli/config-loader.ts** - Config resolution (cdk.json, env vars for `--app` and `--state-bucket`)
- **src/cli/stack-matcher.ts** - Shared stack-name matcher used by deploy/diff/destroy/list. Routes patterns by whether they contain `/` (display-path) or not (physical name) and returns a deduplicated union.

- **src/deployment/secret-redaction.ts** - Secret redaction for resolved dynamic references (GHSA fix). A LEAF module (imports nothing). **What counts as a secret is decided by the RESOLVER, and by TYPE rather than by spelling**: every `{{resolve:secretsmanager:...}}`, plus a `{{resolve:ssm:...}}` whose parameter turns out to be a `SecureString` (issue [#1901](https://github.com/go-to-k/cdkd/issues/1901) — the plain `ssm` form resolves with `WithDecryption`, so it yields a real secret for that type while a `String` / `StringList` parameter is public config and stays RESOLVED in state, or every parameter-backed property would become a perpetual spurious UPDATE). Secret-ness for an ssm reference is therefore DISCOVERED, not spelled: `resolveSSMReference` reports it off the same `GetParameter` response that carries the value, and the resolver remembers the verdict per expression in this module's own `recordedSecretExpressions` store (issue [#1910](https://github.com/go-to-k/cdkd/issues/1910)), so the redaction path can read the same verdicts (process-global, and cleared by `resetAccountInfoCache`) so the cache-hit and `skipDynamicReferences` arms can act on it without a second lookup. That store is deliberately WIDER-lived than the resolved VALUES it used to be paired with: since issue [#1933](https://github.com/go-to-k/cdkd/issues/1933) `cachedDynamicReferences` lives on the RESOLVER INSTANCE (one per stack, each carrying its own region) rather than at module scope, so a cache hit can only ever be a value this stack resolved in this region — the key and the lifetime used to be narrower than the value they stood for, which resolved one region's secret into another region's resource and left a second stack's secrets map empty so `cdkd scrub --all` reported it clean. The verdict store keeping the wider lifetime is safe in the one direction that matters (a verdict inherited across regions can only make a reference be treated AS a secret), and each cache entry additionally carries the verdict that produced it, so another stack's resolver RETRACTING the memo cannot stop this one redacting its own region's secret. The other half of the same outcome — the lookups running through the process-ambient `getAwsClients()` singleton, which `cdkd deploy` re-pins per stack (correct when serial) but the default `--stack-concurrency 4` races for, and which `cdkd scrub` / `drift` / `import` never re-pin at all — was issue [#1957](https://github.com/go-to-k/cdkd/issues/1957) and is closed by the resolver's `clientsForRegion`, which builds region-pinned clients (`AwsClients.withRegion`, carrying the ambient profile / credentials and overriding only the region) unless the ambient clients are PROVEN to already point at the resolver's region. The direction of that test is the correctness argument: "unknown" means SCOPE, not skip, because the case where the region is knowable only from `~/.aws/config` is what `aws configure` produces and failing open there left the disclosure reachable. PROVEN means the ambient's region is EXPLICITLY CONFIGURED (`AwsClients.configuredRegion`); an unconfigured ambient is never taken as a match, however its region might be guessed. Asking one client is not a weaker proof, it is the wrong question: `clientOptions` omits `region` wholesale when unset and the service getters are LAZY, so an unconfigured `AwsClients` is a bag of DEFERRED constructions, each memoizing its own region at its own instant while `deploy.ts`'s `switchRegion` keeps mutating `AWS_REGION`. Its `ssm` can pin one region and its `secretsManager` another, so no single member can answer for the bag — which is why an earlier attempt to settle it by asking the SDK (`config.region()`) was removed rather than refined. A template-derived region (`Fn::GetAZs`) is additionally gated by `isClientSafeRegion` before it can select an endpoint. On the diff / no-op path the type lookup passes `WithDecryption: false`, so a `SecureString` comes back as its encrypted blob — never substituted, never cached — and the comparison stays expression-vs-expression. Owns `RecordedSecretValues` (a `Map<plaintextValue, {{resolve:...}}expression>` the resolver populates during a resolution pass), `redactSecretsForState(bag, secrets)` (deep-clone replacing each secret value — whole-value or embedded `Fn::Join` / `Fn::Sub` substring — with its unresolved expression; identity return when no secrets), `scrubResourceRecord(record, secrets)` (redacts one `ResourceState`'s `properties` / `attributes` / `observedProperties`, shared by the deploy save choke point and `cdkd scrub`), and `maskSecretsInText(text, secrets)` (replaces a secret value with `***` for log / error output) plus its object-level twin `maskSecretsInError(error, secrets)` (issue [#2038](https://github.com/go-to-k/cdkd/issues/2038)) — a CLONE of EVERY link in the error's `cause` CHAIN, each carrying its own masked `message`, needed because `formatError` renders a `CdkdError`'s CAUSE as `Caused by: <cause.message>` and `handleError` logs that at `error` level, so that sink reads the error OBJECT and no amount of masking at the string sites can close it. **The CHAIN, not just the top link**, and the review round that forced that is the interesting part: a provider wrapping an AWS failure in a generic sentence (`new Error('the call failed', { cause: awsError })`) leaves the plaintext ONE link down, where a top-level-only mask hits its identity-return, reports "nothing to mask" and hands back an object still carrying it — the contract says the returned error is safe to render, and `formatError` walking a single level is an implementation detail one edit away from re-opening the hole. The identity-return therefore means "nothing ANYWHERE in the chain changed". Each link's clone copies the prototype and every own property DESCRIPTOR (symbols included) so `markNonRetryable`'s non-enumerable marker, `$metadata` / `Code` and `name` survive for `isMarkedNonRetryable` / `isThrottlingError` / `isTransientServerError` / `extractDeploymentEventError` (`Object.assign` would have dropped the marker, which is why the descriptors form is used); `message` and `cause` are the two descriptors deliberately NOT copied through, since both are re-defined per link and copying a NON-CONFIGURABLE original would make that re-definition throw. `cause` is rewired to the CLONE of whatever it pointed at in a SECOND pass over the already-built clone map, which is what makes a CYCLIC chain (`a.cause = b; b.cause = a`) terminate — the walk additionally carries a visited-set and a depth cap (`ERROR_CAUSE_MASK_MAX_DEPTH` 20, the bounded-walk shape `extractDeploymentEventError` and the retry classifiers already use), and a link beyond the cap keeps its original unmasked message. A `cause` that is not an `Error` keeps its original descriptor verbatim. `extractDeploymentEventError` needs no change of its own: it copies only the TOP link's `message` and walks the chain solely for `$metadata.requestId` / `Code`, neither of which is caller-supplied. **Redaction is BOTH path-based and value-based, and the split is load-bearing** (issues [#1904](https://github.com/go-to-k/cdkd/issues/1904) / [#1900](https://github.com/go-to-k/cdkd/issues/1900)). `redactSecretsForState(bag, secrets, source?)` takes an optional SOURCE bag still carrying the unresolved expressions; wherever the source leaf is a `{{resolve:...}}` string, that string is persisted VERBATIM. Position is what the value map structurally cannot supply: keyed by the plaintext, two expressions resolving to the SAME value collapse (last write wins) and every site is rewritten to the survivor, so state holds an expression the template lacks at that leaf and the stack takes a permanent spurious UPDATE (#1904). Re-keying does not help -- a secret embedded in a joined string is only findable by VALUE -- so the value scan stays for every leaf the source cannot position (a diverged shape, a key the source lacks, a leaf that merely EMBEDS a secret inside surrounding text). An intrinsic OBJECT source (`Fn::Join` / `Fn::Sub`) was in that list until issue [#1916](https://github.com/go-to-k/cdkd/issues/1916), and it was the DOMINANT CDK shape rather than an edge case: `secret.secretValueFromJson(...)` renders the secret's ARN as a `Ref`, so every L2-reached secret is a join and the whole position pass missed it, leaving a colliding pair to collapse exactly as before #1904 (measured against real AWS: the unstaged leaf persisted the `:AWSCURRENT` sibling's spelling). `positionByIntrinsicSkeleton` closes it by SHAPE — the intrinsic's literal parts are escaped and its non-literal parts wildcarded into an anchored pattern (`[^}]*`, so a wildcard cannot cross a token terminator), then matched against the recorded secret expressions. It persists a match only when THREE conditions hold, each removing a different way of being wrong: the bag leaf's WHOLE value is a recorded secret plaintext (an embedded secret is not this shape and must keep going to the substring scan), EXACTLY ONE candidate matches (two means the skeleton genuinely cannot separate them, and guessing would be the collapse this fix removes one step over), and the match is not DEMONSTRABLY another value's expression per the pass's own map (the fence against a bag/source misalignment). Every refusal degrades to the value scan, i.e. to the pre-#1916 behavior, so no case gets worse. There is deliberately NO `isKnownSecretExpression` test on this arm, unlike the plain-string one: that arm's candidate is arbitrary TEMPLATE text and can be a public ssm reference, while these candidates come only from stores the resolver populates on a proven-secret verdict, so the test could never answer `false` and an unfalsifiable guard fences nothing. **Which source leaves may be persisted is gated by PROVENANCE, via `PathSourceRules`, and all THREE of its rules are load-bearing.** `descendArrays` follows the BAG's provenance: a bag produced BY resolving the source (`TEMPLATE_DERIVED_RULES` / `STATE_DERIVED_RULES`) is walked POSITIONALLY, which is sound only because resolution preserves structure, while an AWS readback may be REORDERED — AWS does not preserve list order (the reason `drift-normalize.ts` exists) and positional descent would write an expression onto the WRONG element while leaving the real secret in plaintext. A readback array is not given up on, though: since issue [#1915](https://github.com/go-to-k/cdkd/issues/1915) every kind FIRST tries a KEYED descent that pairs elements by an identity field (`Name` / `Key` — the shape `canonicalizeTagListsDeep` already keys on) with uniqueness required on BOTH sides, so pairing is by string equality and cannot mis-align; a key that is not really an identity fails the uniqueness test and refuses the whole array rather than producing a plausible wrong pairing, and an unpaired element falls to the value scan. That is what reaches a secret nested in an ECS `ContainerDefinitions[].Environment[]` on the UNCHANGED-resource path, where the value scan additionally has no needles because the resource was never resolved this deploy (#1900). It answers the reordering objection on its own terms rather than overriding it: the objection is ORDER, and a key does not depend on order. Keyed runs BEFORE positional, and an element it does not pair takes its POSITIONAL partner when positional would have been exact for the whole array (`descendArrays`, equal lengths, every pairing at its own index) — the invariant being that keying must never pre-empt a descent that would have been exact, since an unpaired leaf on the value scan takes a colliding SIBLING's expression. Two well-keyed lists can also carry DISJOINT identities, and that case falls through to positional by the same rule. Keyed is preferred because `descendArrays` rests on an assumption the module states but cannot enforce — every `effectiveProperties` producer TODAY preserves length and order — so a provider that reorders an equal-length `Tags[]` would satisfy the length check and mis-pair by index while the pairing that cannot mis-align sits one branch away. Two shapes are deliberately out of reach and fail closed: an array whose IDENTITY FIELD itself holds a secret (the two sides are known to differ, so pairing would be the guessing the uniqueness rule forbids), and an array of ARRAYS (the outer elements carry no identity field). `trustAnyExpression` follows the SOURCE's: a template carries PUBLIC ssm expressions too, and persisting one would keep a `String` / `StringList` parameter as an expression in state and re-introduce the perpetual UPDATE #1901 exists to prevent, so from a TEMPLATE source a leaf is substituted only when it is a KNOWN secret — `{{resolve:secretsmanager:` by definition, or an expression the resolver recorded (the ssm `SecureString` case) — while a STATE source holds no public expressions and is trusted wholesale. The definitional arm is what makes the fix work at all — when two expressions share a resolved value the map keeps only the last, so asking it about the LOSING expression answers 'no' for exactly the pair being separated. `sourceIsSameGeneration` (issue [#1917](https://github.com/go-to-k/cdkd/issues/1917) and its review) answers whether the SOURCE describes the same GENERATION of the resource that the BAG does, and it exists for one shape: a bag leaf that is ALREADY a complete `{{resolve:...}}` token, which is either a previously-persisted expression or a secret whose plaintext merely LOOKS like one. It is TRUE for exactly the two STATE-sourced constants whose source is that record's own persisted bag — `STATE_DERIVED_RULES` (the replay resolved its bag FROM the journaled record one statement earlier) and `STATE_SOURCED_READBACK_RULES` (the #1900 observed walk projects from the very `properties` beside it). Every TEMPLATE-sourced constant is FALSE, INCLUDING `TEMPLATE_DERIVED_RULES`, and that last one is the correction the review forced: `redactStateForPersist` walks EVERY record in the state map while `perResourceTemplateProps` is populated right after resolution and BEFORE the provider call, so a resource that merely ENTERED the create/update arm hands today's template to a record that is still the PREVIOUS generation — reachable through an intermediate `saveStateAfterResource`, the pre/post-rollback saves, and Ctrl-C. Keyed on the CALLER's intent that row claimed same-generation and rewrote a rolled-back `:AWSPREVIOUS` onto the template's `:AWSCURRENT`, so a rotation that failed and was reverted would read as applied, the next deploy would see NO_CHANGE, and drift could not see it either because the baseline was rewritten in the same walk. A refusal FALLS BACK to a WHOLE-VALUE redaction rather than returning the leaf untouched, and that is what lets the rule be set conservatively without giving up the disclosure fix: a token-shaped PLAINTEXT the pass resolved is a key of the value map and is still rewritten, while a previous generation's EXPRESSION is not a key and survives. Whole-value and not the full value scan — the scan's SUBSTRING arm would splice a short recorded secret value occurring inside the token's own text into the reference, corrupting a persisted expression; the same bound sits in `redactSecretsForState`'s walk for leaves reached with no source. Note the map is keyed by plaintext, so if two references share one token-shaped resolved value the refused leaf takes the SURVIVOR's expression (the #1910 class, not a disclosure). `secrets.has(bag)` is the wrong test for the same reason it always was — the hazard is GENERATION SKEW, which no value test can see. One constant exists solely because a caller can know something the derivation cannot: `STATE_SOURCED_CROSS_GENERATION_RULES`, which `cdkd scrub` threads into `scrubResourceRecord` for its `observedProperties` walk. Scrub repositions `properties` onto TODAY's template FIRST, so the "record's own properties" that walk falls back to have already moved a generation; it keeps `trustAnyExpression` (that source still holds no public expressions, which is what cleans a legacy PLAINTEXT baseline) but drops the generation claim, or the drift baseline would be rewritten onto a reference the stack may never have deployed and `cdkd drift --revert` would push it to AWS. **Every writer now passes a position source** (issue [#1910](https://github.com/go-to-k/cdkd/issues/1910), which closed the residue #1904 left): the four siblings the issue names — the rollback JOURNAL (`DeployEngine.redactOperationsForJournal`), the stack OUTPUTS (positioned by `DeployEngine.outputsTemplateSource`, the outputs' sibling of `perResourceTemplateProps`, consumed by all three outputs-redaction sites through one `redactOutputs` helper), `cdkd scrub`, and `cdkd import` — plus a FIFTH the issue did not list, `rollback-executor.ts`'s `redactRollbackRecord`, which writes state after re-resolving and is reachable only through a replay, and a SIXTH that sweep structurally could not see — `cdkd state refresh-observed` (`src/cli/commands/state.ts`), which passed no source because it reached this module along NO path at all, so a search for callers of `redactSecretsForState` never named it (issue [#1926](https://github.com/go-to-k/cdkd/issues/1926)). Its readback is the DECRYPTED value for any resource deployed from a secret reference, and it leaked SCALARS as well as arrays because there was no redaction rather than one that declined to descend. Its secrets map is EMPTY by construction (the command neither synthesizes nor resolves), so it is the #1900 shape: the PATH pass carries it alone, positioned against the record's own `properties` under `STATE_SOURCED_READBACK_RULES`, and it inherits #1915's keyed array descent rather than re-solving it. **The path pass certifies only a WHOLE-TOKEN source leaf**, which left the DOMINANT CDK shape leaking on every empty-map readback path — a MIXED leaf (`postgres://u:{{resolve:...}}@h`, an `Fn::Join` around `secretValueFromJson`) fell through to a value scan that has no needles. `refuseUncertifiedReadbackPositions` closes that row inside `redactSecretsForState`, so every caller on that path inherits it with no call-site change: `cdkd state refresh-observed` and — this is why it belongs in the module rather than in the command — a plain `cdkd deploy`, whose `drainObservedCaptures` baseline reaches the persist choke point with exactly the same empty-map / state-source configuration. `cdkd scrub` is NOT an inheritor: its observed walk passes `STATE_SOURCED_CROSS_GENERATION_RULES`, which the gate below excludes by design. It is gated on `trustAnyExpression && !descendArrays && sourceIsSameGeneration`, and the third conjunct took a measurement: without it the pass also selected `STATE_SOURCED_CROSS_GENERATION_RULES` and rewrote a `cdkd scrub` baseline holding the DEPLOYED `:AWSPREVIOUS` reference onto the template's edited `:AWSCURRENT` one — the #1917 hazard, which `--revert` applies to AWS. It refuses only what POSITION justifies (a leaf whose KEY the source carries, taking the record's own value at the record's own path) and descends per identity-keyed element so a mixed leaf inside a paired element is reached too. A MIXED leaf embedding a plain `{{resolve:ssm:` token splits on whether a SECRETS MAP exists, and the `secrets-dynamic-ref` integ is what forced that split after every unit assertion passed without it: with a map, a pass resolved this bag so absence from the verdict store is real evidence the parameter is PUBLIC and the resolved value is kept; with an EMPTY map (`cdkd state refresh-observed`, and the deploy's choke point for an UNCHANGED resource) nothing was resolved, nothing could have been recorded, and reading absence as "public" persisted a DECRYPTED SecureString. Failing closed there is the same premise the whole-token arm already acts on — a public `String` parameter is stored RESOLVED (#1901), so a token SURVIVING in a persisted state bag is a SecureString by construction — and the earlier revision's defect was applying a STRICTER rule to a mixed leaf than to a whole token on the identical source. The accepted price is that a genuinely public ssm mixed leaf is over-redacted on those paths (phantom drift, not a disclosure), tracked as issue [#2036](https://github.com/go-to-k/cdkd/issues/2036). FOUR residual rows remain, one root cause — no needle and no position, so nothing distinguishes a resolved secret from an ordinary literal: an array with no identity key, an element with none, an UNPAIRED element beside a paired one, and an observed KEY the source does not carry (issue [#2012](https://github.com/go-to-k/cdkd/issues/2012)). They are deliberately NOT closed by taking the source subtree: an earlier revision did, and the #1915 fences correctly rejected it — measured, it rewrote `{Name:'', Value:'an-unrelated-literal'}` onto the expression and turned an AWS-reported `[{Value:'x'}]` into `[{Name:'db', Value:<expr>}]`, fabricating drift-baseline content AWS never reported that `--revert` then pushes to the live resource. The journal is the consequential one: `resolveReplayProps` RE-RESOLVES it against AWS, so a leaf collapsed onto a sibling's expression ships the WRONG secret version to the live resource once two version stages diverge, rather than merely reporting a spurious change. Two sides of one op take DIFFERENT sources and must not be conflated — `properties` / `attemptedProperties` are this deploy's desired bags and take the TEMPLATE bag, while `previousState` was read back from STATE and positions itself via `scrubResourceRecord` with no source (the #1900 fallback). The ssm/ssm half is closed by the module-level `recordedSecretExpressions` SET (`recordSecretExpression` / `forgetSecretExpression` / `isRecordedSecretExpression` / `clearRecordedSecretExpressions`), which IS the resolver's SecureString verdict store — homed HERE rather than in the resolver so `isKnownSecretExpression` can consult it with no caller threading it, and reachable from the resolver along an import edge that already exists (the reverse would close a cycle, since this module is the LEAF). Since issue [#1916](https://github.com/go-to-k/cdkd/issues/1916) the set holds EVERY secret expression, not only the ssm ones: nothing has to ask it about a `secretsmanager` reference (spelling settles that), but it is ALSO the candidate list `positionByIntrinsicSkeleton` matches against, and a list holding only the ssm half cannot name the losing member of a collapsed secretsmanager/secretsmanager pair. Recording is gated on the SPELLING rather than on the resolver's `isSecret`, deliberately: an `ssm` reference whose `Type` came back unclassifiable is secret for THAT resolution but must stay unpinned so the next pass re-asks AWS (#1901), and recording it would pin it for the process — so such a pair still falls back to the value scan. The path pass ALSO runs with an EMPTY secrets map, which is the whole point for an UNCHANGED resource: it is never resolved during a deploy, so `perResourceSecrets` has no entry, and an observed-capture refresh echoing a secret would persist plaintext (#1900); `scrubResourceRecord` therefore redacts `observedProperties` against the record's OWN already-redacted `properties` when no template bag was supplied. The source bag is captured by `DeployEngine.perResourceTemplateProps` at the two sites that already populate `perResourceSecrets`, so nothing new is threaded through the resolver. Over-redaction on the value path is harmless and the safe direction. - **src/cli/commands/scrub.ts** - `cdkd scrub [STACK...]` — the permanent STATE SECRET-HYGIENE command (clean + audit), not incident-only tooling (issue [#1902](https://github.com/go-to-k/cdkd/issues/1902) reframed it as such; it shipped as GHSA remediation). That closes the population the command is DOCUMENTED as the remedy for and could not remedy: an output DELETED from the template contributes nothing to `outputSecrets`, so the needle sitting in `perResourceSecrets` never reached `state.outputs` and the plaintext survived a scrub that REPORTED SUCCESS — the same record `cdkd diff` correctly withholds from display (issue [#1948](https://github.com/go-to-k/cdkd/issues/1948)), whose own refusal is unchanged since it still cannot decide the question from a stored string alone. The repaired population is WIDER than that motivating case, and honestly so: a parameterized `Export.Name` (scrub has only template defaults) leaves the deploy's real alias key unaccounted on EVERY run, so those keys take cross-resource value matching as a standing condition rather than as a one-off after a refactor. TWO refusals bound the widening, both because `state.outputs` is re-applied VERBATIM to CONSUMER stacks — by `src/state/export-index-store.ts` and by `Fn::ImportValue` / `Fn::GetStackOutput` in `intrinsic-function-resolver.ts` — so a FABRICATED redaction ships a literal `{{resolve:...}}` token into a consumer's own AWS call (the #1934 class; note `cdkd drift` is NOT such a reader — it reads `state.resources` — and an earlier revision of this entry cited it): nothing is rewritten unless its value genuinely MATCHES a recorded plaintext, so an unrecoverable needle (secret deleted, rotated away, reference gone from the template too) leaves the value untouched and invents / removes no key — delivered by NO single guard, measured rather than assumed: `scrubStack`'s `totalSecrets === 0` early return, `redactUnaccountedOutputs`'s own empty-map guard, and an empty secrets map making every scan the identity are three REDUNDANT reasons, so deleting any one leaves the record byte-identical and none of them may be cited as the fence (the empty-map guard is also reachable in its own right — `totalSecrets` counts the RAW maps while the union is filtered to `MIN_NEEDLE_LENGTH`, so a stack whose every recorded plaintext is sub-floor walks past the early return and arrives with an empty union); and an ACCOUNTED key is never scanned against the union, or a resource's secret value would rewrite a declared output's coinciding literal into that resource's expression. Stated residual: a DECLARED output whose template value no longer resolves a secret but whose STORED value is still a stale plaintext is not repaired either — a redeploy rewrites it. Flags: `--all`, `--dry-run`, `--fail` (exit 1 if plaintext found: with `--dry-run` any of it, and on a real run the part scrub cannot rewrite — CI gate). Exit codes: 0 clean, 1 (`--dry-run --fail` found plaintext, or a REAL run found a leak scrub cannot rewrite — a secret-bearing state KEY, issue [#1919](https://github.com/go-to-k/cdkd/issues/1919)), 2 error. Scrubbing does NOT un-expose an already-leaked secret — a value ever stored in plaintext must be ROTATED in Secrets Manager.

- **src/cli/commands/drift.ts** - `cdkd drift [<stack>...]` implementation. State-driven (no synth). Reads cdkd state from S3, asks each provider's optional `readCurrentState` for the AWS-current snapshot, and pipes the result through `src/analyzer/drift-calculator.ts`. **Secret dynamic references are reconciled here, and this file is where all three of the command's modes met the GHSA-p5qg-v9gv-hc7w redaction** (issue [#1914](https://github.com/go-to-k/cdkd/issues/1914)): the baseline holds unresolved `{{resolve:...}}` expressions while the readback holds the resolved plaintext, so `resolveStateSecretExpressions` (the synth-free counterpart of `rollback-executor.ts`'s `resolveReplayProps`) re-resolves the baseline for COMPARISON ONLY, and again inside `runRevert` before `provider.update` — replaying the literal token there set the live property to the expression string. The resolved baseline no longer trips `calculateResourceDrift`'s `{{resolve:` skip (PR #1899), so a console edit of a secret-bearing property is detectable and revertible again; that skip is now the FALLBACK for a reference cdkd cannot resolve at all. **Redaction is keyed on the PATH as well as on the value, and the path half is what a value-keyed map structurally cannot supply.** The resolution records both a per-resource `RecordedSecretValues` and the set of PATHS that produced one, and `redactDriftChanges` rewrites each side of every `PropertyDrift` as the outcome is BUILT — the one choke point behind the human report, the `--json` payload, both plans, and the value `--accept` persists. The value pass puts a recorded plaintext back on its own expression; the path pass then answers the case the map cannot, because the map holds what the reference resolves to TODAY: after a Secrets Manager ROTATION the deployed resource still carries the previous version, so the path drifts and the AWS side matches no key — a real secret that would otherwise be printed verbatim and persisted. At a known-secret path the only value ever shown is the expression itself; anything else becomes `SECRET_MASK`, `undefined` / `null` excepted (an absent key discloses nothing). `change.path` is masked too, since `redactSecretsForState` walks values and never object KEYS, and a masked path also marks the change secret-bearing. `runAccept` then REFUSES any path whose value came back masked, with a warning naming it: writing `***` would corrupt the baseline and make the next deploy push the literal mask at AWS. The refusal is per-PATH, so the non-secret drifts in the same resource are still accepted. **`runAccept` also redacts the bag it persists**, positioned against the record's own `properties` with `STATE_SOURCED_READBACK_RULES`, and that is NOT a duplicate of the change-level pass: what it reaches is the untouched clone of the record's baseline, which is exactly where a plaintext survives for any user who ran `--accept` on a pre-fix binary — and the positioned form is what names a stored plaintext that a rotation has since made unrecognisable to the map. Its old pinning hazard (rewriting an accepted console edit back to the expression) is gone because such a path is now refused before it can reach the bag. The revert's own narrowing write (#1644) is positioned against the bag the revert RESOLVED (`observedProperties ?? properties`) rather than against `properties`, with `STATE_SOURCED_READBACK_RULES` and NOT the rollback executor's `STATE_DERIVED_RULES`: the delta descends from `buildRevertNewProperties`'s merge of the AWS-CURRENT snapshot with the resolved desired subtrees, so a non-drifted top-level key comes from AWS and may be reordered, and positional array descent would write a sibling's expression onto the wrong element. **Every failure mode of the new lookups is per-resource, never fatal.** A deleted secret, a rotated-away version, or a least-privilege role without `secretsmanager:GetSecretValue` / `ssm:GetParameter` warns and falls back to the unresolved baseline for that one resource; `--revert` reports it as a per-resource failure with its own message instead of `AWS update failed`. **An ABSENT `awsValue` at the EXACT leaf known to hold a secret is DROPPED, not reported** (`secretPaths.has(path)`, not the ancestor-matching `isSecretBearingPath` — a whole subtree vanishing from AWS is real drift the user wants, and pre-#1899 it was reported because that skip only ever covered leaf strings; an absence that survives the drop is instead added to `maskedPaths`, so it is reported AND refused by `--accept`, which would otherwise delete the key and the reference with it): a write-only credential is returned by no readback, and PR #1899's `{{resolve:` skip used to cover exactly that — it stopped covering it precisely because this PR makes the baseline arrive RESOLVED. Reporting it instead is three bugs (permanent exit 1; `--accept` writing `undefined`, which `setAtPath` turns into a DELETED key, erasing the reference out of `properties`; and `--revert` re-pushing the credential every run), and the drop is scoped to `positionIsSecret` rather than to `secretBearing` so a key whose NAME carries a secret is still reported and still refused. `redactDriftChanges` therefore runs BEFORE the clean/drifted decision, since it can empty the change list. A SURVIVING `{{resolve:...}}` token (the resolver's unsupported-service arm warns and returns the literal; `ssm-secure:` is the live spelling) marks its path secret-bearing — but ONLY for a spelling that is secret by definition (`isSecretBySpelling`: CloudFormation defines exactly three services and cdkd resolves the other two), since masking text that merely looks like a reference leaves a path refused by `--accept` and pinned by the revert with no remedy. **`preserveLiveValuesAtUnresolvedTokens` REGISTERS the live values it copies in** (`plaintext -> token`), under three conditions that each remove a different way of being wrong — the leaf must be a WHOLE token (a mixed leaf's send string is already partially resolved, so registering it whole writes the resolvable half's plaintext into state), the spelling must be secret by definition (registering a look-alike's live value makes a needle out of ordinary data), and the live value must clear the needle floor (`redactSecretsForState`'s whole-value branch matches at ANY length, so a live `"1"` would rewrite every unrelated delta leaf equal to it into the token — the #1904 corruption). Preservation itself is gated on the leaf being a WHOLE token, and that gate is a DISCLOSURE boundary rather than tidiness: copying a live value into a MIXED leaf would move the `ssm-secure` plaintext into the payload while the registration guards correctly decline to register it, so the mechanism would CREATE an exposure it cannot mask (unmaskable in the narrowing delta, the retry log and the AWS error text alike). Declining to preserve there restores the pre-#1914 behaviour for that narrow shape — the literal ships, which is what `cdkd deploy` does. **The residual that remains is not created by this command's own bags**: a provider can echo its own readback in `effectiveProperties`, and the #1644 narrowing persists it with no map entry to match; that write previously had no redaction at all, and closing it needs span-masking (issue #1935). A non-string live value is neither registered nor positionable and is a stated residual before the update call, the narrowing redaction and the error masking: `secrets` is empty by construction there — nothing was recorded, which is what made the token a survivor — so moving the plaintext without registering it handed it to three readers that would each have masked it, and an array-nested one (ECS `ContainerDefinitions[].Environment[]`) reached neither the `descendArrays: false` position pass nor the empty value scan and landed in `state.json`. The general rule: a mechanism that deliberately moves plaintext into a bag must also register that plaintext with everything that masks. Such a token is reported and is reported through the pass's `onUnresolved` hook, and is deliberately NOT a failure — failing would abandon every other drifted property on the resource and exit 2. **The `ssm-secure` path is the one place where "the token is already what AWS holds" is FALSE**, and both halves of that matter: CloudFormation resolves `ssm-secure` SERVER-side, so a record adopted by `cdkd import --migrate-from-cloudformation` carries the literal in state while AWS holds the PLAINTEXT. So the path must be masked (`secretPaths.add` on the survivor, exact because `ssm-secure` is secret by spelling — `diffAt` never descends arrays, so an ECS `Secrets[]` drift otherwise reports the whole array with the plaintext in it), and `preserveLiveValuesAtUnresolvedTokens` must run before `provider.update` so the revert leaves the live value at those positions untouched instead of overwriting a working secret with a literal. Deciding by what AWS HOLDS rather than by provenance needs no state flag and is exact in both directions: a cdkd-deployed record has the token live, so copying it back is the same no-op; a migrated one has the resolved value, which survives. Where AWS has nothing at that position the token is kept, since that is what `cdkd deploy` sends. `survivingDynamicReferences` scans with `[^}]+` to agree with the RESOLVER's own pattern (a `{` inside a token separates them) and reports only tokens present in the INPUT, since the scan runs over the RESOLVED string and a secret can contain reference-shaped text. It used to be the ONLY one of cdkd's four spellings that agreed with the resolver, and this entry recorded the split with `isWholeDynamicReference` as a deliberate OPPOSITE agreement — issue [#1936](https://github.com/go-to-k/cdkd/issues/1936) measured that claim and found it wrong in the consequential direction: the questions the two predicates answer do differ, the CHARACTER CLASS does not, and the strict sibling's `[^{}]*` PERSISTED PLAINTEXT for a reference whose inner text contains a `{` (a Secrets Manager JSON key, e.g. `{{resolve:secretsmanager:app/db:SecretString:my{key}}`) — the resolver resolved it, the source arm then refused it as not-a-single-token, and on the #1900 empty-map path the resolved value was stored verbatim. All four now derive from ONE exported constant in `secret-redaction.ts` (`DYNAMIC_REFERENCE_INNER`, byte-identical to the resolver's own `([^}]+)` capture), and `isWholeDynamicReference` is that module's `isSingleDynamicReferenceToken` imported under this file's local name rather than a hand-copied twin. `survivingDynamicReferences` imports the ASSEMBLED scan (`dynamicReferenceTokens`) rather than rebuilding one from the shared class, because sharing only the class is how the four spellings started: the flags and anchors around it are as forkable as the class itself, and the re-fork is behaviourally identical, so nothing but a fence would notice. That fence states the good condition POSITIVELY — a regex matching a `{{resolve:` token must escape both braces, and only `intrinsic-function-resolver.ts` (once, the authority) and `secret-redaction.ts` (twice) may write one, ZERO anywhere else under `src/**` — after three rounds of enumerating bad spellings each let a fourth through. The report names only the TOKENS, never the leaf that held them, because `resolveDynamicReferences` substitutes token by token and a mixed `secretsmanager` + `ssm-secure` leaf comes back carrying real plaintext. For the same reason the detection failure arm masks its message BEFORE clearing the value map, which is why the clear sits after the log. Every AWS error string a revert prints is run through `maskSecretsInText` — the payload carried resolved secrets and AWS quotes the offending value, the same fence `deploy-engine.ts` applies to its own provider calls. **The path answer survives a failed lookup**: `collectDynamicReferencePaths` seeds a SECOND path set offline from where the `{{resolve:` strings simply are, and the report uses the PROVEN set when resolution succeeded and that seed when it did not. Without it the composition of the two failure modes leaks — the comparator's `{{resolve:` skip only re-arms for a LEAF whose state side is a string, so a resource whose `observedProperties` lack the secret's parent drifts at the ANCESTOR with the whole AWS subtree as `awsValue`. The seed is coarser (it cannot tell a public ssm reference from a secret one) and therefore over-masks, which is the direction to err in. **`--accept` refuses two ways**, through one `acceptRefusalReason` predicate shared with `printAcceptPlan` so a `--dry-run` cannot promise a write the run refuses: a masked VALUE, and a masked PATH (a readback keyed BY a secret — `setAtPath` would otherwise invent a key literally named `***`, and with an `undefined` value INSERT it rather than removing the real one). The path check is what makes `redactDriftValue`'s `undefined` / `null` / whole-expression exemptions safe. The refusal is keyed on a `maskedPaths` SET carried on the outcome rather than on comparing a value to `SECRET_MASK`, so a property whose real value is the string `***` at an ordinary path is not refused forever — and a masked path is not detectable from the value at all. The same set tells `runRevert` which subtrees `buildRevertNewProperties` cannot overlay (its key is the path's TOP-LEVEL segment, which a mask makes unmatchable), so the user is told rather than silently not reverted; the accept refusal for that case names ROTATION as the remedy, since a plaintext that leaked into a property NAME is unremovable by any pass — they all walk values. `--accept` also CHECKS each accepted value after the redaction pass and warns when it was overwritten: a PUBLIC `{{resolve:ssm:...}}` can sit in `properties` via the `cdkd import` warn path, and `trustAnyExpression` then wins over the accepted value, which would otherwise be a silent permanent no-op. A revert that could not re-resolve is counted apart from an AWS update failure (it never reached `provider.update`), and the provider lookup + payload build are inside per-resource guards — pre-existing gaps where one unroutable resource aborted the whole run. `carriesRecordedSecret`'s substring branch carries the same 4-character needle floor `secret-redaction.ts` applies when building needles (copied, since that constant is module-private), so it errs toward NOT marking: a sub-threshold plaintext is one the redactor would not substitute anyway, and marking it would mask a PUBLIC reference that merely contains those characters. Auto-selects the single stack in state when no positional arg / `--all` is given (mirrors `cdkd deploy` / `cdkd destroy`); errors with a listing when state has more than one stack. Exits 0 on no drift, 1 on drift detected, 2 on error. `--accept` (state <- AWS) and `--revert` (AWS <- state) both ship; `buildRevertNewProperties` overlays each drifted top-level subtree from the baseline onto the AWS-current snapshot, EXCEPT the AWS-SERVICE-authored entries of a top-level TAG LIST (`mergeTagListForRevert`, issue #1501 — an ordinary console-added tag is still STRIPPED, but `AmazonECSManaged` / any `aws:`-prefixed key survives; gated on a top-level property NAMED `Tags`/`*Tags` rather than on the `[{Key,Value}]` shape alone, which `LoadBalancerAttributes` also matches, and applying even to an EMPTY recorded baseline, because ECS requires the former for managed scaling and AWS reserves the latter; `findRevertPreservedTagKeys` names them in the plan before the confirmation prompt. This is the issue's option 2: option 1 — diffing the WHOLE tag list — was implemented first and FAILED the `drift-revert` integ, whose fixture requires --revert to strip an injected tag). `buildRevertNewProperties`'s `preserveUntemplated` option (issue #1626 items 2 + 3) settles what "absent from desired" MEANS on this caller: the deploy engine passes the last-deployed TEMPLATE as `previousProperties`, so an absence is a template removal, while `runRevert` passes the full `readCurrentState` snapshot, so it ALSO covers a never-templated path — and both provider shapes then destroy it, by different routes (one that KEY-DIFFS a collection reads the absence as a REMOVAL — ELBv2's `LoadBalancerAttributes` carries ~20 AWS-reported keys against a template declaring one or two; one that REPLACES a bag wholesale, e.g. the documented full-replace `PutBucketTagging`, never consults the previous side at all and simply sends a bag the path is missing from). So when the reverted resource has NO `observedProperties` — the baseline is the raw template, where an AWS-authored value and an out-of-band change are indistinguishable — `mergeUntemplatedValue` merges every untemplated path into the bag cdkd SENDS; with `observedProperties` present the baseline IS a deploy-time snapshot, an absence is genuinely an out-of-band addition, and the wholesale overlay is unchanged (which is what the `drift-revert` integ's injected-tag assertion depends on). The fix is on the DESIRED side rather than trimming `previousProperties` precisely because trimming stops the key-diffing removal but leaves the wholesale-replace drop untouched — half the reported paths would still be erased while the plan claimed otherwise. Under the flag the merge is a strict SUPERSET of the #1501 tag carve-out (which keeps only service-authored entries), so it subsumes that branch rather than competing with it — which required BOTH `mergeUntemplatedValue` AND `collectMissingPaths` to accept a DECLARED-but-EMPTY baseline list alongside a populated one: `isKeyedList` deliberately requires a NON-empty array, so a condition-collapsed `Tags: []` fell through to the merge's wholesale arm and handed AWS `[]`, stripping `AmazonECSManaged` — the exact loss the carve-out exists to prevent — while the REPORTER fell to its own whole-list arm, which only fires on an `undefined` desired side and so named nothing at all. Fixing only the merge (the first review pass) left the plan silently under-claiming what survives, which the second review caught; both arms now mirror each other and the correspondence test carries the empty-baseline shape. This inverts the pre-#1626 'emptiness is deliberately excluded' contract on the DESIRED side only, which is safe because the reporter has exactly one caller and it runs only on the template-only baseline. The merge also DEDUPES by `Key`, because AWS can report one twice and `PutBucketTagging` / `ModifyLoadBalancerAttributes` reject a duplicate. The structural rules mirror `collectMissingPaths` case for case — plain records descend, KEYED `[{Key,Value}]` lists merge by `Key`, positional arrays and scalars come from the baseline wholesale — so every path `findRevertUnbaselinedAwsKeys` (renamed from `findRevertDroppedAwsKeys`, since they are now PRESERVED rather than dropped) names in the plan is rescued by the merge and the merge rescues nothing the plan failed to name; a unit test pins that correspondence by diffing the flag-on and flag-off outputs. A service-authored tag is in NEITHER list and that is the carve-out being consistent: it is preserved on the default path too, so the flag does not rescue it, and `isServiceManagedTagKey` omits it from the plan because reporting it would warn about a loss that cannot happen — the test pins that it survives under both settings.
- **src/analyzer/outputs-diff.ts** - The diff-side `Outputs` resolution + comparison behind `cdkd diff`'s Outputs section (issue [#1921](https://github.com/go-to-k/cdkd/issues/1921)) — the preview half of the Outputs-only persist `cdkd deploy` gained in #875. `resolveTemplateOutputs` builds the exact bag shape `DeployEngine.resolveOutputs` writes to `StackState.outputs`: a condition-false output is SKIPPED (CFn never creates it), and an `Export.Name` is stored as a SECOND key holding the same value (what `Fn::ImportValue` resolves against). It takes the STORED outputs bag for exactly one decision (issue [#1942](https://github.com/go-to-k/cdkd/issues/1942)): a LITERAL `Export.Name` in a stack that resolves a secret, where deploy refuses a name CONTAINING a resolved plaintext and the preview — which never substitutes one — cannot evaluate that predicate. State holding the alias KEY proves a previous deploy already evaluated it over the same literal name and published, so the preview publishes the same key with TODAY's value (the stored VALUE is not part of the evidence — requiring equality would suppress exactly the export change #875 exists to show); an ABSENT key records no verdict, so it keeps the previous behaviour of suppressing the whole outputs delta and recording the alias in `failedKeys`. Two residuals live at that branch: a rotation whose new plaintext is a substring of the literal name flips deploy's verdict, and a key stored by a pre-#1919 binary records no verdict at all (the same key `cdkd scrub` reports through `secretBearingStateKeyWarning`). It reports `resolutionFailed` when any output stays unresolved, and `isUnresolvedValue` is deliberately WIDER than the deploy side's `v === undefined` because the diff resolver fails in more ways: `undefined` (the SAME signal — `resolve` returns it WITHOUT throwing for a constructible-but-unknown attribute like `StreamArn` / `PolicyId` / `VpcId`, and `JSON.stringify` drops such a key so state can never hold one), a SYMBOL (a top-level `Fn::If` selecting `Ref: AWS::NoValue` — `resolveValue` strips the sentinel only INSIDE arrays / objects), a surviving intrinsic OBJECT, and — ONLY for a value whose raw template source contained an `Fn::Sub` (`templateUsesSub`, which walks nested `Fn::Join` / `Fn::If`) — an unsubstituted `${...}` STRING (`resolveSub` catches a genuine `Ref` / `GetAtt` miss, WARNS, and KEEPS the literal placeholder — no throw and no object, so an object-only check launders it straight through). Each of the first three would otherwise be a PERMANENT phantom on a stack the deploy considers clean, with `--fail` exiting 1 forever. The `Fn::Sub` SCOPING is what keeps the last one safe: applied to every string it would match an IAM policy body's `${aws:username}`, a UserData shell `${VAR}`, or any literal a user wrote, and one such key suppresses the WHOLE Outputs section for the stack forever. Within `Fn::Sub`-sourced values one false positive remains and is accepted — `${!Literal}` is the ESCAPE and resolves to literal `${Literal}`, indistinguishable post-resolution — because it merely SUPPRESSES the section (the pre-#1921 behavior) whereas the alternative is a phantom every run. Failed keys are returned as `failedKeys` because this resolver DROPS them while deploy keeps them as `undefined`; without that list every failure reads as a phantom REMOVE and the suppression warning fires on the ordinary pending-resource case. `computeOutputsDiff` then compares bag KEY by bag KEY, which is exactly the `outputMapsEqual` predicate the deploy engine gates its persist on, so the preview cannot drift from the apply; a partially-resolved bag reports NO delta, mirroring the deploy engine declining to persist one (nothing is lost — an output only fails to resolve because it references a resource this deploy has yet to CREATE, and that CREATE is already on the resource side) and, like deploy, WARNING when a delta was suppressed so "no Outputs section" is never ambiguous between unchanged and uncomputable. It also WITHHOLDS an `oldValue` that is legacy secret PLAINTEXT, since this is the first code path that DISPLAYS a stored output value and `cdkd diff` is routinely run in CI. TWO signals identify such a record and both are needed: the desired side still being a SECRET-BEARING dynamic reference while the stored side is not (the condition `cdkd scrub` repairs), AND `secretSourceKeys` — keys the TEMPLATE declares as such, collected over EVERY declared output including condition-skipped ones. "Secret-bearing" is deliberately only the spellings that are secret REGARDLESS of target — `{{resolve:secretsmanager:` and `{{resolve:ssm-secure:`. A plain `{{resolve:ssm:` is EXCLUDED because #1901 classifies it by the parameter's TYPE and a `String` / `StringList` parameter is public and legitimately persisted RESOLVED; keying on it would fire on an ordinary record and, since the verdict is record-WIDE, withhold every value in the stack while advising a `cdkd scrub` that would find nothing. The second reaches what the first cannot: a condition-skipped secret output has no desired side at all and would otherwise print in full as a REMOVE row. It does NOT reach `buildDeletedSubtree`'s removed nested child, whose WHOLE bag becomes REMOVEs against an EMPTY template — an earlier revision of this note listed that case here, and it is structurally out of reach for the same reason the deleted OUTPUT is: nothing is declared. That node is covered instead by the third signal below, which `diff-recursive.ts` arms from the PARENT's template (`templateHasSecretDynamicReference`), propagated unchanged to a deleted grandchild since its template is gone for the same reason. A hit on either makes the whole record suspect — it was written by a pre-GHSA binary, so every value in it is unredacted — hence the withholding is RECORD-level, not per-key. It does NOT reach an output DELETED from the template, and an earlier revision of this note claimed it did — `secretSourceKeys` is built from DECLARATIONS, so a record whose only secret-bearing output has since been removed contributes nothing to the set, reads as not-legacy, and renders its stored pre-GHSA plaintext as the `old:` side of a REMOVE row (issue [#1948](https://github.com/go-to-k/cdkd/issues/1948)). That case is answered from the STORED bag by a THIRD signal, and as a REFUSAL rather than a detection, because it is undecidable there — a plaintext is indistinguishable from an ordinary string: a stored key present in neither `declaredKeys` (every declared output name plus every literal `Export.Name`, condition-skipped ones included) nor the resolved bag has its value withheld. Two gates keep that off the common benign case, since deleting an output is a normal refactor: `templateHasSecretReference` (does the template still prove a secret reference ANYWHERE, `Resources` included — an Outputs-only walk would answer false for every case the gate exists to catch) and an EXONERATION when any stored value is itself a secret expression, which proves the last write redacted the whole bag. This arm withholds PER KEY, unlike the two above, and the asymmetry follows from what each concludes — those claim the record was written by a pre-GHSA binary, this one claims only that ONE key is undecidable. Residual: a stack whose ONLY secret reference WAS the deleted output leaves nothing to gate on, and blanket-withholding every REMOVE value is the worse trade. The change is still reported; only the value is withheld. Output / export NAMES are stripped of control characters before printing: an `Export.Name` is a RESOLVED value, so unlike a CFn logical id it never passed a validator and can carry ANSI escapes. **A deliberate SECOND implementation, not shared code**: extracting the deploy-side block would edit `src/deployment/deploy-engine.ts`, which sits in BOTH the `integ-broad` and `integ-destroy` gate scopes, so a diff-only fix would have acquired two real-AWS gates. `tests/unit/analyzer/outputs-diff.test.ts` pays for that trade with an anti-drift fence that READS `deploy-engine.ts` and asserts the mirrored semantics still hold — watching the DEFINITION of deploy's failure signal (`some((v) => v === undefined)`) rather than the line that CONSUMES it, since an earlier version pinned the consumption and would have stayed green through exactly the divergence it exists to catch. Each assertion is verified to fire by a mutation probe.
- **src/analyzer/drift-calculator.ts** - State-vs-AWS property comparator used by `cdkd drift`. Only descends into keys present in cdkd state, so AWS-managed fields cdkd never set (timestamps, generated identifiers, account-wide defaults) cannot surface as false-positive drift. Also exports `undeclaredEmptyObservedKeys(observed, declared)` (issue #1498): on the observed-properties baseline, a top-level key the template never declared whose captured value was EMPTY (`[]` / `{}` / `null`) is fed into `ignorePaths` by `drift.ts` — such keys are materialized AFTER the per-resource capture by sibling resources (`ClusterCapacityProviderAssociations` -> `Cluster.CapacityProviders`, standalone `LifecycleHook` -> the ASG's hook list, standalone SG rules) or by AWS itself, and comparing them produced permanent phantom drift that `--revert` then destructively stripped; an undeclared key captured with a real value stays compared. Accepts an optional `ignorePaths` list (sourced from each provider's `getDriftUnknownPaths`) to skip state property paths the provider deliberately cannot read back from AWS — e.g. Lambda `Code: { S3Bucket, S3Key }`, which `GetFunction` only returns as a pre-signed URL — so a clean run reports no drift on those keys instead of the guaranteed false positive that would otherwise fire on every invocation. `drift.ts` passes the resource's state-recorded `properties` as that method's optional second argument (issue #1602), so a path unreadable only for a SUBSET of a type's resources can be scoped per resource rather than switching the key off for the type: `ApiGatewayV2Provider` declares `TlsConfig` unknown only when `ConnectionType !== 'VPC_LINK'`, because AWS silently discards the field on a public integration and returns it on a private one. `DynamoDBTableProvider` is the second consumer (issue [#1760](https://github.com/go-to-k/cdkd/issues/1760), PR [#1769](https://github.com/go-to-k/cdkd/pull/1769)) and a usefully DIFFERENT shape: ApiGatewayV2 scopes on a SIBLING property's value, whereas this one scopes on whether the template declares the property AT ALL — `WarmThroughput` is unknown unless the desired bag declares it, and `GlobalSecondaryIndexes` / `LocalSecondaryIndexes` likewise — and it uses the seam to cover an UPGRADE transition rather than a configuration split, since records written by an earlier binary already froze the AWS-computed value into `observedProperties`. Its predicate answers DECLARED for an absent or uninformative bag (`declaresWarmThroughput` returns `true` there), which is that rule's concrete spelling: a bag that was never populated is not evidence the template declared nothing. A provider must tolerate an absent bag by falling back to the type-level answer (defaulting to COMPARING — hiding real drift is the worse failure). Before any comparison it canonicalizes both the baseline and AWS-current sides through `src/analyzer/drift-normalize.ts` so that AWS returning a tag list, a resource-id/ARN array, or a provider-declared unordered set of plain strings or of objects (`options.unorderedPaths`, sourced from `getDriftUnorderedPaths`) in a different order than the deploy-time snapshot does not surface as phantom drift (the `deepEqual` walk compares arrays positionally). The LAST pass in that chain is the provider's own `canonicalizeDriftProperties(resourceType, properties)` (issue [#1784](https://github.com/go-to-k/cdkd/issues/1784), applied by `drift.ts` to BOTH sides) — the seam for a difference no PATH can name, a member of an ARRAY ELEMENT: since `diffAt` compares arrays wholesale, `isIgnoredPath` is never asked about a path crossing one, so the only expressible suppression is the WHOLE array and suppressing `GlobalSecondaryIndexes` would mean never detecting an index add / remove / capacity change again. Stripping the AWS-managed member from BOTH bags converges an old `observedProperties` record with a new readback instead, keeping the array compared. It takes no `side` argument on purpose (one-sided normalization is the mistake `drift-normalize.ts`'s header records — it manufactures drift on the `properties`-fallback baseline), must be pure / non-mutating / identity-returning when inapplicable, and is applied to the COMPARISON copies, so the `aws` bag `--revert` diffs against is untouched. **`--accept` is NOT symmetric with that**: it writes each change's `awsValue`, which comes from the CANONICALIZED bags, so a stripping canonicalizer makes `--accept` persist the stripped shape on a path that still drifts (the call site in `drift.ts` says so, and `tests/unit/cli/drift.test.ts` pins it). That is the intended direction — state should stop carrying a member the readback no longer reports — but it means the hook is a WRITE, not only a comparison filter, which a provider author must know before declaring one.
- **src/analyzer/drift-normalize.ts** - Order-normalization helpers for `drift-calculator.ts`. `canonicalizeTagListsDeep` sorts any `{Key,...}[]` tag list by `Key`; `canonicalizeIdArraysDeep` sorts any array whose every element is an AWS resource id (`subnet-…`, `sg-…`) or ARN. Both recurse and are applied to BOTH comparison sides — AWS does not guarantee element ordering across reads, and these two kinds are semantically unordered sets, so without this every reorder would be a false positive. Surfaced by dogfooding the sibling `cdk-real-drift` tool. Plain-string arrays and non-tag OBJECT arrays are NOT canonicalized heuristically (either can be order-significant); instead `canonicalizeUnorderedArraysAtPaths(value, paths)` sorts such an array ONLY at an explicit per-provider opt-in path list, sourced from the new optional `ResourceProvider.getDriftUnorderedPaths(resourceType)` and threaded through `calculateResourceDrift`'s `options.unorderedPaths` by `drift.ts` (issue [#1096](https://github.com/go-to-k/cdkd/issues/1096) item 1). Issue [#1620](https://github.com/go-to-k/cdkd/issues/1620) extended the pass from plain-string arrays to arrays of OBJECTS, sorted by a private key-order-independent `canonicalJson` — key order must not participate, since AWS's readback order for an object's own keys is no more guaranteed than its order for the list, so a raw `JSON.stringify` sort key would reintroduce the phantom drift the pass removes. Each shape is sorted only when the array is HOMOGENEOUS in it; a MIXED array (strings and objects, a `null` element) is left untouched. Both provider-declared path lists share ONE matcher — the exported `matchesPathPrefix(path, entries)` (exact match, or entry followed by `.`), which `drift-calculator.ts`'s `isIgnoredPath` is now a thin alias over — so the two cannot silently drift apart. A plain entry is a SUBTREE declaration; appending `LEAF_ONLY_PATH_SUFFIX` (`[]`) claims the path ALONE (issue [#1783](https://github.com/go-to-k/cdkd/issues/1783)). The leaf-only form exists because THIS walk descends into array elements, so a subtree entry for an object list also claims every array nested inside its elements — `AWS::DynamoDB::Table.GlobalSecondaryIndexes` is an unordered set keyed by `IndexName` while each element's `KeySchema` is order-SIGNIFICANT (HASH before RANGE), so the only available spelling would have sorted the per-index key schema and HIDDEN a real key change, which is why #1767 shipped the reverse-map half and left the ordering half undeclared. The marker is honored by BOTH lists rather than only by the one that needed it, so their spellings cannot diverge (which is the whole reason the matcher is shared); a bare `'[]'` entry matches NOTHING, since it would otherwise name the root bag. One required divergence: `isIgnoredPath` never sees a path crossing an array (the comparator compares arrays wholesale via `deepEqual`), whereas the unordered walk descends into array elements and gives them the parent's path, so `'Items.Aliases'` is meaningful for `getDriftUnorderedPaths` but inert as an ignore-path — strictly more permissive. Nested arrays are not descended into, so an array-of-arrays at a declared path never has its inner lists sorted. `ELBv2Provider` declares `AWS::ElasticLoadBalancingV2::TargetGroup.Targets` (the first object-array consumer, #1620) — which is what let `Targets` move OUT of that provider's TYPE-level `getDriftUnknownPaths` and start being compared at all; its `readCurrentState` reads them back via `DescribeTargetHealth`, excluding exactly the `draining` state (a just-deregistered target keeps reporting for minutes, and freezing one into the deploy-time snapshot is permanent phantom drift) while INCLUDING every other state, since `initial` / `unused` / `unhealthy` / `unavailable` are all registered and health is not registration. The unknown-path entry did not disappear, it became PER-RESOURCE via the #1602 seam: `Targets` is still ignored for a target group whose TEMPLATE declares none, because an ECS-service / ASG-fronting target group has its members registered by the SIBLING resource and re-registered on every scale event — comparing that would report drift on an untouched stack and `--revert` would deregister the tasks the service just placed (the #1498 class; `undeclaredEmptyObservedKeys` only covers it when the capture happened to be empty, which for a redeployed running service it is not). An explicit `Targets: []` IS a declaration and stays compared. `KinesisStreamProvider` declares `AWS::Kinesis::Stream.DesiredShardLevelMetrics` (issue #609) — enhanced-monitoring metrics come back from `DescribeStream` in an order matching neither the request nor alphabetical (measured us-east-1, 2026-08-12), and the same backfill made the field's order observable in the first place by expanding the `ALL` shorthand into the seven names AWS stores. `DynamoDBGlobalTableProvider` declares `AWS::DynamoDB::GlobalTable.AttributeDefinitions` (issue [#1742](https://github.com/go-to-k/cdkd/issues/1742)) — `DescribeTable` returns the definitions in an order matching neither the request nor alphabetical (measured us-east-1, 2026-08-13: a table declaring `[pk, gsipk]` read back as `[gsipk, pk]`), and the list is a genuine set keyed by `AttributeName`, so sorting it cannot hide a real change. `KeySchema` is deliberately NOT declared at either level, being order-SIGNIFICANT (HASH before RANGE). The same paragraph's reachability note is what kept this unseen: it only bites on the `properties` baseline a reverse-replacement rollback leaves behind, since `rollback-executor.ts` strips `observedProperties`. `DynamoDBTableProvider` declares the same path for the sibling `AWS::DynamoDB::Table`, whose readback is identical one type over (issue [#1760](https://github.com/go-to-k/cdkd/issues/1760), shipped in PR [#1769](https://github.com/go-to-k/cdkd/pull/1769)). The per-index `WarmThroughput` half of #1742 has since SHIPPED (PR [#1859](https://github.com/go-to-k/cdkd/pull/1859)): `DynamoDBGlobalTableProvider` is the first consumer of the `canonicalizeDriftProperties` seam (issue [#1784](https://github.com/go-to-k/cdkd/issues/1784), described in the `drift-calculator.ts` entry above), naming the `{ listKey: 'GlobalSecondaryIndexes', member: 'WarmThroughput' }` PAIR in a closed `DRIFT_STRIPPED_INDEX_MEMBERS` table — a list-plus-member pair, NOT a path: this seam takes no paths at all, which is the whole reason it exists two sentences above and stripping that member from BOTH comparison sides. The two halves had to land together: `readCurrentState` reverse-maps the AWS `GlobalSecondaryIndexWarmThroughputDescription` into the CFn shape, surfacing only the two user-settable sub-fields and DROPPING the `Status` member CFn has no concept of — and dropping a readback key otherwise strands every already-written `observedProperties` baseline (the [#1760](https://github.com/go-to-k/cdkd/issues/1760) class), which is exactly what the both-sides strip absorbs, since an old record and a post-fix readback converge on carrying no member at all. Two bounds belong with it: the convergence only reaches records written by a post-[#1420](https://github.com/go-to-k/cdkd/issues/1420) binary (an older bag holds the raw `GlobalSecondaryIndexDescription[]` and is already drifting on five other members — `IndexArn` / `IndexStatus` / `ItemCount` / `IndexSizeBytes` / `Backfilling`; the provider's own comment at the strip site enumerates only four, and is the undercount, tracked in issue [#1938](https://github.com/go-to-k/cdkd/issues/1938)), and the accepted cost is that a DECLARED per-index `WarmThroughput` change is no longer reported by `cdkd drift` at all — a declared-gate is not expressible in a hook that sees ONE bag with no desired-side reference, which is the asymmetry `getDriftUnknownPaths` avoids for a TOP-LEVEL key. The sibling `AWS::DynamoDB::Table` type has the same per-element shape and has NOT adopted the seam — its own change with its own real-AWS verification, tracked as issue [#1812](https://github.com/go-to-k/cdkd/issues/1812). `FSxFileSystemProvider` declares only `WindowsConfiguration.Aliases`; `SelfManagedActiveDirectoryConfiguration.DnsIps` is deliberately NOT declared (AWS documents no set semantics for it and DNS resolver lists are conventionally preference-ordered — declaring an order-significant list would silently HIDE real drift, which is worse than the visible false positive of leaving it undeclared; same reasoning excludes ElastiCache `PreferredAvailabilityZones`). Declaring the path here rather than sorting inside the provider's `readCurrentState` reverse-mapper is load-bearing: the normalizer runs on BOTH sides, so it stays correct for the `properties`-fallback baseline (a resource deployed before observed-capture, whose baseline is the user's template order) — sorting only the read side would manufacture drift there.
- **src/analyzer/drift-principal-normalize.ts** - IAM principal-FORM canonicalization for `cdkd drift` (issue [#1515](https://github.com/go-to-k/cdkd/issues/1515)) — the sibling of `drift-normalize.ts` for a difference that is not about ORDER. AWS renders an IAM role / user principal inside a resource policy either as its ARN or as its `AROA…` / `AIDA…` unique id, substituting the unique id when the principal is transiently unresolvable at write time (the CDK `autoDeleteObjects` role is created concurrently with the bucket policy that references it) and re-rendering the ARN once it resolves; the deploy-time `observedProperties` capture stores whichever form came back, so `cdkd drift` compared two spellings of ONE principal and reported PERMANENT phantom drift that `--revert` could not clear (it wrote the recorded form back and AWS re-canonicalized on write — the #1096 / #1498 class on a different property; two back-to-back runs of the `drift-revert` fixture on 2026-08-10 disagreed for exactly this reason with no code change in between). Unlike its sibling this pass CANNOT be pure — the mapping is not derivable from the string — so the shape detection (`collectPrincipalUniqueIds` / `collectPrincipalArns` / `rewritePrincipalUniqueIds`, walking only `Principal` / `NotPrincipal` positions, where the two forms are interchangeable, and NOT a `Condition` value, where they are not) is pure and the one lookup goes through an injected `PrincipalUniqueIdResolver`; `drift.ts` supplies the live implementation (`iam:GetRole` / `GetUser` off the ARN via the shared `parseIamPrincipalArn`, cached per ARN for the whole command INCLUDING failures). `canonicalizePrincipalUniqueIds` rewrites BOTH sides to the ARN form — the race is symmetric, and one-sided normalization is the mistake `drift-normalize.ts`'s header already records — and short-circuits with NO AWS call unless a unique id AND a candidate ARN are both present. Only a pair PROVEN equal by the lookup is collapsed: a deleted role (exactly when AWS keeps the unique id forever), a cross-account principal, or a missing `iam:GetRole` permission all leave both sides untouched and the drift REPORTED, so the pass can never hide a real principal change. - **src/utils/ip-protocol.ts** + **src/analyzer/drift-protocol-normalize.ts** - EC2 security-group `IpProtocol` VALUE canonicalization (the measured rename table + `canonicalizeIpProtocolValue` live in `src/utils/`, because they have TWO consumers in different layers; the analyzer module owns only WHERE in a resource's properties the canonicalization applies) for `cdkd drift` (issue [#1643](https://github.com/go-to-k/cdkd/issues/1643)) — the second sibling of `drift-normalize.ts` for a difference that is not about ORDER, and unlike `drift-principal-normalize.ts` it IS pure (the mapping is a closed, measured table, so no AWS lookup is needed). EC2 owns the spelling of a rule's `IpProtocol`: it accepts an IANA protocol NUMBER or a NAME and rewrites the four numbers it has a name for before storing the rule, so cdkd recording what it SENT (`'6'`, post-#1633) against a readback of what AWS HOLDS (`'tcp'`) was two spellings of ONE protocol — permanent phantom drift `--revert` could not clear, since it revokes and re-authorizes into the same state (the #1591 / #1633 class via a third route: those two fixed TYPE coercions on the SEND side, this is a VALUE mapping owned by AWS, so it belongs on the READBACK side and covers the inline `AWS::EC2::SecurityGroup.SecurityGroupIngress[]` / `SecurityGroupEgress[]` rules #1633 deliberately does not touch). The rename set was MEASURED, not guessed (us-east-1, 2026-08-12, ingress AND egress): exactly `1` -> `icmp`, `6` -> `tcp`, `17` -> `udp`, `58` -> `icmpv6`, while `-1` / `0` / `2` / `4` / `27` / `41` / `47` / `50` / `51` / `88` / `89` / `94` / `103` / `112` / `132` / `255` all read back as the number — so it is a CLOSED set of the four protocols EC2 has a name for, not the open-ended IANA list, and `-1` being unaffected is why #1633's live test came back clean. Case is AWS's too (`TCP` / `Tcp` / `tcp` authorized on one port collapsed into ONE `tcp` permission in the readback), so a name is matched case-insensitively and lowered — but ONLY the four KNOWN names, so the pass can never make two genuinely different values compare equal. Numbers canonicalize to their STRING form because an unquoted YAML `IpProtocol: 47` parses to a number while AWS always reads back a string. `canonicalizeIpProtocols(baseline, aws, resourceType)` is applied to BOTH sides by `drift.ts` right after the principal pass, and is scoped by a CLOSED `IP_PROTOCOL_PATHS` table (the two standalone rule types at the top level, `AWS::EC2::SecurityGroup` at `SecurityGroupIngress[].IpProtocol` / `SecurityGroupEgress[].IpProtocol`) rather than by a walk for any key named `IpProtocol` — a blanket rewrite would turn an unrelated `'6'` into `'tcp'`. EVERY number is stringified, not only an integer one, so a malformed `6.5` keeps the key it had before #1633 and `NaN` / `Infinity` do not collapse onto one JSON `null` bucket; anything that is neither a string nor a number, most importantly an unresolved intrinsic, is returned untouched, and an unchanged bag is returned by IDENTITY. **`canonicalizeIpProtocolValue` is ALSO consumed by `ec2-provider.ts`'s `sgProtocolKey`**, because the comparison is only half the defect: a standalone rule's physicalId is `<groupId>|<protocol>|<from>|<to>` built from the value cdkd SENT, so for `IpProtocol: 6` both the tuple pre-filter and the full-signature `sgRuleKey` compare in `readSecurityGroupIngressCurrentState` missed AWS's `tcp` rule entirely, the method returned `undefined`, and `cdkd drift` reported the resource as "drift unknown" FOREVER — one layer BELOW the phantom drift, and structurally invisible to a comparison-side fix because no AWS-side bag is ever produced (measured by the real-AWS `drift-revert-arrays` run on 2026-08-12, which is what surfaced it; the issue's own premise that the read "returns `tcp`" was wrong). Normalizing inside `sgProtocolKey` heals the standalone lookup, the inline-rule `reconcileSgRules` ordering AND the write-side `applySecurityGroupRuleDiff` revoke/authorize key from ONE definition of protocol identity, and mirrors the reason its existing comment already gives for stringifying a legacy numeric `-1`: keying the normalization is what heals the deployed population with no migration. Issue [#1648](https://github.com/go-to-k/cdkd/issues/1648) then extended the SAME fold to the DIFF side (`canonicalizeDesiredProperties`, for the standalone type and the `AWS::EC2::SecurityGroup` inline rule lists), because a template edit rewriting `IpProtocol: 6` to `'tcp'` otherwise read as a changed property — and since `IpProtocol` is create-only on the standalone type, that classified as a REPLACEMENT of a rule AWS already held exactly. The fold is deliberately NOT inside `narrowIngressIpProtocol`, which also feeds the CREATE path: the wire value is not the defect (AWS accepts either spelling and stores `tcp` for both), only the diff's classification is.

- **src/deployment/retryable-errors.ts** - Shared transient-error classifier (HTTP 429/503, the transient SERVER statuses 500/502/503/504, and a message-pattern table covering IAM/CW Logs/SQS/KMS/etc. propagation delays). Consumed by `withRetry` in `src/deployment/retry.ts` to decide whether to back off and retry vs. fail fast. The message table is stored as two composed halves — `IAM_PROPAGATION_ERROR_MESSAGE_PATTERNS` (just-created IAM entity not yet visible to a service's authorization layer) plus a private non-propagation half — spread into the single exported `RETRYABLE_ERROR_MESSAGE_PATTERNS`, so retryability has ONE source of truth while `isIamPropagationError(message)` can select the DENSE retry cadence for the propagation class (see `retry.ts`). A misfiled pattern only changes the cadence, never whether the error is retryable. Exports `isThrottlingError(error)` — the single bounded error + `.cause` walk for rate-limit signals (throttling error NAMES and retryable HTTP statuses, both checked at every depth up to 5). Issue [#2026](https://github.com/go-to-k/cdkd/issues/2026) adds `isTransientServerError(error)` alongside it — the same bounded walk against `TRANSIENT_SERVER_ERROR_STATUS_CODES` (500/502/503/504, mirroring `@smithy/service-error-classification`'s own `TRANSIENT_ERROR_STATUS_CODES`). **A SEPARATE set, deliberately, not an addition to `RETRYABLE_HTTP_STATUS_CODES`**: that one is read by `isThrottlingError`, which SEVEN `isRetryable` call sites across four files (`describe-type.ts:67`, `dynamodb-globaltable-provider.ts` x4, `export.ts:1744`, `intrinsic-function-resolver.ts:5216`) pass as a deliberately NARROW classifier — `describe-type.ts` states the intent outright ("retry ONLY throttle-shaped failures") — so widening the shared set would have silently converted every one of them into "retry throttles AND server errors". Three further sites call it as a bare classification (`drift.ts:518`, `export.ts:1755`, `dynamodb-index-busy-delete.ts:381`) and strengthen the case: `drift.ts` would have begun reporting "cannot compare" for a resource whose read merely 500'd. 501 stays terminal: the rule is the SDK's four transient statuses, not "5xx". `isRetryableTransientError` consults the marker, then the throttle walk, then the server-status walk, then the message-pattern table — the server-status check sits ahead of the messages because it is the only one that still works when the response carried NO message, which is exactly the measured failure (SQS answered a mid-propagation `SetQueueAttributes` with HTTP 500 and an empty body, so the SDK substituted its `UnknownError` placeholder and every pattern had nothing to match). Also exports `describeRetryClassificationSignals` / `formatRetryClassificationSignals`, which render what the classifier SAW (`[name=... http=... requestId=...]`) for the give-up line. The walk returns on the first link whose `$metadata` carries a NUMERIC status — returning on any `$metadata` object reported no `http=` for the real SDK network-error shape (`{attempts, totalRetryDelay}` wrapping a 500), contradicting the classifier that had walked past it and retried. When no link carries a status, the name falls back to the deepest one found BELOW depth 0, since a `ProvisioningError`'s own name describes cdkd rather than the service; a link that DOES carry `$metadata` is named at any depth, including 0, because the metadata proves it came from the SDK. `noMetadata` is false whenever a `$metadata` was seen at all, so "a status cdkd does not retry" stays distinguishable from "the response never reached error deserialization". Also exports `isNameCollisionError(message)` (issue #1207) — the name-collision matcher shared by the deploy engine's replacement create-first collision detection, its `--replace` delete-first re-create retry, and the rollback executor's reverse-replacement collision detection + retry; deliberately NOT part of the transient pattern table (a collision is only retryable at the sites that just deleted the old name holder). It accepts BOTH spellings of the phrase — AWS Lambda raises the SINGULAR `Function already exist: <name>`, so a plural-only pattern left every `AWS::Lambda::Function` unable to take the collision path at all (issue #1625) — while a lookbehind refuses the negated / modal forms ("does NOT already exist", "MUST already exist"), whose consequence at these sites is a DELETION rather than a mis-worded message. Issue #1206 adds `isNameCooldownError(message)` (the SQS `QueueDeletedRecently` / "wait 60 seconds" same-name re-creation cooldown — kept separate from the collision matcher because a cooldown at a create-first site must not trigger delete-new-first) and `isRecreateRetryableError(message)` (collision OR cooldown — the retry filter for the delete-then-re-create sites — the `--replace` delete-first fallback, the `--recreate-via-cc-api` / `--recreate-via-sdk-provider` destroy-then-create path (issue #1214; the inner generic retry's ~47s budget ends inside the 60s window), and the rollback executor's delete-new-first — paired with a maxRetries-8 / 10s-cap schedule ≈ 64s total sleep so the full 60s cooldown window is covered; the rollback executor's initial create-first attempt additionally retries the cooldown alone). Issue #1778 adds the escape hatch the message table cannot express: `markNonRetryable(error)` stamps a non-enumerable `Symbol.for('cdkd.nonRetryable')` on an error and `isMarkedNonRetryable(error)` walks the bounded `.cause` chain for it, consulted by `isRetryableTransientError` BEFORE any message heuristic. It exists because the classifiers match by SUBSTRING against a message, so a cdkd-authored refusal whose message interpolates user-controlled text (a logical id, a resource name) can collide with a retryable pattern and burn the full ~47s schedule on a path that cannot succeed — `DependencyViolation` is the only whitespace-free entry in the table, so an ordinary composite CDK logical id was enough (issue #1838). **Two spellings, and the choice is not stylistic**: mark at the `throw` when the class is retryable in general and only this raising of it is not (`sns-subscription-provider.ts`'s abort); mark in the CONSTRUCTOR when the class is a refusal in EVERY instance (`ResourceUpdateNotSupportedError` in `src/utils/error-handler.ts`, raised by ~20 providers from inside the retried `update()` — a per-site marker there is one forgotten call away from re-opening the hole for a single provider). Note this is also why `src/utils/error-handler.ts` imports from this file: `retryable-errors.ts` has zero imports of its own, so it is a graph leaf and the edge cannot cycle. **Marking is NOT the default for a deliberate refusal** — the audit behind #1838 left `IntrinsicResolutionRefusalError` unmarked even though it is deliberate and interpolates user text, because its fabricated-account arm is genuinely time-dependent (`getAccountInfo` caches a fabricated answer for only 10s precisely so a later attempt can heal), and `ProvisioningError` / the `CdkdError` base must stay unmarked because the marker read is a prototype-chain lookup and they wrap RELAYED AWS failures. The test is "can this ever succeed on a retry", not "did cdkd author it".
- **src/deployment/retry.ts** - Retry helper used by DeployEngine. TWO schedules, picked per attempt from the error class: the generic 1s -> 2s -> 4s -> 8s capped at 8s over 8 retries (47s total sleep) for throttling and long resource-state transitions, and a DENSE 0.25s -> 0.5s -> 1s -> 2s -> 2s ... over 26 retries (47.75s total sleep, `IAM_PROPAGATION_{INITIAL_DELAY_MS,MAX_DELAY_MS,MAX_RETRIES}`) for the IAM-propagation class (`isIamPropagationError`). Rationale: cdkd creates an IAM entity and consumes it ~1-3s later, so propagation failures resolve in single-digit seconds — the generic schedule's 4s/8s steps overshoot (a measured 3-instance EC2 stack burned ~10.2s of a 25.9s deploy in backoff after `Invalid IAM Instance Profile name`), while throttling genuinely wants exponential backoff. The dense budget is deliberately >= the generic one so a denser probe grid never shrinks the window in which propagation can still be caught. The class is re-evaluated per attempt, so a throttle hit mid-propagation backs off exponentially. The dense schedule applies ONLY when the caller left the schedule at its defaults (the deploy engine's create/update path, drift revert, the ELBv2 / ServiceDiscovery attribute calls); any explicit `maxRetries` / `initialDelayMs` / `maxDelayMs` / `isRetryable` means the caller owns the cadence and gets it verbatim (the DELETE path's 3 x 5s, the delete-then-re-create sites' ~64s SQS-cooldown budget, `describe-type.ts`'s throttle-only retry). Delegates retryable-error classification to `retryable-errors.ts`. The give-up line also carries the classifier's own inputs (`[name=... http=... requestId=...]`, issue [#2026](https://github.com/go-to-k/cdkd/issues/2026)) — the message is the field that can degenerate, so when it does the bracket is the whole diagnosis. **The propagation retry REPORTS itself (issue [#2018](https://github.com/go-to-k/cdkd/issues/2018))**: a sequence that gives up emits ONE `warn` line naming the retries spent and the backoff consumed (`gave up after 26 IAM-propagation retries over 47.75s of propagation backoff (the full propagation budget)`), and each per-attempt `debug` line carries the running total (`attempt 15/26, 25.75s backoff through this attempt` — the figure INCLUDES the wait the line is announcing, since the line prints before the sleep). **The exhaustion note keys on the loop's own exit condition (`sawPropagation && attempt >= attemptLimit`), NOT on the retry count**: a throttle mid-sequence classifies non-propagation, so it consumes an attempt without advancing the counter, and a count-keyed test reported a genuine 26-attempt exhaustion as "something else ended it" — the false NEGATIVE inverts the branch a reader uses to decide whether the budget needs widening. The seconds likewise count PROPAGATION backoff only, so a mixed sequence's throttle wait is excluded; that keeps the figure comparable against the 47.75s budget rather than reading as total elapsed time. `warn` rather than `debug` is the load-bearing part: an exhausted retry rethrows the RAW AWS error, so at default verbosity a 47.75s retry and a build carrying no retry at all printed byte-identical output — which is why a real field report of this failure could only be diagnosed by reading the source and diffing two releases, and why "the pattern is in the table" was not evidence the symptom was fixed. There are THREE counters (issue [#2026](https://github.com/go-to-k/cdkd/issues/2026) added `serverErrorRetries`), all reporting-only and feeding no control decision, and they advance only AFTER a wait completes so an interrupt cannot inflate the summary with a sleep that never happened. The give-up line is built from the kinds actually spent and joined with ` and `, so a mixed sequence reports both — `gave up after 2 IAM-propagation retries over 0.75s of propagation backoff (the full propagation budget) and 24 transient server-error retries (HTTP 5xx)` — while a propagation-only sequence renders byte-identically to what #2018 shipped. `serverErrorRetries` is gated on the caller NOT having supplied its own `isRetryable`: `RETRYABLE_HTTP_STATUS_CODES` already contains 503, so the throttle-only sites retry one today, and counting it there printed a default-level `warn` on graceful-degradation paths that previously printed nothing. The warn is wrapped in a `try/catch` because it fires immediately before the rethrow — a throwing logger must not REPLACE the error the summary exists to explain. `RetryLogger.warn` is OPTIONAL, and the reason is not merely that bare `{ debug }` callers must keep compiling: `drift.ts`'s revert deliberately threads a MASKING logger (issue [#1914](https://github.com/go-to-k/cdkd/issues/1914) — the summary interpolates the AWS message, which on that path can quote a resolved secret), so a required `warn` would have been silently satisfied by an unmasked `logger.warn`. Do NOT restate that every production caller threads a real `Logger`; an earlier revision of this entry did, and it was false for exactly that caller, which lost the summary entirely until #2018 wired its masked `warn`.

- **src/provisioning/composite-id.ts** - Refusal guard for COMPOSITE physicalIds (issue [#1672](https://github.com/go-to-k/cdkd/issues/1672)). `ResourceProvider` passes a single `physicalId: string`, so a type needing more than one value to address its resource PACKS them joined by `COMPOSITE_ID_SEPARATOR` (`<databaseName>|<tableName>` for `AWS::Glue::Table`, `<apiId>|<typeName>|<fieldName>` for `AWS::AppSync::Resolver`, ...). The separator is NOT escaped, so a segment containing one produces an id with the wrong ARITY — for a Glue table named `a|b` in database `mydb` the recorded `mydb|a|b` decodes to database `mydb`, table `a`, and BOTH halves are non-empty so every existing well-formedness guard passes. The deploy then SUCCEEDS while `cdkd destroy` deletes the wrong table (or warn-and-skips, reporting success while the real one stays alive and billing) and `cdkd drift` reads back `undefined` forever. AWS itself accepts such a name (live probe, us-east-1 2026-08-12: `glue:CreateTable` with `TableInput.Name: 'a|b'` succeeds) and CloudFormation manages it fine, so the limitation is cdkd's own and the honest answer is to REFUSE at deploy time rather than record an id naming something else. Two entry points mirroring `config-shape.ts`'s pair: `packCompositeId(resourceType, logicalId, segments, options?)` is the ACTION (throws a `ProvisioningError`, or warns-and-packs under `options.onRefusal` — the `CreateContext.replayingState` downgrade, since a state record cannot be edited from the template) and `compositeIdSeparatorRefusal(...)` is the bare PREDICATE returning the sentence, for the `import()` paths whose answer is warn-and-SKIP (`return null`). Both share one message builder, and the predicate tests the STRINGIFIED value rather than `typeof value === 'string'` — every call site feeds an unvalidated `as string` cast, so a YAML list `Name: ['a|b']` is truthy, reaches the pack as an ARRAY and stringifies to exactly the ambiguous id the guard exists to refuse. Adopted at every CREATE-path packing site across glue / s3-tables / appsync / ec2 / apigateway / lambda-event-invoke-config, computed BEFORE the AWS call wherever the segments allow (the two that cannot — AppSync ApiKey and EC2 EIP, whose segments come from the create RESPONSE — sit after it and outside the wrapping `try`, so a refusal can never be mis-labelled as an AWS creation failure). `route53-provider.ts`'s three RecordSet packers joined that set in issue [#1711](https://github.com/go-to-k/cdkd/issues/1711) — deferred by the sweep only because a concurrent lane owned the file, and exposed at the one segment the sweep never reached: `recordName` is `properties['Name']`, the only TEMPLATE-chosen segment of the whole family. A four-part id IS rejected by `parseRecordSetCompositeId`'s exact-three-segment rule — but "so the failure mode is loud" was FALSE, and review caught it: three non-empty segments is not proof of a composite either, so a record NAME carrying two pipes (the CFn physicalId `--migrate-from-cloudformation` pre-populates) decoded to a DIFFERENT hosted zone at three sites ABOVE the packers — `importRecordSet`'s early accept, `resolveRecordSetIdentity`'s short-circuit, and `deleteRecordSet`'s own parse, where `cdkd destroy` then targeted a non-existent zone and reported SUCCESS over a live record. All three now cross-check the parsed segments against the template via `compositeAgreesWithTemplate` (TYPE and NAME, each skipped when its template side is unusable; the name compare goes through `canonicalizeQueryName` so case / trailing dot cannot cause a false rejection). `create` refuses before `ChangeResourceRecordSets` (with the ordinary `CreateContext.replayingState` downgrade, which needed `context` threaded through `create()` — the provider declared none); `update` takes the `updateRoute` precedent and downgrades UNCONDITIONALLY, since it has no context and cannot tell a template-borne update from the state-borne bag `drift --revert` / the rollback revert arm hand it; and `import()` takes the method's own `adoptVerbatim` escape hatch rather than freezing a mis-arity id into state. Deliberately NOT covered, with the reason in the module header: `intrinsic-function-resolver.ts`'s joins, which build `Ref` VALUES that nothing decodes. Directions 1 (stop packing where the decode sites already receive the properties bag) and 2 (escape the separator) remain open on #1672. The module's third entry point is the DECODE-side counterpart, `compositeIdFormatMessage(format, logicalId, physicalId, options?)` (issue [#1657](https://github.com/go-to-k/cdkd/issues/1657)): roughly half the decode sites stated the expected shape (`expected "restApiId|resourceId|httpMethod", got "..."`) and half only echoed the value back, and since the format is documented nowhere else (the companion docs gap is issue #1656) the message was the user's ONLY route to it on the silent half. All 17 decode sites that emit a well-formedness message now render through one builder from a per-type `CompositeIdFormat` (`label` + ordered `segments`, plus an optional `alsoAccepts` for `AWS::S3Tables::Table`'s bare-ARN alternative) — the already-correct sites included, so they cannot drift back. **Every segment is a PLACEHOLDER, and the names must match the type's `packCompositeId` segment names**: the first cut of this change gave `AWS::EC2::VPCGatewayAttachment` a literal-segment form rendering `IGW|<vpcId>`, on the belief that `IGW` was a fixed token cdkd packs. It is not — the packer emits the real `internetGatewayId` — so the message named a token no code path produces and a user repairing `state.json` as instructed would have called `DetachInternetGateway(InternetGatewayId: "IGW")`. This is a WORDING change only: each caller keeps its own split-and-guard, because the arities genuinely differ (some sites accept AT LEAST N segments, some destructure the first N and tolerate extras — the #1672 ambiguity) and folding them into one predicate would silently change which ids deploy. The `{ skipping: true }` variant is for the five warn-and-continue DELETE arms: the policy is unchanged, but the warning now says the AWS resource is LEFT IN PLACE while `cdkd destroy` reports success, so the orphan is diagnosable. Unifying the two copies is what surfaced `dkr-ecr-fips.<region>.on.aws`, which BOTH had been missing — on gc's side the irreversible direction, since a missed reference reads as unreferenced and the live image is DELETED. Lives in `src/utils/` because it has TWO consumers in different layers — `src/local/ecr-puller.ts`, which needs the `:tag` tail on top of it, and `src/local/ecs-task-resolver.ts`, which classifies an image that may carry a digest or no tag — and because it must stay free of AWS SDK imports, which is the invariant `ecs-task-resolver.ts` documents about itself. Before issue [#1758](https://github.com/go-to-k/cdkd/issues/1758) each site carried its own copy of a hardcoded `amazonaws.com(\.cn)?` pattern, so fixing the pull path alone left `cdkd local run-task` classifying a non-commercial registry as a public image and attempting an anonymous pull. Issue [#1786](https://github.com/go-to-k/cdkd/issues/1786) then made the whole comparison case-INSENSITIVE at ONE module-private boundary (`matchEcrRegistryHost`, which lower-cases the captured region, the captured suffix AND the derived expected suffix): DNS is case-insensitive, but both halves of the #1758 check were case-SENSITIVE in OPPOSITE directions, so an upper-cased region made a LOOK-ALIKE pass the strict check (it falls through to the commercial partition, whose suffix the look-alike carries) while an upper-cased region or suffix made a GENUINE host FAIL it. The returned `region` is consequently the canonical lower-case spelling, which both consumers rely on as an SDK client region. The same boundary refuses a region segment OR a URL suffix that is not `[A-Za-z0-9-]` / `[A-Za-z0-9.-]`, tested against the RAW capture BEFORE folding: case was only one way to defeat the partition helper's `startsWith` classification, the captured segment is not inert (it becomes an `ECRClient` region and is interpolated into the fallback login endpoint), and `toLowerCase()` maps U+212A onto ASCII `k` -- which, once #1764 landed `aws-isoe`'s `cloud.adc-e.uk`, let a folded suffix impersonate a real partition's. Issue [#1792](https://github.com/go-to-k/cdkd/issues/1792) then folded the last case-sensitive piece, the `dkr.ecr` LABELS, via the regex's `i` flag: an upper-cased label named the same host but did not match the SHAPE at all, so BOTH entry points went quiet (`parseEcrRegistryHost` `undefined` AND `looksLikeEcrHostWithForeignSuffix` `false`, i.e. not even the #1764 diagnostic). Widening rather than refusing is right because docker itself accepts an upper-cased registry host — `distribution/reference` spells `domain-component` as `[a-zA-Z0-9]`-based while the repository PATH is `[a-z0-9]+`, and `ParseNormalizedNamed`'s `must be lowercase` error applies to the remote NAME only — so cdkd is not made to `docker login` for a URI docker would reject, and the repository path is never touched. What docker does NOT fold is its credential STORE (keyed on the hostname verbatim, measured in #1801), so the login / pull spelling is reconciled one layer up by `ecr-puller.ts`'s `canonicalizeImageUriHost`; issue [#1817](https://github.com/go-to-k/cdkd/issues/1817) tracks moving that fold in here. That reconciliation covers the CASE fold only, which is why RECOGNIZING the three widened forms is not yet a working `docker pull` for them: `ecrLogin` authenticates against the PLAIN host (`proxyEndpoint`, or a hardcoded `dkr.ecr` fallback) while the pull targets the host the template names, so a FIPS / dual-stack pull fails with `no basic auth credentials` — issue [#1855](https://github.com/go-to-k/cdkd/issues/1855). One bound is recorded in-code rather than fixed there: three `cdkd local` command files still derive `${AWS::URLSuffix}` from the RAW user `--region`, so an upper-cased `--region` synthesizes a host this module then correctly rejects as a look-alike (issue [#1795](https://github.com/go-to-k/cdkd/issues/1795), shipped separately in PR #1818, which added `canonicalizeRegion` INSIDE `derivePartitionAndUrlSuffix` -- that makes the partition LOOKUP case-insensitive for every caller and is complementary to, not a replacement for, these guards, which decide whether the captured segments are a region id and a suffix at all)), AWS partition helper (`aws-partition.ts` — `derivePartitionAndUrlSuffix(region)`, the closed region -> `{partition, urlSuffix}` mapping CloudFormation applies to `${AWS::Partition}` / `${AWS::URLSuffix}`. Moved here from `src/local/ecs-task-resolver.ts` by the issue #1681 PR review — it gained a consumer in the provisioning layer (`AppSyncProvider` rebuilds a child's ARN when AWS reports none) and a provider importing from `src/local/**` would invert the layering; that module re-exports it so every `cdkd local *` call site is unchanged. `getAccountInfo().partition` (`src/deployment/intrinsic-function-resolver.ts`) is no longer a competing answer: it was hardcoded to `'aws'` on BOTH the success and the STS-failure path — which is how the AppSync update path came to overwrite a correct `arn:aws-cn:` ARN with `arn:aws:`, the regression that review caught, and which left the four `CloudControlProvider` enrichment sites (KMS key, ECR repository x2, Kinesis stream) building the same wrong ARN — and since issue [#1730](https://github.com/go-to-k/cdkd/issues/1730) it DERIVES the field through this helper. Issue [#1746](https://github.com/go-to-k/cdkd/issues/1746) then made that derivation PER CALL rather than per cache entry: `partition` is a function of `region`, and `region` is the CALLER's, so caching a whole `AwsAccountInfo` pinned the FIRST caller's region and a later no-override call inherited both it and the partition derived from it — benign while the field was hardcoded `'aws'`, a stale partition once #1730 made it derived. The cache now holds only the genuinely region-independent `CachedAccountIdentity` (`accountId` + the `fabricated` flag), and `accountInfoFor(identity, overrideRegion)` builds each caller's `region` + `partition` on the way out; `resolveAccountIdentity` takes no region at all, so the shared in-flight promise is region-agnostic by construction rather than by convention. Either spelling is now correct; prefer this one where a region is already in hand, since it needs no STS hop. Issue [#1850](https://github.com/go-to-k/cdkd/issues/1850) then folded the REGION the same way the partition already was: `derivePartitionAndUrlSuffix` canonicalizes its own input (#1795), so the PARTITION segment was already right for an upper-cased `--region`, while the REGION segment beside it was folded nowhere -- and `cdkd deploy --region US-EAST-1` is REACHABLE, since DNS is case-insensitive so the SDK endpoint resolves and the deploy SUCCEEDS. cdkd then recorded `arn:aws:appsync:US-EAST-1:...` into `state.json`, a value no IAM policy matches (policy matching IS case-sensitive) and every SDK call taking it rejects. The fold is applied at `AppSyncProvider.buildAppSyncArn`, at the four `CloudControlProvider` enrichment sites, and -- widest -- ONCE at `constructAttribute`'s `const region = canonicalizeRegion(...)` destructure, which feeds every constructed ARN / URI the resolver builds, so an attribute added later inherits it instead of having to remember. Double-folding is a no-op, which is what makes the region fold and the partition derive safe side by side. The same issue stopped caching a `fabricated` answer (the hardcoded `123456789012` fallback) FOR THE PROCESS, mirroring `write-only-properties.ts`'s "only SUCCESSFUL lookups are cached": one transient STS blip used to poison every later caller in the run, and the ARN-building consumers refuse on `fabricated`, so caching one turned a single bad answer into a whole deploy that records no ARNs. It is not cached for ZERO time either, and the distinction is what PR review had to correct: `getAccountInfo` sits on the path of EVERY `Fn::GetAtt` and every `AWS::AccountId` / `AWS::Partition` / `AWS::StackId` pseudo-parameter, so an uncached failure re-issued `GetCallerIdentity` — with the SDK's own 3-attempt retry, plus one warning — dozens of times per stack. A fabricated answer therefore gets a bounded `FABRICATED_ACCOUNT_INFO_TTL_MS` (10s) window (`accountInfoClock` is the test seam) and a shared `accountInfoInFlight` promise so concurrent callers under `--concurrency` collapse onto ONE round trip; a later phase can still heal. Those four `CloudControlProvider` sites now OMIT the attribute when `fabricated` is set (`accountInfoForSynthesizedArn`), mirroring `AppSyncProvider.childImportAttributes` — an ARN built from the placeholder account carries no wildcard, so `isPlaceholderArn` cannot catch it and the value would be recorded into state as the resource's `Fn::GetAtt` answer), state-bucket owner guard (`expected-bucket-owner.ts` — `resolveExpectedBucketOwner(client)` / `expectedOwnerParam(client)`: STS `GetCallerIdentity` on the client's own credentials, spread as `ExpectedBucketOwner` into EVERY state-bucket-family S3 call — S3StateBackend / LockManager / ExportIndexStore / bootstrap / state-migrate / state.ts raw reads / upload-cfn-template — so a predictable-name bucket pre-created in a foreign account is rejected by S3 itself (403) even when its policy ALLOWS this account; asset-storage has carried the same defense since #1002 PR 1; best-effort: test doubles / STS failure omit the header. Memoized in TWO layers (issue #1283): a per-client `WeakMap` fast path, plus the STS call itself keyed by the resolved ACCESS KEY ID — an access key belongs to exactly one account, so the several clients cdkd builds from one credential chain in a deploy preflight (the bucket-existence probe, the shared `AwsClients.s3`, the region-corrected rebuild) share ONE round trip, while an assumed-role session (its own `ASIA…` key) still resolves its own account — which is what keeps the cross-account `Fn::GetStackOutput` `RoleArn` path correct. `recordResolvedAccountId(client, accountId)` seeds that cache from a `GetCallerIdentity` the caller ALREADY issued with the client's own credentials (the default-state-bucket name resolution); it is keyed by the client's credentials, not by a caller-supplied key, so it is a memoization rather than an override and cannot attach an account to credentials the caller does not hold), cdkd-owned-bucket deny policy (`deny-external-access-policy.ts` — `buildDenyExternalAccessPolicy(bucketName, accountId, region)`, the `DenyExternalAccess` document applied to all three buckets cdkd owns: the state bucket (`cdkd bootstrap`), the `cdkd state migrate` destination bucket, and the asset bucket (`ensureAssetStorage`). The three were byte-identical copies, and all three hardcoded `arn:aws:s3:::` — so outside the commercial partition the statement named a resource that does not exist there, matched nothing, and the deny protected NOTHING while `PutBucketPolicy` still succeeded and each command still printed its checkmark (issue [#1794](https://github.com/go-to-k/cdkd/issues/1794), the [#1745](https://github.com/go-to-k/cdkd/issues/1745) residual). Centralized so the partition is derived in ONE place and a fourth copy cannot re-introduce the class. **Every caller passes the region of the CLIENT that writes the policy** (`await client.config.region()`), never a local `region` variable — the rule is uniform so no call site has to judge whether its own variable is authoritative. That is not cosmetic: the first cut passed `bootstrap`'s `region` on the argument that credentials are partition-scoped so it must agree, and the PR review showed the code does not read the credentials' region at all — `region` is `options.region || AWS_REGION || 'us-east-1'`, a hardcoded commercial fallback, while `AwsClients` omits `region` when `--region` is absent and lets the SDK chain resolve the profile's. A non-commercial profile with no `--region` therefore reproduced the very defect on the fix's own path. ## SDK Providers

SDK Providers are in `src/provisioning/providers/`. See [README](../../README.md) for the full list of supported resource types. Registration is centralized in `src/provisioning/register-providers.ts`.

SDK Providers are preferred over Cloud Control API for performance -- they make direct synchronous API calls with no polling overhead. Cloud Control API is used as a fallback for resource types without an SDK Provider.
