# Key Files and Directories - cdkd drift

Rest of the analyzer layer: [layout-analyzer.md](layout-analyzer.md). Rest of the CLI layer: [layout-cli.md](layout-cli.md).

Index of every area: [code-layout.md](code-layout.md).

## Important Files

- **src/cli/commands/drift.ts** - `cdkd drift [<stack>...]` implementation. State-driven (no synth). Reads cdkd state from S3, asks each provider's optional `readCurrentState` for the AWS-current snapshot, and pipes the result through `src/analyzer/drift-calculator.ts`. **Secret dynamic references are reconciled here, and this file is where all three of the command's modes met the GHSA-p5qg-v9gv-hc7w redaction** (issue [#1914](https://github.com/go-to-k/cdkd/issues/1914)): the baseline holds unresolved `{{resolve:...}}` expressions while the readback holds the resolved plaintext, so `resolveStateSecretExpressions` (the synth-free counterpart of `rollback-executor.ts`'s `resolveReplayProps`) re-resolves the baseline for COMPARISON ONLY, and again inside `runRevert` before `provider.update` — replaying the literal token there set the live property to the expression string. **Both of those re-resolutions route each reference to the region that must ANSWER for it, not to the stack's** (issue [#2108](https://github.com/go-to-k/cdkd/issues/2108), the `drift.ts` half of #2057): since issue #1934 a cross-region cross-stack read records the PRODUCER's region-less spelling into the CONSUMER's state, so resolving it locally answers from a same-named secret in the wrong region — which on the DETECTION side is permanent phantom drift the baseline can never match plus a redaction needle holding the WRONG plaintext, and on the `--revert` side is a foreign credential handed straight to `provider.update` on a LIVE resource. `resolveDriftLeafByRegion` applies `classifyReplaySecretRegion` (since issue [#2134](https://github.com/go-to-k/cdkd/issues/2134) imported from `secret-region-classification.ts` via `rollback-executor.ts`'s re-export, so the two commands cannot answer differently) per reference over the WHOLE leaf before any of them is fetched, and routes a `named-region` verdict through `DriftSecretResolvers` — the structural twin of the replay's `ReplayResolvers`, one instance per STACK because the resolved-value cache lives on the resolver INSTANCE since #1933. The foreign-region evidence is `producerRegionsFromState(state)`, read straight off the record this command already loaded (`state.imports[].sourceRegion` / `outputReads[].sourceRegion`) — the rollback lane had to plumb that through `RollbackExecutorContext`; here it is one call with nothing to thread. An `ambiguous` verdict throws `DRIFT_SECRET_REGION_AMBIGUOUS`, and BOTH call sites already wrap the pass in a per-resource catch whose degradation is exactly the fail-closed behaviour wanted: detection falls back to the UNRESOLVED baseline, whose `{{resolve:...}}` leaves `calculateResourceDrift` SKIPS (not compared, rather than compared against a foreign plaintext, with `seededSecretPaths` still masking the position), and revert counts the resource unresolvable and returns BEFORE `provider.update`. The split is #2057's verbatim and deliberately NOT widened even though the state could sometimes name a single unambiguous foreign producer: an ARN naming a foreign region resolves PINNED there, a region-less name form with a foreign producer on record REFUSES. **The three evidence arguments are REQUIRED options, not defaulted ones** (`logicalId` / `consumerRegion` / `producerRegions`, with no `= {}` on the bag): omitting `producerRegions` verdicts `local` for every name-form reference, i.e. the pre-#2108 defect restored silently, and an omitted `consumerRegion` was worse still -- `''` matches no recorded region, so EVERY producer region reads as foreign and every name-form reference refuses. The rollback twin cannot be misused that way because its evidence rides the required `RollbackExecutorContext`; requiring these gives this side the same property, enforced by the compiler. **A refused resource is reported `notCompared`, and `--json` says so explicitly.** The comparator skips its `{{resolve:...}}` leaves, so the change list is empty -- where PRE-#2108 that resource reported (wrongly, but visibly) as `drifted`, which makes a silent `clean` a regression this change would otherwise introduce. Until issue [#2135](https://github.com/go-to-k/cdkd/issues/2135) the outcome WAS `clean`, carrying a `referencesUnresolved` boolean that every consumer had to remember to read; the default behaviour of forgetting was to report a resource cdkd never checked as one with no drift, and that shape cost two successive review rounds on the #2108 lane (first `--json`, then the exit code). `notCompared` is now a MEMBER of the outcome union, so a consumer switching on `kind` cannot fall through to the clean arm by omission -- `clean` means compared-and-matched and nothing else, and carries no completeness marker at all. The `notCompared` roll-up still lists every incomplete entry, the `drifted` variant included (its changes are real but are not the whole comparison), so a CI job can gate on ONE key (`notCompared.length === 0`, the honest "everything was actually checked" predicate) rather than on `drifted.length === 0`, which a SKIPPED comparison satisfies. Roll-up entries carry `referencesUnresolved: true` so the fact is readable off an entry rather than only off which array holds it. `writeHumanReport` prints the same roll-up as a `PARTIALLY compared` block, because the per-resource warning goes to the LOGGER and a user piping stdout sees only `no drift detected`. **And so does the EXIT CODE, which is the signal most CI gates actually read**: a detection-only run that drifts nowhere but left at least one comparison INCOMPLETE for a cause a re-run can clear -- a refusal, or (since issues [#2151](https://github.com/go-to-k/cdkd/issues/2151) / [#1945](https://github.com/go-to-k/cdkd/issues/1945)) a read that threw -- throws `DriftComparisonIncompleteError` (`exitCode = 2`, this repo's "work completed but something was SKIPPED" code) instead of returning. The class was `DriftComparisonRefusedError` while `refused` was its only cause; it is private to the file, so the rename had no import site. That is a PRESERVATION rather than a new signal -- pre-#2108 the same population resolved in the wrong region, reported phantom drift and exited 1, so exiting 0 would have been the silent downgrade -- and DRIFT WINS when both hold, so a consumer gating on `=== 1` loses no detection it gets today. Scope is detection-only: `--accept` / `--revert` keep their documented codes. **The exit trigger is a STRICT SUBSET of the roll-up, and that asymmetry is load-bearing.** "Not compared" has two causes -- the resolution THREW, or a `{{resolve:...}}` token merely survived -- and the second is a large PRE-EXISTING population (`ssm-secure`, which cdkd resolves for nobody, because CloudFormation resolves it server-side) that predates #2108 and can never clear on a re-run. Driving the exit off the union of both would fail those users' CI forever over an unrelated defect, which is the same "permanently non-zero" hazard `docs/cli-drift.md` cites as a reason not to report an absent write-only credential as drift. So the cause is carried as a `NotComparedCause` enumeration rather than as two booleans, and `outcomeExitSignal` maps the CLEARABLE causes to exit 2 while `'unresolvedToken'` exits 0. Issues [#2151](https://github.com/go-to-k/cdkd/issues/2151) / [#1945](https://github.com/go-to-k/cdkd/issues/1945) added the third member `'readFailed'` and rewrote that map as an EXCLUSION of `'unresolvedToken'` rather than an inclusion list, so a cause added later defaults to the non-zero side -- the default #2135 made impossible for a VARIANT was still reachable one level down, at the CAUSE. Those two issues are also why the whole per-resource body from the read to the outcome push now sits in ONE try/catch: a throw from any of `provider.readCurrentState`, the Cloud Control fallback, `getDriftUnknown/UnorderedPaths`, `canonicalizePrincipalUniqueIds`, `canonicalizeIpProtocols`, `canonicalizeDriftProperties`, `calculateResourceDrift` or `redactDriftChanges` used to propagate out of the loop and out of the command, leaving every other resource in the stack -- and under `--all` every remaining STACK -- unchecked. `isNoReadHandlerError` splits the catch by whether a RE-RUN CAN CLEAR IT: an `UnsupportedActionException` / `TypeNotFoundException` (matched through the cause chain, since `CloudControlProvider.handleError` re-wraps them) reports `unsupported` and exits 0, because it is the same no-read-path condition the fallback otherwise signals by returning `undefined`; everything else is `readFailed`.  The `--json` `notCompared` entries gained a `cause` key and their `referencesUnresolved` stopped being the literal `true`, which it no longer is for a `readFailed` one; the `--json` roll-up and the human block still cover both populations, because as INFORMATION both were genuinely not compared. One enumeration replaced two nearly-identical booleans (`referencesUnresolved`, `comparisonRefused`), which is what #2135 fixed structurally: the population mapping is byte-equivalent to the old pair, and the exhaustiveness fence is `matchOutcome`, whose handlers are a mapped type over the union's `kind`, so adding a variant is a COMPILE error at every consumer rather than a silent wrong answer (proven by probe: a temporary sixth variant fails at all eight). `writeHumanReport` follows the ROLL-UP rather than the exit code -- deliberately, since keying the glyph on the narrower subset would print `✓ ... 1 resource checked` directly above a `PARTIALLY compared` block naming that same resource: the summary line switches from `✓` to `⚠` and reports `<n> of <m> resources fully checked`, since counting a not-compared resource as `checked` contradicted the `PARTIALLY compared` block two lines below it. Issue [#2154](https://github.com/go-to-k/cdkd/issues/2154) added a THIRD branch ahead of both: a stack where `notCompared.length === 0 && checked === 0 && outcomes.length > 0` prints `⚠ ... NOTHING was compared`. All three conjuncts matter -- the first is what keeps a `notCompared`-only stack (a `readFailed` one included) in the EXISTING `⚠` branch, which already says `0 of N fully checked` and names each resource, so the branch fires exactly when every outcome is `unsupported` or `skipped`, because the extreme case of the question the glyph answers was getting the opposite answer from the one the rule implies. It covers the `skipped`-only stack too, which #2154 flagged as its own user-visible call: #323's decision was that a Custom Resource is not ACTIONABLE, which keeps it out of the counts but is not a reason to claim it was checked. The EXIT CODE is untouched by that branch -- `unsupported` and `skipped` still map to `none` -- so it changes only the claim printed about coverage. **`unsupported` is outside BOTH counts** (issue [#2141](https://github.com/go-to-k/cdkd/issues/2141)): main's arithmetic counted it as inspected, so a stack whose only resource has no `readCurrentState` printed `1 resource checked` for a resource cdkd never READ -- #2135 preserved that deliberately rather than change a user-visible number under cover of a refactor claiming byte-equivalence, and #2141 is the change itself. `inspectedCount` now increments in three arms (`drifted` / `clean` / `notCompared`) and none in the two where no read happens, so `skipped` (#323, not actionable) and `unsupported` (no read possible) are excluded for the same reason from opposite directions; the totals are still printed, from `unsupported.length` and the `--json` `notSupported` array, so nothing is lost. The two REPORT readers -- the `--json` roll-up and the human block -- go through ONE `notComparedOutcomes` predicate, because a predicate spelled per reader is how a payload and a rendering come to disagree about the same run; the exit code is the deliberate third answer, and it has its own named predicate rather than an inline condition so the divergence is legible instead of looking like a bug. Both warnings also BRANCH on whether the error is a REFUSAL: a refusal says `refused to resolve` / `refused to re-resolve`, not `could not`, since describing a deliberate decision as a read failure sends the reader hunting for an IAM grant that is not missing. The branch asks `isDriftSecretRefusal(err)` -- a POSITIVE test for the `DriftSecretRefusalError` class both refusals are raised as -- rather than enumerating codes: the two sites originally compared against `DRIFT_SECRET_REGION_AMBIGUOUS` alone, so `DRIFT_SECRET_TOKEN_SCAN_MISMATCH` (whose own message says "Refusing rather than resolving") silently took the read-failure wording, and enumerating bad shapes loses that race every time a third refusal is added. That guard is source-fenced (`tests/unit/cli/drift-secret-refusal-is-positive.test.ts`) rather than driven through the command, because the token-scan refusal is an internal-invariant guard no input reaches while the scanner is correct. **Accepted cost on the refusal path, recorded because it is a behaviour change rather than a side effect**: the per-resource `secrets` map is CLEARED there, so only the offline positional `seededSecretPaths` masks that resource. For the KNOWN OVER-REFUSAL (a purely local name-form reference in a stack with any foreign producer region on record -- CDK's ordinary `secretValueFromJson` shape) the pre-#2108 map held the CORRECT plaintext and value-based redaction masked it wherever it appeared, including at paths whose state side carries no `{{resolve:` for the positional seed to find. Kept anyway: the alternative is resolving the reference to build the needle, which is the wrong-region fetch this whole change exists to refuse. **Pre-v8 residual, the same one #2057 carries**: a cross-region `Fn::GetStackOutput` on a stack last deployed under schema v7 has no `outputReads`, so `producerRegionsFromState` is empty, every name-form reference verdicts `local`, and the wrong-region resolution persists until the next deploy writes a v8 record. The resolved baseline no longer trips `calculateResourceDrift`'s `{{resolve:` skip (PR #1899), so a console edit of a secret-bearing property is detectable and revertible again; that skip is now the FALLBACK for a reference cdkd cannot resolve at all. **Redaction is keyed on the PATH as well as on the value, and the path half is what a value-keyed map structurally cannot supply.** The resolution records both a per-resource `RecordedSecretValues` and the set of PATHS that produced one, and `redactDriftChanges` rewrites each side of every `PropertyDrift` as the outcome is BUILT — the one choke point behind the human report, the `--json` payload, both plans, and the value `--accept` persists. The value pass puts a recorded plaintext back on its own expression; the path pass then answers the case the map cannot, because the map holds what the reference resolves to TODAY: after a Secrets Manager ROTATION the deployed resource still carries the previous version, so the path drifts and the AWS side matches no key — a real secret that would otherwise be printed verbatim and persisted. At a known-secret path the only value ever shown is the expression itself; anything else becomes `SECRET_MASK`, `undefined` / `null` excepted (an absent key discloses nothing). `change.path` is masked too, since `redactSecretsForState` walks values and never object KEYS, and a masked path also marks the change secret-bearing. `runAccept` then REFUSES any path whose value came back masked, with a warning naming it: writing `***` would corrupt the baseline and make the next deploy push the literal mask at AWS. The refusal is per-PATH, so the non-secret drifts in the same resource are still accepted. **`runAccept` also redacts the bag it persists**, positioned against the record's own `properties` with `STATE_SOURCED_READBACK_RULES`, and that is NOT a duplicate of the change-level pass: what it reaches is the untouched clone of the record's baseline, which is exactly where a plaintext survives for any user who ran `--accept` on a pre-fix binary — and the positioned form is what names a stored plaintext that a rotation has since made unrecognisable to the map. Its old pinning hazard (rewriting an accepted console edit back to the expression) is gone because such a path is now refused before it can reach the bag. The revert's own narrowing write (#1644) is positioned against the bag the revert RESOLVED (`observedProperties ?? properties`) rather than against `properties`, with `STATE_SOURCED_READBACK_RULES` and NOT the rollback executor's `STATE_DERIVED_RULES`: the delta descends from `buildRevertNewProperties`'s merge of the AWS-CURRENT snapshot with the resolved desired subtrees, so a non-drifted top-level key comes from AWS and may be reordered, and positional array descent would write a sibling's expression onto the wrong element. **Every failure mode of the new lookups is per-resource, never fatal.** A deleted secret, a rotated-away version, or a least-privilege role without `secretsmanager:GetSecretValue` / `ssm:GetParameter` warns and falls back to the unresolved baseline for that one resource; `--revert` reports it as a per-resource failure with its own message instead of `AWS update failed`. **An ABSENT `awsValue` at the EXACT leaf known to hold a secret is DROPPED, not reported** (`secretPaths.has(path)`, not the ancestor-matching `isSecretBearingPath` — a whole subtree vanishing from AWS is real drift the user wants, and pre-#1899 it was reported because that skip only ever covered leaf strings; an absence that survives the drop is instead added to `maskedPaths`, so it is reported AND refused by `--accept`, which would otherwise delete the key and the reference with it): a write-only credential is returned by no readback, and PR #1899's `{{resolve:` skip used to cover exactly that — it stopped covering it precisely because this PR makes the baseline arrive RESOLVED. Reporting it instead is three bugs (permanent exit 1; `--accept` writing `undefined`, which `setAtPath` turns into a DELETED key, erasing the reference out of `properties`; and `--revert` re-pushing the credential every run), and the drop is scoped to `positionIsSecret` rather than to `secretBearing` so a key whose NAME carries a secret is still reported and still refused. `redactDriftChanges` therefore runs BEFORE the clean/drifted decision, since it can empty the change list. A SURVIVING `{{resolve:...}}` token (the resolver's unsupported-service arm warns and returns the literal; `ssm-secure:` is the live spelling) marks its path secret-bearing — but ONLY for a spelling that is secret by definition (`isSecretBySpelling`: CloudFormation defines exactly three services and cdkd resolves the other two), since masking text that merely looks like a reference leaves a path refused by `--accept` and pinned by the revert with no remedy. **`preserveLiveValuesAtUnresolvedTokens` REGISTERS the live values it copies in** (`plaintext -> token`), under three conditions that each remove a different way of being wrong — the leaf must be a WHOLE token (a mixed leaf's send string is already partially resolved, so registering it whole writes the resolvable half's plaintext into state), the spelling must be secret by definition (registering a look-alike's live value makes a needle out of ordinary data), and the live value must clear the needle floor (`redactSecretsForState`'s whole-value branch matches at ANY length, so a live `"1"` would rewrite every unrelated delta leaf equal to it into the token — the #1904 corruption). Preservation itself is gated on the leaf being a WHOLE token, and that gate is a DISCLOSURE boundary rather than tidiness: copying a live value into a MIXED leaf would move the `ssm-secure` plaintext into the payload while the registration guards correctly decline to register it, so the mechanism would CREATE an exposure it cannot mask (unmaskable in the narrowing delta, the retry log and the AWS error text alike). Declining to preserve there restores the pre-#1914 behaviour for that narrow shape — the literal ships, which is what `cdkd deploy` does. **The residual that remains is not created by this command's own bags**: a provider can echo its own readback in `effectiveProperties`, and the #1644 narrowing persists it with no map entry to match; that write previously had no redaction at all, and closing it needs span-masking (issue [#2102](https://github.com/go-to-k/cdkd/issues/2102) — NOT #1935, whose fix only reaches a leaf the value scan can MATCH). A non-string live value is neither registered nor positionable and is a stated residual before the update call, the narrowing redaction and the error masking: `secrets` is empty by construction there — nothing was recorded, which is what made the token a survivor — so moving the plaintext without registering it handed it to three readers that would each have masked it, and an array-nested one (ECS `ContainerDefinitions[].Environment[]`) reached neither the `descendArrays: false` position pass nor the empty value scan and landed in `state.json`. The general rule: a mechanism that deliberately moves plaintext into a bag must also register that plaintext with everything that masks. Such a token is reported and is reported through the pass's `onUnresolved` hook, and is deliberately NOT a failure — failing would abandon every other drifted property on the resource and exit 2. **The `ssm-secure` path is the one place where "the token is already what AWS holds" is FALSE**, and both halves of that matter: CloudFormation resolves `ssm-secure` SERVER-side, so a record adopted by `cdkd import --migrate-from-cloudformation` carries the literal in state while AWS holds the PLAINTEXT. So the path must be masked (`secretPaths.add` on the survivor, exact because `ssm-secure` is secret by spelling — `diffAt` never descends arrays, so an ECS `Secrets[]` drift otherwise reports the whole array with the plaintext in it), and `preserveLiveValuesAtUnresolvedTokens` must run before `provider.update` so the revert leaves the live value at those positions untouched instead of overwriting a working secret with a literal. Deciding by what AWS HOLDS rather than by provenance needs no state flag and is exact in both directions: a cdkd-deployed record has the token live, so copying it back is the same no-op; a migrated one has the resolved value, which survives. Where AWS has nothing at that position the token is kept, since that is what `cdkd deploy` sends. `survivingDynamicReferences` scans with `[^}]+` to agree with the RESOLVER's own pattern (a `{` inside a token separates them) and reports only tokens present in the INPUT, since the scan runs over the RESOLVED string and a secret can contain reference-shaped text. It used to be the ONLY one of cdkd's four spellings that agreed with the resolver, and this entry recorded the split with `isWholeDynamicReference` as a deliberate OPPOSITE agreement — issue [#1936](https://github.com/go-to-k/cdkd/issues/1936) measured that claim and found it wrong in the consequential direction: the questions the two predicates answer do differ, the CHARACTER CLASS does not, and the strict sibling's `[^{}]*` PERSISTED PLAINTEXT for a reference whose inner text contains a `{` (a Secrets Manager JSON key, e.g. `{{resolve:secretsmanager:app/db:SecretString:my{key}}`) — the resolver resolved it, the source arm then refused it as not-a-single-token, and on the #1900 empty-map path the resolved value was stored verbatim. All four now derive from ONE exported constant in `secret-redaction.ts` (`DYNAMIC_REFERENCE_INNER`, byte-identical to the resolver's own `([^}]+)` capture), and `isWholeDynamicReference` is that module's `isSingleDynamicReferenceToken` imported under this file's local name rather than a hand-copied twin. `survivingDynamicReferences` imports the ASSEMBLED scan (`dynamicReferenceTokens`) rather than rebuilding one from the shared class, because sharing only the class is how the four spellings started: the flags and anchors around it are as forkable as the class itself, and the re-fork is behaviourally identical, so nothing but a fence would notice. That fence states the good condition POSITIVELY — a regex matching a `{{resolve:` token must escape both braces, and only `intrinsic-function-resolver.ts` (once, the authority) and `secret-redaction.ts` (twice) may write one, ZERO anywhere else under `src/**` — after three rounds of enumerating bad spellings each let a fourth through. The report names only the TOKENS, never the leaf that held them, because `resolveDynamicReferences` substitutes token by token and a mixed `secretsmanager` + `ssm-secure` leaf comes back carrying real plaintext. For the same reason the detection failure arm masks its message BEFORE clearing the value map, which is why the clear sits after the log. Every AWS error string a revert prints is run through `maskSecretsInText` — the payload carried resolved secrets and AWS quotes the offending value, the same fence `deploy-engine.ts` applies to its own provider calls. **The path answer survives a failed lookup**: `collectDynamicReferencePaths` seeds a SECOND path set offline from where the `{{resolve:` strings simply are, and the report uses the PROVEN set when resolution succeeded and that seed when it did not. Without it the composition of the two failure modes leaks — the comparator's `{{resolve:` skip only re-arms for a LEAF whose state side is a string, so a resource whose `observedProperties` lack the secret's parent drifts at the ANCESTOR with the whole AWS subtree as `awsValue`. The seed is coarser (it cannot tell a public ssm reference from a secret one) and therefore over-masks, which is the direction to err in. **`--accept` refuses two ways**, through one `acceptRefusalReason` predicate shared with `printAcceptPlan` so a `--dry-run` cannot promise a write the run refuses: a masked VALUE, and a masked PATH (a readback keyed BY a secret — `setAtPath` would otherwise invent a key literally named `***`, and with an `undefined` value INSERT it rather than removing the real one). The path check is what makes `redactDriftValue`'s `undefined` / `null` / whole-expression exemptions safe. The refusal is keyed on a `maskedPaths` SET carried on the outcome rather than on comparing a value to `SECRET_MASK`, so a property whose real value is the string `***` at an ordinary path is not refused forever — and a masked path is not detectable from the value at all. The same set tells `runRevert` which subtrees `buildRevertNewProperties` cannot overlay (its key is the path's TOP-LEVEL segment, which a mask makes unmatchable), so the user is told rather than silently not reverted; the accept refusal for that case names ROTATION as the remedy, since a plaintext that leaked into a property NAME is unremovable by any pass — they all walk values. `--accept` also CHECKS each accepted value after the redaction pass and warns when it was overwritten: a PUBLIC `{{resolve:ssm:...}}` can sit in `properties` via the `cdkd import` warn path, and `trustAnyExpression` then wins over the accepted value, which would otherwise be a silent permanent no-op. A revert that could not re-resolve is counted apart from an AWS update failure (it never reached `provider.update`), and the provider lookup + payload build are inside per-resource guards — pre-existing gaps where one unroutable resource aborted the whole run. `carriesRecordedSecret`'s substring branch carries the same 4-character needle floor `secret-redaction.ts` applies when building needles (copied, since that constant is module-private), so it errs toward NOT marking: a sub-threshold plaintext is one the redactor would not substitute anyway, and marking it would mask a PUBLIC reference that merely contains those characters. Auto-selects the single stack in state when no positional arg / `--all` is given (mirrors `cdkd deploy` / `cdkd destroy`); errors with a listing when state has more than one stack. Exits 0 when nothing drifted and nothing was REFUSED, 1 on drift detected (or on a command error), 2 when nothing drifted but a comparison was refused (see the `notCompared` paragraph above -- narrower than the roll-up) or when `--revert` partially failed. `--accept` (state <- AWS) and `--revert` (AWS <- state) both ship; `buildRevertNewProperties` overlays each drifted top-level subtree from the baseline onto the AWS-current snapshot, EXCEPT the AWS-SERVICE-authored entries of a top-level TAG LIST (`mergeTagListForRevert`, issue #1501 — an ordinary console-added tag is still STRIPPED, but `AmazonECSManaged` / any `aws:`-prefixed key survives; gated on a top-level property NAMED `Tags`/`*Tags` rather than on the `[{Key,Value}]` shape alone, which `LoadBalancerAttributes` also matches, and applying even to an EMPTY recorded baseline, because ECS requires the former for managed scaling and AWS reserves the latter; `findRevertPreservedTagKeys` names them in the plan before the confirmation prompt. This is the issue's option 2: option 1 — diffing the WHOLE tag list — was implemented first and FAILED the `drift-revert` integ, whose fixture requires --revert to strip an injected tag). `buildRevertNewProperties`'s `preserveUntemplated` option (issue #1626 items 2 + 3) settles what "absent from desired" MEANS on this caller: the deploy engine passes the last-deployed TEMPLATE as `previousProperties`, so an absence is a template removal, while `runRevert` passes the full `readCurrentState` snapshot, so it ALSO covers a never-templated path — and both provider shapes then destroy it, by different routes (one that KEY-DIFFS a collection reads the absence as a REMOVAL — ELBv2's `LoadBalancerAttributes` carries ~20 AWS-reported keys against a template declaring one or two; one that REPLACES a bag wholesale, e.g. the documented full-replace `PutBucketTagging`, never consults the previous side at all and simply sends a bag the path is missing from). So when the reverted resource has NO `observedProperties` — the baseline is the raw template, where an AWS-authored value and an out-of-band change are indistinguishable — `mergeUntemplatedValue` merges every untemplated path into the bag cdkd SENDS; with `observedProperties` present the baseline IS a deploy-time snapshot, an absence is genuinely an out-of-band addition, and the wholesale overlay is unchanged (which is what the `drift-revert` integ's injected-tag assertion depends on). The fix is on the DESIRED side rather than trimming `previousProperties` precisely because trimming stops the key-diffing removal but leaves the wholesale-replace drop untouched — half the reported paths would still be erased while the plan claimed otherwise. Under the flag the merge is a strict SUPERSET of the #1501 tag carve-out (which keeps only service-authored entries), so it subsumes that branch rather than competing with it — which required BOTH `mergeUntemplatedValue` AND `collectMissingPaths` to accept a DECLARED-but-EMPTY baseline list alongside a populated one: `isKeyedList` deliberately requires a NON-empty array, so a condition-collapsed `Tags: []` fell through to the merge's wholesale arm and handed AWS `[]`, stripping `AmazonECSManaged` — the exact loss the carve-out exists to prevent — while the REPORTER fell to its own whole-list arm, which only fires on an `undefined` desired side and so named nothing at all. Fixing only the merge (the first review pass) left the plan silently under-claiming what survives, which the second review caught; both arms now mirror each other and the correspondence test carries the empty-baseline shape. This inverts the pre-#1626 'emptiness is deliberately excluded' contract on the DESIRED side only, which is safe because the reporter has exactly one caller and it runs only on the template-only baseline. The merge also DEDUPES by `Key`, because AWS can report one twice and `PutBucketTagging` / `ModifyLoadBalancerAttributes` reject a duplicate. The structural rules mirror `collectMissingPaths` case for case — plain records descend, KEYED `[{Key,Value}]` lists merge by `Key`, positional arrays and scalars come from the baseline wholesale — so every path `findRevertUnbaselinedAwsKeys` (renamed from `findRevertDroppedAwsKeys`, since they are now PRESERVED rather than dropped) names in the plan is rescued by the merge and the merge rescues nothing the plan failed to name; a unit test pins that correspondence by diffing the flag-on and flag-off outputs. A service-authored tag is in NEITHER list and that is the carve-out being consistent: it is preserved on the default path too, so the flag does not rescue it, and `isServiceManagedTagKey` omits it from the plan because reporting it would warn about a loss that cannot happen — the test pins that it survives under both settings.

- **src/analyzer/drift-calculator.ts** - State-vs-AWS property comparator used by `cdkd drift`. Only descends into keys present in cdkd state, so AWS-managed fields cdkd never set (timestamps, generated identifiers, account-wide defaults) cannot surface as false-positive drift. Also exports `undeclaredEmptyObservedKeys(observed, declared)` (issue #1498): on the observed-properties baseline, a top-level key the template never declared whose captured value was EMPTY (`[]` / `{}` / `null`) is fed into `ignorePaths` by `drift.ts` — such keys are materialized AFTER the per-resource capture by sibling resources (`ClusterCapacityProviderAssociations` -> `Cluster.CapacityProviders`, standalone `LifecycleHook` -> the ASG's hook list, standalone SG rules) or by AWS itself, and comparing them produced permanent phantom drift that `--revert` then destructively stripped; an undeclared key captured with a real value stays compared. Accepts an optional `ignorePaths` list (sourced from each provider's `getDriftUnknownPaths`) to skip state property paths the provider deliberately cannot read back from AWS — e.g. Lambda `Code: { S3Bucket, S3Key }`, which `GetFunction` only returns as a pre-signed URL — so a clean run reports no drift on those keys instead of the guaranteed false positive that would otherwise fire on every invocation. `drift.ts` passes the resource's state-recorded `properties` as that method's optional second argument (issue #1602), so a path unreadable only for a SUBSET of a type's resources can be scoped per resource rather than switching the key off for the type: `ApiGatewayV2Provider` declares `TlsConfig` unknown only when `ConnectionType !== 'VPC_LINK'`, because AWS silently discards the field on a public integration and returns it on a private one. `DynamoDBTableProvider` is the second consumer (issue [#1760](https://github.com/go-to-k/cdkd/issues/1760), PR [#1769](https://github.com/go-to-k/cdkd/pull/1769)) and a usefully DIFFERENT shape: ApiGatewayV2 scopes on a SIBLING property's value, whereas this one scopes on whether the template declares the property AT ALL — `WarmThroughput` is unknown unless the desired bag declares it, and `GlobalSecondaryIndexes` / `LocalSecondaryIndexes` likewise — and it uses the seam to cover an UPGRADE transition rather than a configuration split, since records written by an earlier binary already froze the AWS-computed value into `observedProperties`. Its predicate answers DECLARED for an absent or uninformative bag (`declaresWarmThroughput` returns `true` there), which is that rule's concrete spelling: a bag that was never populated is not evidence the template declared nothing. A provider must tolerate an absent bag by falling back to the type-level answer (defaulting to COMPARING — hiding real drift is the worse failure). Before any comparison it canonicalizes both the baseline and AWS-current sides through `src/analyzer/drift-normalize.ts` so that AWS returning a tag list, a resource-id/ARN array, or a provider-declared unordered set of plain strings or of objects (`options.unorderedPaths`, sourced from `getDriftUnorderedPaths`) in a different order than the deploy-time snapshot does not surface as phantom drift (the `deepEqual` walk compares arrays positionally). The LAST pass in that chain is the provider's own `canonicalizeDriftProperties(resourceType, properties)` (issue [#1784](https://github.com/go-to-k/cdkd/issues/1784), applied by `drift.ts` to BOTH sides) — the seam for a difference no PATH can name, a member of an ARRAY ELEMENT: since `diffAt` compares arrays wholesale, `isIgnoredPath` is never asked about a path crossing one, so the only expressible suppression is the WHOLE array and suppressing `GlobalSecondaryIndexes` would mean never detecting an index add / remove / capacity change again. Stripping the AWS-managed member from BOTH bags converges an old `observedProperties` record with a new readback instead, keeping the array compared. It takes no `side` argument on purpose (one-sided normalization is the mistake `drift-normalize.ts`'s header records — it manufactures drift on the `properties`-fallback baseline), must be pure / non-mutating / identity-returning when inapplicable, and is applied to the COMPARISON copies, so the `aws` bag `--revert` diffs against is untouched. **`--accept` is NOT symmetric with that**: it writes each change's `awsValue`, which comes from the CANONICALIZED bags, so a stripping canonicalizer makes `--accept` persist the stripped shape on a path that still drifts (the call site in `drift.ts` says so, and `tests/unit/cli/drift.test.ts` pins it). That is the intended direction — state should stop carrying a member the readback no longer reports — but it means the hook is a WRITE, not only a comparison filter, which a provider author must know before declaring one.
- **src/analyzer/drift-normalize.ts** - Order-normalization helpers for `drift-calculator.ts`. `canonicalizeTagListsDeep` sorts any `{Key,...}[]` tag list by `Key`; `canonicalizeIdArraysDeep` sorts any array whose every element is an AWS resource id (`subnet-…`, `sg-…`) or ARN. Both recurse and are applied to BOTH comparison sides — AWS does not guarantee element ordering across reads, and these two kinds are semantically unordered sets, so without this every reorder would be a false positive. Surfaced by dogfooding the sibling `cdk-real-drift` tool. Plain-string arrays and non-tag OBJECT arrays are NOT canonicalized heuristically (either can be order-significant); instead `canonicalizeUnorderedArraysAtPaths(value, paths)` sorts such an array ONLY at an explicit per-provider opt-in path list, sourced from the new optional `ResourceProvider.getDriftUnorderedPaths(resourceType)` and threaded through `calculateResourceDrift`'s `options.unorderedPaths` by `drift.ts` (issue [#1096](https://github.com/go-to-k/cdkd/issues/1096) item 1). Issue [#1620](https://github.com/go-to-k/cdkd/issues/1620) extended the pass from plain-string arrays to arrays of OBJECTS, sorted by a private key-order-independent `canonicalJson` — key order must not participate, since AWS's readback order for an object's own keys is no more guaranteed than its order for the list, so a raw `JSON.stringify` sort key would reintroduce the phantom drift the pass removes. Each shape is sorted only when the array is HOMOGENEOUS in it; a MIXED array (strings and objects, a `null` element) is left untouched. Both provider-declared path lists share ONE matcher — the exported `matchesPathPrefix(path, entries)` (exact match, or entry followed by `.`), which `drift-calculator.ts`'s `isIgnoredPath` is now a thin alias over — so the two cannot silently drift apart. A plain entry is a SUBTREE declaration; appending `LEAF_ONLY_PATH_SUFFIX` (`[]`) claims the path ALONE (issue [#1783](https://github.com/go-to-k/cdkd/issues/1783)). The leaf-only form exists because THIS walk descends into array elements, so a subtree entry for an object list also claims every array nested inside its elements — `AWS::DynamoDB::Table.GlobalSecondaryIndexes` is an unordered set keyed by `IndexName` while each element's `KeySchema` is order-SIGNIFICANT (HASH before RANGE), so the only available spelling would have sorted the per-index key schema and HIDDEN a real key change, which is why #1767 shipped the reverse-map half and left the ordering half undeclared. The marker is honored by BOTH lists rather than only by the one that needed it, so their spellings cannot diverge (which is the whole reason the matcher is shared); a bare `'[]'` entry matches NOTHING, since it would otherwise name the root bag. One required divergence: `isIgnoredPath` never sees a path crossing an array (the comparator compares arrays wholesale via `deepEqual`), whereas the unordered walk descends into array elements and gives them the parent's path, so `'Items.Aliases'` is meaningful for `getDriftUnorderedPaths` but inert as an ignore-path — strictly more permissive. Nested arrays are not descended into, so an array-of-arrays at a declared path never has its inner lists sorted. `ELBv2Provider` declares `AWS::ElasticLoadBalancingV2::TargetGroup.Targets` (the first object-array consumer, #1620) — which is what let `Targets` move OUT of that provider's TYPE-level `getDriftUnknownPaths` and start being compared at all; its `readCurrentState` reads them back via `DescribeTargetHealth`, excluding exactly the `draining` state (a just-deregistered target keeps reporting for minutes, and freezing one into the deploy-time snapshot is permanent phantom drift) while INCLUDING every other state, since `initial` / `unused` / `unhealthy` / `unavailable` are all registered and health is not registration. The unknown-path entry did not disappear, it became PER-RESOURCE via the #1602 seam: `Targets` is still ignored for a target group whose TEMPLATE declares none, because an ECS-service / ASG-fronting target group has its members registered by the SIBLING resource and re-registered on every scale event — comparing that would report drift on an untouched stack and `--revert` would deregister the tasks the service just placed (the #1498 class; `undeclaredEmptyObservedKeys` only covers it when the capture happened to be empty, which for a redeployed running service it is not). An explicit `Targets: []` IS a declaration and stays compared. `KinesisStreamProvider` declares `AWS::Kinesis::Stream.DesiredShardLevelMetrics` (issue #609) — enhanced-monitoring metrics come back from `DescribeStream` in an order matching neither the request nor alphabetical (measured us-east-1, 2026-08-12), and the same backfill made the field's order observable in the first place by expanding the `ALL` shorthand into the seven names AWS stores. `DynamoDBGlobalTableProvider` declares `AWS::DynamoDB::GlobalTable.AttributeDefinitions` (issue [#1742](https://github.com/go-to-k/cdkd/issues/1742)) — `DescribeTable` returns the definitions in an order matching neither the request nor alphabetical (measured us-east-1, 2026-08-13: a table declaring `[pk, gsipk]` read back as `[gsipk, pk]`), and the list is a genuine set keyed by `AttributeName`, so sorting it cannot hide a real change. `KeySchema` is deliberately NOT declared at either level, being order-SIGNIFICANT (HASH before RANGE). The same paragraph's reachability note is what kept this unseen: it only bites on the `properties` baseline a reverse-replacement rollback leaves behind, since `rollback-executor.ts` strips `observedProperties`. `DynamoDBTableProvider` declares the same path for the sibling `AWS::DynamoDB::Table`, whose readback is identical one type over (issue [#1760](https://github.com/go-to-k/cdkd/issues/1760), shipped in PR [#1769](https://github.com/go-to-k/cdkd/pull/1769)). The per-index `WarmThroughput` half of #1742 has since SHIPPED (PR [#1859](https://github.com/go-to-k/cdkd/pull/1859)): `DynamoDBGlobalTableProvider` is the first consumer of the `canonicalizeDriftProperties` seam (issue [#1784](https://github.com/go-to-k/cdkd/issues/1784), described in the `drift-calculator.ts` entry above), naming the `{ listKey: 'GlobalSecondaryIndexes', member: 'WarmThroughput' }` PAIR in a closed `DRIFT_STRIPPED_INDEX_MEMBERS` table — a list-plus-member pair, NOT a path: this seam takes no paths at all, which is the whole reason it exists two sentences above and stripping that member from BOTH comparison sides. The two halves had to land together: `readCurrentState` reverse-maps the AWS `GlobalSecondaryIndexWarmThroughputDescription` into the CFn shape, surfacing only the two user-settable sub-fields and DROPPING the `Status` member CFn has no concept of — and dropping a readback key otherwise strands every already-written `observedProperties` baseline (the [#1760](https://github.com/go-to-k/cdkd/issues/1760) class), which is exactly what the both-sides strip absorbs, since an old record and a post-fix readback converge on carrying no member at all. Two bounds belong with it: the convergence only reaches records written by a post-[#1420](https://github.com/go-to-k/cdkd/issues/1420) binary (an older bag holds the raw `GlobalSecondaryIndexDescription[]` and is already drifting on five other members — `IndexArn` / `IndexStatus` / `ItemCount` / `IndexSizeBytes` / `Backfilling`), and the accepted cost is that a DECLARED per-index `WarmThroughput` change is no longer reported by `cdkd drift` at all — a declared-gate is not expressible in a hook that sees ONE bag with no desired-side reference, which is the asymmetry `getDriftUnknownPaths` avoids for a TOP-LEVEL key. The sibling `AWS::DynamoDB::Table` type has the same per-element shape and has NOT adopted the seam — its own change with its own real-AWS verification, tracked as issue [#1812](https://github.com/go-to-k/cdkd/issues/1812). `FSxFileSystemProvider` declares only `WindowsConfiguration.Aliases`; `SelfManagedActiveDirectoryConfiguration.DnsIps` is deliberately NOT declared (AWS documents no set semantics for it and DNS resolver lists are conventionally preference-ordered — declaring an order-significant list would silently HIDE real drift, which is worse than the visible false positive of leaving it undeclared; same reasoning excludes ElastiCache `PreferredAvailabilityZones`). Declaring the path here rather than sorting inside the provider's `readCurrentState` reverse-mapper is load-bearing: the normalizer runs on BOTH sides, so it stays correct for the `properties`-fallback baseline (a resource deployed before observed-capture, whose baseline is the user's template order) — sorting only the read side would manufacture drift there.
- **src/analyzer/drift-principal-normalize.ts** - IAM principal-FORM canonicalization for `cdkd drift` (issue [#1515](https://github.com/go-to-k/cdkd/issues/1515)) — the sibling of `drift-normalize.ts` for a difference that is not about ORDER. AWS renders an IAM role / user principal inside a resource policy either as its ARN or as its `AROA…` / `AIDA…` unique id, substituting the unique id when the principal is transiently unresolvable at write time (the CDK `autoDeleteObjects` role is created concurrently with the bucket policy that references it) and re-rendering the ARN once it resolves; the deploy-time `observedProperties` capture stores whichever form came back, so `cdkd drift` compared two spellings of ONE principal and reported PERMANENT phantom drift that `--revert` could not clear (it wrote the recorded form back and AWS re-canonicalized on write — the #1096 / #1498 class on a different property; two back-to-back runs of the `drift-revert` fixture on 2026-08-10 disagreed for exactly this reason with no code change in between). Unlike its sibling this pass CANNOT be pure — the mapping is not derivable from the string — so the shape detection (`collectPrincipalUniqueIds` / `collectPrincipalArns` / `rewritePrincipalUniqueIds`, walking only `Principal` / `NotPrincipal` positions, where the two forms are interchangeable, and NOT a `Condition` value, where they are not) is pure and the one lookup goes through an injected `PrincipalUniqueIdResolver`; `drift.ts` supplies the live implementation (`iam:GetRole` / `GetUser` off the ARN via the shared `parseIamPrincipalArn`, cached per ARN for the whole command INCLUDING failures). `canonicalizePrincipalUniqueIds` rewrites BOTH sides to the ARN form — the race is symmetric, and one-sided normalization is the mistake `drift-normalize.ts`'s header already records — and short-circuits with NO AWS call unless a unique id AND a candidate ARN are both present. Only a pair PROVEN equal by the lookup is collapsed: a deleted role (exactly when AWS keeps the unique id forever), a cross-account principal, or a missing `iam:GetRole` permission all leave both sides untouched and the drift REPORTED, so the pass can never hide a real principal change. Known bound: a policy carried as a JSON STRING rather than a parsed object is not walked (re-serializing would risk manufacturing a different phantom drift).
- **src/utils/ip-protocol.ts** + **src/analyzer/drift-protocol-normalize.ts** - EC2 security-group `IpProtocol` VALUE canonicalization (the measured rename table + `canonicalizeIpProtocolValue` live in `src/utils/`, because they have TWO consumers in different layers; the analyzer module owns only WHERE in a resource's properties the canonicalization applies) for `cdkd drift` (issue [#1643](https://github.com/go-to-k/cdkd/issues/1643)) — the second sibling of `drift-normalize.ts` for a difference that is not about ORDER, and unlike `drift-principal-normalize.ts` it IS pure (the mapping is a closed, measured table, so no AWS lookup is needed). EC2 owns the spelling of a rule's `IpProtocol`: it accepts an IANA protocol NUMBER or a NAME and rewrites the four numbers it has a name for before storing the rule, so cdkd recording what it SENT (`'6'`, post-#1633) against a readback of what AWS HOLDS (`'tcp'`) was two spellings of ONE protocol — permanent phantom drift `--revert` could not clear, since it revokes and re-authorizes into the same state (the #1591 / #1633 class via a third route: those two fixed TYPE coercions on the SEND side, this is a VALUE mapping owned by AWS, so it belongs on the READBACK side and covers the inline `AWS::EC2::SecurityGroup.SecurityGroupIngress[]` / `SecurityGroupEgress[]` rules #1633 deliberately does not touch). The rename set was MEASURED, not guessed (us-east-1, 2026-08-12, ingress AND egress): exactly `1` -> `icmp`, `6` -> `tcp`, `17` -> `udp`, `58` -> `icmpv6`, while `-1` / `0` / `2` / `4` / `27` / `41` / `47` / `50` / `51` / `88` / `89` / `94` / `103` / `112` / `132` / `255` all read back as the number — so it is a CLOSED set of the four protocols EC2 has a name for, not the open-ended IANA list, and `-1` being unaffected is why #1633's live test came back clean. Case is AWS's too (`TCP` / `Tcp` / `tcp` authorized on one port collapsed into ONE `tcp` permission in the readback), so a name is matched case-insensitively and lowered — but ONLY the four KNOWN names, so the pass can never make two genuinely different values compare equal. Numbers canonicalize to their STRING form because an unquoted YAML `IpProtocol: 47` parses to a number while AWS always reads back a string. `canonicalizeIpProtocols(baseline, aws, resourceType)` is applied to BOTH sides by `drift.ts` right after the principal pass, and is scoped by a CLOSED `IP_PROTOCOL_PATHS` table (the two standalone rule types at the top level, `AWS::EC2::SecurityGroup` at `SecurityGroupIngress[].IpProtocol` / `SecurityGroupEgress[].IpProtocol`) rather than by a walk for any key named `IpProtocol` — a blanket rewrite would turn an unrelated `'6'` into `'tcp'`. EVERY number is stringified, not only an integer one, so a malformed `6.5` keeps the key it had before #1633 and `NaN` / `Infinity` do not collapse onto one JSON `null` bucket; anything that is neither a string nor a number, most importantly an unresolved intrinsic, is returned untouched, and an unchanged bag is returned by IDENTITY. **`canonicalizeIpProtocolValue` is ALSO consumed by `ec2-provider.ts`'s `sgProtocolKey`**, because the comparison is only half the defect: a standalone rule's physicalId is `<groupId>|<protocol>|<from>|<to>` built from the value cdkd SENT, so for `IpProtocol: 6` both the tuple pre-filter and the full-signature `sgRuleKey` compare in `readSecurityGroupIngressCurrentState` missed AWS's `tcp` rule entirely, the method returned `undefined`, and `cdkd drift` reported the resource as "drift unknown" FOREVER — one layer BELOW the phantom drift, and structurally invisible to a comparison-side fix because no AWS-side bag is ever produced (measured by the real-AWS `drift-revert-arrays` run on 2026-08-12, which is what surfaced it; the issue's own premise that the read "returns `tcp`" was wrong). Normalizing inside `sgProtocolKey` heals the standalone lookup, the inline-rule `reconcileSgRules` ordering AND the write-side `applySecurityGroupRuleDiff` revoke/authorize key from ONE definition of protocol identity, and mirrors the reason its existing comment already gives for stringifying a legacy numeric `-1`: keying the normalization is what heals the deployed population with no migration. Issue [#1648](https://github.com/go-to-k/cdkd/issues/1648) then extended the SAME fold to the DIFF side (`canonicalizeDesiredProperties`, for the standalone type and the `AWS::EC2::SecurityGroup` inline rule lists), because a template edit rewriting `IpProtocol: 6` to `'tcp'` otherwise read as a changed property — and since `IpProtocol` is create-only on the standalone type, that classified as a REPLACEMENT of a rule AWS already held exactly. The fold is deliberately NOT inside `narrowIngressIpProtocol`, which also feeds the CREATE path: the wire value is not the defect (AWS accepts either spelling and stores `tcp` for both), only the diff's classification is.
