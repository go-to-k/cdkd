# Key Files and Directories - cdkd drift

Rest of the analyzer layer: [layout-analyzer.md](layout-analyzer.md). Rest of the CLI layer: [layout-cli.md](layout-cli.md).

Index of every area: [code-layout.md](code-layout.md).

## Important Files

- **src/cli/commands/drift.ts** - `cdkd drift [<stack>...]`. State-driven (no synth): reads cdkd state from S3, asks each provider's optional `readCurrentState` for the AWS-current snapshot, pipes the result through `src/analyzer/drift-calculator.ts`. Auto-selects the single stack in state when no positional arg / `--all` is given (mirrors `cdkd deploy` / `cdkd destroy`); errors with a listing when state holds more than one. Exit codes: 0 nothing drifted and nothing REFUSED, 1 drift detected (or command error), 2 nothing drifted but a comparison was incomplete (narrower than the roll-up, below) or `--revert` partially failed.

  - **Secret dynamic references are reconciled here; all three modes met the GHSA-p5qg-v9gv-hc7w redaction** (issue #1914). The baseline holds unresolved `{{resolve:...}}`, the readback resolved plaintext, so `resolveStateSecretExpressions` (the synth-free counterpart of `rollback-executor.ts`'s `resolveReplayProps`) re-resolves the baseline for COMPARISON ONLY, and again inside `runRevert` before `provider.update` — replaying the literal token set the live property to the expression string.
  - **Both re-resolutions route each reference to the region that must ANSWER for it, not the stack's** (issue #2108, the `drift.ts` half of #2057). Since issue #1934 a cross-region cross-stack read records the PRODUCER's region-less spelling into the CONSUMER's state, so local resolution answers from the wrong region: phantom drift plus a needle holding the WRONG plaintext on detection, a foreign credential handed to `provider.update` on a LIVE resource under `--revert`. `resolveDriftLeafByRegion` applies `classifyReplaySecretRegion` per reference over the WHOLE leaf before any fetch (since #2134 imported from `secret-region-classification.ts` via `rollback-executor.ts`'s re-export, so the two commands cannot answer differently) and routes a `named-region` verdict through `DriftSecretResolvers` — the twin of the replay's `ReplayResolvers`, one instance per STACK since the resolved-value cache lives on the INSTANCE (#1933). Evidence is `producerRegionsFromState(state)` (`state.imports[].sourceRegion` / `outputReads[].sourceRegion`).
  - `ambiguous` throws `DRIFT_SECRET_REGION_AMBIGUOUS`; both call sites catch per resource, and the degradation IS the wanted fail-closed behaviour: detection falls back to the UNRESOLVED baseline, whose `{{resolve:...}}` leaves `calculateResourceDrift` SKIPS (`seededSecretPaths` still masking), and revert counts the resource unresolvable and returns BEFORE `provider.update`. The split is #2057's verbatim and NOT widened: an ARN naming a foreign region resolves PINNED there, a region-less name form with a foreign producer on record REFUSES.
  - **The three evidence arguments are REQUIRED options, not defaulted** (`logicalId` / `consumerRegion` / `producerRegions`, no `= {}`): omitting `producerRegions` verdicts `local` for every name-form reference (the pre-#2108 defect, silently), and an omitted `consumerRegion` is worse — `''` matches no recorded region, so every name-form reference refuses. The rollback twin gets this from the required `RollbackExecutorContext`; here the compiler does.
  - **Pre-v8 residual (the same one #2057 carries)**: a cross-region `Fn::GetStackOutput` on a stack last deployed under schema v7 has no `outputReads`, so `producerRegionsFromState` is empty, every name-form reference verdicts `local`, and the wrong-region resolution persists until the next deploy writes a v8 record.
  - **A refused resource is reported `notCompared`, and `--json` says so.** Its `{{resolve:...}}` leaves are skipped so the change list is empty, and a silent `clean` there would be a regression on the pre-#2108 (wrong but visible) `drifted`. `notCompared` is a MEMBER of the outcome union (#2135 replaced an earlier `clean` + `referencesUnresolved` boolean pair), so `clean` means compared-and-matched and no consumer reaches it by omission. The roll-up lists every incomplete entry, `drifted` ones included, so CI gates on `notCompared.length === 0`, not `drifted.length === 0`, which a SKIPPED comparison satisfies. Entries carry `referencesUnresolved: true`. `writeHumanReport` prints the roll-up as a `PARTIALLY compared` block, the per-resource warning going to the LOGGER while piped stdout shows only `no drift detected`.
  - **The EXIT CODE carries it too**: a detection-only run that drifts nowhere but left a comparison INCOMPLETE for a cause a re-run can clear — a refusal, or (issues #2151 / #1945) a read that threw — throws `DriftComparisonIncompleteError` (`exitCode = 2`, the "completed but something was SKIPPED" code; formerly `DriftComparisonRefusedError`, private to the file). It preserves the pre-#2108 non-zero signal rather than adding one, and DRIFT WINS when both hold. Detection-only; `--accept` / `--revert` keep their documented codes.
  - **The exit trigger is a STRICT SUBSET of the roll-up, and that asymmetry is load-bearing.** "Not compared" has two causes — the resolution THREW, or a `{{resolve:...}}` token merely survived — and the second is a token cdkd resolves for nobody (no CloudFormation service does since `ssm-secure` joined `ssm` in #2482 — text that merely looks like one), a population predating #2108 that no re-run clears; exiting non-zero on it would fail those users' CI forever (the "permanently non-zero" hazard `docs/cli-drift.md` cites for an absent write-only credential). So the cause is a `NotComparedCause` enumeration and `outcomeExitSignal` maps the CLEARABLE causes to 2 while `'unresolvedToken'` exits 0. Issues #2151 / #1945 added `'readFailed'` and rewrote that map as an EXCLUSION of `'unresolvedToken'`, so a later cause defaults to the non-zero side.
  - Those issues also put the per-resource body from read to outcome push in ONE try/catch: a throw from `provider.readCurrentState`, the Cloud Control fallback, `getDriftUnknown/UnorderedPaths`, `canonicalizePrincipalUniqueIds`, `canonicalizeIpProtocols`, `canonicalizeDriftProperties`, `calculateResourceDrift` or `redactDriftChanges` used to escape the loop and the command, leaving every other resource — and under `--all` every remaining STACK — unchecked. `isNoReadHandlerError` splits the catch by whether a RE-RUN CAN CLEAR IT: `UnsupportedActionException` / `TypeNotFoundException` (matched through the cause chain, since `CloudControlProvider.handleError` re-wraps them) report `unsupported` and exit 0, the no-read-path condition the fallback otherwise signals with `undefined`; everything else is `readFailed`. `--json` `notCompared` entries gained a `cause` key and their `referencesUnresolved` stopped being the literal `true`; both readers still cover both populations.
  - That enumeration replaced two nearly-identical booleans (`referencesUnresolved`, `comparisonRefused`) byte-equivalently (#2135). The exhaustiveness fence is `matchOutcome`, whose handlers are a mapped type over the union's `kind`, so adding a variant is a COMPILE error at every consumer (probe: a temporary sixth variant fails at all eight).
  - `writeHumanReport` follows the ROLL-UP, not the exit code — the narrower subset would print `✓ ... 1 resource checked` above a `PARTIALLY compared` block naming that resource; the summary switches `✓` to `⚠` and reports `<n> of <m> resources fully checked`. Issue #2154 added a THIRD branch ahead of both: `notCompared.length === 0 && checked === 0 && outcomes.length > 0` prints `⚠ ... NOTHING was compared`. All three conjuncts matter — the first keeps a `notCompared`-only stack (`readFailed` included) in the EXISTING `⚠` branch — so it fires exactly when every outcome is `unsupported` or `skipped`, the `skipped`-only stack included (#323: a Custom Resource is not ACTIONABLE, out of the counts but not thereby checked). The EXIT CODE is untouched (`unsupported` / `skipped` map to `none`).
  - **`unsupported` is outside BOTH counts** (issue #2141): `inspectedCount` increments in three arms (`drifted` / `clean` / `notCompared`) and in neither arm where no read happens, so `skipped` (#323) and `unsupported` are excluded for the same reason from opposite directions; totals still print from `unsupported.length` and the `--json` `notSupported` array.
  - Both REPORT readers — `--json` roll-up and human block — go through ONE `notComparedOutcomes` predicate, so payload and rendering cannot disagree; the exit code is a deliberate third answer with its own named predicate.
  - Warnings BRANCH on refusal: `refused to resolve` / `refused to re-resolve`, not `could not`, so a deliberate decision is not read as a missing IAM grant. The branch asks `isDriftSecretRefusal(err)` — a POSITIVE test for the `DriftSecretRefusalError` class, not a code enumeration (which missed `DRIFT_SECRET_TOKEN_SCAN_MISMATCH`). Source-fenced by `tests/unit/cli/drift-secret-refusal-is-positive.test.ts`, the token-scan refusal being an internal-invariant guard no input reaches.
  - **Accepted cost on the refusal path**: the per-resource `secrets` map is CLEARED, so only the offline positional `seededSecretPaths` masks that resource — weaker than the pre-#2108 value-based masking on the KNOWN OVER-REFUSAL (a purely local name-form reference in a stack with any foreign producer region on record, CDK's `secretValueFromJson` shape). Kept anyway: the alternative is the wrong-region fetch this change exists to refuse.
  - The resolved baseline no longer trips `calculateResourceDrift`'s `{{resolve:` skip (PR #1899), so a console edit of a secret-bearing property is detectable and revertible again; that skip is now the FALLBACK for a reference cdkd cannot resolve at all.
  - **Redaction is keyed on the PATH as well as the value.** Resolution records a per-resource `RecordedSecretValues` plus the PATHS that produced one, and `redactDriftChanges` rewrites each side of every `PropertyDrift` as the outcome is BUILT — one choke point behind the human report, the `--json` payload, both plans, and the value `--accept` persists. The value pass restores a recorded plaintext to its own expression; the path pass covers what the map cannot, the map holding only TODAY's value (a ROTATION leaves the deployed resource on the previous one, so the path drifts and the AWS side matches no key). At a known-secret path the only value shown is the expression itself; anything else becomes `SECRET_MASK`, `undefined` / `null` excepted. `change.path` is masked too (`redactSecretsForState` walks values, never KEYS), and a masked path marks the change secret-bearing. `runAccept` REFUSES any path whose value came back masked, warning by name — writing `***` would corrupt the baseline and make the next deploy push the mask at AWS. Per-PATH, so non-secret drifts on the same resource are still accepted.
  - **`runAccept` also redacts the bag it persists**, positioned against the record's own `properties` with `STATE_SOURCED_READBACK_RULES` — not a duplicate: it reaches the untouched clone of the baseline (where a pre-fix `--accept` left plaintext) and names a stored plaintext a rotation made unrecognisable to the map. Its old pinning hazard is gone because such a path is refused first. The revert's narrowing write (#1644) is positioned against the bag the revert RESOLVED (`observedProperties ?? properties`) with `STATE_SOURCED_READBACK_RULES`, NOT the rollback executor's `STATE_DERIVED_RULES`: the delta descends from `buildRevertNewProperties`'s merge of the AWS-CURRENT snapshot with the resolved desired subtrees, so a non-drifted top-level key comes from AWS and may be reordered, and positional array descent would write a sibling's expression onto the wrong element.
  - **Every failure mode of the new lookups is per-resource, never fatal.** A deleted secret, a rotated-away version, or a role without `secretsmanager:GetSecretValue` / `ssm:GetParameter` warns and falls back to the unresolved baseline; `--revert` reports a per-resource failure with its own message instead of `AWS update failed`.
  - **An ABSENT `awsValue` at the EXACT leaf known to hold a secret is DROPPED, not reported** (`secretPaths.has(path)`, not the ancestor-matching `isSecretBearingPath` — a whole subtree vanishing from AWS is real drift; an absence surviving the drop goes into `maskedPaths`, so it is reported AND refused by `--accept`, which would otherwise delete the key and the reference with it). A write-only credential is returned by no readback, and PR #1899's skip stopped covering it once the baseline began arriving RESOLVED. Reporting it is three bugs: permanent exit 1; `--accept` writing `undefined`, which `setAtPath` turns into a DELETED key, erasing the reference; `--revert` re-pushing the credential every run. Scoped to `positionIsSecret` rather than `secretBearing`, so a key whose NAME carries a secret is still reported and refused. `redactDriftChanges` therefore runs BEFORE the clean/drifted decision, since it can empty the change list.
  - A SURVIVING `{{resolve:...}}` token (the resolver's unsupported-service arm warns and returns the literal) does NOT mark its path secret-bearing: since #2482 every CloudFormation service resolves or throws, so a survivor is text that merely LOOKS like a reference, and masking it would leave a path refused by `--accept` and pinned by the revert with no remedy. (Until #2482 `ssm-secure` survived here and WAS marked, via an `isSecretBySpelling` predicate, and `preserveLiveValuesAtUnresolvedTokens` REGISTERED the live values it copied in over such a token; both are gone with the population — registering a look-alike's live value would make a needle out of ordinary data, the #1904 corruption one spelling over.)
  - **Preservation is gated on the leaf being a WHOLE token, and that gate is a DISCLOSURE boundary**: a MIXED leaf's send string is already partially resolved, so copying a live value into it moves whatever AWS holds at the other half into the payload with nothing able to mask it (narrowing delta, retry log and AWS error text alike). Declining restores the pre-#1914 behaviour for that shape — the literal ships, as `cdkd deploy` does.
  - **The remaining residual is not created by this command's own bags**: a provider can echo its readback in `effectiveProperties`, and the #1644 narrowing persists it with no map entry to match; closing that needs span-masking (issue #2102 — NOT #1935, whose fix only reaches a leaf the value scan can MATCH). A non-string live value is not positionable and is a stated residual. Such a token is reported through the pass's `onUnresolved` hook and is deliberately NOT a failure — failing would abandon every other drifted property on the resource and exit 2.
  - **A survivor is the one place where "the token is already what AWS holds" can be FALSE**: a record adopted by `cdkd import --migrate-from-cloudformation`, or a position edited out of band, holds something else there, so `preserveLiveValuesAtUnresolvedTokens` must run before `provider.update` and a revert triggered by a SIBLING key leaves the live value at those positions untouched instead of overwriting it with a literal. (The originating population was `ssm-secure`, resolved SERVER-side by CloudFormation, so a migrated record held the PLAINTEXT on AWS while state held the token; since #2482 that spelling resolves and its position is masked by the ordinary recorded-pair route.) Deciding by what AWS HOLDS rather than by provenance needs no state flag and is exact both ways: a cdkd-deployed record has the token live, so copying it back is a no-op; any other record has a value cdkd cannot compare, which survives. Where AWS has nothing there the token is kept, as `cdkd deploy` sends it.
  - `survivingDynamicReferences` scans with `[^}]+` to agree with the RESOLVER's own pattern (a `{` inside a token separates them) and reports only tokens present in the INPUT, the scan running over the RESOLVED string where a secret can contain reference-shaped text. Issue #1936 retired this entry's claim that the strict sibling should DISAGREE: the character class must not differ, since `[^{}]*` PERSISTED PLAINTEXT for a reference whose inner text contains a `{` on the #1900 empty-map path. All four spellings now derive from ONE exported constant in `secret-redaction.ts` (`DYNAMIC_REFERENCE_INNER`, byte-identical to the resolver's `([^}]+)` capture), and `isWholeDynamicReference` is that module's `isSingleDynamicReferenceToken` under a local name. `survivingDynamicReferences` imports the ASSEMBLED scan (`dynamicReferenceTokens`) rather than rebuilding one from the shared class, flags and anchors being as forkable as the class. The fence states the good condition POSITIVELY: a regex matching a `{{resolve:` token must escape both braces, and only `intrinsic-function-resolver.ts` (once, the authority) and `secret-redaction.ts` (twice) may write one, ZERO anywhere else under `src/**`.
  - The report names only the TOKENS, never the leaf that held them, since `resolveDynamicReferences` substitutes token by token and a mixed `secretsmanager` + look-alike leaf comes back carrying real plaintext. For the same reason the detection failure arm masks its message BEFORE clearing the value map (the clear sits after the log). Every AWS error string a revert prints runs through `maskSecretsInText` — AWS quotes the offending value — the same fence `deploy-engine.ts` applies to its own provider calls.
  - **The path answer survives a failed lookup**: `collectDynamicReferencePaths` seeds a SECOND path set offline from where the `{{resolve:` strings simply are; the report uses the PROVEN set when resolution succeeded and that seed when it did not. Without it the two failure modes compose into a leak — the comparator's skip only re-arms for a LEAF whose state side is a string, so a resource whose `observedProperties` lack the secret's parent drifts at the ANCESTOR with the whole AWS subtree as `awsValue`. The seed is coarser (it cannot tell a public ssm reference from a secret one) and over-masks, the direction to err in.
  - **`--accept` refuses two ways**, through one `acceptRefusalReason` predicate shared with `printAcceptPlan` so a `--dry-run` cannot promise a write the run refuses: a masked VALUE, and a masked PATH (a readback keyed BY a secret — `setAtPath` would otherwise invent a key literally named `***`, and with an `undefined` value INSERT it rather than removing the real one). The path check is what makes `redactDriftValue`'s `undefined` / `null` / whole-expression exemptions safe. Keyed on a `maskedPaths` SET carried on the outcome rather than on comparing a value to `SECRET_MASK`, so a property whose real value is `***` at an ordinary path is not refused forever — and a masked path is not detectable from the value at all. The same set tells `runRevert` which subtrees `buildRevertNewProperties` cannot overlay (its key is the path's TOP-LEVEL segment, which a mask makes unmatchable), so the user is told rather than silently not reverted; the accept refusal there names ROTATION as the remedy, a plaintext leaked into a property NAME being unremovable by passes that all walk values.
  - `--accept` also CHECKS each accepted value after the redaction pass and warns when it was overwritten: a PUBLIC `{{resolve:ssm:...}}` can sit in `properties` via the `cdkd import` warn path, and `trustAnyExpression` then wins over the accepted value — otherwise a silent permanent no-op. A revert that could not re-resolve is counted apart from an AWS update failure (it never reached `provider.update`), and the provider lookup + payload build sit inside per-resource guards. `carriesRecordedSecret`'s substring branch carries the same 4-character needle floor `secret-redaction.ts` applies when building needles (copied, that constant being module-private), so it errs toward NOT marking — a sub-threshold plaintext is one the redactor would not substitute anyway, and marking it would mask a PUBLIC reference that merely contains those characters.
  - `--accept` (state <- AWS) and `--revert` (AWS <- state) both ship. `buildRevertNewProperties` overlays each drifted top-level subtree from the baseline onto the AWS-current snapshot, EXCEPT the AWS-SERVICE-authored entries of a top-level TAG LIST (`mergeTagListForRevert`, issue #1501): a console-added tag is still STRIPPED, but `AmazonECSManaged` / any `aws:`-prefixed key survives. Gated on a top-level property NAMED `Tags`/`*Tags` rather than the `[{Key,Value}]` shape alone (`LoadBalancerAttributes` also matches), and applied even to an EMPTY recorded baseline, since ECS requires the former for managed scaling and AWS reserves the latter; `findRevertPreservedTagKeys` names them in the plan before the confirmation prompt. This is the issue's option 2 — option 1 (diffing the WHOLE tag list) FAILED the `drift-revert` integ, whose fixture requires `--revert` to strip an injected tag.
  - `buildRevertNewProperties`'s `preserveUntemplated` option (issue #1626 items 2 + 3) settles what "absent from desired" MEANS per caller: the deploy engine passes the last-deployed TEMPLATE as `previousProperties`, so an absence is a template removal, while `runRevert` passes the full `readCurrentState` snapshot, so it ALSO covers a never-templated path — and both provider shapes destroy it, by different routes (one KEY-DIFFS a collection and reads the absence as a REMOVAL — ELBv2's `LoadBalancerAttributes` carries ~20 AWS-reported keys against a template declaring one or two; one REPLACES a bag wholesale, e.g. the documented full-replace `PutBucketTagging`, and never consults the previous side). So with NO `observedProperties` — the baseline is the raw template, where an AWS-authored value and an out-of-band change are indistinguishable — `mergeUntemplatedValue` merges every untemplated path into the bag cdkd SENDS; with `observedProperties` the baseline IS a deploy-time snapshot, an absence is genuinely an out-of-band addition, and the wholesale overlay is unchanged (which the `drift-revert` integ's injected-tag assertion depends on). The fix is on the DESIRED side rather than trimming `previousProperties`, since trimming stops the key-diffing removal but leaves the wholesale-replace drop untouched.
  - Under the flag the merge is a strict SUPERSET of the #1501 carve-out and subsumes it — which required BOTH `mergeUntemplatedValue` AND `collectMissingPaths` to accept a DECLARED-but-EMPTY baseline list: `isKeyedList` requires a NON-empty array, so a condition-collapsed `Tags: []` fell to the merge's wholesale arm and handed AWS `[]`, stripping `AmazonECSManaged`, while the REPORTER fell to its own whole-list arm (which fires only on an `undefined` desired side) and named nothing. Both arms now mirror each other and the correspondence test carries the empty-baseline shape. This inverts the pre-#1626 "emptiness is deliberately excluded" contract on the DESIRED side only, safe because the reporter has one caller and runs only on the template-only baseline. The merge DEDUPES by `Key`, since AWS can report one twice and `PutBucketTagging` / `ModifyLoadBalancerAttributes` reject a duplicate. Its structural rules mirror `collectMissingPaths` case for case — plain records descend, KEYED `[{Key,Value}]` lists merge by `Key`, positional arrays and scalars come from the baseline wholesale — so every path `findRevertUnbaselinedAwsKeys` (renamed from `findRevertDroppedAwsKeys`, they now being PRESERVED) names in the plan is rescued by the merge and the merge rescues nothing the plan failed to name; a unit test pins that by diffing the flag-on and flag-off outputs. A service-authored tag is in NEITHER list: it is preserved on the default path too, so the flag does not rescue it, and `isServiceManagedTagKey` omits it from the plan, reporting it would warn about a loss that cannot happen.

- **src/analyzer/drift-calculator.ts** - State-vs-AWS property comparator used by `cdkd drift`. Only descends into keys present in cdkd state, so AWS-managed fields cdkd never set (timestamps, generated identifiers, account-wide defaults) cannot surface as false-positive drift.
  - Exports `undeclaredEmptyObservedKeys(observed, declared)` (issue #1498): on the observed-properties baseline, a top-level key the template never declared whose captured value was EMPTY (`[]` / `{}` / `null`) is fed into `ignorePaths` by `drift.ts` — such keys are materialized AFTER the per-resource capture by sibling resources (`ClusterCapacityProviderAssociations` -> `Cluster.CapacityProviders`, standalone `LifecycleHook` -> the ASG's hook list, standalone SG rules) or by AWS itself, and comparing them produced permanent phantom drift that `--revert` then destructively stripped. An undeclared key captured with a real value stays compared.
  - Accepts an optional `ignorePaths` list (from each provider's `getDriftUnknownPaths`) for state paths the provider deliberately cannot read back — e.g. Lambda `Code: { S3Bucket, S3Key }`, which `GetFunction` only returns as a pre-signed URL — so a clean run reports no drift there instead of a guaranteed false positive.
  - `drift.ts` passes the resource's state-recorded `properties` as that method's optional second argument (issue #1602), so a path unreadable for only a SUBSET of a type's resources is scoped per resource rather than switched off type-wide: `ApiGatewayV2Provider` declares `TlsConfig` unknown only when `ConnectionType !== 'VPC_LINK'` (AWS discards the field on a public integration, returns it on a private one). `DynamoDBTableProvider` is the second consumer (issue #1760, PR #1769) and a usefully DIFFERENT shape: it scopes on whether the template declares the property AT ALL (`WarmThroughput`, `GlobalSecondaryIndexes`, `LocalSecondaryIndexes`), covering an UPGRADE transition rather than a configuration split, since records written by an earlier binary already froze the AWS-computed value into `observedProperties`. Its predicate answers DECLARED for an absent or uninformative bag (`declaresWarmThroughput` returns `true` there): a never-populated bag is not evidence the template declared nothing. A provider must tolerate an absent bag by falling back to the type-level answer, defaulting to COMPARING — hiding real drift is the worse failure.
  - Before any comparison both sides are canonicalized through `src/analyzer/drift-normalize.ts`, so AWS returning a tag list, a resource-id/ARN array, or a provider-declared unordered set of plain strings or of objects (`options.unorderedPaths`, from `getDriftUnorderedPaths`) in a different order than the deploy-time snapshot is not phantom drift (the `deepEqual` walk compares arrays positionally).
  - The LAST pass in that chain is the provider's own `canonicalizeDriftProperties(resourceType, properties)` (issue #1784, applied by `drift.ts` to BOTH sides) — the seam for a difference no PATH can name, a member of an ARRAY ELEMENT: `diffAt` compares arrays wholesale, so `isIgnoredPath` is never asked about a path crossing one, and the only expressible suppression would be the WHOLE array (suppressing `GlobalSecondaryIndexes` would mean never detecting an index add / remove / capacity change again). Stripping the AWS-managed member from BOTH bags converges an old `observedProperties` record with a new readback instead, keeping the array compared. It takes no `side` argument on purpose (one-sided normalization manufactures drift on the `properties`-fallback baseline — the mistake `drift-normalize.ts`'s header records), must be pure / non-mutating / identity-returning when inapplicable, and is applied to the COMPARISON copies so the `aws` bag `--revert` diffs against is untouched. **`--accept` is NOT symmetric with that**: it writes each change's `awsValue`, which comes from the CANONICALIZED bags, so a stripping canonicalizer makes `--accept` persist the stripped shape on a path that still drifts (the call site in `drift.ts` says so, and `tests/unit/cli/drift.test.ts` pins it). That is the intended direction — state should stop carrying a member the readback no longer reports — but the hook is a WRITE, not only a comparison filter, which a provider author must know before declaring one.

- **src/analyzer/drift-normalize.ts** - Order-normalization helpers for `drift-calculator.ts`. `canonicalizeTagListsDeep` sorts any `{Key,...}[]` tag list by `Key`; `canonicalizeIdArraysDeep` sorts any array whose every element is an AWS resource id (`subnet-…`, `sg-…`) or ARN. Both recurse and are applied to BOTH comparison sides — AWS does not guarantee element ordering across reads and these two kinds are semantically unordered sets. Surfaced by dogfooding the sibling `cdk-real-drift` tool.
  - Plain-string arrays and non-tag OBJECT arrays are NOT canonicalized heuristically (either can be order-significant); instead `canonicalizeUnorderedArraysAtPaths(value, paths)` sorts such an array ONLY at an explicit per-provider opt-in path list, from the optional `ResourceProvider.getDriftUnorderedPaths(resourceType)` threaded through `calculateResourceDrift`'s `options.unorderedPaths` by `drift.ts` (issue #1096 item 1). Issue #1620 extended it to arrays of OBJECTS, sorted by a private key-order-independent `canonicalJson` — AWS's readback order for an object's own keys is no more guaranteed than for the list, so a raw `JSON.stringify` sort key would reintroduce the phantom drift. Each shape is sorted only when the array is HOMOGENEOUS in it; a MIXED array (strings and objects, a `null` element) is left untouched.
  - Both provider-declared path lists share ONE matcher — the exported `matchesPathPrefix(path, entries)` (exact match, or entry followed by `.`), which `drift-calculator.ts`'s `isIgnoredPath` is a thin alias over — so the two cannot silently drift apart. A plain entry is a SUBTREE declaration; appending `LEAF_ONLY_PATH_SUFFIX` (`[]`) claims the path ALONE (issue #1783). The leaf-only form exists because THIS walk descends into array elements, so a subtree entry for an object list also claims every array nested inside its elements — `AWS::DynamoDB::Table.GlobalSecondaryIndexes` is an unordered set keyed by `IndexName` while each element's `KeySchema` is order-SIGNIFICANT (HASH before RANGE), so the only available spelling would have HIDDEN a real key change (why #1767 shipped the reverse-map half and left the ordering half undeclared). The marker is honored by BOTH lists so their spellings cannot diverge; a bare `'[]'` entry matches NOTHING, since it would name the root bag.
  - One required divergence: `isIgnoredPath` never sees a path crossing an array (the comparator compares arrays wholesale via `deepEqual`), whereas the unordered walk descends into array elements and gives them the parent's path, so `'Items.Aliases'` is meaningful for `getDriftUnorderedPaths` but inert as an ignore-path — strictly more permissive. Nested arrays are not descended into, so an array-of-arrays at a declared path never has its inner lists sorted.
  - `ELBv2Provider` declares `AWS::ElasticLoadBalancingV2::TargetGroup.Targets` (the first object-array consumer, #1620) — which let `Targets` move OUT of that provider's TYPE-level `getDriftUnknownPaths` and start being compared; its `readCurrentState` reads them via `DescribeTargetHealth`, excluding exactly the `draining` state (a just-deregistered target keeps reporting for minutes, and freezing one into the snapshot is permanent phantom drift) while INCLUDING every other state, since `initial` / `unused` / `unhealthy` / `unavailable` are all registered and health is not registration. The unknown-path entry became PER-RESOURCE via the #1602 seam: `Targets` is still ignored for a target group whose TEMPLATE declares none, an ECS-service / ASG-fronting group having its members registered by the SIBLING resource and re-registered on every scale event — comparing that reports drift on an untouched stack and `--revert` would deregister the tasks the service just placed (the #1498 class; `undeclaredEmptyObservedKeys` only covers it when the capture happened to be empty, which for a redeployed running service it is not). An explicit `Targets: []` IS a declaration and stays compared.
  - `KinesisStreamProvider` declares `AWS::Kinesis::Stream.DesiredShardLevelMetrics` (issue #609) — enhanced-monitoring metrics come back from `DescribeStream` in an order matching neither the request nor alphabetical (measured us-east-1, 2026-08-12), and the same backfill made the order observable by expanding the `ALL` shorthand into the seven stored names. `DynamoDBGlobalTableProvider` declares `AWS::DynamoDB::GlobalTable.AttributeDefinitions` (issue #1742) — same unordered readback (measured us-east-1, 2026-08-13: `[pk, gsipk]` read back as `[gsipk, pk]`), and the list is a genuine set keyed by `AttributeName`, so sorting cannot hide a real change. `KeySchema` is deliberately NOT declared at either level, being order-SIGNIFICANT. The reachability note above is what kept this unseen: it only bites on the `properties` baseline a reverse-replacement rollback leaves behind, since `rollback-executor.ts` strips `observedProperties`. `DynamoDBTableProvider` declares the same path for the sibling `AWS::DynamoDB::Table`, whose readback is identical one type over (issue #1760, PR #1769).
  - The per-index `WarmThroughput` half of #1742 shipped in PR #1859: `DynamoDBGlobalTableProvider` is the first consumer of the `canonicalizeDriftProperties` seam (issue #1784, in the `drift-calculator.ts` entry above), naming the `{ listKey: 'GlobalSecondaryIndexes', member: 'WarmThroughput' }` PAIR in a closed `DRIFT_STRIPPED_INDEX_MEMBERS` table — a list-plus-member pair, NOT a path — and stripping that member from BOTH comparison sides. The two halves had to land together: `readCurrentState` reverse-maps the AWS `GlobalSecondaryIndexWarmThroughputDescription` into the CFn shape, surfacing only the two user-settable sub-fields and DROPPING the `Status` member CFn has no concept of, and dropping a readback key otherwise strands every already-written `observedProperties` baseline (the #1760 class) — which the both-sides strip absorbs. Two bounds: the convergence only reaches records written by a post-#1420 binary (an older bag holds the raw `GlobalSecondaryIndexDescription[]` and is already drifting on `IndexArn` / `IndexStatus` / `ItemCount` / `IndexSizeBytes` / `Backfilling`), and the accepted cost is that a DECLARED per-index `WarmThroughput` change is no longer reported by `cdkd drift` at all — a declared-gate is not expressible in a hook that sees ONE bag with no desired-side reference. The sibling `AWS::DynamoDB::Table` has the same per-element shape and has NOT adopted the seam — its own change with its own real-AWS verification, tracked as issue #1812.
  - `FSxFileSystemProvider` declares only `WindowsConfiguration.Aliases`; `SelfManagedActiveDirectoryConfiguration.DnsIps` is deliberately NOT declared (AWS documents no set semantics and DNS resolver lists are conventionally preference-ordered — declaring an order-significant list would silently HIDE real drift, worse than the visible false positive; same reasoning excludes ElastiCache `PreferredAvailabilityZones`). Declaring the path here rather than sorting inside the provider's `readCurrentState` reverse-mapper is load-bearing: the normalizer runs on BOTH sides, so it stays correct for the `properties`-fallback baseline (a resource deployed before observed-capture, whose baseline is the user's template order) — sorting only the read side would manufacture drift there.

- **src/analyzer/drift-principal-normalize.ts** - IAM principal-FORM canonicalization for `cdkd drift` (issue #1515) — the sibling of `drift-normalize.ts` for a difference that is not about ORDER. AWS renders an IAM role / user principal inside a resource policy either as its ARN or as its `AROA…` / `AIDA…` unique id, substituting the unique id when the principal is transiently unresolvable at write time (the CDK `autoDeleteObjects` role is created concurrently with the bucket policy referencing it) and re-rendering the ARN once it resolves; the `observedProperties` capture stores whichever form came back, so `cdkd drift` compared two spellings of ONE principal and reported PERMANENT phantom drift `--revert` could not clear — it wrote the recorded form back and AWS re-canonicalized on write (the #1096 / #1498 class on a different property; two back-to-back `drift-revert` runs on 2026-08-10 disagreed for this reason with no code change between).
  - Unlike its sibling this pass CANNOT be pure (the mapping is not derivable from the string), so the shape detection (`collectPrincipalUniqueIds` / `collectPrincipalArns` / `rewritePrincipalUniqueIds`, walking only `Principal` / `NotPrincipal` positions, where the two forms are interchangeable, and NOT a `Condition` value, where they are not) is pure and the one lookup goes through an injected `PrincipalUniqueIdResolver`; `drift.ts` supplies the live implementation (`iam:GetRole` / `GetUser` off the ARN via the shared `parseIamPrincipalArn`, cached per ARN for the whole command INCLUDING failures).
  - `canonicalizePrincipalUniqueIds` rewrites BOTH sides to the ARN form (the race is symmetric, and one-sided normalization is the mistake `drift-normalize.ts`'s header records) and short-circuits with NO AWS call unless a unique id AND a candidate ARN are both present. Only a pair PROVEN equal by the lookup is collapsed: a deleted role (exactly when AWS keeps the unique id forever), a cross-account principal, or a missing `iam:GetRole` permission all leave both sides untouched and the drift REPORTED, so the pass can never hide a real principal change. Known bound: a policy carried as a JSON STRING rather than a parsed object is not walked (re-serializing would risk manufacturing a different phantom drift).

- **src/utils/ip-protocol.ts** + **src/analyzer/drift-protocol-normalize.ts** - EC2 security-group `IpProtocol` VALUE canonicalization for `cdkd drift` (issue #1643). The measured rename table + `canonicalizeIpProtocolValue` live in `src/utils/` because they have TWO consumers in different layers; the analyzer module owns only WHERE in a resource's properties the canonicalization applies. Second sibling of `drift-normalize.ts` for a non-ORDER difference, and unlike `drift-principal-normalize.ts` it IS pure (a closed, measured table, no AWS lookup).
  - EC2 owns the spelling: it accepts an IANA protocol NUMBER or a NAME and rewrites the four numbers it has a name for before storing the rule, so cdkd recording what it SENT (`'6'`, post-#1633) against a readback of what AWS HOLDS (`'tcp'`) was two spellings of ONE protocol — permanent phantom drift `--revert` could not clear, since it revokes and re-authorizes into the same state (the #1591 / #1633 class via a third route: those two fixed TYPE coercions on the SEND side, this is a VALUE mapping owned by AWS, so it belongs on the READBACK side and covers the inline `AWS::EC2::SecurityGroup.SecurityGroupIngress[]` / `SecurityGroupEgress[]` rules #1633 deliberately does not touch).
  - The rename set was MEASURED, not guessed (us-east-1, 2026-08-12, ingress AND egress): exactly `1` -> `icmp`, `6` -> `tcp`, `17` -> `udp`, `58` -> `icmpv6`, while `-1` / `0` / `2` / `4` / `27` / `41` / `47` / `50` / `51` / `88` / `89` / `94` / `103` / `112` / `132` / `255` all read back as the number — a CLOSED set of the four protocols EC2 has a name for, not the open-ended IANA list, and `-1` being unaffected is why #1633's live test came back clean. Case is AWS's too (`TCP` / `Tcp` / `tcp` on one port collapsed into ONE `tcp` permission), so a name is matched case-insensitively and lowered — but ONLY the four KNOWN names, so the pass can never make two genuinely different values compare equal. Numbers canonicalize to their STRING form because an unquoted YAML `IpProtocol: 47` parses to a number while AWS always reads back a string.
  - `canonicalizeIpProtocols(baseline, aws, resourceType)` is applied to BOTH sides by `drift.ts` right after the principal pass, scoped by a CLOSED `IP_PROTOCOL_PATHS` table (the two standalone rule types at the top level, `AWS::EC2::SecurityGroup` at `SecurityGroupIngress[].IpProtocol` / `SecurityGroupEgress[].IpProtocol`) rather than by a walk for any key named `IpProtocol` — a blanket rewrite would turn an unrelated `'6'` into `'tcp'`. EVERY number is stringified, not only an integer one, so a malformed `6.5` keeps the key it had before #1633 and `NaN` / `Infinity` do not collapse onto one JSON `null` bucket; anything neither string nor number, most importantly an unresolved intrinsic, is returned untouched, and an unchanged bag is returned by IDENTITY.
  - **`canonicalizeIpProtocolValue` is ALSO consumed by `ec2-provider.ts`'s `sgProtocolKey`**, the comparison being only half the defect: a standalone rule's physicalId is `<groupId>|<protocol>|<from>|<to>` built from the value cdkd SENT, so for `IpProtocol: 6` both the tuple pre-filter and the full-signature `sgRuleKey` compare in `readSecurityGroupIngressCurrentState` missed AWS's `tcp` rule, the method returned `undefined`, and `cdkd drift` reported the resource as "drift unknown" FOREVER — one layer BELOW the phantom drift and invisible to a comparison-side fix, since no AWS-side bag is ever produced (measured by the real-AWS `drift-revert-arrays` run on 2026-08-12; the issue's own premise that the read "returns `tcp`" was wrong). Normalizing inside `sgProtocolKey` heals the standalone lookup, the inline-rule `reconcileSgRules` ordering AND the write-side `applySecurityGroupRuleDiff` revoke/authorize key from ONE definition of protocol identity, mirroring the reason its existing comment gives for stringifying a legacy numeric `-1`: keying the normalization heals the deployed population with no migration.
  - Issue #1648 extended the SAME fold to the DIFF side (`canonicalizeDesiredProperties`, for the standalone type and the `AWS::EC2::SecurityGroup` inline rule lists), because a template edit rewriting `IpProtocol: 6` to `'tcp'` otherwise read as a changed property — and since `IpProtocol` is create-only on the standalone type, that classified as a REPLACEMENT of a rule AWS already held exactly. The fold is deliberately NOT inside `narrowIngressIpProtocol`, which also feeds the CREATE path: the wire value is not the defect (AWS accepts either spelling and stores `tcp` for both), only the diff's classification is.
