# Key Files and Directories - src/analyzer

The `drift-*` normalizers live with `cdkd drift`: [layout-drift.md](layout-drift.md).

## Core Directories

- **src/analyzer/** - DAG builder, template parser, intrinsic function resolution

## Important Files

- **src/analyzer/outputs-diff.ts** - The diff-side `Outputs` resolution + comparison behind `cdkd diff`'s Outputs section (issue [#1921](https://github.com/go-to-k/cdkd/issues/1921)) — the preview half of the Outputs-only persist `cdkd deploy` gained in #875. `resolveTemplateOutputs` builds the exact bag shape `DeployEngine.resolveOutputs` writes to `StackState.outputs`: a condition-false output is SKIPPED (CFn never creates it), and an `Export.Name` is stored as a SECOND key holding the same value (what `Fn::ImportValue` resolves against). It takes the STORED outputs bag for exactly one decision (issue [#1942](https://github.com/go-to-k/cdkd/issues/1942)): a LITERAL `Export.Name` in a stack that resolves a secret, where deploy refuses a name CONTAINING a resolved plaintext and the preview — which never substitutes one — cannot evaluate that predicate. State holding the alias KEY proves a previous deploy already evaluated it over the same literal name and published, so the preview publishes the same key with TODAY's value (the stored VALUE is not part of the evidence — requiring equality would suppress exactly the export change #875 exists to show); an ABSENT key records no verdict, so it keeps the previous behaviour of suppressing the whole outputs delta and recording the alias in `failedKeys`. Two residuals live at that branch: a rotation whose new plaintext is a substring of the literal name flips deploy's verdict, and a key stored by a pre-#1919 binary records no verdict at all (the same key `cdkd scrub` reports through `secretBearingStateKeyWarning`). It reports `resolutionFailed` when any output stays unresolved, and `isUnresolvedValue` is deliberately WIDER than the deploy side's `v === undefined` because the diff resolver fails in more ways: `undefined` (the SAME signal — `resolve` returns it WITHOUT throwing for a constructible-but-unknown attribute like `StreamArn` / `PolicyId` / `VpcId`, and `JSON.stringify` drops such a key so state can never hold one), a SYMBOL (a top-level `Fn::If` selecting `Ref: AWS::NoValue` — `resolveValue` strips the sentinel only INSIDE arrays / objects), a surviving intrinsic OBJECT, and — ONLY for a value whose raw template source contained an `Fn::Sub` (`templateUsesSub`, which walks nested `Fn::Join` / `Fn::If`) — an unsubstituted `${...}` STRING (`resolveSub` catches a genuine `Ref` / `GetAtt` miss, WARNS, and KEEPS the literal placeholder — no throw and no object, so an object-only check launders it straight through). Each of the first three would otherwise be a PERMANENT phantom on a stack the deploy considers clean, with `--fail` exiting 1 forever. The `Fn::Sub` SCOPING is what keeps the last one safe: applied to every string it would match an IAM policy body's `${aws:username}`, a UserData shell `${VAR}`, or any literal a user wrote, and one such key suppresses the WHOLE Outputs section for the stack forever. Within `Fn::Sub`-sourced values one false positive remains and is accepted — `${!Literal}` is the ESCAPE and resolves to literal `${Literal}`, indistinguishable post-resolution — because it merely SUPPRESSES the section (the pre-#1921 behavior) whereas the alternative is a phantom every run. Failed keys are returned as `failedKeys` because this resolver DROPS them while deploy keeps them as `undefined`; without that list every failure reads as a phantom REMOVE and the suppression warning fires on the ordinary pending-resource case. `computeOutputsDiff` then compares bag KEY by bag KEY, which is exactly the `outputMapsEqual` predicate the deploy engine gates its persist on, so the preview cannot drift from the apply; a partially-resolved bag reports NO delta, mirroring the deploy engine declining to persist one (nothing is lost — an output only fails to resolve because it references a resource this deploy has yet to CREATE, and that CREATE is already on the resource side) and, like deploy, WARNING when a delta was suppressed so "no Outputs section" is never ambiguous between unchanged and uncomputable. It also WITHHOLDS an `oldValue` that is legacy secret PLAINTEXT, since this is the first code path that DISPLAYS a stored output value and `cdkd diff` is routinely run in CI. TWO signals identify such a record and both are needed: the desired side still being a SECRET-BEARING dynamic reference while the stored side is not (the condition `cdkd scrub` repairs), AND `secretSourceKeys` — keys the TEMPLATE declares as such, collected over EVERY declared output including condition-skipped ones. "Secret-bearing" is deliberately only the spellings that are secret REGARDLESS of target — `{{resolve:secretsmanager:` and `{{resolve:ssm-secure:`. A plain `{{resolve:ssm:` is EXCLUDED because #1901 classifies it by the parameter's TYPE and a `String` / `StringList` parameter is public and legitimately persisted RESOLVED; keying on it would fire on an ordinary record and, since the verdict is record-WIDE, withhold every value in the stack while advising a `cdkd scrub` that would find nothing. The second reaches what the first cannot: a condition-skipped secret output has no desired side at all and would otherwise print in full as a REMOVE row. It does NOT reach `buildDeletedSubtree`'s removed nested child, whose WHOLE bag becomes REMOVEs against an EMPTY template — an earlier revision of this note listed that case here, and it is structurally out of reach for the same reason the deleted OUTPUT is: nothing is declared. That node is covered instead by the third signal below, which `diff-recursive.ts` arms from the PARENT's template (`templateHasSecretDynamicReference`), propagated unchanged to a deleted grandchild since its template is gone for the same reason. A hit on either makes the whole record suspect — it was written by a pre-GHSA binary, so every value in it is unredacted — hence the withholding is RECORD-level, not per-key. It does NOT reach an output DELETED from the template, and an earlier revision of this note claimed it did — `secretSourceKeys` is built from DECLARATIONS, so a record whose only secret-bearing output has since been removed contributes nothing to the set, reads as not-legacy, and renders its stored pre-GHSA plaintext as the `old:` side of a REMOVE row (issue [#1948](https://github.com/go-to-k/cdkd/issues/1948)). That case is answered from the STORED bag by a THIRD signal, and as a REFUSAL rather than a detection, because it is undecidable there — a plaintext is indistinguishable from an ordinary string: a stored key present in neither `declaredKeys` (every declared output name plus every literal `Export.Name`, condition-skipped ones included) nor the resolved bag has its value withheld. Two gates keep that off the common benign case, since deleting an output is a normal refactor: `templateHasSecretReference` (does the template still prove a secret reference ANYWHERE, `Resources` included — an Outputs-only walk would answer false for every case the gate exists to catch) and an EXONERATION when any stored value is itself a secret expression, which proves the last write redacted the whole bag. This arm withholds PER KEY, unlike the two above, and the asymmetry follows from what each concludes — those claim the record was written by a pre-GHSA binary, this one claims only that ONE key is undecidable. Residual: a stack whose ONLY secret reference WAS the deleted output leaves nothing to gate on, and blanket-withholding every REMOVE value is the worse trade. The change is still reported; only the value is withheld. Output / export NAMES are stripped of control characters before printing: an `Export.Name` is a RESOLVED value, so unlike a CFn logical id it never passed a validator and can carry ANSI escapes. **A deliberate SECOND implementation, not shared code**: extracting the deploy-side block would edit `src/deployment/deploy-engine.ts`, which sits in BOTH the `integ-broad` and `integ-destroy` gate scopes, so a diff-only fix would have acquired two real-AWS gates. `tests/unit/analyzer/outputs-diff.test.ts` pays for that trade with an anti-drift fence that READS `deploy-engine.ts` and asserts the mirrored semantics still hold — watching the DEFINITION of deploy's failure signal (`some((v) => v === undefined)`) rather than the line that CONSUMES it, since an earlier version pinned the consumption and would have stayed green through exactly the divergence it exists to catch. Each assertion is verified to fire by a mutation probe.
