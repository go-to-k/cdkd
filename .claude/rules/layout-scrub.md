## Important Files

- **src/cli/commands/scrub.ts** - `cdkd scrub [STACK...]` — the permanent STATE SECRET-HYGIENE command (clean + audit), not incident-only tooling (issue [#1902](https://github.com/go-to-k/cdkd/issues/1902) reframed it as such; it shipped as GHSA remediation). Rewrites persisted state so a resolved secret dynamic reference is stored as its `{{resolve:...}}` expression, not the plaintext value — WITHOUT a deploy. `--dry-run --fail` is positioned as a STANDING CI gate rather than a one-off migration check, because secrets reaching IaC state is a structural, recurring concern. Its redaction set is NOT a second list to maintain: it re-resolves through the same `IntrinsicFunctionResolver` and reads the same `recordedSecretValues` bag the deploy path redacts from, so it inherits every secret class the resolver classifies (pinned by a test that a spelling-filtering scrub would fail). A normal `cdkd deploy` already scrubs as a side effect (the deploy engine redacts every persisted bag via `withParentInfo`); this command cleans up EXISTING state written by an older cdkd. Unlike the `cdkd state ...` family it NEEDS the CDK app (`--app`), because state records the resolved value with no marker of which values are secrets — only the template carries the references. Synthesizes the app, re-resolves each resource's template properties into a fresh `recordedSecretValues` map (the resolved output is discarded), then `scrubResourceRecord`s every state record against it and saves under the stack lock. No AWS create/update/delete. The stack OUTPUTS bag is repaired in TWO passes, and the split is the scope decision of issue [#2005](https://github.com/go-to-k/cdkd/issues/2005). A stored key today's template can still NAME — a declared output, or an `Export.Name` this run could FULLY compute (literal, or an intrinsic whose best-effort resolution landed) — keeps the pre-existing pass, which positions it against the template and is gated on `outputSecrets` (built from DECLARED outputs) being non-empty. A name that did NOT fully resolve is deliberately excluded from the accounted set, because `deploy-engine.ts`'s alias write guards only on `typeof exportName !== 'string'`: a deploy whose `Fn::Sub` warn-and-KEPT `${Foo}` really does write that literal as a state key, so accounting for it would EXCLUDE it from the widened pass and leave #2005's own population unrepaired while `--dry-run --fail` exits clean. `redactUnaccountedOutputs` then repairs every OTHER stored key by value match alone, against `allRecordedSecrets` — the union of the outputs map and EVERY resource's, which is the only place those two bags are joined (they are separate precisely so one resource's secret cannot rewrite another's coinciding literal, so the resource walk must never see the union), filtered to plaintexts at or above `secret-redaction.ts`'s exported `MIN_NEEDLE_LENGTH` (the no-source arm whole-value-matches at ANY length, which is sound for a POSITION-SCOPED bag and not for this one). Each such key is scanned ONCE, from the STORED value rather than from the positioned pass's output: re-scanning an already-positioned MIXED leaf splices a union needle INTO the expression pass 1 just inserted (`{{resolve:secretsmanager:{{resolve:ssm:/app/env}}/db:...}}`), the corruption `secret-redaction.ts`'s token guard documents, and a single union scan subsumes pass 1 for these keys anyway (the union is a superset with the outputs' expression winning a collision, and an unaccounted key has no position source by construction). That closes the population the command is DOCUMENTED as the remedy for and could not remedy: an output DELETED from the template contributes nothing to `outputSecrets`, so the needle sitting in `perResourceSecrets` never reached `state.outputs` and the plaintext survived a scrub that REPORTED SUCCESS — the same record `cdkd diff` correctly withholds from display (issue [#1948](https://github.com/go-to-k/cdkd/issues/1948)), whose own refusal is unchanged since it still cannot decide the question from a stored string alone. The repaired population is WIDER than that motivating case, and honestly so: a parameterized `Export.Name` (scrub has only template defaults) leaves the deploy's real alias key unaccounted on EVERY run, so those keys take cross-resource value matching as a standing condition rather than as a one-off after a refactor. TWO refusals bound the widening, both because `state.outputs` is re-applied VERBATIM to CONSUMER stacks — by `src/state/export-index-store.ts` and by `Fn::ImportValue` / `Fn::GetStackOutput` in `intrinsic-function-resolver.ts` — so a FABRICATED redaction ships a literal `{{resolve:...}}` token into a consumer's own AWS call (the #1934 class; note `cdkd drift` is NOT such a reader — it reads `state.resources` — and an earlier revision of this entry cited it): nothing is rewritten unless its value genuinely MATCHES a recorded plaintext, so an unrecoverable needle (secret deleted, rotated away, reference gone from the template too) leaves the value untouched and invents / removes no key — delivered by NO single guard, measured rather than assumed: `scrubStack`'s `totalSecrets === 0` early return, `redactUnaccountedOutputs`'s own empty-map guard, and an empty secrets map making every scan the identity are three REDUNDANT reasons, so deleting any one leaves the record byte-identical and none of them may be cited as the fence (the empty-map guard is also reachable in its own right — `totalSecrets` counts the RAW maps while the union is filtered to `MIN_NEEDLE_LENGTH`, so a stack whose every recorded plaintext is sub-floor walks past the early return and arrives with an empty union); and an ACCOUNTED key is never scanned against the union, or a resource's secret value would rewrite a declared output's coinciding literal into that resource's expression. Stated residual: a DECLARED output whose template value no longer resolves a secret but whose STORED value is still a stale plaintext is not repaired either — a redeploy rewrites it. Flags: `--all`, `--dry-run`, `--fail` (exit 1 if plaintext found: with `--dry-run` any of it, and on a real run the part scrub cannot rewrite — CI gate). CROSS-STACK reads (issue [#2133](https://github.com/go-to-k/cdkd/issues/2133)): every resolve context is built by ONE factory that supplies `stateBackend` (a memoizing READ view of it, so the pre-pass and the main resolution share one `listStacks` / `getState` per stack instead of paying both) and deliberately no `exportIndex` (its scan arm PATCHES the index — an S3 write from a command that performs no AWS mutation). A pre-pass, `makeCrossStackPrePass`, resolves each cross-stack node ALONE, outside the per-item best-effort catch, mirroring the resolver's own intrinsic PRECEDENCE (so it never performs a read the main resolution would not) and `Fn::If`'s selected branch only. Three outcomes: a read that FAILED for a user-fixable reason refuses the stack with `SCRUB_CROSS_STACK_READ_UNRESOLVED`; a read that SUCCEEDED but whose PRODUCER's own state record still stores the plaintext, for an export the app's TEMPLATES say is secret-bearing — the producer declares it from a `{{resolve:...}}` expression, OR the producer RE-EXPORTS a value a stack further up the chain declares from one (issue [go-to-k/cdkd#2146](https://github.com/go-to-k/cdkd/issues/2146)) — refuses with `SCRUB_CROSS_STACK_PRODUCER_PLAINTEXT` (there is no expression to write — scrub the producer first, and for a chain every stack in it, head first). **The discriminator is a DIRECT READ of the producer's stored value**, and it took three rounds to get there because every earlier cut INFERRED it from the consumer's side. `reresolveCrossStackValue` RESOLVES a stored expression to plaintext before returning it (#1934), so the healthy case and the unscrubbed-producer case BOTH arrive holding a plaintext: `carriesDynamicReference(resolved)` was inverted, the producer's TEMPLATE is true of both (a real-AWS run caught that one refusing every consumer of a secret-bearing export, one log line under the resolver's own `redacted dynamic reference` note), and the NEEDLE-COUNT test was wrong in both directions — the needle map is keyed by the resolved secret SUBSTRING, so a COMPOSITE export (`postgres://u:{{resolve:...}}@h`, what `secretValueFromJson` produces) has `secrets.has(resolved)` FALSE for the whole leaf and refused a healthy producer on the second reference, a NON-STRING resolved value could not be tested at all, and a needle recorded while resolving the reference's own ARGUMENT satisfied the count and SUPPRESSED a real refusal. Since round 1 wired `stateBackend` into these contexts the proposition can be OBSERVED: read `state.outputs[<the key the read matched>]` on the producer named by the pre-pass's own `recordedImports` / `recordedOutputReads` entry, and test `carriesDynamicReference` on THAT. It is exact for every shape above, needs no needle bookkeeping, and costs no extra AWS call (the read hits the same memoized `getState` promise). The recorded entry is chosen by the intrinsic's OWN family (`Fn::GetStackOutput` reads `recordedOutputReads`) and with `.at(-1)`, since a cross-stack read nested in the ARGUMENT is recorded first and may be in the other bag. The producer's TEMPLATE is still HALF the discriminator and cannot be dropped: from the consumer's side a stored bucket name and a stored password are both bare strings, so without it every ordinary import would refuse. Its verdict is four-valued (`declared` / `widened` / `chained` / `no`) so the refusal message never asserts more than was checked: not that the producer declares THIS key from an expression when the verdict came from the widened all-outputs scan, and not that it declares one AT ALL when the evidence came from following its re-export up the chain — a `chained` verdict names the stack that does declare it instead. The chain walk (go-to-k/cdkd#2146) follows a matched output's `Fn::ImportValue` / `Fn::GetStackOutput` into the next producer's template through an export-name index, terminates by never revisiting a `(stack, export)` pair (a depth cap would return `no` for a long chain, which is the silent success it exists to kill), and WIDENS at the direct producer only, since one hop up the key is a literal name read out of a template and a miss there means that template genuinely does not declare it. A read cdkd DECLINES BY DESIGN becomes an unremediable FINDING like a secret-bearing state key rather than a whole-stack refusal, since no re-run could clear it and refusing would strand every other secret in the stack — matched on `CrossAccountSecretRefusalError`, the SUBCLASS, never on `IntrinsicResolutionRefusalError`: five of that class's six throw sites are USER-FIXABLE and are reachable here whenever a cross-stack node's argument is an `Fn::Sub` / `Fn::GetAtt` / `Fn::Split` (`resolveSub` re-raises the class), so matching the base class downgraded a fixable refusal to a finding and let scrub print `No plaintext secrets found` and exit 0 over surviving plaintext. A CONDITION-SUPPRESSED output is resolved for its needles but cannot refuse — for EITHER refusal, and the `canRefuse` test runs ahead of the by-design branch so such a position records no finding either. Suppression is decided by the condition AND by state: `conditions` comes from template parameter DEFAULTS (scrub takes no `--parameters`) and degrades to `{}` on failure, so a key present in `state.outputs` proves the deploy wrote that output whatever this run concluded. `orderScrubTargets` sorts a multi-stack run producer-before-consumer using `dependencyNames` plus `inferCrossStackStackDeps`, so one `--all` run can scrub a producer and then resolve its expression in the consumer; it runs AFTER `expandMacrosForStacks`, which rewrites the templates it scans in place, so a macro-introduced `Fn::ImportValue` is visible to the sort (a non-target producer's template is still unexpanded, which errs toward not refusing). Exit codes: 0 clean, 1 (`--dry-run --fail` found plaintext, or a REAL run found a leak scrub cannot rewrite — a secret-bearing state KEY, issue [#1919](https://github.com/go-to-k/cdkd/issues/1919), or a cross-stack read cdkd declined by design), 2 error (including both cross-stack refusals above). Scrubbing does NOT un-expose an already-leaked secret — a value ever stored in plaintext must be ROTATED in Secrets Manager.
