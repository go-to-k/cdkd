## Important Files

- **src/provisioning/import-helpers.ts** - Shared helpers for `ResourceProvider.import`: `resolveExplicitPhysicalId` (trust `--resource` `knownPhysicalId`, else read the template's physical-name property) and `normalizeAwsTagsToCfn` (re-shape any AWS tag list — `{Key,Value}` / `{TagKey,TagValue}` / map / lowercase — into the canonical CFn `Tags` shape, stripping `aws:`-prefixed entries so a CDK-deployed resource's reserved tags never fire false-positive drift). There is deliberately no `aws:cdk:path` tag walk: AWS rejects `aws:`-prefixed tag writes, so that tag never exists on a real resource and a walk keyed on it could not match (issue [#1134](https://github.com/go-to-k/cdkd/issues/1134), which removed the former `import-tag-walk.ts` helper + every provider's tag walk). Auto-mode import resolves any remaining ids from a same-named CloudFormation stack's `DescribeStackResources` (issue #1128 / #1130), in `src/cli/commands/import.ts`.

- **src/provisioning/register-providers.ts** - Shared provider registration (called from deploy.ts and destroy.ts)

- **src/provisioning/data-delete-intent.ts** - Shared destroy data-guard intent helpers (issue #1340): `hasCdkAutoDeleteTag(properties, tagKey)` / `isTruthyCfnBoolean(value)` plus the CDK tag-key constants `S3_AUTO_DELETE_OBJECTS_TAG` (`aws-cdk:auto-delete-objects`, stamped by `autoDeleteObjects: true`) and `ECR_AUTO_DELETE_IMAGES_TAG` (`aws-cdk:auto-delete-images`). Consumed by `S3BucketProvider.delete` (auto-empty of a non-empty bucket only with the tag / `DeleteContext.forceDataDelete`), `S3DirectoryBucketProvider.delete` (issue #1344 — same gate; no CDK `autoDeleteObjects` sugar exists for directory buckets, but `Tags` is a handled property since issue #609 so the `aws-cdk:auto-delete-objects` tag is declarable first-class on the L1; without it, plain destroy of a non-empty one fails with a manual-empty remediation), and `ECRProvider.delete` (`force: true` only with `EmptyOnDelete: true`, the tag, or `forceDataDelete`) — without an opt-in the AWS not-empty error surfaces like CloudFormation DELETE_FAILED. `DeleteContext.forceDataDelete` (src/provisioning/region-check.ts) is set ONLY by the deploy engine's replacement/recreate delete sites under `--force-stateful-recreation`. See the "Destroy data guards" section in docs/cli-reference.md and the DeleteContext contract note in .claude/rules/providers.md.
- **src/provisioning/config-shape.ts** - Shape guards for reading a string out of a nested CFn config block (issue #1471). `readConfigString(container, key, fallback, containerPath)` refuses a container that is present but not a plain object, and a key that is present but not a non-blank string, while still defaulting for an ABSENT container or an ABSENT key; `requireConfigString(value, fallback, path)` is the value-level half for a field already read off the provider's `properties` bag. Replaces the `(config['X'] as string) || 'default'` idiom AND its `??` spelling (issue #1493 — 9 nested-container sites across CodeBuild / DynamoDB GlobalTable / Route 53 / CloudFront OAI / ECS, plus the two `AWS::Lambda::Url` `AuthType` sites the #1471 sweep's `as string`-specific grep missed, where the default is a PUBLIC function URL; the TOP-LEVEL `properties['X'] ?? 'default'` reads followed in issue #1513, PER SITE rather than as a sweep — `requireConfigString` grew a `ConfigStringOptions` bag for the two relaxations that split required: `coerceNumber` (an unquoted YAML `IpProtocol: -1` / `Qualifier: 1` is a NUMBER today and deploys fine, so those sites stringify while the enum-valued ones still refuse) and `onUnusable` (WARN + default instead of throwing, for UPDATE-path sites only — a rollback replays `update()` with a historical STATE record as the desired bag, so a refusal there would leave the resource un-rollbackable with no template-side remedy). Guarded: API Gateway `AuthorizationType` (default = NO authorization), EC2 `InstanceType` / `Domain` / the SecurityGroupIngress-create `IpProtocol`, IAM access-key `Status`, Lambda event-invoke `Qualifier`, RDS DB-proxy `TargetGroupName`, and DynamoDB GlobalTable `BillingMode` (the one site #1513 left open while its file was owned by a parallel lane — enum-valued so no `coerceNumber`, `replayWarn` on create, an unconditional warn on update, and the refusal wrapped in a `ProvisioningError` because the read sits outside `create()`'s try, matching the `StreamSpecification` guard in the same method). Left unguarded with the reason in-code: `EC2Provider.buildIpPermission`'s `IpProtocol` (also reached from `deleteSecurityGroupIngress` and the REVOKE half of the inline-rule diff, both state-borne — the create call site is guarded instead), every `delete()` / `readCurrentState` read, and the GlobalTable `previousProperties` `BillingMode` sibling. Two things #1493 learned the hard way and the header now records: the class-covering grep is `as [A-Za-z<>,| ]+\) \?\? '` — the obvious `\] \?\? '` finds NOTHING and the cast-word form is blind to `as string | undefined` sites — and a guard behind a TRUTHINESS gate is skipped by a FALSY malformed container, so the gate must be `!= null`), which was measured at 16 sites across 5 providers and silently substituted a default — frequently the OPPOSITE of the declared intent — whenever the container was a string / array / unresolved intrinsic (`VersioningConfiguration: 'Enabled'` turned versioning OFF on a live bucket). Two constraints are load-bearing and both are enforced by tests: callers pass the **DESIRED side only** (the previous side comes from cdkd state, and refusing a malformed value recorded there would make the stack permanently undeployable — `KinesisProvider`'s `previousProperties` read is deliberately left unguarded), and TOP-LEVEL call sites use `requireConfigString(properties['X'], …)` rather than handing the whole bag to `readConfigString`, so the `properties['X']` element-read stays visible to the `handled-property-wiring` critic. This is a provider-layer guard rather than a pre-flight template check because the field rules are only decidable AFTER intrinsic resolution — at pre-flight a legitimate `Fn::If`-valued block is an object whose inner key does not exist yet. Two CONTAINER-only guards sit beside the string pair for blocks the caller never reads a string out of, so `readConfigString`'s rule 2 is unreachable from them: `requireConfigArray(value, path, options?)` for a LIST block (issue #1493 review; the `onUnusable` downgrade added by #1579) and `requireConfigObject(value, path, options?)` for an OBJECT block (issue #1581). Both take only the `onUnusable` half of the options bag (`coerceNumber` is meaningless for a container), both are overloaded so a throw-only caller keeps a non-`undefined` return type, and both leave the ABSENT case to the caller's own `!= null` test — an omitted block legitimately means "defaulted", and `{}` / `[]` are legitimate values. `requireConfigObject` exists for the silent-DROP shape its siblings structurally miss: a container whose members are probed for PRESENCE (`filter?.['Prefix'] ?? rule['Prefix']`, `storageClassAnalysis?.['DataExport'] != null`) indexes every probe of a malformed value to `undefined`, so the block reads as EMPTY and the caller proceeds without it — an S3 lifecycle rule losing its whole location scope and applying BUCKET-WIDE, an analytics configuration losing its data export. Guarded today: S3 `LifecycleConfiguration.Rules[].Filter`, `AnalyticsConfigurations[].StorageClassAnalysis` and its `.DataExport`, and `ReplicationConfiguration.Rules[].Filter` — the last found by the #1581 PR review and the widest of the three, because its fall-through arm emits `Filter: {}`, the valid CFn form meaning "replicate EVERY object", so a malformed container replicated the whole bucket instead of the declared subset (that site also sat behind a TRUTHINESS gate, the #1493 shape, so a falsy `Filter: ''` skipped the branch entirely; it is `!= null` now). Audited and deliberately left unguarded, with the reason in-code: the per-ITEM `config` containers of the six S3 appliers that carry the `onUnusable` replay callback — four already refuse a non-object item through an existing `readConfigString(config | rule, …)` (lifecycle rules, replication rules, intelligent tiering, inventory), and the other two (metrics / analytics) fail LOUDLY at S3 on the missing required `Id`, which is not the silent hazard these guards exist for. The count read "five appliers, three refuse" until issue #1595, whose own comments corrected the enumeration: the fourth refusal sits in `applyReplicationConfiguration`, the same function whose `Filter` container #1581 had just guarded, which is why it read as already-handled. Those existing per-item refusals then needed a replay split of their OWN (issue #1595): each is a `readConfigString` carrying no `onUnusable`, so it hard-threw on the state-replay paths — but the helper's warn-and-DEFAULT downgrade is the WRONG answer there, because every default at those sites (`Status` -> `Enabled`, `IncludedObjectVersions` -> `All`) lands on a LIVE resource and would START an expiration / archive-tiering / replication rule the template had disabled. So `configStringRefusal(container, key, fallback, containerPath, options?)` exports the predicate WITHOUT the action: it returns the refusal sentence (or `undefined`) and the caller performs the SKIP its sibling container guard already uses, with the same per-applier unit — the WHOLE Put for lifecycle / replication (whose Put replaces every rule) and the single configuration ITEM for intelligent tiering / inventory (whose Put is per-Id). `requireConfigString` is implemented on the same internal predicate so the probe and the read cannot diverge (pinned by a test that enumerates both over every value shape), and the create path never probes, so its refusal is byte-identical to before. Guarded this way today: the lifecycle + replication per-rule `Status`, the intelligent-tiering per-item `Status`, and the inventory per-item `IncludedObjectVersions`. The FIELD-level reads on the same replay-reachable paths were split out as issue #1605 and are now settled, each with a DIFFERENT skip unit because the unit was the whole question: versioning `Status` SKIPS the Put (there is no item to skip and no previous value to keep, and the `Suspended` fallback is the direction #1471 measured turning versioning OFF on a live bucket — so the skip's real cost, an un-reverted rollback of a versioning change, is the cheaper one and is announced in the warning); the logging destination + `LogFilePrefix` pair SKIPS the Put TOGETHER (`PutBucketLogging` replaces the whole status, and the destination's blank fallback makes the clearing branch turn access logging OFF), with the GATE in `applyAllSubConfigsForCreate` taking the same downgrade because it reads the same field to decide whether to call at all; and the inventory `ScheduleFrequency` / `Schedule.Frequency` pair takes a THIRD shape neither #1581 nor #1595 needed — a malformed FIRST source FALLS THROUGH to the second (the value the template also declares), and only when that is unusable too is the configuration ITEM skipped, since inventing a `Weekly` cadence for a live report is the substitution this class of guard exists to refuse. #1605 also threaded `CreateContext` into `applyConfiguration`, whose versioning read was reachable from the reverse-replacement create with no way to downgrade. A BOOLEAN pair joined the family in issue #1751: `coerceCfnBoolean(value)` (moved here from `s3-bucket-provider.ts`, which had it module-local — CloudFormation is stringly typed, so `'true'` / `'false'` are legitimate declarations) and `configBooleanRefusal(container, key, containerPath)`, the boolean twin of `configStringRefusal` sharing the same two halves (CONTAINER then FIELD) and the same detail clause. It exists for the shape neither string guard can see: a member read as `x ?? <default>`, where `??` treats a DECLARED `null` as absent — the S3 inventory `Enabled`, whose default `true` ENABLED a report the template was disabling, with no warning anywhere. The FIELD half IS `coerceCfnBoolean`, i.e. the function the wire read calls, per this module's share-the-predicate rule.
- **src/provisioning/composite-id.ts** - Refusal guard for COMPOSITE physicalIds (issue [#1672](https://github.com/go-to-k/cdkd/issues/1672)). `ResourceProvider` passes a single `physicalId: string`, so a type needing more than one value to address its resource PACKS them joined by `COMPOSITE_ID_SEPARATOR` (`<databaseName>|<tableName>` for `AWS::Glue::Table`, `<apiId>|<typeName>|<fieldName>` for `AWS::AppSync::Resolver`, ...). The separator is NOT escaped, so a segment containing one produces an id with the wrong ARITY — for a Glue table named `a|b` in database `mydb` the recorded `mydb|a|b` decodes to database `mydb`, table `a`, and BOTH halves are non-empty so every existing well-formedness guard passes. The deploy then SUCCEEDS while `cdkd destroy` deletes the wrong table (or warn-and-skips, reporting success while the real one stays alive and billing) and `cdkd drift` reads back `undefined` forever. AWS itself accepts such a name (live probe, us-east-1 2026-08-12: `glue:CreateTable` with `TableInput.Name: 'a|b'` succeeds) and CloudFormation manages it fine, so the limitation is cdkd's own and the honest answer is to REFUSE at deploy time rather than record an id naming something else. Two entry points mirroring `config-shape.ts`'s pair: `packCompositeId(resourceType, logicalId, segments, options?)` is the ACTION (throws a `ProvisioningError`, or warns-and-packs under `options.onRefusal` — the `CreateContext.replayingState` downgrade, since a state record cannot be edited from the template) and `compositeIdSeparatorRefusal(...)` is the bare PREDICATE returning the sentence, for the `import()` paths whose answer is warn-and-SKIP (`return null`). Both share one message builder, and the predicate tests the STRINGIFIED value rather than `typeof value === 'string'` — every call site feeds an unvalidated `as string` cast, so a YAML list `Name: ['a|b']` is truthy, reaches the pack as an ARRAY and stringifies to exactly the ambiguous id the guard exists to refuse. Adopted at every CREATE-path packing site across glue / s3-tables / appsync / ec2 / apigateway / lambda-event-invoke-config, computed BEFORE the AWS call wherever the segments allow (the two that cannot — AppSync ApiKey and EC2 EIP, whose segments come from the create RESPONSE — sit after it and outside the wrapping `try`, so a refusal can never be mis-labelled as an AWS creation failure). `route53-provider.ts`'s three RecordSet packers joined that set in issue [#1711](https://github.com/go-to-k/cdkd/issues/1711) — deferred by the sweep only because a concurrent lane owned the file, and exposed at the one segment the sweep never reached: `recordName` is `properties['Name']`, the only TEMPLATE-chosen segment of the whole family. A four-part id IS rejected by `parseRecordSetCompositeId`'s exact-three-segment rule — but "so the failure mode is loud" was FALSE, and review caught it: three non-empty segments is not proof of a composite either, so a record NAME carrying two pipes (the CFn physicalId `--migrate-from-cloudformation` pre-populates) decoded to a DIFFERENT hosted zone at three sites ABOVE the packers — `importRecordSet`'s early accept, `resolveRecordSetIdentity`'s short-circuit, and `deleteRecordSet`'s own parse, where `cdkd destroy` then targeted a non-existent zone and reported SUCCESS over a live record. All three now cross-check the parsed segments against the template via `compositeAgreesWithTemplate` (TYPE and NAME, each skipped when its template side is unusable; the name compare goes through `canonicalizeQueryName` so case / trailing dot cannot cause a false rejection). `create` refuses before `ChangeResourceRecordSets` (with the ordinary `CreateContext.replayingState` downgrade, which needed `context` threaded through `create()` — the provider declared none); `update` takes the `updateRoute` precedent and downgrades UNCONDITIONALLY, since it has no context and cannot tell a template-borne update from the state-borne bag `drift --revert` / the rollback revert arm hand it; and `import()` takes the method's own `adoptVerbatim` escape hatch rather than freezing a mis-arity id into state. Deliberately NOT covered, with the reason in the module header: `intrinsic-function-resolver.ts`'s joins, which build `Ref` VALUES that nothing decodes. Directions 1 (stop packing where the decode sites already receive the properties bag) and 2 (escape the separator) remain open on #1672. The module's third entry point is the DECODE-side counterpart, `compositeIdFormatMessage(format, logicalId, physicalId, options?)` (issue [#1657](https://github.com/go-to-k/cdkd/issues/1657)): roughly half the decode sites stated the expected shape (`expected "restApiId|resourceId|httpMethod", got "..."`) and half only echoed the value back, and since the format is documented nowhere else (the companion docs gap is issue #1656) the message was the user's ONLY route to it on the silent half. All 17 decode sites that emit a well-formedness message now render through one builder from a per-type `CompositeIdFormat` (`label` + ordered `segments`, plus an optional `alsoAccepts` for `AWS::S3Tables::Table`'s bare-ARN alternative) — the already-correct sites included, so they cannot drift back. **Every segment is a PLACEHOLDER, and the names must match the type's `packCompositeId` segment names**: the first cut of this change gave `AWS::EC2::VPCGatewayAttachment` a literal-segment form rendering `IGW|<vpcId>`, on the belief that `IGW` was a fixed token cdkd packs. It is not — the packer emits the real `internetGatewayId` — so the message named a token no code path produces and a user repairing `state.json` as instructed would have called `DetachInternetGateway(InternetGatewayId: "IGW")`. PR review caught it; the literal form was deleted rather than corrected, since nothing else wanted it. This is a WORDING change only: each caller keeps its own split-and-guard, because the arities genuinely differ (some sites accept AT LEAST N segments, some destructure the first N and tolerate extras — the #1672 ambiguity) and folding them into one predicate would silently change which ids deploy. The `{ skipping: true }` variant is for the five warn-and-continue DELETE arms: the policy is unchanged, but the warning now says the AWS resource is LEFT IN PLACE while `cdkd destroy` reports success, so the orphan is diagnosable. Two rows of the issue's own table were already stale when it was worked: `AWS::S3Tables::Table` had gained its expected-format text, and `route53-provider.ts`'s message no longer exists at all — PR #1678 removed that arm in favour of `parseRecordSetCompositeId` + a template-derived fallback, so there is no malformed-id message left to fix there.
- **src/provisioning/nested-stack-messages.ts** - User-facing message builders for the `AWS::CloudFormation::Stack` delete path (issue [#1777](https://github.com/go-to-k/cdkd/issues/1777)). Today one export: `nestedStackChildFailureMessage(childStackName, errorCount, alsoSkippedCount, alsoInterrupted)` — the message `NestedStackProvider.delete` THROWS when the child stack's own destroy reported `errorCount > 0`. **The module must stay a LEAF — no imports, ever.** That is the whole reason it exists rather than living in `providers/nested-stack-provider.ts`: that provider imports `destroy-runner.ts` (it recurses into a child destroy), which imports `register-providers.ts`, which imports every provider including `nested-stack-provider` itself — so importing the builder from there pulled the entire provider registry into two unrelated unit tests and closed that cycle, which is harmless only for as long as nothing on the ring does module-scope work. A builder rather than an inline template literal because the exact string is needed by tests on BOTH callers of `delete()`: the runner and the deploy engine each classify a delete failure by MESSAGE, reading an already-deleted-shaped phrase (`not found` / `does not exist` / `No policy found` / `NoSuchEntity` / `NotFoundException`, plus the deploy engine's `was not found` / `ResourceNotFoundException`) as idempotent success and DROPPING the state row — the exact outcome the throw exists to prevent — so a hand-copied literal in a test would keep passing while the shipped wording drifted into that shape.
- **src/provisioning/final-snapshot.ts** - `DeletionPolicy` / `UpdateReplacePolicy: Snapshot` support (issues #1352 / #1353 / #1354): `ATOMIC_FINAL_SNAPSHOT_TYPES` (RDS DBInstance / DBCluster, Neptune / DocDB clusters, ElastiCache CacheCluster — the delete call sites generate `buildFinalSnapshotIdentifier(physicalId, resourceType)` and thread it via `DeleteContext.finalSnapshotIdentifier`; each provider flips its delete from `SkipFinalSnapshot: true` to the API's atomic final-snapshot form; ONLY on the SDK route — a cc-api-routed atomic type is refused and `CloudControlProvider.delete` fail-closes on the field), `PRE_DELETE_SNAPSHOT_TYPES` + `createPreDeleteFinalSnapshot` dispatcher (all CC-routed: `AWS::EC2::Volume` via EC2 `CreateSnapshot` tagged `cdkd:final-snapshot-of`; `AWS::Redshift::Cluster` via `CreateClusterSnapshot`; `AWS::ElastiCache::ReplicationGroup` via ElastiCache `CreateSnapshot` — each waited to ready, idempotent reuse via the tag / the `finalSnapshotNamePrefix` name prefix across delete re-runs), `unsupportedFinalSnapshotError` / `ccRoutedFinalSnapshotError` refusals, and (issue #1366) `finalSnapshotMechanism(type, route)` / `refusesFinalSnapshot(type, route)` — the mechanism matrix as a PURE function, so the executor that ACTS on it and the `cdkd rollback` plan preview that DESCRIBES it read one source (issue #1368 extends that to the preview's STATE effect: a refused Snapshot delete no longer unwinds the record, since the next-older segment is classified against it). The two type sets are DISJOINT by construction — `finalSnapshotMechanism` tests the atomic set first, so a type in both would silently take the atomic arm and never reach the pre-delete snapshot; pinned in `final-snapshot.test.ts` alongside the union-equals-the-CFn-documented-list fence (re-homed there from the deleted `supportsFinalSnapshot` predicate, #1368). Consumed by the deploy engine (`prepareFinalSnapshotForDelete` — the shared gate for the DELETE branch AND the four replacement / recreate delete sites), `destroy-runner.ts`, and `rollback-executor.ts` — the latter twice: `rollbackFinalSnapshotId` for the delete-of-the-NEW-resource under `UpdateReplacePolicy` (honors only the atomic SDK-routed shape, plain-deletes otherwise — scope decision on #1354), and `prepareCreateRollbackFinalSnapshot` for a rolled-back CREATE under `DeletionPolicy` (the FULL matrix, refusing what it cannot snapshot — issue #1358). The engine's clients come from `DeployEngineOptions.finalSnapshotClients` (stack-region-pinned `AwsClients`, structurally a `PreDeleteSnapshotClients`), threaded on to `RollbackExecutorContext.finalSnapshotClients`; `--skip-final-snapshot` (deploy / destroy / state destroy / rollback, `skipFinalSnapshotOption` in `src/cli/options.ts` — deliberately NOT in the shared `destroyOptions` array `cdkd orphan` consumes) is the explicit data-loss opt-out.
- **src/provisioning/emr-configuration.ts** - Shared CFn -> SDK shape converters for the `AWS::EMR::*` nested config blobs whose CFn key spelling diverges from `@aws-sdk/client-emr` (issue #1383): `toSdkConfigurations` (renames `Configuration.ConfigurationProperties` -> the SDK's `Properties` at EVERY `Configurations` nesting level), `toSdkStepConfigs` (`HadoopJarStepConfig.StepProperties` -> `Properties`), and `toSdkInstanceTypeConfigs` (per-instance-type nested `Configurations`). Both are pure key renames — the VALUE shapes already match (`Record<string,string>` / `KeyValue[]`, verified against the live CFn registry schema) — but the AWS SDK v3 serializer drops unknown members, so before the conversion every EMR application configuration (spark-defaults / hive-site / yarn-site ...) silently vanished while cdkd reported success. Consumed by `EMRClusterProvider` (top-level `Configurations` / `Steps`, per-group `Configurations`, per-fleet `InstanceTypeConfigs`), `EMRInstanceGroupConfigProvider` (create), and `EMRInstanceFleetConfigProvider` (create + the `ModifyInstanceFleet` update). No inverse is needed: `Configurations` / `Steps` / `InstanceTypeConfigs` are all declared in `EMRClusterProvider.getDriftUnknownPaths` and neither instance provider implements `readCurrentState`. Non-object / non-array inputs (an unresolved intrinsic) pass through untouched so AWS surfaces the real validation error. The `AWS::EMR::*` types are NOT yet in `NESTED_KEY_TARGETS` (`scripts/gen-nested-key-coverage.ts`) — critic target expansion is tracked in issue #1393.
- **src/provisioning/dynamodb-warm-throughput.ts** - The two `WarmThroughput` rules shared by `AWS::DynamoDB::Table` and `AWS::DynamoDB::GlobalTable` (issue [#1857](https://github.com/go-to-k/cdkd/issues/1857)): `coerceWarmThroughput` (per-member coercion of the stringly-typed CFn value into the SDK's Long field — a quoted `'12000'` or an `Fn::Sub` result otherwise reaches the wire as a string and AWS rejects it; it drops an unusable member while sending the usable one and REPORTS the dropped names so the caller's warning can say which half it refused) and `isWarmThroughputDecrease` (AWS rejects an `UpdateTable` that LOWERS warm throughput, so a template declaring a value AWS has since grown past issues a call that can only fail, and `cdkd drift --revert` re-issues it forever — declared members only, and it fails OPEN on a MIXED or unreadable-live block so a false positive cannot swallow a real increase). The coercion's `spec` presence IS the sendability predicate, so the write-side send and any drift-side gate cannot answer differently. **Provenance, stated precisely because the first cut over-claimed it**: only the `AWS::DynamoDB::Table` spelling ever SHIPPED (PR #1808, issues #1760 / #1768) — the GlobalTable side never existed outside issue #1857 — so this is the Table rule LIFTED, not two shipped rules reconciled, and no deployed behaviour changed for either type when it moved. What was compared is the shipped rule against the GlobalTable DRAFT: the decrease guard agreed on every probe and the coercion on all but a whitespace-only string (`Number('   ')` is `0`, not `NaN`), where the shared rule takes the REFUSING answer. `dynamodb-table-provider.ts` keeps its own `coerceWarmThroughput` name as a thin adapter, so its behavior is unchanged; the drift-side gates with no GlobalTable counterpart (`isSendableWarmThroughput` / `isRefusedWarmThroughput` / `declaresWarmThroughput` / `warmThroughputAlreadyMatches`) stay there, and the replica / per-region plumbing stays in the GlobalTable provider. It also exports `toFiniteNumber`, the reader for every OTHER numeric CFn member (capacity units, on-demand ceilings, auto-scaling min/seed): the same rule had been hand-written THREE times — here, as the Table provider's `capacityNumber` (byte-identical) and as the GlobalTable provider's own copy — and the review of issue #1857's PR collapsed them into this one, since a file REFUSING a whitespace `WarmThroughput` while reading a whitespace `MaxReadRequestUnits` as ZERO is exactly the divergence this module exists to prevent, one property over. `WARM_THROUGHPUT_MEMBERS` is shared for the same reason: both providers' member loops read it rather than re-spelling the tuple. The RULE is pinned by `tests/unit/provisioning/dynamodb-warm-throughput.test.ts`, named for the module so a third consumer's author finds it; each provider's suites exercise it through their own send sites.
- **src/provisioning/dynamodb-index-busy-delete.ts** - The index-busy `DeleteTable` rule BOTH DynamoDB providers read (issues [#1830](https://github.com/go-to-k/cdkd/issues/1830) / [#1931](https://github.com/go-to-k/cdkd/issues/1931)). AWS refuses `DeleteTable` while any GSI is mid-transition (`Cannot delete table while indexes are being created, updated, or deleted`), and the condition is TRANSIENT — application auto-scaling can start an index capacity change at any moment — so surfacing it as a hard `PartialFailureError` made users re-run a destroy for something that clears itself. Owns `INDEX_BUSY_DELETE_MESSAGE` / `isIndexBusyDeleteError` (the classifier, keyed on the MESSAGE because AWS reports this as a plain `ResourceInUseException` — the same NAME it uses for terminal conflicts like "Table is being created", so a name-keyed predicate would spend the whole budget on them, a settle poll plus a backoff step per attempt, i.e. minutes, before failing identically), `INDEX_TRANSITIONAL_STATUSES` / `hasTransitionalIndex` (the CONDITION the re-arm waits on, tested on the TRANSITIONAL values rather than `!== 'ACTIVE'`, so an unrecognized status cannot park a delete for its whole cap on a table that is fine), the budgets — `TABLE_DELETE_INDEX_BUSY_MAX_RETRIES` (14) and `GLOBAL_TABLE_DELETE_INDEX_BUSY_MAX_RETRIES` (8), PER CALLING TYPE and passed in at the call site rather than read from the module, plus `DELETE_INDEX_BUSY_REARM_MAX_ATTEMPTS` (60) and `INDEX_SETTLE_POLL_INTERVAL_MS` (1s, the unit every poll count on this path is denominated in, including the 900-poll #1521 gate and the `Table` provider's `waitForTableActiveAfterUpdate`), `waitForIndexesSettled` (the bounded best-effort poll — on timeout it warns and RETURNS rather than throwing, because a throw on the delete path would STRAND the resource; a throttled describe keeps waiting rather than reading as settled, and its unclassified-error arm logs only the error CLASS at default verbosity, since AWS's raw text carries the account id and assumed-role ARN into the terminal and the persisted events store), `indexBusyRetryWarning` (the ONE line at default verbosity, as `withRetry` announces retries only at debug; its remaining-attempt count AND its remaining-wall-clock floor are DERIVED from the budgets, and it deliberately does NOT quote AWS's own sentence, which the integ greps for to prove AWS really refused), and `deleteTableWithIndexBusyRetry` (the loop itself). **The re-arm bound is the load-bearing arithmetic**: the poll runs PER RETRY, so the loop's wall clock is the product — at the #1521 gate's 15-minute default it would be hours, and at 60 polls (~1.2s each: 1s of sleep plus a `DescribeTable` round trip) it is ~18.4 min at the `Table` budget and ~10.4 min at the `GlobalTable` one. `destroy-runner.ts` runs the delete under a per-resource deadline (30 min by default) that wraps its whole OUTER retry loop — up to 4 `delete()` calls, not one — and the budgets survive that only because this refusal matches no `RETRYABLE_ERROR_MESSAGE_PATTERNS` entry, so the outer loop never re-invokes `delete()` for it; adding the message to those patterns would silently take the `Table` worst case to ~74 min. **Why the budgets differ, and why they are per CALLER**: both types shipped at 8 until issue [#1950](https://github.com/go-to-k/cdkd/issues/1950), where a live run measured a 5-item table's GSI create consuming 7 of those 8 — i.e. the budget cleared only the FLOOR of AWS's roughly fixed index-create latency. What is left of the deadline when each type REACHES the loop is not the same: `Table` has spent at most a <=60-poll ACTIVE wait (~72s), while `GlobalTable` may have spent the #1521 gate's 900 polls (~18 min) and `waitForReplicaGone`'s 600 polls (~12 min) per non-local replica. So `Table` took 14 — the largest value keeping its delete path inside two thirds of the deadline (16 reaches ~27.4 min at a pessimistic poll cost, against a deadline `withResourceDeadline` does not CANCEL at) — and `GlobalTable` kept 8, because gate + loop(8) is ~28.4 min and FITS while gate + loop(14) is ~36.4 min and does not: the raise would have pushed the common single-region `TableV2` shape over a line it is currently inside. The replicated shape (~40 min) was already over before #1950 and is unchanged by it — issue [#1955](https://github.com/go-to-k/cdkd/issues/1955). Living here rather than in either provider is the point, the same reason `dynamodb-warm-throughput.ts` exists: two files spelling the classifier or the budget independently are two chances for a later fix to move one while the sibling type keeps the old answer. Deliberately NOT here: `GlobalTable`'s pre-delete #1521 gate and its replica / auto-scaling teardown, which the `Table` provider has neither of; and each provider keeps its OWN `deleteTableRetryDelays` sleep seam, so one suite cannot silence the other's backoff. The RULE is pinned by `tests/unit/provisioning/dynamodb-index-busy-delete.test.ts`, which also pins that BOTH providers route through it rather than each holding a copy, and whose budget fences MEASURE the real loop (attempts, re-arms, every millisecond `withRetry` asks to sleep) rather than restating its schedule — one per type, since the ceiling that binds each is different: for `Table`, the floor it must clear (2x the measured 8-min one) and a delete-path worst case inside two thirds of `DEFAULT_RESOURCE_TIMEOUT_MS`; for `GlobalTable`, the #1521 gate's OBSERVED poll cap plus the loop staying under the deadline, with the `Table` budget asserted as a premise NOT to fit there. Both providers' re-arm wiring is fenced too — the `Table` twin was missing, and a 900-poll mutation there left the whole suite green.
- **src/provisioning/ec2-termination-protection.ts** - Shared `--remove-protection` helper for `AWS::EC2::Instance`: `disableInstanceApiTermination()` (flip `DisableApiTermination` off, idempotent, errors swallowed at debug), `isTerminationProtectionPropagationError()` (matches the "may not be terminated. Modify its disableApiTermination" 400 from both `TerminateInstances` and the Cloud Control `DeleteResource` wrapper), and `TERMINATION_PROTECTION_MAX_ATTEMPTS`. Used by `EC2Provider.deleteInstance` (SDK path) and `CloudControlProvider.delete` (CC-API path — an instance routes through Cloud Control whenever its template trips the #614 silent-drop routing) so `--remove-protection` works regardless of which delete path the instance takes; the modify WRITE lags the delete READ, so both callers flip-off + retry the delete to close the propagation window. ALSO used by `ASGProvider.delete` (issue #796): an `AWS::AutoScaling::AutoScalingGroup` whose launch template sets `DisableApiTermination: true` launches instances that survive the group's `DeleteAutoScalingGroup(ForceDelete: true)` (ASG-level DeletionProtection + ForceDelete governs only the group + scale-in protection, not EC2-level termination protection), so under `--remove-protection` the provider enumerates the group's current instances and flips each one's `DisableApiTermination` off before the force delete — the ASG's own async terminate loop then absorbs the modify-WRITE propagation lag, so no per-instance delete retry is needed there. An ASG can ALSO route via Cloud Control when its template sets a silent-drop property such as `AvailabilityZoneIds` (#614 routing) — Cloud Control's `DeleteResource` cannot `ForceDelete` a protected ASG or clear its protection, so `CloudControlProvider.delete` detects `removeProtection === true && resourceType === 'AWS::AutoScaling::AutoScalingGroup'` and delegates to `new ASGProvider().delete(...)` (the single source of truth for protected-ASG deletion), keeping the SDK and CC routing paths behaviourally identical (issue #798; CDK's L2 emits `availabilityZones` names not `AvailabilityZoneIds`, so this CC path only fires for hand-written L1 / imported templates).

- **src/provisioning/property-coverage.ts** + **property-coverage.generated.ts** - Pre-flight property-level rejection (parallel to unsupported-types but at top-level CFn property granularity). The `.generated.ts` ships per-Tier-1-type `{ handled, silentDrop }` records, codegen'd from `tests/fixtures/cfn-schemas/*.json` + each SDK provider's `handledProperties` / `unhandledByDesign` declarations by `scripts/gen-property-coverage.ts` (`vp run gen:property-coverage`; CI fails on drift; the codegen parses provider sources via the TypeScript Compiler API so no `dist/` bootstrap is needed). - **src/provisioning/mutually-exclusive-properties.ts** - Pre-flight rejection of property COMBINATIONS AWS accepts only one of (issue [#1634](https://github.com/go-to-k/cdkd/issues/1634)) — the third member of the pre-flight family beside `unsupported-types.ts` (whole TYPES) and `property-coverage.ts` (individual PROPERTIES). Owns the hand-written `MUTUALLY_EXCLUSIVE_PROPERTIES` rule table, `findMutuallyExclusiveViolations()` and `buildMutuallyExclusiveMessage()`; applied by `ProviderRegistry.validateMutuallyExclusiveProperties`, which `validateResourceProperties` runs BEFORE the silent-drop routing chatter (a template CFn itself rejects should not first emit a page of routing lines). Exists because a PROVIDER-side refusal is only reachable on a template-borne CREATE: once the resource exists the diff classifies `NO_CHANGE`, the provider is never called, and the invalid template deploys forever — which is what `EC2Provider.createRoute`'s #1566 multi-destination refusal could not catch after #1591 normalized both diff sides. **The presence predicate is the load-bearing part**: pre-flight runs BEFORE intrinsic resolution, so a key behind an unresolved intrinsic (`{Fn::If: [...]}` / `{Ref: ...}`) counts as UNKNOWN, never as declared — an `Fn::If` arm can resolve to `AWS::NoValue`, so a template carrying BOTH keys conditionally is VALID and must not be refused; otherwise the predicate is `Boolean(value)`, matching `narrowRouteDestinations`' truthiness narrowing in `ec2-provider.ts` so pre-flight cannot refuse a bag the provider would have accepted. The fail-SAFE direction is deliberate (a combination this module lets through is still caught by the provider's create-path refusal, whereas a false refusal blocks a valid deploy). There is deliberately NO `--allow-*` escape hatch — the defect is in the TEMPLATE, not in cdkd — so the table is seeded with only the ONE verified combination (`AWS::EC2::Route`'s three destination keys, duplicated from the module-private `ROUTE_DESTINATION_KEYS` and fenced by a unit test that pins every rule property against the type's CFn schema fixture, so a rename on either side fails a test instead of leaving a silently dead rule). `cdkd diff` is deliberately NOT wired: #1591's canonicalization warning already fires there — `DiffCalculator.compareProperties` warns whenever `canonicalizeProperties` changes the desired bag (`src/analyzer/diff-calculator.ts`), which is exactly this shape — so a second surface would be duplicate noise. Verified live 2026-08-12: with the second destination added to a deployed route, `cdkd diff` prints that warning and reports no changes (exit 0) while `cdkd deploy` refuses at pre-flight.

- **src/provisioning/interrupt-watch.ts** - The ONE SIGINT watch every bounded wait under `src/provisioning/**` uses (issues [#2053](https://github.com/go-to-k/cdkd/issues/2053) / [#1952](https://github.com/go-to-k/cdkd/issues/1952) / [#2104](https://github.com/go-to-k/cdkd/issues/2104)), plus the `InterruptedWaitError` type and the `isInterruptedWaitError` cause-chain classifier `deploy-engine.ts` reads. Four module-local copies preceded it and the consolidation is what made two properties correctable at all, since one `delete()` traverses more than one module: ONE error type (the engine's own `InterruptedError` is module-private, so a bare `Error` from a provider read as a resource failure and triggered an automatic ROLLBACK on Ctrl-C — worse still on create paths, where the interrupt landed in partial-create cleanup arms that issue a delete) and ONE STICKY latch (clearing it on dispose looks equivalent and is not: sequential waits always empty the live set between them, so a signal in the #1521 gate left the index-busy loop and the gone-wait after it deaf — issue #1952's own scenario surviving its own fix). Only a COMMAND clears the latch, via the scope `forwardSigtermToSigint()` opens in `src/utils/interrupt-signals.ts`; the process listener is never removed BETWEEN waits, because one torn down in that gap cannot record a signal landing in it. Two further properties are each the fix for a measured failure. It arms only inside that command scope, NOT on `process.listenerCount('SIGINT') > 0` — `cdkd drift --revert` owns no shutdown path and runs `provider.update` at concurrency 4, and a concurrent CloudFront / ACM / Route53 wait installs a transient SIGINT listener, so a count-based gate armed the watch permanently through someone else's listener and left Ctrl-C unable to terminate the command. And the handler force-quits when it is the LAST SIGINT listener. The case that motivated it was a multi-stack destroy: `destroy.ts` registered none and `destroy-runner.ts` removes its own in a `finally`, so between two stacks the watch was alone, and merely latching there swallowed the Ctrl-C while the loop went on to delete the next stack. Issue [#2117](https://github.com/go-to-k/cdkd/issues/2117) closed THAT instance from the other side — `destroy.ts` / `state.ts` now hold a command-scoped handler for their whole run (`watchCommandInterrupt`, `src/utils/interrupt-signals.ts`) and their loops read it live — so this handler no longer fires during a destroy, which is the improvement rather than a loss: it used to exit 130 with the lock stranded and without stopping the loop gracefully. Its remaining population is the commands that register NO handler at all (`import` / `export` / `scrub` / `orphan` / `drift` / `state refresh-observed`), which is what its own scope note in the source enumerates. That property imposes a rule on any lock-holding command — release BEFORE unregistering your SIGINT handler — because unregister-first leaves the lock held with no handler and turns a Ctrl-C there into a 30-minute stranded lock; `destroy-runner.ts`'s main `finally` had it backwards and now matches its own strong-ref path, and `rollback.ts`'s did too until issue [#2118](https://github.com/go-to-k/cdkd/issues/2118), which also put both unregistrations in a nested `finally` so a synchronously throwing release cannot leak them (defence in depth — `releaseLock` is `async`, so nothing in `LockManager` reaches that shape today). The ORDER within the teardown pair is consistency and not mechanism, which is worth stating because the first cut of that fix claimed otherwise in four places: the two calls are adjacent and synchronous, so no signal lands between them, and `unforwardSigterm()` first would not empty the SIGINT set anyway since the command's own handler is still registered at that point. `deploy-engine.ts` is now the only site that still unregisters first, and says at the call site why that is safe there: `deploy.ts` holds a top-level SIGINT handler that outlives the method, so the process is never left with zero listeners under the lock. The rule has a second half that cost a review round to find: arming for longer MOVES the window a signal can arrive in, so anything READING the interrupt has to be re-checked — `destroy-runner.ts` reads `result.interrupted` once inside its `try` and re-syncs it at the end of the `finally`, or a Ctrl-C during the release left `destroy --all` free to delete the next stack. That re-sync is a narrowing rather than a closure — it runs AFTER the runner has already dropped its own listener — and issue [#2117](https://github.com/go-to-k/cdkd/issues/2117) supplied the structural half: the command-scoped handler above, which is armed in every window rather than the ones the runner spans. Both are kept, because they answer different questions: `result.interrupted` is the PER-STACK outcome (state preservation, the summary line, the `--purge-events` skip), the command-level flag is what the loop and the exit code read. The command scope is a DEPTH COUNTER, so a nested command's close cannot disarm the watch its caller relies on. `isInterruptedWaitError` walks the `cause` chain with a `visited` set and no depth ceiling, because the chain grows by one `ProvisioningError` per nested-stack level and a ceiling reinstates the rollback bug at depth. `interruptWatchTestSeam` / `disarmInterruptWatchForTests` exist because arming is a one-way door inside a command and a provider suite runs no command; the unit that owns the module drives the real scope functions instead.

- **src/provisioning/describe-type.ts** - Shared `cloudformation:DescribeType` invocation with THROTTLE-ONLY retry (issue #1236), consumed by `write-only-properties.ts`, `create-only-properties.ts`, and `export.ts`'s primary-identifier resolution (which passes its own injected CFn client via the optional second argument). ## SDK Providers

SDK Providers are in `src/provisioning/providers/`. See [README](../../README.md) for the full list of supported resource types. Registration is centralized in `src/provisioning/register-providers.ts`.

SDK Providers are preferred over Cloud Control API for performance -- they make direct synchronous API calls with no polling overhead. Cloud Control API is used as a fallback for resource types without an SDK Provider.
