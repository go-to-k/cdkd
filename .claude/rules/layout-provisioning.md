## Important Files

- **src/provisioning/import-helpers.ts** - Shared helpers for `ResourceProvider.import`: `resolveExplicitPhysicalId` (trust `--resource` `knownPhysicalId`, else read the template's physical-name property) and `normalizeAwsTagsToCfn` (re-shape any AWS tag list — `{Key,Value}` / `{TagKey,TagValue}` / map / lowercase — into canonical CFn `Tags`, stripping `aws:`-prefixed entries so a CDK-deployed resource's reserved tags never fire false-positive drift). Deliberately no `aws:cdk:path` tag walk: AWS rejects `aws:`-prefixed tag writes, so the tag never exists on a real resource and a walk keyed on it could not match (issue [#1134](https://github.com/go-to-k/cdkd/issues/1134), which removed `import-tag-walk.ts` + every provider's tag walk). Auto-mode import resolves remaining ids from a same-named CloudFormation stack's `DescribeStackResources` (issues #1128 / #1130, in `src/cli/commands/import.ts`).

- **src/provisioning/register-providers.ts** - Shared provider registration (called from deploy.ts and destroy.ts)

- **src/provisioning/data-delete-intent.ts** - Shared destroy data-guard intent helpers (issue #1340): `hasCdkAutoDeleteTag(properties, tagKey)` / `isTruthyCfnBoolean(value)` + the CDK tag-key constants `S3_AUTO_DELETE_OBJECTS_TAG` (`aws-cdk:auto-delete-objects`) and `ECR_AUTO_DELETE_IMAGES_TAG` (`aws-cdk:auto-delete-images`). Consumers: `S3BucketProvider.delete` (auto-empty a non-empty bucket only with the tag / `DeleteContext.forceDataDelete`), `S3DirectoryBucketProvider.delete` (issue #1344 — same gate; no CDK `autoDeleteObjects` sugar exists for directory buckets, but `Tags` is handled since issue #609 so the tag is declarable on the L1; without it a plain destroy of a non-empty one fails with a manual-empty remediation), and `ECRProvider.delete` (`force: true` only with `EmptyOnDelete: true`, the tag, or `forceDataDelete`). Without an opt-in the AWS not-empty error surfaces like CloudFormation DELETE_FAILED. `DeleteContext.forceDataDelete` is set ONLY by the deploy engine's replacement/recreate delete sites under `--force-stateful-recreation`. See docs/cli-destroy.md "Destroy data guards" and the DeleteContext note in .claude/rules/providers.md.
- **src/provisioning/region-check.ts** - `DeleteContext` + the shared `assertRegionMatch()` helper: one implementation, THREE outcomes (recorded region unset OR empty -> no-op; match -> silent; mismatch or unresolvable client region -> `ProvisioningError`), plus (issue [#2301](https://github.com/go-to-k/cdkd/issues/2301)) a `RegionCheckPhase` that changes only the MESSAGE: `'not-found'` (default — every pre-#2301 call site untouched) words the reactive use where a `*NotFound` is about to be trusted; `'pre-delete'` / `'pre-update'` word a call not yet issued. The pre-flight phases exist because a wrong-region call usually never REACHES the `NotFound` arm — most physical ids are NAMES and the same name commonly exists in the client's region, so the call succeeds against the wrong resource. `CloudControlProvider` therefore runs the check UNCONDITIONALLY for every CC-routed type at the top of both `delete()` and `update()` (ahead of the `--remove-protection` flips, SDK delegations and the `AWS::S3::Bucket` identity probe), and marks the refusal non-retryable. How SDK providers call it: [provider-delete-path.md](provider-delete-path.md).
- **src/provisioning/config-shape.ts** - Shape guards for reading values out of nested CFn config blocks (issue #1471), which measured 16 sites across 5 providers silently substituting a default — frequently the OPPOSITE of the declared intent — whenever the container was a string / array / unresolved intrinsic (`VersioningConfiguration: 'Enabled'` turned versioning OFF on a live bucket).
  - `readConfigString(container, key, fallback, containerPath)` refuses a container that is present but not a plain object, and a key that is present but not a non-blank string, while still defaulting for an ABSENT container or key; `requireConfigString(value, fallback, path)` is the value-level half for a field already read off `properties`. Replaces the `(config['X'] as string) || 'default'` idiom AND its `??` spelling (issue #1493 — 9 nested-container sites plus the two `AWS::Lambda::Url` `AuthType` sites the `as string`-specific grep missed, where the default is a PUBLIC function URL; top-level `properties['X'] ?? 'default'` reads followed in issue #1513, PER SITE).
  - `ConfigStringOptions` carries the two relaxations that split "required": `coerceNumber` (an unquoted YAML `IpProtocol: -1` / `Qualifier: 1` is a NUMBER today and deploys fine, so those sites stringify while enum-valued ones still refuse) and `onUnusable` (WARN + default, UPDATE-path sites only — a rollback replays `update()` with a historical STATE record as the desired bag, so a refusal there leaves the resource un-rollbackable with no template-side remedy). Guarded: API Gateway `AuthorizationType` (default = NO authorization, so an unusable value must never silently default), EC2 `InstanceType` / `Domain` / SecurityGroupIngress-create `IpProtocol`, IAM access-key `Status`, Lambda event-invoke `Qualifier`, RDS DB-proxy `TargetGroupName`, DynamoDB GlobalTable `BillingMode` (deferred while a parallel lane owned the file; enum-valued so no `coerceNumber`, refusal wrapped in a `ProvisioningError` because the read sits outside `create()`'s try). Left unguarded with the reason in-code: `EC2Provider.buildIpPermission`'s `IpProtocol` (also reached from state-borne delete / revoke paths — the create call site is guarded instead), every `delete()` / `readCurrentState` read, and the GlobalTable `previousProperties` `BillingMode` sibling.
  - Two #1493 lessons recorded in the header: the class-covering grep is `as [A-Za-z<>,| ]+\) \?\? '` (the obvious `\] \?\? '` finds NOTHING; the cast-word form is blind to `as string | undefined`), and a guard behind a TRUTHINESS gate is skipped by a FALSY malformed container — the gate must be `!= null`.
  - Two test-enforced constraints: callers pass the **DESIRED side only** (the previous side comes from cdkd state; refusing a malformed recorded value would make the stack permanently undeployable — `KinesisProvider`'s `previousProperties` read is deliberately unguarded), and TOP-LEVEL sites use `requireConfigString(properties['X'], ...)` rather than handing the whole bag over, so the element-read stays visible to the `handled-property-wiring` critic. This is a provider-layer guard, not a pre-flight template check, because the field rules are only decidable AFTER intrinsic resolution (a legitimate `Fn::If` block is an object whose inner key does not exist yet).
  - Two CONTAINER-only guards: `requireConfigArray(value, path, options?)` for a LIST block (#1493 review; `onUnusable` added by #1579) and `requireConfigObject(value, path, options?)` for an OBJECT block (issue #1581). Both take only `onUnusable` (`coerceNumber` is meaningless for a container), both are overloaded so a throw-only caller keeps a non-`undefined` return type, and both leave the ABSENT case to the caller's own `!= null` test (`{}` / `[]` are legitimate values). `requireConfigObject` exists for the silent-DROP shape the string guards miss: presence-probing members of a malformed value indexes to `undefined`, so the block reads as EMPTY and the caller proceeds without it. Guarded: S3 `LifecycleConfiguration.Rules[].Filter`, `AnalyticsConfigurations[].StorageClassAnalysis` + `.DataExport`, and `ReplicationConfiguration.Rules[].Filter` — the widest, found by the #1581 review: its fall-through emits `Filter: {}` (valid CFn for "replicate EVERY object"), so a malformed container replicated the whole bucket; it also sat behind a truthiness gate (the #1493 shape) and is `!= null` now.
  - Audited and deliberately unguarded, reason in-code: the per-ITEM `config` containers of the six S3 appliers carrying the `onUnusable` replay callback — four already refuse a non-object item via an existing `readConfigString` (lifecycle rules, replication rules, intelligent tiering, inventory), and metrics / analytics fail LOUDLY at S3 on the missing required `Id`, not the silent hazard. (The count read "five appliers, three refuse" until issue #1595's own comments corrected it — the fourth refusal sits in `applyReplicationConfiguration`, the function #1581 had just guarded.)
  - Issue #1595: those per-item refusals hard-threw on state-replay paths, and the warn-and-DEFAULT downgrade is the WRONG answer there — every default at those sites (`Status` -> `Enabled`, `IncludedObjectVersions` -> `All`) would START an expiration / archive-tiering / replication rule the template had disabled. So `configStringRefusal(container, key, fallback, containerPath, options?)` exports the predicate WITHOUT the action: it returns the refusal sentence (or `undefined`) and the caller performs the SKIP, at the per-applier unit — the WHOLE Put for lifecycle / replication (their Put replaces every rule), the single ITEM for intelligent tiering / inventory (per-Id Put). `requireConfigString` is implemented on the same internal predicate so probe and read cannot diverge (pinned by a test enumerating both over every value shape); the create path never probes, so its refusal is byte-identical. Guarded this way: lifecycle + replication per-rule `Status`, intelligent-tiering per-item `Status`, inventory per-item `IncludedObjectVersions`.
  - Issue #1605 settled the FIELD-level reads on the same replay-reachable paths, each with a DIFFERENT skip unit because the unit was the whole question: versioning `Status` SKIPS the Put (no item to skip, no previous value to keep; the `Suspended` fallback is the direction #1471 measured turning versioning OFF live — the skip's real cost, an un-reverted rollback, is cheaper and is announced); the logging destination + `LogFilePrefix` pair SKIPS the Put TOGETHER (`PutBucketLogging` replaces the whole status; a blank destination fallback turns access logging OFF), with the gate in `applyAllSubConfigsForCreate` taking the same downgrade; the inventory `ScheduleFrequency` / `Schedule.Frequency` pair FALLS THROUGH from a malformed first source to the second (also template-declared), skipping the ITEM only when both are unusable — inventing a `Weekly` cadence is the substitution this guard family exists to refuse. #1605 also threaded `CreateContext` into `applyConfiguration` (its versioning read was reachable from the reverse-replacement create with no way to downgrade).
  - Issue #1751 added the BOOLEAN pair: `coerceCfnBoolean(value)` (moved from `s3-bucket-provider.ts`; CFn is stringly typed, so `'true'` / `'false'` are legitimate) and `configBooleanRefusal(container, key, containerPath)`, the boolean twin of `configStringRefusal` with the same CONTAINER-then-FIELD halves. It exists for the shape neither string guard sees: a member read as `x ?? <default>`, where `??` treats a DECLARED `null` as absent — the S3 inventory `Enabled`, whose default `true` ENABLED a report the template was disabling, with no warning. The FIELD half IS `coerceCfnBoolean` — the function the wire read calls — per this module's share-the-predicate rule.
- **src/provisioning/composite-id.ts** - Refusal guard for COMPOSITE physicalIds (issue [#1672](https://github.com/go-to-k/cdkd/issues/1672)). `ResourceProvider` passes a single `physicalId: string`, so multi-value types PACK segments joined by `COMPOSITE_ID_SEPARATOR` (`<databaseName>|<tableName>` for `AWS::Glue::Table`, ...). The separator is NOT escaped, so a segment containing one yields the wrong ARITY — `mydb|a|b` decodes to table `a` — passing every well-formedness guard: the deploy SUCCEEDS while `cdkd destroy` deletes the wrong table (or warn-skips over a live, billing one) and `cdkd drift` reads `undefined` forever. AWS accepts such names (live probe 2026-08-12: `glue:CreateTable` with `Name: 'a|b'` succeeds) and CloudFormation manages them, so the limitation is cdkd's own and the honest answer is to REFUSE at deploy time.
  - Two entry points mirroring `config-shape.ts`'s pair: `packCompositeId(resourceType, logicalId, segments, options?)` is the ACTION (throws `ProvisioningError`, or warns-and-packs under `options.onRefusal` — the `CreateContext.replayingState` downgrade, since a state record cannot be edited from the template) and `compositeIdSeparatorRefusal(...)` the bare PREDICATE for `import()` paths whose answer is warn-and-SKIP (`return null`). One shared message builder; the predicate tests the STRINGIFIED value, not `typeof value === 'string'` — every call site feeds an unvalidated `as string` cast, so a YAML list `Name: ['a|b']` reaches the pack as an ARRAY and stringifies to exactly the ambiguous id.
  - Adopted at every CREATE-path packing site (glue / s3-tables / appsync / ec2 / apigateway / lambda-event-invoke-config), computed BEFORE the AWS call wherever segments allow; the two that cannot (AppSync ApiKey, EC2 EIP — segments come from the create RESPONSE) sit after it and OUTSIDE the wrapping `try`, so a refusal is never mis-labelled an AWS creation failure.
  - `route53-provider.ts`'s three RecordSet packers joined in issue [#1711](https://github.com/go-to-k/cdkd/issues/1711) (deferred only because a concurrent lane owned the file): `recordName` is `properties['Name']`, the only TEMPLATE-chosen segment in the family. `parseRecordSetCompositeId`'s exact-three-segment rule does NOT make the failure loud (review caught the false claim): a record name carrying two pipes (the CFn physicalId `--migrate-from-cloudformation` pre-populates) decoded to a DIFFERENT hosted zone at three sites above the packers — `importRecordSet`'s early accept, `resolveRecordSetIdentity`'s short-circuit, and `deleteRecordSet`'s own parse, where destroy targeted a non-existent zone and reported SUCCESS over a live record. All three now cross-check parsed segments against the template via `compositeAgreesWithTemplate` (TYPE and NAME, each skipped when its template side is unusable; the name compare goes through `canonicalizeQueryName` so case / trailing dot cannot false-reject). `create` refuses before `ChangeResourceRecordSets` (ordinary `replayingState` downgrade — `context` had to be threaded through `create()`); `update` downgrades UNCONDITIONALLY (no context; cannot tell a template-borne update from the state-borne bag `drift --revert` / rollback hand it); `import()` takes its own `adoptVerbatim` escape hatch rather than freezing a mis-arity id into state.
  - Deliberately NOT covered (reason in the module header): `intrinsic-function-resolver.ts`'s joins, which build `Ref` VALUES nothing decodes. Directions 1 (stop packing where decode sites already receive the properties bag) and 2 (escape the separator) remain open on #1672.
  - Third entry point, decode-side (issue [#1657](https://github.com/go-to-k/cdkd/issues/1657)): `compositeIdFormatMessage(format, logicalId, physicalId, options?)`. Half the decode sites stated the expected shape and half only echoed the value; since the format is documented nowhere else (docs gap = issue #1656) the message was the user's only route to it. All 17 decode sites now render through one builder from a per-type `CompositeIdFormat` (`label` + ordered `segments` + optional `alsoAccepts` for `AWS::S3Tables::Table`'s bare-ARN alternative) — already-correct sites included, so they cannot drift back. **Every segment is a PLACEHOLDER whose name must match the type's `packCompositeId` segment names**: the first cut gave `AWS::EC2::VPCGatewayAttachment` a literal `IGW|<vpcId>` form for a token no code path produces (the packer emits the real `internetGatewayId`); review caught it and the literal form was DELETED, not corrected. Wording change only — each caller keeps its own split-and-guard, because arities genuinely differ (some sites accept AT LEAST N segments, some destructure N and tolerate extras — the #1672 ambiguity) and one shared predicate would silently change which ids deploy. The `{ skipping: true }` variant serves the five warn-and-continue DELETE arms: policy unchanged, but the warning now says the AWS resource is LEFT IN PLACE while destroy reports success, so the orphan is diagnosable. Two of the issue's table rows were already stale when worked (`AWS::S3Tables::Table` had gained its text; route53's message was removed by PR #1678 in favour of `parseRecordSetCompositeId` + a template-derived fallback).
- **src/provisioning/nested-stack-messages.ts** - User-facing message builders for the `AWS::CloudFormation::Stack` delete path (issue [#1777](https://github.com/go-to-k/cdkd/issues/1777)). One export today: `nestedStackChildFailureMessage(childStackName, errorCount, alsoSkippedCount, alsoInterrupted)` — what `NestedStackProvider.delete` THROWS when the child destroy reported `errorCount > 0`. **The module must stay a LEAF — no imports, ever**: the provider imports `destroy-runner.ts` -> `register-providers.ts` -> every provider including itself, and importing the builder from there closed that cycle (pulling the whole registry into unrelated unit tests) — harmless only while nothing on the ring does module-scope work. A builder rather than an inline literal because the exact string is needed by tests on BOTH callers of `delete()`: the runner and the deploy engine classify a delete failure by MESSAGE, reading already-deleted-shaped phrases (`not found` / `does not exist` / `No policy found` / `NoSuchEntity` / `NotFoundException`, plus the engine's `was not found` / `ResourceNotFoundException`) as idempotent success and DROPPING the state row — the exact outcome the throw exists to prevent — so a hand-copied literal would keep a test passing while the shipped wording drifted into that shape.
- **src/provisioning/final-snapshot.ts** - `DeletionPolicy` / `UpdateReplacePolicy: Snapshot` support (issues #1352 / #1353 / #1354): `ATOMIC_FINAL_SNAPSHOT_TYPES` (RDS DBInstance / DBCluster, Neptune / DocDB clusters, ElastiCache CacheCluster — delete sites generate `buildFinalSnapshotIdentifier(physicalId, resourceType)`, thread it via `DeleteContext.finalSnapshotIdentifier`, and each provider flips `SkipFinalSnapshot: true` to the API's atomic form; SDK route ONLY — a cc-api-routed atomic type is refused and `CloudControlProvider.delete` fail-closes on the field), `PRE_DELETE_SNAPSHOT_TYPES` + `createPreDeleteFinalSnapshot` dispatcher (all CC-routed: `AWS::EC2::Volume` via `CreateSnapshot` tagged `cdkd:final-snapshot-of`; `AWS::Redshift::Cluster` via `CreateClusterSnapshot`; `AWS::ElastiCache::ReplicationGroup` via ElastiCache `CreateSnapshot` — each waited to ready, idempotent reuse via the tag / `finalSnapshotNamePrefix` across delete re-runs), `unsupportedFinalSnapshotError` / `ccRoutedFinalSnapshotError`, and (issue #1366) `finalSnapshotMechanism(type, route)` / `refusesFinalSnapshot(type, route)` — the mechanism matrix as a PURE function so the executor and the `cdkd rollback` plan preview read one source (#1368 extends that to the preview's STATE effect: a refused Snapshot delete no longer unwinds the record). The two type sets are DISJOINT by construction — `finalSnapshotMechanism` tests the atomic set first, so a type in both would silently never reach the pre-delete snapshot; pinned in `final-snapshot.test.ts` with the union-equals-the-CFn-documented-list fence (re-homed from the deleted `supportsFinalSnapshot`, #1368). Consumers: the deploy engine (`prepareFinalSnapshotForDelete` — shared gate for the DELETE branch AND the four replacement / recreate delete sites), `destroy-runner.ts`, and `rollback-executor.ts` twice: `rollbackFinalSnapshotId` for delete-of-the-NEW-resource under `UpdateReplacePolicy` (honors only the atomic SDK-routed shape, plain-deletes otherwise — scope decision on #1354) and `prepareCreateRollbackFinalSnapshot` for a rolled-back CREATE under `DeletionPolicy` (the FULL matrix, refusing what it cannot snapshot — issue #1358). Engine clients come from `DeployEngineOptions.finalSnapshotClients` (stack-region-pinned, structurally `PreDeleteSnapshotClients`), threaded to `RollbackExecutorContext.finalSnapshotClients`; `--skip-final-snapshot` (deploy / destroy / state destroy / rollback, `skipFinalSnapshotOption` in `src/cli/options.ts` — deliberately NOT in the shared `destroyOptions` array `cdkd orphan` consumes) is the explicit data-loss opt-out.
- **src/provisioning/emr-configuration.ts** - Shared CFn -> SDK shape converters for `AWS::EMR::*` nested config blobs whose CFn spelling diverges from `@aws-sdk/client-emr` (issue #1383): `toSdkConfigurations` (`Configuration.ConfigurationProperties` -> `Properties` at EVERY nesting level), `toSdkStepConfigs` (`HadoopJarStepConfig.StepProperties` -> `Properties`), `toSdkInstanceTypeConfigs` (per-instance-type nested `Configurations`). Pure key renames — value shapes already match (verified against the live CFn registry schema) — but the SDK v3 serializer drops unknown members, so before this every EMR application configuration silently vanished while cdkd reported success. Consumed by `EMRClusterProvider`, `EMRInstanceGroupConfigProvider` (create), `EMRInstanceFleetConfigProvider` (create + `ModifyInstanceFleet`). No inverse needed: all three blobs are in `EMRClusterProvider.getDriftUnknownPaths` and neither instance provider implements `readCurrentState`. Non-object / non-array inputs (an unresolved intrinsic) pass through untouched so AWS surfaces the real validation error. `AWS::EMR::*` is NOT yet in `NESTED_KEY_TARGETS` (`scripts/gen-nested-key-coverage.ts`) — expansion tracked in issue #1393.
- **src/provisioning/dynamodb-warm-throughput.ts** - The two `WarmThroughput` rules shared by `AWS::DynamoDB::Table` and `GlobalTable` (issue [#1857](https://github.com/go-to-k/cdkd/issues/1857)): `coerceWarmThroughput` (per-member coercion of the stringly-typed CFn value into the SDK's Long field — a quoted `'12000'` / `Fn::Sub` result otherwise reaches the wire as a string and AWS rejects it; drops an unusable member while sending the usable one and REPORTS the dropped names for the caller's warning) and `isWarmThroughputDecrease` (AWS rejects an `UpdateTable` that LOWERS warm throughput, so a template value AWS has grown past issues a call that can only fail and `cdkd drift --revert` re-issues forever — declared members only, failing OPEN on a MIXED or unreadable-live block so a false positive cannot swallow a real increase). The coercion's `spec` presence IS the sendability predicate, so the write-side send and any drift-side gate cannot answer differently. Provenance, stated precisely because the first cut over-claimed it: only the Table spelling ever SHIPPED (PR #1808, issues #1760 / #1768) — this is the Table rule LIFTED, not two shipped rules reconciled; the shipped rule vs the GlobalTable DRAFT agreed everywhere except a whitespace-only string (`Number('   ')` is `0`), where the shared rule takes the REFUSING answer. `dynamodb-table-provider.ts` keeps its own `coerceWarmThroughput` name as a thin adapter (behavior unchanged); drift-side gates with no GlobalTable counterpart (`isSendableWarmThroughput` / `isRefusedWarmThroughput` / `declaresWarmThroughput` / `warmThroughputAlreadyMatches`) stay there, replica plumbing stays in the GlobalTable provider. Also exports `toFiniteNumber`, the reader for every OTHER numeric CFn member — the same rule was hand-written THREE times (here, the Table provider's byte-identical `capacityNumber`, the GlobalTable copy) and the #1857 review collapsed them: refusing a whitespace `WarmThroughput` while reading a whitespace `MaxReadRequestUnits` as ZERO is exactly the divergence the module prevents. `WARM_THROUGHPUT_MEMBERS` shared for the same reason. Pinned by `tests/unit/provisioning/dynamodb-warm-throughput.test.ts` (named for the module so a third consumer finds it); each provider's suites exercise it through their own send sites.
- **src/provisioning/dynamodb-index-busy-delete.ts** - The index-busy `DeleteTable` rule BOTH DynamoDB providers read (issues [#1830](https://github.com/go-to-k/cdkd/issues/1830) / [#1931](https://github.com/go-to-k/cdkd/issues/1931)). AWS refuses `DeleteTable` while any GSI is mid-transition, and the condition is TRANSIENT (auto-scaling can start an index change any moment), so surfacing it as a hard `PartialFailureError` made users re-run destroys for something that clears itself.
  - Owns `INDEX_BUSY_DELETE_MESSAGE` / `isIndexBusyDeleteError` — keyed on the MESSAGE, because AWS reports this as a plain `ResourceInUseException`, the same NAME as terminal conflicts ("Table is being created"); a name-keyed predicate would spend the whole budget (a settle poll + backoff per attempt, minutes) before failing identically. `INDEX_TRANSITIONAL_STATUSES` / `hasTransitionalIndex` — the re-arm CONDITION, tested on TRANSITIONAL values rather than `!== 'ACTIVE'`, so an unrecognized status cannot park a delete for its whole cap on a healthy table.
  - Budgets: `TABLE_DELETE_INDEX_BUSY_MAX_RETRIES` (14) and `GLOBAL_TABLE_DELETE_INDEX_BUSY_MAX_RETRIES` (8) — PER CALLING TYPE, passed in at the call site; `DELETE_INDEX_BUSY_REARM_MAX_ATTEMPTS` (60); `INDEX_SETTLE_POLL_INTERVAL_MS` (1s, the unit every poll count on this path is denominated in, incl. the 900-poll #1521 gate and `waitForTableActiveAfterUpdate`).
  - `waitForIndexesSettled` — bounded best-effort poll: on timeout it warns and RETURNS (a throw on the delete path would STRAND the resource); a throttled describe keeps waiting rather than reading as settled; the unclassified-error arm logs only the error CLASS at default verbosity (AWS's raw text carries the account id and assumed-role ARN into the terminal and the persisted events store). `indexBusyRetryWarning` — ONE line at default verbosity (`withRetry` announces retries only at debug); its remaining-attempt count AND remaining-wall-clock floor are DERIVED from the budgets, and it deliberately does NOT quote AWS's own sentence (the integ greps for that to prove AWS really refused). `deleteTableWithIndexBusyRetry` is the loop.
  - **The re-arm bound is the load-bearing arithmetic**: the poll runs PER RETRY, so wall clock is the product — at the #1521 gate's 15-min default it would be hours; at 60 polls (~1.2s each) it is ~18.4 min at the Table budget, ~10.4 min at GlobalTable's. `destroy-runner.ts` wraps its whole OUTER retry loop (up to 4 `delete()` calls) in a 30-min per-resource deadline; the budgets survive only because this refusal matches no `RETRYABLE_ERROR_MESSAGE_PATTERNS` entry — adding the message there would silently take the Table worst case to ~74 min.
  - Why the budgets differ, and why they are per CALLER: both shipped at 8 until issue [#1950](https://github.com/go-to-k/cdkd/issues/1950), where a live run measured a 5-item table's GSI create consuming 7 of 8 — the budget cleared only the FLOOR of AWS's roughly fixed index-create latency. What remains of the deadline when each type reaches the loop differs: Table has spent at most a <=60-poll ACTIVE wait (~72s); GlobalTable may have spent the #1521 gate's 900 polls (~18 min) plus `waitForReplicaGone`'s 600 polls (~12 min) per non-local replica. So Table took 14 (largest value keeping its delete path inside two thirds of the deadline) and GlobalTable kept 8 (gate + loop(8) ~28.4 min FITS; gate + loop(14) ~36.4 min does not — a raise would push the common single-region `TableV2` shape over a line it is currently inside). The replicated shape (~40 min) was already over and is unchanged — issue [#1955](https://github.com/go-to-k/cdkd/issues/1955).
  - Living here rather than in either provider is the point (same reason as `dynamodb-warm-throughput.ts`): two independent spellings of the classifier or budget are two chances for a fix to move one while the sibling keeps the old answer. Deliberately NOT here: GlobalTable's pre-delete #1521 gate and replica / auto-scaling teardown (the Table provider has neither); each provider keeps its OWN `deleteTableRetryDelays` sleep seam so one suite cannot silence the other's backoff. Pinned by `tests/unit/provisioning/dynamodb-index-busy-delete.test.ts`, which also pins that BOTH providers route through it, and whose budget fences MEASURE the real loop (attempts, re-arms, every ms `withRetry` sleeps) rather than restating its schedule — one per type, since the binding ceiling differs — for `Table`, a floor of 2x the measured 8-min index-create plus a delete-path worst case inside two thirds of `DEFAULT_RESOURCE_TIMEOUT_MS`; for `GlobalTable`, the #1521 gate's observed poll cap plus the loop staying under the deadline, with the `Table` budget asserted as a premise NOT to fit there (without that negative pin a later raise of the GlobalTable budget passes silently); both providers' re-arm wiring is fenced (the Table twin was missing — a 900-poll mutation there left the suite green).
- **src/provisioning/ec2-termination-protection.ts** - Shared `--remove-protection` helper for `AWS::EC2::Instance`: `disableInstanceApiTermination()` (flip `DisableApiTermination` off, idempotent, errors swallowed at debug), `isTerminationProtectionPropagationError()` (matches the "may not be terminated. Modify its disableApiTermination" 400 from both `TerminateInstances` and the Cloud Control `DeleteResource` wrapper), `TERMINATION_PROTECTION_MAX_ATTEMPTS`. Used by `EC2Provider.deleteInstance` (SDK path) and `CloudControlProvider.delete` (CC path — an instance routes through CC whenever its template trips the #614 silent-drop routing) so `--remove-protection` works on either delete path; the modify WRITE lags the delete READ, so both flip-off + retry the delete to close the propagation window. ALSO used by `ASGProvider.delete` (issue #796): an ASG whose launch template sets `DisableApiTermination: true` launches instances that survive `DeleteAutoScalingGroup(ForceDelete: true)` (ForceDelete governs only group-level protection + scale-in, not EC2-level termination protection), so under `--remove-protection` the provider enumerates the group's instances and flips each off before the force delete — the ASG's own async terminate loop absorbs the propagation lag, so no per-instance retry there. An ASG can ALSO route via CC when its template sets a silent-drop property such as `AvailabilityZoneIds` (#614) — CC's `DeleteResource` cannot `ForceDelete` a protected ASG — so `CloudControlProvider.delete` detects `removeProtection === true && resourceType === 'AWS::AutoScaling::AutoScalingGroup'` and delegates to `new ASGProvider().delete(...)` (the single source of truth), keeping the two routes behaviourally identical (issue #798; CDK's L2 emits `availabilityZones`, so this CC path only fires for hand-written L1 / imported templates).
- **src/provisioning/unsupported-types.ts** + **unsupported-types.generated.ts** - Pre-flight unsupported-type rejection. The `.generated.ts` ships the provider-coverage Tier 3 set (`ProvisioningType: NON_PROVISIONABLE`) into the runtime, codegen'd from `docs/_generated/provider-coverage.json` by `scripts/gen-unsupported-types.ts` (`vp run gen:unsupported-types`; CI fails on drift). The hand-written `.ts` adds `isNonProvisionable()` + `unsupportedTypeIssueUrl()`; both consulted by `CloudControlProvider.isSupportedResourceType` (rejects Tier 3) and `ProviderRegistry.validateResourceTypes` (per-type error + issue link). `--allow-unsupported-types` routes named types through Cloud Control via `ProviderRegistry.allowUnsupportedTypes()`.
- **src/provisioning/property-coverage.ts** + **property-coverage.generated.ts** - Pre-flight property-level rejection (parallel to unsupported-types at top-level CFn property granularity). The `.generated.ts` ships per-Tier-1-type `{ handled, silentDrop }` records, codegen'd from `tests/fixtures/cfn-schemas/*.json` + each provider's `handledProperties` / `unhandledByDesign` declarations by `scripts/gen-property-coverage.ts` (`vp run gen:property-coverage`; CI fails on drift; parses provider sources via the TS Compiler API — no `dist/` bootstrap). - **src/provisioning/mutually-exclusive-properties.ts** - Pre-flight rejection of property COMBINATIONS AWS accepts only one of (issue [#1634](https://github.com/go-to-k/cdkd/issues/1634)) — third member of the pre-flight family beside `unsupported-types.ts` (TYPES) and `property-coverage.ts` (PROPERTIES). Owns the hand-written `MUTUALLY_EXCLUSIVE_PROPERTIES` table, `findMutuallyExclusiveViolations()`, `buildMutuallyExclusiveMessage()`; applied by `ProviderRegistry.validateMutuallyExclusiveProperties`, run BEFORE the silent-drop routing chatter. Exists because a PROVIDER-side refusal is only reachable on a template-borne CREATE: once the resource exists the diff classifies `NO_CHANGE`, the provider is never called, and the invalid template deploys forever — what `EC2Provider.createRoute`'s #1566 refusal could not catch after #1591 normalized both diff sides. **The presence predicate is the load-bearing part**: pre-flight runs BEFORE intrinsic resolution, so a key behind an unresolved intrinsic counts as UNKNOWN, never declared (an `Fn::If` arm can resolve to `AWS::NoValue`, so a template carrying BOTH keys conditionally is VALID); otherwise the predicate is `Boolean(value)`, matching `narrowRouteDestinations`' truthiness so pre-flight cannot refuse a bag the provider would accept. Fail-SAFE by design (a let-through is still caught by the provider's create-path refusal; a false refusal blocks a valid deploy). Deliberately NO `--allow-*` escape hatch — the defect is in the TEMPLATE — so the table holds only the ONE verified combination (`AWS::EC2::Route`'s three destination keys, duplicated from the module-private `ROUTE_DESTINATION_KEYS` and fenced by a unit test pinning every rule property against the type's CFn schema fixture, so a rename fails a test instead of leaving a dead rule). `cdkd diff` is deliberately NOT wired: `DiffCalculator.compareProperties` already warns whenever `canonicalizeProperties` changes the desired bag (#1591), exactly this shape. Verified live 2026-08-12: a second destination on a deployed route -> `cdkd diff` warns + exit 0, `cdkd deploy` refuses at pre-flight.

- **src/provisioning/interrupt-watch.ts** - The ONE SIGINT watch every bounded wait under `src/provisioning/**` uses (issues [#2053](https://github.com/go-to-k/cdkd/issues/2053) / [#1952](https://github.com/go-to-k/cdkd/issues/1952) / [#2104](https://github.com/go-to-k/cdkd/issues/2104)), plus `InterruptedWaitError` and the `isInterruptedWaitError` cause-chain classifier `deploy-engine.ts` reads (a `visited` set and NO depth ceiling — the chain grows one `ProvisioningError` per nested-stack level, and a ceiling reinstates the rollback bug at depth). Four module-local copies preceded it; consolidation made two properties correctable, since one `delete()` traverses multiple modules:
  - ONE error type — the engine's own `InterruptedError` is module-private, so a bare `Error` from a provider read as a resource failure and triggered an automatic ROLLBACK on Ctrl-C (worse on create paths, where the interrupt landed in partial-create cleanup arms that issue a delete). ONE STICKY latch — clearing it on dispose looks equivalent and is not: sequential waits empty the live set between them, so a signal in the #1521 gate left the index-busy loop and the gone-wait after it deaf (issue #1952's own scenario surviving its own fix). Only a COMMAND clears the latch, via the scope `forwardSigtermToSigint()` opens in `src/utils/interrupt-signals.ts`; the process listener is never removed BETWEEN waits (one torn down in that gap cannot record a signal landing in it).
  - It arms only inside that command scope, NOT on `process.listenerCount('SIGINT') > 0` — `cdkd drift --revert` owns no shutdown path and runs `provider.update` at concurrency 4, and a concurrent CloudFront / ACM / Route53 wait installs a transient SIGINT listener, so a count-based gate armed the watch permanently through someone else's listener and left Ctrl-C unable to terminate the command.
  - The handler force-quits when it is the LAST SIGINT listener (motivating case: a multi-stack destroy where the watch was alone between stacks, and merely latching swallowed the Ctrl-C while the loop deleted the next stack). Issue [#2117](https://github.com/go-to-k/cdkd/issues/2117) closed that instance from the other side — `destroy.ts` / `state.ts` hold a command-scoped handler for the whole run (`watchCommandInterrupt`) whose loops read it live — so the force-quit now has NO live population: arming is gated on the command scope, which only `deploy` / `destroy` / `rollback` / `state destroy` open (commands registering no handler at all — `import` / `export` / `scrub` / `orphan` / `drift` / `state refresh-observed` — never arm the watch), and each of the four holds a graceful handler across its whole scope. The branch is KEPT as a structural guarantee: it becomes reachable the moment a command opens the scope without holding a handler across it.
  - That property imposes a rule on any lock-holding command — release BEFORE unregistering your SIGINT handler, because unregister-first leaves the lock held with no handler and a Ctrl-C there strands the lock for 30 min. `destroy-runner.ts`'s main `finally` had it backwards and now matches its strong-ref path; `rollback.ts`'s did too until issue [#2118](https://github.com/go-to-k/cdkd/issues/2118), which also nested the unregistrations in a `finally` so a synchronously throwing release cannot leak them (defence in depth — `releaseLock` is async, so nothing reaches that shape today). The ORDER within the teardown pair is consistency, not mechanism (the first cut claimed otherwise in four places): the calls are adjacent and synchronous, and `unforwardSigterm()` first would not empty the SIGINT set while the command's own handler is still registered. `deploy-engine.ts` is the only site still unregistering first, and says at the call site why that is safe (`deploy.ts` holds a top-level handler that outlives the method).
  - Second half of the rule, found by review: arming for longer MOVES the window a signal can arrive in, so everything READING the interrupt must be re-checked — `destroy-runner.ts` re-syncs `result.interrupted` at the end of its `finally`, or a Ctrl-C during the release left `destroy --all` free to delete the next stack. The re-sync is GATED on `statePreserved`: ungated it answered the command-level question in the per-stack channel, flipping the flag true over a stack whose `deleteState` had already run — the caller ORs it into the terminal verdict, which then exited 2 with "State preserved -- re-run 'cdkd destroy' to finish" over a fully completed destroy. The invariant: a stack whose state was deleted never reports `interrupted`.
  - Ownership after #2117's follow-up — each signal has ONE owner whose consumers all read it. PER-STACK ("did THIS stack finish?") is `result.interrupted`, owned by `destroy-runner.ts` (consumers: that stack's state preservation, its summary line, `destroy.ts`'s `--purge-events` skip). PER-RUN ("has the user asked this COMMAND to stop?") is the watch, read live by the loops' `break`s. The EXIT CODE asks a third, narrower question: a signal in the run's TAIL (after the last stack, during `eventRecorder.finalize` / the purge) sets the command-level flag over a completed destroy, so both commands carry `stoppedEarly` — set only where a `break` leaves a stack or region target unprocessed — and the terminal `PartialFailureError` reads `interrupted || (watch.interrupted() && stoppedEarly)`. In `state.ts` "unprocessed" is tested against `stateRefs` rather than counting indexes (under `--stack-region` a later name whose only record lives in another region is warn-and-skipped and was never a target); `destroy.ts`'s twin needs no such test because `candidateStacks` is pre-filtered to names that have state.
  - The command scope is a DEPTH COUNTER, so a nested command's close cannot disarm the watch its caller relies on. `interruptWatchTestSeam` / `disarmInterruptWatchForTests` exist because arming is a one-way door inside a command and a provider suite runs no command; the unit that owns the module drives the real scope functions instead.

- **src/provisioning/describe-type.ts** - Shared `cloudformation:DescribeType` invocation with THROTTLE-ONLY retry (issue #1236), consumed by `write-only-properties.ts`, `create-only-properties.ts`, and `export.ts`'s primary-identifier resolution (which passes its own injected CFn client via the optional second argument). DescribeType is throttled per-account and the #1182 create-only prefetch can burst through the limit at deploy start, so an on-critical-path lookup moments later was reliably throttled — and the resolvers' graceful fallbacks turned that transient throttle into a real failure (dropped `AWS::ECS::Service.VolumeConfigurations` -> UpdateService 400, or a registry-only replacement classification). `describeTypeWithThrottleRetry` wraps the call in `withRetry` with `isRetryable: isThrottlingError` (name/$metadata-based, NOT message-based), 4 retries (1s->2s->4s->8s, ~15s max sleep); non-throttle failures (missing IAM permission) rethrow immediately so the warn-and-fall-back path stays fast. `describeTypeRetryDelays.sleep` is the test seam. Also exports `hasNoRegistrySchema(resourceType)` — the ONE list of types with no CloudFormation registry entry (`Custom::*`, `AWS::CloudFormation::CustomResource`, the `AWS::CDK::Metadata` synth sentinel), for which DescribeType can only fail. Both resolvers short-circuit on it, and the deploy engine's create-only prefetch filters the template's type set through it, so the `AWS::CDK::Metadata` resource in EVERY synthesized template no longer burns a guaranteed-to-fail call plus a misleading "Grant cloudformation:DescribeType" warning per deploy.
- **src/provisioning/write-only-properties.ts** - Write-only property resolution for Cloud Control UPDATE patches (issue #809). `getTopLevelWriteOnlyProperties(resourceType)` resolves the registry-schema `writeOnlyProperties` via `cloudformation:DescribeType`, reduced to top-level names (nested `/properties/Foo/Bar` strips to `Foo`), short-circuiting to the empty set for `hasNoRegistrySchema` types, cached per type in a module-level promise map for the deploy lifetime — only SUCCESSFUL lookups cached: a DescribeType failure warns and falls back to an empty set for that update WITHOUT caching, so a transient throttle does not poison write-only re-inclusion for the rest of the deploy (a later update retries); a Schema-less response is a successful "no write-only props" lookup, warning-free. Consumed by `CloudControlProvider.update`, which strips these from the PREVIOUS side before patch generation so the patch always carries `add` ops for write-only properties in the desired state — CC applies patches read-modify-write and read handlers cannot return write-only properties, so one absent from the patch would be dropped on every UPDATE (`AWS::ECS::Service.VolumeConfigurations` hard-fails; other types lose config silently). Mirrors terraform-provider-awscc's prior-state clearing. DescribeType goes through the #1236 throttle-only retry before the fallback fires. `clearWriteOnlyPropertiesCache()` is test-only.
- **src/provisioning/slow-cc-operation-timeouts.ts** - Per-(resourceType, operation) wall-clock timeout floors (ms) for types whose async CREATE / UPDATE / DELETE routinely exceeds the generic deadlines (OpenSearch / Elasticsearch domains; Redshift / ElastiCache / RDS clusters — all 60 min). `slowCcOperationTimeoutMs(resourceType, operation)` returns the floor or `0`. The SINGLE source of truth for all three cap sites so inner and outer budgets can never drift: `CloudControlProvider.waitForOperation`'s poll cap (`Math.max(MAX_WAIT_TIME_MS, floor)`), the destroy-runner outer per-resource deadline, and the deploy-engine outer deadline (both `Math.max(providerMinTimeoutMs, floor, globalTimeoutMs)`). Fixes the `opensearch-domain-getatt` destroy timeout (a domain delete runs 15-30 min against a flat 15-min CC cap). A `--resource-timeout <TYPE>=<DURATION>` override still wins at the outer sites.
- **src/provisioning/resource-timeout-registry.ts** - Process-wide registry of the resolved `--resource-timeout` input (issue #1280) — the SDK-provider analogue of `slow-cc-operation-timeouts.ts`'s inner-undercuts-outer fix, sourced from CLI input instead of hardcoded floors. `setResolvedResourceTimeouts(opt)` is seeded by `deploy.ts` / `destroy.ts` / `state.ts` (state destroy) right after `validateResourceTimeouts` (wiring pinned by a source-level test); `resolvedResourceTimeoutMs(resourceType)` resolves per-type override > explicit global > `undefined` (the compile-time 30m default deliberately does NOT leak in — only an explicit user value may lift an inner waiter's floor). Consumers: `ECSProvider.settleService`'s `--full-wait` waiter (cap `max(600s, resolved)`) and `CloudFrontDistributionProvider.waitForDistributionStable`'s Deployed-wait budget (cap `max(20min, resolved)`, issue #1282 — reached by the `--full-wait` create/update settle AND the delete path's API-required disable-then-wait), so `--resource-timeout` actually reaches the inner waiters.
- **src/provisioning/create-only-properties.ts** - Create-only (immutable) property resolution for REPLACEMENT detection — read-side sibling of `write-only-properties.ts` (same `cloudformation:DescribeType` + per-type cache + graceful degradation). `getCreateOnlyPropertyPaths(resourceType)` resolves the registry-schema `createOnlyProperties` as FULL segment paths (schema-less types skip the lookup entirely per `hasNoRegistrySchema`; issue #1016), and the pure `createOnlyChangeRequiresReplacement` compares a changed top-level property at PATH granularity — a nested createOnly entry only forces replacement when the value AT that path changed (issue #960; unresolvable shapes and unresolved intrinsics stay conservative = replacement). Consumed by `DiffCalculator.compareProperties` as a fallback for any property the hand-authored `ReplacementRulesRegistry` does not classify (`isClassified` gates it so a deliberate `updateableProperties` decision is never overridden) — so an immutable-property change on ANY type is classified as replacement instead of in-place. The engine's property-driven replacement path then applies the same `--force-stateful-recreation` stateful guard as `--replace`, so a template immutable-property change can no longer silently DELETE+CREATE a stateful resource's data. DescribeType goes through the #1236 throttle-only retry before the fallback fires. **The fallback is only as good as the registry schema**: some types declare NO `createOnlyProperties` even though AWS rejects the update (`AWS::EC2::Volume` — live-verified 2026-08-03, issue #1356), so the change is misclassified as in-place; such a type needs a hand-authored `ReplacementRulesRegistry` entry, and when data-bearing, an entry in `STATEFUL_TYPES` in the same change. `clearCreateOnlyPropertiesCache()` is test-only.

## SDK Providers

SDK Providers are in `src/provisioning/providers/`. See [docs/supported-resources.md](../../docs/supported-resources.md) for the full list of supported resource types. Registration is centralized in `src/provisioning/register-providers.ts`.

SDK Providers are preferred over Cloud Control API for performance -- they make direct synchronous API calls with no polling overhead. Cloud Control API is used as a fallback for resource types without an SDK Provider.
