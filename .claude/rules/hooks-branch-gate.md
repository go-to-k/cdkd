# `branch-gate.sh`

Split out of [hooks.md](hooks.md) on 2026-09-03, for the reason
[hooks-main-tree-branch.md](hooks-main-tree-branch.md) was split out two days
earlier: that file is loaded WHOLE by every `.claude/hooks/**` touch and was back
at its per-file byte cap, while this entry is only wanted when the gate itself is
under the knife. So the `paths:` glob here is the gate and its suite and nothing
wider, and every other hook lane stops paying for this text.

- **`.claude/hooks/branch-gate.sh`** — blocks `git commit` and `git push` when the **target git working tree** is on `main` / `master`. Cwd-aware (reads `tool_input.cwd` from the hook payload + parses `cd <path>` / `git -C <path>` from the command), so worktree work that `cd /parent && git commit`s into a parent worktree on `main` is also caught. **A DETACHED HEAD in the MAIN checkout blocks too** (issue [#2402](https://github.com/go-to-k/cdkd/issues/2402)). `symbolic-ref --short HEAD` is EMPTY while detached, so the `case "$branch" in main|master)` matched neither arm and fell to `exit 0` — and the comment above it asserted the empty string meant "the dir doesn't exist or isn't inside a git repo", i.e. the one reading that is harmless. A detached HEAD in a perfectly valid repo produces the same empty string and is the opposite: the tree has LEFT `main`. The two composed into a hole neither gate had alone, because `main-tree-branch-gate.sh` passes `git checkout <sha>` in the main checkout. Measured on a scratch opted-in repo, same `git commit` payload: rc=2 on `main`, rc=0 once detached. The gate now reads `$target_top` (`rev-parse --show-toplevel`, already non-empty by the opt-in check above) as the discriminator, and blocks ONLY when that toplevel IS the main checkout — the first `worktree ` line of `git worktree list --porcelain`. A detached LINKED worktree keeps passing: that is the lane-clearing state `stop-unmerged-lane-warn.sh` prescribes (`git switch --detach origin/main`), so blocking it would refuse a documented instruction. The compare reads TOPLEVELS, not the raw resolved dir the sibling's `main_tree_of` compares, which fixes two things at once — a cwd one level down inside the main checkout, and a payload cwd still carrying a symlink git has resolved out of `--show-toplevel` (`/var` → `/private/var` on macOS). Smoke test at `.claude/hooks/branch-gate.test.sh` (66 cases, and it now runs the HOOK under the harness's bash rather than PATH's — a `HOOK_BASH` shim, proven with a bash-4-only parse error that scores 41/25 under 3.2 and 66/0 under 5.x). When blocked, the error names the resolved target dir and the parsed command — create a feature branch in that dir (`git -C <target-dir> switch -c <branch>`) and retry. **The remedy it prints follows the operation in progress** (go-to-k/cdkd#2402 review): a conflicted rebase is one of the ways the shared checkout reaches a detached HEAD, and `git switch main` is refused there with `fatal: cannot switch branch while rebasing`, so a correct block used to end in an impossible instruction. The gate now reads the TARGET's resolved git dir for `rebase-merge` / `rebase-apply` (with the `applying` sentinel separating `git am` from `git rebase --apply`) / `CHERRY_PICK_HEAD` / `REVERT_HEAD` / `MERGE_HEAD` / `BISECT_LOG` and prints `<op> --continue` / `<op> --abort`, or `bisect reset`, falling back to `switch main` only when nothing is running.

  **Where the remedy leaves HEAD is stated conditionally, because it IS conditional** (round 3). The previous round checked that all nine printed remedies EXIT 0 — they do — and then promised `--abort` would "abandon it and re-attach", false in four of the six. Exit status was the wrong observable. Measured on git 2.53 by running each remedy verbatim and reading HEAD: `am` / `cherry-pick` / `revert` / `merge --abort` all leave HEAD DETACHED, and so does `rebase --abort` when the rebase started while ALREADY detached; only a rebase started FROM a branch, plus `bisect reset`, re-attaches. Those four never detach HEAD themselves, so this arm is reachable for them only from an already-detached tree and `--abort` restores exactly that. The gate now reads git's own `head-name` (`refs/heads/<branch>`, or the literal `detached HEAD`) and prints "Either ending re-attaches HEAD to '<branch>'" or "NEITHER ending re-attaches HEAD" plus the `switch main` still needed. One sentence covers both endings because the outcome is a property of the SESSION, not of the ending — `--continue` splits the same way, measured. Eight rows now RUN the printed remedy and assert the resulting HEAD beside that claim.

  **The `applying` sentinel is load-bearing in the direction that fails SILENTLY.** `git am --abort` inside a `git rebase --apply` session exits 0 with no output and leaves HEAD DETACHED, where `git rebase --abort` from that state lands on `main`; the reverse crossing is loud (rc=128, `fatal: It looks like 'git am' is in progress. Cannot rebase.`). `fatal: no rebase in progress`, cited here before as that crossing's answer, is what git says when NOTHING is in progress. That `rebase --apply` branch had no row until round 3; mutating it to `am` left all three suites green.

  **Two stated bounds.** A path containing a NEWLINE fails open: awk's records ARE lines, so an embedded newline ends the record early whatever field expression reads it — measured, a detached MAIN checkout at `<tmp>/nl<LF>repo` scores rc=0, and rc=2 without the newline. `worktree list --porcelain -z` DOES read it and is deliberately not taken: `-z` is newer than `--porcelain` and an unsupported flag makes `worktree list` print NOTHING (failing OPEN, the same bug class), so the awk would have to stay behind it — and once `-z` ran first that awk would stop executing on every git that has `-z`, retiring the spaced-path fence over a shape this repo HAS produced for one over a shape nobody has. Second: a `rebase-apply/` holding neither `applying` nor `head-name` reads as a rebase, so the printed `rebase --abort` exits 1 with `warning: could not read '.git/rebase-apply/head-name'` — `git status` calls that same state "You are currently rebasing." and no git command produces it, so it is a bound rather than a bug.
