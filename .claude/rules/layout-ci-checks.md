# The CI checks that replaced PreToolUse gates

Split out of [layout-scripts.md](layout-scripts.md) by issue
[#2717](https://github.com/go-to-k/cdkd/issues/2717) — the same move
`hooks.md` made for its satellites, and for the same reason: the union of these
entries with issue #2718's took that file past its 80,000 B per-file cap, and a
rule file is loaded WHOLE whenever its glob matches. The glob above is narrow,
so this detail costs tokens only on a session actually touching these files.

**Why they are not in `layout-scripts.md` on the merits either.** Every
generator and critic documented there analyses `src/` statically and reports
through a `vp run audit:*` task and a `docs/_generated` artifact. These take a
GitHub artifact — a PR title, a changed-file list, an issue body — as input,
and report by failing a workflow job. Different subject, different failure
mode, different fences.

**The stopping rule that put them here** lives in
[hooks.md](hooks.md): a PreToolUse gate may BLOCK only when the harm completes
at the moment of the action and lands on a THIRD PARTY's artifact, where the
actor cannot undo it; everything else goes
to CI, or nowhere. Read that before adding a check to either side.

- **scripts/check-pr-title-prefix-scope.ts** - PR-title conventional-prefix scope check, run from `.github/workflows/pr-title-check.yml` on `pull_request` `opened` / `edited` / `synchronize` / `reopened`. The CI port of two PreToolUse gates retired by issue [#2717](https://github.com/go-to-k/cdkd/issues/2717) — `pr-title-prefix-scope-gate.sh` and `commit-prefix-scope-gate.sh`. Unlike its siblings above this is NOT static analysis of `src/`: its subject is a GitHub artifact, so it takes the title and the changed-file list as inputs and is exercised by `tests/unit/scripts/pr-title-prefix-scope.test.ts` (109 cases) rather than by a `vp run audit:*` task.
  - **What it enforces.** A `feat:` / `fix:` PR title feeds a release-please version bump, so it must be backed by at least one changed file under `src/**`. `revert:` and every non-release type pass. The grammar is `^([a-z]+)(\([^)]+\))?!?: ` — lowercase-only type and a REQUIRED space after the colon, so `Fix:`, `feat2:` and `fix:x` are not release prefixes and pass.
  - **Why ONE title check replaces two hooks.** The repo squash-merges, so the PR title becomes the squash subject release-please parses, and branch commit subjects never reach `main` as their own objects. That is a claim about GitHub SETTINGS, not about the code — measured 2026-09-07: `allow_merge_commit: false`, `allow_rebase_merge: false`, `squash_merge_commit_title: PR_TITLE`, `squash_merge_commit_message: BLANK`. All four matter. Under GitHub's other title option, `COMMIT_OR_PR_TITLE`, a SINGLE-commit PR squashes under that commit's subject and the per-commit check would still be doing real work; a message setting of `COMMIT_MESSAGES` would put branch commit bodies in front of release-please's footer parser.
  - **The audit CANNOT run in CI at all, and that is a permission boundary rather than a choice.** GitHub returns the repository's merge settings only to a token with ADMIN on the repo — and it is ALL of them, not just the two admin-gated `squash_merge_commit_*` fields. Measured 2026-09-07: `gh api repos/aws/aws-cdk` (no admin) returns null for `allow_merge_commit`, `allow_rebase_merge`, `allow_squash_merge` and both squash fields, while `gh api repos/go-to-k/cdkd` (admin) returns the real values. An earlier revision of THIS BULLET said the opposite — that the merge-method booleans "ARE readable by any token, so they still FAIL the job" — and told the next session not to "simplify that into an early return". Both halves were wrong, and acting on them would have restored a check that could never fire. Readability is now ALL-OR-NOTHING over the four fields the audit actually reads — both `squash_merge_commit_*` and both merge-method booleans: if any of THOSE is missing the step emits `::warning:: NOT VERIFIED`, exits 0, and says explicitly that nothing was checked, never a success line. (`allow_squash_merge` is fetched and deliberately unread, and NOT because the case is someone else's — an earlier revision said it was go-to-k/cdkd#2736's, which covers neither merge settings nor this check. It needs no assertion of its own: GitHub refuses to disable every merge method, so squash being off forces `allow_merge_commit` or `allow_rebase_merge` ON, and the clause below already raises a violation on exactly that.) **The real audit runs in `/verify-pr`**, where a maintainer's token can see the fields; the CI step is a reminder that the premise exists, not enforcement of it.
  - **So the premise is ASSERTED, not assumed.** Those are web-UI toggles living outside the repo — flipping one silently restores exactly the exposure the deleted gate covered, with nothing in any diff to notice, which is the "deleted a check on an argument and never re-checked the argument" failure. `--check-settings <repo-settings.json>` re-reads them on every PR as a second workflow step and fails naming which precondition broke and how to restore the per-commit check. A `gh` TRANSPORT failure warns instead of failing: an unreachable API is not evidence a setting changed. The CHECK itself never fails open that way.
  - **What CI buys over the hook, beyond relocation.** The hook fired once, at `gh pr create`. This re-runs on `synchronize`, so a title that was correct when the PR opened and stops being correct when a later push drops the last `src/**` file is now caught; and on `edited`, so a web-UI retitle — which never touches `gh` and was invisible to the hook in principle — is caught too.
  - **What was dropped**: 100% of the shell parsing. No `lib/command-match.sh`, no `cd` / `-C` target resolution, and none of the title-extraction shapes the hook needed (`--title=`, `-f`/`-F`/`--field`/`--raw-field title=`, `-m`, `--message=`, `-F <file>`, `-F -` heredoc, `--amend` and editor-mode pass-throughs). A workflow is handed the title.
  - **Fail-open surfaces, each closed deliberately.** The changed-file list comes from `gh api repos/{o}/{r}/pulls/{n}/files --paginate` rather than a local `git diff`: `actions/checkout` fetches depth 1, so a local 3-dot diff would be silently wrong, and a wrong file list fails OPEN (an empty diff passes). `--paginate` because the endpoint pages at 100 and a truncated list is the same fail-open. The step runs under `set -euo pipefail` so a `gh` failure reds the step instead of feeding an empty list to the check.
  - **Local use**: `--git-diff` takes the file list from `git diff --name-only origin/main...HEAD` for a pre-push or `/verify-pr` run. **Read its output, not just its exit code** — on a branch with no commits yet the diff is EMPTY and every title passes through the `no-diff` arm at rc=0, which is a correct pass and a vacuous probe. Probe with `--files-from <path>` against a real list instead.
- **scripts/check-gh-body-english.ts**, **scripts/check-issue-classification-labels.ts**, **scripts/check-issue-dup-check.ts**, **scripts/gh-subject.ts** - ISSUE / COMMENT / PR-BODY checks, run from `.github/workflows/issue-conventions.yml` on `issues` / `issue_comment` / `pull_request`. CI ports of `gh-body-english-gate.sh`, `issue-classification-label-gate.sh` and `issue-dup-check-gate.sh` (issue #2717); `gh-subject.ts` is the shared subject type and carries the full inventory of dropped shell parsing. Unit-tested by the three same-named suites under `tests/unit/scripts/` (62 / 33 / 36 cases, measured 2026-09-07 -- the first and third had drifted from 35 and 28).
  - **`pull_request`, NOT `pull_request_target`, and that is a security decision.** These checks only have to say no, so a failing check run is the whole output and no write token is needed; `pull_request_target` would hand a fork PR's author-controlled body a workflow with write permissions and base-repo secrets, for zero extra capability. The usual `pull_request` residual — a fork shipping a modified copy of the checker it is judged by — is closed by checking out `base.sha` while fetching the body from the API.
  - **`issue-classification-labels` REPAIRS where the hook could only refuse**: it reads `Severity:` / `Effort:` off the body and APPLIES the matching `severity:*` / `effort:*` label. It reports instead of applying when the body and an EXISTING family label contradict — silently overwriting a deliberate human label is the one case where applying is wrong. `Session-fit` and `Estimate` stay out, now as assertions rather than prose.
  - **A fifth loss, and it is about TIMING rather than surface.** A PreToolUse gate refused BEFORE the artifact existed; a workflow speaks after it is public. For an issue or comment there is no merge to withhold, so the check reports on text every reader can already see — `check-gh-body-english.ts` and `check-issue-classification-labels.ts` both state this in their headers, and until the go-to-k/cdkd#2717 spec review they cited `layout-scripts.md` for it, where it was never written. It is written HERE. The related hazard: a maintainer who deliberately REMOVES a `severity:*` label sees it re-applied on the next `edited` event, because a removal is indistinguishable from one never applied — which is why `unlabeled` is deliberately NOT a trigger, and why the check reports instead of applying when body and label CONTRADICT.
  - **`issue-dup-check` is strictly WEAKER than the gate it replaces, recorded rather than hidden**: the hook stopped the issue existing; CI can only comment once it does, so the comment asks for fold-and-CLOSE. Accepted because a duplicate issue closes cleanly and leaves no residue on anyone else's artifact — the #2717 criterion. The threat model is unchanged and is what carries the rule: FORGETTING the search, not defeating a gate.
  - **Three things got STRONGER in the move**: the web UI and any non-`gh` client are covered (the hooks saw only `gh` invocations); the `-b` / `-t` / `-n` short-flag blind spot is gone (the hooks refused to scan them because attributing a short flag is shell parsing); and the `Dup-check:` anchor now applies universally, with the loose spelling kept as a DIAGNOSIS that separates "missing" from "written mid-sentence".
  - **Coverage LOSSES, named because they are not recoverable here.** (1) The hooks fired on `gh -R go-to-k/cdk-local issue create` from a cdkd worktree, so they policed cross-repo filing; a workflow only sees its own repository's events, so each sibling repo needs its own copy. (2) **The retired `GATE_RE_GH_PROSE_CARRIER` armed on a bare `gh api`**, so every body-carrying POST was scanned whatever endpoint it hit. These workflows subscribe to `issues`, `issue_comment` and `pull_request` only, which leaves PR *review* comments (`gh api .../pulls/N/comments`, `gh pr review --body`), commit comments, discussions and gists uncovered — a strictly wider gap than the endpoint list suggests, and the reason to think in terms of the EVENT SET rather than the verb set. (3) `gh release create --notes` **and `gh release edit --notes`** (an earlier revision of this list named only `create`).
  - **`issue-dup-check`'s disposition needs a predicate the headline rule does not state, and here it is.** The rule asks whether the ACTOR can undo the harm, and by that test alone a duplicate issue should BLOCK: you cannot un-mint an issue number or un-send its notifications. What makes it CI-appropriate is the rule's SECOND clause — **whether the residue lands on someone else's artifact.** (That clause used to be compressed out of the headline in both this file and CLAUDE.md, which is what made this bullet necessary; both now state it, so read this as the worked example rather than as the missing half.) A duplicate issue is the filer's own, closes cleanly, and leaves the backlog exactly as it was; a bare `#N` writes a permanent `referenced` event on a THIRD PARTY's issue, which is why `pr-body-item-number-gate` stays a blocking hook and this one did not. State both clauses when applying the rule to a new gate; the spec review of go-to-k/cdkd#2717 caught this one being used without being written down.
  - **The Bot-sender filter lives in BOTH halves, and the script is the authority.** Two of these jobs POST comments and a comment is itself an `issue_comment: created` event, so without the filter the check scans its own output — and fails on it the moment a report QUOTES an offending body back at the author, who then cannot clear it. It was only `github.event.sender.type != 'Bot'` in the job's `if:` until issue [#2736](https://github.com/go-to-k/cdkd/issues/2736): no test can read a workflow `if:`, so deleting it was silent. `isBotSender` in `check-gh-body-english.ts` now decides, the `if:` stays as a runner-saving filter, and `workflow-registration.test.ts` pins that the two agree — the same split #2717 made for `isMintEvent`. `english-issue` passes `SENDER_TYPE`; `english-pr` deliberately does NOT (it posts no comment, so there is no loop, and skipping a bot-opened PR would drop real coverage) and that negative is asserted too. An ABSENT `SENDER_TYPE` means SCAN: defaulting to skip would disable the check for any caller that forgot the variable.
  - **A sibling script is imported with a `.ts` extension, not `.js`.** Node's type stripping resolves specifiers literally, so a `.js` specifier for `scripts/gh-subject.ts` fails under `node scripts/check-issue-dup-check.ts`. That matches the existing `scripts/**` convention — `scripts/github-links.ts` and `scripts/markdown-table.ts` are already imported that way — while CLAUDE.md's `.js`-extension rule governs bundled `src/**`, which these are not.
- **The PR-CONTENT checks** — `scripts/check-pr-non-english-text.ts` (+ `scripts/non-english-allowlist.txt`), `check-pr-internal-labels.ts` and `check-pr-closes-paren.ts`, all three run from `.github/workflows/pr-content-checks.yml`. Two read the PR DIFF, one reads the PR BODY; the third is the only check in this family that WARNS instead of failing. Full entries — what each preserves from the gate it replaces, the fail-open surfaces, the allow-list discipline and the known detector bounds — in [layout-ci-pr-content.md](layout-ci-pr-content.md), whose `paths:` glob is narrow enough that the detail is a token toll only on a session actually touching them.
