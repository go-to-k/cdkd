- **A failed EMR (Cluster, InstanceGroupConfig, InstanceFleetConfig), FSx FileSystem or EFS (FileSystem, MountTarget, AccessPoint) create, update or delete no longer writes the caller's account id, assumed-role ARN and session name into the persisted deployment events (issue [#2319](https://github.com/go-to-k/cdkd/issues/2319))** -- `src/provisioning/providers/{emr-cluster,emr-instance-group-config,emr-instance-fleet-config,fsx-filesystem,efs}-provider.ts`, and unit cases. The thrown message quoted AWS's raw text, which names the caller on an access denial, and `deployments/{runId}.jsonl` outlives the run. The message now carries the error class (`AccessDeniedException. Re-run with --verbose for AWS's own message.`), and AWS's text goes to the debug log, through the operation's secret masker. This also covers the EMR cluster's describe-before-delete and termination-poll failures and the FSx file system's deletion-poll failure. A cdkd-authored or transport error keeps its text (on EFS still masked, as before). The AWS error stays as the `cause`, so an IAM grant that is still propagating is retried as before, and an EMR or FSx create that left a resource behind still names it for `cdkd rollback --revert-failed`. An "already exists" is still stated as such.
