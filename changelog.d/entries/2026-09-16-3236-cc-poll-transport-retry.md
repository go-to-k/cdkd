- **A network blip during a Cloud Control wait no longer discards the request token and leaves the resource untracked (issue [#3236](https://github.com/go-to-k/cdkd/issues/3236))** -- `src/provisioning/cloud-control-provider.ts`. `waitForOperation` polled `GetResourceRequestStatus` with no per-poll error handling, so a transport failure propagated out of the loop and took the `RequestToken` -- which lived only in that parameter list -- with it. The operation kept running server-side, so a CREATE that AWS went on to complete left a LIVE resource with no state record: invisible to rollback, to `cdkd destroy`, and to `cleanupFailedCreateRemnant`, whose first guard admits only a `CloudControlOperationFailedError`. Reported against an `AWS::RDS::DBInstance` that reached `available` while a VPN dropped; the untracked instance then blocked the deletion of five tracked resources. The poll is now retried on the SAME token -- idempotent in a way replaying the create is not, since `GetResourceRequestStatus` invokes no resource handler, so [#2039](https://github.com/go-to-k/cdkd/issues/2039)'s duplicate-create is structurally absent. Throttles and transient 5xx are covered too, and were the worse case: aborting propagated AWS's `Rate exceeded`, which the retry classifier matches, so the outer `withRetry` re-invoked `create()` against a resource already being created. The retry stays inside the existing wall-clock budget, bounded by a two-minute grace over one unbroken run of failures. When cdkd does stop waiting -- at the grace, at the deadline (which lost the token for the same reason), or on a failure too non-transient to retry -- it throws the new `CloudControlWaitAbandonedError` carrying the token, the last `Identifier` any poll reported, and a pasteable `aws cloudcontrol get-resource-request-status` line. Fixes all four `waitForOperation` call sites, not just the reported CREATE. Mechanism and the per-operation retryability rule are in the module's own doc comments.
