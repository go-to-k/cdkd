- **`cdkd local run-task` and `cdkd local start-api --watch` no longer leave a container behind when ^C lands during a container start (issue [#4495](https://github.com/go-to-k/cdkd/issues/4495))** -- `src/local/ecs-task-runner.ts`, `src/local/ecs-network.ts`, `src/cli/commands/local-run-task.ts`, `src/local/container-pool.ts`, `src/cli/commands/local-start-api.ts`. `run-task` recorded a container only after its `docker run` returned, so a ^C during that run (or during the network + metadata sidecar start, or a `docker volume create`) removed what it knew and exited, and the run then left its container behind. `start-api --watch` disposed a reload's previous container pool in the background, and the ^C cleanup exited without waiting for it, so a container that pool was still starting survived; a pool's own dispose also stopped waiting for an in-flight start after 5s. The ^C cleanup now waits for the in-flight docker step and removes what it created, and starts nothing more; `start-api` waits for every pool a reload replaced, and a reload whose re-synth outlasts the ^C swaps in no new pool. The wait is bounded at 20s; past it cdkd removes what the command creates by name and warns, naming it and the command that removes it (`docker rm -f`, `docker volume rm -f` or `docker network rm`), since a `docker` command still pending can create it later. Tests: `tests/unit/local/ecs-task-runner-runner.test.ts`, `tests/unit/cli/local-run-task-command-body.test.ts`, `tests/unit/local/container-pool.test.ts`, `tests/unit/cli/local-start-api-reload-shutdown.test.ts`; integ arms in `tests/integration/local-run-task/verify.sh` and `tests/integration/local-start-api/verify.sh`.
