- **`cdkd drift --revert` no longer disables a freshly deployed `AWS::Lambda::EventSourceMapping` (issue [#5737](https://github.com/go-to-k/cdkd/issues/5737))** -- `src/provisioning/providers/lambda-eventsource-provider.ts` (`readCurrentState`, new `enabledFromState`). `Enabled` was derived from `State` as `Enabled` / `Enabling` / `Updating`, so the observed baseline captured right after the create, while the mapping is still `Creating`, recorded `Enabled: false` for every mapping the template leaves enabled (every `SqsEventSource`). Once the mapping settled, `cdkd drift` reported `Enabled: false -> true` and `--revert` sent `Enabled: false`, stopping the consumer. `Creating`, `Updating` and `Deleting` carry no enabled-ness (a mapping created or updated with `Enabled: false` passes through `Creating` / `Updating` to `Disabled`, and a `Deleting` one settles to nothing), so for those the readback now answers what the call that started the transition sent, with CloudFormation's absent default `true`; `Enabled` / `Enabling` and `Disabled` / `Disabling` still read their own state. `Updating` used to read `true` even on a disabled mapping, the same defect in the other direction. A mapping deployed by an earlier version keeps its recorded `Enabled: false` baseline (a no-change deploy does not re-read it); `cdkd drift` no longer reports or reverts that value while the template and the live mapping agree on enabled (issue [#5749](https://github.com/go-to-k/cdkd/issues/5749)).
