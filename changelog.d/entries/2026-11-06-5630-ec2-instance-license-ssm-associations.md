- **`AWS::EC2::Instance` with `LicenseSpecifications` / `SsmAssociations` now deploys on the SDK path (issue [#5630](https://github.com/go-to-k/cdkd/issues/5630))** -- `src/provisioning/providers/ec2/` (new `instance-ssm.ts`), the regenerated coverage map, unit tests and the `ec2-instance` integ fixture. Before this change, either property sent the whole instance through Cloud Control. `LicenseSpecifications` is sent on `RunInstances`; it is create-only, so any change replaces the instance, as in CloudFormation, and `cdkd drift` does not read it back (EC2 does not report it). `SsmAssociations` is created with Systems Manager `CreateAssociation` once the instance runs (a create declaring it waits for `running` even under `--no-wait`); the deploy does not wait for the association to execute. Two or more entries, or an entry without an `IamInstanceProfile`, are refused before any AWS call, as CloudFormation refuses them. Two deliberate differences from CloudFormation: a changed or removed association is updated in place (delete, then create), where CloudFormation fails the update; and deleting the instance also deletes its association (best effort, a warning on failure), where CloudFormation leaves it. If the create after a delete fails, the error says the instance has no association. Association parameter values are never logged. `cdkd drift` reads the association back. Resources already recorded as Cloud Control-provisioned stay on Cloud Control. The other `AWS::EC2::Instance` properties listed on #5630 still route through Cloud Control.
