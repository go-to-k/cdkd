- **`cdkd local` resolves CloudFormation dynamic references before a container starts (issue [#2056](https://github.com/go-to-k/cdkd/issues/2056))** -- `package.json` (`cdk-local` ^0.149.9), `src/cli/commands/{local-invoke,local-start-api,local-invoke-agentcore,local-run-task}.ts`, `src/local/{container-pool,ecs-task-runner,ecs-task-resolver}.ts`. A container env value carrying `{{resolve:secretsmanager:...}}` / `{{resolve:ssm:...}}` / `{{resolve:ssm-secure:...}}` reached the container as the token text, including a `--from-state` `Fn::ImportValue` / `Fn::GetStackOutput` of a secret-bearing output, which cdkd persists redacted to its token (#1899). `local invoke`, `local start-api`, `local invoke-agentcore` and `local run-task` now resolve it with the developer's credentials (`--profile` honoured, never the `--role-arn` role: `src/local/dynamic-reference.ts`) through cdk-local's resolver (go-to-k/cdk-local#784): a cross-stack value in the producer's region, any other in the owning stack's. A resolved key is a value-less `-e KEY`, off the `docker run` argv and every log line; an `--env-vars` override skips the lookup; a failed lookup fails the command before any container starts, naming the reference and the IAM permission. `local run-task` refuses a token in `Command` / `EntryPoint` / a health-check command. The engine commands (`start-agentcore`, `start-cloudfront`, `start-service`, `start-alb`) get the same behaviour from the `cdk-local` bump. Tests: `tests/unit/cli/{local-invoke,local-container-env,local-run-task}-dynamic-reference.test.ts`, `tests/unit/local/ecs-task-runner-dynamic-reference.test.ts`, `tests/unit/local/container-pool.test.ts`; integ `local-invoke-from-state`.
