- **A replacement whose new physical name is held by ANOTHER resource no longer points at `--replace`, and `--replace` no longer deletes the managed resource there (issue [#3808](https://github.com/go-to-k/cdkd/issues/3808))** -- new `src/deployment/replacement-name-holder.ts`, `src/deployment/deploy-engine.ts`, `docs/cli-deploy-safety.md`. When a property-driven replacement's create-first attempt collided on a name, cdkd assumed the old resource held it and advised `cdkd deploy --replace`, which deletes the old resource first. When the replacement also CHANGES the name (the template's explicit name property differs from the name state records for the old resource, and the old physical id does not name it), the holder is some other resource: `--replace` deleted the managed resource and then hit the same collision. The deploy now fails with `NAMED_REPLACEMENT_COLLISION` saying the name is held by another resource, under every flag and `UpdateReplacePolicy`, and deletes nothing. The UPDATE-not-supported fallback's `Retain` refusal, which advised removing `Retain` so cdkd deletes the old resource first, takes the same verdict. The `--recreate-via-cc-api` replacement also now refuses a type Cloud Control cannot create before deleting anything, inside the engine as well as at pre-flight (issue [#3899](https://github.com/go-to-k/cdkd/issues/3899)).
