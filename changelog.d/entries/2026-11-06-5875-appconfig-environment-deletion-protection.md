- **`cdkd destroy` now honors an `AWS::AppConfig::Environment`'s `DeletionProtectionCheck` (issue [#5875](https://github.com/go-to-k/cdkd/issues/5875))** -- `src/provisioning/providers/appconfig-environment-provider.ts` (new), `provider-classes.ts`, `register-providers.ts`, `provider-registry.ts`. The type had no SDK provider, so Cloud Control deleted it with only the identifier. `DeletionProtectionCheck` is write-only, so the template's `BYPASS` was lost and AppConfig applied the account default: an environment whose configuration had been read inside AppConfig's protection window (60 minutes by default, configurable from 15 to 1440; for example by a Lambda function destroyed in the same run) failed with "actively being used" and kept failing on re-runs until the window passed. The new provider calls `DeleteEnvironment` with the value recorded in state, as CloudFormation does; an unset value keeps the account default. Create, update (`Name`, `Description`, `Monitors`, `Tags`) and `cdkd import` with an explicit `<ApplicationId>|<EnvironmentId>` are covered, and the physical id stays the Cloud Control one. A record written by an earlier cdkd as `provisionedBy: 'cc-api'` now deletes through the new provider too (the type joins the sticky-Cloud-Control exemptions as `cc-broken`), so #5875 is fixed for stacks deployed before this release as well. `AWS::AppConfig::ConfigurationProfile` is unchanged.
