- **A successful fix-forward deploy now deletes the NAT gateway or Elastic IP an earlier failed CREATE left under the same logical id (issue [#4606](https://github.com/go-to-k/cdkd/issues/4606))** -- `src/provisioning/providers/ec2-provider.ts`. After `cdkd deploy --no-rollback` failed with an `AWS::EC2::NatGateway` or `AWS::EC2::EIP` already created (a journaled proven orphan: a gateway whose available-state wait failed, an address whose instance association failed) and the fixed template created a new one under the same logical id, the successful deploy warned, named the earlier one, exited `2` and left it in AWS. `EC2Provider` now answers `isSameResource` for those two types when SDK-routed (a Cloud Control-routed one, e.g. a NAT gateway setting `MaxDrainDurationSeconds`, is unchanged) from the AWS-generated id (the `nat-` gateway id; the `eipalloc-` allocation id from the composite `PublicIp|AllocationId` or the bare form, never the public IP): the client must be in the stack's region and the record's resource must read back live (a NAT gateway `pending` or `available`), and the earlier one is then `different`, so the settle deletes it; equal ids (including the composite and bare spellings of one allocation id) are `same`, and a bare journaled allocation id (the create's fallback when the composite fence refuses) is never `different`, since the settle's holder checks compare the id string. Every other EC2 type, an unrecognised id form and a failed read stay `unknown` (the previous warning and exit `2`). An earlier gateway or address already gone is named in one info line. Tests: `tests/unit/provisioning/ec2-nat-eip-same-resource-4606.test.ts`; integ `vpc-nat-gateway` Phases 1d / 1e assert the earlier resource deleted, the new one kept, exit `0`.
