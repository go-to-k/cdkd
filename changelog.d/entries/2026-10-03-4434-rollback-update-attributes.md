- **A rolled-back update now records the attributes the provider returned, so a reverted `AWS::EC2::SecurityGroupIngress` keeps its new `sgr-` rule id instead of the revoked one (issue [#4434](https://github.com/go-to-k/cdkd/issues/4434))** -- `src/deployment/rollback-executor/replay-retry.ts` (`recordAfterRollbackUpdate`), `src/deployment/rollback-executor.ts`, `src/deployment/rollback-executor/replay-revert.ts`, `src/deployment/rollback-executor/replay-reverse-replacement.ts`, `src/deployment/secret-redaction/mask-only.ts` (`recordNoEchoAttributeValues`), `tests/unit/deployment/rollback-executor-update-attributes.test.ts`. Both UPDATE arms (`cdkd rollback` / the automatic rollback, and `--revert-failed`) kept the restored record's attributes, so after a revert that re-authorized a rule, `cdkd export` and a later `Fn::GetAtt <rule>.Id` read a revoked id. The record now takes the returned set wholesale when the update replaced, merges it key-wise when it updated in place, and keeps the restored set when the provider returned none; an update that replaced under a new physical id is recorded under that id, without the removed resource's attributes when it returned none. A `NoEcho` declaration on those attributes (a custom resource's response, a nested stack's masked outputs) is registered before the record is redacted, as the deploy engine does, so they persist as `***`; the reverse-replacement replay-CREATE arm, which already recorded its create's attributes, now does the same.
