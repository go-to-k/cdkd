- **`cdkd deploy` / `cdkd publish-assets` now warn about the asset-manifest values they forward verbatim, instead of passing them silently (issue [#3497](https://github.com/go-to-k/cdkd/issues/3497), PR #3539)** -- `src/assets/manifest-passthrough-warnings.ts`, `src/assets/{docker-build,asset-publisher}.ts`. `cdkd deploy -a <dir>` consumes a pre-synthesized assembly with no CDK subprocess in between, and most of an asset manifest is handed to Docker or S3 as written. **Behavior change:** three new warnings at default verbosity, none of them a refusal. (1) A BuildKit passthrough whose host path resolves outside the assembly -- `dockerFile`, `dockerBuildContexts`, `dockerBuildSecrets`, `dockerBuildSsh`, `cacheFrom`, `cacheTo`, `dockerOutputs` -- names the field and the path, and says WRITE when the value carries a `dest=` key (the FIELD does not decide: `cacheFrom` can carry a `dest=`). (2) `source.executable` names the command line before it runs, because a Docker asset may declare one instead of a Dockerfile, so `-a <dir>` DOES execute code from the assembly and nothing said so. The warn names the command and the argument COUNT only; the full argv stays at `--verbose`, because the layer's redaction knows `docker build` flag shapes and not a build script's own secret arguments. `cdkd local invoke` warns too. (3) An asset destination bucket or ECR repository that is neither default-bootstrap-shaped nor cdkd-managed names itself, since `redirectFileAsset` rewrites only bootstrap-shaped destinations and anything else is uploaded to verbatim. **Deliberately NOT a refusal and NOT an opt-in flag**, per the maintainer decision recorded on the issue: this is CDK-CLI parity territory, the attack presupposes someone who already controls the assembly and therefore the account, and a default-deny plus flag reduces who holds the capability without protecting who uses it. Docs: `docs/cli-deploy-safety.md` gains a section saying a pre-synthesized assembly is trusted input.
