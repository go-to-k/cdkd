- **A deploy now waits for EC2 instance monitoring, metadata options and IAM instance profile changes, an ECS cluster's Service Connect attachments, an EFS access point and backup policy, an EMR automatic scaling policy and a DynamoDB GlobalTable Kinesis precision change to settle, as CloudFormation does; `--full-wait` also waits for Route 53 changes to reach `INSYNC` (issue [#7132](https://github.com/go-to-k/cdkd/issues/7132))** -- `src/provisioning/providers/ec2/instance-settle-wait.ts`, `src/provisioning/providers/ecs/cluster-attachments.ts`, `src/provisioning/providers/efs/settle-waits.ts`, `src/provisioning/providers/emr-instance-group-config/scaling-policy-wait.ts`, `src/provisioning/providers/dynamodb-settle-waits.ts`, `src/provisioning/providers/route53/change-wait.ts`. These providers returned while AWS still read the change as transitional (`pending` / `associating` monitoring and profile associations, `PROVISIONING` clusters, `creating` access points, `ENABLING` backup policies, `PENDING` / `ATTACHING` scaling policies, an `UPDATING` Kinesis destination), so the drift baseline could record the old value and `cdkd drift --revert` pushed it back, and a policy AWS later marked `FAILED` deployed with exit 0. CloudFormation completes each of these only once the change has landed (measured in us-east-1), and a default deploy now waits the same way; `--no-wait` skips them. A GlobalTable precision update also waits first for a destination a `--no-wait` deploy left `UPDATING`, which AWS would refuse, and takes AWS's "already set to the desired value" as success. Route 53 hosted zone, record and VPC association changes keep returning while `PENDING` by default, as CloudFront `Deployed` does: they are usable at once and have no failure state; `--full-wait` waits for `INSYNC` and warns if the wait runs out. The added time on a default deploy is the time CloudFormation spends on the same change (about 1 s for an instance change, 1-2 s for EFS, about 20 s for a Service Connect cluster, 10-15 s for a scaling policy, about 3 min for a GlobalTable precision change). A Bedrock AgentCore runtime delete, in deploy and destroy alike, now waits until the runtime is gone (about 3 min), as CloudFormation does: while it is `DELETING` it keeps its name, and a same-named create was refused with `ConflictException`. `cdkd drift` no longer reports a pre-fix baseline that recorded an instance's or file system's setting mid-change while the live resource matches the template.
