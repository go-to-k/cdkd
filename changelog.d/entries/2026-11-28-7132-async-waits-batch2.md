- **A deploy now waits for more asynchronous AWS changes to settle, as CloudFormation does; `--full-wait` also waits for Route 53 changes to reach `INSYNC` (issue [#7132](https://github.com/go-to-k/cdkd/issues/7132))** -- `src/provisioning/async-operation-waits.ts`. These calls returned while AWS still read the change as transitional, so the drift baseline could record the old value (which `cdkd drift --revert` then pushed back) and a change AWS later marked failed deployed with exit 0. Each now waits, as CloudFormation does (measured in us-east-1): EC2 instance monitoring, metadata options and IAM instance profile changes (about 1 s); an ECS cluster's Service Connect attachments (about 20 s); an EFS access point and backup policy (1-2 s); an EMR automatic scaling policy (10-15 s); a DynamoDB GlobalTable Kinesis precision change (about 3 min), which also first waits out a destination a `--no-wait` deploy left `UPDATING` and takes "already set to the desired value" as success; an RDS DB proxy target registration; and a Bedrock AgentCore runtime delete (about 3 min, in every mode: the name stays taken while `DELETING`). `--no-wait` skips the deploy-side waits. Route 53 zone, record and VPC association changes still return while `PENDING` by default, as CloudFront `Deployed` does: they are usable at once and have no failure state. `cdkd drift` no longer reports a baseline an earlier release recorded mid-change while the live resource matches the template.
