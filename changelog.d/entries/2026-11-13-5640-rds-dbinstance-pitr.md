- **The SDK provider restores an `AWS::RDS::DBInstance` to a point in time (issue [#5640](https://github.com/go-to-k/cdkd/issues/5640))** -- `src/provisioning/providers/rds/instance-pitr.ts`, `instance-create.ts`, `instance-update.ts`, `instance-restore.ts`, `drift.ts`, `rds-provider.ts`, `src/provisioning/restore-source-guard.ts`, `src/deployment/restore-source-identity.ts`, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, unit tests, the RDS wire cases, and a new point-in-time phase in the `rds-dbinstance-snapshot-restore` integ. Before, an instance declaring `RestoreTime`, `UseLatestRestorableTime`, `SourceDBInstanceAutomatedBackupsArn` or `SourceDbiResourceId` routed through Cloud Control. Now the create is a `RestoreDBInstanceToPointInTime` carrying the members CloudFormation's handler sends, tested before a read replica and a snapshot restore as the handler tests them: a `SourceDBInstanceIdentifier` beside a point-in-time key names the restore's source. The engine, when undeclared, is read from the source instance, the instance a `SourceDbiResourceId` names, or the automated backup; a source that does not exist, or a `RestoreTime` that is not an ISO 8601 timestamp with a time zone, fails the create before anything is made. The members the restore call has no room for go out in the same follow-up `ModifyDBInstance` a snapshot restore gets. An added or changed point-in-time key on an existing instance is refused, as CloudFormation refuses it; a removed one changes nothing. A replacement whose point-in-time source is the replaced instance itself (by name, resource id, or its automated backups) is refused before the delete, which would remove those backups. A restored instance, from a snapshot or to a point in time, now waits for `available` up to the `--resource-timeout` deadline when that allows more than 30 minutes. None of the keys is read back for drift. `SourceDBClusterIdentifier` stays on Cloud Control. Resources already deployed through Cloud Control stay there.
