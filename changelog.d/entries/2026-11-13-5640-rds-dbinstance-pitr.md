- **The SDK provider restores an `AWS::RDS::DBInstance` to a point in time (issue [#5640](https://github.com/go-to-k/cdkd/issues/5640))** -- `src/provisioning/providers/rds/instance-pitr.ts`, `instance-create.ts`, `instance-update.ts`, `instance-restore.ts`, `drift.ts`, `rds-provider.ts`, `src/provisioning/restore-source-guard.ts`, `src/deployment/restore-source-identity.ts`, the regenerated property-coverage map, unit tests, and a point-in-time phase in the `rds-dbinstance-snapshot-restore` integ. Before, an instance declaring `RestoreTime`, `UseLatestRestorableTime`, `SourceDBInstanceAutomatedBackupsArn` or `SourceDbiResourceId` routed through Cloud Control. Now the create is a `RestoreDBInstanceToPointInTime` carrying the members CloudFormation's handler sends, tested before a read replica and a snapshot restore: a `SourceDBInstanceIdentifier` beside a point-in-time key names the restore's source. An undeclared engine is read from the source; a missing source, or a `RestoreTime` that is not an ISO 8601 timestamp with a time zone, fails the create before anything is made. The members the restore call cannot carry go out in the follow-up `ModifyDBInstance` a snapshot restore gets. An added or changed point-in-time key on an existing instance is refused, as CloudFormation refuses it; a removed one changes nothing. A replacement restoring from the instance it replaces is refused before the delete, which would remove its backups. A restored instance (from a snapshot too) now waits for `available`, under `--no-wait` too, up to the `--resource-timeout` deadline. None of the keys is read back for drift. `SourceDBClusterIdentifier` stays on Cloud Control; resources deployed through Cloud Control stay there.
