- **A Cognito UserPool update now refuses an immutable Schema change before applying anything, and a rollback over an added custom attribute no longer leaves state ahead of AWS (issue [#6375](https://github.com/go-to-k/cdkd/issues/6375))** -- `src/provisioning/providers/cognito/update.ts`. `update()` sent `UpdateUserPool` first and refused a removed or modified custom attribute only after it, so the refused update had already applied everything else. A rollback reverting a deploy that added an attribute hit this: it applied the old password policy and MFA settings, then refused, and reported `Rollback failed`. State kept the failed deploy's record over a pool holding the old settings, so the next deploy of the same update diffed `NO_CHANGE` and the pool kept the weaker settings while cdkd reported success. The check now runs before the first write. A template-path update refuses with nothing applied. A rollback warns, applies everything else, leaves the attributes on the pool (AWS can only add them), and records the Schema the pool holds. `cdkd drift --revert` keeps the refusal, now before any write.
