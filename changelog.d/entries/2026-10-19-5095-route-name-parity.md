- **An un-named resource gets the same generated name on the SDK provider and Cloud Control routes (issue [#5095](https://github.com/go-to-k/cdkd/issues/5095))** -- `src/provisioning/resource-name.ts`, every SDK provider that generates a name, `src/deployment/deploy-engine/routing.ts`, `src/deployment/deploy-engine/update-in-place.ts`, `src/deployment/replacement-name-holder/`. Each type now has one name rule that both routes read. A Cloud Control create of an un-named `AWS::CodeCommit::Repository`, `AWS::RDS::DBProxy` or `AWS::RDS::DBProxyEndpoint` used to fail, because their schemas require the name; it now gets the name the SDK provider gives. An un-named `AWS::S3Express::DirectoryBucket` on Cloud Control used to be sent a name without the required `--<zone id>--x-s3` suffix; it now gets the suffix from `LocationName`, and a create whose `LocationName` is not a zone id is refused with the fix named. On a stack with a stack instance id, an un-named CodeBuild project, EC2 security group, CloudTrail trail, Glue job, crawler, connection or trigger, or Firehose delivery stream is now named `{stackName}-{logicalId}-{suffix}` instead of its bare logical id, which collided across stacks sharing a VPC or account and region and on every replacement, and Cloud Control names log groups, SSM parameters, Auto Scaling groups, DynamoDB global tables, ECS task definitions, Lambda network connectors, EventBridge pipes and Scheduler schedules as their SDK providers do. Neither route generates an `AWS::Events::EventBus` name any more: CloudFormation requires it. Stacks without an instance id keep every name either route generated before.
