- **`cdkd destroy` re-reads the stack's state under its lock, so a write during the confirmation prompt cannot make it delete another stack's resource (issue [#5220](https://github.com/go-to-k/cdkd/issues/5220))** -- `src/cli/commands/destroy-runner.ts` (`namesEveryResourceOf`), `docs/cli-destroy.md`, a new unit file and updated destroy test harnesses. Before, a destroy deleted the resources of the record read BEFORE its confirmation prompt: a `cdkd refactor` that moved a resource to another stack, or a deploy that replaced one, while the prompt waited left the destroy deleting a resource the record no longer owned. Now, under the stack lock, the record is read again (beside the refactor marker, in one concurrent round trip) and the destroy refuses with `STATE_CHANGED`, deleting nothing, unless the record still names every resource it named before under the same logical and physical ids; a resource added since is left alone.
