- **A Cognito user pool that consumes a same-deploy SMS (SNS-caller) IAM role no longer fails the deploy outright on IAM trust-policy propagation** (issue [#2901](https://github.com/go-to-k/cdkd/issues/2901)). CDK's `UserPool` L2 auto-creates that role for `mfaSecondFactor: {sms: true}`, and cdkd's fast SDK path issues `CreateUserPool` before IAM has propagated the trust policy, so AWS answered `InvalidSmsRoleTrustRelationshipException` / "Role does not have a trust relationship allowing Cognito to assume the role". No entry in `IAM_PROPAGATION_ERROR_MESSAGE_PATTERNS` matched it (0 of 49, across all three arrays), so this was not a mis-shaped retry budget — the create was **single-shot**. The same template deploys under `cdk deploy`, whose latency lets IAM settle.

  cdkd now retries it on the dense IAM-propagation grid, like the Firehose / Glue / Step Functions / CloudTrail / KMS races already in that table. **One entry covers every call that validates the role**, including `SetUserPoolMfaConfig` — reached from both `create()` and `update()`. The entry keys on the message tail rather than the exception name the issue asked for, and drops the service name even though AWS supplies one; both reasons, and the arithmetic behind not widening the provider's own inner retry instead, are at the entry in `retryable-errors.ts`.

  Live A/B against real AWS, one variable (a stack whose SMS role deliberately omits Cognito from its trust policy, so the rejection is permanent): **70s / 26 IAM-propagation retries** with the entry, **13s / no retry** without it. Same template, same AWS message — which is what establishes the dense grid is selected, not merely that a retry happens.
