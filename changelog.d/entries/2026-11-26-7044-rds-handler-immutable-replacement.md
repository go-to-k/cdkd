- **`cdkd diff` shows the RDS changes CloudFormation answers with a new DB instance or cluster as replacements (issue [#7044](https://github.com/go-to-k/cdkd/issues/7044))** -- `src/analyzer/replacement-rules/rds-immutability.ts` (new), `src/analyzer/replacement-rules/rules.ts`, `src/analyzer/replacement-rules/evidence.ts`, `src/provisioning/providers/rds/{instance-update,cluster-update,shared}.ts`. A changed `AWS::RDS::DBInstance` `AvailabilityZone` (except one dropped on a `MultiAZ: true` instance), a `PerformanceInsightsKMSKeyId` changed or removed after a key was declared, an added or changed `SourceDBInstanceIdentifier` / `SourceDBClusterIdentifier` (a promotion stays in place), an added or changed `DBSnapshotIdentifier` / `DBClusterSnapshotIdentifier` / `RestoreTime` / `SourceDBInstanceAutomatedBackupsArn` / `SourceDbiResourceId`, a `UseLatestRestorableTime` turned on, and an added or changed `AWS::RDS::DBCluster` `GlobalClusterIdentifier` used to show as updates (so `--fail-on destructive` and `--require-approval destructive` passed them); the deploy then refused them saying CloudFormation refuses the same update. They now show as replacements, as CloudFormation's RDS handler makes them (measured on #7038 for the zone and the key), and the deploy refuses them before any call unless `--force-stateful-recreation` is given, as for `Engine` (#5467). The provider's own refusals, still reached by `drift --revert`, a rollback or a value the diff could not resolve, no longer claim CloudFormation refuses the change.
