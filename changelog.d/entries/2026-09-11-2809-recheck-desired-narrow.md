- **`cdkd deploy` no longer calls a provider's `update()` for a change the no-change re-check should absorb -- a `DeletionPolicy` / `UpdateReplacePolicy`-only flip, or an intrinsic resolving to the stored value -- on a resource carrying a `--prefer-sdk-route` silent drop (issue [#2809](https://github.com/go-to-k/cdkd/issues/2809))** -- `src/deployment/deploy-engine.ts` (the UPDATE arm's no-change re-check) and `tests/unit/deployment/deploy-engine-silent-drop-record.test.ts`. Since issue [#2750](https://github.com/go-to-k/cdkd/issues/2750) the re-check compared a record NARROWED to what the SDK route can write against a desired bag that still carried an allow-listed removable drop (a create-only drop stays on both sides), so the two could never match for an SDK-routed resource carrying one. Such a resource took a redundant `update()` whenever the diff reported a change the re-check exists to absorb, and the attribute-only branch nested inside the skip was unreachable. For `AWS::SNS::Subscription`, where `Region` is such a drop, that update is the provider's delete-then-create, so by that code path a `DeletionPolicy` / `UpdateReplacePolicy`-only flip re-created the subscription under a new ARN. Live-tested by `sdk-to-cc-autoroute` phases 4b/4c. The desired operand is now narrowed by the diff's own desired-side rule (`withoutAcceptedSilentDropProperties`: the allow set only, and not for a record on Cloud Control; a pre-v7 record with no `provisionedBy` counts as SDK, as it does for the stored side) -- deliberately not the record side's every-drop rule, because an un-allowed drop auto-routes the resource to Cloud Control, which does write the key. One consequence: a record a pre-#2750 binary wrote keeps its stale allow-listed key through such a deploy, where the redundant `update()` used to rewrite it away; the diff and the re-check narrow it before comparing, and `cdkd drift` compares against it only for a record with no observed baseline.
