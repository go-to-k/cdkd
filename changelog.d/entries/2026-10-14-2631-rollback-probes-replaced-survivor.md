- **A rollback no longer re-creates the old resource of a replacement whose delete the deploy could not confirm while that resource is still there (issue [#2631](https://github.com/go-to-k/cdkd/issues/2631))** -- `src/deployment/deploy-engine/replacement.ts`, `src/deployment/deploy-engine/update-replace.ts`, `src/deployment/deploy-engine/execute.ts`, `src/deployment/deploy-engine.ts`, `src/deployment/rollback-executor/replay-reverse-replacement.ts`, new `src/deployment/rollback-executor/replaced-survivor.ts`, `src/types/rollback-journal.ts`, `src/cli/commands/rollback.ts`. When a replacement's delete of the old resource failed (including the post-deploy retry from #4900, or a deploy that failed before it), was skipped by the provider, or was blocked by a failed `UpdateReplacePolicy: Snapshot` snapshot, a later failure in the same deploy rolled the replacement back by re-creating the old resource. When the old one was still alive, that made a duplicate (auto-named types) or failed with `AlreadyExists` (named types). The rollback journal now records `oldResourceMaySurvive` on such an operation (`kept` when AWS refused the delete outright or it was never sent, `unconfirmed` otherwise; an additive field, no journal version change), and the rollback reads AWS for the old resource through the provider's drift read before re-creating it. If AWS reports it gone, it is re-created as before. If it is still there and `kept`, it is re-adopted, with a warning to check it with `cdkd drift` (exit 2). Otherwise (a delete that may still be running, or no answer) the operation is refused with the journal kept, and the message offers `cdkd rollback --orphan`. The `cdkd rollback` plan preview names all three outcomes. An ordinary deploy, and the rollback of any other replacement, makes no extra AWS call.
