- **A create retried after an ambiguous failure no longer reads its replay's "already exists" as the resource's own name collision (issue [#3978](https://github.com/go-to-k/cdkd/issues/3978))** -- `src/deployment/retry.ts` and `src/deployment/retryable-errors.ts` (`isAmbiguousOutcomeError`, `markReplayMayCollide`), with unit tests in `tests/unit/deployment/retry-ambiguous-create-replay-3978.test.ts` and `retry-ambiguous-cc-create-3978.test.ts`. When a main create call (a Kinesis `CreateStream`, or a Cloud Control `CreateResource`) succeeded on the AWS side but answered with an HTTP 5xx, the retry wrapper ran the create again, and the replay met the resource the first call had made. That "already exists" was treated as a collision on the resource's own name, so `--replace` deleted the live old resource and a replacement rollback deleted the live new one. After an attempt that ends without saying whether AWS acted on it -- a 500, 502, 503 or 504 that is not a throttle, or a Cloud Control handler failing mid-create (including its `Throttling` and `GeneralServiceException`, which it reports after it may have made the resource) -- every error that retry throws from then on is now marked so the collision is not credited. A connection reset or timeout after the send is recognised too, though no retry path replays one today. An API-level throttle or other 4xx does not arm this, so a collision with a resource that already held the name still classifies. Known costs: an update that first hit such an error can fail on Cloud Control's `UnsupportedActionException` instead of replacing the resource (a re-run replaces it), and the orphaned-name advice is not printed for such a replayed create (#3984). The AWS SDK's own retries inside a single call are not covered by this change.
