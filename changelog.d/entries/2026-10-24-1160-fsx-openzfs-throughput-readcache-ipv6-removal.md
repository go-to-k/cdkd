- **`AWS::FSx::FileSystem`: the warning for a removed OpenZFS `ThroughputCapacity`, `ReadCacheConfiguration` or `EndpointIpv6AddressRange` now says CloudFormation keeps the value too, on the shapes measured (issue [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/fsx-filesystem-provider.ts`. A CloudFormation A/B on the issue (us-east-1, 2026-10-24) removed each property from an OpenZFS `MULTI_AZ_1` file system. Every update completed in place, with the same file system, the value unchanged and no FSx administrative action: `ThroughputCapacity` on `SSD` and on `INTELLIGENT_TIERING`, `ReadCacheConfiguration` on `INTELLIGENT_TIERING`, and `EndpointIpv6AddressRange` on a dual-stack `SSD` file system in the same update that removed `NetworkType`. cdkd already sent nothing for these removals, so only the warning changes: it now reads `... and keeps its current AWS value, as CloudFormation leaves it; ...` on those shapes, for `ThroughputCapacity` and `ReadCacheConfiguration` only as the deploy's single removal with `NetworkType` not declared `DUAL` (CloudFormation refused every update while it was). Any other shape keeps the line that claims nothing about CloudFormation: a `SINGLE_AZ_*` file system, a deploy that also changes `StorageType`, an `EndpointIpv6AddressRange` removal while `NetworkType` stays declared, and, on `MULTI_AZ_1`, a `NetworkType` removal while `EndpointIpv6AddressRange` stays declared (CloudFormation refused both). Tests: `tests/unit/provisioning/providers/fsx-filesystem-provider.test.ts`; the `fsx-openzfs` integ gains a phase that removes `ThroughputCapacity` on its `SINGLE_AZ_1` file system and asserts the value stays and the warning makes no CloudFormation claim.
