- **An RDS, DocumentDB, Neptune, ElastiCache or DynamoDB create whose 5xx hid a server-side success is no longer replayed inside the AWS SDK and credited as somebody else's resource (issue [#4639](https://github.com/go-to-k/cdkd/issues/4639))** -- `src/provisioning/providers/{rds,rds-dbproxy,rds-dbproxy-endpoint,docdb,docdb-subnet-group,neptune,elasticache,dynamodb-table,dynamodb-globaltable}-provider.ts` (`getCreateClient`) and new `*-create-retry-4639` unit files. `CreateDBSubnetGroup` / `CreateDBCluster` / `CreateDBInstance` (RDS, DocumentDB, Neptune), `CreateDBProxy`, `CreateDBProxyEndpoint`, `CreateCacheSubnetGroup` / `CreateCacheCluster` and `CreateTable` (table and global table) carry no idempotency token and were sent through a client with the SDK's default retry, so a 5xx whose request had succeeded was replayed inside one `send`, and the replay's "already exists" surfaced from the deploy engine's FIRST attempt, read as a name another holder owns. Each now goes through a dedicated client wrapped by `withoutServerErrorRetries`: the 5xx reaches the engine's retry, whose ambiguous-outcome latch (#3983) marks the replay's collision as possibly this create's own. Such a 5xx is now retried on the engine's logged schedule rather than the SDK's quick in-`send` retries. Every other call keeps the full SDK retry, a name that existed before any ambiguous attempt is still a name collision, and nothing is adopted on that collision -- a name is not attribution. **Residual**: the other #4639 sites and the socket reset or timeout the SDK still replays.
