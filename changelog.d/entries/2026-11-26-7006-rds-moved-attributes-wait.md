- **`cdkd deploy`: an in-place RDS instance Port / CA certificate / Multi-AZ change, or a Neptune cluster DBPort change, records the new value once AWS applies it (issue [#7006](https://github.com/go-to-k/cdkd/issues/7006))** -- `src/provisioning/providers/rds/instance-update.ts`, `rds/instance-moved-attributes.ts`, `rds/waits.ts`, `neptune/cluster-update.ts`, `neptune/waits.ts`, `neptune/shared.ts`. The update recorded `Endpoint.Port` / `ListenerEndpoint.Port`, `CertificateDetails.*` and `SecondaryAvailabilityZone` (Neptune: `Port`) from a read taken right after the modify call, which still reports the old value (measured: the new port sits under `PendingModifiedValues` for about a minute, a Multi-AZ conversion's standby zone appears after about 7 minutes). A reader in the same deploy, such as a security group rule or an SSM parameter built from `instance.dbInstanceEndpointPort`, kept the old port. The update now waits until the instance reports the change applied and nothing pending for it, as CloudFormation does; an update changing none of them adds no call. Under `--no-wait` the update records those attributes absent rather than stale, and a `Fn::GetAtt` of one waits for the change, then reads the instance again. Tests: `tests/unit/provisioning/rds-dbinstance-moved-attributes-7006.test.ts`, `neptune-cluster-port-7006.test.ts`; integ `rds-dbinstance-getatt-attributes`.
