- **A standalone `AWS::EC2::SecurityGroupIngress` whose source changes is replaced, and a rolled-back deploy no longer leaves the new rule open (issue [#7071](https://github.com/go-to-k/cdkd/issues/7071))** -- `src/deployment/type-change-guard.ts`, `src/provisioning/sg-rule-identity.ts`. The rule's physical id (`<GroupId>|<IpProtocol>|<FromPort>|<ToPort>`) holds no source, so changing `CidrIp`, `CidrIpv6`, `SourcePrefixListId` or `SourceSecurityGroupId` (including through a replaced source security group) gave the new rule the old rule's id. cdkd read that as a name-idempotent create and refused the deploy, after the new rule was already authorized: it was recorded nowhere, the automatic rollback left it in place, and `cdkd drift` reported no drift. Two readable sources that differ are now two rules, as `AWS::Lambda::Permission` and `AWS::Glue::Table` already were: the new rule is kept and the old one revoked through its own record, as CloudFormation does. A group named by `SourceSecurityGroupName`, an unresolved value or a masked one keeps the refusal. Integ: `sg-ingress-source-replacement`.
