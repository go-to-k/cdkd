- **A resource `Type` change on an existing logical id is replaced through BOTH types (issues [#2668](https://github.com/go-to-k/cdkd/issues/2668), [#3036](https://github.com/go-to-k/cdkd/issues/3036))** -- `deploy-engine.ts`, `rollback-executor.ts`, `type-change-guard.ts`, `rollback-journal.ts`, `commands/rollback.ts`, new `type-change-replacement` integ. The diff emits a Type change as an UPDATE carrying the template's (new) type, and the engine routed both halves of the replacement on it, so the OLD resource's delete went to the NEW type's provider: an API error, a leak, or, where two types share a physical-id namespace, the deletion of an unrelated live resource. The old resource's delete, final snapshot and stateful guard now use the state record's type and layer; the create uses the template's. So leaving a stateful type for a non-stateful one now requires `--force-stateful-recreation`, and the reverse no longer does. An equal physical id across two types is treated as two resources. A Type change whose two property bags compare equal is no longer skipped as "no changes" (it left AWS and the record on the old type under a green deploy). The rollback journal gains an additive `previousResourceType` on completed UPDATE ops (no `journalVersion` bump, no state-schema change); both rollbacks re-create the old resource through its own type's provider. A journal from an older cdkd falls back to the previous record's type; an op naming no old type, two different ones, or a nested-stack pair is refused with `ROLLBACK_REPLACEMENT_UNROUTABLE` and the journal is kept (`--orphan <id>` skips it). `--revert-failed` skips a failed Type change with a warning. A Type change into or out of `AWS::CloudFormation::Stack` is still refused (`TYPE_CHANGE_NESTED_STACK`), with its message corrected. Design: [docs/design/2668-type-change-routing.md](https://github.com/go-to-k/cdkd/blob/main/docs/design/2668-type-change-routing.md).
