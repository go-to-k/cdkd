- **A regional `AWS::EC2::NatGateway` (`AvailabilityMode: regional`) is now provisioned by the SDK provider, and its `AvailabilityZoneAddresses` and `Tags` update in place (issue [#2762](https://github.com/go-to-k/cdkd/issues/2762))** -- `src/provisioning/providers/ec2-provider.ts`, `src/analyzer/replacement-rules.ts`, `src/deployment/intrinsic-resolver/getatt-construct-compute.ts`. `AvailabilityMode`, `VpcId` and `AvailabilityZoneAddresses` were unwired, so a gateway declaring them was auto-routed through Cloud Control. They now reach `CreateNatGateway`, and a regional gateway needs no `SubnetId`. A changed `AvailabilityZoneAddresses` associates the added Elastic IPs first, then releases the removed ones; it waits only where AWS would refuse the call (an address still being released or associated, or a release leaving no associated address). As in CloudFormation, adding it to an automatic-mode gateway replaces the gateway, and removing it is refused. A `Tags` change on any NAT gateway is applied with `CreateTags` / `DeleteTags`; before, every NAT gateway update was refused with `cannot be updated in place`. A malformed `AvailabilityZoneAddresses` is refused before any call. `drift` reads back the mode, the VPC and a manual-mode gateway's per-zone addresses, and `Fn::GetAtt` now resolves `RouteTableId`, `AutoProvisionZones`, `AutoScalingIps` and a zonal gateway's `EniId`, read live when the record lacks them; under `--no-wait` a referenced attribute waits for the gateway to become available, and one that never comes is refused with the cause, never answered with the gateway id. Changes to a zonal gateway's secondary addresses are still refused. Unit cases in `tests/unit/provisioning/ec2-natgateway-regional-2762.test.ts` and `tests/unit/analyzer/replacement-rules-ec2-natgateway.test.ts`; the `vpc-nat-gateway` integ fixture creates a regional gateway, adds and removes a zone, and destroys it.
