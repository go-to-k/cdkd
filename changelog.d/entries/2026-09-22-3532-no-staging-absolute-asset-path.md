- **`cdkd deploy` and `cdkd publish-assets` now consume a `cdk synth --no-staging` assembly, instead of failing with an `ENOENT` on a path that exists nowhere (issue [#3532](https://github.com/go-to-k/cdkd/issues/3532), PR #3536)** -- `src/assets/{asset-manifest-loader,docker-build,absolute-asset-path-warning}.ts`, `src/utils/assembly-path.ts`. Under `aws:cdk:disable-asset-staging` CDK writes each asset's absolute SOURCE directory into `files[*].source.path` and `dockerImages[*].source.directory`. `resolveAssemblyPath` joins with `path.join`, which ignores a leading separator, so an absolute value was folded INTO the output directory and died at `statSync` or BuildKit, with nothing naming the flag. **Behavior change:** an absolute value is now HONOURED, warned about when it falls outside `StackInfo.assetOutdir`, silent when inside; a value resolving onto the outdir ITSELF is accepted with its own line rather than silently; a RELATIVE escape still refuses. The warning names the sink, per caller: the destination `s3://bucket/key`, the BuildKit context, a `source.executable`'s working directory, or the AgentCore watch loop's `docker cp`. **Security note, because the first draft of this entry got it wrong:** the old fold was a boundary, not just a bad message -- no spelling of an absolute path reached a file outside the assembly (`/etc/passwd` folded inside and ENOENTed, `/../etc/passwd` and a symlink were refused). Honouring one removes that: an untrusted assembly can now have any readable directory packaged to a bucket it names, gated by the warning. Accepted because upstream `cdk-assets` honours the field with no containment at all. `assetOutdir` became REQUIRED on both resolvers and both publishers, so dropping it is a compile error (go-to-k/cdkd#3489's own defect). Also fixed: `absoluteAssemblyPathEscape` warned about two spellings of ONE directory (`/var` vs `/private/var`), crying wolf on ordinary macOS runs. Docs: `docs/cli-deploy-safety.md`.
