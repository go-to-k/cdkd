- **`cdkd deploy` and `cdkd publish-assets` now consume a `cdk synth --no-staging` assembly, instead of failing with an `ENOENT` on a path that exists nowhere (issue [#3532](https://github.com/go-to-k/cdkd/issues/3532), PR #3536)** -- `src/assets/asset-manifest-loader.ts`, `src/assets/docker-build.ts`, `src/assets/file-asset-publisher.ts`. Under `aws:cdk:disable-asset-staging` CDK writes each asset's absolute SOURCE directory into `files[*].source.path` and `dockerImages[*].source.directory`. Both were resolved through `resolveAssemblyPath`, whose lexical arm is `path.resolve(path.join(base, candidate))` -- and `path.join` ignores a leading separator, so an absolute value was folded INTO the output directory, read as CONTAINED, and died later at `statSync` or at BuildKit, with nothing naming the flag. **Behavior change:** an absolute `source.path` / `source.directory` is now HONOURED, and warned about -- naming the directory, and saying cdkd will package and upload it or hand it to the image build as the context -- when it falls outside `StackInfo.assetOutdir`; silent when inside. A RELATIVE escape still refuses, bound to the asset outdir so a Stage's `../asset.<hash>` keeps loading. Deploy-side twin of go-to-k/cdkd#3494, taken for its reasons: `--no-staging` is a documented CDK CLI flag and upstream `cdk deploy` honours an absolute value. For an absolute value the warning is the whole signal, not a boundary -- the relative arm catches an accidental `..`, not an adversary, who would write the absolute spelling. `assetOutdir` also became REQUIRED on both resolvers, so dropping it is a compile error rather than a silent narrowing onto the manifest directory (go-to-k/cdkd#3489's own defect). The nested-stack `aws:asset:path` walk still REFUSES an absolute value -- CDK always writes a nested template into the output directory. Docs: `docs/cli-deploy-safety.md`.
