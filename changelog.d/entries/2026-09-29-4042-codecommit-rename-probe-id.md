- **A CodeCommit repository rename no longer adopts, overwrites and later deletes a different repository that already holds the new name (issues [#4042](https://github.com/go-to-k/cdkd/issues/4042), [#4051](https://github.com/go-to-k/cdkd/issues/4051))** -- `src/provisioning/providers/codecommit-repository-provider.ts`, `src/types/resource.ts` (`UpdateContext.recordedAttributes`), and the `update()` calls in `src/deployment/deploy-engine.ts`, `src/deployment/rollback-executor.ts` (both revert arms) and `src/cli/commands/drift.ts` (`--revert`), with unit tests in `tests/unit/provisioning/providers/codecommit-repository-provider-rename-probe-4042.test.ts` and each caller's suite. When the rename call found the recorded repository gone, cdkd treated whatever repository held the desired `RepositoryName` as its own and sent it the description, key, tag and trigger writes, recording it as this resource so that a later `cdkd destroy` deleted it. Every `update()` caller now hands the provider the attributes cdkd recorded for the resource, and the repository under the new name is adopted only when its id is the `RepositoryId` cdkd recorded (or the one read just before this run's own rename). That still covers a deploy that stopped between a rename and its state write. A repository with a different id is refused with nothing sent to it. A record with no `RepositoryId` is refused too, with the `cdkd import ... --force` command that re-adopts the repository once the user has confirmed it is theirs. The same check guards the live trigger read on a retry, and the update now refuses before any call when the AWS client's region is not the one the record names.
