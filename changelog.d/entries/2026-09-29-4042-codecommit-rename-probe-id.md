- **A CodeCommit repository rename no longer adopts, overwrites and later deletes a different repository that already holds the new name (issue [#4042](https://github.com/go-to-k/cdkd/issues/4042))** -- `src/provisioning/providers/codecommit-repository-provider.ts`, with unit tests in `tests/unit/provisioning/providers/codecommit-repository-provider-rename-probe-4042.test.ts`. When the rename call found the recorded repository gone, cdkd treated whatever repository held the desired `RepositoryName` as its own, a previous attempt's rename, and sent it the description, key, tag and trigger writes, recording it as this resource so that a later `cdkd destroy` deleted it. cdkd now reads the repository's id just before renaming it and adopts the repository under the new name only when that id matches. Otherwise it refuses, sends nothing to that repository, and explains how to re-adopt it with `cdkd import --resource ... --force` if it is this resource's repository. That applies both when the matching id belongs to a different repository and when there is no id to compare, as after a deploy that stopped between the rename and its state write. The same check guards the live trigger read on a retry. Checking against the `RepositoryId` cdkd records, so the interrupted-deploy case can adopt automatically, is [#4051](https://github.com/go-to-k/cdkd/issues/4051).
