- **An `AWS::IAM::Policy` or `AWS::IAM::UserToGroupAddition` whose principals come from a secret no longer refuses every in-place update after its first deploy** (`src/deployment/deploy-engine.ts`, `src/provisioning/iam-policy-targets.ts` `withUnchangedSecretPrincipalLists`, go-to-k/cdkd#4064). State keeps a secret-derived `Roles` / `Groups` / `Users` entry as its `{{resolve:...}}` expression. That is not a list of IAM names, and neither provider can read the old side from IAM. So a change to the policy document, or an added principal, was refused with the orphan-and-redeploy repair. When the template still spells the same reference, the engine now drops that entry from the recorded side it hands the update. The desired side names that principal too, so the provider re-applies it (both calls are idempotent) and removes it from nothing. A principal named only by a secret value rotated away since the last deploy keeps its policy or membership and has to be removed by hand (before this, it kept it too, behind the refusal); a warning, by kind and never by name, says so. Only these two types' principal lists are touched, so no other provider stops re-sending a rotated secret on update. No plaintext enters the recorded side, and state keeps the reference. Nothing is dropped, and the update is refused as before, when any list keeps a re-pointed reference or a recorded `***` mask, or when `GroupName` / `PolicyName` changed, is itself secret-derived, or, for `PolicyName`, disagrees with the physical id. Both refusals' wording now says so. Destroying such a record still skips (go-to-k/cdkd#4150). Tests: `tests/unit/deployment/deploy-engine-secret-principal-previous.test.ts`, `tests/unit/provisioning/iam-policy-targets.test.ts`; fixture: `iam-secret-derived-principals`.
