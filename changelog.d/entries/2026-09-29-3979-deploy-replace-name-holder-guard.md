- **`cdkd deploy --replace` deletes the old resource first only when it provably holds the colliding name (issue [#3979](https://github.com/go-to-k/cdkd/issues/3979))** -- `src/deployment/deploy-engine.ts`, `src/deployment/replacement-name-holder.ts`, with unit tests in `tests/unit/deployment/deploy-engine-replace-name-holder.test.ts` and `tests/unit/deployment/replacement-name-holder.test.ts`. When a replacement's create-first attempt collided on a name, `--replace` deleted the old resource and re-created it, refusing only when the template's explicit name was known to differ from the old one. A template that named no name, or a name the IAM / ELBv2 providers rewrite under the stack prefix, collided just the same with an orphan of an earlier attempt, a retried create or a resource made outside the stack, and the live old resource was deleted though it never held that name. The delete-first now runs only once the old resource is shown to hold the name the create actually sent (its record, its physical id, cdkd's generated or rewritten name, and the parent that places it), with the same rule the rollback arm uses; otherwise the deploy fails with `NAMED_REPLACEMENT_COLLISION` and deletes nothing. The same check runs without `--replace` and under `UpdateReplacePolicy: Retain`, so their refusals no longer advise a `--replace` that would refuse. A `Type` change now deletes the old resource first only between types sharing one name space. In both directions — this and the rollback's reverse-replacement — a holder whose state record and last read-back name it differently (renamed outside cdkd) is no longer proven by its physical id, so nothing is deleted.
