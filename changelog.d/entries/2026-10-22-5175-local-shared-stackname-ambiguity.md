- **`cdkd local invoke` / `run-task` / `start-api` refuse a target naming a physical stack name that two CDK Stage stacks share, instead of running the first Stage's code (issue [#5175](https://github.com/go-to-k/cdkd/issues/5175))** -- `src/cli/stack-matcher.ts`, `src/local/lambda-resolver.ts`, `src/local/ecs-task-resolver.ts`, `src/cli/commands/local-start-api.ts`, `tests/integration/local-invoke-stage/`. Take an app with two Stages that each declare `new Stack(stage, 'Api', { stackName: 'SharedApiStack' })`. Before this change, `cdkd local invoke SharedApiStack:Fn` (or `SharedApiStack/...`) silently ran the first Stage's function, and `cdkd local start-api --stack SharedApiStack` served only the first Stage. Now invoke and run-task refuse with `matched 2 stacks`, naming both stacks by their CDK paths, and say to address one by its path (`Beta/Api/...`). start-api refuses to serve two stacks that share a physical name, because it reads deployed state by that name. It also refuses any served set in which two stacks declare the same routed Lambda or API logical id. Its container and stage / CORS maps are keyed by the bare logical id, so one stack's Lambda used to answer the other's routes. That case includes `--stack '**'` over a Stage deployed twice. Each error names the stacks and tells you to pass `--stack '<CDK path>'`. Separately, `deploy`, `diff`, `list`, `synth`, `publish-assets` and `scrub` given a CDK path such as `Prod/Api` now select that stack. They used to select the first stack carrying the same physical name, `Beta/Api`.
