- **An `AWS::EC2::SecurityGroupIngress` create no longer adopts an identical rule it did not create (issue [#4355](https://github.com/go-to-k/cdkd/issues/4355))** -- `src/provisioning/providers/ec2-provider.ts`, `src/deployment/prior-attempt-scope.ts`, `src/deployment/deploy-engine/provision.ts`, `src/deployment/deploy-engine/execute.ts`, `src/utils/aws-clients.ts`. When `AuthorizeSecurityGroupIngress` answered `InvalidPermission.Duplicate`, the create treated it as success and recorded the existing rule as the stack's, so `cdkd destroy` later revoked a rule added by hand or by another stack. The rule is now adopted only when this stack's rollback journal shows the same logical id attempted the same rule, with no later delete of it (a re-run after a failed or interrupted deploy, including one whose earlier attempt got no definite answer from AWS), or during a rollback replay; otherwise the deploy refuses, naming the existing `sgr-` id with a revoke command. The journal is read only on that duplicate path, and a refused op (or an Authorize AWS provably did not apply, judged per send: the Authorize is sent without SDK retries) is journaled without its attempted properties, so the refusal itself never reads as a prior attempt on the next deploy and `cdkd rollback --revert-failed` never reverts an update from the refused rule; it re-authorizes the previous rule the refused update had revoked. Deleting a rule now revokes it by its recorded `sgr-` id (a stale id: the one live rule matching its identity and description), and a revoke by properties no longer sends the description: a recorded description the live rule lacked made AWS answer not-found, read as already deleted.
