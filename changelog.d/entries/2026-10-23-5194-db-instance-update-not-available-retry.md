- **An RDS, Neptune or DocDB DB instance update that AWS refuses because the instance is not `available` is retried once it reads `available` again (issue [#5194](https://github.com/go-to-k/cdkd/issues/5194))** -- `src/provisioning/providers/db-instance-modify-retry.ts` (new), `src/provisioning/providers/neptune-provider.ts`, `src/provisioning/providers/docdb-provider.ts`, `src/provisioning/providers/rds-provider.ts`, and a new unit file. A deploy that changed a DB cluster (for example by removing its `VpcSecurityGroupIds`) and a member instance together could fail with `Database instance is not in available state.`: the cluster change moves the member to `modifying` a moment after the cluster update returns, and the instance's `ModifyDBInstance` was sent before that showed up. CloudFormation lets the cluster change settle first, so the same template succeeded there. Now only that refusal (`InvalidDBInstanceStateFault` / `InvalidDBClusterStateFault` with the not-available wording) is retried. cdkd waits out any transitional status and resends, for up to 30 minutes or what `--resource-timeout` leaves, whichever is less. A terminal status (`failed`, `incompatible-*`, ...) fails at once and names the status. An update AWS accepts makes no call beyond the one `ModifyDBInstance`. A modify AWS answered with success is never resent; a request the SDK replayed after a lost response can be resent once with the same values.
