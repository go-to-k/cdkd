- **A reverse-replacement refusal in a nested child's own rollback now names the child stack in its `cdkd rollback --orphan` command (issue [#3859](https://github.com/go-to-k/cdkd/issues/3859))** -- `src/deployment/rollback-executor.ts` (`orphanRemedy`, `RollbackExecutorContext.nestedChildStack`), `src/deployment/deploy-engine.ts`, with unit tests in `tests/unit/deployment/rollback-executor-retain-new-resource.test.ts`, `tests/unit/deployment/deploy-engine-rollback-context.test.ts` and `tests/unit/cli/commands/rollback.test.ts`. When a nested child's deploy failed and its own in-process rollback hit one of the two refusals (a replacement whose old type cannot be routed, or a name collision under `UpdateReplacePolicy: Retain`), the refusal ended on `To orphan it: cdkd rollback --orphan <id>`. That command names no stack, so it resolved to the parent, whose rollback never replays the child's failure segment. The id was then either ignored or matched a parent resource of the same logical id, whose revert it skipped. The command now reads `cdkd rollback '<parent>~<child>' --orphan <id>`; a child name the gate will not print is a quoted hole, explained in the prose. A top-level stack's remedy is unchanged.
