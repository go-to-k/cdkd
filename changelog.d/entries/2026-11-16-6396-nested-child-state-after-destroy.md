- **`cdkd destroy` now retires a nested child's record when the child failed its first deploy (issue [#6396](https://github.com/go-to-k/cdkd/issues/6396))** -- `src/cli/commands/destroy-runner/child-records.ts` (new), `src/cli/commands/destroy-runner/run.ts`, `src/cli/commands/destroy-runner/under-lock.ts`, `src/state/s3-state-backend/listing.ts`. When a nested stack's first deploy failed inside the child, the child rolled back to an empty record at `cdkd/<Parent>~<Child>/<region>/state.json` (with a rollback journal), but the parent's `AWS::CloudFormation::Stack` row recorded no physical id. The parent's destroy then printed `✓ State deleted` for the parent only, and the child's record and journal outlived it, still listed by `cdkd state list`. After deleting the parent's record, `cdkd destroy` and `cdkd state destroy` now list the parent's `<Parent>~*` records in its region with one prefix-scoped request, and delete each one that names this parent and holds nothing (no resource, rollback orphan, superseded resource or journaled orphan). The delete takes the child's own lock and re-checks every guard, the same way an empty top-level record is deleted. A child record that still holds anything is kept and named in a warning, never destroyed. Integ fixture: `tests/integration/nested-child-first-deploy-failure`.
