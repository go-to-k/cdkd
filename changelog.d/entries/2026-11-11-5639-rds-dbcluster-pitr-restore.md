- **The SDK provider restores an `AWS::RDS::DBCluster` to a point in time (issue [#5639](https://github.com/go-to-k/cdkd/issues/5639))** -- `src/provisioning/providers/rds/cluster-restore.ts` (new) and `cluster-create.ts` beside it, `rds-provider.ts`, `rds/drift.ts`, `src/provisioning/restore-source-guard.ts`, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, a new unit file, the RDS wire cases, and a new `rds-dbcluster-pitr-restore` integ. Before, a cluster declaring `SourceDBClusterIdentifier`, `RestoreToTime`, `RestoreType` or `UseLatestRestorableTime` routed through Cloud Control. Now a non-empty source makes the create a `RestoreDBClusterToPointInTime` with the members CloudFormation's handler puts on it, after reading the source cluster (a cross-account ARN is looked up among shared clusters) and refusing the encryption combinations CloudFormation refuses. Once the cluster is `available` (waited for under `--no-wait` too), the follow-up `ModifyDBCluster` CloudFormation sends applies the declared parameter group, retention (1 when absent), windows, deletion protection, master password and the rest, then a declared Data API is turned on. A `RestoreToTime` that Java's `ZonedDateTime` cannot parse is refused before any call, as CloudFormation refuses it; `UseLatestRestorableTime: true` wins over a `RestoreToTime`. The restored cluster keeps its source's engine, version and master user, and a warning names any the template declares otherwise. All four keys are create-only, so a change replaces the cluster, and a replacement restoring from itself is refused. Resources already deployed through Cloud Control stay there.
