- **A template timestamp with no offset (`2026-01-01T00:00:00`) is now read as UTC, as CloudFormation reads it, instead of in the deployer's local time zone (issue [#5311](https://github.com/go-to-k/cdkd/issues/5311))** -- new `src/utils/cfn-timestamp.ts`, used by `AWS::CloudWatch::AnomalyDetector` (`Configuration.ExcludedTimeRanges`, whose documented format has no offset), `AWS::Scheduler::Schedule` (`StartDate` / `EndDate`), `AWS::Budgets::Budget` (`TimePeriod`), `AWS::S3::Bucket` (lifecycle `ExpirationDate` / `TransitionDate`), `AWS::Pipes::Pipe` and `AWS::Lambda::EventSourceMapping` (`StartingPositionTimestamp`). JavaScript's `new Date()` reads such a string in the host's zone, so on a machine set to `Asia/Tokyo` the value sent to AWS moved nine hours earlier: an anomaly detector excluded the wrong window, and an S3 lifecycle date stopped being midnight UTC. Strings with `Z` or an offset, date-only strings and epoch numbers are unchanged. The S3 diff now also normalizes an offset-less lifecycle date, which it skipped before because its value depended on the host. CloudFormation's own reading was measured with a temporary stack: it stored `2026-01-01T00:00:00Z` for `2026-01-01T00:00:00`, with or without `MetricTimeZone`. Unit cases set `TZ` to a non-UTC zone and fail without the fix. A resource already deployed from a non-UTC host keeps its shifted value until that property next changes in the template (a Budget's drift now reports the difference); redeploy after touching the value to correct it.
