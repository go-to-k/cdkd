- **EFS access-point adoption also compares `PosixUser` and `RootDirectory` before adopting a conflicting access point (issue [#3894](https://github.com/go-to-k/cdkd/issues/3894))** -- `src/provisioning/providers/efs-provider.ts` (`createOrAdoptAccessPoint`, `samePosixUser`, `sameRootDirectory`), `docs/provider-rules.md`, with unit tests in `tests/unit/provisioning/efs-access-point-idempotency-token.test.ts`. When a retried `CreateAccessPoint` is refused with `AccessPointAlreadyExists`, cdkd reads the named access point back and adopts it. The adoption used to be confirmed only on the `ClientToken` and the `FileSystemId`, but EFS refuses a repeated token whether or not the repeat's parameters match (measured in #2442), so a token re-sent with a different POSIX user or root directory would have been adopted. The adoption now declines on either mismatch, naming the field but not its value. EFS's defaults are applied first -- an unset POSIX user reads back as absent or `null`, an omitted root as `/` -- so a default-root access point is still adopted. `SecondaryGids` order and a `755` versus `0755` mode spelling do not count as mismatches. No path sends a repeated token with different parameters today, so this is defense in depth.
