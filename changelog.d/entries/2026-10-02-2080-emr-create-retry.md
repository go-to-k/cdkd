- **An EMR cluster, instance fleet or instance group create that hits a 5xx now reports candidate orphans instead of duplicating silently (issue [#2080](https://github.com/go-to-k/cdkd/issues/2080), Plan C: EMR)** -- `src/provisioning/providers/{emr-cluster,emr-instance-fleet-config,emr-instance-group-config}-provider.ts`, `src/provisioning/providers/orphan-report.ts` (renamed from `apigateway-orphan-report.ts`, now shared), `docs/troubleshooting.md`. `RunJobFlow`, `AddInstanceFleet` and `AddInstanceGroups` mint their id and carry no idempotency token, so a 5xx whose request had succeeded left a second cluster (or TASK fleet / group) billing per instance-hour with no state record. These creates no longer let the AWS SDK retry a 5xx inside one call; the 5xx reaches cdkd's retry, which first lists what the failed attempt may have made and warns about each match created during that attempt: a live cluster of the same name, or a TASK fleet / group of the same name (any name when the template sets none) in the same cluster. Each match comes with a read command, then a command to run only after confirming: `terminate-clusters` (with a note to turn termination protection off first when the template turns it on and the candidate shows it), or a scale to zero for a fleet / group, which EMR cannot remove. Nothing is adopted, terminated or scaled. A cluster holds at most one MASTER and one CORE, so those trigger no lookup; nor does a throttle, a 4xx or IAM propagation. The lookup needs `elasticmapreduce:ListClusters` (clusters); without it cdkd warns and the create proceeds. A reset connection or timeout after the send is still retried inside the SDK and not reported (#3978 layer (b)). Tests: `tests/unit/provisioning/emr-create-retry-2080.test.ts`.
