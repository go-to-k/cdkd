- **A rollback that restores an updated resource in place now refreshes its drift baseline (issue [#6526](https://github.com/go-to-k/cdkd/issues/6526))** -- `src/deployment/rollback-executor/replay-observed-refresh.ts` (new), `src/deployment/rollback-executor/replay-revert.ts`, `src/deployment/rollback-executor/replay-failed.ts`, `src/deployment/read-current-state-context.ts` (moved from `src/cli/commands/drift/compare.ts`, which re-exports it). After a failed deploy, the in-deploy rollback and `cdkd rollback` used to keep the restored record's pre-deploy `observedProperties` verbatim. Where the restore's write made AWS generate a new value, such as the `Id` of an S3 lifecycle rule declared without one, every later `cdkd drift` reported drift nobody made, and `cdkd drift --revert` pushed the stale value back. Both in-place revert arms now read the resource back once after a successful restore, as a deploy's update does, with the same state-built sibling context `cdkd drift` reads with, and scrub the readback through the deploy capture's redaction before it replaces the baseline. The read runs only on the rollback path, never on an ordinary deploy. A record without a baseline, a refused or masked baseline, any `NoEcho` marking, a provider without `readCurrentState`, and a failed or empty read keep the previous baseline, as before; a failed read never fails the rollback. Integ fixture: `tests/integration/rollback-observed-baseline-refresh/`.
