- **A Kinesis stream create whose 5xx hid a server-side success is no longer replayed inside the AWS SDK and credited as somebody else's stream (issue [#3978](https://github.com/go-to-k/cdkd/issues/3978))** -- `src/provisioning/providers/kinesis-provider.ts` (`getCreateClient`) and a new unit file. `CreateStream` carries no idempotency token and was sent through a client with the SDK's default retry, so a 5xx whose request had succeeded was replayed inside one `send`, and the replay's `ResourceInUseException` surfaced from the deploy engine's FIRST attempt, read as a name another holder owns. `CreateStream` now goes through a dedicated client wrapped by `withoutServerErrorRetries`: the 5xx reaches the engine's retry, whose ambiguous-outcome latch (#3983) marks the replay's collision as possibly this create's own. What the user sees changes accordingly: a plain create now prints the replay advice (the holder is most likely this create's own stream) instead of "an earlier cdkd run left it behind", and a replacement surfaces the raw create error instead of `NAMED_REPLACEMENT_COLLISION`. A `CreateStream` 5xx that did NOT hide a success is now retried on the engine's logged schedule rather than the SDK's quick in-`send` retries. Every other Kinesis call keeps the full SDK retry, and a stream that existed before any ambiguous attempt is still a name collision. The stream is not adopted on that collision -- a name is not attribution. **Residual**: [#4639](https://github.com/go-to-k/cdkd/issues/4639), the other token-less name-unique creates, and the socket reset or timeout the SDK still replays.
