- **An "already exists" that the AWS SDK's own retry hits after a dropped connection is no longer credited to another holder (issue [#4639](https://github.com/go-to-k/cdkd/issues/4639), socket-reset residual)** -- `src/provisioning/providers/ambiguous-create.ts`, `docs/troubleshooting.md`. Every token-less create sent through a `withoutServerErrorRetries` client (the IAM, Lambda, EventBridge bus, ECR, data / streaming, Kinesis stream, CodeCommit, KMS, Cognito, AppSync and other sites) already refused the SDK's in-call replay of a 5xx. A socket reset, broken pipe or timeout after the request was sent was still replayed inside the same call, so when AWS had completed the first request, the replay's "already exists" reached the deploy engine as an ordinary name collision with someone else's resource. Every attempt that follows such an ambiguous one in the same call is now marked as a possible replay -- the same mark the engine sets after an ambiguous attempt of its own -- so the collision is reported as possibly this create's own, and a create that looks for an orphan after an ambiguous attempt (KMS, Cognito, AppSync, API Gateway, EMR, EC2, ECS, DLM, Lambda layers and event source mappings) now looks after such a call too. The SDK still retries the reset itself, so a flaky network does not fail the deploy; a refused connection, an unresolved host and a throttle are not marked, since the request never reached the service or the service declared it did nothing. Residual: a replay that SUCCEEDS after a reset is still a second, unreported resource for a create that is not name-unique (KMS key, Cognito user pool, AppSync API, IAM access key; [#4687](https://github.com/go-to-k/cdkd/issues/4687)). The replayed-collision advice now names a dropped connection as a cause and says to confirm the holder is yours first, since a reset can precede the request. Tests: `tests/unit/provisioning/ambiguous-create.test.ts`, `deploy-engine-orphaned-name-collision.test.ts`.
