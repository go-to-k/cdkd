- **An `AWS::SNS::TopicPolicy` is now actually removed from a topic: on destroy, and from a topic an update drops from `Topics` (issue [#4610](https://github.com/go-to-k/cdkd/issues/4610))** -- `src/provisioning/providers/sns-topic-policy-provider.ts`. `delete()` sent an empty `Policy`, and SNS requires a policy on a topic, per CloudFormation's own TopicPolicy handler source. It read the resulting `Invalid parameter` rejection as "already removed", so the destroy reported the policy deleted and dropped its record while every topic kept the statement. It now writes each topic its default policy, as that handler does, and an `InvalidParameter` fails the delete. A record whose id is not a list of topic ARNs (the policy name an old `--migrate-from-cloudformation` recorded) falls back to the topic ARNs its `Topics` lists. When neither names one, the destroy now refuses, naming the by-hand reset and the `cdkd state orphan --resource` remedy. `update()` wrote only the new `Topics`, so a dropped topic kept the old statement; this is also what an in-place rollback of `Topics [T1] -> [T1,T2]` left on `T2`. It now resets each topic the record's id names that the new list drops, after writing the new list. A topic only the previous properties list (the attempted list a revert of a failed update passes) is reset only while its live policy matches that bag's `PolicyDocument` by content. Tests: `tests/unit/provisioning/sns-topic-policy-provider-dropped-topics-4610.test.ts`; integ arm in `tests/integration/sns-sqs-event/`.
