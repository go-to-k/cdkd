- **`cdkd local start-cloudfront` accepts `--from-state` again, `start-alb`'s `--from-state` reaches Lambda target groups, and `cdkd local invoke <image-fn> | jq` gets a clean payload (issues [#2600](https://github.com/go-to-k/cdkd/issues/2600), [#2429](https://github.com/go-to-k/cdkd/issues/2429), [#2525](https://github.com/go-to-k/cdkd/issues/2525), [#3393](https://github.com/go-to-k/cdkd/issues/3393); [#2602](https://github.com/go-to-k/cdkd/issues/2602))** -- `package.json` (cdk-local 0.151.1), `src/cli/commands/local-start-cloudfront.ts`, `local-start-alb.ts`, `local-invoke.ts`, `local-state-source.ts`, `src/utils/local-aws-failure.ts`. With cdk-local 0.151.0 consulting a host's state provider on every state-backed path, `start-cloudfront` no longer refuses `--from-state` / `--state-bucket` / `--state-prefix`: they resolve a deployed S3 origin's bucket, `cf.kvs()` stores and the Function URL / Lambda@Edge environment. Under `--role-arn` with no `--profile`, the startup warning now also names the engine's origin, KeyValueStore and `${AWS::AccountId}` reads under either state flag. `start-alb` drops its boot warning that `--from-state` misses a Lambda target, since it no longer does. cdk-local's own log lines now go through cdkd's logger, so `local invoke` keeps `Building container image ...` off stdout, `--verbose` reaches cdk-local's debug lines, and its warnings print in cdkd's format (no `WARN:` prefix) unless `CDKL_LOG_LEVEL` / `CDKL_LOG_STREAM` is set. Bundled-engine fixes picked up by the bump: the `start-cloudfront --help` text says Lambda@Edge runs locally, a `--profile` name is rendered safely in cdk-local's messages, and a `--verbose` build line masks `--build-arg` and cache-credential values.
