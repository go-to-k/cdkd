- **One stack name deployed under two state backends no longer takes over, and then deletes, the other deployment's resources (issue [#4705](https://github.com/go-to-k/cdkd/issues/4705))** -- `src/deployment/{generated-name-guard,kept-in-history,retained-readoption}.ts`, `src/state/{stack-registry,s3-state-backend,cross-prefix-stack-scan,lock-manager,create-token-ledger}.ts`, `src/provisioning/name-lookup.ts`, the name-adopting SDK providers, `src/cli/commands/{deploy,cross-prefix-gate,destroy-runner,destroy,state,rollback,import,force-unlock}.ts`. A second deployment of the same stack under another `--state-prefix`, `--state-bucket` or account's bucket was handed the first one's SQS queue and log group (generated names derive from the stack name), and its rollback deleted the queue. Now a create of a type whose API hands back or overwrites an existing name (queue, topic, log group, alarm, rule, S3 bucket, ECS cluster, load balancer, target group, state machine) reads its generated name exactly first and refuses (`GENERATED_NAME_HELD`) unless this stack's state, journal, intent ledger, `retained.json` (what it kept under this prefix) or own history names the holder; about one round trip, none on a redeploy. In one bucket, a marker `_cdkd-registry/<region>/<stack>.json` names the stack's prefix: a first deploy claims it, and destroy, state destroy, rollback, a destructive plan and the automatic rollback's deletes refuse a stack another prefix holds. A record or stale marker from before pays one prefix listing, then claims. A 403 warns and continues. Residual: a cross-bucket pair formed before this version keeps both records. Docs: `docs/state-store.md`. Tests: `tests/unit/**/*4705*.test.ts`; integ `cross-backend-same-stack`, `cross-backend-same-stack-migration`, `perf-cross-backend-check`.
