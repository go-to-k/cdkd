- **One stack name deployed under two state backends no longer takes over, and then deletes, the other deployment's resources (issue [#4705](https://github.com/go-to-k/cdkd/issues/4705))** -- `src/deployment/generated-name-guard.ts`, `src/state/stack-registry.ts`, `src/state/{s3-state-backend,cross-prefix-stack-scan}.ts`, `src/provisioning/name-lookup.ts`, the name-adopting SDK providers, `src/cli/commands/{deploy,cross-prefix-gate,destroy-runner,destroy,state,rollback,import}.ts`. cdkd-generated names derive from the stack name and logical id, so a second deployment of the same stack under another `--state-prefix`, `--state-bucket` or account's bucket was handed the first one's SQS queue and log group, and its failed deploy's rollback deleted the queue. Now a create of a type whose API hands back or overwrites an existing name (queue, topic, log group, alarm, EventBridge rule, S3 bucket, ECS cluster, load balancer, target group, state machine) looks its generated name up first and refuses (`GENERATED_NAME_HELD`, CloudFormation-style) unless this stack's state, rollback journal, create-token ledger or `retained.json` (what a destroy under this prefix kept) names the holder. The lookups start once the plan is known, batched per type, about one round trip; a redeploy makes none. Within one bucket, a marker `_cdkd-registry/<region>/<stack>.json` names the stack's prefix: a first deploy claims it, and destroy, state destroy, rollback, a destructive plan and the automatic rollback's deletes refuse a stack another prefix holds, pointing at `cdkd state orphan`. A record that predates the marker pays one prefix listing, then claims it. A 403 warns and continues. Residual: a cross-bucket pair formed before this version keeps both records. Docs: `docs/state-store.md`. Tests: `tests/unit/**/*4705*.test.ts`; integ `cross-backend-same-stack`, `cross-backend-same-stack-migration`, `perf-cross-backend-check`.
