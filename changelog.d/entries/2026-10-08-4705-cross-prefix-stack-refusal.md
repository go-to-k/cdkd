- **`cdkd deploy`, `cdkd destroy`, `cdkd state destroy` and `cdkd rollback` refuse a stack the state bucket also records under another `--state-prefix` (issue [#4705](https://github.com/go-to-k/cdkd/issues/4705))** -- `src/state/cross-prefix-stack-scan.ts`, `src/state/s3-state-backend.ts`, `src/cli/commands/{deploy,cross-prefix-gate,destroy-runner,destroy,state,rollback}.ts`, `src/deployment/{deployment-approval,rollback-executor,deploy-engine/*}.ts`. A stack name is one deployment per account and region, as in CloudFormation: cdkd-generated names derive from the stack name and logical id, so a second deployment of the same stack name under another prefix was handed the first one's SQS queue and log group, and its failed deploy's rollback deleted the queue. A stack's first deploy under a prefix now checks the bucket's other prefixes and refuses before any provider call, naming the other prefix and the remedies; a later deploy is checked, before any approval prompt, only when its plan deletes, replaces or may replace a resource, or updates a nested stack; an ordinary redeploy lists nothing. A replacement found only on a readback is checked too (a refusal keeps the resource, exit 2), and a failed deploy's automatic rollback keeps a created resource another record may hold. Destroy, state destroy and rollback refuse the same pair and point at `cdkd state orphan`. Only a record that can own a resource blocks; a failed first deploy's empty leftover is named in a note. A successful deploy keeps (exit 2) a journaled orphan another prefix may hold. A 403 warns and continues. Not detected, and documented as unsupported: another bucket, a prefix with a `/` before its end, and two first deploys at the same moment. Docs: `docs/state-store.md` (the contract), `docs/concepts.md`. Tests: `tests/unit/**/*4705*.test.ts`; integ `cross-backend-same-stack`, `cross-backend-same-stack-migration`.
