- **An S3 bucket create no longer adopts a bucket already holding its explicit `BucketName` on the paths the deploy engine's name lookup does not cover (issue [#4684](https://github.com/go-to-k/cdkd/issues/4684))** -- `src/provisioning/providers/s3-bucket-provider.ts`. Defense in depth behind the engine's lookup before a plain create (#4180) and a renamed replacement (#3937). A create the lookup does not cover, or a bucket made between the lookup and `CreateBucket`, took S3's `BucketAlreadyOwnedByYou` (or, in us-east-1, the legacy 200 that resets the bucket's ACLs) as success. It then configured that bucket and recorded it as the stack's, for a later destroy to delete. The uncovered creates are a replacement keeping its name and a rollback's re-create of a replaced bucket. The provider now refuses an explicit name held by a bucket this create did not make, in us-east-1 before the send. The refusal names the bucket, points at `cdkd import`, and applies nothing. It is non-retryable and marked a name collision, so a same-name replacement fails as CloudFormation's does, without reconfiguring the old bucket first, or uses `--replace`, and a rollback's reverse replacement refuses a bucket a stranger took. A generated name is still adopted (#4345). The #4639 ambiguous-create refusal now points an explicit name at `cdkd import` instead of a re-run. Tests: `tests/unit/provisioning/providers/s3-bucket-explicit-name-held-4684.test.ts`, `s3-bucket-create-retry-4639.test.ts`; integ: `s3-lifecycle` phase 2d.
