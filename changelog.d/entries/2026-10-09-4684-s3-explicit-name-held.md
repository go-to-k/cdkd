- **An S3 bucket create no longer adopts a bucket already holding its explicit `BucketName` on the paths the deploy engine's name lookup does not cover (issue [#4684](https://github.com/go-to-k/cdkd/issues/4684))** -- `src/provisioning/providers/s3-bucket-provider.ts`. Defense in depth behind the engine's lookup before a plain create (#4180) and a renamed replacement (#3937). A create the lookup does not cover (a replacement keeping its name, a rollback's re-create of a replaced bucket), or a bucket made between the lookup and `CreateBucket`, took `BucketAlreadyOwnedByYou` (or, in us-east-1, the legacy 200 that resets the bucket's ACLs) as success, configured that bucket and recorded it for a later destroy to delete. The provider now refuses an explicit name a bucket already holds, in us-east-1 before the send, asking the account's bucket list when the location lookup cannot answer. The refusal names the bucket, points at `cdkd import` and applies nothing. It is marked a name collision: a same-name replacement fails as CloudFormation's does (or uses `--replace`) without reconfiguring the old bucket first, a rollback's reverse replacement refuses a bucket a stranger took, and one whose new bucket holds the name deletes that new bucket and re-creates the old one instead of adopting it. A delete-first re-create still retries it while a deleted name is released. A generated name is still adopted (#4345). The #4639 ambiguous-create refusal now points an explicit name at `cdkd import`. Tests: `tests/unit/provisioning/providers/s3-bucket-explicit-name-held-4684.test.ts`, `s3-bucket-create-retry-4639.test.ts`; integ: `s3-lifecycle` phase 2d.
