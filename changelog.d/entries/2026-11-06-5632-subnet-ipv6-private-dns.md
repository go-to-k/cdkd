- **Subnet `AssignIpv6AddressOnCreation`, `Ipv6Native` and `PrivateDnsNameOptionsOnLaunch` use the SDK route** (Refs [#5632](https://github.com/go-to-k/cdkd/issues/5632)). A subnet declaring one used to auto-route through Cloud Control and pin `provisionedBy: 'cc-api'`; a NEW subnet now stays on `EC2Provider` (an existing cc-api record stays where it is). `Ipv6Native` goes to `CreateSubnet`, which may now omit `CidrBlock` when it is true; it is create-only, so a change replaces the subnet. `AssignIpv6AddressOnCreation` and each `PrivateDnsNameOptionsOnLaunch` member are written with `ModifySubnetAttribute` after the IPv6 block is associated (a disable before an IPv6 block change; an IPv6-only subnet's starting auto-assign is respected), each read back before the call returns. Removing either property, or one member, leaves the live value as it is, like `EnableDns64`. EC2 refuses to detach an IPv6 block while auto-assign, the AAAA record or DNS64 is on, so an `Ipv6CidrBlock` change or removal turns each off first and, when a new block attaches, back on unless the template now says false; with no block left they stay off, with a warning when the template still declares one true. An `Ipv6Native` subnet's block change is refused (EC2 cannot do it in place). Malformed values are refused before any call, a `"true"` / `true` spelling change is no change, and drift reads all three back. `EnableLniAtDeviceIndex` and `OutpostArn` (AWS Outposts only) are declared not wired by design and keep the Cloud Control route.
