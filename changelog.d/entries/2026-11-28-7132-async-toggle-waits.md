- **A deploy now waits for a DynamoDB Contributor Insights toggle, a DynamoDB Kinesis streaming destination and a Lambda event source mapping to settle, as CloudFormation does (issue [#7132](https://github.com/go-to-k/cdkd/issues/7132))** -- `src/provisioning/providers/dynamodb-settle-waits.ts`, `src/provisioning/providers/lambda-eventsource/settle-wait.ts`. `AWS::DynamoDB::Table` and `AWS::DynamoDB::GlobalTable` returned while Contributor Insights (table or index) read `ENABLING` / `DISABLING` and a newly enabled Kinesis destination read `ENABLING`, and `AWS::Lambda::EventSourceMapping` returned while the mapping read `Creating` / `Updating`. The drift baseline then recorded the transitional state, and a change AWS later refused (`FAILED`, `ENABLE_FAILED`) still deployed with exit 0. CloudFormation completes these resources only once the change has landed (measured in us-east-1), and a default deploy now waits the same way; `--no-wait` skips these waits and returns as before. A failure fails the resource with AWS's reason in `--verbose` output; a mapping that settles opposite to the `Enabled` it was sent draws a warning instead, since whether CloudFormation fails there is unmeasured. The wait is bounded and honors `--resource-timeout` and Ctrl-C, which report the change as not confirmed. A mapping whose create wait fails is recorded for `cdkd rollback --revert-failed`. The added time on a default deploy is the time CloudFormation spends on the same change (about 15 s for a mapping, 15-20 s for a Kinesis destination, 1-2 s for Contributor Insights).
