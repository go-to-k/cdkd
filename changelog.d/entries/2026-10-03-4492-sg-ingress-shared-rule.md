- **`cdkd deploy` no longer fails when two `AWS::EC2::SecurityGroupIngress` resources of one stack resolve to the same rule (issue [#4492](https://github.com/go-to-k/cdkd/issues/4492))** -- `src/provisioning/providers/ec2-provider.ts`, `src/deployment/stack-records-scope.ts`, `src/deployment/deploy-engine/execute.ts`, `src/deployment/deploy-engine/provision.ts`, `src/deployment/rollback-executor.ts`, `src/cli/commands/destroy-runner.ts`, `src/cli/commands/export.ts`. CDK cannot dedupe a rule whose port is a token, so an Aurora cluster with a `DatabaseProxy` on the same security group plus an explicit `addIngressRule(sg, Port.tcp(3306))` emits two rules AWS stores as one. Since #4393 the second create was refused as someone else's rule. It now records the existing rule when another record of the same stack holds it — a `SecurityGroupIngress` record with the same group, protocol, ports and source, or the group's own record declaring it inline — waiting for a twin created in the same deploy to finish first; CloudFormation accepts both. A rule recorded under a different `sgr-` id than the live one is still refused, as is a rule held by nothing in the stack. A delete, a rollback, a destroy and a security group update dropping the rule from its inline list leave it in place while a record that outlives the operation still holds it (a destroy's retained records, a deploy's records it does not delete); the last holder revokes it, and a second revoke finding it gone succeeds (one with no recorded rule id still warns that nothing was revoked). `cdkd export` refuses two such records, naming each other, since an import adopts a rule into one logical id. Tests: `tests/unit/provisioning/ec2-sg-ingress-sibling-holder.test.ts`, `tests/unit/deployment/stack-records-scope.test.ts`, `tests/unit/deployment/deploy-engine-stack-records-binding.test.ts`, `tests/unit/cli/destroy-runner-stack-records.test.ts`, `tests/unit/cli/export-sg-ingress-rule-id-backfill.test.ts`.
