- **`Ref` on an `AWS::S3Tables::Table` now resolves to the table ARN, as in CloudFormation (issue [#5316](https://github.com/go-to-k/cdkd/issues/5316))** -- `src/deployment/intrinsic-resolver/ref-values.ts`. cdkd resolved it to the table name: the trailing segment of the SDK route's `<tableBucketARN>|<namespace>|<name>` physical id, or the recorded `TableName` on the Cloud Control route (issue #974). A CloudFormation stack measured in us-east-1 returns the ARN, equal to `Fn::GetAtt TableARN` and unchanged across a `TableName` or `Namespace` change. cdkd now serves the recorded `TableARN` attribute for the SDK route and the physical id (which is the ARN) for the Cloud Control route. A table created before cdkd recorded `TableARN` (before v0.201.0) has its `Ref` read like `Fn::GetAtt TableARN`: `cdkd deploy` re-reads the table from AWS and records the ARN, and refuses the `Ref` when that read cannot supply one. A recorded value that is not an ARN falls back to the raw physical id, never the name. **Existing stacks:** a resource or output that read the `Ref` recorded the name, so the next `cdkd deploy` updates it to the ARN, as for any changed input (a replacement where the reading property is create-only); an export changes value too, and a stack importing it picks the ARN up on its own next deploy. Since the ARN survives a rename, the diff no longer re-provisions `Ref` readers when a table is renamed (`src/analyzer/diff-calculator.ts`). Unit cases in `tests/unit/deployment/intrinsic-functions.test.ts` and the `Ref` state-mask suites, which now use the recorded `TableARN`; the `s3-tables` integ asserts the ARN on both routes and adds a phase that seeds a reader with the table name and checks the redeploy rewrites it.
