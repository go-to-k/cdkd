- **`AWS::EC2::VPC` with `Ipv4IpamPoolId` / `Ipv4NetmaskLength` / `VpcEncryptionControl`, and `AWS::EC2::Instance` with `CpuOptions` / `HibernationOptions` / `InstanceInitiatedShutdownBehavior`, now deploy on the SDK path (issues [#5633](https://github.com/go-to-k/cdkd/issues/5633), [#5630](https://github.com/go-to-k/cdkd/issues/5630))** -- `src/provisioning/providers/ec2-provider.ts`, the regenerated coverage map, unit tests, the `ec2-vpc` and `ec2-instance` integ fixtures and the new `ec2-vpc-ipam` fixture. Before this change, a template that set any of these properties sent the whole resource through Cloud Control, which is slower and sticky. They are now sent on `CreateVpc` / `RunInstances`. A VPC with no `CidrBlock` takes its CIDR from the IPAM pool, and `Fn::GetAtt Vpc.CidrBlock` resolves to the allocated CIDR, after an update too. `InstanceInitiatedShutdownBehavior` changes in place. Removing it is refused, because CloudFormation fails that update ("No attributes specified"; measured). The other properties are create-only, so a change replaces the resource, and `cdkd drift --revert` refuses to revert one. A malformed value is refused before any AWS call. `cdkd drift` reads these properties back, with three gaps: `Ipv4IpamPoolId` is not read back, because `DescribeVpcs` does not report it; the exclusions of a `monitor` encryption control are not read back either, because AWS reports none; and `Ipv4NetmaskLength` and `InstanceInitiatedShutdownBehavior` are read back only when the template declares them. Deleting an IPAM-allocated VPC now waits, for up to 15 minutes, until the pool releases its allocation, so the pool CIDR can be deprovisioned next (`docs/cli-deploy-waits.md`). Resources already recorded as Cloud Control-provisioned stay on Cloud Control. The other `AWS::EC2::Instance` properties listed on #5630 still route through Cloud Control.
