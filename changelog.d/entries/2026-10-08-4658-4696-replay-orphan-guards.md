- **`cdkd rollback` and `cdkd destroy` no longer delete a journaled failed-CREATE orphan unless it is proven to be the resource the failed deploy made and no other stack's state record holds it** (`src/deployment/rollback-executor.ts`, `src/deployment/rollback-executor/{orphan-identity,journaled-orphans}.ts`, `src/cli/commands/{rollback,destroy-runner}.ts`, go-to-k/cdkd#4658, go-to-k/cdkd#4696). The replay deleted such an orphan by physical id alone, so it deleted a resource that a later `cdkd import` had adopted into another stack, and a resource that reused the name of an orphan deleted by hand. It now runs the success settle's checks, in its order and through its helpers (`askForeignHolder`, `createdResourceStillThere`).
  - **Name-keyed types:** a name-keyed type's live `resourceIdentity` must equal the one the CREATE journaled. Only a Kinesis stream and an RDS or DocumentDB cluster or instance journal one today. **Every other name-keyed type (an S3 bucket, a Lambda function, an IAM role, a DynamoDB table, an SQS queue, ...) has none, so its journaled orphan is now kept instead of deleted.** Types whose id AWS generates and never reuses are unaffected.
  - **Held, disproven, or no identity:** the orphan is a warned skip that names its physical id and says to delete it by hand if unused. `cdkd rollback` and `cdkd destroy` both exit 2.
  - **Unreadable:** if a record or the live identity cannot be read, the entry stays in the journal as a failed operation for a re-run. `--drop-failed` removes only the record.
  - **Gone:** an orphan AWS reports gone is settled with no delete.
  - **Automatic rollback:** it runs neither check. It acts inside the failed deploy, over that attempt's own operations.
  - **`--remove-protection`:** strips protection only from an orphan these checks cleared.
  - **Tests:** `tests/unit/deployment/journaled-orphan-replay-guards-4658-4696.test.ts` and the rollback and destroy suites; integ `rollback-command` steps O10 and O11.
