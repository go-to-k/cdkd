- **`cdkd rollback` and `cdkd destroy` no longer delete a journaled failed-CREATE orphan that another stack's state record holds, or whose name a different resource now uses** (`src/deployment/rollback-executor.ts`, `src/deployment/rollback-executor/orphan-identity.ts`, `src/deployment/rollback-executor/journaled-orphans.ts`, `src/cli/commands/rollback.ts`, `src/cli/commands/destroy-runner.ts`, go-to-k/cdkd#4658, go-to-k/cdkd#4696). The replay of a journaled proven orphan deleted it by physical id alone. So a resource a later `cdkd import` adopted into another stack was deleted, and so was a resource created under the name of an orphan the user had deleted by hand. The replay now runs the same checks as the success settle, in the same order and through the same helpers (`askForeignHolder`, `createdResourceStillThere`). If another stack's record holds the resource, or (for a name-keyed type) the live `resourceIdentity` differs from the journaled one or none was journaled, the orphan is kept as a warned skip that names its physical id: `cdkd rollback` exits 2, and `cdkd destroy` goes on to destroy the stack. If a record or the live identity cannot be read, the entry stays in the journal as a failed operation for a re-run. An orphan AWS reports gone is settled without a delete. The success settle passes on the orphans it has already proved, so they get no second identity read. The automatic in-process rollback gets neither check: it runs seconds after the failure and its identity is best-effort. `--remove-protection` now strips protection only from an orphan these checks cleared.
