- **A successful fix-forward deploy now deletes the FSx file system an earlier failed CREATE left under the same logical id (issue [#4606](https://github.com/go-to-k/cdkd/issues/4606))** -- `src/provisioning/providers/fsx-filesystem-provider.ts`. After `cdkd deploy --no-rollback` failed with an `AWS::FSx::FileSystem` already created (a journaled proven orphan: a file system whose wait failed and whose cleanup delete failed too) and the fixed template created a new one under the same logical id, the successful deploy warned, named the earlier one, exited `2` and left it in AWS, billed by the hour. `FSxFileSystemProvider` now answers `isSameResource` for every variant (Lustre / Windows / ONTAP / OpenZFS) from the `fs-` file system id FSx generates: the client must be in the stack's region and the record's file system must read back short of `DELETING` / `FAILED`, and the earlier one is then `different`, so the settle deletes it; equal ids are `same`. An unrecognised id form and a failed read stay `unknown` (the previous warning and exit `2`). An earlier file system already gone is named in one info line. Tests: `tests/unit/provisioning/fsx-same-resource-4606.test.ts`; integ `fsx-lustre` Phase 2c asserts the earlier file system deleted, the new one kept, exit `0`.
