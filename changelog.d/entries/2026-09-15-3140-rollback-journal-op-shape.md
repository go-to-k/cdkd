- **A planted `rollback-journal.json` whose operation carries a non-string `logicalId` is now refused by the parser instead of crashing `cdkd rollback` at its first lookup (issue [#3140](https://github.com/go-to-k/cdkd/issues/3140))** -- `src/types/rollback-journal.ts`. `parseRollbackJournal` validated only `journalVersion` and that `segments` was an array; every per-operation field was an unchecked cast, and the executor keys every lookup on `op.logicalId` -- so a numeric id coerced into the record named `'123'`, and an object whose `toString` is not callable threw a raw `TypeError` from `stateResources[op.logicalId]` after the lock was taken. The parser now refuses a segment that is not an object, an `operations` (or a present `failedOperations`) that is not an array, an operation that is not an object, and an operation whose `logicalId` is not a non-empty string, whose `resourceType` / `changeType` is not a string, or whose present `physicalId` is not a string. The refusal names the index and the TYPE (`segments[0].operations[1].logicalId must be a non-empty string (got number)`), never the value, so there is nothing to sanitize -- and names the way out (remove the stack's `rollback-journal.json`; `cdkd destroy` sweeps it too). The same text reaches `cdkd deploy`'s `Failed to write rollback journal` warning, since appending a segment parses the existing journal first. Every journal cdkd itself writes passes unchanged. The executor keeps its own `typeof` guard on the pasted `--orphan` remedy as defense-in-depth: the deploy engine's in-process rollback reaches it without this parser. Found by the round-5 security review of [#3104](https://github.com/go-to-k/cdkd/pull/3104).
