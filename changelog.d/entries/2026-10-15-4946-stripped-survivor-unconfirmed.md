- **A rollback no longer re-adopts the old resource of a replacement when the deploy's delete had already stripped it before AWS refused the delete (issue [#4946](https://github.com/go-to-k/cdkd/issues/4946))** -- `src/deployment/rollback-executor/replaced-survivor.ts`, `src/provisioning/delete-started.ts`. Several providers change a resource before the call that deletes it: an IAM role, user or group loses its policies, memberships and instance profiles, a managed policy is detached from every principal, an EventBridge rule loses its targets, a CloudFront distribution is disabled, an ECS service is scaled to 0, a CloudTrail trail stops logging, a VPC Lambda function is detached from its VPC, and so on. When AWS then refused the delete by name (an SCP denying `iam:DeletePolicy` but allowing the detach, for example) and a later resource failed the deploy, the rollback re-adopted the stripped resource in place of the working new copy, and the next `cdkd deploy` saw no difference to repair. Such a delete now marks its error, and the replacement journals `oldResourceMaySurvive: unconfirmed`: the rollback refuses that operation with the journal kept and offers `cdkd rollback --orphan`, as it already did for the same providers' own in-update replacement. A refusal before the delete changed anything still re-adopts the old resource. Providers changed: IAM role, managed policy, policy, user / group / `UserToGroupAddition`, instance profile, EventBridge rule and event bus, CloudFront distribution, CloudTrail trail, ECS service, Glue trigger, Lambda function, Route 53 hosted zone, RDS DB cluster (a global-cluster detach), DynamoDB global table, SQS queue policy and SNS topic policy. The `cdkd rollback` plan line for such an operation now also names a delete that only partly ran. No extra AWS call is made.
