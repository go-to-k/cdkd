- **A replaced resource is now deleted only after the rest of the deploy succeeds, so a failed deploy no longer loses what the old resource held (issue [#6374](https://github.com/go-to-k/cdkd/issues/6374))** -- `src/deployment/deploy-engine/replacement/delete-replaced.ts`. A create-first replacement deleted the old resource right after creating the new one, before the resources referencing it had moved. Deleting a container can delete its children: renaming a `ScheduleGroup` deleted every schedule in it at once. When the deploy then failed, the rollback re-created an empty group, and the schedules were gone for good. cdkd now deletes the old resource in a cleanup phase after every other change succeeds, as CloudFormation does. Until then it is kept in state, so a deploy killed first leaves it for the next deploy or `cdkd destroy`. A failed deploy never sends the delete, and its rollback (automatic or `cdkd rollback`) takes the old resource back. Four cases still delete right away, as before: a record holding a NoEcho value, an IAM inline policy, `UpdateReplacePolicy: Snapshot` without `--skip-final-snapshot` (the snapshot must not fall behind the data), and an old physical id another resource of the stack now records.
