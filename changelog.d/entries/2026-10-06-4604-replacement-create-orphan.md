- **A replacement's new resource that was created and then failed is now deleted by every rollback path, and an in-place update that changed a physical id is now rolled back in place (issues [#4604](https://github.com/go-to-k/cdkd/issues/4604), [#4615](https://github.com/go-to-k/cdkd/issues/4615))** -- `src/deployment/deploy-engine/{execute,update-in-place}.ts`, `src/deployment/deploy-engine.ts`, `src/deployment/rollback-executor.ts`, `src/deployment/rollback-executor/{plan,journaled-orphans,replay-reverse-replacement,types}.ts`, `src/cli/commands/rollback.ts`, `src/types/rollback-journal.ts`, provider warnings. A provider that proved it made a resource before its create failed (#1710) was journaled only on a first-time CREATE; when the same create ran as a replacement's new resource, nothing recorded it and it stayed in AWS, billed and untracked. It is now journaled beside the replacement's UPDATE, naming the record it was replacing, and the automatic rollback, `cdkd rollback`, `cdkd destroy` and a later successful deploy delete it per its `DeletionPolicy` without touching that record; a record that names anything else still skips it with a warning. A rollback's own re-create that leaves such a resource deletes it there (kept and named under `Retain` / `Snapshot`, or when the delete fails). Separately, the rollback treated every completed UPDATE whose physical id changed as a replacement, so an in-place SQS `QueuePolicy` or SNS `TopicPolicy` update that moved its id was undone by re-creating the old policy and then deleting the "new" one, which removed the policy it had just written; the journal now records the provider's `wasReplaced`, and an in-place update is reverted in place (a journal from an older cdkd keeps the old reading). Tests: `tests/unit/deployment/{replacement-create-orphan,deploy-engine-rollback-journal}.test.ts`, `tests/unit/types/rollback-journal.test.ts`; integ Phase P in `tests/integration/rollback-command/`.
