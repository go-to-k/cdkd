- **The SDK provider sends `AdditionalStorageVolumes` for `AWS::RDS::DBInstance` (issue [#5640](https://github.com/go-to-k/cdkd/issues/5640))** -- a new `src/provisioning/providers/rds/additional-storage-volumes.ts`, its callers in `instance-create.ts`, `instance-update.ts`, `read-state.ts` and `drift.ts` beside it, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, a new unit file, the RDS wire cases, and a new `rds-dbinstance-additional-storage-volumes` integ. Before, an instance declaring additional storage volumes (RDS for SQL Server and Oracle) routed through Cloud Control. cdkd now sends what CloudFormation was measured to send: the list on `CreateDBInstance`; on an update, only the changed and new volumes, each in full, and `SetForDelete` for each volume removed from the list, or every volume when the property is removed (which deletes those volumes, as under CloudFormation); then it waits for the instance to settle, unless `--no-wait`. No request shrinks a volume: a rollback keeps a grown size, and a volume that storage autoscaling grew keeps its live size. `drift --revert` leaves a volume added outside cdkd in place with a warning instead of deleting it. A malformed list is refused before any call. `cdkd drift` compares the volumes by name in any order, by the members the template declares. Resources already deployed through Cloud Control stay there.
