- **Stack selection now matches the AWS CDK CLI: patterns use the hierarchical id with path-aware globs, and `--all` selects top-level stacks only (issue [#4474](https://github.com/go-to-k/cdkd/issues/4474))** -- `src/utils/glob-match.ts`, `src/cli/stack-matcher.ts`, `src/synthesis/assembly-reader.ts`, and `src/cli/commands/deploy.ts`, `destroy.ts` and `diff.ts`, with unit tests beside each. A pattern without `/` used to match only the physical CloudFormation name, so `cdkd deploy Api` missed `new Stack(app, 'Api', { stackName: 'prod-api' })`, and `*` crossed `/`. Every pattern now matches the stack's hierarchical id (its CDK display path), as `cdk` does: `*` stays within one `/` segment, so `'*'` selects the top-level stacks only and `'MyStage/*'` one Stage's stacks, and `'**'` selects every stack. An EXACT physical name still selects its stack as a cdkd extension when no hierarchical id matches, but a glob no longer matches physical names. **`--all` changed scope:** on `deploy`, `destroy` and `diff` it selects the top-level stacks only, as `cdk deploy --all` / `cdk destroy --all` do; the run names the Stage stacks it left out with the `'MyStage/*'` / `'**'` patterns, and a stage-only app is refused. `publish-assets --all` and `scrub --all` still cover every stack. **Re-audit scripts that pass physical names or globs to `cdkd destroy` / `cdkd deploy`:** a pattern without `/` now matches CDK ids first, so it can select a different stack than before, and `'*'` or `'MyStage-*'` no longer reaches Stage stacks; both commands warn in one line naming any stack the old rule would have selected (including one `'MyStage/*'` used to reach deeper than one segment).
