- **An `AWS::DocDB::DBCluster` that declares `GlobalClusterIdentifier` deploys on the SDK route (go-to-k/cdkd#5628)** -- `src/provisioning/providers/docdb-provider.ts`. Such a template was refused pre-flight, since the type has no Cloud Control handlers. The cluster now joins the named global cluster through `CreateDBCluster`. An update follows what a real CloudFormation A/B measured: removing the property, or setting it to `""`, detaches the cluster from its global cluster in place (`RemoveFromGlobalCluster`, then a wait until it is available again), and adding it or naming another global cluster is refused before any write, as CloudFormation refuses it for a member and a non-member cluster alike, unless the cluster is already part of that global cluster; joining another one takes a replacement. A rollback replay or `cdkd drift --revert` changes no membership: one that would re-join, or would detach a membership cdkd only found and never added, warns and keeps the cluster where it is. A cluster in a global cluster is detached before its delete, as cdkd already does for an RDS cluster in a global cluster; one the global cluster no longer lists is deleted without a detach, and a primary whose global cluster still has other members fails at once, naming them. A cluster whose deletion protection is still on is not detached before a delete, since the detach cannot be undone and the delete would fail. An update also sends `EngineVersion` only when it changed: AWS refuses any `EngineVersion`, the cluster's own included, on a cluster with no healthy primary instance, so re-sending an unchanged one failed every update of such a cluster. The new `docdb-global-cluster` integration fixture covers the create, the in-place removal, both refusals and the destroy.
