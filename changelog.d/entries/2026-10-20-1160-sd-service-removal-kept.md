- **`AWS::ServiceDiscovery::Service`: a `Description`, `DnsConfig` or `HealthCheckConfig` removed from the template now follows CloudFormation (issue [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/servicediscovery-provider.ts`. `UpdateService` replaces its body, and cdkd sent it whenever any of the three was declared, so a removal on its own cleared a removed `Description` / `HealthCheckConfig` and failed the deploy for a removed `DnsConfig` (`Service dns config cannot be null`). CloudFormation A/Bs on the issue showed it sends the update only when a declared `Description` or `HealthCheckConfig` changed, with the declared values as they are; cdkd now does the same: a removal on its own keeps the value, and beside such a change a removed field is cleared (a removed `DnsConfig` is refused by AWS, as for CloudFormation). Deliberate divergence: CloudFormation drops a `DnsConfig.DnsRecords`-only change (a TTL); cdkd applies it and keeps any removed `Description` / `HealthCheckConfig` from the live service. Known divergence: an unchanged `Description` recorded as any dynamic reference (`{{resolve:...}}`) or a NoEcho `***` counts as changed, so a `HealthCheckConfig` removed beside it is cleared ([#5112](https://github.com/go-to-k/cdkd/issues/5112)). The type is audited into `removalHandledInUpdate`. Tests: `tests/unit/provisioning/providers/servicediscovery-provider.test.ts`; the `servicediscovery` integ fixture gains three removal phases.
