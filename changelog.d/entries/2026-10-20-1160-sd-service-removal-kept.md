- **`AWS::ServiceDiscovery::Service`: a `Description`, `DnsConfig` or `HealthCheckConfig` removed from the template now follows CloudFormation (issue [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/servicediscovery-provider.ts`. `UpdateService` replaces its `ServiceChange` body rather than merging it, and cdkd sent it whenever any of the three was declared, so a removal on its own cleared a removed `Description` or `HealthCheckConfig` and failed the deploy for a removed `DnsConfig` (`Service dns config cannot be null`). Two CloudFormation A/Bs (on the issue: issuecomment-6272137682 and issuecomment-6281592365) showed CloudFormation sends the update only when a declared `Description` or `HealthCheckConfig` changed, with the declared values as they are. cdkd now does the same: a removal on its own keeps the value; beside a `Description` / `HealthCheckConfig` change a removed field is cleared, and a removed `DnsConfig` is refused by AWS as it is for CloudFormation. One deliberate divergence: CloudFormation drops a change to `DnsConfig.DnsRecords` alone (a TTL, say); cdkd applies it, keeping any removed `Description` / `HealthCheckConfig` from the live service so their final state still matches CloudFormation. The comparison is against the state record, which keeps a secret dynamic reference or `NoEcho` value redacted while the template value is resolved; such a leaf counts as changed, so a real change is never dropped. That leaves one known divergence: an unchanged secret- or NoEcho-sourced `Description` with a `HealthCheckConfig` removed beside it clears the health check where CloudFormation keeps it ([#5112](https://github.com/go-to-k/cdkd/issues/5112) tracks a template-to-template comparison). The type is also audited into `removalHandledInUpdate`. Tests: `tests/unit/provisioning/providers/servicediscovery-provider.test.ts`; the `servicediscovery` integ fixture gains three removal phases.
