- **`AWS::ServiceDiscovery::Service`: a `Description`, `DnsConfig` or `HealthCheckConfig` removed from the template now follows CloudFormation (issue [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/servicediscovery-provider.ts`. `UpdateService` replaces its `ServiceChange` body rather than merging it, and cdkd sent it whenever any of the three was declared, so a removal on its own cleared a removed `Description` or `HealthCheckConfig` and failed the deploy for a removed `DnsConfig` (`Service dns config cannot be null`). Two CloudFormation A/Bs (on the issue: issuecomment-6272137682 and issuecomment-6281592365) showed CloudFormation sends the update only when a declared `Description` or `HealthCheckConfig` changed, with the declared values as they are. cdkd now does the same: a removal on its own keeps the value; beside a `Description` / `HealthCheckConfig` change a removed field is cleared, and a removed `DnsConfig` is refused by AWS as it is for CloudFormation. One deliberate divergence: CloudFormation drops a change to `DnsConfig.DnsRecords` alone (a TTL, say); cdkd applies it, keeping any removed `Description` / `HealthCheckConfig` from the live service so their final state still matches CloudFormation. The comparison reads a recorded secret dynamic reference or `NoEcho` mask as unchanged, since the state record keeps those redacted while the template value is resolved; otherwise an unchanged secret-sourced `Description` would read as a change and clear a `HealthCheckConfig` removed beside it. The type is also audited into `removalHandledInUpdate`. Tests: `tests/unit/provisioning/providers/servicediscovery-provider.test.ts`; the `servicediscovery` integ fixture gains three removal phases.
