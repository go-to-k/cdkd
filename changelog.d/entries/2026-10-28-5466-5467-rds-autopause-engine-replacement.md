- **An Aurora Serverless v2 cluster's `SecondsUntilAutoPause` now reaches AWS, and a changed DBCluster / DBInstance `Engine` replaces the resource as CloudFormation does (issues [#5466](https://github.com/go-to-k/cdkd/issues/5466), [#5467](https://github.com/go-to-k/cdkd/issues/5467))** -- `src/provisioning/providers/rds-provider.ts`, `src/analyzer/replacement-rules.ts`. `ServerlessV2ScalingConfiguration.SecondsUntilAutoPause` was never sent on `CreateDBCluster` / `ModifyDBCluster`, so a declared auto-pause delay was ignored, and any later cluster update reset it to AWS's 300-second default. It is now sent on create and update, read back for drift, and compared only where the template declares it. A removed value resets to the default, as measured against CloudFormation. A changed `Engine` (for example aurora-mysql to aurora-postgresql, or mysql to mariadb) used to report the deploy done while the resource kept its old engine. It now replaces the cluster or instance, as CloudFormation does (measured). Both types are stateful, so the replacement needs `--force-stateful-recreation`. The engine changes CloudFormation's RDS handlers treat as in place still update in place: `aurora` to `aurora-mysql` on either type, and on an instance `oracle-se` / `oracle-se1` to `oracle-se2` and the Oracle non-CDB to CDB conversions, which send the new `Engine` on `ModifyDBInstance`. A changed cluster `MasterUsername` still applies nothing: CloudFormation keeps the live user too (measured).
