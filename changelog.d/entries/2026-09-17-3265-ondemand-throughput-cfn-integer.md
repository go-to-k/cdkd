- **Every `AWS::DynamoDB::Table` `OnDemandThroughput` ceiling now reaches AWS as a NUMBER, and a spelling CloudFormation rejects is dropped and named instead of forwarded (issue [#3265](https://github.com/go-to-k/cdkd/issues/3265))** -- `src/provisioning/providers/dynamodb-table-provider.ts`, `tests/unit/provisioning/dynamodb-table-provider-cfn-integer.test.ts`. Both members are `Long` in the SDK model, and all FOUR send sites forwarded the declared block verbatim, so a CFn-legal `MaxReadRequestUnits: '100'` went out as the STRING `"100"` and the request failed, while a `' 100 '` / `'0x64'` / `'1e2'` CloudFormation refuses the template for went out unchanged. All four now read `coerceCfnInteger`, the measured DynamoDB Integer grammar every sibling capacity property has used since issue [#3147](https://github.com/go-to-k/cdkd/issues/3147). FOUR, not the three the issue enumerated: `create()`'s per-index forward is a CAST of the whole `GlobalSecondaryIndexes` array, invisible to any grep for the property name -- the blind spot that also hid its `ProvisionedThroughput` twin. A rejected spelling drops the MEMBER and never the block, keeping a sibling the template spelled legally and leaving the drift-side "would cdkd send this block" gate unchanged. The announcement is a SEPARATE sentence from the capacity one on purpose: both ceiling members are OPTIONAL, so DynamoDB does not reject the request -- the deploy succeeds with no maximum applied for that half, and the warning says so rather than promising a failure that never comes. That success is also the residual the capacity twin escapes by failing at AWS: state keeps the declared spelling and `cdkd drift` reports it until the template is fixed, tracked as issue [#3286](https://github.com/go-to-k/cdkd/issues/3286). The two per-index `Update` actions send no ceiling at all -- a missing send, issue [#3287](https://github.com/go-to-k/cdkd/issues/3287).
