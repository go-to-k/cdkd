- **A replacement that moves its explicit name off the one the old resource holds now creates before it deletes, and a rename onto a name a name-adopting create would take over is refused before anything changes (issues [#3931](https://github.com/go-to-k/cdkd/issues/3931), [#3937](https://github.com/go-to-k/cdkd/issues/3937); ELBv2 and ECS remain on #3937)** -- `src/deployment/deploy-engine.ts` (`checkedReplacementNameChange`, `createFirstThenDeleteOld`, `deleteReplacedAfterCreate`), `src/deployment/replacement-name-holder.ts` (`replacementNameProbe`), `docs/_contents/cli-deploy-safety.md`, two unit files and the new `tests/integration/replacement-rename-onto-holder/` fixture. The UPDATE-not-supported fallback and the `--recreate-via-cc-api` / `--recreate-via-sdk-provider` recreate used to delete the old resource first even when the template also renamed it; when another resource held the new name the create collided and the managed resource was gone. When the name is KNOWN to differ, both now create first: a collision fails with `NAMED_REPLACEMENT_COLLISION` and nothing deleted, and the old resource is deleted only once its replacement exists (a failed delete warns, like the property-driven cleanup). SQS queues, SNS topics, Step Functions state machines, EventBridge rules, CloudWatch alarms and S3 buckets hand back, overwrite or adopt a resource already holding the name, so such a rename "succeeded" with a stranger's resource, deleted the old one, and recorded the stranger's for a later `cdkd destroy` to delete. On the SDK route the new name (a rule's new bus, or a `Type` change onto one of these types, included) is now looked up first; a resource found there, or a lookup that cannot run, fails the deploy with nothing created or deleted. Names compare exactly, unless the type folds case. The third bullet of #3931 (`--replace` after a dropped name) was closed by #4028's holder proof.
