- **A replacement renaming an ECS cluster onto a name an ACTIVE cluster already holds is refused before anything changes, and `cdkd import` no longer adopts a deleted cluster (issue [#3937](https://github.com/go-to-k/cdkd/issues/3937); ELBv2 remains there)** -- `src/deployment/replacement-name-holder.ts` (`NAME_ADOPTING_SDK_CREATE_TYPES`), `src/provisioning/providers/ecs-provider.ts` (the cluster `import()`), `docs/cli-deploy-safety.md`, unit cases and an ECS arm in `tests/integration/replacement-rename-onto-holder/`. `CreateCluster` returns an existing ACTIVE cluster of the requested name instead of refusing (measured), so a rename onto a stranger's cluster "succeeded", deleted the stack's own cluster and recorded the other one for a later `cdkd destroy` to delete. The SDK route now looks the new `ClusterName` up first, as for the other name-adopting types; a cluster found there, or a lookup that fails, fails the deploy with nothing created or deleted. The lookup is the cluster `import()`, which returned a cluster `DescribeClusters` still lists as `INACTIVE` after its delete; that one is now absent, since its name is free to create again, and any other status still counts as the holder; a listing with no cluster and a failure reason other than `MISSING` now fails the lookup rather than reading as free. A created cluster is recorded under the name ECS answers with.
