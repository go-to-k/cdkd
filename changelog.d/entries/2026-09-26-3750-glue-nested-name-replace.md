- **A Glue Table or Connection rename through its nested name is now planned as a replacement, as in CloudFormation (issue [#3750](https://github.com/go-to-k/cdkd/issues/3750))** -- `glueTableNameChanged` and an `AWS::Glue::Table` rule in `src/analyzer/replacement-rules.ts`; unit tests in `tests/unit/analyzer/replacement-rules-glue-nested-name.test.ts`; phase 2c of the `glue-update-hardening` fixture. A `TableInput.Name` change diffed as an in-place update that the provider then refused, asking for `cdkd deploy --replace`, so `cdkd diff` forecast a change the deploy never made. CloudFormation replaces the table on that change (measured), and cdkd now does too: the diff plans a replacement and the stateful guard asks for `--force-stateful-recreation`, as for any table replacement. A case-only difference is the same table (Glue folds names to lowercase) and still updates in place. A `ConnectionInput.Name` change was already a replacement through the schema's nested createOnly path; it is now pinned by tests, which also pin that an unrelated `ConnectionInput` edit is not. A `DatabaseInput.Name` change is unchanged: CloudFormation's update fails on it, and cdkd still refuses it before any AWS call. When a table already holds the new name, the replacement's create now fails with a message naming that table and database instead of the engine's name-collision advice to retry with `--replace`, which would have deleted the managed table first and then failed again. The provider's refusal stays as a backstop for paths that still reach an update with a changed name.
