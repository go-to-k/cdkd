- **A `cdkd refactor` interrupted mid-move is now safe and finishes itself on the next run (issue [#5212](https://github.com/go-to-k/cdkd/issues/5212))** -- `src/cli/commands/refactor-move.ts`, `src/cli/commands/refactor.ts`, `src/state/pending-moves.ts` and `src/state/refactor-marker.ts` (new), `src/state/s3-state-backend.ts` (`getRefactorMarker` / `saveRefactorMarker`), `src/utils/deferred-interrupts.ts` (new), `src/types/state.ts` (`pendingMovesOut`), `src/deployment/deploy-engine/deploy-flow.ts`, `src/cli/commands/{deploy,destroy,destroy-runner,diff-recursive}.ts`, `docs/cli-refactor.md`, `docs/state-management.md`, a new Guides page `docs/refactor.md`, new unit files, and new phases in the `refactor-move` integ. Before, a refactor killed between the state writes of a move left the resource in no cdkd state, and the destination's next deploy created a second one; Ctrl+C also skipped every `finally`, stranding the stack locks. Now SIGINT / SIGTERM is held until the writes finish, and a move is first listed in `{prefix}/_refactor/pending.json`, then marked in the source record (`pendingMovesOut`, ids only) while the source keeps the resource, then added to the destination, dropped from the source, and unlisted. While a move is listed, `cdkd deploy` and `cdkd destroy` of either stack refuse and `cdkd diff` exits 3; the next `cdkd refactor` of either stack finishes it (`--dry-run` only lists it). A deploy reads the list per stack beside that stack's state read, so it adds no wait; a destroy reads it under each stack's lock; a denied read counts as no move. The record field is additive, so no schema bump.
