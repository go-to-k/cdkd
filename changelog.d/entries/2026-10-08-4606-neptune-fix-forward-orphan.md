- **A successful fix-forward deploy now deletes the Neptune DB cluster or DB instance an earlier failed CREATE left under the same logical id, once live reads prove it is not the new one and is still the one that failed CREATE made (issue [#4606](https://github.com/go-to-k/cdkd/issues/4606))** -- `src/provisioning/providers/neptune-provider.ts`. After `cdkd deploy --no-rollback` failed with an `AWS::Neptune::DBCluster` or `AWS::Neptune::DBInstance` already created, and the fixed template created a new one under the same logical id with another identifier, the successful deploy warned, named the earlier resource, exited `2` and left it in AWS. `NeptuneProvider` now implements `isSameResource` and `resourceIdentity`, as `RDSProvider` does: both rest on the immutable `DbClusterResourceId` / `DbiResourceId`, identifiers equal apart from case are the same resource, and the failed CREATE journals the resource id its create call returned. Neptune shares its identifier namespace with RDS and DocumentDB, and its describe also answers for their resources: a resource of another engine under the identifier is never compared, so it is kept with a warning. Only the not-found fault name counts as gone. Deleting an earlier resource that is already gone prints one info line. Tests: `tests/unit/provisioning/neptune-provider-same-resource-4606.test.ts`; new integ `neptune-fix-forward-orphan`.
