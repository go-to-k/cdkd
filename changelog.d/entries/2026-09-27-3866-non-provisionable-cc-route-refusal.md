- **`AWS::CodeBuild::Project`, `AWS::DocDB::DBCluster` and `AWS::DocDB::DBInstance` refuse an unhandled property pre-flight instead of failing mid-deploy on Cloud Control (issue [#3866](https://github.com/go-to-k/cdkd/issues/3866))** -- `src/provisioning/providers/codebuild-provider.ts`, `src/provisioning/providers/docdb-provider.ts`, `src/provisioning/providers/docdb-subnet-group-provider.ts` (new), `src/provisioning/providers/docdb-shared.ts` (new), `src/provisioning/register-providers.ts`, `src/provisioning/property-coverage.generated.ts`, with unit tests in `tests/unit/provisioning/non-provisionable-cc-route-refusal-3866.test.ts`. AWS reports the three types as `NON_PROVISIONABLE` (Cloud Control has no handlers for them), but their SDK providers did not opt out of the Cloud Control fallback. So a template using a property the SDK provider does not handle, such as a CodeBuild `Triggers` block (CDK's `webhook: true`) or a DocDB cluster's `EnableCloudwatchLogsExports`, was routed to Cloud Control and failed there with an opaque `UnsupportedActionException`, after other resources had already been created. The deploy now stops before provisioning anything, naming each property and the `--prefer-sdk-route` escape hatch. `AWS::DocDB::DBSubnetGroup`, which Cloud Control can manage, moved to a provider of its own and keeps its Cloud Control route.
