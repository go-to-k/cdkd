- **`cdkd gc` and `cdkd bootstrap --destroy` stop rendering an S3 state key's segments raw, and gc stops building a pasteable command out of one (issue [#3179](https://github.com/go-to-k/cdkd/issues/3179) section C)** -- `src/cli/commands/{state-file-keys,gc,bootstrap-destroy}.ts`, three suites. A state-bucket key is chosen by anyone holding `s3:PutObject`, the premise [#3207](https://github.com/go-to-k/cdkd/issues/3207) already rests on for the record BODY; `describeStateKey` split one into `stack (region)` and every reader put that in front of an operator deciding whether to destroy something. **Measured before the change**: a segment `Prod<ESC>[2K<CR>SafeStack` rendered as itself, so a terminal ERASED the line and showed `SafeStack (us-east-1)` -- a different stack than the record names. Both halves now render through `displayIdent`, and so do the raw key beside each row, the marker-sibling region list, and three `logger.debug` keys -- guarding one and not the others is inert, since the same escape reaches the same line either way. A whole KEY renders at its own cap, since a key CONTAINS a stack name. **The worse reader was one the issue did not name**: `gc.ts` re-parsed its own rendered string to build a `cdkd state show ...` command it tells the operator to RUN, which measured out as `cdkd state show $(whoami) --stack-region us-east-1`. It now takes the parts from a new structural `parseStateKey` and offers the command ONLY when both pass `isPasteableIdent`, else names the key. That predicate is an allow-list plus the `displayIdent` round-trip; the deny-list written first was defeated in review by a leading `~`, and the measured shell behaviour behind the set is recorded on the constant's own doc comment. Legitimate names and regions render byte-identically. Sections A, B, D, E and F of the issue stay open (F is a completeness note about `displayIdent`'s cut marker, in the same held file); go-to-k/cdkd#3313 is a separate listing defect this surfaced.
