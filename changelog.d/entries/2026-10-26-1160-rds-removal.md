- **`AWS::RDS::DBCluster` / `AWS::RDS::DBInstance`: removing `Port`, `MonitoringInterval` or `ManageMasterUserPassword` from the template now does what CloudFormation does (issue [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/rds-provider.ts`. A CloudFormation A/B on the issue (us-east-1, 2026-10-25) removed each remaining property. Three cases disagreed with cdkd. A removed DBCluster `Port` is reset to the engine default: 5432 on `aurora-postgresql`, 3306 on `aurora-mysql`. Before, cdkd sent nothing and the old port stayed. A Multi-AZ DB cluster (`mysql` / `postgres`) was not measured and still sends nothing. A DBCluster update that changes the port now waits until the cluster reports the new one, so `Fn::GetAtt <cluster>.Endpoint.Port` reads it in the same deploy (`--no-wait` skips the wait). A removed DBCluster `MonitoringInterval` keeps the live interval, with or without `MonitoringRoleArn` removed too. Before, cdkd reset it to 0 and turned Enhanced Monitoring off. A removed `ManageMasterUserPassword` (previously `true`) on either type sends `ManageMasterUserPassword: false`. With a `MasterUserPassword` declared in the same deploy, that switches the master password to it. Without one, RDS refuses the update, as it refuses CloudFormation's. Before, cdkd sent nothing, so the managed password stayed on without a word. Every other removed property measured is kept by CloudFormation too, and cdkd still sends nothing for it: DBCluster `EngineVersion`, `ServerlessV2ScalingConfiguration` and `MonitoringRoleArn`; DBInstance `EngineVersion`, `Port`, `PubliclyAccessible`, `AllocatedStorage` and `MonitoringRoleArn`. Tests: `tests/unit/provisioning/rds-provider-update-removal.test.ts`. The `rds-aurora` integ's removal phase also drops the SecurityCluster's `Port`, monitoring settings and managed password.
