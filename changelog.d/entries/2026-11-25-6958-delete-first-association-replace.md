- **A deploy that replaces an `AWS::EC2::VPCGatewayAttachment` (its `VpcId` changed, as when a `Vpc`'s `ipAddresses` CIDR changes while the old VPC holds no public address) or an `AWS::EC2::SubnetRouteTableAssociation` (its `RouteTableId` or `SubnetId` changed) deletes the old one before it creates the new one, as CloudFormation does, instead of failing with `Resource.AlreadyAssociated` (issue [#6958](https://github.com/go-to-k/cdkd/issues/6958))** -- `src/deployment/delete-first-replacement-types.ts`, `src/deployment/deploy-engine/update-replace/create-first.ts`, `src/deployment/deploy-engine/replacement/delete-first.ts`, `src/analyzer/destructive-changes.ts`, `src/deployment/rollback-executor/replay-failed-replaced-deleted.ts`, `src/deployment/rollback-executor/plan/failed-ops.ts`, `src/deployment/deploy-engine/rollback/perform.ts`, `tests/unit/deployment/deploy-engine-delete-first-association-6958.test.ts`, `tests/unit/analyzer/destructive-early-delete-6713.test.ts`, `tests/integration/ec2-association-replace/`. AWS allows one gateway per VPC and one route table association per subnet, so the create-first order was refused. The replacement now goes through the same delete-first path `--replace` uses: the rollback journal records that the old link was deleted first, so a failed deploy's rollback deletes the new link and re-creates the old one, and when the new link's create itself fails, the rollback (and `cdkd rollback --revert-failed`) re-creates the old one from its recorded properties. The plan (`cdkd diff`, `--require-approval`) says the old one goes first. Under `UpdateReplacePolicy: Retain` the old link is kept, so the create-first order stays. `AWS::EC2::SubnetNetworkAclAssociation` keeps the create-first order, which already succeeds. With a NAT gateway or other public address in the old VPC, AWS refuses the detach, so the deploy fails as CloudFormation's does and keeps the old attachment. A deploy that replaces neither type sends no extra call.
