- **The SDK provider handles `AbacStatus`, `BucketNamePrefix`, `BucketNamespace` and `MetadataConfiguration` on `AWS::S3::Bucket` (issue [#2762](https://github.com/go-to-k/cdkd/issues/2762))** -- `src/provisioning/providers/s3-bucket-provider.ts`, the bucket rule in `src/analyzer/replacement-rules.ts`, the regenerated coverage files, a new unit file, the S3 wire cases, and a second bucket in the `s3-subconfig-removal` integ. Before, a bucket declaring any of them routed through Cloud Control. A prefix now names the bucket `<prefix>-<account>-<region>-an`, CloudFormation's exact spelling, with the namespace on `CreateBucket`; a prefix beside `BucketName`, or without `BucketNamespace: account-regional`, is refused as CloudFormation refuses it, and a change to either replaces the bucket. Removing `AbacStatus` sets it to `Disabled`. S3 refuses `PutBucketTagging` while ABAC is on, so a tag change on such a bucket goes through S3 Control (`s3:TagResource`, `s3:UntagResource`), and turning ABAC on or off is ordered around the tag write. `MetadataConfiguration` is created, updated per table, and deleted on removal; a table encryption change is refused, as CloudFormation refuses it. Deploys wait in every wait mode for each enabled table's ARN, which backs the new `MetadataConfiguration.*` `Fn::GetAtt` names. A table S3 reports `FAILED`, such as a journal table left by an earlier bucket of the same name, gets a warning naming the remedy and the deploy continues, which CloudFormation does too for that case. `cdkd drift` reads both `AbacStatus` and `MetadataConfiguration`. `MetadataTableConfiguration` (V1) stays on Cloud Control: S3 answers `V1APIsNotAllowed` to an account that never used it.
