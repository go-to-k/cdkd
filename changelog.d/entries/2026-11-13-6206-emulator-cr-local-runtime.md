- **Under `--aws-emulator`, a custom resource's `ServiceToken` function runs in the official Lambda runtime image (issue [#6206](https://github.com/go-to-k/cdkd/issues/6206))** -- `src/local/custom-resource-runtime.ts` (new), `src/provisioning/providers/custom-resource/dispatch.ts` (`invokeLambda`), `src/synthesis/{synthesizer,synthesized-stacks}.ts`, `src/local/layer-tree-copy.ts` (`layerAssetDirectory`), `src/local/lambda-resolver/{asset-code,layers}.ts`, `src/cli/{options,program}.ts`, unit tests and docs. Before, the event went to `lambda:Invoke` on AWS Emulator, whose embedded runtimes miss `https` (Node.js) and `_signal` (Python), so `autoDeleteObjects: true` and `s3deploy.BucketDeployment` failed and the deploy rolled back. Now `deploy`, `destroy`, `state destroy` and `rollback` run that function locally in Docker, as `cdkd local invoke` does: code, handler, runtime and layers from the synthesized cloud assembly, environment, timeout and memory from the deployed function, and the emulator's keys, endpoint and CA. With an emulator on `127.0.0.1`, Node.js handlers that drop the `ResponseURL`'s port get a URL signed for port 443, forwarded inside the container. The runtime image is pulled once per run. Without Docker or the image, or when the app was not synthesized, the event goes to the emulator as before, with a warning. `--no-local-custom-resources` turns it off. A `cr.Provider` framework's second hop to the user's handler still runs in the emulator. A `.zip` layer asset (such as `AwsCliLayer`) is now extracted for `cdkd local invoke` and `local start-api` too. Real AWS deploys are unchanged.
