- **`AWS::Logs::DeliverySource`, `AWS::Logs::DeliveryDestination` and `AWS::Logs::Delivery` now deploy through SDK providers, so they also deploy under `--aws-emulator` (issue [#6584](https://github.com/go-to-k/cdkd/issues/6584))** -- new `src/provisioning/providers/logs-delivery-source-provider.ts`, `logs-delivery-destination-provider.ts`, `logs-delivery-provider.ts` and `logs-delivery/shared.ts`, registered in `register-providers.ts`, with unit and sdk-wire tests. The three types went through Cloud Control, which works on real AWS but polls every operation; against AWS Emulator, Cloud Control reported a source or destination created without making it, so a delivery reading the destination's `Arn` failed with `attributes are not enriched for this resource type`. The providers call `PutDeliverySource` / `PutDeliveryDestination` / `CreateDelivery` directly, record CloudFormation's physical ids (the source and destination `Name`, the delivery id), return every read-only attribute, wire `Tags`, `DeliveryDestinationPolicy`, `OutputFormat`, `RecordFields`, `FieldDelimiter` and the S3 suffix options, and implement drift and import. A create refuses a source or destination name that already exists rather than overwriting it. A `RecordFields`, `FieldDelimiter` or S3 option removed from the template keeps its live value, with a warning, because `UpdateDeliveryConfiguration` cannot clear one.
