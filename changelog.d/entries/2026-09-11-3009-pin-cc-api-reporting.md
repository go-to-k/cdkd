- **A `--pin-cc-api` resource was told its properties "will be silently dropped" while Cloud Control was writing them, and never told its `--prefer-sdk-route` preference was inert (issue [#3009](https://github.com/go-to-k/cdkd/issues/3009))** — `src/provisioning/provider-registry.ts`, `src/deployment/deploy-engine.ts`, `tests/unit/provisioning/provider-registry-report-silent-drops.test.ts`. THREE inputs force a resource onto Cloud Control regardless of its properties — a `provisionedBy: 'cc-api'` record, an un-allowed silent drop, and `--pin-cc-api` — and the reporting path saw only two. The pin beats the record: a resource recorded `sdk` still routes its update through Cloud Control while pinned, so every branch reasoned about a route the deploy was not taking. Two consequences, both the defects their own issues had just removed, reached through the pin instead: the false "will be silently dropped" line issue [#2750](https://github.com/go-to-k/cdkd/issues/2750) retired came back, and issue [#3000](https://github.com/go-to-k/cdkd/issues/3000)'s inert-preference warning stayed silent in the case a user is most likely to report. The three tests are now ONE predicate returning the CAUSE rather than a boolean — `forcedCcRoute`, whose doc comment records that a caller which must explain itself to a user cannot get the explanation from a `true`, which is how two of the three readers came to be updated and the third not. The pin's remedy is its own: dropping `--pin-cc-api <LogicalId>` is a plain, complete, non-destructive change, so it is the only one of the three that names a command — the sticky case hands off to `docs/cli-deploy-safety.md` instead. The engine's threading is fenced separately, because deleting it leaves every registry-level case green: a probed callee says nothing about its wiring.
