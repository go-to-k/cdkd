- **An `AWS::S3::Bucket` now sends its tags on `CreateBucket` itself, and an access denial from an explicit deny fails fast instead of being retried (issue [#4969](https://github.com/go-to-k/cdkd/issues/4969))** -- `src/provisioning/providers/s3-bucket-provider.ts`, `src/deployment/retryable-errors/transient.ts`. cdkd created a bucket untagged and applied its tags afterwards with `PutBucketTagging`, so an organization SCP requiring a tag on `s3:CreateBucket` (`aws:RequestTag/...`) denied the create, where `cdk deploy` succeeds. The template's tags now go in `CreateBucketConfiguration.Tags`, and a create that carried them no longer repeats them with `PutBucketTagging`; an adopted bucket still gets the `PutBucketTagging`. Tags on `CreateBucket` need `s3:TagResource`: a role that lacks it but holds `s3:PutBucketTagging` gets the old path back automatically (one untagged retry of each bucket's create, then `PutBucketTagging`); when that untagged create is denied too, the error names the missing `s3:TagResource` (and fails at once when the untagged denial is an explicit deny); an endpoint that refuses the `Tags` member itself takes the same untagged path. Separately, an `AccessDenied` that says the call was refused `with an explicit deny` (a service control policy, resource control policy, identity- or resource-based policy, permissions boundary, session policy, VPC endpoint policy or role trust policy) was matched as IAM propagation and retried for about 48 seconds; it now fails on its first answer, and an S3 bucket error names the policy type that denied it. A role holding `s3:TagResource` makes no extra AWS call, and its tagged bucket's create makes one call fewer.
