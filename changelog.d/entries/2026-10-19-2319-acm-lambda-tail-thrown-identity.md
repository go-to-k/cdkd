- **A failed ACM certificate, Lambda web function revision or endpoint, Lambda MicroVM image, event source mapping or function URL create, update or delete no longer writes the caller's account id, assumed-role ARN and session name into the persisted deployment events (issue [#2319](https://github.com/go-to-k/cdkd/issues/2319))** -- `src/provisioning/providers/acm-certificate-provider.ts`, `lambda-web-function-revision-provider.ts`, `lambda-web-function-endpoint-provider.ts`, `lambda-microvm-image-provider.ts`, `lambda-eventsource-provider.ts`, `lambda-url-provider.ts`, and unit cases. The thrown message quoted AWS's raw text, which names the caller on an access denial, and `deployments/{runId}.jsonl` outlives the run. The message now carries the error class (`AccessDeniedException. Re-run with --verbose for AWS's own message.`), and AWS's text goes to the debug log, masked through the operation's secret masker. This also covers a web function revision or endpoint that AWS reports as Failed: its status reason stays out of the message (a revision keeps its build error's code). A cdkd-authored or transport error keeps its text. The AWS error stays as the `cause`, so an IAM grant that is still propagating is retried as before. An occupied name (an event source mapping or MicroVM image that already exists) still says it already exists, so a create-first replacement still recognises the name collision. An ACM create whose cleanup could not delete the requested certificate still names it.
