- **After a destroy that kept an EFS or FSx file system or a CloudFront origin access identity, the same stack's next deploy creates a new one; a re-run of an interrupted deploy takes the one it made (issue [#4438](https://github.com/go-to-k/cdkd/issues/4438))** -- `src/provisioning/providers/{create-token-ledger,efs-provider,fsx-filesystem-provider,cloudfront-oai-provider}.ts`, `src/state/{create-token-ledger,s3-state-backend}.ts`, the deploy engine, the rollback executor, `src/cli/commands/{orphan,rollback}.ts`. These create tokens were deterministic per stack, so a resource that outlived cdkd's record of it (`RemovalPolicy.RETAIN`, CDK's default for both file systems, `RetainExceptOnCreate`, `UpdateReplacePolicy: Retain`, `cdkd orphan`) still held the token the next create sent: EFS and FSx refused that redeploy where the AWS CDK CLI creates a new resource, and CloudFront handed the old identity back. A per-stack ledger, `create-tokens.json` beside `state.json`, folds a nonce into those tokens. It is deleted before the state record (failing the command if it cannot be), and rotated by `cdkd orphan` and by any Retain or `--orphan`. Each send is recorded before the create and kept until that deploy succeeds, so an interrupted deploy's re-run takes the resource it made, which #4437 refused. A deploy that finds no state record but a ledger written under one (an earlier cdkd destroyed the stack) starts a fresh ledger. A ledger that cannot be read or written refuses these creates, naming the stack and logical id. A create interrupted under an earlier cdkd creates a fresh resource on its re-run; for EFS, cdkd warns naming the file system left behind. Tests: `tests/unit/{provisioning/create-token-ledger,state/create-token-ledger,deployment/deploy-engine-create-token-ledger-4438}.test.ts` and the provider and orphan suites; integ: `stack-copy-create-tokens`.
