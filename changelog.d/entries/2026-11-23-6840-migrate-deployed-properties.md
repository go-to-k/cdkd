- **A CDK change made after the last `cdk deploy` is no longer lost by `cdkd import --migrate-from-cloudformation` (issues [#6840](https://github.com/go-to-k/cdkd/issues/6840), [#6842](https://github.com/go-to-k/cdkd/issues/6842))** -- `src/cli/commands/import/deployed-properties.ts`, `src/cli/commands/import/locked-import.ts`, `src/cli/commands/import/nested.ts`, `tests/unit/cli/import-deployed-properties-6840.test.ts`, `tests/integration/import-migrate-pending-change/`. The migration's Retain update keeps CloudFormation's template, so AWS keeps the last-deployed configuration, but state recorded the newly synthesized properties: `cdkd diff` said "no changes" and `cdkd deploy` never applied the change (a widened IAM trust condition stayed narrow while state and `cdkd drift` called it in sync). Each resource now records its properties as CloudFormation last deployed them, nested children included, so the next `cdkd diff` shows and `cdkd deploy` applies the change, as the next `cdk deploy` would. A resource whose deployed properties cannot be resolved against the synthesized template (a renamed sibling, a changed condition or mapping, a changed type, a cross-stack read the code dropped) keeps the synthesized properties with a warning naming it.
