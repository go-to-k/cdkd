- **A log group's create refuses a name another log group already holds, as CloudFormation does, instead of adopting it (issue [#6655](https://github.com/go-to-k/cdkd/issues/6655))**. `CreateLogGroup`'s `ResourceAlreadyExistsException` was read as success: the deploy recorded whatever group held the name as the stack's own, and a later destroy deleted it. The pre-create lookup already refused a taken name; the adopt still reached a group created after that lookup, and a rollback's re-create of a replaced log group, where it also hid the collision from delete-new-first. The create now fails with the raw exception as the error's cause, which the collision classifier reads. One exception is the log group the generated-name check licenses from the stack's own records (an interrupted deploy's, one it kept), which the create still takes back, and no other: the engine runs each create with that license in an async-local scope. The other: a retry that meets the group its own earlier attempt made, after that attempt's answer was lost, still takes it, when the group's creation time falls after that attempt was sent. A collision no longer counts as proof that a create made nothing, so a replay meeting its own lost first create keeps the ledger intent for the next deploy's take-back. The audit of the other in-scope creates found no other provider-side adopt: ECR repositories, SSM parameters (`Overwrite: false`), KMS aliases and EventBridge buses and archives fail on a taken name, a Route 53 hosted zone adopts only the zone matching the caller reference this process minted, and SNS `CreateTopic` / EventBridge `PutRule` hand back or overwrite by API design, behind the existing lookup.
