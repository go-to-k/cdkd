- **A nested `cdkd export` that fails partway names only the steps each stack still needs, in order, lists the deletes its phase 2 needs, and recovers from every step after an IMPORT (issue [#3988](https://github.com/go-to-k/cdkd/issues/3988))** -- `src/cli/commands/export.ts`, with unit tests in `tests/unit/cli/export-nested-failure-render.test.ts` and `export-nested-loop.test.ts`. The failed stack's line said "once this stack's IMPORT / adoption and phase 2 succeed by hand" whatever was left: it asked for a phase 2 a stack had no work for, never for the no-op tag update a non-root stack needs to leave `IMPORT_COMPLETE` before its parent adopts it, and a Phase 1A or 1B failure never listed the deletes of the IMPORT-unsupported resources phase 2 re-creates, so a by-hand phase 2 hit a name collision or left a duplicate unmanaged. The line now names only the IMPORT, adoption, phase 2 or closing tag update still needed, and prints those deletes first. A failure after a stack's Phase 1A (reading its CloudFormation stack, either tag update, preparing the adoption) threw the bare error with no recovery while a re-run was already refused; it now gives the same whole-tree recovery. The re-run refusal no longer wraps `cdkd export` in backticks, which ran it when pasted, and the Phase 1B failure no longer calls an adopted stack standalone.
