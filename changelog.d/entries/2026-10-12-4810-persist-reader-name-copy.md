- **`cdkd destroy` no longer fails on a reader of a resource named from a secret because a deploy stored the reader's copy of that resource's physical id as a `{{resolve:...}}` reference (issue [#4810](https://github.com/go-to-k/cdkd/issues/4810))** -- `src/deployment/secret-redaction/physical-name-copies.ts` (new), `src/deployment/secret-redaction/redact-state.ts`, `src/deployment/intrinsic-resolver/refs.ts`, `src/deployment/deploy-engine/update.ts`, `src/provisioning/providers/scheduler-schedule-provider.ts`. An `AWS::SQS::QueuePolicy` whose `Queues` reads a queue named from a secret, and whose policy document also spells the secret reference literally, had its plaintext `Queues` URL rewritten into `https://sqs.../{{resolve:secretsmanager:...}}` by the save after the deploy (and after an automatic rollback), because the policy's own secrets bag held the queue name. The provider deletes by that URL, so the next `cdkd destroy` failed with `InvalidAddress`. Each physical id a `Ref` / `Fn::GetAtt` reads is now recorded beside the reader's secrets, and the save keeps a secret's text where it lies inside such an id, as the id itself is stored in plaintext. A secret elsewhere in the same value, and the literal reference, are still stored as the reference. A record an earlier deploy rewrote is repaired by the next `cdkd deploy`, which sends nothing for it and replaces nothing (a create-only copy such as an SNS subscription's `TopicArn` included); a `cdkd destroy` run first still fails on it. A copy read from another stack, through a nested stack's parameter, or of a `NoEcho` value is not covered yet (issue [#4819](https://github.com/go-to-k/cdkd/issues/4819)).
