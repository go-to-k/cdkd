- **`cdkd destroy` no longer fails on a reader of a resource named from a secret because a deploy stored the reader's copy of that resource's physical id as a `{{resolve:...}}` reference (issue [#4810](https://github.com/go-to-k/cdkd/issues/4810))** -- `src/deployment/secret-redaction/physical-name-copies.ts` (new), `secret-redaction/redact-state.ts`, `intrinsic-resolver/refs.ts`, `deploy-engine/update.ts`, `src/cli/commands/drift.ts`, `src/provisioning/providers/scheduler-schedule-provider.ts`. An `AWS::SQS::QueuePolicy` whose `Queues` reads a queue named from a secret, and whose policy document spells the secret reference literally, had its plaintext `Queues` URL rewritten into `https://sqs.../{{resolve:secretsmanager:...}}` by the save after a deploy (the final save after an automatic rollback included), because the policy's own secrets bag held the queue name; `cdkd drift --accept` / `--revert` did the same. The provider deletes by that URL, so `cdkd destroy` failed with `InvalidAddress`. Each physical id a `Ref` / `Fn::GetAtt` reads (for drift, every other record's) is now recorded beside the reader's secrets, and those writes keep a secret's text inside such an id, as the id is stored in plaintext. Elsewhere in a value, and in a literal reference, it is still the reference. The automatic rollback's own restore is go-to-k/cdkd#4801's half; that shape is fixed once both are released. A record an earlier deploy rewrote is repaired by the next `cdkd deploy`, which sends and replaces nothing for it, though its plan, `cdkd diff` and `--require-approval` show the reader as changed once; a `cdkd destroy` run first still fails. A copy read from another stack, through a nested stack's parameter, or of a `NoEcho` value is not covered (issue [#4819](https://github.com/go-to-k/cdkd/issues/4819)).
