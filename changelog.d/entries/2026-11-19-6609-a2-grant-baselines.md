- **A KMS key policy, delivery destination policy, log group data protection policy, RestApi `Policy`, EFS file system policy or CodeBuild project `Visibility` that cdkd just wrote no longer leaves a drift baseline that `cdkd drift --revert` would undo when the write is not yet visible (issue [#6609](https://github.com/go-to-k/cdkd/issues/6609))** -- `src/provisioning/settle-after-own-write.ts`, `src/provisioning/providers/{kms,efs,codebuild,logs-loggroup}/read-state.ts`, `src/provisioning/providers/apigateway/rest-api-own-write.ts`, the six provider facades, `src/cli/commands/drift/baseline-keys.ts`, unit tests. The deploy recorded the first read after the write as the `observedProperties` baseline. The capture after cdkd's own write now re-reads a declared member whose first answer differs from the template (up to 3 more reads, 3.5 seconds at most, only when the first answer differs; the member's own call, or for a RestApi or CodeBuild project the one call that reads it whole; a deterministic read failure such as `AccessDenied` is not re-read). If none is set yet after that (for a KMS key, still KMS's default policy), the declared value is recorded; another value is recorded as read. Either way a warning names the resource and member and points at `cdkd state refresh-observed`. Drift, import and `state refresh-observed` still take the first answer. Drift no longer compares the member while the live resource holds exactly the declared value (and, where removing it deletes it, while neither declares nor holds one), which also heals a baseline written by an earlier cdkd.
