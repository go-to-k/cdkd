- **A change to an `AWS::KMS::Key`'s `KeySpec`, `KeyUsage`, `MultiRegion` or `Origin` now fails the deploy instead of reporting success with nothing changed, and a key policy update now sends `BypassPolicyLockoutSafetyCheck` (issue [#5299](https://github.com/go-to-k/cdkd/issues/5299))** -- `src/provisioning/providers/kms-provider.ts`. KMS fixes these four properties when a key is created and has no call that changes them, and the type's schema lists no create-only property, so the change reached the in-place update, which sent nothing. CloudFormation fails the same update rather than replacing the key (A/B, us-east-1: each of the four fails; declaring or dropping a default value beside another change completes). cdkd now refuses the change before any write, naming the changed properties; `cdkd deploy --replace` replaces the key (with `--force-stateful-recreation` unless its `UpdateReplacePolicy` is `Retain`; without `Retain` the old key is scheduled for deletion). Before refusing, cdkd reads the key with `DescribeKey`: a stack deployed by an earlier cdkd may have recorded a changed value the key never took, and a template put back to the live value then goes through. Each side is compared with its default filled in, so declaring or dropping `KeySpec: SYMMETRIC_DEFAULT` and the like is no change. The update's `PutKeyPolicy` also never carried `BypassPolicyLockoutSafetyCheck`, which the create sends, so KMS refused a policy the template had told it to accept; CloudFormation forwards it on update (A/B: the same lockout policy updates with the flag and fails without it). Unit cases in `tests/unit/provisioning/providers/kms-provider-immutable-5299.test.ts`; the `kms-encryption` integ adds an IMMUTABLE and a BYPASS phase.
