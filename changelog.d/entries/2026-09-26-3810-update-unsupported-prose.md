- **A failed update whose error message contains "does not support UPDATE" no longer replaces the resource without `--replace` (issue [#3810](https://github.com/go-to-k/cdkd/issues/3810))** -- `src/deployment/retryable-errors.ts` (`isUpdateUnsupportedError`; `CC_UPDATE_UNSUPPORTED_MESSAGE_FALLBACK` removed), with unit tests in `tests/unit/deployment/retryable-errors.test.ts` and `tests/unit/deployment/deploy-engine-replace.test.ts` and a shared fixture in `tests/unit/_cc-unsupported-action.ts`. The update-failure fallback's Cloud Control classifier still matched that phrase in any top-level error message, after [#3757](https://github.com/go-to-k/cdkd/issues/3757) had excluded only the typed refusal. A cdkd refusal that quotes a template value (AppSync's non-numeric `DeltaSyncTableTTL`, for one) or an AWS error echoing its input therefore ran the DELETE + CREATE on a non-stateful type with no flag, and the replacement's CREATE could then hit the same refusal, leaving the resource deleted. The classifier now reads only the structured signals: the `UnsupportedActionException` name down the cause chain, and the async `ccErrorCode` for an UPDATE. Both are what Cloud Control's real rejection carries, so a genuine "no UPDATE handler" type still falls back as before; an error carrying only the wording now fails the deploy.
