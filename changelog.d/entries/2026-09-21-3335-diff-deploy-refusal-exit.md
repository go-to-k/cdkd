- **`cdkd diff` now exits 3 over a record whose repaired container `cdkd deploy` refuses, instead of 0 (issue #3335)** — an unreadable resource `properties` map (#3317) and an unreadable `outputs` bag (#3189) are repaired to empty for the preview and warned about, while the deploy refuses the record. When the template declared nothing in the damaged container the repaired `{}` produced no change rows, so `cdkd diff --fail` exited 0 and a CI step gating on it passed over a record the next deploy stops on; where the template did declare something, `--fail` exited 1 for a change the deploy will not make and exit 3 stayed unset. Both repairs now put one reason per REPAIR PASS and damaged CONTAINER on the node's `blocking` — a record with both containers torn reports two, and so does one damaged in both the load and the orphan splice — the mechanism #2943 already uses for a refused rollback-orphan adoption, so `countBlocking` raises `DeployRefusalPreviewError` (exit 3) ahead of `--fail`. The ids are deliberately NOT added to `--json`'s `unreadable`, which means "dropped from the diff" — these rows are previewed. A torn map on an ADOPTED orphan record counts too, from the second repair after the splice. TOP-LEVEL only, as a conservative choice: a nested child keeps its repair warning and adds no reason, because the deploy skips an unchanged nested-stack row and an attribute-only UPDATE never diffs the child, so a reason there would promise exit 3 over a deploy that succeeds.
