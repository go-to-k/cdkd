- **`cdkd rollback` now reverses a replacement that re-created a resource under the same physical id, instead of reporting success over it (issue [#5096](https://github.com/go-to-k/cdkd/issues/5096))** -- `src/deployment/rollback-executor/plan.ts`. A replacement that deleted the old resource first and re-created it under the same name (`cdkd deploy --replace`'s delete-first fallback, a fixed-name `--recreate-via-*`, an update the provisioning layer rejects) was rolled back in place: the provider could not change the create-only property, so the re-created resource stayed while the rollback wrote the old record into state and reported success. Such a replacement is now reversed: the re-created resource is deleted and the old one re-created, as for any delete-first replacement; a re-run after a completed reversal does nothing. When the stack records a resource AWS stores inside it (a function's permission, a topic's subscription, a role's inline policy), which deleting it again would take too, the rollback refuses that resource before deleting anything and names `cdkd deploy --replace` of the previous template as the fix. It refuses the same way when every property the deploy changed is a secret redacted identically in state before and after, since state then cannot tell whether an earlier rollback already reversed it.
