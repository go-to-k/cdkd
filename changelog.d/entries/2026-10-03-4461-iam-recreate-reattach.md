- **A same-name IAM role, user or group re-create no longer silently drops the managed policies, instance profile and group memberships attached to it (issue [#4461](https://github.com/go-to-k/cdkd/issues/4461))** -- `src/deployment/child-of-recreated-parent.ts`, `src/deployment/deploy-engine/update.ts`, `src/deployment/deploy-engine/update-in-place.ts`, `src/deployment/deploy-engine/execute.ts`, `src/provisioning/providers/iam-user-group-provider.ts`, `src/provisioning/providers/iam-instance-profile-provider.ts`. When a deploy re-created a fixed-name role, user or group under the same name, IAM had detached what was attached to it: an `AWS::IAM::ManagedPolicy` (`Roles` / `Users` / `Groups`), an `AWS::IAM::InstanceProfile`'s role, a user's `Groups` membership, a `UserToGroupAddition`'s members, and an inline `AWS::IAM::Policy` / `UserPolicy` / `GroupPolicy` on a user or group. Their references resolved to the same names, so every deploy diffed them unchanged while state kept recording them -- a Deny guardrail silently absent from the re-created role. cdkd now attaches each of them again in place (also when the same deploy edits the list) and writes the inline policies again. A deploy that fails first keeps their records minus the re-created principals, so the next deploy attaches them. Re-adding a role an instance profile already holds now succeeds instead of failing with `LimitExceeded`, and an IAM user's update no longer re-sends an unchanged `LoginProfile`, which reset its password. Tests: `tests/unit/deployment/child-of-recreated-parent.test.ts`, `tests/unit/deployment/deploy-engine-iam-reattach.test.ts`, `tests/unit/provisioning/iam-user-group-provider-roundtrip.test.ts`, `tests/unit/provisioning/iam-instance-profile-provider-roundtrip.test.ts`.
