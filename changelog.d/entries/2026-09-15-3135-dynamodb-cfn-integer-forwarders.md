- **The DynamoDB capacity / throughput forwarders read an Integer the way CloudFormation's DynamoDB handler does, and refuse the spellings it rejects instead of forwarding their `Number()` reading (issue [#3135](https://github.com/go-to-k/cdkd/issues/3135))** -- `src/provisioning/dynamodb-warm-throughput.ts` (`coerceWarmThroughput`, both DynamoDB types; the DynamoDB row of the measurement added to `toCfnInteger`'s doc beside the Logs one), `src/provisioning/providers/dynamodb-globaltable-provider.ts` (every capacity / ceiling forwarder, the auto-scaling `RegisterScalableTarget` min / max and `PutScalingPolicy` cooldowns, plus the diagnostic / mirror predicates paired with each), `.claude/rules/layout-provisioning.md`, unit tests. Live A/B on `AWS::DynamoDB::Table.ProvisionedThroughput` (us-east-1, 2026-09-14): the accepted grammar is `/^[+-]?\d+$/` with NO whitespace trimming -- `" 7 "`, `"7 "` and `""` are rejected at properties validation, hex / exponent / decimal-point by the handler, `"+8"` / `"010"` accepted. The forwarders read through `Number()`, so a template CloudFormation refuses deployed with `7` / `9` / `10`. They now read through `config-shape.ts`'s `coerceCfnInteger` (that grammar exactly), and a rejected spelling takes the arm each site already had for an unresolved intrinsic -- dropped and NAMED (`WarmThroughput`), the announced 5/5 fallback on a PROVISIONED capacity, an announced suppression on an on-demand ceiling -- never silent, never absent, never a throw (#1428's replay reasoning). Diagnostics name the grammar. Guard-only readers (live-readback compares, the already-matches / decrease / zero-capacity tests) stay on `toFiniteNumber`, where over-acceptance is the safe side. `toCfnInteger` (the Logs helper) is unchanged. The `AWS::DynamoDB::Table` provider's raw `Number(x ?? 5)` capacity forwarders are a sibling class with their own default arithmetic, filed as [#3147](https://github.com/go-to-k/cdkd/issues/3147).
