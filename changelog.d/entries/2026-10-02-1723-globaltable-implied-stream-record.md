- **A multi-replica `AWS::DynamoDB::GlobalTable` whose template declares no `StreamSpecification` now records the stream cdkd enables for it, and an update no longer re-sends a stream the table already has (issue [#1723](https://github.com/go-to-k/cdkd/issues/1723))** -- `src/provisioning/providers/dynamodb-globaltable-provider.ts` (`replicationImpliedStreamSpecification`, `create()`'s `needsStream` arm, `update()`'s stream arm and its end, a new `canonicalizeDesiredProperties`), a new unit file and the `dynamodb-globaltable-implied-stream` integ fixture. `create()` enables a `NEW_AND_OLD_IMAGES` stream where the template is silent, but state recorded none. That was not phantom drift, but declaring the same stream later diffed as an UPDATE, and `update()` sent `StreamEnabled: true` for a live stream (a stream change the CloudFormation docs allow only on a single-replica table). Now `create()` records the stream, `update()` re-records it when the live table confirms it, and the twin folds it into both diff sides, so older records diff `NO_CHANGE` too. `update()` also skips the stream when the table already holds the declared view type, which covers older records and a rollback of a two-to-one replica change. Only the region-independent case (more than one replica, no `MultiRegionConsistency` declared) is recorded. A single replica outside the deploy region still records nothing, though the live check keeps a later declaration of its stream from being re-sent. Such a record that later moves to Cloud Control (a template adding a property cdkd's provider does not handle) now fails that update, since the patch asks to remove the recorded stream; the template is one CloudFormation rejects.
