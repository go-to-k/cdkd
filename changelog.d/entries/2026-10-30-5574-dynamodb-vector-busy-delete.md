- **`AWS::DynamoDB::Table`: the index-busy `DeleteTable` retry waits for a busy vector index too, and `create()`'s rollback `DeleteTable` retries it (issue [#5574](https://github.com/go-to-k/cdkd/issues/5574))** -- `src/provisioning/dynamodb-index-busy-delete.ts`, `src/provisioning/providers/dynamodb-table-provider.ts`, `tests/unit/provisioning/dynamodb-vector-busy-delete-5574.test.ts`. When AWS refused `DeleteTable` with `Cannot delete table while indexes are being created, updated, or deleted`, the wait before each retry read only the global secondary indexes, so on a table whose vector index was still `CREATING` or `DELETING` it returned at once and every retry spent only its backoff. It now reads `VectorIndexes` as well, and while only a vector index is building it waits up to 900 polls (within the delete path's shared allowance) instead of 60: AWS does refuse `DeleteTable` during a vector-index build, with the same message, and a measured build took ~8.5 min. `create()`'s rollback of a partially-created table (sent when a step after `CreateTable`, such as the vector-index wait, fails) sent one `DeleteTable` and reported the table left behind on any refusal; it now retries the index-busy refusal the same way, within what the per-resource deadline has left (no retry once that is under four minutes). The `Table` messages now say "a global secondary index or vector index"; `AWS::DynamoDB::GlobalTable`'s are unchanged.
