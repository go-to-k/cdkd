- **A nested stack's skipped DELETE is re-attempted by the next `cdkd deploy`, which exits 2 again until it lands (issue [#4453](https://github.com/go-to-k/cdkd/issues/4453))** -- `src/provisioning/providers/nested-stack-provider.ts`. A top-level stack's skipped DELETE keeps its record and is retried by the next deploy, but inside a nested child (or grandchild) the retry never ran: the parent's `AWS::CloudFormation::Stack` row diffed only `TemplateURL` / `Parameters`, so with no template change it was `NO_CHANGE`, the child never deployed, and the second deploy reported nothing and exited 0 over a resource cdkd still owns. A nested row now records the record-only key `cdkd:PendingChildDeletes` (the child's skipped-DELETE count, descendants included) while any remain, so the next deploy re-runs the child chain, retries the DELETE and counts it again; `cdkd diff` shows that pending re-run as a change on the row. A clean re-run records the plain template properties and the key is gone. A skip left by an earlier cdkd version carries no key, so it is re-attempted the next time that child stack deploys for another reason. Tests: `tests/unit/deployment/deploy-engine-nested-child-unaddressed-e2e.test.ts`, `tests/unit/provisioning/nested-stack-provider.test.ts`; integ: `nested-stack-3level`.
