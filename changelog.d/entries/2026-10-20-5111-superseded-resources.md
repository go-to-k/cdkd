- **A replaced resource whose delete was refused "in use" is no longer lost when the deploy stops before its cleanup (issue [#5111](https://github.com/go-to-k/cdkd/issues/5111))** -- `src/deployment/superseded-resources.ts`, `src/deployment/deploy-engine/{replacement,superseded-retry,execute,deploy-flow}.ts`, `src/cli/commands/destroy-runner.ts`, `src/types/state.ts`. A replacement whose old resource was still used by something the deploy had yet to update (an ELBv2 target group behind a listener) deferred that delete to the end of the deploy, but only in memory, while state already recorded the new resource: a deploy killed, crashed or interrupted before the end left the old resource in AWS with no record, and nothing ever deleted it -- it survived `cdkd destroy` and kept billing. The old resource is now recorded in state (`supersededResources`, additive, no schema bump) by the same save that records the replacement. Every later deploy, an unchanged one included, retries its delete after its own changes and drops the record once it is gone; `cdkd destroy` deletes it after the stack's own resources and keeps the state while it fails. The end-of-deploy retry also waits out an "in use" refusal for up to a minute (a deleted load balancer's listeners go asynchronously; an endpoint moving off a Lambda web function revision), and a delete still refused keeps the record with a warning naming the next deploy and `cdkd destroy` as the remedy.
