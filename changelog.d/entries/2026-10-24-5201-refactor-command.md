- **New `cdkd refactor` keeps a resource whose logical ID a construct rename changed, instead of letting the next deploy replace it (issue [#5201](https://github.com/go-to-k/cdkd/issues/5201))** -- `src/cli/commands/refactor.ts`, `src/analyzer/refactor-pairing.ts`, `src/state/logical-id-rename.ts`, `src/cli/program.ts`, `src/cli/index.ts`, `docs/cli-refactor.md`, three new unit files, and the new `refactor-command` integ. Before, renaming or moving a construct within a stack made `cdkd deploy` delete the old logical ID and create the new one, so the AWS resource was replaced and a stateful one lost its data. `cdkd refactor [stacks...]` pairs each removed logical ID with an added one of the same type and renames the state record when the new resource then shows no change in the same diff `cdkd deploy` computes; look-alikes it cannot tell apart are reported as ambiguous and named with `--override-file` (the `cdk refactor` mapping format, `--revert` applies it in reverse). A pair whose properties also changed is refused, as by `cdk refactor`. Only cdkd state is rewritten, under the stack lock and conditional on the state it planned from; no AWS resource is touched. `--dry-run` prints the plan. Moving a resource between stacks is not supported yet ([#5202](https://github.com/go-to-k/cdkd/issues/5202)).
