- **A successful deploy no longer deletes a resource that reused the name of a journaled orphan the user deleted by hand (issue [#4655](https://github.com/go-to-k/cdkd/issues/4655))** -- `src/deployment/deploy-engine/execute.ts`, `src/deployment/rollback-executor/{journaled-orphans,orphan-identity,types}.ts`, `src/types/{resource,rollback-journal}.ts`, `src/provisioning/providers/kinesis-provider.ts`. After `cdkd deploy --no-rollback` failed with a resource already created, the journal recorded it by physical id alone. If the user deleted it and something else created a resource under the same name, the next successful deploy deleted that unrelated resource. Providers gain an optional `resourceIdentity`; the failed CREATE journals its token as `createdResourceIdentity` (additive, no `journalVersion` bump), and the success-path settle deletes a name-keyed orphan only when a live read returns the same token, and drops one reported gone without a delete. Otherwise it warns, names the resource, clears the entry and exits `2`. A journal an older cdkd wrote, and a name-keyed type without `resourceIdentity`, now lands there too instead of being deleted. `AWS::Kinesis::Stream` implements it (ARN plus creation time). Types whose physical id AWS generates and never reuses, `AWS::SQS::QueuePolicy` / `AWS::SNS::TopicPolicy` (whose delete compares content) and nested stacks (a cdkd-minted id) are unchanged. `cdkd rollback` and `cdkd destroy` are not covered yet (#4658). Tests: `tests/unit/deployment/journaled-orphan-identity-4655.test.ts`, `tests/unit/provisioning/providers/kinesis-resource-identity-4655.test.ts`; integ `rollback-command` step O9.
