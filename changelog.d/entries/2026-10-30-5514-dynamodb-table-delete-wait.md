- **Deleting an `AWS::DynamoDB::Table` now waits until the table is gone, so `cdkd destroy` no longer reports success while the table is still `DELETING` (issue [#5514](https://github.com/go-to-k/cdkd/issues/5514))** -- `src/provisioning/providers/dynamodb-table-provider.ts`, and unit tests. Before this change `delete()` returned as soon as AWS accepted `DeleteTable`, so a destroy followed by a deploy of a table with a fixed `TableName` could fail with `ResourceInUseException`, a resource deleted after the table (a KMS key, an IAM role) could be deleted while the table still existed, and a check right after the destroy still saw the table. It now polls `DescribeTable` until `ResourceNotFoundException`, as CloudFormation does and as the `AWS::DynamoDB::GlobalTable` provider already did, through the shared post-delete wait (`src/provisioning/delete-gone-wait.ts`). The wait is capped at ~12 minutes and by what the DynamoDB delete budget has left, keeps polling through throttling, and never fails the delete: a cap, a Ctrl-C, or a status read AWS refuses warns and returns, since AWS finishes the accepted delete on its side. Integration fixture: `tests/integration/dynamodb-sse` now asserts the table is gone straight after destroy.
