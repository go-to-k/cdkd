- **A delete of an S3 Tables table bucket or an S3 Vectors vector bucket that still holds tables, namespaces or vector indexes the stack did not create is refused instead of deleting them (issue [#6749](https://github.com/go-to-k/cdkd/issues/6749))** -- `src/provisioning/providers/s3-tables/table-bucket.ts`, `src/provisioning/providers/s3-vectors-provider.ts`, `src/provisioning/stateful-types.ts` (comments), `docs/cli-destroy-guards.md`, `docs/cli-deploy-safety.md`, `docs/cli-deploy-safety-internals.md`, and unit tests. `cdkd destroy`, a removal and a replacement deleted every table and namespace in a table bucket, or every index in a vector bucket, before deleting the bucket, with no opt-in. CloudFormation's delete handlers for both types hold only the bucket's own delete permission, so a non-empty bucket fails there, and the stack's own tables, namespaces and indexes are deleted before their bucket, so what the emptying reached was data written from outside the stack (for example by Firehose, Athena or Spark). The bucket is now deleted as is; when AWS refuses it, cdkd lists what it holds twice, two seconds apart (at most five names of each), and when something is in both listings it fails without a retry, naming it and the next step. A replacement under `--force-stateful-recreation` still empties the bucket first.
