- **Data and streaming creates no longer let the AWS SDK replay a 5xx inside one call (issue [#4639](https://github.com/go-to-k/cdkd/issues/4639), data / streaming slice)** -- the `glue`, `firehose`, `kinesis-streamconsumer`, `pipes`, `cloudtrail`, `s3-vectors`, `s3-tables` and `s3-directory-bucket` providers. Glue `CreateDatabase` / `CreateTable` / `CreateWorkflow` / `CreateSecurityConfiguration` / `CreateJob` / `CreateCrawler` / `CreateConnection` / `CreateTrigger`, Firehose `CreateDeliveryStream`, Kinesis `RegisterStreamConsumer`, Pipes `CreatePipe`, CloudTrail `CreateTrail`, S3 Vectors `CreateVectorBucket`, S3 Tables `CreateTableBucket` / `CreateNamespace` / `CreateTable` and S3 Express `CreateBucket` carry no idempotency token and were sent through a client whose SDK retry replays a 5xx even when AWS completed the request. The replay collided with the resource the first request made, the collision was credited to another holder, and the resource was left in no state record for every re-run to collide with. They now go through a dedicated client that refuses the SDK's 5xx retry, built with the same region and identity as the provider's other calls, so the 5xx reaches the deploy engine, which marks a later collision as possibly this create's own. Nothing is adopted. Scheduler `CreateSchedule` (its SDK-filled `ClientToken` is serialized once and reused by the SDK's retries) and S3 `CreateBucket` (a replay answers `BucketAlreadyOwnedByYou`, or 200 in us-east-1, and both paths already record the bucket) are unchanged. A failed Pipes create or update now passes AWS's error text through the secret masker before it reaches the error message. Tests: `tests/unit/provisioning/*-create-retry-4639.test.ts`, `scheduler-create-token-4639.test.ts`.
