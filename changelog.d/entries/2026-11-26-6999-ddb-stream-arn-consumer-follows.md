- **`cdkd deploy`: changing a DynamoDB table's stream view type moves its Lambda event source mapping onto the new stream (issue [#6999](https://github.com/go-to-k/cdkd/issues/6999))** -- `src/analyzer/diff-calculator/shared.ts`. A `StreamSpecification` change (for example `stream: NEW_IMAGE` to `NEW_AND_OLD_IMAGES`) disables the table's stream and creates a new one with a new ARN. The event source mapping that `fn.addEventSource(new DynamoEventSource(table, ...))` creates was left on the disabled old stream while the deploy exited `0`, so the function stopped receiving the table's changes until another deploy, and `cdkd drift` reported nothing. cdkd now treats `StreamArn` as moving with `StreamSpecification` on `AWS::DynamoDB::Table` and `AWS::DynamoDB::GlobalTable`, so the mapping (and the consumer role's policy naming the stream) is updated in the same deploy and the mapping is replaced onto the new stream, as CloudFormation does; `cdkd diff` lists the mapping as a possible replacement. A table update that leaves `StreamSpecification` alone touches neither. Tests: `tests/unit/analyzer/diff-calculator-stream-arn-6999.test.ts`; integ `dynamodb-streams` phases M1, M2 and M4.
