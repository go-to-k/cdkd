- **An `AWS::ECS::TaskDefinition` `Tags` change now updates the same revision in place, and an `AWS::ECS::Service` `LaunchType` change replaces the service instead of being silently dropped (issue [#5392](https://github.com/go-to-k/cdkd/issues/5392))** -- `src/provisioning/providers/ecs-provider.ts`, `src/analyzer/replacement-rules.ts`. Every task definition update was refused, so a tags-only change failed the deploy and pointed at `--replace`; CloudFormation tags the same revision (measured: `Replacement: False`, same ARN), and cdkd now does too with `TagResource` / `UntagResource`. A change to any other task definition property is still refused on that path; a value state records as its secret reference is compared by what it resolves to. `UpdateService` has no launch type member, so a changed or added `LaunchType` was recorded in state while AWS kept the old one. As in CloudFormation (measured), it now replaces the service, and a removed `LaunchType` stays an in-place update that keeps the live launch type; `update()` refuses a launch type changed between two values that reaches it, and under `cdkd drift --revert` also one the AWS readback lacks (a service moved to a capacity provider strategy). Unit cases in `tests/unit/provisioning/ecs-provider.test.ts`, `tests/unit/provisioning/ecs-provider-roundtrip.test.ts` and `tests/unit/analyzer/replacement-rules-ecs-service-launch-type.test.ts`; the new `ecs-taskdef-tags-launch-type` integ fixture covers all three.
