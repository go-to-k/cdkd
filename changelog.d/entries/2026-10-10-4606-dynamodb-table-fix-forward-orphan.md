- **A fix-forward deploy now deletes the DynamoDB table an earlier failed CREATE left behind (issue [#4606](https://github.com/go-to-k/cdkd/issues/4606), DynamoDB table slice)** -- `src/provisioning/providers/dynamodb-table-provider.ts`. When a `cdkd deploy --no-rollback` made an `AWS::DynamoDB::Table`, failed configuring it (a TTL, point-in-time recovery or stream setting) and could not delete it again, and a later deploy kept the logical id under another table name, the successful deploy warned about the earlier table, left it in AWS and exited 2: it could not prove the two were different tables, nor that the table under the old name was still the one the failed CREATE made. The DynamoDB provider now answers both by the table's `TableId`, which AWS generates and never reuses: the failed CREATE records the id its `CreateTable` returned, and the successful deploy deletes the earlier table only when the record's table reads back under another `TableId` and the old name still reads back under the recorded one. A table deleted by hand and re-created under the name has another `TableId` and is kept, with a warning. The same identity serves `cdkd rollback` and `cdkd destroy` for such a journaled table. Tests: `tests/unit/provisioning/dynamodb-table-provider-same-resource-4606.test.ts`; integ: `dynamodb-fix-forward-orphan`.
