- **A reader promoted because a value it reads may move now treats a create-only property as create-only on every type, not only the ~28 in the hand-written replacement registry (issue [#3803](https://github.com/go-to-k/cdkd/issues/3803))** -- `src/analyzer/diff-calculator.ts`, unit tests, `docs/architecture.md`.
  - **Before.** Both promotion passes, replacement propagation and in-place attribute propagation, asked only the registry. On any other type, for example `AWS::RDS::DBInstance.MasterUsername` or `AWS::IAM::ManagedPolicy.Description`, a moved value in a create-only property was sent to an in-place `update()`. There it was ignored, so the resource stayed stale under a green deploy, or it was refused.
  - **Now.** The passes use the ordinary diff's CFn-schema createOnly fallback wherever the registry has no opinion. Only a whole-property create-only path counts; a nested one (`ConnectionInput.Name`) stays in place, as before.
  - **What this means in practice.** The result is the usual replacement ceiling. The deploy still updates or skips the reader when the value did not move (including a `NoEcho` value AWS confirms). It replaces the reader when the value did move, and a stateful type stops at `STATEFUL_REPLACE_BLOCKED`.
