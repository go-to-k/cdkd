- **A re-deploy no longer fails with `Method already exists for this resource` after an API Gateway `Method` was left behind (issue [#5294](https://github.com/go-to-k/cdkd/issues/5294))** -- `src/provisioning/providers/apigateway-provider.ts`. When a `Method`'s wiring (`PutIntegration`, `PutMethodResponse`, `PutIntegrationResponse`) failed after `PutMethod` and the cleanup `DeleteMethod` failed too, the method stayed in API Gateway with no state record, and every later deploy of the stack failed on `PutMethod` until it was deleted by hand. Now, when `PutMethod` answers `ConflictException` "already exists", the method is deleted and put again with the template's wiring (a warning names it) only on the stack's own proof that an earlier attempt of the same logical id left THAT method behind: a failed CREATE the rollback journal records with that method's id as one the provider proved it made (`provenOrphanIdsInJournal` in `src/deployment/prior-attempt-scope.ts`, supplied by `src/deployment/deploy-engine/provision.ts`), or an earlier attempt of the same dispatch. A bare attempted bag is not enough, since a create another owner's method refused leaves one too; without proof, with an unreadable journal, or on a concurrent-modification `ConflictException`, AWS's refusal is kept. A leftover already gone at the delete is put again. Unit cases in `tests/unit/provisioning/apigateway-method-left-behind-5294.test.ts` and `tests/unit/deployment/deploy-engine-prior-attempt-binding.test.ts`.
