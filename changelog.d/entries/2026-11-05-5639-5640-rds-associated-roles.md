- **The SDK provider attaches `AssociatedRoles` for `AWS::RDS::DBCluster` and `AWS::RDS::DBInstance` (issues [#5639](https://github.com/go-to-k/cdkd/issues/5639), [#5640](https://github.com/go-to-k/cdkd/issues/5640))** -- `src/provisioning/providers/rds-provider.ts`, a new `src/provisioning/providers/db-associated-roles.ts` that `neptune-provider.ts` now shares, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, a new unit file, the RDS wire cases, new arms in the `rds-aurora` and `rds-dbinstance-backfill` integs, the RDS row of the `--no-wait` table in `docs/cli-deploy.md`, and the RDS removal rule in `docs/provider-rules.md`. Before, a cluster or instance declaring roles routed through Cloud Control. A create attaches each role with `AddRoleToDBCluster` / `AddRoleToDBInstance` once the resource is `available`; an update detaches the roles the template dropped and attaches the ones it added, as CloudFormation's handler plans them, skipping what AWS already shows done, so a retry neither attaches nor detaches twice. A role attached outside cdkd is left alone, and a declared role detached outside cdkd is not attached again by an unrelated update; `AWS::Neptune::DBCluster`, which shares the plan, now does the same. Removing the whole list detaches every recorded role, as CloudFormation's handler does. Both calls wait for `available` first, under `--no-wait` too; otherwise the deploy waits until each change reads back. A malformed list is refused before any call, and a DB instance's entry needs its `FeatureName`. `cdkd drift` reads the roles back, in any order. Resources already deployed through Cloud Control stay there.
