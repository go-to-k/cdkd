- **ECS local commands: task-role credentials reach the containers, `--env-vars` skips the secret fetch, same-stack ECR images take `--image-override`, and two `start-alb` runs coexist (issues [#5755](https://github.com/go-to-k/cdkd/issues/5755), [#5756](https://github.com/go-to-k/cdkd/issues/5756), [#5763](https://github.com/go-to-k/cdkd/issues/5763))** -- `package.json` (`cdk-local` `^0.158.0` -> `^0.158.1`), `src/local/ecs-network.ts`, `src/local/ecs-task-runner.ts`, `src/local/ecs-task-resolver.ts`, `docs/local-run-task.md`, `docs/local-start-service.md`, `docs/local-start-alb.md`, `docs/local-start-service-image-overrides.md`, `docs/local-emulation-value-resolution.md`. `cdkd local run-task --assume-task-role` set `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI=/role/<arn>`, which the metadata sidecar answers 404, so no container got the task role's credentials; it now sets `/creds`, where the sidecar serves the assumed credentials. `run-task` no longer fetches an ECS `Secrets` entry whose key the `--env-vars` file gives; the file's value for a declared secret, or for one dropped for lack of state, stays off the `docker run` argv. From cdk-local: `start-service` / `start-alb --assume-role` serve the credentials the same way, on `169.254.170.0/24`, and refuse services that resolve to different task roles; an image from an `AWS::ECR::Repository` in the same stack is a target `--image-override` can replace, and is refused before boot when nothing covers it; the new `--image-context` flag sets the build context of an override build; their `--env-vars` skips the secret fetch too; and concurrent `start-service` / `start-alb` runs pick non-overlapping subnets.
