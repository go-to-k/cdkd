- **`cdkd destroy` no longer reports SUCCESS having deleted nothing over a record whose `resources` map cannot be read, and `cdkd deploy` no longer re-creates the whole stack from one (issue [#3161](https://github.com/go-to-k/cdkd/issues/3161))** -- `src/cli/commands/destroy-runner.ts`, `src/deployment/deploy-engine.ts`, `src/state/malformed-resources-bag.ts`, `src/analyzer/diff-calculator.ts`, plus their new suites and cases in `malformed-resources-bag.test.ts`. `parseStateBody` validates nothing inside a record, so `resources` could hold a string, a list, a number, a boolean or `null`. The destroy routed on `Object.keys(state.resources).length`, which splits three ways and the middle one was the damage: `[]`, a number or a boolean enumerate NO keys, so the count was `0`, the run took the empty-stack fast path, deleted `state.json` with no confirmation, and reported success -- leaving every resource the record named live in AWS and untraceable. A string enumerated one fabricated logical id per character; `null` or an absent field threw a bare `TypeError`. The deploy read the same map and planned every template resource as a `CREATE`. Both now REFUSE (`STATE_RESOURCES_MALFORMED`, exit `1`) at their state load, above the first read -- the destroy before the prompt AND the lock, and again on the record the fast path re-reads under it; the deploy before any provider call or state write, **under `--dry-run` too**. Repairing to `{}` is not the safe half: `[]`, a number and a boolean ARE the repaired case and each reaches the identical outcome, measured through the real runner and the real `DiffCalculator`. The discriminator is the container's SHAPE, never its size, so a legitimately empty `{}` still takes the fast path and still deploys. The destroy refusal names `cdkd state orphan` for dropping the record while leaving the live resources standing. `cdkd diff` and `cdkd state show` still repair and warn.
