- **A malformed `Tags` no longer untags a CloudWatch Logs log group or a Glue resource (issue [#4073](https://github.com/go-to-k/cdkd/issues/4073))** -- `src/provisioning/providers/logs-loggroup-provider.ts`, `glue-provider.ts`, now reading `Tags` through `src/provisioning/tag-list.ts` as [#3994](https://github.com/go-to-k/cdkd/issues/3994) did for the other providers. The `AWS::Logs::LogGroup` update untagged every recorded key and re-tagged the raw desired value on any `Tags` difference, so a malformed desired `Tags` (reachable on a rollback or `cdkd drift --revert`) stripped every tag, and a recorded bare string failed the update; it now untags only the keys the template dropped and sets only new or changed tags, sent to the log-group ARN without the trailing `:*`. The `AWS::Glue::Job` / `Crawler` / `Trigger` diffs read a non-object `Tags` as none and dropped or coerced malformed entries, then untagged every recorded key the short desired side lacked; a `null` list entry threw a `TypeError`. For every Glue type that declares `Tags` (a key -> value map; a `{Key, Value}` list is read too), and for the log group, a malformed desired `Tags` is refused before any AWS call on create and update, naming the property but never its content; a malformed recorded `Tags` is applied ADD-only with a warning; a recorded key holding a dynamic reference or its mask is never untagged. Separately, `AWS::Glue::Workflow` now applies a `Tags` change on update; it used to drop it. A number or boolean Glue tag value is now sent as its string instead of `''`. Neither repairs a resource already deployed that way until its `Tags` change again: run `cdkd drift --revert` to bring such tags back to the template. A log group create or update error now passes through the secret masker. Tests: `logs-loggroup-provider-malformed-tags-4073.test.ts`, `glue-provider-malformed-tags-4073.test.ts`.
