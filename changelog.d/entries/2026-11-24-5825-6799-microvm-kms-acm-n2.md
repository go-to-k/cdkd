- **`AWS::Lambda::MicrovmImage` `KmsKeyIdentifier` and `AWS::CertificateManager::Certificate` `RootHierarchyType` / `CertificateUsage` are now written by the SDK providers, so a resource declaring them is no longer routed through Cloud Control (issues [#5825](https://github.com/go-to-k/cdkd/issues/5825), [#6799](https://github.com/go-to-k/cdkd/issues/6799))** -- `src/provisioning/providers/lambda-microvm-image-provider.ts`, `src/provisioning/providers/acm-certificate-provider.ts`, `src/provisioning/providers/acm-certificate/{create,read-state,update}.ts`. The MicroVM image key goes on `CreateMicrovmImage` and `UpdateMicrovmImage`. A change or removal rebuilds the image, and a removal builds on an AWS owned key. It stays out of the drift comparison because the CloudFormation schema marks it write-only. The two Amazon N2 certificate properties go on `RequestCertificate` and are read back for `cdkd drift`. Both are create-only, so a change replaces the certificate, as under CloudFormation. An N2 certificate requested without `CertificateUsage`, which ACM reports as `CLIENT_AND_SERVER_AUTH`, is not a change on `drift --revert`. A resource already recorded on the Cloud Control route stays there.
