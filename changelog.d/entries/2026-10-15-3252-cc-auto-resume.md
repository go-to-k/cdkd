- **A Cloud Control create cdkd stopped waiting for is now resumed by the next `cdkd deploy`, and settled by `cdkd destroy` and `cdkd rollback` (issue [#3252](https://github.com/go-to-k/cdkd/issues/3252))** -- `src/deployment/cc-pending-requests.ts`, `src/deployment/deploy-engine/create.ts`, `src/deployment/deploy-engine/deploy-flow.ts`, `src/deployment/deploy-engine/execute.ts`, `src/deployment/deploy-engine/rollback.ts`, `src/provisioning/cloud-control-provider.ts`, `src/provisioning/wait-abandoned.ts`, `src/deployment/rollback-executor/journaled-orphans.ts`, `src/cli/commands/destroy-runner.ts`, `src/cli/commands/rollback.ts`, `src/cli/commands/rollback-drop-failed.ts`, `src/state/s3-state-backend.ts`, `src/types/rollback-journal.ts`, `src/deployment/rollback-executor/orphan-identity.ts`. When a network outage made cdkd give up on a Cloud Control create, the request token was printed and lost, and the user had to check it and import or delete the resource by hand. The rollback journal now records it (`pendingCloudControlRequest`, additive, no `journalVersion` bump). The next deploy, destroy or rollback reads the request's status under the stack lock before anything else. Whether its id is unique is read from the type's registry schema: a read-only primary identifier field AWS minted, not a name the create sent. A deploy whose template still declares the resource with the same properties takes a unique one over instead of creating another; otherwise it becomes a journaled resource the failed deploy created, deleted when its id is unique and named in a warning, with the `cdkd import` remedy, when it is a name. A create that made nothing, or that Cloud Control no longer has (requests expire after seven days), is forgotten. One still unknown refuses the command, which names the status command and `cdkd rollback --drop-failed`.
