- **`cdkd state refresh-observed <stack> --accept-refused <LogicalId> --template <file>` clears one resource's parameter baseline refusal on the user's assertion (issue [#3466](https://github.com/go-to-k/cdkd/issues/3466))** -- new `src/cli/commands/state-refresh-observed.ts`, `src/cli/commands/state.ts`, `src/cli/commands/refused-baseline-remedy.ts`, `docs/cli-state-writing.md`, `docs/cli-destroy-prompts.md`. Previously an `unverifiable-parameter` (or reason-less) refusal cleared only on replacement or a re-import a CloudFormation stack could prove, impossible after `--migrate-from-cloudformation`. The new flag takes one logical id of one stack (`--all`, several stacks and a second id are refused) and the template the stack was last deployed from. It refuses an `incomplete-resolution` refusal, a resource the template does not define or types differently, a template it cannot judge, a resource that still reads a declared parameter (directly or through another resource's attribute), a record that does not hold exactly what the template defines (`Ref` / `Fn::GetAtt` / `Fn::Join` / `Fn::Sub` / `Fn::Select` evaluated against the stack's records, anything else refused), and a record holding a parameter's `Default`. The prompt states the assertion: AWS holds no secret the template does not spell as a dynamic reference, because whatever it holds is written to `state.json`. `-y` / `--yes` logs it as a warning instead; without it a non-interactive run is refused. Only that resource is read back, through the same position-based redaction as any refresh, and both `observedBaselineRefused` and `observedBaselineRefusalReason` are removed only after the read succeeds. The sticky remedies name the command. Tests: `tests/unit/cli/state-refresh-observed-accept-refused.test.ts`. Integ `import-deployed-parameter-secret` step 6d refuses an undeployed template and the parameter-bound record, then accepts a function moved to a dynamic reference.
