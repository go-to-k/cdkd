- **A failed CloudWatch Logs log group, EventBridge Scheduler schedule, DLM lifecycle policy or EventBridge Pipes pipe operation, and a failed detach of an RDS cluster from its global cluster, no longer write the caller's account id, assumed-role ARN and session name into the persisted deployment events (issue [#2319](https://github.com/go-to-k/cdkd/issues/2319))** -- `src/provisioning/providers/{logs-loggroup,scheduler-schedule,dlm-lifecycle-policy,pipes,rds}-provider.ts`, and unit cases. The thrown message quoted AWS's raw text, which names the caller on an access denial, and `deployments/{runId}.jsonl` outlives the run. The message now carries the error class (for example `AccessDeniedException. Re-run with --verbose for AWS's own message.`), and AWS's text goes to the debug log, through the operation's secret masker. This covers the create, update and delete failures of the four types, the `Fn::GetAtt` lookup failure of a schedule, lifecycle policy or pipe, a pipe's `*_FAILED` state reason, and the RDS `RemoveFromGlobalCluster` / `DescribeGlobalClusters` failures that stop a cluster delete. A cdkd-authored or transport error keeps its text, masked through the operation's secret masker on every create, update and delete wrap. Each wrap that carried the AWS error as its `cause` still does, so an IAM grant that is still propagating is retried as before, and an "already exists" is still stated as such (except for a log group's create-time wiring call, where "it" would read as the log group).
