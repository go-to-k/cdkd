- **An `AWS::RDS::DBInstance` declaring `ProcessorFeatures` or `UseDefaultProcessorFeatures` stays on the SDK provider (issue [#5640](https://github.com/go-to-k/cdkd/issues/5640))** -- `src/provisioning/providers/rds-provider.ts`, `src/provisioning/providers/rds/instance-members.ts`, `instance-create.ts`, `instance-update.ts`, `read-state.ts` and `drift.ts` beside it, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, a new unit file, the RDS wire cases, and a new `rds-dbinstance-processor-features` integ (SQL Server Web on `db.m7i.large`, the cheapest engine offering processor features). Before, either property routed the instance through Cloud Control. As CloudFormation's handler sends them, the list rides `CreateDBInstance` (the flag is no member there), both ride a read replica's create, and an update sends the desired values of both only when either changed, applied immediately and waited out. Removing `ProcessorFeatures` therefore leaves the instance's features as they are, as under CloudFormation; declare `UseDefaultProcessorFeatures: true` to restore the class defaults. A malformed value is refused before any call. `cdkd drift` compares the live list only where the template declares it, and only the features it names, and never the write-only flag.
