- **The `cdkd force-unlock ...` command a lock-contention failure tells you to run can no longer be redrawn by its own `--profile` / `--state-bucket` / `--state-prefix` (issue [#3377](https://github.com/go-to-k/cdkd/issues/3377), widened by go-to-k/cdkd#3390's review)** -- `src/state/lock-contention-message.ts`, `src/cli/commands/state.ts`. All three fragments reached the terminal through `shellQuote` ALONE, which is the wrong instrument: inside `'...'` an injected `\ncurl ... | sh` is a literal, while an ESC still redraws the line. The BUCKET is third-party plantable -- `config-loader.ts` resolves it from a repo's `cdk.json` `context.cdkd.stateBucket`, so cloning a repository chooses it. All three now take one shared sanitize + EXACTNESS guard, the same pair the stack name and region already took: a fragment whose rendering CHANGED names a different lock, and for `--profile` a different ACCOUNT, so the whole command is suppressed rather than pointed at the wrong one. They take the DENYLIST where the stack name and region take the ASCII allowlist, because those two come from an S3 key and have a known charset while a profile name does not -- `asciiOnly` would have deleted the entire hint for `prod-café`. Three sentences told a user WHICH value could not be shown and two of them still said "the name or region"; they now share one binding, so the list cannot go stale in one copy again.
