- **Removing `VpcSecurityGroupIds` from an RDS or Neptune DB cluster now moves the cluster to its VPC's default security group, as CloudFormation does (issue [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/rds-provider.ts`, `neptune-provider.ts`, `docdb-provider.ts`, `tests/unit/provisioning/db-cluster-sg-removal-1160.test.ts`. Before this change, cdkd sent no security groups when the property was removed, and `ModifyDBCluster` then kept the removed groups attached while the deploy reported success. A real CloudFormation A/B showed CloudFormation attaches the VPC's `default` security group in place of the removed ones on `AWS::RDS::DBCluster` and `AWS::Neptune::DBCluster`. cdkd now finds that group (the cluster's DB subnet group gives the VPC; `ec2:DescribeSecurityGroups` gives the group named `default`) and sends it. If the group cannot be found, the update fails before any change and says to declare `VpcSecurityGroupIds`. The lookup runs only on this removal, and the deploy credentials need `ec2:DescribeSecurityGroups` for it. A warning names the group attached. An update that changes a cluster's security groups (this reset, or a changed declared list, DocDB included) now waits until the cluster reports the new groups `active` and each member instance is `available`, as CloudFormation does, so a member instance's own change in the same deploy is no longer refused with "Database instance is not in available state"; `--no-wait` skips the wait, as it does on create. An empty list is still never sent, and `cdkd drift --revert` does not reset. `AWS::DocDB::DBCluster` is unchanged: CloudFormation keeps a DocDB cluster's groups on removal, and so does cdkd.
