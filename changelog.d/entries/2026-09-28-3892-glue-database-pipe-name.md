- **A Glue table in a database whose name contains `|` now deploys, updates, destroys and resolves `Ref` as in CloudFormation (issue [#3892](https://github.com/go-to-k/cdkd/issues/3892))** -- `src/provisioning/providers/glue-provider.ts`, `src/provisioning/composite-id.ts`, `src/deployment/intrinsic-function-resolver.ts`, `src/deployment/deploy-engine.ts`; unit tests in `tests/unit/provisioning/`, `tests/unit/deployment/intrinsic-{functions,ref-state-mask}.test.ts` and `tests/unit/analyzer/orphan-rewriter.test.ts`; assertion 12 of the `glue-update-hardening` fixture. Glue accepts `|` in a database name (probed through that fixture), but `cdkd deploy` and `cdkd import` refused a table in such a database. The table's id stays `<databaseName>|<tableName>`, and every reader places the table name by the recorded `DatabaseName`, which a create always records; `cdkd import` also records it as an attribute, so `Ref` can anchor when the imported property stays unresolved. Without a usable anchor, update and destroy still refuse or skip an id with more than one `|` rather than guess, and their message now says to set the record's `DatabaseName` rather than edit a correct id. A masked `DatabaseName` refuses a `Ref` that needs it on deploy, and passes the mask through elsewhere, since the first-`|` fallback is no longer exact. The refusal for an output with such a masked value no longer claims it would publish the raw physical id. Because two different tables can now share an id (table `db|orders` in database `my`, table `orders` in database `my|db`), a replacement between them keeps the id: the deploy engine's name-idempotent-create guards and the rollback's replacement, already-reverted and adopted-live readings now treat two records whose `DatabaseName` both prefix the id and differ as two tables (`equalIdNamesDifferentResources` in `src/deployment/type-change-guard.ts`), so such a replacement completes and rolls back instead of stranding the new table.
