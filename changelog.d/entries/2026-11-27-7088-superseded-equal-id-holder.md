- **`cdkd deploy` / `cdkd rollback` / `cdkd destroy`: an old copy whose new copy carries the same physical id while naming another resource stays tracked when its delete fails (issue [#7088](https://github.com/go-to-k/cdkd/issues/7088))** -- `src/deployment/superseded-resources.ts` (`namesSameResource`), `src/deployment/deploy-engine/nested-cleanup.ts`, `src/deployment/rollback-executor/replay-moved-id-cleanup.ts`. The superseded-resource bookkeeping read "same physical id and same type" as one resource. A stage moved to another REST API keeps its id (`prod`), as do a Lambda permission on another function, an ingress rule from another source, a Glue table in another database, and an ingress record holding another `sgr-` id. So when the old copy's delete failed (a base path mapping still used the old stage), the deploy's save dropped its `supersededResources` entry as "held" by the new record, and the old stage stayed in AWS untracked, while the warning said cdkd kept it; a later `cdkd destroy` then failed on the deployment it used. The holder checks (the save, the carried-row retry, `cdkd destroy`, a rollback's deferred delete of the new copy) and the entry de-duplication now ask `equalIdNamesDifferentResources` / `recordedIdsNameDifferentResources` whether the two records name the same resource; a record of another type under the id still holds it, as before. Tests: `tests/unit/deployment/superseded-equal-id-7088.test.ts`; integ fixture `tests/integration/superseded-stage-equal-id/`.
