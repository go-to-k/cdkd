- **`--recreate-via-*` creates first for a renamed resource whose name only the replacement name keys read (issue [#6589](https://github.com/go-to-k/cdkd/issues/6589))** -- `src/deployment/replacement-name-holder/holder-probe.ts`, `src/deployment/deploy-engine/replacement/name-change.ts`, `src/deployment/deploy-engine/update-replace.ts`, `src/deployment/deploy-engine/update-replace/recreate.ts`, `src/deployment/superseded-resources.ts`, `docs/cli-deploy-safety-recreate.md` and unit tests. A recreate whose template also renamed the target deleted the old resource first when the type's name was not in the adoption tables (an `AWS::Logs::DeliverySource`, an `AWS::Logs::DeliveryDestination`, an `AWS::Events::Archive`). An `AWS::Logs::Delivery` still using the old source then made CloudWatch Logs refuse that delete (`ConflictException`), and the deploy failed and rolled back. Such a rename now creates the new resource first and deletes the old one in the cleanup phase, after its dependents have moved, as a renamed recreate of a type with an adoption-table name already did. A name that cannot be read (a mask, an unrecorded old name) keeps the delete-first order. When a delete-first recreate fails with an in-use or conflict refusal and same-stack records depend on the target, the error now names them and says to rename the target or to remove them, deploy, recreate and add them back.
