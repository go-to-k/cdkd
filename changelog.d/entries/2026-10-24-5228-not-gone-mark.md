- **A delete failure that is not proof the resource is gone keeps its retries (issue [#5228](https://github.com/go-to-k/cdkd/issues/5228))** -- `src/provisioning/not-gone.ts` (new), the three already-deleted classifiers (`src/deployment/deploy-engine/delete.ts`, `src/deployment/deploy-engine/update-in-place.ts`, `src/cli/commands/destroy-runner.ts`), and the delete guards in the Cloud Map, ECS, CodeCommit, CloudFront, API Gateway Account, Scheduler and Cloud Control providers, with their unit suites and a new unit file. Before, the only way a provider could stop those classifiers reading a needle such as `NotFound` in a delete failure's message as "already deleted" was to mark the failure non-retryable. So a guarded failure lost every retry, and a transient failure that carried a needle (a throttle on a logical id like `PageNotFound`) could not be guarded: once its retries ran out, the classifiers dropped a live resource's state record. Now a dedicated not-gone mark, which the classifiers refuse, carries that verdict on its own. Each guard sets it instead, so a retry the failure qualifies for comes back, and Cloud Control marks a needle-bearing failure whether or not it is transient.
