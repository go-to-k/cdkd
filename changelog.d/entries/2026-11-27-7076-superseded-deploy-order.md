- **`cdkd deploy`: an old copy an earlier deploy could not delete (`supersededResources`) is deleted before the resources this deploy removes that it uses, so removing a VPC no longer fails on a kept old security group (issue [#7076](https://github.com/go-to-k/cdkd/issues/7076); the deploy half of [#7073](https://github.com/go-to-k/cdkd/issues/7073))** -- `src/deployment/deploy-engine/carried-users-of-removals.ts`, `src/deployment/deploy-engine/execute.ts`, `src/analyzer/implicit-delete-deps.ts`. A deploy retried such a kept old copy only in its cleanup, after its removal deletes, so a template that removed the VPC deleted the VPC while the old group still lived in it: the VPC delete waited, failed `DependencyViolation`, and was kept until the next deploy. Before its removal deletes, a deploy now deletes each kept old copy whose record names a removed resource, or whose type must be deleted before a removed resource's type (the table the delete order uses), and the kept copies using those, as it already did for this deploy's own replaced resources (#6977). Each is sent once there; one that fails keeps its entry and is sent again in the cleanup. Nothing is taken early when a removed resource may still use a taken copy, nor a copy held for consumer stacks (#7017). A deploy whose kept copies use no removed resource makes no extra call. Tests: `tests/unit/deployment/deploy-engine-carried-users-of-removals-7076.test.ts`; integ fixture `tests/integration/superseded-sg-destroy-order/` (a v3 deploy that removes the VPC), which now keeps the old group by stopping the replacing deploy instead of waiting out its delete.
