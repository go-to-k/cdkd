- **`--from-cfn-stack` on `cdkd local invoke` / `start-api` / `run-task` / `invoke-agentcore` now reads the deployed stack with your own credentials instead of the `--role-arn` role, and the four engine `start-*` commands warn at startup when the role reaches the container (issue [#3240](https://github.com/go-to-k/cdkd/issues/3240))** -- `src/cli/commands/local-state-source.ts`, `src/cli/commands/local-start-service.ts`, `src/cli/commands/local-start-alb.ts`, `src/cli/commands/local-start-cloudfront.ts`, `src/cli/commands/local-start-agentcore.ts`. With `--role-arn` and no profile, the `--from-cfn-stack` reader resolved as the role, so a SecureString parameter the caller could not read was decrypted and baked into the container's environment, and the deployed function's environment was read the same way. cdkd now builds that reader's CloudFormation / Lambda / SSM / AgentCore clients on the caller's identity, matching what `--profile` already gave; a cross-account stack the caller cannot read now falls back with the reader's own warning. If a future cdk-local release changes the members cdkd reviewed, the command refuses under a role with no profile rather than read as it. `start-service` / `start-alb` / `start-cloudfront` / `start-agentcore` run inside the local emulation engine, which accepts no caller credentials yet (go-to-k/cdk-local#783); they now print a warning naming what reaches the role (container credentials, ECS task secrets, `${AWS::AccountId}`, `--from-cfn-stack`, the STS call behind `--assume-role`) when `--role-arn` or `CDKD_ROLE_ARN` is set without the `--profile` flag. Tests: `tests/unit/cli/local-state-source-caller-identity.test.ts`.
