- **A rollback no longer strips every property off a live resource when the record it would restore has no usable `properties` bag (issue [#3203](https://github.com/go-to-k/cdkd/issues/3203))** -- `src/deployment/rollback-executor.ts`, one new suite. All three replay arms coalesced the desired bag (`desiredProps ?? {}`), and `{}` is not a no-op: it is a complete desired state saying "this resource has no properties". A patch provider then removes every key; an SDK provider may reset a subset or, where the bag names the resource, replace it; and the reverse-replacement arm CREATES a default-configured resource and DELETES the live one. Each arm now refuses to replay such a bag, and the disposition follows what the record HOLDS: an ABSENT bag is SKIPPED (nothing was recorded, so nothing is repairable — the `skip-failed-absent` precedent), while a PRESENT but unusable one (`null`, a string, an array) FAILS the op, keeping the journal so the record can be repaired and the rollback re-run — the `refuseMaskedReplayBaseline` precedent. Either way the pass continues. Each message names the remedy its arm supports: `cdkd deploy`, or `cdkd drift` on `--revert-failed`, where the op died mid-flight so `cdkd diff` (which reads `state.properties`, not AWS) would report no change. The predicate tests "is this a plain object", not "is it absent": `null ?? {}` is also `{}` -- shapes issue [#3149](https://github.com/go-to-k/cdkd/issues/3149) refuses at the parser for a JOURNAL-sourced record, while `previousState` is equally often STATE-sourced, where nothing validates them. A present but empty `{}` still replays: a resource that really has no properties is a legitimate thing to restore to. Recorded rather than implied: the `reverse-replacement-readopt` arm writes such a record into `state.json`, but it sends NO desired bag to a provider, so it is issue [#3211](https://github.com/go-to-k/cdkd/issues/3211)'s class rather than this one's.
