- **`cdkd local` reads a `cdk.Stage` stack's asset manifest by the name the assembly gives it (issue [#5872](https://github.com/go-to-k/cdkd/issues/5872))** -- `src/assets/asset-manifest-loader.ts` (new `loadStackManifest`), `src/cli/commands/local-invoke.ts`, `src/cli/commands/local-start-api/container-spec.ts`, `src/cli/commands/local-invoke-agentcore.ts`, `src/local/ecs-task-runner.ts`, `src/local/invoke-agentcore-watch-loop.ts`. These readers rebuilt the manifest's file name as `<stackName>.assets.json`, but CDK names a Stage stack's manifest after its artifact id (`devlocalApi6B226F7F.assets.json`, not `dev-local-Api.assets.json`). So `cdkd local invoke` / `start-api` stopped on a `DockerImageFunction` in a Stage with "Container Lambda ... has no matching asset in cdk.out", `cdkd local run-task` and the other ECS paths that build through `runEcsTask` stopped on a CDK-asset container image there with "No asset manifest at ... for stack ...", and `cdkd local invoke-agentcore` could not find a Stage runtime's image or code bundle. They now read the file `StackInfo.assetManifestPath` names, and fall back to `<stackName>.assets.json` only for a record without one. Tests: `tests/unit/assets/asset-manifest-loader.test.ts`, `tests/unit/local/ecs-task-runner-runner.test.ts`.
