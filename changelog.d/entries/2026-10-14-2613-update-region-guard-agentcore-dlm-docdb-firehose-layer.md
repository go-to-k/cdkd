- **An update of a Bedrock AgentCore evaluator or runtime, a DLM lifecycle policy, a DocumentDB subnet group, a Kinesis Data Firehose delivery stream or a Lambda layer version is refused when the AWS client's region differs from the region recorded in cdkd state (issue [#2613](https://github.com/go-to-k/cdkd/issues/2613))** -- `src/provisioning/providers/{agentcore-evaluator,agentcore-runtime,dlm-lifecycle-policy,docdb-subnet-group,firehose,lambda-layer}-provider.ts` (`update()` now takes the `UpdateContext` and calls `assertRegionMatch` before any AWS call), `src/provisioning/providers/{agentcore-browser,agentcore-code-interpreter,wait-condition-handle}-provider.ts` (they take the `UpdateContext` too, with no guard: their `update()` sends nothing), `scripts/check-provider-update-context.ts` (nine names leave `OMITS_UPDATE_CONTEXT`), and unit cases in each provider's test file. These providers ignored the recorded region on update, so a deploy, rollback or `cdkd drift --revert` run with a client in another region sent its writes there -- for a subnet group or a delivery stream, to whatever carried the same name in that region, a resource cdkd does not manage. A DLM `DefaultPolicy` change and any Lambda layer version update instead failed with a "cannot be updated in place" error pointing at a replacement, the wrong next step when it is the region that disagrees. The update now stops before the first call and names both regions. An update whose state record has no region is unchanged.
