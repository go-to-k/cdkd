- **`state.imports` / `state.outputReads` no longer persist a secret in plaintext, and `cdkd deploy`'s recreate prompt no longer silently omits a consumer it cannot name.** Both lists carry names the resolver took from the TEMPLATE and both rode `redactStateForPersist`'s `...state` spread untouched, so an `Fn::ImportValue` / `Fn::GetStackOutput` whose name an `Fn::Sub` assembled around a resolved `{{resolve:secretsmanager:...}}` wrote that plaintext into `state.json` and kept it there. `imports[].exportName`, `outputReads[].outputName` and `outputReads[].sourceStack` are now redacted back to the unresolved expression at persist; `sourceRegion` and `imports[].sourceStack` deliberately are NOT. No state schema bump — the fields keep their shape. The third of those IS the literal key `findDownstreamConsumers` matches on, so a redacted entry can never match a live stack name; rather than vanish from a DATA-LOSS `[y/N]` prompt it is now reported, region-narrowed, with a line saying cdkd cannot name the producer and that it may or may not be this stack — asserting that cdkd cannot rule the dependency out, never that it holds. Changed: `src/deployment/deploy-engine.ts`, `src/cli/commands/recreate-downstream-consumers.ts`. Issue go-to-k/cdkd#3289; the per-field provenance table, why redaction sits at persist rather than record time, and the no-bump reasoning are in `docs/design/3289-cross-stack-read-name-redaction.md`. Residuals: `MIN_NEEDLE_LENGTH` still applies, so an EMBEDDED secret of 1-3 characters is not substituted (a whole-value one is, at any length); and a record an older binary wrote self-repairs only if a later deploy re-resolves that reference to the SAME value — if the secret has since ROTATED, or it is never re-resolved again, the stale plaintext survives, and `cdkd scrub` cannot reach the rotated one either. `cdkd scrub` is owed the repair (go-to-k/cdkd#3337).
