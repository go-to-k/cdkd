- **`cdkd destroy --remove-protection` restores the guard on an EC2 instance, or on a Cloud Control protection-registry type, whose delete then failed terminally (issue [#2204](https://github.com/go-to-k/cdkd/issues/2204))** -- `src/provisioning/ec2-termination-protection.ts`, `src/provisioning/providers/ec2-provider.ts`, `src/provisioning/cloud-control-provider.ts`, `src/provisioning/cc-protection-properties.ts`, with unit tests in `tests/unit/provisioning/providers/ec2-instance-remove-protection-compensate.test.ts` and `tests/unit/provisioning/cloud-control-remove-protection-compensate.test.ts`. Before, the `DisableApiTermination` flip (both delete routes) and the Cloud Control patch for DSQL, NeptuneGraph, SMSVOICE ProtectConfiguration, VerifiedPermissions PolicyStore, EKS and the RDS / DocDB global clusters were never undone, so a failed destroy left the resource live with its guard silently stripped. Now the guard is turned back on before the failure is reported, under the rules the other `--remove-protection` sites follow: only a guard a pre-flip read saw ON (`DescribeInstanceAttribute`, or a Cloud Control `GetResource` holding the registry's new `onValue`) and this run turned off, only on a terminal failure, never once EC2 accepted the terminate or a Cloud Control delete attempt may already be deleting (an abandoned wait, or an ambiguous handler code such as `NotStabilized`; cdkd then warns with the check and restore commands), and a failed re-enable is its own log line with a pasteable `aws ec2 modify-instance-attribute --disable-api-termination` or `aws cloudcontrol update-resource` command. The Cloud Control re-enable waits for its patch to apply, a printed command names the client's region when the state records none, and a Cloud Control-routed instance's flip now refuses, before touching anything, an EC2 client aimed at another region than the vetted one.
