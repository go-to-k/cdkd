- **A create-only change to a cdkd-named ELBv2 target group deploys again, and a rollback that must delete the new resource first can reach that path (issue [#3208](https://github.com/go-to-k/cdkd/issues/3208))** -- `src/deployment/retryable-errors.ts`, `src/deployment/deploy-engine.ts`, `src/deployment/rollback-executor.ts`. `isNameCollisionError` recognised only `already exist(s)` and the `AlreadyExists` code, and ELBv2 says neither: measured live (us-east-1, 2026-09-16) a duplicate name answers `DuplicateTargetGroupNameException` with `A target group with the same name 'x' exists, but with different settings`, and the NAME never reached the predicate because providers render `Failed to create X: ${err.message}`. Both consumers of that predicate are RECOVERY paths, so both went inert for such a service: `cdkd deploy --replace`'s delete-first fallback never engaged, making a create-only change to a cdkd-named target group undeployable with or without the flag (the deploy died at the forward replacement reporting `No completed operations to roll back`), and the rollback executor's delete-new-first arm could not be reached either. New `isNameCollisionErrorFrom` reads the ERROR instead, walking the bounded `cause` chain for an exception NAME in `NAME_COLLISION_ERROR_NAMES`, ANCHORED on the resource's logical id so a rejection naming another resource cannot classify this one, and reading the existing message test at depth 0 only -- which keeps the message half exactly as wide as before. All four call sites holding the error object now use it; the string form is unchanged for callers that have only text. The admission rule for that list, and why `DuplicateListenerException` / `DuplicateTagKeysException` are excluded, are in `.claude/rules/name-collision-classification.md`. Live coverage: `tests/integration/elbv2-same-name-replacement/`, measured failing on a pre-fix binary and passing with the fix.
