- **`cdkd destroy` / `cdkd state destroy` no longer delete what a failed delete depends on (issue [#5670](https://github.com/go-to-k/cdkd/issues/5670))** -- `src/cli/commands/destroy-runner.ts` (`runDestroyForStack`: `blockedBy`, `blockDependenciesOf`, the new `blockedCount` result field), `docs/cli-destroy.md`, a new unit file and the new `destroy-failed-delete-keeps-dependencies` integ fixture. A delete that failed was only counted before the reverse level loop moved on, so the next levels deleted the resources it depends on: an `AWS::ECS::Gateway` whose delete failed lost its infrastructure role and could no longer be deleted ([#5664](https://github.com/go-to-k/cdkd/issues/5664)), and a failed `VPCGatewayAttachment` detach lost its internet gateway. Now every resource a failed delete depends on (transitively, over the same graph that orders the deletes) is left in AWS and in state, printed as `not deleted (<id> depends on it and its delete failed)`, recorded as a `RESOURCE_SKIPPED` event, and counted as `N blocked` in the summary; a re-run deletes them once the failed resource is gone. Resources unrelated to the failure are still deleted, which is what CloudFormation's `DELETE_FAILED` does (checked against a throwaway stack: an unrelated chain was deleted after the failure, the failed bucket's dependencies kept). A skipped delete does not block, as in the deploy engine's DELETE phase. The exit code stays `2`.
