- **A successful fix-forward deploy now deletes the load balancer, target group or listener an earlier failed CREATE left under the same logical id (issue [#4606](https://github.com/go-to-k/cdkd/issues/4606))** -- `src/provisioning/providers/elbv2-provider.ts`. After `cdkd deploy --no-rollback` failed with an `AWS::ElasticLoadBalancingV2::LoadBalancer`, `TargetGroup` or `Listener` already created and its wiring-failure cleanup unable to delete it (a journaled proven orphan) and the fixed template created a new one under the same logical id, the successful deploy warned, named the earlier one, exited `2` and left it in AWS. `ELBv2Provider` now answers `isSameResource` for the three types from the ARN, whose last segment AWS mints per create (a name alone is reusable, so it is never the identity): both ARNs must be the type's form in the stack's partition, account and region, the client must be in that region, and the record's ARN must read back as itself; the earlier one is then `different` when it reads back as itself or ELBv2 reports it gone by the type's own not-found error, so the settle deletes it. Equal ARNs are `same`; any other id form, a read naming another resource and a failed read stay `unknown` (the previous warning and exit `2`). An earlier resource already gone (only by the type's own not-found error name) is named in one info line. A deletion-protected earlier load balancer still needs its protection cleared before the settle can delete it. Tests: `tests/unit/provisioning/elbv2-same-resource-4606.test.ts`; integ `alb` Phase 4 asserts the earlier load balancer deleted, the new one kept, exit `0`.
