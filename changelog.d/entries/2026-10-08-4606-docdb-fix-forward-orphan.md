- **A successful fix-forward deploy now deletes the DocumentDB DB cluster or DB instance an earlier failed CREATE left under the same logical id, once live reads prove it is not the new one and is still the one that failed CREATE made (issue [#4606](https://github.com/go-to-k/cdkd/issues/4606))** -- `src/provisioning/providers/docdb-provider.ts`. After `cdkd deploy --no-rollback` failed with an `AWS::DocDB::DBCluster` or `AWS::DocDB::DBInstance` already created, and the fixed template created a new one under the same logical id with another identifier, the successful deploy warned, named the earlier resource, exited `2` and left it in AWS. `DocDBProvider` now implements `isSameResource` and `resourceIdentity`, both resting on the immutable `DbClusterResourceId` / `DbiResourceId`; identifiers equal apart from case are the same resource. The failed CREATE journals the resource id its create call returned, carried on the failure itself. A resource someone re-created under the identifier, in any case spelling, reads back under another resource id and is kept with a warning, and one of another engine (DocumentDB shares the identifier namespace and the describe calls with RDS and Neptune) is never read as a DocumentDB resource: it too is kept with a warning. Only the not-found fault name (or an empty describe list) counts as gone. Deleting an earlier resource that is already gone prints one info line. Tests: `tests/unit/provisioning/docdb-provider-same-resource-4606.test.ts`; new integ `docdb-fix-forward-orphan`.
