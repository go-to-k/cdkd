- **The six gate-scoped consumers of a non-object `outputs` bag stop fabricating from it, `cdkd deploy` and `cdkd destroy` included (issue [#3207](https://github.com/go-to-k/cdkd/issues/3207))** -- `src/deployment/{deploy-engine,intrinsic-function-resolver}.ts`, `src/cli/commands/{destroy-runner,local-state-loader,scrub}.ts`, `src/provisioning/providers/nested-stack-provider.ts`, `src/local/s3-local-state-provider.ts`, `src/state/malformed-resources-bag.ts`, `src/utils/error-handler.ts`, plus their docs and suites. [#3192](https://github.com/go-to-k/cdkd/issues/3192) scoped these out for sitting in a real-AWS integ gate scope, not for taking a different answer; each now tests the bag through the shared `hasReadableOutputs` at its LOAD. **Refuse versus repair is per site; `docs/design/3192-outputs-consumers.md` §4 records each call.** `cdkd deploy`, `cdkd destroy` / `state destroy`, and a nested stack's CHILD record REFUSE (`STATE_RESOURCES_MALFORMED`, exit 1) -- no new exit code; `cdkd local *` (`--from-state`) REPAIRS and WARNS once per damaged RECORD. Destroy is the one where repairing is unsafe, not merely lossy: the bag decides whether the cross-stack check runs, and a `null` / number / boolean reads as "exports nothing", SKIPPING it and deleting a producer other stacks import from. **The one site that RE-APPLIES rather than displays** is the resolver's `Fn::GetStackOutput` arm: `Object.hasOwn('abcdef','0')` is true, so `OutputName: "0"` resolved the character `a` and the deploy SENT it to AWS. It refuses with a new `MalformedProducerRecordRefusalError`, an `IntrinsicResolutionRefusalError` subclass so an `Fn::Sub` cannot launder it -- and so `cdkd scrub` keeps #3192's answer: the consumer stack is still scrubbed, the read counted, exit 2. An ABSENT field stays exempt; a healthy or empty bag is silent. The `resources` bag at these sites stays open on [#3161](https://github.com/go-to-k/cdkd/issues/3161) / [#3202](https://github.com/go-to-k/cdkd/issues/3202).
