- **`cdkd destroy --remove-protection` restores `DeletionProtection` on an RDS, DocDB or Neptune cluster or instance whose delete then failed terminally (issue [#2204](https://github.com/go-to-k/cdkd/issues/2204), partial)** -- `src/provisioning/providers/deletion-protection-compensation.ts` (new), `rds-provider.ts`, `docdb-provider.ts`, `neptune-provider.ts`, `dynamodb-delete-budget.ts`, `docs/_contents/cli-destroy.md`, with unit tests in `tests/unit/provisioning/providers/rds-family-remove-protection-compensate.test.ts`. Before, the flip-off was never undone, so a failed destroy left the resource live with its guard silently stripped. Now the guard is turned back on before the failure is reported, under the rules the DynamoDB pair already follows (issue [#1978](https://github.com/go-to-k/cdkd/issues/1978)): only a guard a pre-flip `Describe*` saw ON and this run turned off, only on a terminal failure, never once AWS has accepted the `Delete*`, and a failed re-enable is its own log line with a pasteable `modify-db-*` command. The mechanism moved out of the DynamoDB module into a shared one; DynamoDB's wording is unchanged. The other `--remove-protection` types stay open under #2204.
