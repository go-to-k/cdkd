- **A refusal raised inside a CDK Stage is fatal again, and a stack dropped with a failed Stage is reported as such (issue [#3482](https://github.com/go-to-k/cdkd/issues/3482))** -- `src/synthesis/{assembly-reader,synthesizer,failed-stages}.ts`, `src/cli/stack-matcher.ts` and four commands; ten suites. `AssemblyReader.getAllStacks` recursed into a `cdk:cloud-assembly` artifact inside a `try` whose `catch` only WARNED, so every refusal raised while reading a Stage -- the absolute `aws:asset:path` tripwire, an escaping `templateFile` or asset manifest, an unreadable template, the side-file refusal -- degraded to advice and silently dropped every stack under it, though each aborts the command at the top level. The `try` now wraps ONLY the read of the Stage's own `manifest.json` -- its SCOPE is the classifier, no error subclass or message match -- so a Stage whose directory was never synthesized still warns and the run continues, while everything else propagates, re-raised naming the innermost Stage and keeping the origin's frames. The surviving tolerance is now honest: `readAssembly` returns the Stages that failed, `Synthesizer` carries them on `SynthesisResult.failedStages`, and the shared `renderNoStackMatch` appends `Stage MyStage failed to load, so stacks under it are missing from this list rather than missing from the app: <reason>` -- to the no-match message AND to the zero-stack case, which used to answer `Multiple stacks found: .`. Every assembly-chosen name in these messages -- a Stage path, a `directoryName`, each stack name -- renders through `displayIdent`, and a read failure names only its own error code, so none can forge a cdkd-sounding clause. **`SynthesisResult.failedStages` is now REQUIRED**, which is breaking only for code that hand-builds that literal; reading the result is unaffected. `cdkd scrub` and `cdkd destroy` still word their own empty-selection message ([#3507](https://github.com/go-to-k/cdkd/issues/3507)).
