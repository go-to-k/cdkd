- **A refusal raised inside a CDK Stage is fatal again, and a stack that was dropped with a failed Stage is reported as such (issue [#3482](https://github.com/go-to-k/cdkd/issues/3482))** -- `src/synthesis/{assembly-reader,synthesizer}.ts`, a new `src/synthesis/failed-stages.ts`, `src/cli/stack-matcher.ts` and four commands (`deploy`, `diff`, `list`, `publish-assets`); five suites plus two new ones. `AssemblyReader.getAllStacks` recursed into a `cdk:cloud-assembly` artifact inside a `try` whose `catch` only WARNED, so every refusal raised while reading a Stage -- the absolute `Metadata['aws:asset:path']` tripwire, a missing or escaping `templateFile`, an unreadable template, an escaping asset-manifest `file` -- degraded to advice and silently dropped every stack under that Stage. The same conditions abort the command at the top level, so a hardened check became weaker exactly where an assembly is most likely hand-modified. Now the `try` wraps ONLY the read of the Stage's own `manifest.json` -- the scope of the `try` IS the classifier, no error subclass or message match -- so a Stage referencing a directory that was never synthesized still warns and the run continues, while everything else propagates, re-raised naming the innermost Stage (`Stage 'MyStage/Inner': Stack 'X' ...`). The surviving tolerance is now honest: `readAssembly` returns the Stages that failed to load, `Synthesizer` carries them on `SynthesisResult.failedStages`, and the new shared `renderNoStackMatch` -- which takes that result as a REQUIRED argument, so a call site cannot forget it -- appends `Stage 'MyStage' failed to load, so stacks under it are missing from this list rather than missing from the app: <reason>` instead of leaving `cdkd deploy 'MyStage/Api'` answering `No stacks matching ...`. `cdkd scrub` and `cdkd destroy` still word their own empty-selection message; open PRs held both files.
