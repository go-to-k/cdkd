- **A failed create that left a resource behind is no longer retried into making another one** -- `src/deployment/retry.ts`, `src/provisioning/auxiliary-failure.ts`, and the `iam-access-key`, `appsync`, `cognito`, `ec2`, `emr-cluster`, `emr-instance-fleet-config`, `emr-instance-group-config` and `lambda-web-function-revision` providers. A create whose attempt made its resource and then failed (marked for the failed-CREATE journal) was retried, and for a type whose create sends no name and no idempotency token, each retry made another resource while the journal recorded only the last one. An `AWS::IAM::AccessKey` with `Status: Inactive`, deployed by a principal denied `iam:UpdateAccessKey` and `iam:DeleteAccessKey`, minted a second key on the retry (the deny reads like IAM propagation, which is retried), filled the user's 2-key quota, and failed on `LimitExceeded` with the first key unrecorded. That create now fails on its own error once it leaves its resource behind, for the access key, AppSync GraphQL API, Cognito user pool, EC2 VPC and EIP, EMR cluster, instance fleet and instance group, and Lambda web function revision, so `cdkd rollback --revert-failed` and a fix-forward find the one resource. An EIP, a web function revision and an EMR TASK instance group that a later step failed after are now released, deleted or scaled to 0 first, so a transient failure there is still retried. For every other type, a retry whose create made a resource other than the one an earlier attempt left behind stops there with a warning; a create that resumes its earlier resource (KMS, S3, an idempotency token, an SNS or SQS policy over several targets) is retried as before. Issue [#4945](https://github.com/go-to-k/cdkd/issues/4945).
