- **A fix-forward deploy now deletes the DynamoDB global table an earlier failed CREATE left behind (issue [#4606](https://github.com/go-to-k/cdkd/issues/4606), DynamoDB global table slice)** -- `src/provisioning/providers/dynamodb-globaltable-provider.ts`. When a `cdkd deploy --no-rollback` made an `AWS::DynamoDB::GlobalTable`, failed configuring it (a replica, a TTL or a replica tag) and could not delete it again, and a later deploy kept the logical id under another table name, the successful deploy warned about the earlier table, left it in AWS and exited 2; `cdkd rollback` and `cdkd destroy` kept it the same way. The global table provider now answers both questions by the `TableId` of the table in the stack's region, which AWS generates and never reuses: the failed CREATE records the id its `CreateTable` returned, and the successful deploy deletes the earlier table only when the record's table reads back under another `TableId` and the old name still reads back under the recorded one. A table deleted by hand and re-created under the name has another `TableId` and is kept, with a warning. Tests: `tests/unit/provisioning/dynamodb-globaltable-provider-same-resource-4606.test.ts`; integ: `globaltable-fix-forward-orphan`.
