- **`AWS::ElastiCache::CacheCluster`: a `CacheNodeType` change now resizes the cluster in place (issue [#5438](https://github.com/go-to-k/cdkd/issues/5438))** -- `src/provisioning/providers/elasticache-provider.ts`, with unit tests in `tests/unit/provisioning/elasticache-provider-modify-5438.test.ts` and a node-type phase in the `cache-streaming` integ fixture. The update sent `ModifyCacheCluster` without `CacheNodeType`, so a node-type change deployed "successfully" while the cluster kept its old type. It is now sent on every update, as CloudFormation does for Redis and Memcached (so a cluster whose live type drifted is scaled back too), and the deploy waits until the cluster reports the template's type, failing early if AWS drops the change; the type's update deadline is raised to 60 minutes (`src/provisioning/slow-cc-operation-timeouts.ts`), so a long scale does not fail the deploy while AWS keeps scaling. A Memcached scale-out with `PreferredAvailabilityZones` now places the added nodes in the listed zones the live nodes do not cover (`NewAvailabilityZones`, with `AZMode`), as CloudFormation does. A `PreferredAvailabilityZone`, `TransitEncryptionEnabled` or (with no zones to add) `AZMode` change cannot be applied to an existing cluster; CloudFormation completes such an update with the cluster unchanged, and cdkd now does the same with a warning naming the property (for `TransitEncryptionEnabled`, the cluster's live setting).
