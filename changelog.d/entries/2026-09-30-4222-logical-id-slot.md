- **Provider errors name the resource's logical id in their `logicalId` field, not its physical id (issue [#4222](https://github.com/go-to-k/cdkd/issues/4222))** -- `src/provisioning/providers/{asg,budgets-budget,cloudwatch-anomaly-detector,dlm-lifecycle-policy,firehose,iam-access-key,wait-condition-handle}-provider.ts`, `src/types/resource.ts`, `src/analyzer/orphan-rewriter.ts`, `src/provisioning/auxiliary-failure.ts`. 18 `ProvisioningError`s (the Firehose destination-update failures and the `getAttribute` failures of the other six providers) carried the resource's physical id, which can be built from a secret, in their `logicalId` field, so an error dump labelled a live resource name as the logical id and the retry classifiers anchored on the logical id never matched the error to its resource. They now carry the logical id, with the physical id in `physicalId`; `getAttribute` takes the logical id as a fourth argument, which `cdkd orphan` passes. An auxiliary-failure mark is now recognised by its read-only shape as well as its `/auxiliary` suffix, so a physical id ending in `/auxiliary` is no longer read as one, and `withRetry` (`src/deployment/retry.ts`) marks a replayed failure with the fixed owner `withRetry` instead of its label, so a label holding a table or policy name never becomes the mark `maskSecretsInError` copies unmasked. The two sites in `scheduler-schedule-provider.ts` remain. Tests: `tests/unit/provisioning/logical-id-slot-4222.test.ts` (including a source fence over every construction under `src/`) and the per-provider suites.
