- **An `AWS::DynamoDB::Table` GSI whose `IndexName` is an unquoted YAML NUMBER no longer takes the whole `cdkd deploy` down (found while closing issue [#3287](https://github.com/go-to-k/cdkd/issues/3287))** -- `src/provisioning/providers/dynamodb-table-provider.ts` (`warmThroughputOpFor`). `IndexName` is an UNCHECKED cast off the template, so `IndexName: 2024` reaches the provider as a number, and the real `maskSecrets` is a `String.prototype.replace` call that THROWS on one. That method opened with a bare, EAGER `maskSecrets(indexName)` ahead of every gate, and it runs for every same-name and adopted index -- so on a stack with any resolved secret, an ORDINARY capacity edit on such a table failed with `Failed to update DynamoDB table <id>: text.replace is not a function`, from a purely diagnostic code path. The `indexScopeAt` guard the review of issue [#3255](https://github.com/go-to-k/cdkd/issues/3255) added for exactly this covered the create-path and capacity sites and missed this one; the four interpolations now read through it, so the rendered string is byte-identical for a string name and a non-string name renders `<unnamed>` instead of throwing. Pinned by `site 5 update: survives a NUMERIC IndexName with a masker in play` in `tests/unit/provisioning/dynamodb-table-provider-cfn-integer.test.ts`, whose site-4 twin could not reach this arm.
