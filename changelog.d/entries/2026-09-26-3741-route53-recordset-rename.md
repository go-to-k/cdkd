- **Renaming an `AWS::Route53::RecordSet` no longer leaves the old record live and untracked (issue [#3741](https://github.com/go-to-k/cdkd/issues/3741))** -- `src/provisioning/providers/route53-provider.ts`.
  - A change to a record's `Name`, `Type` or `SetIdentifier` used to send a single `UPSERT` built from the new properties. Route 53 created the new record beside the old one, and the old record kept resolving. `cdkd destroy` could not remove it. A rename whose new record conflicts with the old one was refused outright, for example a new `SetIdentifier` on a geoproximity record or an A -> CNAME swap on one name.
  - Such a change now sends one atomic `ChangeBatch`: a `DELETE` of the old record, read back live because Route 53 requires an exact match, plus a `CREATE` of the new record. This matches CloudFormation (live A/B on the issue). A refused batch leaves the old record serving. If the old record is no longer live, the new record is written by `UPSERT` as before.
  - A rename also needs `route53:ListResourceRecordSets` (to read the old record), beside `route53:ChangeResourceRecordSets`.
  - Route 53's refusal to create a CNAME beside a live record of the same name now counts as a name collision. So a rollback reversing a CNAME -> A rename deletes the A first, then restores the CNAME.
  - A difference in letter case or trailing dot only is still the same record, updated by `UPSERT`. `cdkd drift --revert` never renames.
  - On rollback, a `SetIdentifier`-only rename is renamed back the same way, and a `Name` / `Type` rename is reversed as a replacement. Either way the rollback leaves no record behind.
  - `cdkd drift` now reads a weighted, latency, failover or geo record by its recorded `SetIdentifier`. It used to read whichever sibling with the same name and type sorted first.
