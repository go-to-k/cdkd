- **The state bucket now expires custom-resource response objects with a one-day lifecycle rule (issue [#2353](https://github.com/go-to-k/cdkd/issues/2353))** -- new `src/state/state-bucket-lifecycle.ts`, `src/cli/commands/bootstrap.ts`, `src/provisioning/providers/custom-resource-provider.ts`. A custom resource's handler writes its whole response, `Data` included, under `custom-resource-responses/` in the state bucket. A run killed before cdkd deleted it left that object live until `cdkd gc` ran. `cdkd bootstrap` now adds the lifecycle rule `cdkd-custom-resource-responses-expiration` for `custom-resource-responses/cdkd-1`: a current version expires after one day and its noncurrent version one day later, each rounded up to midnight UTC. A state bucket bootstrapped earlier gets the rule from the first deploy or destroy that runs a custom resource: one `GetBucketLifecycleConfiguration` per run, started beside the response placeholder write and never awaited, plus a listing and one `PutBucketLifecycleConfiguration` the first time. Stacks with no custom resource make no call. The rule is merged into the existing configuration: every existing rule is kept, and nothing is written when a rule with the same ID exists, when the configuration cannot be read, or when a stack's state is stored where the rule would reach it (`--state-prefix custom-resource-responses` with a stack named `cdkd-1*`). A missing permission prints a warning on each such run and never fails the bootstrap, deploy or destroy.
