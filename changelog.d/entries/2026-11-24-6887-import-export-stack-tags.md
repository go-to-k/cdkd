- **`cdkd import` records a stack's tags (`StackProps.tags`) on each imported resource, and `cdkd export` gives the CloudFormation stack it creates its stack tags (issue [#6887](https://github.com/go-to-k/cdkd/issues/6887))** -- `src/cli/commands/import/locked-import.ts`, `src/cli/commands/import/nested.ts`, `src/cli/commands/import/deployed-properties.ts`, `src/cli/commands/export/changeset.ts`, `src/cli/commands/export/exported-stack-tags.ts`, `src/cli/commands/export/per-stack-phases.ts`, `tests/unit/cli/export-stack-tags-6887.test.ts`. Since #6871 a deploy merges the stack tags into every taggable resource, but an import recorded the resources without them, so the first `cdkd diff` / `cdkd deploy` after an import showed a `Tags` update on each taggable resource of a tagged stack. An import now records them merged in; `--migrate-from-cloudformation` merges the tags the CloudFormation stack holds (what CloudFormation applied to the resources), each nested stack its own. `cdkd export` created its CloudFormation stack with no stack tags, and the update that readies a nested stack for adoption REPLACED that stack's tags with cdkd's marker tag, removing the stack tags from its resources. CloudFormation refuses stack tags on an IMPORT changeset that creates a stack (measured), so the export now sets them with one stack update after the last changeset (a failure there is a warning: the export has completed), and a nested stack takes its tags (its parent's plus its own `Tags`) with that readying update. A stack without stack tags makes no extra call.
