- **A rollback re-creates a replaced resource's old copy before reverting what references it (issue [#5064](https://github.com/go-to-k/cdkd/issues/5064))** -- `src/deployment/rollback-executor.ts`, `src/deployment/rollback-executor/plan.ts`, `replay-reverse-replacement.ts`, `replay-scope.ts`, `src/deployment/superseded-resources.ts`, `src/cli/commands/rollback.ts`, `src/deployment/nested-child-journal.ts`. When a replacement gave the resource a new physical id (a generated name at its next generation, or a renamed resource), `cdkd rollback` and the automatic rollback reverted the resources that moved onto it (an IAM managed policy's `Roles`, an inline policy's role) BEFORE re-creating the old resource, so they named one AWS no longer had ("The role with name ... cannot be found") and the rollback exited with a partial failure. The old resource is now re-created before the first revert that may reference it (and before a replaced resource its own old properties reference), and the new one is deleted after those reverts, as CloudFormation does. Until that delete runs, `cdkd rollback` keeps the new resource in `supersededResources`, so a killed run leaves it for the next deploy to delete; there it also stays, for both rollbacks, when its delete fails or a resource still using it did not revert, and when `cdkd rollback` is interrupted. A same-physical-id re-create, a delete-first reversal, and one whose old id another record still holds keep their order.
