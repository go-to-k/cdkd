- **A plain create of an explicitly named queue, topic, rule, alarm, state machine, ECS cluster, S3 bucket or CloudWatch Logs log group no longer takes over a resource that already holds the name (issue [#4180](https://github.com/go-to-k/cdkd/issues/4180))** -- `src/deployment/deploy-engine-create.ts` (`refuseTakenCreateName`), `src/deployment/replacement-name-holder.ts` (`createNameQuestion`, `createLookupArn`), `cloudwatch-alarm-provider.ts`, the `replacement-rename-onto-holder` integ (phases B5 / C5), a new unit file and `docs/cli-deploy-safety.md`. These SDK create APIs hand back or overwrite an existing resource of the requested name instead of failing, so the deploy reported success, recorded the resource as the stack's, and a later `cdkd destroy` deleted it. The create arm now looks the name up through the provider's `import()` first, as the replacement path has since #3937, and fails with `NAMED_CREATE_COLLISION` and nothing created when a resource holds it or the lookup cannot run — CloudFormation's create fails with "already exists". That includes the stack's own resource left by an earlier interrupted deploy, which AWS cannot tell apart: delete it or adopt it with `cdkd import`. A log group something else already created (a Lambda function's, on its first invocation) is refused the same way, and the alarm lookup now sees composite alarms. A name cdkd generates is not looked up (#4345), and the Cloud Control route is unchanged.
