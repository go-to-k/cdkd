- **A create-only property an earlier deploy kept off AWS with `--prefer-sdk-route` (or `--allow-unsupported-properties`) is no longer silently forgotten once a later release's SDK provider writes it (issue [#5572](https://github.com/go-to-k/cdkd/issues/5572))** -- `src/provisioning/property-coverage.ts` (`findHandledUnwrittenCreateOnly`, `acceptedCreateOnlyDropsEvidence`), the engine's record writer and refusal (`deploy-engine/record-shape.ts`, `update.ts`), the `cdkd diff` preview (`diff-recursive.ts`), the rollback re-create (`rollback-executor/replay-reverse-replacement.ts`), unit files, a Phase 1e arm in `tests/integration/s3-tables/verify.sh`, and two docs pages. Both #2790 readers keyed on today's coverage map, so a key a #2762 backfill slice moved from silent drop to handled fell out of them: the unchanged template diffed NO_CHANGE, the deploy reported success, and the value named in `acceptedCreateOnlyDrops` never reached AWS. Such a top-level create-only key now reads as unwritten, so the deploy refuses the replacement with `CREATE_ONLY_DROP_NEEDS_REPLACEMENT` until `--replace` / `--recreate-via-cc-api` opts in, whatever `--prefer-sdk-route` names; `cdkd diff` warns (exit 0). The record side drops such a key only where the refusal covers it (asked unchanged) or the template no longer declares it, so a value that differs is compared like any create-only change. When AWS already holds the value, the refusal names `cdkd import --resource <id>=<physical-id> --force`, which re-records it without the evidence. A rollback re-create now rebuilds the field for its route instead of carrying it.
