- **AWS published 3 writable properties the 2026-11-05 schema refresh now carries, so cdkd classifies each instead of treating them as unrecognized (PR [#5822](https://github.com/go-to-k/cdkd/pull/5822))** -- `AWS::EMR::Cluster`: `MonitoringConfiguration`, `SessionEnabled`; `AWS::Lambda::MicrovmImage`: `KmsKeyIdentifier`. Changed: `tests/fixtures/cfn-schemas/`, `src/provisioning/property-coverage.generated.ts` (regenerated). On `AWS::Lambda::MicrovmImage`, no SDK provider writes it yet (`not yet implemented by cdkd`), so pre-flight classifies each as SDK-unwired and the issue [#614](https://github.com/go-to-k/cdkd/issues/614) auto-route sends a resource whose template carries one through Cloud Control, which forwards the full property map. Since issue #3713 a key absent from the snapshot already routed so, unless the state record held it with the declared value; such a resource moves on its next deploy. `AWS::EMR::Cluster` cannot take that route — its provider declines the Cloud Control fallback, or AWS reports the type NON_PROVISIONABLE — so a template carrying one is REFUSED at pre-flight with the unroutable-property message instead of deploying. `AWS::Lambda::MicrovmImage` is not in `STICKY_CC_MIGRATION_EXEMPT`, so an existing SDK-provisioned resource of that type whose template gains one moves to Cloud Control and pins `provisionedBy: 'cc-api'` ONE-WAY. The snapshot marks `AWS::EMR::Cluster`.`MonitoringConfiguration`, `AWS::EMR::Cluster`.`SessionEnabled` create-only, so they join `createOnlyDrops` and the record narrowing keeps them in the record; the capture is top-level-only, so it says nothing about a nested create-only path.
