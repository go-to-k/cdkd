- **A Glue table replacement that keeps the table's address can now be performed with `cdkd deploy --replace`, and `--replace` on a table whose new address another table holds is refused with nothing deleted (issue [#3932](https://github.com/go-to-k/cdkd/issues/3932))** -- `src/provisioning/providers/glue-provider.ts`, `src/deployment/replacement-name-holder/name-keys.ts`, `src/deployment/replacement-name-holder/holder.ts`. The Glue provider reworded every `CreateTable` `AlreadyExistsException` so the engine never treated it as a name collision (#3750). That kept `--replace` from deleting the old table when a third party held a renamed table's address, but it also hid the collision when the replacement kept the address (a change to the top-level `Name` alone): the create-first attempt then collides with the old table itself, and no flag could perform the replacement. The provider now relays the error, and the engine's name-holder check decides: `--replace` deletes the old table first only when it holds the address the create sent, reading the name as the provider does (`TableInput.Name`, else `Name`) and placing it by `DatabaseName` and, newly, `CatalogId`. Table names compare with ASCII case folded, as Glue stores them, and a table's `<database>|<table>` id never proves the name it holds (either name may contain `|`). A rename, another database or another Data Catalog is refused before anything is deleted, and so is a `CatalogId` given on only one side or a recorded name cdkd cannot read. Tests: `tests/unit/deployment/deploy-engine-glue-table-collision-3932.test.ts`, `tests/unit/deployment/replacement-name-holder.test.ts`, `tests/unit/provisioning/providers/glue-provider.test.ts`; integ phase 2f (and step 2b) in `tests/integration/glue-update-hardening/`.
