- **An EC2 VPC, internet gateway or Elastic IP create that hits a 5xx now reports candidate orphans instead of duplicating silently, and a subnet or security group create surfaces its replayed collision as possibly its own (issue [#2080](https://github.com/go-to-k/cdkd/issues/2080), Plan B: `CreateVpc`, `CreateSubnet`, `CreateInternetGateway`, `AllocateAddress`, `CreateSecurityGroup`; the SDK-5xx half of #3978 layer (b) for these creates)** -- `src/provisioning/providers/ec2-provider.ts`. None of the five carries an idempotency token, so a 5xx whose request had succeeded left a second VPC, gateway or address (an unassociated Elastic IP keeps billing) with no state record, unreported when the AWS SDK replayed it inside one call. All five now refuse the SDK's 5xx retry. After an ambiguous `CreateVpc`, `CreateSubnet`, `CreateInternetGateway` or `AllocateAddress`, cdkd's retry first lists untagged candidates the failed attempt may have made -- VPCs with the same CIDR, subnets with the same CIDR in the same VPC, detached internet gateways, unassociated addresses of the same domain -- and warns with a `describe-*` read command and no delete command, since EC2 reports no creation time for them. Nothing is adopted or deleted; a throttle or 4xx triggers no lookup, and a failed lookup warns and lets the create proceed. A subnet CIDR and a security group name cannot repeat in a VPC, so those replays fail with `InvalidSubnet.Conflict` / `InvalidGroup.Duplicate` rather than duplicating; the group's collision is no longer credited to another holder. A reset or timeout after the send is still retried inside the SDK. Tests: `tests/unit/provisioning/ec2-create-retry-2080.test.ts`.
