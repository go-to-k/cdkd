- **A planted `rollback-journal.json` can no longer forge the plan rows `cdkd rollback` asks you to confirm (issue [#3064](https://github.com/go-to-k/cdkd/issues/3064))** -- `src/types/rollback-journal.ts`, `src/cli/commands/rollback.ts`, cases in two suites. The journal is a SIBLING of `state.json` in the same bucket, so anyone with `s3:PutObject` writes it, and it carries no more validation than an unchecked cast. Issue [#3003](https://github.com/go-to-k/cdkd/issues/3003) hardened the `state.json` / `lock.json` readers; this is the reader it did not cover. **Two surfaces.** `parseRollbackJournal` interpolated the raw V8 `SyntaxError` -- which QUOTES the offending input -- plus the stack name (an S3 key segment) and the record's own `journalVersion`; nothing downstream caught it, because `formatError` prints a non-`CdkdError`'s `message` RAW and sanitizes only `cause`. **The worse one is the PLAN PREVIEW**, which rendered each entry's `logicalId` / `resourceType` / `changeType` and each segment's `reason` / `runId` unsanitized: cdkd's output is line-oriented, so an injected newline invents a line that reads exactly like a planned operation -- and unlike a forged diagnostic, this is the text a user CONFIRMS against, so the confirmation attested to something other than what would run. Both modules route every rendered value through ONE predicate (the ASCII allowlist -- a logical id, a CFn resource type, a change type, a run id and a region all have known charsets). The six `previewState` LOOKUPS keep the raw `logicalId` deliberately: sanitizing a key silently mismatches the record it is meant to find, and a test pins that. NOT changed: the thrown error's CLASS. `formatError` prints `message` raw in both branches, so what fixes this is sanitizing the interpolation, not wrapping -- and a new class would break callers matching on the current one.
