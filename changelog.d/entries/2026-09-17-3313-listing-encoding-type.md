- **Every S3 listing cdkd takes now survives a carriage return in a key, so a sweep can no longer report success having deleted nothing (issue [#3313](https://github.com/go-to-k/cdkd/issues/3313))** -- new `src/utils/s3-listing-keys.ts`, plus `src/state/{s3-state-backend,s3-noncurrent-version-purge}.ts`, `src/cli/commands/{gc,bootstrap-destroy,state-migrate}.ts`, `src/provisioning/providers/s3-{bucket,directory-bucket}-provider.ts`, one suite. `ListObjectsV2` / `ListObjectVersions` answer in XML, and an XML parser normalises a CR to an LF per the specification -- so a key containing a CR came back with an LF in its place and every later use addressed a key that does not exist. **Measured against real S3**: `PutObject` stores such a key, the un-encoded listing returns `\n`, and `EncodingType: 'url'` returns `%0D` which decodes to the real CR. The dangerous half is the delete that follows: it SUCCEEDS and removes nothing, so `s3-noncurrent-version-purge.ts` -- the sweep that removes state versions carrying a secret plaintext -- could skip an entry and still report a clean run. **The request and the decode are ONE decision**, which is why they share a module: a site that asks for encoding without decoding corrupts every legitimate `%` in a key. `NextContinuationToken` is deliberately NOT decoded (it is opaque and unencoded; decoding it breaks pagination) while `NextKeyMarker` is (the next request sends the raw value) -- both measured, not inferred. **Two sites deliberately do not ask**: `config-loader.ts` reads `KeyCount` and `recreate-targets.ts` is an emptiness probe, so neither reads a key at all. NUL is out of scope by measurement -- S3 refuses to store such a key -- and an ESC survives verbatim, so the transformation is specific to the line-ending class. `src/cli/commands/state.ts` is the one listing still unfixed, held by an open PR, and the new suite records it so it cannot be forgotten.
