- **`AWS::RDS::DBCluster` / `DBInstance`, `AWS::DocDB::DBCluster` / `DBInstance`, `AWS::Neptune::DBCluster` / `DBInstance`: a create that lands in a terminal status now fails at once (issue [#5426](https://github.com/go-to-k/cdkd/issues/5426))** -- `src/provisioning/providers/{rds,docdb,neptune}-provider.ts`, `src/provisioning/providers/deletion-protection-compensation.ts` and `src/provisioning/providers/db-instance-modify-retry.ts`, with unit tests in `tests/unit/provisioning/rds-family-create-wait-fail-fast-5426.test.ts`, `tests/unit/provisioning/neptune-instance-update-wait-5194.test.ts` and `tests/unit/provisioning/providers/deletion-protection-compensation.test.ts`. The create-path `available` waits polled for the full 30 minutes when the new cluster or instance entered a status it does not leave on its own (`incompatible-parameters`, `incompatible-network`, `inaccessible-encryption-credentials`, `failed`, `*-failed`, ...), then failed with a timeout that did not name the status. They now fail on the first such read, naming the logical id and the status, so the created-before-failure cleanup retires the resource sooner. `inaccessible-encryption-credentials-recoverable` is no longer treated as terminal by any deploy wait (these create waits, the update-path cluster waits for a port or security-group change, and the `ModifyDBInstance` not-available retry): the wait keeps polling within its budget, as it did before these waits failed fast, since AWS reports that status as recoverable once the KMS key is usable again. When the RDS cluster create's own cleanup delete is refused because the cluster is already `deleting` or gone, the warning now says so instead of "THE CLUSTER IS STILL RUNNING AND BILLING". The `--remove-protection` final-snapshot paths still treat it as terminal.
