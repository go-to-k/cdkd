- **`cdkd drift` now sees an `AWS::DynamoDB::GlobalTable` replica's key, table class, deletion protection, resource policies, point-in-time recovery period and Contributor Insights mode (issue [#5381](https://github.com/go-to-k/cdkd/issues/5381))** -- `src/provisioning/providers/dynamodb-globaltable-provider.ts`, `src/provisioning/dynamodb-replica-settings.ts`. The read-back spelled a cross-region replica's key as a flat `Replicas[].KMSMasterKeyId`, put the deploy region's class and protection at the top level (where the GlobalTable schema has neither) and never read a cross-region replica's, never read `Replicas[].ResourcePolicy` or `Replicas[].ReplicaStreamSpecification.ResourcePolicy`, and dropped `RecoveryPeriodInDays` and `Mode`; so drift missed an out-of-band change to any of them, and `drift --revert` re-sent point-in-time recovery without its period, which DynamoDB reads as its 35-day default. Each is now read back per replica under its CFn spelling (a resource policy only where the template declares one), and a state record written by the old read-back is compared in the new shape, so an untouched table does not report drift after upgrading. `drift --revert` keeps a replica's class, protection, key and recovery period where its recorded side holds none (a read that failed, or a record with no read-back), instead of resetting them. A replica's transient `ENABLING` point-in-time recovery or Contributor Insights status now reads as enabled, so a baseline captured right after a deploy turned it on no longer records it off. Removing `KinesisStreamSpecification.ApproximateCreationDateTimePrecision` while keeping the stream now resets the precision to `MILLISECOND`, as CloudFormation does (measured); before, `MICROSECOND` stayed.
