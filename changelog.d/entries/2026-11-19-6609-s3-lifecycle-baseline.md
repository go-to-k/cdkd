- **An S3 bucket's lifecycle rules that cdkd just wrote no longer leave a drift baseline holding the previous rules, which `cdkd drift --revert` would re-apply (issue [#6609](https://github.com/go-to-k/cdkd/issues/6609))** -- `src/provisioning/providers/s3-bucket/{lifecycle-baseline,read-state,apply-lifecycle,apply-diffs}.ts`, `src/provisioning/providers/s3-bucket-provider.ts`, `src/cli/commands/drift/baseline-keys.ts`, unit tests, the `s3-lifecycle` integ. Right after `PutBucketLifecycleConfiguration` / `DeleteBucketLifecycle`, `GetBucketLifecycleConfiguration` can answer the previous rules, or none, for several seconds, and the deploy recorded that first answer as the `observedProperties` baseline: `cdkd drift` then reported an untouched bucket, and `drift --revert` re-applied an old expiration or deleted the declared rules. When that create or update sent a lifecycle Put or Delete, the capture after it now re-reads an answer that differs from what was written (up to 4 more reads, 7.5 seconds at most, only when the first answer differs). If the written rules are still not visible after that, they are recorded, in the shape the read returns, with a warning; a just-deleted configuration that is still visible records no lifecycle baseline. A capture after an update that left the lifecycle alone takes the first answer, as before. A rule declared without an `Id` is recorded without one, since S3 generates it. Drift, import and `state refresh-observed` still take the first answer. A baseline written by an earlier cdkd is not compared on `LifecycleConfiguration` while the live bucket holds the declared rules (or none, when none are declared); the next update of the bucket rewrites it.
