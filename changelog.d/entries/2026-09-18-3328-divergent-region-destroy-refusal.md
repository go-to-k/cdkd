- **`cdkd destroy` / `cdkd state destroy` now REFUSE a state record whose body named a different region than its key while it still lists resources, instead of reporting the whole stack destroyed (issue [#3328](https://github.com/go-to-k/cdkd/issues/3328), review round 1)** -- `src/state/malformed-resources-bag.ts`, `src/cli/commands/destroy-runner.ts`, `src/cli/commands/destroy.ts`, `src/cli/commands/state.ts`, `src/provisioning/providers/nested-stack-provider.ts`, `src/types/state.ts`, `tests/unit/state/state-key-region-authority.test.ts`. The sibling entry makes the S3 KEY decide such a record's region -- right for the lock and the record's identity, undecidable for WHERE THE RESOURCES ARE. If the body is the planted half they are in the key's region; if the KEY is (an `aws s3 cp` between region prefixes, a restore, another tool), they are not, and the runner reads each provider's `*NotFound` as ALREADY DELETED: `deletedCount++`, the row dropped, then `deleteState`. A whole stack would be reported destroyed with every resource still live in the other region and nothing naming it. `assertRegionMatch`, the guard for that inference, cannot fire -- `DeleteContext.expectedRegion` and the client region are now the same value by construction. So the runner refuses, above the empty-stack fast path and below the malformed-bag guard that proves the bag can be counted, with `STATE_REGION_DIVERGED` and a message naming the key's region, the resource count and the value's KIND but never the value. The trigger is the CONJUNCTION: a resource-less record is NOT refused, since nothing can be stranded and that is the recovery destroy the read side exists to protect; `cdkd state show` / `state list` / `state orphan` all keep working on a record this refuses to delete from. Also drops a non-string or empty `region` on the LEGACY read path (`tryGetLegacy`'s gate short-circuits on falsy, so `""` and `0` reached `acquireLock` as regions and built `cdkd/<stack>//state.json`).
