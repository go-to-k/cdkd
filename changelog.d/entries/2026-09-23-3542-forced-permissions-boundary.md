- **`deploy --permissions-boundary <arn>` attaches an IAM permissions boundary to every Role and User cdkd creates or updates, overriding the template (issue [#3542](https://github.com/go-to-k/cdkd/issues/3542))** -- new `src/provisioning/forced-permissions-boundary.ts`, `resolvePermissionsBoundary` in `src/cli/config-loader.ts`, the option in `src/cli/options.ts`, the scope in `src/cli/commands/deploy.ts`, and both IAM principal providers (`iam-role-provider.ts`, `iam-user-group-provider.ts`). Also `CDKD_PERMISSIONS_BOUNDARY` and `cdk.json` `context.cdkd.permissionsBoundary`, resolved highest-first like `--prefix-user-supplied-names`. **The override is the point.** A template-declared `PermissionsBoundary` belongs to whoever wrote the CDK app, so an app that omits it, or declares a weaker one, escapes the boundary the operator asked for. That makes it possible to deploy an app you did not write under a session role whose `iam:CreateRole` is conditioned on `iam:PermissionsBoundary` -- a condition that otherwise refuses every ordinary app, since CDK apps almost never attach a boundary themselves. The CDK CLI has no equivalent: `PermissionsBoundary.of()` is a synth-time construct the app's own code can simply not call. The applied value is recorded via `effectiveProperties` and folded onto the desired side by a new `canonicalizeDesiredProperties` on both providers, so the template's declared value does not read back as a pending change on every later deploy; the fold is gated on `AWS::IAM::User` in the user/group provider, since Group and UserToGroupAddition have no boundary and folding the key onto them would be phantom drift in the opposite direction. `previousProperties` is left alone (it is a cdkd STATE record), so turning the flag on for an existing principal reads as a change and attaches the boundary on the next deploy. A blank or non-string value from any source is ignored with a warning rather than read as "no boundary", since an operator passing the flag is asking for one.
