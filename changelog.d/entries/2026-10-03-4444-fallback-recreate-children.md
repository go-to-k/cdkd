- **The update-failure fallback's same-id re-create now brings back the sub-resources stored inside the resource (issue [#4444](https://github.com/go-to-k/cdkd/issues/4444))** -- `src/deployment/deploy-engine/update-in-place.ts`, `src/deployment/deploy-engine/execute.ts`, `src/deployment/child-of-recreated-parent.ts`. When a provider refuses an in-place update (`ResourceUpdateNotSupportedError` under `--replace`, or Cloud Control's `UnsupportedAction`), cdkd deletes the resource and creates it again; with a fixed name it comes back under the same physical id, and what AWS stored inside it (a log group's streams and metric or subscription filters, from the #4411 table) went with the old one. The diff never promoted those children, since the parent was an in-place update, so they stayed `NO_CHANGE` and were never dispatched: after a green deploy they were missing in AWS while state recorded them. The fallback now records such a re-create, and as soon as the re-created resource completes the engine dispatches each `NO_CHANGE` child of it through the #4411 arm (re-created without a delete, or re-put), before anything that reads the child, so a later failure elsewhere in the deploy no longer leaves it missing. Tests: `tests/unit/deployment/deploy-engine-fallback-recreate-children.test.ts`, `tests/unit/deployment/child-of-recreated-parent.test.ts`.
