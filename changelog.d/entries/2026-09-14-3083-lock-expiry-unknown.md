- **A lock whose `expiresAt` is not a finite number renders as `expires at an unknown time` instead of `expired NaNmNaNs ago` (issue [#3083](https://github.com/go-to-k/cdkd/issues/3083))** -- `src/cli/commands/state.ts` (`formatLockSummary` via a new `formatExpiry`), `src/state/lock-manager.ts` (a private `formatExpiry` shared by the expired-lock takeover warning, the acquire retry line and the final `LockError`), `docs/cli-state.md`, `docs/troubleshooting.md`, and cases in `tests/unit/cli/state-record-shape.test.ts` / `tests/unit/state/lock-manager.test.ts`. `expiresAt` is an unchecked cast, so `{}`, `"soon"`, an absent field, or the `NaN` that `getLockRecord` substitutes for a coercion that throws (issue [#2947](https://github.com/go-to-k/cdkd/issues/2947)) all reached `formatDuration` through subtraction and printed `NaNmNaNs`, while `lock-contention-message.ts`'s `formatRemaining` already said "at an unknown time" for the same input. For those inputs the two lock renderers now agree (a NUMERIC string still diverges: `formatExpiry` reads it raw as non-finite, while the contention message subtracts first — that file is held by go-to-k/cdkd#3072; issue [#3085](https://github.com/go-to-k/cdkd/issues/3085) folds the three renderers into one after it lands); `isLockExpired`'s verdict on such a value (expired, so the lock is taken over) is unchanged. The takeover warning also stops blaming a crashed owner for a deadline that was simply unreadable: it names the non-finite `expiresAt` as the cause. Two changes on the FINITE path: the `LockError` refusal reads `expires in 4m12s` rather than `expires in: 4m12s`, so all three `LockManager` sites share one spelling; and the retry line and that refusal render a finite PAST deadline (an expired lock whose takeover was refused) as `expired 5s ago` where `formatDuration` used to floor it to `expires in -5s`.
