- **A nested stack's unchanged resource now records a dependency a later template adds, and a failed parent's revert restores one it removed (issue [#6314](https://github.com/go-to-k/cdkd/issues/6314))** -- `src/deployment/deploy-engine/record-shape.ts` (`nestedDependencySnapshot`, `withRecordedDependencies`), `rollback/settle.ts`, `rollback/journal-write.ts`, `src/deployment/nested-child-journal.ts`, `src/deployment/rollback-executor/journaled-orphans.ts`, `src/types/rollback-journal.ts`. Since [#6308](https://github.com/go-to-k/cdkd/issues/6308) a nested child's success only drops the dependency ids its template no longer lists from an unchanged record, because a failed parent reverts the child's updated records and an added edge could then record a cycle. So `a.node.addDependency(b)` on an otherwise unchanged nested resource was never recorded, and `cdkd destroy` could delete the two in the wrong order; and a dependency dropped that way stayed dropped when a failed parent reverted the child. The child's `nested-pending-parent` journal segment now carries both halves (additive fields, no journal version bump): the top-level deploy's success writes the full template lists onto the child's records under the child's lock, reading the journal it already loads (no extra S3 read; one state write only when a list changes), and a failed parent's revert puts the removed ids back. Neither write happens when it would record a dependency cycle. Tests: `tests/unit/deployment/deploy-engine-dependencies-refresh-6308.test.ts`, `deploy-engine-nested-journal.test.ts`, `nested-child-journal.test.ts`, `tests/unit/types/rollback-journal.test.ts`; integ fixture `tests/integration/depends-on-flip/` (nested arm).
