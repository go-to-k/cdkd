- **`cdkd destroy` and `cdkd rollback` now act on an orphan a fix-forward deploy kept, instead of asking for manual attention (issue [#4754](https://github.com/go-to-k/cdkd/issues/4754))** -- `src/deployment/rollback-executor.ts`, `src/deployment/rollback-executor/plan.ts`, `src/cli/commands/rollback.ts`. When a successful deploy kept a resource an earlier failed CREATE left behind (its delete failed, or it was an S3 bucket that still held objects), a later `cdkd destroy` or `cdkd rollback` skipped that journal entry with a warning that it needed manual attention and exited 2, even after the user had emptied the bucket or deleted it by hand: only the deploy that kept it had proven it was not the resource state now tracks under the same logical id. Both commands now ask the resource's provider that question again. Proven, the resource is deleted while its creation identity still matches (an S3 bucket is still never emptied), and an entry whose resource is already gone is dropped. When the provider cannot answer (no such check, an error, or no answer within the same time limit), the entry is kept with the warning as before. The `cdkd rollback` plan shows the same outcome before you confirm. A deploy's own automatic rollback is unchanged. Tests: `tests/unit/deployment/replay-recheck-kept-orphan-4754.test.ts`, `tests/unit/cli/rollback-preview-recheck-4754.test.ts`; integ: `s3-fix-forward-orphan`.
