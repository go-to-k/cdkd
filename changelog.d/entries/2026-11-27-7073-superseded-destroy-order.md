- **`cdkd destroy`: an old copy a deploy could not delete (`supersededResources`) is deleted in dependency order with the stack's own resources, so a replaced security group no longer makes the VPC delete fail (issue [#7073](https://github.com/go-to-k/cdkd/issues/7073))** -- `src/cli/commands/destroy-runner/superseded-schedule.ts`, `src/cli/commands/destroy-runner/under-lock.ts`. Every old copy other than a custom resource's (#6117) was deleted only after the whole reverse level walk, so an old security group still lived in the stack's VPC when the VPC was deleted: the VPC delete waited about 5 minutes, failed `DependencyViolation`, and the destroy exited 2 with state preserved until a re-run. Each old copy now goes just before the first level holding a resource its record depends on (or one whose type must be deleted after its type, the same table the levels use), and never before the level of its own current record, of a record that names its logical id, or of a type that must be deleted before it; an old copy naming no remaining resource, or whose bounds cross, keeps the after-the-levels position. Old copies keep their dependents-first order among themselves (#6770), and one never moves past its own bound to follow another (both then go after the levels); a custom resource's retry after a failed early delete takes the same position, so it now runs before its handler is deleted. A failed or skipped delete keeps its entry and the state as before. No AWS call is added. Tests: `tests/unit/cli/destroy-runner-superseded-order-7073.test.ts`; integ fixture `tests/integration/superseded-sg-destroy-order/`.
