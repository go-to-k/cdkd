- **The DynamoDB GlobalTable provider masks a secret-derived table name in its remaining log lines and failure messages (issue [#2177](https://github.com/go-to-k/cdkd/issues/2177), DynamoDB GlobalTable slice)** -- `src/provisioning/providers/dynamodb-globaltable-provider.ts`; unit tests in `tests/unit/provisioning/dynamodb-globaltable-provider-masked-log.test.ts`. `create()` and `update()` of `AWS::DynamoDB::GlobalTable` still printed the table name unmasked on several lines no deploy-engine mask reaches: the `CreateTable initiated`, ACTIVE-wait status and `Successfully created` debug lines, and the auto-scaling `Upserted auto-scaling policy`, `Deregistered auto-scaling target` and `Could not probe existing auto-scaling targets` lines. Each operation now routes every line through one masked sink set, as do the table-ACTIVE, replica-ACTIVE and replica-removal waits and the failures they throw. A secret-derived `TableName` is masked wherever it occurs, including names shorter than four characters, and including a name that state recorded as a secret reference whose old plaintext is in no bag of this deploy (a rotated secret). The protected-replacement refusal withholds its `aws dynamodb update-table` command when the table name is secret-derived. The AWS error text a create or update failure wraps is masked before it is joined; when the mask changed that text, the failure is stamped so the retry classifiers still read AWS's unmasked wording (the issue [#4244](https://github.com/go-to-k/cdkd/issues/4244) class). The `delete()` path still has no masker (issue [#2007](https://github.com/go-to-k/cdkd/issues/2007)).
