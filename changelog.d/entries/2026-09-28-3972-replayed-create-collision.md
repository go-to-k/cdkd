- **A retried create whose earlier attempt failed on an auxiliary call no longer reads its replay's "already exists" as the resource's own name collision (issue [#3972](https://github.com/go-to-k/cdkd/issues/3972))** -- `src/deployment/retry.ts` and `src/provisioning/auxiliary-failure.ts` (`isAuxiliaryFailure`), with unit tests in `tests/unit/deployment/retry-replayed-create-collision-3972.test.ts`. When a call made after the main create failed with a retryable error (a Kinesis `AddTagsToStream` throttled with `Rate exceeded`, say), the retry wrapper ran the whole `create()` again, and the replayed main create met the resource the first attempt had just made. That "already exists" was treated as a collision on the resource's own name, so `--replace` deleted the live old resource and a replacement rollback deleted the live new one. Once an attempt has failed on an auxiliary call, every error the retry wrapper throws for that operation now carries the same auxiliary mark, including through the nested retry loops of the delete-then-re-create sites. The error text and the retry schedule are unchanged, and a collision on the first attempt's main create still classifies.
