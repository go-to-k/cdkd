- **A Cloud Control-routed delete no longer deletes, by name, a resource another holder re-created under that name (issue [#6666](https://github.com/go-to-k/cdkd/issues/6666))**. A record with `provisionedBy: 'cc-api'` was deleted by its name (or name-derived ARN) with only its region compared, so after an out-of-band delete and same-name re-create, `DeleteResource` removed the newcomer. A record holding the AWS-minted id Cloud Control returns for its type (`AWS::IAM::Role` `RoleId`, `AWS::IAM::ManagedPolicy` `PolicyId`, `AWS::RDS::DBInstance` `DbiResourceId`, `AWS::RDS::DBCluster` `DBClusterResourceId`; `CC_DELETE_RECORDED_IDENTITY_ATTRIBUTES`, derived from the shared `SURVIVOR_IDENTITY_ATTRIBUTES`) is now read with one `GetResource` before the delete and compared through the same `assertRecordedIdentity` the SDK deletes use (#6655): a different id is read once more after the shared delay, then refused non-retryably, naming the attribute but neither value, keeping the record and naming `cdkd state orphan`; an absent resource proceeds to the existing already-deleted arm; a failed read throws to the retry classifiers and never falls back to the by-name delete. The read also runs before an RDS delete is handed to its SDK provider, which deletes by identifier too. A record without a usable id (`isUsableIdentityValue`), and every other type, keeps today's delete with no extra call. `AWS::DynamoDB::Table` is left out: its Cloud Control model does not return `TableId`.
