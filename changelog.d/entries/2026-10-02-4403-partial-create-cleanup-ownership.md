- **A failed create no longer deletes a pre-existing ELBv2 load balancer or target group, SNS topic or EventBridge rule that the create handed back (issue [#4403](https://github.com/go-to-k/cdkd/issues/4403))** -- `src/provisioning/providers/create-ownership.ts` (new), `src/provisioning/providers/{elbv2,sns-topic,eventbridge-rule}-provider.ts`, `docs/_contents/provider-rules.md`, unit cases per site. These create APIs answer success with a resource that already held the name (ELBv2 on identical settings, SNS `CreateTopic`, EventBridge `PutRule`, which overwrites). When a later step of the same create failed (a load balancer's `active` wait or attributes, a target group's attributes or targets, a topic's policies, delivery logging or subscriptions, a rule's targets), the provider's cleanup deleted whatever the create returned, so another stack's or a hand-made resource of that name was deleted, and an EventBridge rule was stripped of its targets first. Each provider now looks the name it sends up before the create, only when such a step is declared: `Describe*` by name for ELBv2, `GetTopicAttributes` on the ARN built from STS for SNS, `DescribeRule` on the rule's bus for EventBridge. Only the service's own not-found answer lets the cleanup run. A name that was held is left in place with a warning that it existed before this create attempt (an earlier attempt or failed deploy, another stack, or someone else), that this deploy may have changed its configuration, and that a cdkd-generated name is adopted by the next deploy, with the delete command to use only once it is confirmed no one else's; a lookup that could not answer (an ELBv2 empty answer included) leaves the resource too, with the delete command to run if this deploy created it. The EventBridge rule's cleanup warnings now go through the deploy's secret masker. The lookup and the create are two calls, so a resource created between them is still treated as this create's.
