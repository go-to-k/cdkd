- **A Lambda function's or layer version's `S3ObjectStorageMode`, and a function's `Code.SourceKMSKeyArn`, now reach AWS (issue [#5300](https://github.com/go-to-k/cdkd/issues/5300)).** cdkd copied only the bucket, key and object version of an `AWS::Lambda::LayerVersion`'s `Content` and an `AWS::Lambda::Function`'s `Code` into the request, so a template asking for `S3ObjectStorageMode: REFERENCE` deployed as the default `COPY`, and a function's deployment package was encrypted with the AWS owned key instead of the `SourceKMSKeyArn` key. Both are now sent on `PublishLayerVersion` and `CreateFunction`, and, for a function, again on the `UpdateFunctionCode` a code change sends. As with CloudFormation, removing `SourceKMSKeyArn` from a template does not move an existing function back to the AWS owned key (Lambda keeps the key on a code update that names none), and removing `S3ObjectStorageMode: REFERENCE` with a code change stores the new package as a `COPY`. `cdkd drift` skips a function's `Code.S3ObjectStorageMode`, which `GetFunction` does not return. A `REFERENCE` package is read from the asset bucket rather than copied, so [`cdkd gc`](https://github.com/go-to-k/cdkd/blob/main/docs/cli-gc.md#edge-cases) now notes what that means for versions state no longer records. Source: `src/provisioning/providers/lambda-layer-provider.ts`, `src/provisioning/providers/lambda-function-provider.ts`.
