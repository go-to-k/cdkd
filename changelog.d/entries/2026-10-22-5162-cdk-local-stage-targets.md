- **`cdkd local start-service` / `start-alb` / `start-cloudfront` / `invoke-agentcore` / `start-agentcore` now resolve a stack inside a `cdk.Stage` by its display path, and a bad `--max-tasks` / `--restart-policy` value is reported like cdkd's own option errors (issues [#5162](https://github.com/go-to-k/cdkd/issues/5162), [#5163](https://github.com/go-to-k/cdkd/issues/5163))** -- `package.json` (`cdk-local` `^0.153.2` -> `^0.154.0`), `tests/unit/cli/local-start-service.test.ts`, `tests/unit/cli/local-embed-logger-stdout.test.ts`, `tests/integration/local-invoke-container/verify.sh`, `tests/integration/local-invoke-from-state/verify.sh`. Before this change, those commands took a path-form target's first `/`-segment as the stack, matched a slash-free stack pattern as a glob over the physical name only, and kept one of two stacks sharing a physical name. Now the longest display-path prefix wins, a pattern matches the hierarchical id first and the exact physical name second (as `cdkd deploy` does), and two stacks sharing a physical name are both kept, so a command needing one stack reports the ambiguity instead of taking the first. Their `Available stacks` lists show `Physical (Display/Path)` when the two differ. A value such as `--max-tasks 84` used to be rethrown as a cdkd error; it now prints `error: option '--max-tasks <n>' argument '84' is invalid. --max-tasks 84 exceeds ...` and exits 1, with the same message text. The local engine's log lines also change: a continuation line of a multi-line message starts with two spaces, a control character renders as `\uXXXX` where cdkd showed a space, a plain identifier loses the quotes it used to carry (`Lambda 'Fn'` -> `Lambda Fn`), and an argv element on the `--verbose` docker build and docker run lines that carries a `*` is quoted (`--build-arg "KEY=***"`, `-e "KEY=***"`).
