- **An in-place update of an `AWS::IAM::Role`, `AWS::IAM::User`, `AWS::IAM::Group` or `AWS::IAM::InstanceProfile` no longer writes to a same-named one someone else made (issue [#6722](https://github.com/go-to-k/cdkd/issues/6722), part of [#6655](https://github.com/go-to-k/cdkd/issues/6655))**. The update writes by name (`UpdateRole`, its own `ManagedPolicyArns` / `Policies` / tags / permissions boundary, `UpdateUser` / `UpdateGroup`, an instance profile's `Roles`), so one re-created out of band under the recorded name received cdkd's change. With a recorded `RoleId` / `UserId` / `GroupId` / `InstanceProfileId`, the `GetRole` / `GetUser` / `GetGroup` / `GetInstanceProfile` the update already made after its writes (for its attributes) is now made before the first write and compared, so no call is added (a user or group whose `Path` moves is read again after the move, as its ARN changes). Another id refuses the update non-retryably with nothing written, naming the logical id and the attribute (no value), with `cdkd import --force` for one you replaced yourself and `cdkd state orphan` otherwise; a rollback replay and `cdkd drift --revert` compare the same way. A denied read refuses naming the permission; a credential or clock failure (an expired token), here and on the inline / managed policy principal reads, is no longer reported as a missing permission. A record this deploy created or replaced, one already matched in the same run, and a record without a usable id (written before the id was recorded, or masked) read nothing before the writes, as before.
