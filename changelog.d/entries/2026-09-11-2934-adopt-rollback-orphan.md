- **A deploy following a rolled-back deploy no longer collides with what the rollback left behind** ([#2934](https://github.com/go-to-k/cdkd/issues/2934)). A `DeletionPolicy: Retain` resource survives a rollback and leaves cdkd's state, and because cdkd's generated physical names are deterministic, the next `cdkd deploy` asked AWS for a name the orphan still held — failing and repeating forever ([#2902](https://github.com/go-to-k/cdkd/issues/2902)). The rollback now records the discarded `ResourceState` in `StackState.orphans`, and the next deploy verifies it (still in AWS, still declared by the pruned template under the same logical id and type with no explicit name, claimed by no other stack) and splices it back into state before the diff runs, so the diff produces an ordinary UPDATE and the redeploy works, contents intact. A hand-deleted orphan drops its record and the ordinary CREATE succeeds; a renamed or unverifiable one is KEPT with an info line, so the [#2916](https://github.com/go-to-k/cdkd/issues/2916) diagnosis still prints on the collision that follows; one another stack already claims STOPS the deploy. `cdkd rollback` and `cdkd destroy` no longer treat a stack holding such records as empty: the former deleted `state.json` in the same run that minted the record, the latter's fast path deleted it unconfirmed. Destroy now lists what stops being tracked. No schema bump: absent `orphans` is today's behaviour in every direction. Changed: `src/types/state.ts`, `src/deployment/{orphan-adoption,deploy-engine,rollback-executor}.ts`, `src/cli/commands/{rollback,destroy-runner,import}.ts`, `src/provisioning/resource-name.ts`. Verified on real AWS by `tests/integration/retain-orphan-redeploy` and `retain-orphan-secret`, the latter seeding a canary secret out of band and proving the plaintext reaches no S3 object version. Residual: [#2943](https://github.com/go-to-k/cdkd/issues/2943).
