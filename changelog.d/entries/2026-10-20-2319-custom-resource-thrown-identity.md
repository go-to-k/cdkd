- **A failed custom resource create or update no longer writes the caller's account id, assumed-role ARN and session name into the persisted deployment events (issue [#2319](https://github.com/go-to-k/cdkd/issues/2319))** -- `src/provisioning/providers/custom-resource-provider.ts`, and unit cases. When the backing Lambda `Invoke`, the SNS `Publish` or the response placeholder `PutObject` was denied, the thrown message quoted AWS's raw text, which names the caller, and `deployments/{runId}.jsonl` outlives the run. The message now carries the error class (`AccessDeniedException. Re-run with --verbose for AWS's own message.`), and AWS's text goes to the debug log, masked through the operation's secret masker. A backing Lambda that never became ready keeps its `StateReasonCode` / `LastUpdateStatusReasonCode` in the message, but the reason sentence, which AWS words with ARNs, goes to the debug log too. The retry warning for a denial before the request was delivered, and the warning for a delete whose handler could not be reached, name the class too. The handler's own FAILED reason and other cdkd-authored errors keep their text. An IAM grant that is still propagating is retried as before: that retry runs on AWS's own error inside the invoke loop, before the message is built. The AWS error stays as the `cause`.
