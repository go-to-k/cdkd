- **`cdkd state list --tree` no longer loses the WHOLE listing to one deep parent chain (issue [#3155](https://github.com/go-to-k/cdkd/issues/3155))** -- `src/cli/commands/state-list-tree.ts`, `src/cli/commands/state.ts`, `docs/cli-state.md`, `.claude/rules/layout-cli.md`, `tests/unit/cli/{state-list-tree,state-list,state-list-tree-cap-doc-sync}.test.ts`. Four steps in the `--tree` path recursed once per level of the tree -- the child sort inside `buildStackTree`, the box-drawing renderer, `stackTreeToJson`, and the `JSON.stringify` that serializes it for `--tree --json` -- and NONE of them sits inside `renderTreeMode`'s per-stack guard, which covers only the state READ. So a long enough chain of `parentStack` links ended the command with a `RangeError` and printed no rows at all, for every stack in the bucket, not just the chain's own. `buildStackTree` now caps a node's depth at 100 levels below its root: one that would sit deeper is placed at the root instead, the treatment an orphan or a parent-loop member already gets, and the chain resumes there as its own tree. That bounds all four steps at once; `MAX_STACK_TREE_DEPTH`'s doc comment carries why rewriting any single step iteratively could not. Every record still appears exactly once, and a tree within the cap renders byte-identically, so no ordinary listing changes -- CloudFormation stops at five levels of nested stacks, so an app that also deploys through CloudFormation cannot exceed it; cdkd's own nested-stack engine imposes no limit, so a deeper tree IS possible and now stays readable instead of failing. The depth is computed in one non-recursive pass over the parent links, like the existing loop detection; the child sort still recurses, bounded by the cap like every other step. This also covers a deep chain hanging off a parent LOOP, which go-to-k/cdkd#3157 made reachable by correctly rooting every loop member.
