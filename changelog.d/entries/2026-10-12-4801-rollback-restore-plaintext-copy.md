- **A rollback that restores a resource holding a copy of a secret-derived physical name now records that copy as AWS knows it, so the next `cdkd destroy` can delete it (issue [#4801](https://github.com/go-to-k/cdkd/issues/4801))** -- `src/deployment/rollback-executor/replay-secrets.ts` (`redactRollbackRecord`, `keepPersistedPlainLeaves`), with the previous record's attributes passed in by `src/deployment/rollback-executor.ts`, `src/deployment/rollback-executor/replay-revert.ts` and `src/deployment/rollback-executor/replay-reverse-replacement.ts`, and the rollback journal's copy of each previous record in `src/deployment/deploy-engine/rollback.ts`. When an automatic rollback (or `cdkd rollback`) reverted a resource such as an `AWS::SQS::QueuePolicy` whose queue is named from a `{{resolve:secretsmanager:...}}` reference, the restored record had the queue name inside its `Queues` URL replaced by the reference, so `cdkd destroy` failed with "The address https://sqs.../{{resolve:secretsmanager:...". The restore, and the journal `cdkd rollback` restores from, now keep a plaintext value exactly as the previous record stored it, in properties and attributes, as a normal deploy stores it. A value the previous record stored as a reference is still stored as the reference, and the rollback writes no value the previous record did not already hold. A record an older cdkd wrote with a secret value in plaintext is restored as it was; `cdkd scrub` repairs it.
