- **An `AWS::ApiGateway::Authorizer`, `AWS::ApiGateway::Stage` or `AWS::ApiGateway::Method` recorded `provisionedBy: 'cc-api'` returns to its SDK provider (issue [#6490](https://github.com/go-to-k/cdkd/issues/6490), batch 7)** -- `src/provisioning/provider-registry/sticky-exempt.ts`, `src/provisioning/sticky-exempt-physical-id.ts` and the new `cc-to-sdk-reroute-common-types-7` integ. The three types are now `'sdk-coverage'` members of `STICKY_CC_MIGRATION_EXEMPT`, so such a resource on Cloud Control moves to the SDK provider in place on the next deploy that changes it; `--pin-cc-api <LogicalId>` declines that. Cloud Control records an authorizer as `<restApiId>|<authorizerId>` and a stage as `<restApiId>|<stageName>` while the SDK provider records the bare second segment, so each entry declares a strict physical-id normalizer and the flip writes the bare id; an id of any other shape is refused before any AWS call, naming `--pin-cc-api <LogicalId>`. A method's `<restApiId>|<resourceId>|<httpMethod>` is the same in both layers. Both forms were measured on live resources. `AWS::ApiGateway::Resource` is not admitted, since every property it has is create-only and so no deploy updates one in place, and neither is `AWS::ApiGateway::Deployment`, whose SDK provider does not write `StageName`, `StageDescription` or `DeploymentCanarySettings`. `cdkd diff` annotates the move `[returning to SDK provider]`.
