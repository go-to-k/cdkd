- **An `AWS::GuardDuty::Detector` can now be updated in place (issue [#4910](https://github.com/go-to-k/cdkd/issues/4910))** -- `src/provisioning/cloud-control-provider.ts`, a new `src/provisioning/guardduty-detector-patch.ts`, unit cases and a new `guardduty-detector-update` integ fixture. cdkd updates the detector through Cloud Control, which applies the patch on top of the model it reads back. For a detector that model carried both `DataSources` and the full `Features` list on every read measured (us-east-1 and us-west-2), and `UpdateDetector` refused them together, whichever of the two the template declared: a scalar-only change failed with `EKS_RUNTIME_MONITORING and RUNTIME_MONITORING cannot be provided in the same request`, and a `Features` change with `both data sources and features were provided`. So the detector deployed once and then refused those updates. Now, for each of the two keys a non-empty update patch has no op on, the patch also gets `add /<key>` with the declared value, or `remove /<key>` when the template does not declare it, so the request carries what the template declares, as a CloudFormation update does. Features the template omits keep their AWS status, and `RDS_DATA_RISK`, which GuardDuty enables under `RDS_LOGIN_EVENTS`, stays enabled. Every other type is unchanged.
