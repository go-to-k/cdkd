- **An `AWS::GuardDuty::Detector` declared with `Features` can now be updated in place (issue [#4910](https://github.com/go-to-k/cdkd/issues/4910))** -- `src/provisioning/cloud-control-provider.ts`, a new `src/provisioning/guardduty-detector-patch.ts`, unit cases and a new `guardduty-detector-update` integ fixture. cdkd updates the detector through Cloud Control, which applies the patch on top of the model it reads back. For a detector that model carries `DataSources` and the full `Features` list, and `UpdateDetector` refused both: a scalar-only change failed with `EKS_RUNTIME_MONITORING and RUNTIME_MONITORING cannot be provided in the same request`, and a `Features` change with `both data sources and features were provided`. The detector deployed once and then could not change. Now, when the template declares `Features` as a list and no `DataSources`, a non-empty update patch also gets `add /Features` with the declared list and `remove /DataSources`, each unless the patch already has an op on that key. Features the template omits keep their AWS status, and `RDS_DATA_RISK`, which GuardDuty enables under `RDS_LOGIN_EVENTS`, stays enabled. A detector declaring `DataSources` and every other type are unchanged.
