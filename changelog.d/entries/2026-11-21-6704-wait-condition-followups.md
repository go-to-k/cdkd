- **A wait condition on a handle deployed by an earlier cdkd now works, and a wait condition no longer needs `DependsOn` on the instance that signals it (issue [#6704](https://github.com/go-to-k/cdkd/issues/6704))** -- `src/analyzer/dag-builder.ts`, `src/analyzer/diff-calculator/legacy-handle-heal.ts` (new), `src/analyzer/diff-calculator/calculate-diff.ts`, `src/cli/commands/diff-recursive/render.ts`, `src/deployment/deploy-engine/update/provision-update.ts`, `src/provisioning/providers/wait-condition-handle-provider.ts`, `src/provisioning/wait-condition-handle-id.ts` (new), `src/provisioning/wait-condition-signal-store.ts`. A handle recorded with the pre-signal-URL placeholder id kept it forever, so a wait condition on it was refused until the handle was renamed. When a wait condition in the template waits on such a handle, the deploy now issues its URL and updates the resources embedding it in the same run (with a warning: an EC2 instance's `UserData` change stops and starts it, and a booted instance signals only once replaced); any other placeholder handle is left alone. Every resource downstream of a wait condition's handle (an instance, or an Auto Scaling group through its launch template) now runs before the wait, so a small `--concurrency` cannot start the wait first and time it out. The handle URL is valid for 12 hours, CloudFormation's own lifetime, instead of 7 days, and the short-lifetime warning fires only when the signing credentials end it sooner.
