- **`cdkd rollback` no longer deletes a resource `cdkd import` adopted after the failed deploy (issue [#4523](https://github.com/go-to-k/cdkd/issues/4523))** -- `src/cli/commands/import.ts`, `src/state/s3-state-backend.ts`, `src/types/rollback-journal.ts`, `src/cli/commands/rollback.ts`, `src/deployment/nested-child-journal.ts`, `src/deployment/rollback-executor/plan.ts`. The import did not touch the rollback journal. If a kept journal segment held a completed CREATE of an explicitly named resource, and the user then re-created that name by hand and imported it under the same logical id, the replay saw a physical id equal to the imported record's and deleted the resource the user had just adopted. Before it writes state, the import now records each adopted resource, as its logical id, the physical id it records and its type, in a new additive `importedResources` field on every segment that holds an operation of that resource, and marks the id superseded on the newest segment. `cdkd rollback` leaves those operations alone (an op of the id that recorded another physical id or type, or an id passed to `--orphan`, replays as before), including failed ones under `--revert-failed`, and lists them in its plan as `adopted by cdkd import after this deploy`. The nested-child replay does the same, and neither a completed in-place UPDATE nor (under `--revert-failed`) a failed UPDATE is reverted onto a record that now names another resource. Segments that later deploys add carry no mark and replay as before. The import now refuses, and writes no state, when it cannot read or write the journal.
