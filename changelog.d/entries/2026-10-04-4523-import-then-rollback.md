- **`cdkd rollback` no longer deletes a resource `cdkd import` adopted after the failed deploy (issue [#4523](https://github.com/go-to-k/cdkd/issues/4523))** -- `src/cli/commands/import.ts`, `src/state/s3-state-backend.ts`, `src/types/rollback-journal.ts`, `src/cli/commands/rollback.ts`, `src/deployment/nested-child-journal.ts`. The import did not touch the rollback journal. If a kept journal segment held a completed CREATE of an explicitly named resource, and the user then re-created that name by hand and imported it under the same logical id, the replay saw a physical id equal to the imported record's and deleted the resource the user had just adopted. Before it writes state, the import now records each adopted resource (logical id, physical id and type) in a new additive `importedResources` field on every segment that holds an operation of that logical id, and marks the id superseded on the newest segment. `cdkd rollback` and the nested-child replay then run none of those segments' operations for the id, failed ones included. An operation that recorded the adopted resource is listed as `adopted by cdkd import after this deploy`. One that recorded another resource under the id is listed with its physical id as not reverted, records a `ROLLBACK_RESOURCE_SKIPPED` event, warns and makes the rollback exit 2. Completed operations of an id passed to `--orphan` are not covered. Segments that later deploys add carry no mark and replay as before. The import now refuses, and writes no state, when it cannot read or write the journal.
