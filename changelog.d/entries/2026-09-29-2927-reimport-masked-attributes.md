- **A `cdkd import --resource <id>=<physicalId> --force` re-import no longer replaces a good recorded attribute with the redaction mask, and says so when it cannot clear one (issue [#2927](https://github.com/go-to-k/cdkd/issues/2927))** -- `src/cli/commands/import.ts` (new `reimportedAttributes`, called from `buildStackState`), `src/provisioning/cloud-control-provider.ts` (the two unreadable-model warnings), `docs/import.md`, a new unit file and a new `import-reimport-masked-attrs` integ fixture. `CloudControlProvider.import` masks every model key it cannot certify as an attribute but keeps the key, so a re-import's bag of masks was non-empty and overwrote a deploy-recorded bag of real values for the same physical id; every dependent's next `Fn::GetAtt` of those keys was then refused. Now a masked value never displaces an unmasked stored value, per top-level key (the import names each kept key), while certified keys still take the fresh value. The opposite case keeps its behavior on purpose: when the re-import yields no value for a key the record already masks (an unreadable `GetResource` model, the key masked again, or a partial import omitting it), the mask is kept rather than cleared, because an attribute missing from state resolves to the physical id instead of failing. That used to happen silently, so the next deploy repeated the refusal whose remedy the user had just followed; the import now warns, naming the logical id and each key that stays masked, and the Cloud Control unreadable-model warnings no longer claim an `Fn::GetAtt` falls back to the physical id when a same-physical-id record's attributes are kept.
