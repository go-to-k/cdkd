- **The Glue providers mask secret-derived names in their own log lines and refusals (issue [#2177](https://github.com/go-to-k/cdkd/issues/2177), Glue family slice)** -- `src/provisioning/providers/glue-provider.ts`; unit tests in `tests/unit/provisioning/glue-providers-masked-warn.test.ts`. A Glue database, table, workflow, security configuration, job, crawler, connection or trigger name resolved from a `{{resolve:secretsmanager:...}}` reference used to reach the provider's own debug and warning lines in plaintext, since those lines pass through no deploy-engine mask. `create()` and `update()` of every Glue type now route each line through the deploy's masker, and each name and catalog id is masked before it joins the sentence, so a secret shorter than four characters is caught too. A name of three or more characters that is itself a secret is also masked where an AWS error quotes it back in the spelling it was given; a short secret merely embedded in AWS error text, or a database or table name AWS echoes lowercased, is not. The same holds for the update refusals (a nested rename, a `CatalogId` move, an undecodable table id) and the pre-update read failure. On `update()` the recorded name is masked as well when the previous value in state is a secret reference or the redaction mask `***`, which covers a rotated secret whose old plaintext is in no bag of this deploy; the `***` case is in the shared `src/provisioning/masked-retry-logger.ts` helper, so the IAM and S3 bucket providers' `update()` lines gain it too. The `delete()` path still has no masker (issue [#2007](https://github.com/go-to-k/cdkd/issues/2007)).
