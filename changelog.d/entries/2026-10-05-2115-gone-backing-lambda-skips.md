- **`cdkd destroy` now reports a custom resource whose backing Lambda is gone as skipped, keeping its state record, instead of treating it as already deleted (issue [#2115](https://github.com/go-to-k/cdkd/issues/2115))** -- `src/provisioning/providers/custom-resource-provider.ts`, `src/provisioning/region-check.ts` (`DeleteContext.stackDestroy`), `src/cli/commands/{destroy,state,destroy-runner}.ts`, `src/provisioning/providers/nested-stack-provider.ts` (a nested child inherits the flag only from a stack destroy). The issue-#804 `GetFunction` pre-check used to answer `ResourceNotFoundException` by dropping the record and letting `cdkd destroy` exit 0. Its usual caller was the second destroy after a handler refused its `Delete` (#2054): the first run kept the record but deleted the backing Lambda, and the second dropped the record over a resource that was still live. On a stack destroy (`cdkd destroy` / `cdkd state destroy`) the pre-check now returns a skip (`backing Lambda function is gone — Delete handler not invoked`), so the record is kept and the destroy exits 2. This matches CloudFormation, where a custom resource whose delete cannot be confirmed leaves the stack `DELETE_FAILED` until you retry with `RetainResources`. **Compatibility:** a shared provider stack destroyed before the stacks that use it now makes their destroy exit 2. Redeploy a function at that ARN and re-run, or confirm what the handler manages is gone and drop the records with `cdkd state orphan <stack> --stack-region <region>`. A `cdkd deploy` delete (template removal, replacement, rollback) keeps the warn-and-drop, as CloudFormation ignores delete failures in an update's cleanup phase. The pre-check is still fail-fast: one `GetFunction` call, no 10-minute waiter. Docs: `docs/_contents/cli-destroy.md`, `docs/_contents/troubleshooting.md`. Tests: `tests/unit/provisioning/custom-resource-delete-failed-response.test.ts` and its CR siblings; integ phase 4 of `tests/integration/custom-resource-provider/`.
