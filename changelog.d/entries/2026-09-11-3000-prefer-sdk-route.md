- **`--allow-unsupported-properties` is renamed `--prefer-sdk-route`, and cdkd now says when your preference had no effect (issue [#3000](https://github.com/go-to-k/cdkd/issues/3000))** — `src/cli/options.ts`, `src/cli/commands/deploy.ts`, `src/provisioning/provider-registry.ts`, `src/deployment/recreate-targets.ts`, 8 docs pages, `tests/unit/cli/options.test.ts`, `tests/unit/provisioning/provider-registry-report-silent-drops.test.ts`. The old name read as the OPPOSITE of its behaviour and rhymed with `--allow-unsupported-types`, which runs the other way: that one ENABLES a Cloud Control attempt, this one DECLINES the Cloud Control auto-route. Why `prefer` rather than a negative is in `preferSdkRouteOption`'s doc comment: routing is per RESOURCE while the preference is per `<Type>:<Prop>`, so "do not route" is a promise the flag cannot keep. The help text carries what the name does not — the named values go UNWRITTEN when the preference is honoured, and it is ignored when the resource routes to Cloud Control for another reason. **The old spelling still works**: hidden from `--help`, warning once per process and naming the successor. Both feed one set. **New behaviour**: when the preference is INERT — a property was named, an uncovered sibling routed the resource to Cloud Control, and Cloud Control wrote the named property after all — cdkd WARNS, naming the ignored property, the sibling that caused it, and the remedy. It fires only for a user who passed the flag for a property on that resource, so it is not the broadcast warn issue [#2750](https://github.com/go-to-k/cdkd/issues/2750) retired; that one falsely claimed the property would be dropped, and the narrowed assertion in `provider-registry-report-silent-drops.test.ts` keeps the false sentence gone. Five option-surface probes, all red; live-verified on the built binary.
