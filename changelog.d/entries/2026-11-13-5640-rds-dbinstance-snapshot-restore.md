- **The SDK provider restores an `AWS::RDS::DBInstance` from `DBSnapshotIdentifier` or `DBClusterSnapshotIdentifier` (issue [#5640](https://github.com/go-to-k/cdkd/issues/5640))** -- `src/provisioning/providers/rds/instance-restore.ts`, `instance-create.ts`, `instance-update.ts`, `drift.ts`, `rds-provider.ts`, `src/provisioning/restore-source-guard.ts`, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, unit tests, the RDS wire cases, and the new `rds-dbinstance-snapshot-restore` integ. Before, an instance declaring either key (CDK's `DatabaseInstanceFromSnapshot`) routed through Cloud Control. Now the create is a `RestoreDBInstanceFromDBSnapshot` carrying the members CloudFormation's handler sends: the engine, when undeclared, is read from the snapshot, an undeclared `MultiAZ` is sent as `false` for a DB snapshot (except SQL Server Enterprise / Standard), and the members the restore call has no room for (the password, retention, windows, ...) go out in the same follow-up `ModifyDBInstance` a read replica gets, once the instance is `available`. A snapshot that does not exist fails the create before anything is made. Keys the snapshot decides instead (`KmsKeyId`, `MasterUsername`, ...) are named in a warning. An added or changed snapshot on an existing instance is refused, as CloudFormation refuses it; a removed one changes nothing. A replacement whose `DBSnapshotIdentifier` names one of the replaced instance's own automated snapshots is refused before the delete, which would remove it. A declared `SourceDBInstanceIdentifier` still makes a read replica and the snapshot is not applied, as in CloudFormation. Neither key is read back for drift. The point-in-time keys (`RestoreTime`, `UseLatestRestorableTime`, `SourceDBInstanceAutomatedBackupsArn`, `SourceDbiResourceId`) and `SourceDBClusterIdentifier` stay on Cloud Control. Resources already deployed through Cloud Control stay there.
