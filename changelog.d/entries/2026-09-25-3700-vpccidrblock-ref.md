- **`Ref` to an `AWS::EC2::VPCCidrBlock` returns the association id, not cdkd's composite physical id (issues [#3700](https://github.com/go-to-k/cdkd/issues/3700) and [#3704](https://github.com/go-to-k/cdkd/issues/3704))** -- `src/deployment/intrinsic-function-resolver.ts`, `src/cli/commands/export.ts` (comment only), `tests/unit/deployment/intrinsic-functions.test.ts`.
  - The type is always Cloud-Control-routed and stored as `<Id>|<VpcId>`, while CloudFormation's `Ref` returns the association id (`vpc-cidr-assoc-…`). A hand-written `Ref` to one resolved to the raw composite. The type now joins `REF_RETURNS_SEGMENT_BEFORE_FIRST_PIPE`; a pipe-free id passes through unchanged. CDK's own dual-stack `Vpc` only `DependsOn` the resource, so generated templates were not affected.
  - The `cdkd export` splitter's comment no longer says a migrate records the bare id. No cdkd writer does: Cloud Control rejects the bare id as an identifier (measured), so an import that passed it through adopted nothing, and since #3701 a migrate completes it first. The splitter still accepts it, defensively.
