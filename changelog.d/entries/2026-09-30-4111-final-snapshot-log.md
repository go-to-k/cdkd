- **A `DeletionPolicy: Snapshot` delete no longer logs the final-snapshot identifier built from the physical id (issue [#4111](https://github.com/go-to-k/cdkd/issues/4111))** -- `src/provisioning/providers/{rds,docdb,neptune,elasticache}-provider.ts`, `docs/_contents/cli-destroy.md`. Deleting an `AWS::RDS::DBInstance`, `AWS::RDS::DBCluster`, `AWS::DocDB::DBCluster`, `AWS::Neptune::DBCluster` or `AWS::ElastiCache::CacheCluster` under a Snapshot policy (in `cdkd destroy`, a rollback or a deploy's delete) printed `with final snapshot <physicalId>-final-<timestamp>` at INFO, so a physical id taken from a `{{resolve:secretsmanager:...}}` value reached default-verbosity output in a lowercased spelling. The line now reads `Deleting <type> <logicalId> with a final snapshot (DeletionPolicy: Snapshot)`, and the other lines of those five delete paths name the logical id instead of the physical id: the debug lines (the entry line, the `--remove-protection` flip failure, the already-gone skip, the wait-for-deleted status poll) and the `Timed out waiting for ... to be deleted` error. The snapshot is still taken under the same identifier; `docs/_contents/cli-destroy.md` spells out how the identifier is derived from the physical id, so the snapshot can be found by its prefix. The `--remove-protection` guard helper's debug line and AWS-supplied error text can still carry the physical id; a masker threaded through the delete context, which those and other providers' lines need, stays with issue [#3869](https://github.com/go-to-k/cdkd/issues/3869). Tests: `tests/unit/provisioning/final-snapshot-delete-log-4111.test.ts`.
