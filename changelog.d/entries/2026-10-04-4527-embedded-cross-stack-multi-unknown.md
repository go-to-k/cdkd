- **A cross-stack secret read embedded beside two or more parts the template cannot state, or under an `Fn::If`, now persists its OWN `{{resolve:...}}` expression, not a sibling's (issue [#4527](https://github.com/go-to-k/cdkd/issues/4527), the residual of [#2298](https://github.com/go-to-k/cdkd/issues/2298))** -- `src/deployment/intrinsic-function-resolver.ts`, `src/deployment/intrinsic-resolver/sub.ts`, `src/deployment/intrinsic-resolver/string-functions.ts`, `src/deployment/secret-redaction/pairs.ts`, `src/deployment/secret-redaction/placeholder-positions.ts`. A leaf such as `Fn::Sub 'jdbc:mysql://${AWS::Region}.${AWS::AccountId}.host/?pw=${Child.Outputs.Pw}'`, the same through `Fn::Join`, or an `Fn::If` selecting such a leaf, was still redacted by the plaintext-keyed value scan: the #2298 fix aligned the template against the resolved string and allowed at most one part of unknown text. When another leaf of the same resource resolved to the same plaintext (one secret at two version-stage spellings), the embedded leaf was persisted with the OTHER reference, which a rollback or `cdkd drift --revert` would re-resolve and push to AWS as the wrong secret version. No plaintext was exposed. The resolver now records where each `Fn::ImportValue` / `Fn::GetStackOutput` / `Fn::GetAtt` read (and each `${Res.Attr}` placeholder) landed on an `Fn::Sub` / `Fn::Join` output, keyed as the association store keys that read, and the persist path answers each such span from that read's own association, as it already did for a parameter `Ref`. A resource whose record holds the sibling's expression can take one UPDATE on the first deploy after upgrading (a replacement if the property is create-only), even though the value sent is unchanged. Tests: `tests/unit/deployment/secret-redaction-cross-stack-embedded.test.ts`; integ arm `MultiUnknownSecretPair` in `tests/integration/nested-stack-secret/`.
