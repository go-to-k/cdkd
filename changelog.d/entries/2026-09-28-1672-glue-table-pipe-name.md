- **A Glue table whose name contains `|` now deploys, updates, destroys and resolves `Ref` as in CloudFormation (issue [#1672](https://github.com/go-to-k/cdkd/issues/1672))** -- `src/provisioning/composite-id.ts`, `src/provisioning/providers/glue-provider.ts`, `src/deployment/intrinsic-function-resolver.ts`; unit tests in `tests/unit/provisioning/composite-id*.test.ts`, `tests/unit/provisioning/providers/glue-provider.test.ts` and `tests/unit/deployment/intrinsic-{functions,ref-state-mask}.test.ts`; assertion 11 of the `glue-update-hardening` fixture. AWS accepts a table named `a|b` and CloudFormation manages it, but `cdkd deploy` refused it, because the recorded id `<databaseName>|a|b` was read back by its last `|`: `Ref` would have returned `b`. `Ref` now returns everything after the recorded `DatabaseName`, falling back to everything after the first `|`, and the create no longer refuses the table name. `cdkd import` adopts such a table when it is paired with the template's `DatabaseName`, including CloudFormation's bare `a|b` id; an id equal to the template's table name is read only as that name, and otherwise every reading of an id is probed and the import refuses when more than one exists and the template's table name does not settle it. A database name containing `|` is still refused. The per-type audit found no other type whose AWS-accepted values can contain `|` except the Route 53 record name, tracked in [#3890](https://github.com/go-to-k/cdkd/issues/3890); a Glue database name containing `|` is tracked in [#3892](https://github.com/go-to-k/cdkd/issues/3892). The refusal message now names those issues instead of the closed #1672, and makes no claim about AWS for any other type.
