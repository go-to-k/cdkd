- **`cdkd local invoke` / `cdkd local start-api` now REFUSE a relative `aws:asset:path` that escapes the assembly, and WARN on an absolute one that points outside it (issue [#3494](https://github.com/go-to-k/cdkd/issues/3494), PR #3529)** -- `src/local/lambda-resolver.ts`, `src/cli/commands/local-start-api.ts`, `src/utils/assembly-path.ts`. Both resolvers spelled a Lambda's code path as `isAbsolute(p) ? p : resolve(cdkOutDir, p)`, so `..` folded exactly as `join` does and left the assembly silently. The result is bind-mounted read-only at `/var/task` (a layer's at `/opt`) into a container running handler code the SAME assembly supplied, and `cdkd local invoke` forwards the caller's credentials -- so a hand-modified `cdk.out` could hand the attacker's handler any host directory. Measured before the change: both sites returned a throwaway directory beside the assembly verbatim as the path to mount. **Behavior change:** a relative path resolving outside the app's outdir is now refused; nothing a real `cdk synth` emits has that shape. An ABSOLUTE path is still honoured, and that asymmetry is deliberate: `cdk synth --no-staging` (`aws:cdk:disable-asset-staging`) makes CDK emit the asset's absolute SOURCE directory rather than `asset.<hash>` (measured, aws-cdk-lib 2.268), so refusing it would reject the output of a documented CDK CLI flag. It now prints a warning naming the directory when it leaves the outdir, and stays silent when it does not. Containment binds to `StackInfo.assetOutdir`, NOT the manifest's directory: a Lambda under a `cdk.Stage` legitimately carries `../asset.<hash>`. Both sites share ONE spelling, `resolveAssetCodeDirectory`, throwing through each caller's own `wrapError` so each keeps its error class; the absolute arm's verdict comes from the new `absoluteAssemblyPathEscape`, beside `resolveAssemblyPath` so the rule is not re-spelled. Verified accepted against a real 2.268 synth with a Stage, a nested stack, a `Code.fromAsset` function and a layer.
