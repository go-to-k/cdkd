- **`cdkd local invoke` / `cdkd local start-api` now REFUSE an `aws:asset:path` that is absolute or escapes the assembly, instead of bind-mounting it (issue [#3494](https://github.com/go-to-k/cdkd/issues/3494), PR #3529)** -- `src/local/lambda-resolver.ts`, `src/cli/commands/local-start-api.ts`, `tests/unit/local/local-asset-code-path-containment.test.ts`. Both resolvers spelled a Lambda's code path as `isAbsolute(p) ? p : resolve(cdkOutDir, p)`, so an ABSOLUTE `Metadata['aws:asset:path']` was honoured on purpose and `..` folded exactly as `join` does. The result is bind-mounted read-only at `/var/task` (a layer's at `/opt`) into a container running handler code the SAME assembly supplied, and `cdkd local invoke` forwards the caller's credentials -- so a hand-modified `cdk.out` could hand the attacker's handler any host directory, adding raw long-lived credentials and non-AWS secrets to a session it already held. Measured before the change against a throwaway directory beside the assembly: both shapes, at both sites, returned it verbatim as the path to mount. **Behavior change:** an assembly that used to work can now be refused. Two refusals worded APART, because refusing `..` while honouring an absolute path closes almost nothing and looks closed. Both sites now share ONE spelling, `resolveAssetCodeDirectory`, throwing through each caller's own `wrapError` so `cdkd local invoke` keeps `LocalInvokeResolutionError` and its own command name -- a second copy is how a guard on one twin becomes a guard on neither. Containment binds to `StackInfo.assetOutdir`, NOT the manifest's directory: a Lambda under a `cdk.Stage` legitimately carries `../asset.<hash>`, since `cdk synth` stages a Stage's assets into the app outdir. Verified accepted against a real aws-cdk-lib 2.268 synth carrying a Stage, a nested stack, a `Code.fromAsset` function and a layer, and against every committed integ assembly. The matching `cdk-local` change is a separate PR in that repository.
