- **`cdkd local invoke` / `cdkd local start-api` now REFUSE an `aws:asset:path` that is absolute or escapes the assembly, instead of bind-mounting it (issue [#3494](https://github.com/go-to-k/cdkd/issues/3494), PR #3529)** -- `src/local/lambda-resolver.ts`, `src/cli/commands/local-start-api.ts`. Both resolvers spelled a Lambda's code path as `isAbsolute(p) ? p : resolve(cdkOutDir, p)`, so an ABSOLUTE value was honoured on purpose and `..` folded exactly as `join` does. The result is bind-mounted read-only at `/var/task` (a layer's at `/opt`) into a container running handler code the SAME assembly supplied, and `cdkd local invoke` forwards the caller's credentials -- so a hand-modified `cdk.out` could hand the attacker's handler any host directory, adding raw long-lived credentials and other secrets to a session it already held. Measured before the change: both shapes, at both sites, returned a throwaway directory beside the assembly verbatim as the path to mount. **Behavior change:** an assembly that used to work can now be refused -- including a real one, since `cdk synth --no-staging` (`aws:cdk:disable-asset-staging`) makes CDK emit the absolute SOURCE directory rather than `asset.<hash>` (measured, aws-cdk-lib 2.268). cdkd cannot tell that apart from a planted path, so it refuses and the message names `--no-staging` as the likely benign cause and says to re-synthesize without it. Two refusals worded APART, because refusing `..` while honouring an absolute path closes almost nothing and looks closed. Both sites share ONE spelling, `resolveAssetCodeDirectory`, throwing through each caller's own `wrapError` so each keeps its error class and command name. Containment binds to `StackInfo.assetOutdir`, NOT the manifest's directory: a Lambda under a `cdk.Stage` legitimately carries `../asset.<hash>`. Verified accepted against a real 2.268 synth with a Stage, a nested stack, a `Code.fromAsset` function and a layer, and against the integration fixtures' assemblies.
