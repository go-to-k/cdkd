- **A failed DynamoDB Table or GlobalTable create, update or delete no longer writes the caller's account id, assumed-role ARN and session name into the persisted deployment events (issue [#2319](https://github.com/go-to-k/cdkd/issues/2319))** -- `src/provisioning/providers/dynamodb-table-provider.ts`, `dynamodb-globaltable-provider.ts`, and unit cases. The thrown message quoted AWS's raw text, which names the caller on an `AccessDeniedException`, and `deployments/{runId}.jsonl` outlives the run. The message now carries the error class (`AccessDeniedException. Re-run with --verbose for AWS's own message.`), and AWS's text goes to the debug log, masked with the operation's secret masker. A cdkd-authored or transport error keeps its text. The AWS error stays as the `cause`, so an IAM grant that is still propagating is retried as before. An occupied name (`Table already exists`) still says it already exists, so a create-first replacement still recognises the name collision, and a delete that gives up on a busy global secondary index still says so and that re-running the destroy succeeds once the index is ACTIVE. The GlobalTable TimeToLive rate-limit refusal closes the class as one sentence before its remedy.
