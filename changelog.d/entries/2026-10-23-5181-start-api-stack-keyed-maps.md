- **`cdkd local start-api` serves several stacks that reuse a construct id, each with its own Lambdas, Stage and CORS (issue [#5181](https://github.com/go-to-k/cdkd/issues/5181))** -- `src/cli/commands/local-start-api.ts`, `tests/integration/local-invoke-stage/`. Take two stacks with their own physical names that each declare `new HttpApi(this, 'Api')` backed by a `Handler` Lambda, served together with `--stack 'Svc*'`. Before [#5177](https://github.com/go-to-k/cdkd/pull/5177), one stack's Lambda, Stage variables or CORS settings answered the other stack's routes. #5177 made start-api refuse that set instead. Now the container specs and the Stage and CORS maps are keyed by stack and logical ID, so each stack's API is served from its own handler with its own Stage and CORS. Two refusals remain. start-api still refuses two served stacks that share one physical stack name ([#5175](https://github.com/go-to-k/cdkd/issues/5175)). It also refuses a bare logical ID in `--assume-role <LogicalId>=<arn>` or an `--env-vars` key when more than one served stack declares that Lambda. The error names the stacks, and for `--env-vars` it suggests the stack-qualified construct-path key, such as `"SvcA/Handler"`.
