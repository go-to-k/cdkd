- **A Glue `TableInput.Name` rename is refused instead of written onto another table (issue [#3724](https://github.com/go-to-k/cdkd/issues/3724))** -- `GlueProvider.updateTable` / `updateDatabase` and `GlueConnectionProvider.update` in `src/provisioning/providers/glue-provider.ts`, unit tests in `tests/unit/provisioning/providers/glue-provider.test.ts`, and phase 2c of the `glue-update-hardening` fixture. None of the registry schemas marks the nested name CDK emits (`TableInput.Name`, `DatabaseInput.Name`, `ConnectionInput.Name`) createOnly, so a rename through it was deployed as an in-place update. For a table, `UpdateTable` addresses the table by `TableInput.Name`, so the update rewrote whichever table held the new name -- possibly one cdkd does not manage -- while the state record kept the old one; for a database or connection the record kept the old name whatever AWS did with the new one. The update now fails before any Glue call with a `ResourceUpdateNotSupportedError` naming both names, and `cdkd deploy --replace` (plus `--force-stateful-recreation` for a table or database) performs the rename as a DELETE + CREATE. A case-only change to a table or database name, which Glue folds to lowercase, still updates in place; a name that is neither a string nor a safe integer is refused. On a stack that already hit the bug, the state record can differ from an unchanged template, and the refusal says so.
