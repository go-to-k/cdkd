- **Replacing an un-named `AWS::Lambda::Permission` no longer fails the name-idempotent guard, with or without `--replace` (issue [#5137](https://github.com/go-to-k/cdkd/issues/5137))** -- `src/provisioning/providers/lambda-permission-provider.ts`, `src/deployment/type-change-guard.ts`, `docs/provisioning-layers.md`. The SDK provider sent the bare logical id as the statement id. When a permission was replaced (for example because its function was replaced behind an API Gateway method), the new statement came back under the old id, and the deploy refused it as "the create returned the existing resource". Under `--replace` it deleted the old statement and then failed to re-create the new one, because the new one already existed. On a stack with a stack instance id, the statement id is now generated as `<StackName>-<LogicalId>-<suffix>`, as CloudFormation does, with a new suffix for each replacement, so the replacement creates first. A legacy stack keeps sending the bare logical id. On either kind of stack, two records with the same id whose `FunctionName`s name different functions now count as two statements, so the old one is deleted from the old function. Existing records keep their ids.
