- **`cdkd destroy --remove-protection` no longer fails when AWS refuses the final-snapshot delete right after the guard change on an RDS / DocDB / Neptune DB cluster or a standalone RDS DB instance (issue [#5184](https://github.com/go-to-k/cdkd/issues/5184))** -- `src/provisioning/providers/deletion-protection-compensation.ts` (`deleteAfterProtectionFlipWithFinalSnapshot`), `rds-provider.ts`, `docdb-provider.ts`, `neptune-provider.ts`, `tests/unit/provisioning/providers/deletion-protection-compensation.test.ts`. Before this change, the wait added by [#5155](https://github.com/go-to-k/cdkd/issues/5155) could end on its first read. After `DeletionProtection` was turned off, AWS could keep reading the resource `available`, then move it to `modifying` and refuse the delete ("Can't create a snapshot because the database cluster ... isn't currently in the available state"). The destroy failed and the guard was put back. Now a delete AWS refuses that way is retried once the resource reads `available` again, within the same 15-minute cap and resource timeout. Both before the delete and between retries, cdkd waits through any status that is neither `available` nor terminal (`modifying`, `configuring-enhanced-monitoring`, `backing-up`, ...). A terminal status (`stopped`, `failed`, `inaccessible-*`, ...) is not waited on, and neither is `storage-optimization` or `storage-initialization`, which AWS documents as still available. Any other refusal still fails at once, so a cluster that still has members is not retried. A read of protection off and `available` before any such status has shown is held for up to 30 seconds from the first read showing protection off. As before, all of this runs only when this destroy turned the guard off and a final snapshot is requested.
