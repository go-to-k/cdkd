- **`AWS::CloudFormation::WaitCondition` is supported, and a `WaitConditionHandle`'s `Ref` is a real signal URL (issue [#6694](https://github.com/go-to-k/cdkd/issues/6694))** -- `src/provisioning/wait-condition-signal-store.ts` (new), `src/provisioning/providers/wait-condition-provider.ts` (new), `src/provisioning/providers/wait-condition-handle-provider.ts`, `src/provisioning/secret-physical-id.ts`, `src/provisioning/register-providers.ts`, `src/provisioning/provider-registry.ts`, `src/state/state-prefix.ts`. A handle's `Ref` was a placeholder that is not a URL, so EC2 user data that signalled it with `cfn-signal` / `curl` failed (and stopped a `set -e` script) while the deploy succeeded, and a `WaitCondition` was refused as unsupported. A handle is now a seven-day pre-signed PUT URL for one key under `wait-condition-signals/` in the state bucket; every PUT is its own object version, so a `WaitCondition` waits for `Count` distinct `SUCCESS` signals, fails on a `FAILURE` or after `Timeout`, and records `Data` as CloudFormation does. Destroying the handle deletes its signals. The URL's signature is masked wherever the physical id is displayed. A handle recorded by an earlier release keeps its placeholder; a wait condition on it is refused until the handle gets a new logical id.
