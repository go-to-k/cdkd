- **`cdkd import --migrate-from-cloudformation` records the resource CloudFormation holds after the Retain update, not one it replaced (issue [#4873](https://github.com/go-to-k/cdkd/issues/4873))** -- `src/cli/commands/import.ts`, `src/cli/commands/retire-cfn-stack.ts`. The command wrote cdkd state from the physical ids it read before the `UpdateStack` that adds the Retain policies. When that update replaced a resource (an auto-named `AWS::SSM::Document` is a known case), state named the superseded copy, and `cdkd destroy` left the live replacement unmanaged. The Retain update now runs before the state write; when it completes, cdkd re-reads the ids (nested stacks included), adopts every resource by the new ids, and warns with both ids; the superseded copy is kept by `UpdateReplacePolicy: Retain` for you to delete. A failed update or re-read leaves no state from the run, and its error names the manual route (Retain update by hand, `cdkd import` without the flag, then `DeleteStack`) and says a replacement CloudFormation cannot perform fails by hand too. When the update may have completed, the error also says how to find retained copies in the stack events. A failed `DeleteStack` says the state is written and every resource is retained, and to delete the stack by hand once its cause is resolved. After a replacement, `--record-resource-mapping` is rewritten so it no longer names a superseded id. A resource replaced at any nesting depth that can no longer be imported by its new id refuses before `DeleteStack` rather than orphan it. A re-import that adopts a different number of resources than were confirmed warns with both counts. Declining the retirement prompt still writes the confirmed state and leaves the stack unchanged; that prompt and its non-interactive refusal now say nothing was written yet. Integ: `migrate-from-cfn` now fails when the replacement Document survives the destroy.
