- **FSx Windows file system changes that CloudFormation replaces on are now planned as replacements, behind `--force-stateful-recreation` (issue [#7083](https://github.com/go-to-k/cdkd/issues/7083))** -- `src/analyzer/replacement-rules/evidence-fsx.ts`, `src/analyzer/replacement-rules/spec-replacement-properties.generated.ts`. CloudFormation was measured replacing the file system on a change of any of these `WindowsConfiguration` members: `ActiveDirectoryId`, `CopyTagsToBackups`, `DeploymentType`, `PreferredSubnetId`, and the self-managed directory's `DomainName`, `FileSystemAdministratorsGroup` and `OrganizationalUnitDistinguishedName`. Before this, cdkd's diff planned each change as an in-place update. For the first four, the FSx provider then refused the update. For the three self-managed directory members, the update went to `UpdateFileSystem` in place, where CloudFormation replaces the file system. A file system is stateful, so the deploy now refuses all seven changes before any call unless `--force-stateful-recreation` is passed, and `cdkd diff` shows the replacement. For the three self-managed directory members, a deploy that used to succeed in place is now refused, as CloudFormation would replace the file system. Also recorded with CloudFormation measurements: a Batch compute environment replaces on an `EksConfiguration` change, which the schema already planned. EMR Serverless `ImageConfiguration` / `WorkerTypeSpecifications` changes and KafkaConnect connector `ConnectorConfiguration` / `Plugins` / `WorkerConfiguration` changes stay in place. Every spec-replacement candidate has now been measured. The 13 left in the baseline are ones that neither verdict describes, each with a note.
