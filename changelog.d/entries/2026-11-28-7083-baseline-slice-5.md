- **FSx Windows file system and Batch EKS compute environment changes that CloudFormation replaces on are now planned as replacements (issue [#7083](https://github.com/go-to-k/cdkd/issues/7083))** -- `src/analyzer/replacement-rules/evidence-fsx.ts`, `src/analyzer/replacement-rules/evidence.ts`, `src/analyzer/replacement-rules/spec-replacement-properties.generated.ts`. The FSx rows are Windows `ActiveDirectoryId`, `CopyTagsToBackups`, `DeploymentType`, `PreferredSubnetId`, and the self-managed directory's `DomainName`, `FileSystemAdministratorsGroup` and `OrganizationalUnitDistinguishedName`. Before this, cdkd's diff planned each as an in-place update, which the FSx provider then refused. CloudFormation was measured replacing the file system on each change. A file system is stateful, so the deploy refuses the replacement before any call unless `--force-stateful-recreation` is passed, and `cdkd diff` shows it. A Batch compute environment's `EksConfiguration` change (another cluster or namespace) is now a replacement too, as CloudFormation was measured doing (a new compute environment ARN). EMR Serverless `ImageConfiguration` / `WorkerTypeSpecifications` and KafkaConnect connector `ConnectorConfiguration` / `Plugins` / `WorkerConfiguration` changes stay in place, as measured. Every unmeasured spec-replacement candidate now has a measured verdict.
