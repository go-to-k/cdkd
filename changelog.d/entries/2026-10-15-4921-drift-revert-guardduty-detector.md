- **`cdkd drift --revert` can now revert drift on an `AWS::GuardDuty::Detector` (issue [#4921](https://github.com/go-to-k/cdkd/issues/4921))** -- `src/provisioning/guardduty-detector-patch.ts`, `src/provisioning/cloud-control-provider.ts`, unit cases and a new phase in the `guardduty-detector-update` integ fixture. The revert hands Cloud Control the AWS snapshot with the drifted keys overlaid, and that snapshot carried both `DataSources` and the full `Features` list on every read measured, which `UpdateDetector` refuses together, so a revert failed, for a drifted scalar or a drifted feature alike, with `EKS_RUNTIME_MONITORING and RUNTIME_MONITORING cannot be provided in the same request`. Now, on a revert, each of the two keys the patch has no op on (an undrifted one) is removed from the request instead of being sent as read back; GuardDuty leaves an omitted setting as it is. A drifted `Features` list, which the revert takes from a read-back baseline too, is narrowed to the entries whose value differs from the live entry of the same `Name`, so a toggled feature is reverted without resending the rest; when no entry differs, `Features` is left out too, and when an entry has no `Name`, the live list is unreadable or the op carries no list, the op is sent as before. Beside a `Features` list that is still sent, a drifted `DataSources` (GuardDuty's legacy view of the features that have one, such as S3 and EKS audit logs) is left out. Still refused: a drift that switched the runtime monitoring mode, since reverting it changes both runtime features.
