- **`cdkd drift --revert` can now revert drift on an `AWS::GuardDuty::Detector` (issue [#4921](https://github.com/go-to-k/cdkd/issues/4921))** -- `src/provisioning/guardduty-detector-patch.ts`, `src/provisioning/cloud-control-provider.ts`, unit cases and a new phase in the `guardduty-detector-update` integ fixture. The revert hands Cloud Control the AWS snapshot with the drifted keys overlaid. That snapshot carried both `DataSources` and the full `Features` list on every read measured, which `UpdateDetector` refuses together, so reverting a drifted scalar or feature failed with `EKS_RUNTIME_MONITORING and RUNTIME_MONITORING cannot be provided in the same request`. Now an undrifted `Features` or `DataSources` (one the patch has no op on) is removed from the request instead of sent as read back, unless the live read lacks it; GuardDuty leaves an omitted setting as it is. A drifted `Features` list is narrowed to the entries that differ from the live entry of the same `Name`, so a toggled feature is reverted alone, and a drifted `DataSources` beside it (GuardDuty's legacy view of features such as S3 and EKS audit logs) is left out. When no entry differs, the drift is only in entry order or in entries GuardDuty added, which `UpdateDetector` cannot undo: the revert fails with an error saying so, rather than reporting a revert that changed nothing, and warns that `cdkd drift --accept` records every drifted property of the stack, so other drift on the detector should be reverted first. A desired entry without a string `Name`, an unreadable live list or an op without a list keeps the op as it was. Still refused: a drift that switched the runtime monitoring mode, since reverting it changes both runtime features.
