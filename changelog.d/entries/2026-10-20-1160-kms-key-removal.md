- **`AWS::KMS::Key`: a removed `RotationPeriodInDays` or `KeyPolicy` is reset, as CloudFormation does (issue [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/kms-provider.ts`. A CloudFormation A/B showed that a Key update resets a removed `RotationPeriodInDays` to 365 and a removed `KeyPolicy` to the KMS default key policy (`Id: key-default-1`, `kms:*` for the account root), alone and beside another change. cdkd sent nothing for either, so the old period and policy stayed. It now re-sends the period with `EnableKeyRotation` whenever it changes while rotation stays on (a period change was dropped too), and puts the default policy, named from the key ARN's partition and account. `cdkd drift --revert` still never puts a policy it did not read. The update follows CloudFormation's order: `EnableKey`, the rotation calls, `DisableKey`, then tags and the key policy, so a policy denying `kms:DisableKey` deploys. A rotation change on a key that stays disabled fails, as it does in CloudFormation, and the error now says to enable the key first (declare `Enabled: true`, or enable it in AWS) or drop the rotation change. A string `'false'` for `Enabled` or `EnableKeyRotation` (a String parameter's Ref) now reads as false on create and update, as in CloudFormation; it used to turn rotation on and leave the key enabled. The existing resets of a removed `Description`, `Enabled` and `EnableKeyRotation` already matched CloudFormation. Tests: `tests/unit/provisioning/kms-provider-removal-1160.test.ts`; the `kms-encryption` integ fixture gains a `verify.sh` with a removal phase.
