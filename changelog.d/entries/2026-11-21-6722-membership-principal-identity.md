- **An instance profile's `Roles`, an `AWS::IAM::UserToGroupAddition` and an `AWS::IAM::User`'s `Groups` no longer add or remove a same-named role, group or user someone else made (issue [#6722](https://github.com/go-to-k/cdkd/issues/6722), part of [#6655](https://github.com/go-to-k/cdkd/issues/6655))**. `AddRoleToInstanceProfile` / `RemoveRoleFromInstanceProfile` and `AddUserToGroup` / `RemoveUserFromGroup` name the principals, so one re-created out of band under a recorded name joined cdkd's profile or group, or was removed from it. Each principal of the stack with a recorded `RoleId` / `GroupId` / `UserId` (for a `UserToGroupAddition`, the group and every user) is now read and compared before the first write: another id refuses an add non-retryably with nothing written, and a removal is skipped with a warning on an update and refuses a `UserToGroupAddition` delete with the record kept. Each refusal names logical ids and the attribute, never a value. An instance profile's delete reads no role: it removes the roles its own profile holds right before deleting it. A principal this deploy created or replaced, one already matched in the same run, one outside the stack and a record without a usable id read nothing, as before. Principal names now match the stack's records ignoring case, as IAM does, so `Roles: ['My-Role']` is compared against a role recorded as `my-role` (inline and managed policy attaches too), and a denied principal read on an inline or managed policy says to allow the permission (an IAM policy, permission boundary, SCP or VPC endpoint policy may deny it) rather than to grant it.
