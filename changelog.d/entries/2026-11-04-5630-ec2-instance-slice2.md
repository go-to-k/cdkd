- **`AWS::EC2::Instance` with `PrivateDnsNameOptions` / `Ipv6AddressCount` / `Ipv6Addresses` / `AdditionalInfo` now deploys on the SDK path (issue [#5630](https://github.com/go-to-k/cdkd/issues/5630))** -- `src/provisioning/providers/ec2-provider.ts`, the `AWS::EC2::Instance` replacement rule, the in-place reader promotion in `src/analyzer/diff-calculator.ts`, the regenerated coverage map, unit tests and the `ec2-instance` integ fixture. Before this change, a template that set any of these properties sent the whole instance through Cloud Control, which is slower and sticky. All four are now sent on `RunInstances`. These update behaviors follow what CloudFormation did on a measured throwaway stack. Adding `PrivateDnsNameOptions` or changing one of its members keeps the instance: the DNS record flags change in place, and a `HostnameType` change stops and starts the instance (sharing the stop with an `InstanceType` / `UserData` change); an instance-store-backed instance, which cannot be stopped, is refused (not measured against CloudFormation). Removing the whole block replaces the instance. Removing one member is refused before any AWS call, since CloudFormation fails that update. A resource reading `Fn::GetAtt Instance.PrivateDnsName` is updated when the hostname changes. `Ipv6AddressCount` and `Ipv6Addresses` are create-only, so a change replaces the instance. `AdditionalInfo` is reserved by EC2, which refuses it at launch as it fails a CloudFormation stack; changing it later sends nothing, as in CloudFormation. A malformed value is refused before any AWS call. `cdkd drift` reads back `PrivateDnsNameOptions`; the other three are write-only launch inputs, so drift does not check them. Resources already recorded as Cloud Control-provisioned stay on Cloud Control. `KernelId` and `RamdiskId` (paravirtual AMIs only) and the other `AWS::EC2::Instance` properties listed on #5630 still route through Cloud Control.
