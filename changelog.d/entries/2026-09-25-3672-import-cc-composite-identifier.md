- **`cdkd import` adopts Cloud-Control-routed types whose identifier is composite, such as `AWS::EC2::VPCCidrBlock` (issue [#3672](https://github.com/go-to-k/cdkd/issues/3672))** -- `src/provisioning/cc-import-identifier.ts` (new), `CloudControlProvider.import()`, `tests/unit/provisioning/cc-import-identifier.test.ts`, and the `tests/integration/import-migrate-vpc/` fixture, which gains an IPv6 CIDR block. Cloud Control identifies such a resource by its primary-identifier values joined with `|`, while CloudFormation's physical id is often one of them: a VPCCidrBlock is the bare `vpc-cidr-assoc-…` id, not `<Id>|<VpcId>`. `--migrate-from-cloudformation` passed CloudFormation's id to `GetResource` unchanged, so the lookup failed and the import did not adopt the resource. The provider now reads the type's `primaryIdentifier` from the registry schema. It fills every other field from the template's literal values, after `Ref` substitution, and records the completed identifier. When the template cannot supply exactly the other fields, the import fails for that resource and names the composite `--resource` value to pass. A full-arity id, a single-field type, or an unreadable schema is passed through unchanged.
