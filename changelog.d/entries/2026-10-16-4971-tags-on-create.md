- **An `AWS::IAM::Role`, `AWS::SSM::Parameter`, `AWS::Kinesis::Stream` and the EC2 `VPC`, `Subnet`, `InternetGateway`, `EIP`, `NatGateway`, `RouteTable`, `SecurityGroup`, `Instance` and `NetworkAcl` now send their tags on the create call itself (issue [#4971](https://github.com/go-to-k/cdkd/issues/4971))** -- `src/provisioning/providers/{iam-role-provider,ssm-parameter-provider,kinesis-provider,ec2-provider}.ts`. cdkd created these resources untagged and tagged them afterwards (`TagRole`, `AddTagsToResource`, `AddTagsToStream`, `CreateTags`), so an organization SCP requiring a tag on the create action (`aws:RequestTag/...`) denied the create, where `cdk deploy` succeeds. The tags now go in `CreateRole.Tags`, `PutParameter.Tags`, `CreateStream.Tags` and each EC2 create's `TagSpecifications`, and the follow-up tagging call is gone: a tagged create makes one AWS call fewer. A tagged create needs the tagging permission the follow-up call already needed (`iam:TagRole`, `ssm:AddTagsToResource`, `kinesis:AddTagsToStream`, `ec2:CreateTags`). The old EC2 path only warned when `CreateTags` failed, so a role without `ec2:CreateTags` could still create: such a role's tagged create is re-sent once untagged and then tagged with `CreateTags` as before. Updates still tag with the separate calls (SSM refuses `Tags` with `Overwrite`). An EC2 tag the create call refuses now fails the create instead of warning. A possible orphan of a lost EC2 create response is now matched by carrying no tags or exactly the template's tags, and the deploy's post-create EC2 read re-reads a not-found answer briefly before dropping the drift baseline.
