- **An S3 bucket that exists after a server error on its own `CreateBucket` is refused, not adopted (issue [#4639](https://github.com/go-to-k/cdkd/issues/4639), S3 bucket residual)** -- `src/provisioning/providers/s3-bucket-provider.ts`. `CreateBucket` carries no idempotency token. When a 5xx hid a create S3 had completed, the replay answered `BucketAlreadyOwnedByYou` (or 200 in us-east-1) and the provider adopted the bucket as one that was already there: no created-before-failure mark, so a later configuration failure in the same create left a bucket this run made in no state record and out of `cdkd rollback --revert-failed`'s reach. `CreateBucket` now goes through a dedicated client that refuses the SDK's 5xx retry (same region and identity as the provider's other calls), and when an earlier attempt of the SAME create ended ambiguous and the bucket now exists in this region, the create fails with a non-retryable refusal naming the bucket. It leads with `aws s3api list-buckets --prefix` (only this account's buckets; `CreationDate` is a hint) and `list-object-versions`, then a `delete-bucket` command only for an empty bucket of this account that nobody else uses, or a re-run to adopt a bucket you mean the stack to own. In us-east-1 the refusal comes from the pre-flight, before any re-create (also when the pre-flight could not read the bucket, where a re-create could make an unattributed bucket). An attempt interrupted by a non-ambiguous retryable failure (an `OperationAborted`, a `SlowDown`, a throttled location read) keeps the earlier attempt's window for the next one. Nothing is configured or deleted. A bucket that existed before any ambiguous attempt is still adopted as before (tracked in [#4684](https://github.com/go-to-k/cdkd/issues/4684)). Tests: `tests/unit/provisioning/s3-bucket-create-retry-4639.test.ts`.
