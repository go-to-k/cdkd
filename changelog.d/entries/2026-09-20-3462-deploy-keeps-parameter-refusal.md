- **A `cdkd deploy` after `cdkd import` no longer records a decrypted secret as a drift baseline for a resource whose parameter was deployed over a placeholder `Default`, and neither does a re-import (issue [#3462](https://github.com/go-to-k/cdkd/issues/3462))** -- `deploy-engine.ts`, `import.ts`, `types/state.ts`, `docs/import.md`, `docs/state-management.md`, a redeploy arm on the `import-deployed-parameter-secret` integ. `cdkd import` refuses the observed baseline of a resource that depends on a template parameter it cannot prove was deployed at its `Default` (#2854), and an UPDATE used to clear every such refusal. But `cdkd deploy` binds the same `Default`, so an update that leaves the parameter-bound property alone (a code-only Lambda change) left the deployed value in AWS, dropped the marker, and wrote the readback -- the decrypted secret -- to `observedProperties`. The import now records WHY it refused, in a new optional `observedBaselineRefusalReason: "unverifiable-parameter"` beside `observedBaselineRefused` (no schema version bump; absent on every older record, where an UPDATE clears the marker as before). For that reason an in-place UPDATE keeps both fields and reads nothing back from AWS, whatever it changed; a replacement (`wasReplaced` AND a changed physical id) or a fresh CREATE clears them. The same hole one command over is closed too: re-running `cdkd import` once the CloudFormation stack is gone had nothing to compare against, rebuilt the record without the marker and captured the secret; it now carries the refusal across a re-import on an unchanged physical id, and clears it only when that run had deployed parameter values and they proved the `Default`. Cost: such a resource has no observed baseline for the life of the physical resource. Not covered: a stack imported with 0.290.35, the one version that wrote the refusal without the reason (#3468); a binary older than the field ignores it.
