- **`Ref` on four types now returns the value CloudFormation returns (issue [#6243](https://github.com/go-to-k/cdkd/issues/6243))** -- `src/deployment/intrinsic-resolver/ref-values.ts` (split into `ref-values/type-refs.ts`), `refs.ts`, the `cdkd orphan` rewriter, unit tests and a new `ref-shape-vector-namespace-attachment` integ fixture. `AWS::S3Vectors::VectorBucket` and `AWS::AppSync::GraphQLApi` resolved to the bucket name / API id instead of the ARN, `AWS::S3Tables::Namespace` to the bare namespace name instead of `<tableBucketARN>|<namespace>`, and `AWS::EC2::VPCGatewayAttachment` to `<gatewayId>|<vpcId>` instead of `IGW|<vpcId>` / `VGW|<vpcId>`, each with no warning. A template wiring one of these `Ref`s into an IAM policy, an output or a sibling property got a value CloudFormation never returns. Each value was measured against a real CloudFormation deploy of the same template. A GraphQL API or vector bucket that `cdkd import` adopted before it recorded the ARN has its ARN read from AWS at the next deploy, and the `Ref` is refused if none can be read. A template that relied on the old values -- for example `VectorBucketName: !Ref Bucket`, `ApiId: !Ref Api` or a table's `Namespace: !Ref Namespace`, none of which CloudFormation accepts -- now receives the CloudFormation value, so its next deploy sees a changed property and may replace the resource or fail.
