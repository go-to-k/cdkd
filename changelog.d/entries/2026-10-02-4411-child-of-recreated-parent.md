- **A resource stored inside a parent the deploy destroys and re-creates under the same physical id is now re-created with it (issue [#4411](https://github.com/go-to-k/cdkd/issues/4411))** -- `src/deployment/child-of-recreated-parent.ts`, `src/deployment/deploy-engine/update.ts`, `src/deployment/deploy-engine/update-replace.ts`, `src/deployment/deploy-engine.ts`. Recreating a fixed-name Lambda function (`--recreate-via-cc-api` / `--recreate-via-sdk-provider`, or a delete-first `--replace`) deletes its resource-based policy with it, but the `AWS::Lambda::Permission` reading the function resolved exactly as recorded, so the deploy skipped it as unchanged: after a green deploy the new function had no permission while state still recorded one, and its trigger stopped invoking it. The engine now records each resource it destroyed and re-created under the same id, and a child of one -- a Lambda `Permission`, `Version`, `Alias` or `EventInvokeConfig`, an SNS `Subscription`, `TopicPolicy` or `TopicInlinePolicy`, an SQS `QueuePolicy` or `QueueInlinePolicy`, an S3 `BucketPolicy`, a Logs `LogStream`, `MetricFilter` or `SubscriptionFilter`, an IAM `RolePolicy` or role-attached `Policy` -- is created again without deleting the old one, which went with its parent (a delete would remove the fresh statement, since a permission's id is its statement id); a permission on an alias of the function is covered too, and a policy naming several parents (topic, queue, multi-role IAM policy) is written again in place. `src/analyzer/diff-calculator.ts` marks such a child as replaced whatever the schema lookup answers, so its own readers are promoted. Residuals: go-to-k/cdkd#4443, go-to-k/cdkd#4444. Tests: `tests/unit/deployment/child-of-recreated-parent.test.ts`, `tests/unit/deployment/deploy-engine-child-of-recreated-parent.test.ts`.
