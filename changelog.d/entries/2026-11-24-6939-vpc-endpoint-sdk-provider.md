- **`AWS::EC2::VPCEndpoint` has an SDK provider, so `cdkd deploy --no-wait` returns once `CreateVpcEndpoint` answers instead of waiting 30-50 s for an Interface endpoint to become `available` (issue [#6939](https://github.com/go-to-k/cdkd/issues/6939))** -- `src/provisioning/providers/ec2-vpc-endpoint-provider.ts`, `src/provisioning/providers/ec2-vpc-endpoint/shape.ts`, `src/provisioning/vpc-endpoint-dns-entries.ts`, `src/deployment/intrinsic-resolver/getatt-construct-core.ts`, `src/analyzer/diff-calculator/shared.ts`, `src/provisioning/delete-blocker-inventory.ts`, `tests/unit/provisioning/ec2-vpc-endpoint-provider.test.ts`, `tests/integration/ec2-vpc-endpoint/`. The type went through Cloud Control, whose handler returns only once the endpoint is `available`. An ordinary deploy still waits for `available`, as CloudFormation does, and an endpoint that turns `failed`, `rejected`, `expired`, `partial` or deleting fails it. An update sends one `ModifyVpcEndpoint` for subnets, security groups, route tables, the policy (a removed policy is reset), private DNS (a removed value is CloudFormation's `false`), DNS options and IP address type, then waits again unless `--no-wait`. `DnsEntries` (`<hosted zone>:<name>`) and `NetworkInterfaceIds` come from the create's own answer; after a `--no-wait` modify a `Fn::GetAtt` of either reads the endpoint live and waits while it is `pending`. A resource reading either attribute is updated in the same deploy when the endpoint's subnets (or, for `DnsEntries`, its DNS settings) change, on either route. A delete waits until the endpoint is gone in every mode, since its network interfaces hold the subnets and security groups the destroy deletes next. An endpoint already recorded `provisionedBy: cc-api` stays on Cloud Control.
