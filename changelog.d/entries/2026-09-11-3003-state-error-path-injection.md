- **`cdkd state show` / `cdkd state resources` refusals can no longer forge a row with the record that caused them (issue [#3003](https://github.com/go-to-k/cdkd/issues/3003))** -- `src/utils/error-handler.ts`, `src/state/s3-state-backend.ts`, `src/state/lock-manager.ts`, `src/cli/commands/state.ts`, `src/cli/commands/export.ts`, `docs/cli-state.md`, cases in six suites. Issue [#2772](https://github.com/go-to-k/cdkd/issues/2772) made every value those views RENDER control-safe, because cdkd's output is line-oriented and a state record is an unchecked cast anyone with `s3:PutObject` on the state bucket can write. The ERROR paths were not, and a refusal is the path a malformed record is MOST likely to take -- so the diagnostic a reader trusts most could invent a row the rendered output no longer can. **The widest of them is `formatError`'s `Caused by:` line**, which printed the underlying error verbatim: every site below passes the original error as its `cause`, and a cause is routinely a `JSON.parse` `SyntaxError` -- which quotes the offending INPUT, so an unreadable `state.json` or `lock.json` put bucket bytes on the terminal one line BELOW an already-sanitized message. Measured: `state show` rendered four lines where two were owed, with a live ESC among them. Sanitized at that one print site, so every thrower inherits it. Ten refusal sites take the guard too, across `parseStateBody`, `getState`, `tryGetLegacy`, `getLockRecord` (its catch AND the has-no-body sibling a `LockError` rethrow skips), `resolveSingleRegion`, both commands' own refusals, and the nested-stack walker. Each command file routes them through ONE predicate rather than the expression per site, which is the shape the issue is about. Known-charset values take the ASCII allowlist; free-form text takes the denylist class. NOT closed: a value that throws on STRING COERCION still throws -- issue [#2947](https://github.com/go-to-k/cdkd/issues/2947)'s call.
