- **`cdkd state show` / `cdkd state resources` refusals can no longer forge a row with the record that caused them (issue [#3003](https://github.com/go-to-k/cdkd/issues/3003))** -- `src/utils/error-handler.ts`, `src/utils/logger.ts`, both `src/state/` backends, the `state` / `export` commands, `docs/cli-state.md`, cases in eight suites. Issue [#2772](https://github.com/go-to-k/cdkd/issues/2772) made every value those views RENDER control-safe: cdkd's output is line-oriented and a state record is an unchecked cast anyone with `s3:PutObject` can write. The ERROR paths were not, and a refusal is what a malformed record MOST likely triggers -- so the diagnostic a reader trusts most could invent a row the rendered output cannot. **The widest of them is `formatError`'s `Caused by:` line**, which printed the underlying error verbatim: every site below passes the original error as its `cause`, routinely a `JSON.parse` `SyntaxError`, which QUOTES the offending input -- so an unreadable `state.json` put bucket bytes on the terminal one line BELOW an already-sanitized message. Measured: `state show` rendered four lines where two were owed, one with a live ESC. Sanitized at that one site, so every thrower inherits it. The refusal sites take it too: `parseStateBody`, `getState`, `tryGetLegacy`, `getLockRecord` (its catch AND the has-no-body sibling a `LockError` rethrow skips), `resolveSingleRegion`, both commands' refusals, and the nested-stack walker. Each command file routes them through ONE predicate, not a per-site expression. Known-charset values take the ASCII allowlist, free-form text the denylist. The LOGGER's extra args take it too: `JSON.stringify` escapes C0, so no line could be forged, but `U+0085`, the C1 range xterm reads as CSI, and `U+2028` survive it -- and `getLockRecord` logs the parsed `lock.json` whole, of which two keys were safe. NOT closed: a value throwing on STRING COERCION still throws -- issue [#2947](https://github.com/go-to-k/cdkd/issues/2947).
