- **A `cdkd import` baseline REFUSAL is now carried on the state record, so no later writer refills it (issue [#2944](https://github.com/go-to-k/cdkd/issues/2944), state schema v9 -> v10)** -- `src/types/state.ts`, `src/cli/commands/{import,state,drift,export}.ts`, `src/deployment/deploy-engine.ts`, unit tests, `tests/integration/schema-v9-to-v10-migration/`. **Bug:** the observed-baseline refusal ((#2828) / (#2850)) left only `observedProperties: undefined` behind — ALSO what a pre-v3 record leaves — so the commands whose job is to FILL a missing baseline filled it against the record's `properties`, which after a refusal can hold the WRONG-BRANCH LITERAL the refusal distrusted. Such a literal pairs with a string readback as an ordinary drifted literal, so the redaction refuses nothing and the DECRYPTED value is persisted — the GHSA-p5qg-v9gv-hc7w direction re-opened by a later run. FIVE writers, three more than the issue named (this fix's sibling sweep plus review): the deploy auto-refresh and `cdkd state refresh-observed` persist the plaintext as a baseline, `cdkd drift --accept` persists it into `properties`, `cdkd drift --revert` pushes the placeholder to AWS OVER the live secret, and `cdkd import` itself refills a record a SELECTIVE MERGE preserved. **Fix:** `ResourceState.observedBaselineRefused?: true` (schema v10). `cdkd import` sets it on a refusal and clears it on a capture that succeeds FOR A ROW IT RE-IMPORTED; all five writers skip a marked record. **Clearing it:** deploy a CHANGE to the resource — the record rebuild drops the flag. A NO_CHANGE deploy does not, nor does re-running `refresh-observed`. **Visibility:** `cdkd state show` renders an `ObservedBaseline: REFUSED` line. **Migration is transparent** — absent means "not refused", the pre-fix behaviour of every writer. An OLDER binary refuses a v10 blob: the point, not a side effect, since one ignoring the flag would refill the baseline — at the cost of hard-failing on any stack a v10 binary wrote.
