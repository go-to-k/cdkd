- **`cdkd deploy --no-wait` now waits for a skipped-wait resource when the deploy itself needs it (issue [#6940](https://github.com/go-to-k/cdkd/issues/6940))** -- `src/provisioning/deferred-readiness.ts`, `src/deployment/deferred-readiness-run.ts`, `src/deployment/deploy-engine/execute/provision-node.ts`, `src/deployment/intrinsic-resolver/getatt-heal.ts`, `src/analyzer/dag-builder.ts`, `src/provisioning/providers/custom-resource/invoke-retry.ts`, the skipped-wait providers, `docs/cli-deploy-waits.md`, `docs/cli-deploy-tuning.md`, `src/cli/options.ts`. A provider that skips a readiness wait hands it to the deploy with `deferReadiness()`. The deploy runs it once per resource, shared by every need and bounded by the type's `--resource-timeout`. A `Fn::GetAtt` of a value that exists only once the resource is ready waits and reads the resource again; an RDS, DocumentDB, Neptune or ElastiCache endpoint used to be refused at once. A custom resource waits, before its handler is invoked, for every such resource upstream of it through `DependsOn`, `Ref` or `Fn::GetAtt`, a nested stack's for those upstream of its parent row too. In every mode a CDK-defensive `DependsOn` from a function upstream of a custom resource or nested stack onto a VPC route is no longer relaxed by `--aggressive-vpc-parallel`, so the handler runs after the route through its NAT gateway; other functions still relax. An Elastic IP's association with an instance the deploy did not wait for now waits instead of being skipped. A resource that only depends on one does not wait. A resource that ends failed fails the deploy, as in the default mode. Tests: `tests/unit/deployment/*6940*.test.ts`, `tests/unit/provisioning/*6940*.test.ts`, `custom-resource-provider-referenced-lambda-active-wait.test.ts`.
