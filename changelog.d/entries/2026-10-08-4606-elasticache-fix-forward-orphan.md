- **A successful fix-forward deploy now deletes the ElastiCache cache cluster an earlier failed CREATE left under the same logical id, once live reads prove it is not the new one and is still the one that failed CREATE made (issues [#4606](https://github.com/go-to-k/cdkd/issues/4606), [#4655](https://github.com/go-to-k/cdkd/issues/4655))** -- `src/provisioning/providers/elasticache-provider.ts`. After `cdkd deploy --no-rollback` failed with an `AWS::ElastiCache::CacheCluster` already created, and the fixed template created a new one under the same logical id with another cluster id, the successful deploy warned, named the earlier cluster, exited `2` and left it in AWS. `ElastiCacheProvider` now implements `isSameResource` and `resourceIdentity`. A cache cluster has no immutable AWS-generated id, so its identity is its ARN plus its `CacheClusterCreateTime`; cluster ids equal apart from case are the same cluster, since ElastiCache ids are case-insensitive. The failed CREATE carries the first identity its create call or an available-wait poll answered with, so a later poll that fails does not cost the orphan its identity. A cluster whose failed CREATE never saw its creation time (AWS may omit it while the cluster is being created) is kept with a warning, as is one re-created under the id, which reads back with another creation time, and one whose template-set `ClusterName` is not all lower case (cdkd records it as written, while AWS and `cdkd import` use the lower-cased id). Only the not-found fault name counts as gone. Deleting an earlier cluster that is already gone prints one info line. Tests: `tests/unit/provisioning/elasticache-same-resource-4606.test.ts`; new integ `elasticache-fix-forward-orphan`.
