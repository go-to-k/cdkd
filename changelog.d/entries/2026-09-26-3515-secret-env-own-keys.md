- **A secret named `__proto__` reaches the local container through the spawn env (issue [#3515](https://github.com/go-to-k/cdkd/issues/3515))** -- `src/utils/docker-cmd.ts` (`partitionSensitiveEnv`, `dockerSpawnEnvWithSensitive`), `src/local/ecs-task-runner.ts`, `src/local/ecs-secrets-resolver.ts`.
  - `cdkd local run-task` handed each resolved secret to `docker run` by assigning it onto a plain object. For a secret NAMED `__proto__`, that ran `Object.prototype`'s setter, so its value vanished while the value-less `-e __proto__` flag stayed on the argv, and docker resolved it against the client's own environment. The three writes (the runner's secrets merge, and `partitionSensitiveEnv` / `dockerSpawnEnvWithSensitive` in the helper `cdkd local invoke` shares) are own-key defines now. The value still travels only through the spawn env, never the argv, which a test pins. `cdkd local invoke` cannot carry such a name yet, because cdk-local's env resolution drops it first.
  - A Secrets Manager `json-key` named after a prototype member the secret does not carry (e.g. `constructor`) resolved to an empty value, which again left docker to fill it from the client env. It now fails with the named "no such key" refusal.
