- **A stack's tags (`StackProps.tags`) are now applied to its resources, as CloudFormation applies the stack tags `cdk deploy` passes it (issue [#6871](https://github.com/go-to-k/cdkd/issues/6871))** -- `src/provisioning/stack-tags.ts`, `src/provisioning/stack-tag-targets.ts`, `src/deployment/nested-stack-tags.ts`, `tests/unit/provisioning/stack-tags-6871.test.ts`, `tests/unit/deployment/deploy-engine-stack-tags-6871.test.ts`, `tests/unit/cli/diff-stack-tags-6871.test.ts`, `tests/integration/tags-propagation/`. The AWS CDK puts `StackProps.tags` only in the cloud assembly manifest, so cdkd deployed every resource without them. They are now merged into each taggable resource before the diff, in the shape and under the property its registry schema names; a tag the resource declares itself keeps its own value, an Auto Scaling group gets `PropagateAtLaunch: true`, and types whose schema says `taggable: false` or `tagUpdatable: false` get none. **The next deploy of a stack with stack tags updates its resources in place to add them**, and each nested stack of a stack with tags is updated once so its resources get them too (the parent's tags plus the nested stack resource's own `Tags`). `cdkd diff` shows the same changes, and `cdkd drift` compares the tags. The stack record gains `nestedStackTags` (state schema: additive, no version bump), which tells a later deploy when a nested stack's tags changed. Tags added with `Tags.of(app)` or `Tags.of(stack)` are stack tags too; CDK already writes them into each resource, so for them the change is mostly the one-time nested-stack update. A stack without tags makes no extra call.
