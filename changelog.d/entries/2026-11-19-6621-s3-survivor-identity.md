- **A rollback no longer re-adopts someone else's bucket under a replaced S3 bucket's old name, nor deletes the stack's new bucket for it (issue [#6621](https://github.com/go-to-k/cdkd/issues/6621))** -- `src/deployment/rollback-executor/replaced-survivor.ts`, `src/provisioning/providers/s3-bucket/survivor-identity.ts`, `src/deployment/deploy-engine/replacement/delete-replaced.ts`. A failed deploy that renamed a bucket leaves the old one in place, its delete deferred, and the rollback re-adopted whatever answered the old name and deleted the new bucket. S3 names are global, so if the old bucket had been deleted out of band and another party took the name, the rollback made that bucket the stack's. Now the deploy journals the old bucket's creation date when it defers the delete (`oldResourceIdentity`), and the rollback reads who holds the name before it replays any op. A bucket not in this account's `ListBuckets`, or in another region, is refused. In us-east-1 a different creation date means the bucket was re-created, so it is refused. Elsewhere a configuration write also moves that date, so a different date is refused with its own message saying the bucket may have been re-created or modified. A journal written before this change still re-adopts this account's bucket. Every refusal sends nothing, keeps the journal, and offers `--orphan`.
