- **An `AWS::IAM::Policy` that cdkd just wrote no longer leaves a drift baseline that `cdkd drift --revert` would undo when the write is not yet visible (issue [#6609](https://github.com/go-to-k/cdkd/issues/6609))** -- `src/provisioning/providers/iam-policy/read-state.ts`, `src/provisioning/providers/iam-policy-provider.ts`, `src/provisioning/providers/iam-policy/differing-copies.ts`, `src/cli/commands/drift/baseline-keys.ts`, unit tests. The deploy recorded the first `Get{Role,User,Group}Policy` answer after the write as the `observedProperties` baseline, so a copy still showing the replaced document was frozen in (a copy not visible yet left the policy with no baseline). The capture after cdkd's own write now re-reads the copy it reads (the first principal's) when its first answer is not the declared document (up to 3 more reads, 3.5 seconds at most, only when the first answer differs; a deterministic read failure such as `AccessDenied` is not re-read). If the copy is still absent after that, the declared document is recorded and the principal stays in its `Roles` / `Groups` / `Users` list; another document is recorded as read. Either way a warning names the resource and points at `cdkd state refresh-observed`. Drift, import and `state refresh-observed` still take the first answer and read every principal's copy. A baseline an earlier cdkd already froze this way is healed at drift time: `PolicyDocument` is not compared while every principal's copy is the declared document (copies that differ keep it compared), nor `PolicyName` / `Roles` / `Groups` / `Users` while the live value is exactly the declared one. An out-of-band change accepted with `drift --accept` and later undone outside cdkd, putting the policy back to the template, is not reported (CloudFormation would not report it either).
