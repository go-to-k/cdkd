- **A state record whose `orphans` list is not a list is no longer read as "no orphans", and `cdkd rollback` no longer rewrites it (issue [#3379](https://github.com/go-to-k/cdkd/issues/3379), PR #3481)** -- `malformed-resources-bag.ts`, `deploy-engine.ts`, `destroy-runner.ts`, `rollback.ts`, `diff-recursive.ts`, `scrub.ts`. `parseStateBody` validates the record root and the schema version only, so a hand-edited or truncated `"orphans": "abc"`, `5`, `{}` or `null` survived the load, and every reader reached it through `?? []`, `?.length` or `?.map`. Three outcomes followed: a string was WALKED one character at a time, and `orphansAfterRollback` returned a list of those characters that `cdkd rollback` then SAVED; a number or a plain object read as an empty list, so `cdkd diff` previewed no adoption and `cdkd destroy` deleted the record without ever reporting resources an earlier failed deploy had left live in AWS; the remaining shapes threw a bare `TypeError` naming nothing. **Behavior change:** a command that can write state now refuses such a record before it acts -- `cdkd deploy` before any resource operation, `cdkd destroy` at both its first read and its under-lock re-read, `cdkd rollback` before any replay, `cdkd scrub` on a real run -- with a non-retryable error naming the `orphans` container and the `cdkd state show ... --json` command to inspect it. Read-only paths continue instead: `cdkd diff` and `cdkd scrub --dry-run` treat the container as empty, warn, and list an `(orphans container)` row in the diff node's `unreadable` set, which `--fail` and `--json` both see. A well-formed record is unaffected, and a record with NO `orphans` key stays untouched -- that is the ordinary shape for a stack that never had a failed deploy, and no command materializes an empty list over it. Entry-level damage inside a readable list is unchanged (go-to-k/cdkd#3344).
