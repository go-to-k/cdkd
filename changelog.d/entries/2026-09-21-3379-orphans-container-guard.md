- **A state record whose `orphans` list is not a list is no longer read as "no orphans", and `cdkd rollback` no longer rewrites it (issue [#3379](https://github.com/go-to-k/cdkd/issues/3379), PR #3492)** -- `malformed-resources-bag.ts`, `deploy-engine.ts`, `destroy-runner.ts`, `rollback.ts`, `import.ts`, `diff-recursive.ts`, `scrub.ts`. `parseStateBody` validates the record root and the schema version only, so a hand-edited `"orphans": "abc"`, `5`, `{}` or `null` survived the load, and no reader asked `Array.isArray` before walking or counting it. Three outcomes followed: a string was WALKED one character at a time, and `orphansAfterRollback` returned a list of those characters that `cdkd rollback` then SAVED; shapes counting zero read as an empty list, so `cdkd diff` previewed no adoption and `cdkd destroy` deleted the record without reporting resources an earlier failed deploy had left live in AWS; the rest threw a bare `TypeError` naming nothing. **Behavior change:** a command that can write state now refuses such a record before it acts -- `cdkd deploy` before any resource operation, `cdkd destroy` at both its first read and its under-lock re-read, `cdkd rollback` before any replay, `cdkd import` before it carries the container into the record it writes, `cdkd scrub` on a real run -- with a non-retryable error naming the `orphans` container and how to inspect the record. The destroy carries its own text, naming `cdkd state orphan` as the way to drop a record deliberately. Read-only paths continue instead: `cdkd diff` and `cdkd scrub --dry-run` treat it as empty, warn, and list an `(orphans container)` row in the diff node's `unreadable` set, which `--fail` and `--json` see. A well-formed record is unaffected, and a record with NO `orphans` key stays untouched -- the ordinary shape for a stack that never had a failed deploy, over which no command materializes an empty list. Entry-level damage inside a readable list is unchanged (go-to-k/cdkd#3344).
