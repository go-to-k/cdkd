- **A state record whose `orphans` list is not a list is no longer read as "no orphans", and `cdkd rollback` no longer rewrites it (issue [#3379](https://github.com/go-to-k/cdkd/issues/3379), PR #3492)** -- `malformed-resources-bag.ts`, `deploy-engine.ts`, `destroy-runner.ts`, `rollback.ts`, `import.ts`, `diff-recursive.ts`, `scrub.ts`. `parseStateBody` validates only the record root and the schema version, so a hand-edited `"orphans": "abc"`, `5`, `{}` or `null` survived the load with no reader asking `Array.isArray` first. Three outcomes: a string was WALKED one character at a time and `orphansAfterRollback` returned a list of those characters, which `cdkd rollback` SAVED; shapes counting zero read as an empty list, so `cdkd diff` previewed no adoption and `cdkd destroy` deleted the record without reporting resources an earlier failed deploy left live in AWS; the rest threw a bare `TypeError` naming nothing. **Behavior change:** a command that READS this container on a path that can write state now refuses the record before it acts -- `cdkd deploy` before any resource operation, `cdkd destroy` at its first read and its under-lock re-read, `cdkd rollback` before any replay, `cdkd import` before it carries the container into the record it writes, `cdkd scrub` on a real run -- with a non-retryable error naming the container and how to inspect the record. `cdkd orphan` never reads it and still runs, carrying it verbatim; the destroy refusal names `cdkd state orphan` as the way to drop a record deliberately. Read-only paths continue: `cdkd diff` and `cdkd scrub --dry-run` treat it as empty, warn, and list an `(orphans container)` row in the diff's `unreadable` set, which `--fail` and `--json` see. A well-formed record is unaffected, and a record with NO `orphans` key stays untouched -- the ordinary shape for a stack that never had a failed deploy -- with no empty list materialized over it. Entry-level damage inside a readable list is unchanged (go-to-k/cdkd#3344).
