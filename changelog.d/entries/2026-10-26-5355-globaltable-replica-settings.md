- **`AWS::DynamoDB::GlobalTable` replicas now get their KMS key, table class and deletion protection (issue [#5355](https://github.com/go-to-k/cdkd/issues/5355))** -- `src/provisioning/providers/dynamodb-globaltable-provider.ts`, `src/provisioning/protection-flags.ts`. A replica's KMS key and table class were read as `Replicas[].KMSMasterKeyId` / `Replicas[].TableClassOverride`, names the CloudFormation schema does not have, so a `TableV2` with a customer managed key or a `tableClass` deployed every replica, the local table included, under the AWS managed key and the `STANDARD` class and reported success. They are now read from `Replicas[].SSESpecification.KMSMasterKeyId` and `Replicas[].TableClass`, on create and update; an update also checks the declared class and key ARN against AWS, so a table deployed before this fix is corrected on its next update. A cross-region replica's `DeletionProtectionEnabled`, never sent before, is now set on that replica's own table and checked against AWS on update; a value that is not a boolean is reported and left alone. `cdkd destroy --remove-protection` turns a protected replica's guard off before dropping it (and back on if the drop is refused), and the destroy prompt counts a protected replica. Removing `SSESpecification` now resets the table to the AWS owned key, removing a replica's `TableClass` resets it to `STANDARD` (both as CloudFormation does, measured). On a table with cross-region replicas a key change goes out as one `ReplicaUpdates` call naming every region's key, and a table-class or encryption change in an `UpdateTable` of its own, the only shapes DynamoDB accepts (measured). An `SSEEnabled` that is not a boolean is refused; a string `"false"` no longer enables encryption, and a string `"true"` for the local table's `DeletionProtectionEnabled` now protects it.
