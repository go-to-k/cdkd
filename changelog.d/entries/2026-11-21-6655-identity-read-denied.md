- **A Cloud Control, DynamoDB table or RDS DB instance / cluster delete whose identity read AWS denies stops with the missing permission named, instead of retrying (issue [#6655](https://github.com/go-to-k/cdkd/issues/6655))** -- `src/provisioning/identity-read-denied.ts`, `src/provisioning/cloud-control/delete-identity.ts`, `src/provisioning/providers/dynamodb-table/delete.ts`, `src/provisioning/providers/rds/{instance-delete,cluster-delete}.ts`. A record holding a recorded AWS-minted id makes one read before the delete (`GetResource`, `DescribeTable`, `DescribeDBInstances`, `DescribeDBClusters`). When AWS denied that read, the retry classifiers took AWS's `not authorized to perform` for IAM propagation and retried it, so a caller without the read permission (which the delete did not need before the compare was added) waited out the retries and then failed with AWS's text. It now refuses on the first answer, non-retryable, sends no delete and keeps the record, and names the permission (for Cloud Control, `cloudformation:GetResource` with the type's read handler permissions: both answer `AccessDeniedException`), then `cdkd state orphan --resource`, with no AWS text. The refusal now says to allow the permission and that an IAM policy, permission boundary, SCP or VPC endpoint policy may deny it, for the log group, Step Functions and ECR reads too. An expired token, bad signature or skewed clock is no longer called a missing permission when it answers 403 (RDS answers `SignatureDoesNotMatch` / `InvalidClientTokenId` with 403); it keeps the ordinary path. No new AWS call.
