- **`cdkd import` now records the `FunctionUrl` / `FunctionArn` attributes of an `AWS::Lambda::Url` (issue [#3624](https://github.com/go-to-k/cdkd/issues/3624))** -- `src/provisioning/providers/lambda-url-provider.ts`, `tests/unit/provisioning/lambda-url-provider.test.ts`, and the new `tests/integration/import-lambda-url-attributes/` fixture. `LambdaUrlProvider.import()` returned an empty attribute map, and neither attribute can be derived from the physical id. So after `cdkd import` (including `--migrate-from-cloudformation`), a sibling's `Fn::GetAtt [<Url>, FunctionUrl]`, such as a CloudFront `FunctionUrlOrigin`, was written to its record as the raw intrinsic, and every later `cdkd diff` / `cdkd deploy` warned `Unknown attribute FunctionArn`. `import()` now reads both attributes from `GetFunctionUrlConfig`, and returns not-found when no URL config exists. Importing a function URL now needs `lambda:GetFunctionUrlConfig`: without it, that resource's import fails and is reported, where before it was recorded without any AWS call. The deploy-time stale-attribute heal ([#1852](https://github.com/go-to-k/cdkd/issues/1852)) re-reads through the same method, so a record imported before this fix heals on the next `cdkd deploy`. Measured live: that deploy UPDATEs the dependent resource once with the resolved value, and the deploy after it reports no changes. `cdkd diff` does not preview that update ([#3456](https://github.com/go-to-k/cdkd/issues/3456)). Separately, an `update()` that changed nothing returned an empty attribute map, which replaced the recorded attributes. It now returns none, so the recorded values are kept.
