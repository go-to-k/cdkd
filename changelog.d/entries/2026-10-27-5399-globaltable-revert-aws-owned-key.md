- **`cdkd drift` now reports, and `drift --revert` now undoes, an out-of-band move to a KMS key on a GlobalTable recorded on the AWS owned key (issue [#5399](https://github.com/go-to-k/cdkd/issues/5399))** -- `src/types/resource.ts` (new optional provider hook `getDriftAbsentMeansDefaultKeys`), `src/cli/commands/drift.ts` (`withAbsentDefaultKeys`, `driftAbsentMeansDefaultKeys`, and the `absentMeansDefault` option of `buildRevertNewProperties`), `src/provisioning/providers/dynamodb-globaltable-provider.ts`, unit tests, and an arm in the `dynamodb-globaltable-replica-settings` integ. The read-back omits `SSESpecification` unless encryption is ENABLED, so a baseline captured on the AWS owned key has no such block, and the comparator walks only the baseline's top-level keys: the move showed only as a `Replicas` key change, and the revert kept the live block, so `update()` saw no encryption change and the table stayed on the customer managed key. A provider can now name top-level keys whose absence from an observed baseline records the default. Drift compares each one even when the baseline lacks it, and `--revert` sends it absent, so `update()` takes its removal path. For a GlobalTable that path is `SSESpecification: { Enabled: false }`, which returns every region to the AWS owned key, as CloudFormation does on removal (#5355). The GlobalTable names `SSESpecification` only while the template leaves the table on the AWS owned key (no block, or `SSEEnabled: false`), so a baseline that disagrees with a template declaring encryption never turns that encryption off.
