- **cdkd now refuses, instead of substituting the placeholder account `123456789012`, when STS cannot name the deploy's account and `AWS_ACCOUNT_ID` is unset (issue [#1730](https://github.com/go-to-k/cdkd/issues/1730))** -- `src/deployment/intrinsic-resolver/account-drain.ts` (`getAccountInfo` / `resolveAccountIdentity`) and its unit tests. When `sts:GetCallerIdentity` failed (or answered with no `Account`), `getAccountInfo` used to answer `123456789012` with only a warning. That id is structurally valid and has no wildcard, so `Ref: AWS::AccountId` and `AWS::StackId` served it silently, and nothing downstream could tell it from a real account. Now the lookup throws `Cannot determine the AWS account id: ...`, naming the STS failure's class (never its text, which can carry the caller's role ARN), the `aws sts get-caller-identity` check, and the `AWS_ACCOUNT_ID` escape hatch. An operator-supplied `AWS_ACCOUNT_ID` is still used and cached as a real answer. A failure is never cached: concurrent callers share one in-flight lookup, and the next caller (or a retry) asks STS again, so a transient blip does not poison the rest of the run. The 10-second placeholder window (`FABRICATED_ACCOUNT_INFO_TTL_MS`) is gone with the placeholder.
