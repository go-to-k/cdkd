- **cdkd now refuses, instead of substituting the placeholder account `123456789012`, when STS cannot name the deploy's account and `AWS_ACCOUNT_ID` is unset (issue [#1730](https://github.com/go-to-k/cdkd/issues/1730))** -- `src/deployment/intrinsic-resolver/{account-drain,functions,getatt-heal}.ts`, `src/utils/error-handler.ts` (`AccountIdUnavailableError`), and the Cloud Control / SSM / AppSync / API Gateway V2 / custom-resource providers and `cdkd import`. A failed `sts:GetCallerIdentity` used to answer `123456789012` with only a warning, so `Ref: AWS::AccountId` and `AWS::StackId` served it silently and a custom resource's `StackId` carried `000000000000`. Now they refuse with `Cannot determine the AWS account id: ...`, withholding AWS-authored message text from the STS failure, naming the `aws sts get-caller-identity` check and the `AWS_ACCOUNT_ID` escape hatch, which must be 12 digits. `AWS::Region`, `AWS::Partition`, `Fn::GetAZs` and any `Fn::GetAtt` whose value does not embed the account still resolve. An ARN a provider records after the resource exists is left out with a warning rather than failing the create; `cdkd import` leaves an account-bearing name unresolved; a custom-resource Delete asks again for about 17 seconds before it is reported skipped. A failure is never cached, so the next lookup asks STS again; the 10-second placeholder window is gone.
