- **A deploy finishes sooner after its last resource (issue [#4837](https://github.com/go-to-k/cdkd/issues/4837))** -- `src/provisioning/providers/dynamodb-table-provider.ts`, `src/state/{lock-manager,s3-state-backend,export-index-store}.ts`, `src/provisioning/providers/create-token-ledger.ts`, `src/deployment/deploy-engine/{deploy-flow,rollback}.ts`, `src/cli/commands/deploy.ts`. The bookkeeping after the last resource took ~5s on a 5-resource stack. A DynamoDB table's follow-up reads for its drift baseline (tags, point-in-time recovery, TTL, resource policy, Kinesis destination, contributor insights, stream members) now run concurrently, in the same key order; per-index contributor insights stay one after another. A deploy that finds no rollback journal at its start (under the stack lock) purges the journal key's leftover versions then, beside the deploy (on a first deploy, once its pre-provisioning gate passes), and waits for that purge before releasing the lock on every path; and its success then no longer reads, deletes and purges the absent journal again; any journal write through the same backend voids that. The create-token ledger, and the exports index when the stack's record publishes no export, are read at the start too, so an unchanged success needs no read of either. The state backend opens its connections beside the final drain, as S3 drops a keep-alive socket idle about five seconds. `cdkd deploy` no longer waits for the lock's old-version purge before its events flush: the lock is still deleted before the deploy returns, and the purge finishes beside the flush, before the command exits. Tests: `tests/unit/provisioning/{dynamodb-table-provider-readcurrentstate,create-token-ledger}.test.ts`, `tests/unit/state/{lock-noncurrent-version-purge,rollback-journal-version-purge,export-index-store}.test.ts`, `tests/unit/deployment/deploy-engine-tail-ordering.test.ts`.
