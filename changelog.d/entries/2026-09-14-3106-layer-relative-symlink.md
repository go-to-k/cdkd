- **A relative symlink inside a Lambda Layer no longer arrives dangling in the local container (issue [#3106](https://github.com/go-to-k/cdkd/issues/3106), found in the [#3105](https://github.com/go-to-k/cdkd/pull/3105) review)** -- `src/cli/commands/local-invoke.ts` (`materializeLambdaLayers`), `src/cli/commands/local-start-api.ts` (the `start-api` layer merge), unit tests, the `local-invoke-layers` fixture. Both layer merges copied each layer's asset directory into one tmpdir with `fs.cpSync`, whose `verbatimSymlinks` defaults to `false` in every Node release: a RELATIVE link such as `bin/rel-link -> real.sh` (the shape a layer build tool emits) was rewritten to the ABSOLUTE host path of the source asset, so `/opt/bin/rel-link` resolved to a path that does not exist inside the container and a handler executing through it failed with `ENOENT`. Both merges now go through one helper, `src/local/layer-tree-copy.ts` (`copyLayerTreeLastWins`): an explicit walk that recurses only into real directories, copies each file on its own with `cpSync` (so `+x` survives), recreates each symlink with the SOURCE's own target string, and lets the last layer win for every kind (a link, a file or a directory over any of the others) — a bare `verbatimSymlinks: true` would instead have made Node's C++ `cpSync` (every release after 22.12) throw `EEXIST` when two layers carry a symlink at the same path (`node_modules/.bin/<tool>` from a shared dependency) and a recursive `readdirSync` descends into directory symlinks on the same releases. The comment above each call had claimed the opposite of the default since the #241 backlog. Only the multi-layer merge path was affected (a single layer is bind-mounted directly); absolute symlinks are unchanged. Measured live: the `local-invoke-layers` fixture execs `/opt/bin/rel-link` and returns `real-via-link`; the pre-fix binary fails with `ENOENT`. cdk-local tracks the same fix as [#727](https://github.com/go-to-k/cdk-local/issues/727).
