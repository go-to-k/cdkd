- **A nested-stack child resource reading a secret-carrying parameter no longer reports a change on every deploy (and `cdkd scrub` of a nested stack persists the same value) when the parameter's expression cannot be certified (issue [#2349](https://github.com/go-to-k/cdkd/issues/2349))** -- `src/deployment/secret-redaction/nested-stack.ts`, `src/deployment/secret-redaction/redact-path.ts`, `src/deployment/deploy-engine/masking.ts`, `src/deployment/intrinsic-resolver/parameter-secrets.ts`. When two child parameters resolved to one secret plaintext and a resource read both, a `{Ref: <Param>}` leaf that cdkd could not tie to its parameter's own `{{resolve:...}}` expression (a value EMBEDDING the secret, such as a `postgres://u:<secret>@host` connection string the parent built with `Fn::Sub`, or a parameter whose association was refused) was persisted with whichever parameter's expression resolved last, while the diff side used the parent's. The two never matched, so the child reported an UPDATE that no deploy cleared (the post-resolve re-check prevented any AWS write). Both sides now answer such a leaf with one function over the parent's bag, `redactInheritedParameterValue`. The persisted leaf falls back to the previous redaction whenever that answer would leave a plaintext the resource's own bag holds, so nothing is persisted less redacted than before. Composite `Fn::Sub` / `Fn::Join` leaves that every positioning arm refuses keep the old behaviour. `cdkd diff --recursive` still renders such a parameter with its own spelling and can disagree in one parent resolution order (issue [#4644](https://github.com/go-to-k/cdkd/issues/4644)). Tests: `tests/unit/deployment/secret-redaction-nested-parameter-list.test.ts` (the two pinned residual cases now assert agreement), `tests/unit/deployment/secret-redaction-nested-parameter-fallthrough.test.ts`.
