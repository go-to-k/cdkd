- **A transport failure keeps its wording everywhere `describeAwsFailure` is used, and a credential-resolution failure stops passing through verbatim (issue [#3297](https://github.com/go-to-k/cdkd/issues/3297))** -- `src/utils/aws-failure-text.ts`, `src/provisioning/cloud-control-provider.ts`. `isAwsAuthoredFailure` decides whether a caught failure's text is AWS's -- and so must be withheld from a user-facing or PERSISTED message. It tested for the PRESENCE of `$metadata` / `$fault` / `$response`, and `@smithy/core`'s retry middleware stamps `$metadata` onto EVERY error it gives up on, socket errors included. Measured: a plain `ECONNREFUSED` carries one, so it was reduced to its `name` -- for a socket error the bare token `Error`. The predicate is now a real SERVICE signal (`$fault`, or a NUMERIC `$metadata.httpStatusCode`) plus the `CredentialsProviderError` NAME, which carries neither because credential resolution runs OUTSIDE the retry middleware. `$response` is gone: the same catch that sets it also sets `$metadata.httpStatusCode`, so the status-code arm subsumes it. **The change runs BOTH ways.** Five call sites inherit it -- `asset-storage.ts`, `s3-bucket-provider.ts`, `efs-provider.ts` and two in `cloud-control-provider.ts`: each had been reporting a transport failure as `Error`, and four of the five had been letting a `CredentialsProviderError` through verbatim into a persisted message, which under `credential_process` meant the helper's ARGV and its stderr (the fifth catches `config.region()`, which that shape cannot reach). That is withheld now and reachable at `debug`; the cost is the corporate-proxy `self-signed certificate` symptom reading as a class name at default verbosity. `s3-state-backend.ts` is deliberately untouched -- it reads `detail`, not `summary`. The LOCAL duplicate predicate [#3236](https://github.com/go-to-k/cdkd/issues/3236) had to carry is deleted with it, so one error can no longer be classified two ways.
