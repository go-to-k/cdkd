- **`AWS::Lambda::EventSourceMapping` applies a changed `SelfManagedKafkaEventSourceConfig` / `AmazonManagedKafkaEventSourceConfig` on update (issue [#3851](https://github.com/go-to-k/cdkd/issues/3851))** -- `src/provisioning/providers/lambda-eventsource-provider.ts` (`kafkaConfigForUpdate`), with unit tests in `tests/unit/provisioning/lambda-eventsource-provider-kafka-update.test.ts` and a schema-registry add and removal phase in `tests/integration/lambda-esm-self-managed-kafka/`. `update()` never sent either block, so adding, changing or removing a `SchemaRegistryConfig` on an existing Kafka or MSK mapping reported success without reaching AWS, and the next diff showed no change. `update()` now sends the members that changed. A removed `SchemaRegistryConfig` is sent as `{ SchemaRegistryConfig: {} }`, the shape Lambda clears it with; an empty block leaves it in place. An unchanged `ConsumerGroupId` is left out, because Lambda rejects the member on every update, even with the same value. A changed one is sent, and Lambda rejects it, as it does under CloudFormation.
