- **A `Ref` to a parameter resolves to the parameter, never to a state record of the same name (issue [#3916](https://github.com/go-to-k/cdkd/issues/3916))** -- `src/deployment/intrinsic-function-resolver.ts`, with unit tests in `tests/unit/deployment/resolver-ref-parameter-precedence.test.ts` and `tests/unit/cli/export-nested-failure-render.test.ts`. The resolver answered a `Ref` from cdkd state BEFORE the template's Parameters, so a state record keyed by a parameter's name (planted or stale, since CloudFormation cannot declare one logical id as both) replaced that parameter's value: on `cdkd deploy` for every property the parameter fed, and on nested `cdkd export` for the child's IMPORT parameters, where a record naming an attacker's role could pass the IAM::Policy check and have phase 2 grant the policy to that role. A name the template declares as a Parameter, or the caller binds as one, and a pseudo-parameter name (`AWS::...`) are now never read from state: `Ref` returns the parameter (or pseudo-parameter) value, and `Fn::GetAtt` on such a name fails as `Resource <name> not found for Fn::GetAtt`, while a `${Name.Attr}` placeholder in `Fn::Sub` on such a name warns and keeps the placeholder, as it does when no record exists. A `Ref` / `Fn::GetAtt` to a resource still reads its record, and a record whose name no parameter uses resolves as before.
