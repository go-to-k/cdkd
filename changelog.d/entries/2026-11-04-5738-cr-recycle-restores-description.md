- **The custom-resource IAM-propagation retry no longer leaves its marker as the backing Lambda's `Description`, a permanent `cdkd drift` (issue [#5738](https://github.com/go-to-k/cdkd/issues/5738))** -- `src/provisioning/providers/custom-resource-provider.ts` (`recycleBackingFunctionExecEnv`) and a new unit file. The recycle forces a cold start by writing `cdkd: recycled for IAM-propagation retry (<logicalId>)` onto the backing function and never wrote the old text back; its comment claimed this could not surface as drift, but CDK's own handlers declare a Description (e.g. `Custom::S3BucketNotifications`), so `cdkd drift` reported it forever and no redeploy repaired it (the template diff is `NO_CHANGE`). The recycle now reads the prior Description first and restores it once the marker's update settles; the restore is itself a configuration update, so the next invoke still cold-starts. Recycles on one backing function are serialised (a qualified and an unqualified ServiceToken count as one function), so a concurrent custom resource reads the restored text rather than another's marker. A restore refused with `ResourceConflictException` waits and re-sends a bounded number of times (every wait in one recycle shares a 240s budget), and a read that returns a marker (an earlier restore failed) falls back to the remembered original. An empty Description is restored as empty; an unreadable one is left alone. Every step stays best-effort: a failed read or restore is logged at debug and never fails the custom resource.
