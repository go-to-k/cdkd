- **An `AWS::IAM::Policy` or `AWS::IAM::ManagedPolicy` no longer grants its permissions to a same-named role, group or user someone else made (issue [#6722](https://github.com/go-to-k/cdkd/issues/6722), part of [#6655](https://github.com/go-to-k/cdkd/issues/6655))**. The inline policy is put on each principal by name, and a managed policy is attached to / detached from its `Roles` / `Groups` / `Users` by name, so a principal re-created out of band under the recorded name received cdkd's policy. Before any write, each principal that is a record of the same stack with a recorded `RoleId` / `GroupId` / `UserId` is now read (`GetRole` / `GetGroup` / `GetUser`, at most 5 at a time) and compared. One this deploy itself created or replaced is not read (its id is this run's), so a first deploy makes no extra call; a later create or update of such a policy reads each pre-existing in-stack principal it puts the inline policy on, or (a managed policy update) adds or removes, and a principal that matched is not read again in the same deploy, destroy or rollback run (the #6655 removal reads included; a mismatch or failed read is re-read on each attempt). Another id refuses the create or update non-retryably with nothing put or attached anywhere, naming the principal's logical id and the attribute (no value), with `cdkd import --force` for a principal you replaced yourself and `cdkd state orphan` otherwise; a rollback replaying an update backwards refuses the same way. A managed policy's leaving principal held by another id is sent no detach and warned about. A denied read refuses non-retryably naming the permission, on the #6655 removal paths too. A principal outside the stack, or whose record holds no usable id, is handled by name as before.
