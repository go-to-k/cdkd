- **An EFS file system or access point tag change now applies in place, as CloudFormation does (issue [#5464](https://github.com/go-to-k/cdkd/issues/5464))** -- `src/provisioning/providers/efs-provider.ts` (`applyTagDiff`, new `updateAccessPoint`), a new unit file, and the `efs-standalone` integ fixture. Before, a `FileSystemTags` change on `AWS::EFS::FileSystem` sent nothing: the deploy reported success, AWS kept the old tags, and state recorded the new ones, so `cdkd diff` showed nothing afterwards. An `AccessPointTags` change on `AWS::EFS::AccessPoint` failed the deploy with "no in-place update API", although the CloudFormation schema leaves that property tag-updatable; the only workaround, `--replace`, deleted and recreated the access point. Both now diff the recorded and desired tags through `planTagDiff`: changed or added keys go through `TagResource`, dropped keys (or the whole property removed) through `UntagResource`, and a malformed desired tag list is refused before any call. Any other access-point property change is still refused, since every other property is create-only. A file system whose tag change was deployed before this fix still carries the old tags on AWS while state already records the new ones, so the next deploy sends nothing for it and a key removed then is never untagged automatically: `cdkd drift` shows it, and `cdkd drift --revert` fixes it.
