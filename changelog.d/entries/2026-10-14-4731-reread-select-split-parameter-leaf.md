- **`cdkd diff --recursive --fail` no longer reports a change on an unchanged nested stack in which one child resource reads a parameter the parent spelled as a literal embedding `{{resolve:...}}` tokens beside a sibling parameter spelling the same secret differently, either of the two through `Fn::Select` / `Fn::Split` (issue [#4731](https://github.com/go-to-k/cdkd/issues/4731)).** After upgrading, the first deploy of such a stack shows a change on the child resources reading the literal parameter, because their state now records the parameter's own `{{resolve:...}}` spelling instead of the sibling's. The other direction happens too: where one child resource reads such a parameter as a bare `Ref` inside an array that also holds an `Fn::If` or `AWS::NoValue` element, beside the sibling, every resource in that child reading the parameter now records the sibling's spelling. Either way the deployed VALUE is unchanged, and a create-only property is replaced once with an identical value. Before, cdkd fell back to the sibling's spelling for that parameter in the whole child while `cdkd diff --recursive` rendered its literal. A child leaf whose source holds `Fn::Select` / `Fn::Split` (possibly with `Fn::Join` beneath or around it) over the child's parameters is now persisted as the deploy's diff side computes it, re-read with the same parameter bindings, when that answer renders back to the resolved value through the parent's own secret pairs. Three cases keep the old behaviour: a read under `Fn::If`, through `Fn::Sub` inside `Fn::Select`, or inside an array holding an `Fn::If` or `AWS::NoValue` element ([#4919](https://github.com/go-to-k/cdkd/issues/4919)); a split that cuts a token ([#4914](https://github.com/go-to-k/cdkd/issues/4914)); and two reads in the child's `Outputs` ([#4913](https://github.com/go-to-k/cdkd/issues/4913)). Source: `src/deployment/secret-redaction/{nested-stack,redact-path}.ts`, `src/deployment/intrinsic-resolver/parameter-secrets.ts`.
