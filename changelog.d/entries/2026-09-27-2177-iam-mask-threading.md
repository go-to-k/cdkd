- **The IAM providers mask secret-derived names in their own log lines and remediation commands (issue [#2177](https://github.com/go-to-k/cdkd/issues/2177), IAM slice)** -- `src/provisioning/providers/iam-{role,user-group,policy,managed-policy,instance-profile,access-key}-provider.ts`, with the shared sink builder `createMaskedLogSinks` in `src/provisioning/masked-retry-logger.ts`; unit tests in `tests/unit/provisioning/iam-providers-masked-warn.test.ts`. A role, user, group, policy, instance profile or access-key user name resolved from a `{{resolve:secretsmanager:...}}` reference used to reach the IAM providers' own debug and warning lines in plaintext, since those lines pass through no deploy-engine mask, and to be pasted verbatim into the `aws iam ...` cleanup commands a failed create prints. Every `create()` / `update()` line now goes through the deploy's masker, each name is masked before it joins the sentence (so a name that IS a secret shorter than four characters is caught too; a short secret embedded in a longer name is not), a physical name cdkd derives from a secret (stack prefix, folded characters, truncation) is masked as well, including the OLD name on a replacement whose previous value is a secret reference in state, and a cleanup command that would carry a masked name is withheld rather than printed with `***` in it. The IAM role and managed policy replacement paths hand the masker to the `create()` they run. The `delete()` path still has no masker (issue [#2007](https://github.com/go-to-k/cdkd/issues/2007)), and a derived name is masked only inside the operation that derived it (issue [#3869](https://github.com/go-to-k/cdkd/issues/3869)).
