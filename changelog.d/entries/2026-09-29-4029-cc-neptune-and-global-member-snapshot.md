- **A Cloud Control-routed `AWS::Neptune::DBCluster`, and an `AWS::RDS::DBCluster` in a global cluster, no longer leave an untagged final snapshot when deleted (issue [#4029](https://github.com/go-to-k/cdkd/issues/4029))** -- `src/provisioning/cloud-control-provider.ts`, `src/provisioning/providers/rds-provider.ts`, `src/provisioning/providers/neptune-provider.ts`, `src/cli/commands/destroy-runner.ts`, `src/deployment/deploy-engine.ts`. Cloud Control never tells a delete handler the `DeletionPolicy`, and some handlers then take a final snapshot of their own. cdkd already deleted Cloud Control-routed RDS clusters and instances through RDS for that reason ([#3993](https://github.com/go-to-k/cdkd/issues/3993)), except a cluster in a global cluster, which it left on Cloud Control with a warning. A new integration fixture measured the Neptune cluster handler doing the same, and the ElastiCache cache-cluster handler not doing it. A Cloud Control-routed Neptune cluster is now deleted through Neptune with `SkipFinalSnapshot`, including one with no `DeletionPolicy`, whose CloudFormation default is `Delete`. An RDS cluster in a global cluster is now detached from it with `RemoveFromGlobalCluster`, then deleted through RDS once it has left the global cluster and is available again, as CloudFormation does. A busy or throttled detach is waited through. A cluster whose deletion protection is still on is not detached, since the detach cannot be undone and the delete would fail; the error says to pass `--remove-protection`. Any other detach failure fails the delete and never reads as already deleted. Two cases stay on Cloud Control with the warning: a Neptune cluster in a global cluster, and an RDS cluster whose recorded `GlobalClusterIdentifier` is not a plain name. The new `cc-final-snapshot-handlers` fixture fails if any of the three types leaves a snapshot.
