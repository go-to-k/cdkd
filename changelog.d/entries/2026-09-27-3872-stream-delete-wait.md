- **Deleting a Kinesis stream or a Firehose delivery stream now waits until the stream is gone, so a destroy followed by a redeploy (or a delete-first replacement) of a named stream no longer fails with `already exists` (issue [#3872](https://github.com/go-to-k/cdkd/issues/3872))** -- `src/provisioning/providers/kinesis-provider.ts`, `src/provisioning/providers/firehose-provider.ts`, new `src/provisioning/delete-gone-wait.ts`, and unit tests. Both services keep a stream's NAME while it is `DELETING` and refuse a create of that name with the same `ResourceInUseException ... already exists` text a live stream gets, so no retry could tell the two apart: the window measured 4-7s for Kinesis and ~103-107s for Firehose, which outlasts the name-cooldown retry grid. `delete()` returned the moment `DeleteStream` / `DeleteDeliveryStream` was accepted; it now polls `DescribeStreamSummary` / `DescribeDeliveryStream` until `ResourceNotFoundException`, like CloudFormation. The wait is capped (5 min Kinesis, 10 min Firehose; half an explicit `--resource-timeout` when that is lower), keeps polling through throttling, and never fails the delete: a cap, a Ctrl-C, or a status read AWS refuses (e.g. no describe permission) warns and returns, since AWS finishes the accepted delete on its side. A stream already gone on delete stays idempotent and is not waited on. Integration fixture: `tests/integration/stream-delete-redeploy`.
