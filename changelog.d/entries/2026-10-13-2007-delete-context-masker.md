- **A provider's delete is handed the secret masker, so it can tell a name is secret-derived (issue [#2007](https://github.com/go-to-k/cdkd/issues/2007))** -- `src/provisioning/region-check.ts`, `src/types/resource.ts`, `src/deployment/deploy-engine/{delete,replacement,update-replace,update-in-place}.ts`, `src/cli/commands/destroy-runner.ts`, `src/deployment/rollback-executor.ts`, `src/deployment/rollback-executor/{names,replay-scope,replay-revert,replay-reverse-replacement,replay-orphan-delete}.ts`, `src/provisioning/cloud-control-provider.ts` and the custom-resource, S3 Express directory bucket, IAM role / managed policy / user / group, DynamoDB global table, Glue, RDS DB proxy target group, SNS subscription and ACM certificate providers. `DeleteContext` had no `maskSecrets`, so a provider could not tell that a name it printed was derived from a secret. The S3 Express "bucket is not empty" refusal therefore printed `aws s3 rm s3://*** --recursive` once the log masked the name: a command that names no bucket. It now says the name is secret-derived and prints no command. A deploy's replacement delete also ran with no resolved value bound for the logger, so a provider's own delete lines could print one; they are masked now. Every cdkd delete site passes a masker: a replacement over the deploy's resolved secrets and its secret-named records, a rollback over both the re-resolved previous generation and the failed deploy's values (its own failure lines and events included), and `cdkd destroy` or a template-removal delete over the record's secret-derived names. A provider's internal delete during an update or a failed create's cleanup is handed the operation's masker too.
