- **`cdkd refactor` no longer renames a resource that references something the next deploy changes, and `cdkd diff` no longer suggests it (issue [#6097](https://github.com/go-to-k/cdkd/issues/6097))** -- `src/analyzer/refactor-pairing.ts`, `src/analyzer/refactor-hints.ts`, `src/cli/commands/refactor/plan.ts`, `src/cli/commands/refactor-move.ts`, `src/cli/commands/diff-recursive/build-tree.ts` and `src/deployment/deployment-approval.ts`, plus a new `refactor-lambda-version` integ. Before, after a code change to a function behind a CDK `fn.currentVersion` and an `Alias`, `cdkd diff` and the deploy approval prompt marked the old version `(moved to ..., run 'cdkd refactor' to keep it)`. Following that advice rebound the old version to the new logical ID, so the next deploy published no version, and the alias kept serving the old code. That deploy exited 0 and `cdkd drift` stayed clean. An API Gateway deployment after a method change took the same path. Like the AWS CDK CLI, whose refactor digest covers everything a resource references, cdkd now treats such a resource as a new one. Within a stack it reports it as `Not refactored: ... it references <id>, which the next deploy changes`, refuses a mapping-file pair or a move between stacks on the same grounds, and shows no hint for it.
