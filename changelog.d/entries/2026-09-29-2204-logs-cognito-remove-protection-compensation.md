- **`cdkd destroy --remove-protection` restores deletion protection on a CloudWatch Logs log group or a Cognito user pool whose delete then failed terminally (issue [#2204](https://github.com/go-to-k/cdkd/issues/2204), partial)** -- `src/provisioning/providers/logs-loggroup-provider.ts`, `cognito-provider.ts`, `deletion-protection-compensation.ts`, `docs/_contents/cli-destroy.md`, with unit tests in `tests/unit/provisioning/providers/logs-cognito-remove-protection-compensate.test.ts`. Before, the flip-off (`PutLogGroupDeletionProtection` / `UpdateUserPool`) was never undone, so a failed destroy left the resource live with its guard silently stripped. Now the guard is turned back on before the failure is reported, under the rules the DynamoDB and RDS-family sites follow: only a guard a pre-flip `DescribeLogGroups` / `DescribeUserPool` saw ON and this run turned off, only on a terminal failure, never once AWS has accepted the delete, and a failed re-enable is its own log line with a pasteable restore command. The Cognito user pool now reads the live `DeletionProtection` even when the recorded properties say `ACTIVE`, and skips the `UpdateUserPool` flip when the pool is already `INACTIVE`. The other `--remove-protection` types stay open under #2204.
