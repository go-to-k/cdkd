- **Destroying an Elastic IP associated through its own `InstanceId` disassociates it before releasing, instead of failing (issue [#6715](https://github.com/go-to-k/cdkd/issues/6715))** -- `src/provisioning/providers/ec2/igw-eip.ts`, `src/provisioning/providers/ec2-provider.ts`. A destroy reaches the EIP before the instance it names, and in a non-default VPC `ReleaseAddress` refuses an associated address with `InvalidIPAddress.InUse`, so `cdkd destroy` failed where CloudFormation, whose delete handler disassociates first, succeeds. After that refusal cdkd now reads the address and disassociates it when the association is to the instance the EIP's recorded `InstanceId` names, then releases it; an association another resource made is left, and AWS's refusal stands. The ordinary release sends no extra call. Found by the new delete-blocker inventory, `src/provisioning/delete-blocker-inventory.ts`, which lists what each SDK provider type's CloudFormation delete handler removes first and is checked by `tests/unit/provisioning/delete-blocker-inventory.test.ts`.
