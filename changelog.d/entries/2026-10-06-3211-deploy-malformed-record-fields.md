- **`cdkd deploy` no longer hands a resource record's torn `properties` map or missing `physicalId` to a provider (issue [#3211](https://github.com/go-to-k/cdkd/issues/3211), deploy half)** -- `src/deployment/deploy-engine/{deploy-flow,update,delete,observed-capture}.ts`, `src/deployment/read-only-attribute-healer.ts`, `src/state/malformed-resources-bag.ts`. A record whose `properties` is absent, `null` or not an object is now refused at the state load, naming the stack, before any provider call. Before, the refusal came from the diff, after the observed-state auto-refresh had already handed the map to `provider.readCurrentState`. For a record whose `physicalId` is absent, empty, whitespace-only or not a string (other than a nested stack's not recorded on Cloud Control): a template removal skips the delete with `skipped (state record has no physical id)` and keeps the record, as `cdkd destroy` does; before, the provider was called with that value, and a `*NotFound` answer read as already deleted dropped the record of a resource still live. An update of such a record now fails before anything is sent, instead of calling `provider.update` (or a replacement's delete) with it. The auto-refresh and the `Fn::GetAtt` attribute heal (shared with `cdkd diff`) no longer read such a record. An unchanged record is not refused. A custom resource handler answering a whitespace-only `PhysicalResourceId` now takes the fallback an empty one always took (the logical id on create, the current id on update, `src/provisioning/providers/custom-resource-provider.ts`), so it is never recorded as an id later deploys would refuse. Tests: `tests/unit/deployment/deploy-engine-unaddressable-record-3211.test.ts`, `tests/unit/deployment/deploy-engine-malformed-properties-refusal.test.ts`, `tests/unit/deployment/read-only-attribute-healer.test.ts`, `tests/unit/provisioning/custom-resource-unaddressable-physical-id-3211.test.ts`.
