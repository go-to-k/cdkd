- **cdkd no longer prints a secret-derived Cloud Control identifier in a Cloud Control create's or delete's log lines, or in the error a create, update or delete throws (part of issue [#3869](https://github.com/go-to-k/cdkd/issues/3869))** -- `src/provisioning/cloud-control-provider.ts` (`IdScrubLog`, installed per call so every line the call prints, its helpers' included, goes through it); unit tests in `tests/unit/provisioning/cloud-control-provider-create-delete-id-masking.test.ts`, and the `secret-derived-immutable-names` integration fixture now asserts its deploy and destroy logs. A Cloud Control identifier can carry a name taken from a secret (`AWS::Logs::MetricFilter` is `<LogGroupName>|<FilterName>`), and a pre-rotation or AWS-derived spelling of that name is one the deploy's masker cannot recognise. The update path already withheld it in its lines; now `create()` withholds the identifier Cloud Control returns (or a failed create's error names) when the desired properties hold a secret-derived value, `delete()` withholds it when the recorded properties hold a `{{resolve:` reference or `***`, and the error leaving any of the three has the identifier and each `|` part replaced by `***` in every message of its cause chain and in its `physicalId` field, AWS status text included; an abandoned wait's request token and resume command are kept whole. A CC delete's skipped and indeterminate-guard reasons are scrubbed too. The identifier the call returns is unchanged, and a withheld create's name-collision advice is dropped rather than printed. **Residual**: a delete handed resolved plaintext (an in-process rollback's) has no evidence to withhold on, a failed create whose error names no identifier cannot be scrubbed of it, and the engine-level registry, the engine's own lines, persisted events' `physicalId` field, `import()`'s two unreadable-model WARNs and other providers' lines stay open under [#3869](https://github.com/go-to-k/cdkd/issues/3869).
