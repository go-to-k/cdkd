- **`cdkd local invoke` / `local start-api` run container-image Lambdas built on a non-AWS base image (issue [#6018](https://github.com/go-to-k/cdkd/issues/6018))** -- `src/local/rie-mount.ts`, `src/local/rie-client.ts`, `src/local/container-pool.ts`, `src/cli/commands/local-invoke/command.ts`, `src/cli/commands/local-start-api/container-spec.ts`, `src/utils/cache-home.ts`. cdkd now mounts the Lambda Runtime Interface Emulator read-only at `/var/rapid/aws-lambda-rie` into every container-image function and runs it as the entrypoint, handing it the image's `ENTRYPOINT` + `CMD` (each replaced by its `ImageConfig` field when set), as SAM CLI does. The binary is copied once per architecture out of `public.ecr.aws/lambda/provided:al2023` into `$XDG_CACHE_HOME/cdkd/lambda-rie/` (or `~/.cache/cdkd/lambda-rie/`). An image whose entrypoint already is `aws-lambda-rie` is left alone, and when the binary cannot be obtained cdkd warns once and runs the image as built. Before, an image without its own emulator (distroless, Alpine + a runtime client) was never invoked: the request reached whatever the image served on `:8080`, and its 404 body came back as the result. `local invoke` (and the WebSocket server) now also fail an invoke answered with HTTP 404 / 405, which the emulator never sends for its invoke path. Integ: `local-invoke-container` step 6, `local-start-api-container` `GET /non-aws`.
