- **A resource whose name comes from a secret dynamic reference can be updated in place again (issues [#4263](https://github.com/go-to-k/cdkd/issues/4263), [#4264](https://github.com/go-to-k/cdkd/issues/4264), [#4275](https://github.com/go-to-k/cdkd/issues/4275))** -- `src/provisioning/secret-reference-immutable.ts` and the API Gateway V2 Stage, DynamoDB GlobalTable, ECS Service, EMR Cluster / InstanceFleetConfig / InstanceGroupConfig, RDS DBProxy / DBProxyEndpoint / DBProxyTargetGroup, S3 Vectors VectorBucket and Kinesis StreamConsumer providers. State keeps a secret-derived value as its `{{resolve:...}}` reference while `update()` receives the resolved value, so each provider's immutable-name guard saw a change on every in-place update and refused it, although the template never changed the name. A guard now compares the resolved value with the name the physical id carries (Stage, table, ECS service ARN, proxy, endpoint, vector bucket, consumer ARN), and otherwise lets it through only when the recorded side is a `{{resolve:` reference whose resolved value the deploy's masker recognises, on a key the engine replaces on any change (a re-pointed reference there is a replacement, never an update). A key whose resolved value addresses the provider's writes is confirmed with AWS first (a DBProxyTargetGroup's proxy name: the resolved names must return the recorded target group ARN) or never exempted (an EMR fleet's or group's cluster id), so a rotated secret cannot redirect a write. A Scheduler Schedule's secret-derived `GroupName` stays refused: nothing non-secret in the record identifies the group. A real rename, a recorded `***` without a physical-id witness, and an update with no masker are still refused. Update-path debug lines those names now reach are masked. Tests: `tests/unit/provisioning/secret-reference-immutable.test.ts`, `tests/unit/provisioning/secret-reference-immutable-sites.test.ts`.
