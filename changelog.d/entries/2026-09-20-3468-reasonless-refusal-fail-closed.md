- **A stack imported with cdkd 0.290.35 no longer records a decrypted secret as a drift baseline on the next `cdkd deploy` or re-import (issue [#3468](https://github.com/go-to-k/cdkd/issues/3468), PR #3471)** -- `analyzer/parameter-dependence.ts` (new; the walk, moved unchanged), `deploy-engine.ts`, `import.ts`, `types/state.ts`, `docs/import.md`, `docs/state-management.md`, a reason-stripping arm on the `import-deployed-parameter-secret` integ. 0.290.35 shipped the unverifiable-parameter baseline refusal (#2854) without the reason field that lets it survive an in-place UPDATE (#3462), so its markers carry no `observedBaselineRefusalReason` and were still cleared by an UPDATE: a code-only Lambda update wrote the deployed secret to `observedProperties`. A marker with NO reason is now read fail closed. At the start of every deploy, a reason-less marker on a resource whose template definition reads a declared template parameter -- directly, through a condition, through an attribute of a resource that does, or, in a template that reads one, in a shape the walk cannot classify -- is stamped `"unverifiable-parameter"`: the update keeps it, reads nothing back, and the next state write records the explicit form. An unreadable template stamps all. `cdkd import` carries such a marker the same way across a re-import on an unchanged physical id. Pseudo parameters and CDK's `BootstrapVersion` do not count; a reason-less marker on a resource that reads no parameter still clears on UPDATE. Every refusal now records a reason -- the other three import arms write the new value `"incomplete-resolution"` (no schema bump; older binaries clear it on UPDATE, as before) -- so the cautious reading only ever applies to old records. Cost: an old refusal of that other kind on a resource that reads a parameter stays until replacement or a proving re-import. Known gap: replacing the parameter reference with its literal before the first fixed-binary deploy that writes state hides the dependence.
