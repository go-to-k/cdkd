- **A token-less create the AWS SDK replayed inside one call after a reset connection is now checked for the duplicate its first request may have made (issue [#4687](https://github.com/go-to-k/cdkd/issues/4687))** -- `src/provisioning/providers/ambiguous-create.ts` (`replayedInSend` / `replayFollowedAmbiguousAttempt` / `replayedSendWindow` / `ambiguousAttemptLead`), `orphan-report.ts`, `iam-access-key-provider.ts`, and the `AmbiguousCreateLatch` providers (`kms`, `cognito`, `appsync`, `apigateway`, `apigatewayv2`, `emr-*`, `lambda-layer`, `lambda-eventsource`, `dlm-lifecycle-policy`, `ecs`, `ec2`), their unit tests and `docs/troubleshooting.md`. Before, a socket reset or timeout after the request reached AWS was replayed by the SDK; when that replay SUCCEEDED, a create that is not name-unique had made a second resource -- for `AWS::IAM::AccessKey` a live credential no state records -- and nothing reported it. After a create the SDK retried inside its call, cdkd now checks right away: for `CreateAccessKey`, only when the retry followed a reset or timeout, the existing orphan reconcile deletes a key absent from the pre-create baseline, dated after the attempt started and not recorded by this process (never the key just returned; a failed delete warns with the `aws iam delete-access-key` command); for every latched create, its existing report-only lookup names candidates from the first request to the reply, never the returned resource, never adopting or deleting. A single-attempt create makes no extra call. A throttle the SDK retried also runs the report-only lookup: it finds nothing for a type with a creation date, and for an undated type it can name an unrelated resource of the same name, which the warning says may be another stack's.
