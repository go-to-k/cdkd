- **An `AWS::WAFv2::WebACL` or `AWS::CodeCommit::Repository` recorded `provisionedBy: 'cc-api'` returns to its SDK provider (issue [#6490](https://github.com/go-to-k/cdkd/issues/6490), batch 10)** -- `src/provisioning/provider-registry/sticky-exempt.ts`, `src/provisioning/sticky-exempt-physical-id.ts`, `src/provisioning/provider-registry.ts` and the new `cc-to-sdk-reroute-common-types-10` integ. Both types are now `'sdk-coverage'` members of `STICKY_CC_MIGRATION_EXEMPT`, so such a resource on Cloud Control moves to the SDK provider in place on the next deploy that changes it; `--pin-cc-api <LogicalId>` declines that. Cloud Control records a web ACL as `<Name>|<Id>|<Scope>` and a repository by its RepositoryId, while the SDK providers record the web ACL ARN and the repository name, neither of which is inside the Cloud Control id. A physical-id normalizer can now read the record's properties and the region, account and partition it lives in: the web ACL ARN is built from those (`global/webacl` for a CLOUDFRONT web ACL, which must be in us-east-1), and the repository name is the record's `RepositoryName`. Each normalizer still refuses an id of any other shape, and a web ACL whose recorded `Scope` or `Name` disagrees with its id, before any call to the resource; a read through a repository name that returns another RepositoryId is refused too. Each refusal names `--pin-cc-api <LogicalId>`. Only the web ACL resolves the account. Every form was measured on live resources. `Ref` stays `<Name>|<Id>|<Scope>` for a web ACL and the RepositoryId for a repository across the move. `cdkd diff` annotates the move `[returning to SDK provider]`. `AWS::EC2::SecurityGroupIngress` stays sticky (its SDK provider does not write the EC2-Classic `GroupName` / `SourceSecurityGroupName`), and so does `AWS::CloudTrail::Trail` (nothing on the trail itself can witness a recreate).
