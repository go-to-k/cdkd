- **A reverse-replacement refusal inside a nested child's revert no longer prints a `cdkd rollback --orphan` command that cannot reach it (issue [#3845](https://github.com/go-to-k/cdkd/issues/3845))** -- `src/deployment/rollback-executor.ts` (`orphanRemedy`, `RollbackExecutorContext.nestedChildReplay`), `src/deployment/nested-child-journal.ts`, `src/deployment/deploy-engine.ts`, with unit tests in `tests/unit/deployment/rollback-executor-retain-new-resource.test.ts`, `tests/unit/deployment/nested-child-journal.test.ts` and `tests/unit/deployment/deploy-engine-rollback-context.test.ts`. Since #3829 a nested stack's UPDATE revert replays the child's own journal, so both refusals (a replacement whose old type cannot be routed, and a name collision under `UpdateReplacePolicy: Retain`) can fire inside that replay. They ended on `To orphan it: cdkd rollback --orphan <id>`, but `--orphan` feeds only the replay of the stack it is run on, and a direct rollback of the child is refused while its parent's run is unsettled — so following the remedy hit the same refusal again. A nested child engine's own in-process rollback inside its parent's deploy printed the same command, and the parent's rollback replays that failure segment too. In both places the two refusals now print no command and say instead to resolve the cause and re-run the top-level stack's rollback, or re-deploy it. Outside a nested revert nothing changes.
