- **The SDK provider wires `AWS::RDS::DBCluster` `EnableGlobalWriteForwarding`, `ReplicationSourceIdentifier` and `SourceRegion` (issue [#5639](https://github.com/go-to-k/cdkd/issues/5639))** -- `src/provisioning/providers/rds/cluster-create.ts`, `cluster-update.ts`, `cluster-members.ts`, `cluster-restore.ts`, `shared.ts`, `drift.ts`, `rds-provider.ts`, `src/provisioning/property-coverage.ts`, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, unit tests, the RDS wire cases, and the `rds-aurora` integ. Before, a cluster declaring any of the three routed through Cloud Control. Now `EnableGlobalWriteForwarding` rides `CreateDBCluster` (a restore's follow-up `ModifyDBCluster`) and, when changed, `ModifyDBCluster`, and the create or update waits until forwarding is no longer `enabling` / `disabling`, as CloudFormation's handler does; a removal sends nothing. `ReplicationSourceIdentifier` rides `CreateDBCluster`, making the cluster a read replica; a changed or removed one is not applied to the existing cluster (ModifyDBCluster has no such member, and CloudFormation neither sends nor promotes), and cdkd warns. `SourceRegion` is refused when it names no AWS region, as CloudFormation refuses it, and is never sent: the AWS SDK for JavaScript presigns a cross-region source from its ARN. A cross-region `aws-cn` replica source keeps the Cloud Control route, as for a DB instance. None of the three is read back for drift yet. `Domain` / `DomainIAMRoleName` stay on Cloud Control. Resources already deployed through Cloud Control stay there.
