- **A custom-resource delete skipped during `cdkd deploy` no longer tells the user to run `cdkd state orphan` (issue [#4596](https://github.com/go-to-k/cdkd/issues/4596))** -- `src/provisioning/providers/custom-resource-provider.ts`, `docs/cli-deploy.md`. When a custom resource's delete was skipped (the handler answered `FAILED`, the invoke did not complete, or the recorded `ServiceToken` was the redaction mask or a `{{resolve:...}}` reference), the warning told the user to tear the resource down by hand and clear the stack's records with `cdkd state orphan <stack> --stack-region <region>`. That is safe on `cdkd destroy`, but on a deploy the stack is still deployed, so the command dropped the record of every live resource in it and the next deploy re-created or collided with all of them. The warning keeps that advice only on `cdkd destroy` / `cdkd state destroy`. Everywhere else it says to fix the handler (or restore `ServiceToken` in `state.json`) and re-deploy, which re-attempts the delete, that `--allow-unaddressed` lets a deploy exit 0 meanwhile, that a replacement or rollback whose other copy already exists leaves the surviving one untracked to tear down by hand, and not to run `cdkd state orphan` on a stack that is still deployed. The error for a recorded `ServiceToken` that is not a string no longer offers `cdkd state orphan` on create, update or a deploy-side delete; on create and update it points at the template, which a deploy reads and a rollback re-applies by re-deploying, and on a delete it names restoring the ARN. The skip outcome and reason are unchanged, and a destroy's warning no longer carries the deploy-only text. Tests: `tests/unit/provisioning/custom-resource-skip-remedy-4596.test.ts`.
