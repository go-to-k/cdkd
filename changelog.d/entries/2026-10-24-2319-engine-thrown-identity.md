- **A failed resource whose AWS error reaches the deploy engine unwrapped, and three engine replacement refusals, no longer write the caller's account id, assumed-role ARN and session name into the persisted deployment events (issue [#2319](https://github.com/go-to-k/cdkd/issues/2319))** -- `src/types/deployment-events.ts`, `src/deployment/deploy-engine/update-replace.ts`, `update-in-place.ts`, and unit cases. When a provider lets AWS's own error escape, `deployments/{runId}.jsonl` recorded AWS's text as the event message, and AWS names the caller on an access denial. The recorder now writes the error class instead (for example `AccessDenied. Re-run with --verbose for AWS's own message.`), next to the `awsErrorCode` and `requestId` it already kept. The same applies to the `--recreate-via-*` destroy failure, the create-first collision refusals of a replacement, and the create failure after the update-not-supported fallback: each names an AWS-authored failure by its class, with AWS's text in the debug log through the same secret masker and on the error's `cause`. A cdkd-authored or transport error keeps its text. Two refusals get the same treatment: the `--strict-getatt` output refusal, and the refusal of an AWS CDK-generated cross-account `Fn::GetStackOutput` whose lookup role was denied. The lookup role's ARN stays in that message. `cdkd events` also stops printing the class twice on such a row.
