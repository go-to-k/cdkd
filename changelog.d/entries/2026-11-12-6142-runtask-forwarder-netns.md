- **`cdkd local run-task` under a loopback AWS endpoint starts each container inside a forwarder that is already up, so its first AWS call no longer races the forwarder (issue [#6142](https://github.com/go-to-k/cdkd/issues/6142))** -- `src/local/ecs-task-runner.ts`, `ecs-task-runner/docker-run-args.ts`, `ecs-task-runner/loopback-forwarder.ts`, `ecs-task-runner/cleanup.ts`; cdk-local's `buildNamespaceOwnerForwarderDockerArgs` (`cdk-local` bumped to ^0.162.0). **Behavior change:** with `--aws-emulator` or a forwarded `AWS_ENDPOINT_URL*` on loopback, the forwarder starts FIRST on the task network carrying the container's network aliases, `-p` publishes, `--add-host` mappings and `--link`s, and the container joins it with `--network container:<forwarder>` once it reports READY (before: it attached just after `docker run`, so an essential container calling AWS at once could fail with `connection refused` and exit unexplained). Teardown removes the forwarders after the containers; `--keep-running` keeps those a container joined (one whose container never started is removed); `--detach` prints both sets of names, because `docker ps --filter network=<name>` lists only the forwarders. A forwarder failure under `--aws-emulator` now stops the task before any container starts; under a forwarded endpoint it is the same once-per-port warning, and the container starts on its own network endpoint. Under `--aws-emulator`, a forwarder whose `docker run` fails (e.g. a published host port already in use, now bound by the forwarder) is reported as that container's `docker run failed`. `start-service` / `start-alb` still attach after start.
