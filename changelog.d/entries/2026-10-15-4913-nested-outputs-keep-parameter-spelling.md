- **`cdkd diff --recursive --fail` no longer reports a change on an unchanged nested stack whose child `Outputs` read a parameter the parent spelled as a literal embedding `{{resolve:...}}` tokens beside a sibling parameter spelling the same secret differently (issue [#4913](https://github.com/go-to-k/cdkd/issues/4913)).** Before, no output was positioned per parameter, so cdkd fell back to the sibling's spelling for that parameter in the whole child (its resources included) while `cdkd diff --recursive` rendered the literal. Now the outputs redaction carries the outputs pass's parameter reads and the parent's per-parameter associations, so an output whose `Value` is a bare `Ref`, an `Fn::Select` / `Fn::Split` re-read, or an `Fn::Join` / `Fn::Sub` over the parameters (with at most one other non-literal part) persists each parameter's own spelling, and the collision check reads each output `Value` as it reads a resource. After upgrading, the first deploy of such a stack shows a change on those outputs, and on child resources reading the literal parameter that had taken the sibling's spelling; the deployed VALUE is unchanged, and a create-only property is replaced once with an identical value. A read the outputs redaction cannot position (under `Fn::If`, through `Fn::Sub` inside `Fn::Select`, inside a list-valued output, in an `Fn::Join` / `Fn::Sub` with two or more other non-literal parts, or in an `Export.Name`) keeps the old behaviour. `cdkd scrub` writes the same outputs. Source: `src/deployment/intrinsic-resolver/parameter-secrets.ts`, `src/deployment/deploy-engine/outputs.ts`.
