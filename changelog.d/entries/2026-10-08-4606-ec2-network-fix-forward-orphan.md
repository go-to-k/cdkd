- **A successful fix-forward deploy now deletes the VPC, subnet or security group an earlier failed CREATE left under the same logical id (issue [#4606](https://github.com/go-to-k/cdkd/issues/4606))** -- `src/provisioning/providers/ec2-provider.ts`. When an `AWS::EC2::VPC`, `AWS::EC2::Subnet` or `AWS::EC2::SecurityGroup` CREATE failed after AWS made the resource and its cleanup delete failed too, the resource was journaled as a proven orphan. If a later deploy created a new one under the same logical id, that successful deploy warned, named the earlier one, exited `2` and left it in place. `EC2Provider` now answers `isSameResource` for these types, using the AWS-generated `vpc-`, `subnet-` or `sg-` id. The client must be in the stack's region, and the record's resource must read back live (a VPC or subnet `pending` or `available`; a security group whenever EC2 lists it). The earlier resource is then `different`, whether it still exists or is not found, so the settle deletes it. Equal ids are `same`. Any other id form and a failed read stay `unknown`, which keeps the previous warning and exit `2`. An earlier resource EC2 no longer lists is named in one info line. Tests: `tests/unit/provisioning/ec2-network-same-resource-4606.test.ts`. Integ `ec2-instance` Phase 1c runs the read and the settle's delete against live resources, a throwaway VPC / subnet / security group and ids that never existed.
