- **A `--assume-role` / `--ecr-role-arn` ARN can no longer redraw your terminal from a `cdkd local` failure message (go-to-k/cdkd#3390 security review, a sibling class of issue [#3377](https://github.com/go-to-k/cdkd/issues/3377))** -- `src/cli/commands/local-invoke.ts`, `local-invoke-agentcore.ts`, `local-run-task.ts`, `local-start-api.ts`, `src/local/ecr-puller.ts`; 11 sites. `src/utils/role-arn.ts` has rendered its own ARNs through `displaySafe` since issue [#2170](https://github.com/go-to-k/cdkd/issues/2170); the `cdkd local` copies never adopted it, and `ConsoleLogger.formatMessage` sanitizes only a call's EXTRA ARGS, so a message's own text was raw. This is the WIDER boundary of the two values on those lines: `resolveAssumeRoleArn` can source the ARN from a DEPLOYED STATE RECORD rather than from argv, and nothing validates it before the STS call whose failure prints it. A legitimate ARN's characters are all plain, so every existing line renders byte-identically. The SDK error message interpolated beside it takes `displaySafe` too, and that one is not symmetry: STS answers an unparseable RoleArn with a `ValidationError` that ECHOES THE SUBMITTED VALUE VERBATIM, so the attacker-controlled ARN came back through the error string onto the very line the ARN guard protects. Two sites are left raw deliberately -- a `encodeURIComponent`'d credentials URI and a cache key, neither of which is displayed. The deploy-path copies in `src/deployment/intrinsic-function-resolver.ts` are a separate surface, tracked separately.
