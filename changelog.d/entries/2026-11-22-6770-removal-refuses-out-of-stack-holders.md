- **A deploy that removes an IAM role or group refuses an instance profile or user outside the stack still holding it, instead of stripping it (issue [#6770](https://github.com/go-to-k/cdkd/issues/6770))** -- `src/provisioning/region-check.ts` (`DeleteContext.stackHoldersStillAttached`), `src/provisioning/providers/iam-role/delete.ts`, `src/provisioning/providers/iam-user-group/group.ts`, the delete-first sites that set the field, `docs/cli-destroy-guards.md`, the `iam-role-refuse-out-of-stack-profile-6750` / `iam-group-refuse-out-of-stack-members-6750` unit suites, and a removal arm in the `iam-role-prefixed-name-update` integ. #6750 refused these on `cdkd destroy` only. A deploy's template removal, its teardown of a removed nested stack, a replaced role's or group's cleanup-phase delete and a rollback's delete of a created copy still removed the role from every instance profile, or every user from the group, before the delete, including ones the stack did not create; CloudFormation's delete handler holds no `iam:RemoveRoleFromInstanceProfile` / `iam:RemoveUserFromGroup`, so there the delete fails with `DeleteConflict`. Those deletes now refuse as the destroy does, naming the holders and saying to run the command again once they are removed. Only a same-name re-create's delete-first (`--recreate-via-*`, `--replace`'s delete-first and update fallback, a rollback's delete-new-first) and the role provider's own old-role delete in a `RoleName` update still remove the holders, since the stack's own profile or membership adds the new copy back (#4461).
