- **A CDK Stage whose cloud assembly cannot be read now stops every command, as in the AWS CDK CLI (issue [#3507](https://github.com/go-to-k/cdkd/issues/3507))** -- `src/synthesis/assembly-reader.ts` and `src/synthesis/failed-stages.ts` (`stageLoadError`), with the selection-time handling removed from `src/cli/stack-matcher.ts` and `src/cli/commands/deploy.ts`, `destroy.ts`, `diff.ts`, `publish-assets.ts`, `scrub.ts`, `import.ts`, `export.ts`, `orphan.ts`, `list.ts` and `synth.ts`; unit tests in `tests/unit/synthesis/assembly-stage-refusal.test.ts` and beside each command, and `tests/integration/stage-assets` Phases 2b and 2g. A Stage whose own `manifest.json` could not be read was tolerated: its stacks silently left the synthesized app, and a run then acted on the stacks that did load. That tolerance needed a refusal per selection -- `--all`, no stack named, a wildcard -- and this replaces those refusals, and the failed-Stage note appended to "no stacks matching", with one synthesis error, `Stage <path> failed to load: <reason>. ...`, raised before any stack is selected or any state is read, whatever was named. `cdkd destroy` no longer falls back to state for an exact name in that case, and its error names `cdkd state destroy '<stack>'`, which needs no app. `cdkd scrub` refuses with exit 2 (`SCRUB_STAGE_LOAD_FAILED`), replacing the `SCRUB_ALL_PARTIAL_APP` / `SCRUB_AUTO_PICK_PARTIAL_APP` codes. The exported `SynthesisResult.failedStages` and `AssemblyContents.failedStages` fields are removed. Separately, `cdkd destroy` now warns about each pattern that matched nothing, as the AWS CDK CLI's destroy does, and about a name in state that is not a stack of this app.
