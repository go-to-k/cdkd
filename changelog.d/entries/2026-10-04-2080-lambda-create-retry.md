- **A Lambda layer version or event source mapping create that hits a 5xx now reports candidate orphans instead of duplicating silently (issue [#2080](https://github.com/go-to-k/cdkd/issues/2080), Plan C: Lambda; #3978 layer (b) for these two creates)** -- `src/provisioning/providers/{lambda-layer,lambda-eventsource}-provider.ts`, `docs/troubleshooting.md`. `PublishLayerVersion` and `CreateEventSourceMapping` mint their id and carry no idempotency token, so a 5xx whose request had succeeded left a second layer version or mapping with no state record -- and, when the AWS SDK replayed it inside one call, nothing reported it. These creates no longer let the SDK retry a 5xx; the 5xx reaches cdkd's retry, which first lists what the failed attempt may have made and warns: a version of the same layer published during that attempt (a read command, then `delete-layer-version` to run only after confirming), or a mapping between the same function and source that this deploy did not record and that was not last modified before the attempt (a read command only: Lambda reports no creation time for a mapping). Nothing is adopted or deleted. Where Lambda refuses a second mapping for the same function and source (an SQS queue), the replayed create then fails naming the orphan's UUID instead of duplicating it. A throttle, a 4xx or IAM propagation triggers no lookup. The lookup needs `lambda:ListLayerVersions` / `lambda:ListEventSourceMappings`; without it cdkd warns and the create proceeds. A reset connection or timeout after the send is still retried inside the SDK and not reported. Tests: `tests/unit/provisioning/lambda-create-retry-2080.test.ts`.
