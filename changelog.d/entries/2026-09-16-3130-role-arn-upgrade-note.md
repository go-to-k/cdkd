- **UPGRADE NOTE for anyone already combining `--profile` with `--role-arn` (issue [#3130](https://github.com/go-to-k/cdkd/issues/3130))** -- `docs/cli-reference.md`, `docs/cross-stack-internals.md`, `docs/troubleshooting.md`; the behaviour they document comes from `src/utils/aws-client-defaults.ts` and `src/utils/role-arn.ts`. Now that cdkd genuinely runs as the role rather than as the profile, three things move on the first run after upgrading, all of them the same correction seen from different places. (1) The default state bucket follows the identity, so it is the ROLE account's -- copy the state across before the first deploy; `--state-bucket` cannot point back at the profile account's bucket, because `ExpectedBucketOwner` rejects it. (2) A cross-account `Fn::GetStackOutput` assumes the producer role AS the assumed role, so the PRODUCER role's trust policy has to name the `--role-arn` role rather than the profile's principal -- until it does, the first deploy resolving such a reference fails with `AssumeRole into <producer> failed: AccessDenied`, which names the producer role and not the principal that changed. (3) `CDK_DEFAULT_ACCOUNT` becomes the role's account, which is correct (it is where the stack is deployed), while the CDK app's OWN context lookups -- `Vpc.fromLookup` and friends -- still resolve the profile, so a cross-account run can synthesize for one account and look up in another. The remedy for both (2) and (3) is the same: name the role in the trust policy, or drop `--profile` (pass `--region` and let `--role-arn` supply the identity alone). `docs/cli-reference.md` carries all three.
