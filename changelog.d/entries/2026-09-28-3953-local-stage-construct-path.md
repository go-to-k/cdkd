- **`cdkd local invoke`, `local run-task` and `local start-api` resolve a construct-path target in a stack under a CDK Stage (issue [#3953](https://github.com/go-to-k/cdkd/issues/3953))** -- `src/local/lambda-resolver.ts`, `src/local/ecs-task-resolver.ts`, `src/cli/commands/local-start-api.ts`, with the stack lookup shared from `src/cli/cdk-path.ts`; unit tests in `tests/unit/local/{lambda,ecs-task}-resolver.test.ts` and `tests/unit/cli/local-start-api-pick-target-stacks.test.ts`, and a new local-only fixture `tests/integration/local-invoke-stage` (a nested Stage beside a top-level stack). A path-form target took its FIRST `/`-segment as the stack pattern, so a stack inside a `Stage` -- whose display path is `MyStage/Api`, or `Outer/Inner/Api` nested -- was unreachable: `cdkd local invoke MyStage/Api/Fn` answered `Stack 'MyStage' not found`, and `local start-api MyStage/Api/HttpApi` selected no stack. The stack is now the one whose display path (or physical name) followed by `/` is the longest prefix of the target -- the rule `cdkd orphan` adopted in [#3943](https://github.com/go-to-k/cdkd/issues/3943) -- so a nested Stage resolves and `MyStage/Api` never claims `MyStage/ApiV2/...`. `local run-task` picks the stack whose state feeds `--from-state` / `--from-cfn-stack` by the same rule, and `local start-api` selects the matched stack itself rather than re-matching its physical name. A head no stack path prefixes, such as a wildcard, still goes through the stack matcher, and the `Stack:LogicalId` form keeps the stack it names. `local start-service`, `start-alb`, `start-cloudfront` and the agentcore commands resolve targets in cdk-local, tracked by [go-to-k/cdk-local#746](https://github.com/go-to-k/cdk-local/issues/746).
