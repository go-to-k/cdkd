- **`--remove-protection` no longer stalls two minutes per resource when the network is down (issue [#3253](https://github.com/go-to-k/cdkd/issues/3253))** -- `src/provisioning/cloud-control-provider.ts`. The Cloud-Control deletion-protection flip (`AWS::DSQL::Cluster`, `AWS::EKS::Cluster`, `AWS::RDS::GlobalCluster` and their siblings) polls its own `UpdateResource` through `waitForOperation`, so it inherited the transport-retry grace [#3236](https://github.com/go-to-k/cdkd/issues/3236) added -- two minutes of re-polling before giving up. That is dead wall clock there: the flip is best-effort by construction and every failure is swallowed, the `DeleteResource` that follows surfaces the real error if the protection is still on, and under the same outage that delete fails too. It now takes a 10-second grace instead, long enough to ride out the blip the retry exists for (the 1s -> 1.5s -> 2.25s -> 3.4s schedule fits inside it) and short enough that a `cdkd destroy --remove-protection` against a dead link fails in seconds rather than minutes per protected resource. The grace is a per-call argument to `waitForOperation` defaulting to the two-minute value, so every provisioning call site is unchanged and a new one has to say why it differs. When the flip IS abandoned, the swallowed warning carries the request token and the `aws cloudcontrol get-resource-request-status` line -- it always did, since the abandonment error builds them in; what this changes is only how long the user waits to see it. That warning also stopped quoting the caller back: it runs at DEFAULT verbosity, and AWS words a rejected flip as `User: arn:aws:sts::<acct>:assumed-role/<role>/<session> is not authorized to perform: ...`, so a role lacking the update permission printed the account id, role and session name into the terminal and into any CI log. It now carries the wire name, with the full sentence at `debug`.
