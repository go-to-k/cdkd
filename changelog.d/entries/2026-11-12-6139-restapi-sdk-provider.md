- **`AWS::ApiGateway::RestApi` is deployed through the API Gateway SDK instead of Cloud Control (issue [#6139](https://github.com/go-to-k/cdkd/issues/6139))** -- `src/provisioning/providers/apigateway/rest-api.ts`. A REST API is now created with one synchronous `CreateRestApi` (or `ImportRestApi` for a `Body` / `BodyS3Location` definition) instead of a polled Cloud Control create, which sat at the root of every `RestApi` / `LambdaRestApi` stack's critical path. It also deploys against AWS Emulator, whose Cloud Control answered an unusable identifier for the API. Updates follow CloudFormation, measured against its handler: a changed `Name` renames the API in place (it was a replacement before), a changed body is put in `overwrite` mode unless `Mode` says otherwise, and removed properties keep or clear their live value as CloudFormation does. `cdkd drift` now reads the API back through `GetRestApi`, skipping the write-only `Body` / `BodyS3Location` inputs instead of reporting the whole resource as drift unknown. A REST API already recorded as created by Cloud Control stays on Cloud Control. The template's `BinaryMediaTypes` are merged with the ones an OpenAPI definition declares, as CloudFormation merges them. `CreateRestApi` / `ImportRestApi` (one call every 30 seconds per account for an edge-optimized API, every 3 seconds for a Regional or private one), `PutRestApi` (one per second) and `DeleteRestApi` (one every 30 seconds) are paced at API Gateway's limits, so a stack with several REST APIs is not throttled on deploy or destroy. A `Body` embedding a `NoEcho` parameter value is not put again when it differs from the record only at that value, since cdkd records the value only as `***`: the deploy warns that a change to that value alone is not applied (a salted witness to compare it is [#6146](https://github.com/go-to-k/cdkd/issues/6146)).
