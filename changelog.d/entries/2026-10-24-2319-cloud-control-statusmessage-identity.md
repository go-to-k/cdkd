- **A failed Cloud Control create, update or delete keeps the handler's message but no longer writes the caller's principal ARN or account id into the persisted deployment events (issue [#2319](https://github.com/go-to-k/cdkd/issues/2319))** -- `src/provisioning/cloud-control-provider.ts` and `tests/unit/provisioning/cloud-control-statusmessage-identity-2319.test.ts`. The handler's `StatusMessage`, and the text of a rejected `CreateResource` / `UpdateResource` / `DeleteResource`, is what a user fixes the template from (`Property validation failure: ...`), so it stays in the message. A denial in it quoted the caller (`User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized ...`), and `deployments/{runId}.jsonl` outlives the run. Now an STS session ARN, an IAM user / role / root ARN in the denied-principal position, and a principal's unique id read `<caller-principal>`, and an account id in an ARN, a name, a path, a host, or after a word such as `account` reads `<account-id>`; a resource ARN keeps its service, region and name, and a free-standing 12-digit size or template value is kept. The unmasked text is printed at `--verbose`. Name-collision, retry, already-deleted and downstream-403 hint classification is unchanged.
