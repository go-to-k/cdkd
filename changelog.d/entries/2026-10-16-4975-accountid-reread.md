- **`cdkd diff --recursive --fail` no longer reports a change on an unchanged nested stack in which one child resource reads a parameter the parent spelled as a literal embedding `{{resolve:...}}` tokens beside a sibling parameter spelling the same secret differently, through an `Fn::Select` / `Fn::Split` / `Fn::If` over an `Fn::Sub` (or `Fn::Join`) naming `AWS::AccountId` (issue [#4975](https://github.com/go-to-k/cdkd/issues/4975)).** The #4962 fix left `AWS::AccountId` unbound in the nested-stack parameter re-read; it is now bound too. After upgrading, the first deploy of such a stack shows a change on the child resources reading the literal parameter, because their state now records the parameter's own `{{resolve:...}}` spelling instead of the sibling's; the deployed VALUE is unchanged, and a create-only property is replaced once with an identical value. The account comes from the same lookup and cache as `AWS::AccountId` itself, so every pass binds the same value whether or not the account was already known. That can add one STS `GetCallerIdentity` call per process, made only by a nested child that inherits parent secrets and has a resource naming `AWS::AccountId` beside an `Fn::Select` / `Fn::Split` / `Fn::If`, and only when the account is not yet known; any other stack makes no added call. If the lookup fails, the account stays unbound (the earlier behavior) and no new error is raised. Source: `src/deployment/intrinsic-resolver/{account-drain,parameter-secrets,params-conditions}.ts`, `src/deployment/secret-redaction/nested-stack.ts`.
