- **A Cloud Control-routed `AWS::RDS::DBCluster` or `AWS::RDS::DBInstance` no longer leaves an untagged final snapshot on every delete (issue [#3993](https://github.com/go-to-k/cdkd/issues/3993))** -- `src/provisioning/cloud-control-provider.ts`, `src/provisioning/providers/rds-provider.ts`, `src/provisioning/region-check.ts`, `src/cli/commands/destroy-runner.ts`, `src/deployment/deploy-engine.ts`. The RDS Cloud Control delete handlers take a final snapshot whenever the request does not say whether one is wanted, and Cloud Control never says, so every destroy of such a cluster or standalone instance left a manual `rds-snapshot-<random>` snapshot behind, even under `DeletionPolicy: Delete`. Under an explicit `DeletionPolicy: Delete`, `cdkd destroy`, `cdkd state destroy` and a deploy's removal delete now hand both types to the SDK `RDSProvider`, bound to the Cloud Control client's region, which deletes with `SkipFinalSnapshot=true` and waits up to 60 minutes for the resource to be gone. With no `DeletionPolicy` the Cloud Control delete and its snapshot stay, since CloudFormation's default for these types is `Snapshot` (issue [#4030](https://github.com/go-to-k/cdkd/issues/4030)); replacement and rollback deletes also stay on Cloud Control (issue [#4029](https://github.com/go-to-k/cdkd/issues/4029)). It also brings `--remove-protection` to these resources. A `DeleteAutomatedBackups` value in the template is sent with the delete, as CloudFormation sends it. `DeletionPolicy: Snapshot` on a Cloud Control-routed resource is still refused as before. A cluster that sets `GlobalClusterIdentifier` is still deleted through Cloud Control, because its handler removes the cluster from the global cluster first, and cdkd now warns that this delete leaves the snapshot. The `rds-aurora` and `rds-full-stack` integration fixtures now fail when a run leaves a manual snapshot of their Cloud Control-routed cluster or instance.
