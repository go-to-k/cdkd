- **`cdkd diff --recursive --fail` no longer reports a change on an unchanged nested stack whose parent passes a parameter embedding `{{resolve:...}}` tokens (e.g. `postgres://{{resolve:...user}}:{{resolve:...password}}@host`) beside a sibling parameter that spells the same secret differently and resolves later (issue [#4644](https://github.com/go-to-k/cdkd/issues/4644)).** After upgrading, the first deploy of such a stack shows a change on the nested-stack row's `Parameters.<Name>` and on the child resources reading it, because their state now records the parameter's own `{{resolve:...}}` spelling instead of the sibling's; the deployed VALUE is unchanged, and a create-only property (e.g. an ECS TaskDefinition environment variable) is replaced once with an identical value. For a one-token literal only those child resources change (its row already kept its own spelling), and only where such a sibling exists. Before, state held the map's survivor per plaintext while `cdkd diff --recursive` rendered the parameter's literal. A literal now persists its own spelling when rendering it with the plaintexts this pass resolved each token to reproduces the resolved value exactly and its literal text holds no secret; the child's diff side, its `{Ref}` leaves, its `Fn::Join` / `Fn::Sub` leaves and the inherited-secret carry (so `Fn::Select`, `Fn::Split`, arrays and `Fn::If` too) read it. An `Fn::Join` / `Fn::Sub` parent source, a literal holding a public `ssm` token, and a parameter that one child resource reads beside such a sibling, either of the two through an intrinsic other than `Fn::Join` / `Fn::Sub` (`Fn::Select`, ...), or that the child's `Outputs` read beside it, keep the old behaviour ([#4731](https://github.com/go-to-k/cdkd/issues/4731)). Source: `src/deployment/secret-redaction/{positions,nested-stack,placeholder-positions}.ts`, `src/deployment/intrinsic-resolver/parameter-secrets.ts`, `src/deployment/deploy-engine/deploy-flow.ts`, `src/cli/commands/scrub.ts`.
