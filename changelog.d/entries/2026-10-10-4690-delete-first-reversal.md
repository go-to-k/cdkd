- **A rollback reverses a delete-first replacement by deleting the new resource first (issue [#4690](https://github.com/go-to-k/cdkd/issues/4690))** -- `src/deployment/rollback-executor/replay-reverse-replacement.ts`, `src/deployment/deploy-engine/execute.ts`, `src/types/rollback-journal.ts`, `src/deployment/rollback-executor/types.ts`, plus tests and the `alb` integ's Phase 6. Before this change, when a `--recreate-via-cc-api` / `--recreate-via-sdk-provider` recreate (or the update-unsupported fallback, `--replace`'s delete-first fallback, or a child lost with its re-created parent) succeeded and a later operation in the same deploy failed, the rollback re-created the OLD resource while the NEW one still existed. For a resource only one copy of which can exist (an ELBv2 listener's port), the re-create collided, the rollback refused, and the user had to run `cdkd rollback --orphan`. The rollback journal now records, on every completed UPDATE, whether the deploy deleted the old resource before creating the new one (`oldDeletedBeforeCreate`, additive, no `journalVersion` bump). When it did, the rollback deletes the new resource first and then re-creates the old one. If that delete fails or is skipped, state keeps pointing at the new resource and the journal is kept. A journal written by an older cdkd, and a new resource kept by `UpdateReplacePolicy: Retain`, keep the create-first order, as does a resource whose old properties name another resource the same deploy replaced or deleted, which the rollback may not be able to restore under that id; its re-create never deletes the new resource first.
