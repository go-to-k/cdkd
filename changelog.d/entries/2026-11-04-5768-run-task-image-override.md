- **`cdkd local run-task` takes `--image-override` and its build flags, and runs a same-stack ECR image from a local build (issue [#5768](https://github.com/go-to-k/cdkd/issues/5768))** -- `src/cli/commands/local-run-task.ts`, `src/local/ecs-task-resolver.ts`, `src/local/ecs-task-runner.ts`, `docs/local-run-task.md`, `docs/local-run-task-images.md`, `docs/local-start-service-image-overrides.md`. `run-task` rejected `--image-override` as an unknown option, so a task whose image is a registry image always ran the pushed bytes, and an image from an `AWS::ECR::Repository` in the same stack could not run at all without `--from-state` / `--from-cfn-stack`. It now registers the same seven flags as `start-service` / `start-alb` (`--image-override`, `--image-build-arg`, `--image-build-secret`, `--image-target`, `--image-context`, `--no-interactive-overrides`, `--strict-overrides`) through cdk-local's override engine, and rebuilds the task's essential container from the given Dockerfile. A same-stack ECR image with no state is now a target the override can cover; left uncovered, the run stops before any network or container exists, with an error naming `--image-override`. In a terminal, a task whose image is a registry image now asks for a Dockerfile at startup, as `cdkl run-task` does; `--no-interactive-overrides` turns the question off. A `Fn::GetAtt` of the repository's `RepositoryUri` with no state is treated the same way instead of being refused as an unparseable image. Tests: `tests/unit/cli/local-run-task-image-override.test.ts`, `tests/unit/local/ecs-task-resolver.test.ts`, `tests/unit/local/ecs-task-runner-runner.test.ts`; integ: `local-run-task-from-state` step 10.
