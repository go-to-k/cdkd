- **An "already exists" from a provider's auxiliary create call no longer reads as the resource's own name collision (issue [#3826](https://github.com/go-to-k/cdkd/issues/3826))** -- `src/provisioning/auxiliary-failure.ts` (`markAuxiliaryFailure`), wired into the `create()` of the API Gateway (Stage, Method), AppSync GraphQL API, CloudTrail, CodeCommit, Cognito user pool, custom resource, EC2 (VPC, Subnet, EIP, SecurityGroup, Instance), ECR, EFS file system, ELBv2 (load balancer, target group, listener), EventBridge rule, IAM (role, user, group, instance profile, managed policy, access key), KMS key, Lambda function, log group, RDS proxy target group, S3 bucket, Cloud Map service, SNS topic and SSM parameter providers, with unit tests in `tests/unit/provisioning/auxiliary-failure-3826.test.ts`. A provider's `create()` makes calls besides the one that creates the resource -- a security-group rule, a concurrency setting, a subscription, a policy -- and when one of them failed with AWS's "already exists", the relayed text classified as the resource's collision: `--replace` deleted the live old resource, and a replacement rollback deleted the live new one, before the re-create failed again on the same auxiliary object. Such a failure is now anchored to a logical id no template can spell, which the collision classifier refuses; the error text is unchanged, and a collision on the main create still classifies. The providers whose files were held by other open work at the time are go-to-k/cdkd#3877.
