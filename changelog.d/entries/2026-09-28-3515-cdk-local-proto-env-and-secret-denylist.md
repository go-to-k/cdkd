- **`cdkd local invoke` / `start-api` / `invoke-agentcore` now deliver an env var named `__proto__`, and the `local start-*` engine commands refuse a secret named after a container-client variable, via cdk-local 0.149.7 (issue [#3515](https://github.com/go-to-k/cdkd/issues/3515))** -- `package.json` (`cdk-local` `^0.149.6` -> `^0.149.7`), `tests/integration/local-invoke/`, `tests/unit/cli/local-invoke-env-proto-key.test.ts`.
  - These commands resolve env vars through the bundled engine, which assigned each one onto a plain object, so a variable literally named `__proto__` (from `--env-vars`, either block) ran `Object.prototype`'s setter and never reached the container. It is delivered now (go-to-k/cdk-local#769); the same fix covers the engine's own env writes in `start-service` / `start-alb` / `start-agentcore` / `start-cloudfront`.
  - `start-service` / `start-alb` / `start-agentcore` / `start-cloudfront` now drop a sensitive env var or secret whose name is a variable the container client, the dynamic loader or a credential helper reads (`DOCKER_HOST`, `PATH`, `LD_PRELOAD`, ...) or is malformed (empty, or containing `=` / NUL), with a warning naming it, instead of writing it into the client's spawn env (go-to-k/cdk-local#772). The denylist is the one `cdkd local run-task` / `invoke` already apply, so `docs/local-run-task.md`'s "Secret names that are not forwarded" now holds for every `cdkd local` command.
