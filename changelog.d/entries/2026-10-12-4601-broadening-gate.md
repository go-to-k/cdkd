- **`cdkd diff --fail-on=broadening` and `cdkd deploy --require-approval=broadening` (issue [#4601](https://github.com/go-to-k/cdkd/issues/4601))** -- `src/analyzer/security-diff.ts` (new), `src/deployment/deployment-approval.ts`, `src/deployment/deploy-engine/options.ts`, `src/deployment/deploy-engine/deploy-flow.ts`, `src/cli/commands/{diff,diff-recursive,deploy,require-approval}.ts`, `package.json`. Both options were refused as invalid choices, and `"requireApproval": "broadening"` in `cdk.json` (the AWS CDK CLI's default) was ignored with a warning, so a deploy that `cdk` would stop for approval went ahead. Both now take `broadening`, decided by the AWS CDK CLI's own security diff (`@aws-cdk/cloudformation-diff`'s `permissionsBroadened`, now a direct dependency, loaded only at this level): an added IAM statement, managed-policy attachment, `AWS::Lambda::Permission` or security-group rule. `cdk.json`'s `broadening` is honoured, so such a deploy now asks, and without a terminal it fails unless `--yes`. The approval prompt and the `--fail-on` report print the CDK CLI's security table. A secret value is shown as `***` in the table; a masked policy or rule that changed counts as broadening, since it cannot be judged. With no deployed template, cdkd compares its state with the change, resolved as far as `cdkd diff` resolves it; a reference to a replaced resource is not a change. `--fail-on=broadening` walks nested stacks; under `--require-approval` each nested stack asks for its own changes. The default level stays `never`. Integ: `require-approval-broadening`. Tests: `tests/unit/analyzer/security-diff.test.ts`, `tests/unit/deployment/deployment-approval-broadening-cost.test.ts`, `tests/unit/cli/diff-broadening-secrets-4601.test.ts` (new), `tests/unit/cli/{diff-fail-on,require-approval}.test.ts`, `tests/unit/deployment/{deployment-approval,deploy-engine-require-approval}.test.ts`.
