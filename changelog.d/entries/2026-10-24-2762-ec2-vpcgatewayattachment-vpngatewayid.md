- **The SDK provider attaches a VPN gateway to a VPC itself: `AWS::EC2::VPCGatewayAttachment.VpnGatewayId` (issue [#2762](https://github.com/go-to-k/cdkd/issues/2762))** -- `src/provisioning/providers/ec2-provider.ts`, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, a new unit file, the physical-id rows in `docs/import-resource-types.md` / `docs/state-management-physical-ids.md` / `docs/state-schema-internals.md`, and a new VPN gateway arm in the `ec2-route-targets` integ. Before, an attachment naming `VpnGatewayId` routed through Cloud Control. It now sends `AttachVpnGateway` and waits for the attachment to be `attached`, so a route through the gateway can be created next. The record is `<vgwId>|<vpcId>`. Destroy sends `DetachVpnGateway` and waits for `detached`, because AWS refuses to delete the VPN gateway or the VPC until then. Drift reads the attachment with `DescribeVpnGateways`. `--migrate-from-cloudformation` and `cdkd import` now adopt a CloudFormation `VGW|<vpcId>` attachment. A template naming both `InternetGatewayId` and `VpnGatewayId`, or neither, is refused before any AWS call: CloudFormation's documentation allows exactly one of the two. Changing `InternetGatewayId` / `VpnGatewayId` now swaps the attached gateway in place, as CloudFormation does (issue [#5216](https://github.com/go-to-k/cdkd/issues/5216)). Before, it was refused, and `--replace` could not help because AWS allows one gateway of each kind per VPC. A record naming only the attachment type (`VGW|<vpcId>`) resolves its gateway from the VPC. An attachment Cloud Control already created stays on Cloud Control.
