- **A deploy that only changes a resource's `DependsOn` now updates that resource's recorded dependencies, so reversing an explicit dependency no longer blocks `cdkd destroy` with a circular-dependency error (issue [#6308](https://github.com/go-to-k/cdkd/issues/6308))** -- `src/deployment/deploy-engine/record-shape.ts` (`withTemplateDependencies`), `execute.ts`, `deploy-flow/no-change.ts`. The diff does not compare `DependsOn`, so such a resource stays unchanged and is never sent to its provider; before, its state record kept the dependency list an older template wrote. A reversed `node.addDependency` then left both directions recorded and `cdkd destroy` refused (with or without the cloud assembly), and a dependency on a resource the update deleted printed `Resource X depends on Y, but Y not found in template` on every destroy. Every successful deploy now writes the deployed template's dependencies onto each record the template still declares, unchanged ones included, without a provider call (in a nested stack an unchanged record only drops the ids its template no longer lists, since a failed parent reverts the child's updated records); a deploy with no resource change saves state when a list moved, so redeploying heals a stack already in that state. A failed deploy's saves keep the old lists. Tests: `tests/unit/deployment/deploy-engine-dependencies-refresh-6308.test.ts`; integ fixture `tests/integration/depends-on-flip/`.
