- **`VectorIndexes` on `AWS::DynamoDB::Table` / `AWS::DynamoDB::GlobalTable` now reaches AWS instead of being dropped with a warn (PR [#3167](https://github.com/go-to-k/cdkd/pull/3167))** -- `tests/fixtures/cfn-schemas/AWS-DynamoDB-Table.json`, `tests/fixtures/cfn-schemas/AWS-DynamoDB-GlobalTable.json`, `tests/fixtures/cfn-schemas/_todo-backfill.json`, `src/provisioning/property-coverage.generated.ts` (regenerated). The daily schema refresh picked the property up from AWS's public CloudFormation bundle, along with its nested `VectorIndex` / `VectorAttribute` / `SearchSchemaElement` definitions. Before this, `VectorIndexes` post-dated the committed fixture snapshot, so deploy-time pre-flight read it as UNRECOGNIZED: `reportUnrecognizedProperties` warned and the SDK provider dropped it while the deploy reported success (the issue [#614](https://github.com/go-to-k/cdkd/issues/614) failure class that machinery cannot observe). It is now a `silentDrop` entry on both types -- neither SDK provider writes it (`not yet implemented by cdkd`) -- so the #614 auto-route applies instead: a template carrying it moves that resource onto Cloud Control, which forwards the full property map, and the value reaches AWS. It is not create-only on either type, so `createOnlyDrops` and the record narrowing are unchanged. Both types also enter the standing backfill checklist, which is regenerated from `main` on merge. `AWS::BedrockAgentCore::Browser` and `AWS::BedrockAgentCore::CodeInterpreter` have no entry in the public bundle and keep the authenticated `DescribeType` path as their only refresh route; they were left untouched.
