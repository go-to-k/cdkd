- **Two copies of one stack in an account and region get their own FSx and EFS file systems and CloudFront origin access identities (issue [#4428](https://github.com/go-to-k/cdkd/issues/4428))** -- `src/provisioning/providers/{idempotency-token,fsx-filesystem-provider,efs-provider,cloudfront-oai-provider}.ts`. The FSx `ClientRequestToken`, EFS `CreationToken` and OAI `CallerReference` came from the logical id (and create-only properties) only, so a Dev and a Staging copy sent the same token: FSx and CloudFront handed the second copy the FIRST copy's resource, which its `cdkd destroy` then deleted, and EFS refused the second deploy. All three now cover the stack name and region, stay stable across retries and runs of one stack, and fit the APIs' length limits. A create takes a handed-back or named file system only when it was created after the create's first send, judged on AWS's clock (the response `Date`), so a fast host clock does not refuse ordinary creates: EFS adopts its own lost-response retry (which used to fail), and a file system an earlier destroy kept is refused with its id and an inspect command instead of being recorded, and so later deleted. **If you deployed stack copies with an earlier cdkd, compare their state files for a shared FSx `FileSystemId` or OAI id before destroying either.** Re-running an INTERRUPTED deploy now refuses the FSx file system the interrupted run made, as EFS already did, naming it with an inspect command: import it into the stack or delete it, then deploy again ([#4438](https://github.com/go-to-k/cdkd/issues/4438) tracks adopting it). A create interrupted under an earlier cdkd sends the new token and so creates a fresh resource.
