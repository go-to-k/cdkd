- **A rollback no longer re-creates the old resource of a replacement a provider made inside its own update when that provider could not delete it (issue [#4911](https://github.com/go-to-k/cdkd/issues/4911))** -- `src/deployment/deploy-engine/update-in-place.ts`. A provider that replaces a resource inside `update()` (an `AWS::CertificateManager::Certificate` whose `ValidationMethod` changes; also the IAM role, IAM managed policy and API Gateway resource providers) and whose delete of the old one failed or was skipped reports a partial update. The deploy journaled that operation without the #2631 survivor mark, so when a later resource of the same deploy failed, the rollback re-created the old resource while it was still there: a duplicate certificate, for example, when ACM refused the delete because a load balancer or CloudFront distribution still used it. The operation is now journaled with `oldResourceMaySurvive`, from the provider's own verdict on the old resource: `kept` when the ACM or API Gateway provider proves AWS refused the delete outright (by AWS error name, ACM's in-use refusal included) or never sent it, `unconfirmed` otherwise, and always for the IAM role and managed policy, whose delete strips them before the refused call. The rollback reads AWS for the old resource first: re-created when AWS reports it gone, re-adopted when it is still there and `kept` (the replacement is deleted, as CloudFormation would), otherwise refused with the journal kept and `cdkd rollback --orphan` offered (the refusal now also names a delete that only partly ran). Providers also changed: `acm-certificate-provider.ts`, `apigateway-provider.ts`, and `src/types/resource.ts` (`oldResourceSurvivor` on a partial update). The deliberate `UpdateReplacePolicy: Retain` survivor of the update-unsupported fallback is still recorded as retained, and an ordinary deploy makes no extra AWS call.
