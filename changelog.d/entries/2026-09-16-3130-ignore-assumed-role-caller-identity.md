- **`ignoreAssumedRole` now genuinely resolves the CALLER's identity, so the `cdkd local` opt-out is no longer a no-op without a profile (issue [#3130](https://github.com/go-to-k/cdkd/issues/3130))** -- `src/utils/aws-client-defaults.ts`, `src/utils/role-arn.ts`, `tests/unit/utils/aws-client-defaults-assumed-role.test.ts`, `tests/unit/utils/aws-client-defaults-chain-logger.test.ts`, `tests/unit/utils/role-arn.test.ts`, `tests/unit/local/ecs-secrets-resolver.test.ts`. `awsClientDefaults({ ignoreAssumedRole: true })` returned `{}` with no proxy configured, so the client fell through to the SDK's own chain -- whose FIRST link reads the very `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN` triple `applyRoleArnIfSet` had just overwritten with the role. Only the `--profile` shape was safe, because `credential-provider-node` skips that link once a profile is named. So with `--role-arn` and no profile, `cdkd local run-task` / `invoke` / `start-api` resolved ECS SecureString and Secrets Manager PLAINTEXT as the deploy role and injected it into the user's container, took the `--assume-role` STS hop as the deploy role (a container could receive a role its caller could not assume), and reported the role's account as the emulated `${AWS::AccountId}`. The opt-out now answers in three shapes: a selected profile is left to the SDK chain, a caller that had a static triple gets the pre-assume snapshot back, and a caller with neither (SSO, an instance or container role) gets its real chain with the environment link EXCLUDED. A second `applyRoleArnIfSet` is now refused BEFORE its `sts:AssumeRole` rather than after. That shape-3 chain also drops `credential-provider-node`'s `Multiple credential sources detected` warning -- false for a triple cdkd itself wrote -- while forwarding every other warning.
