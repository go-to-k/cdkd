- **Reversing a replacement no longer deletes the new resource when something else holds the name the old one needs (issue [#3979](https://github.com/go-to-k/cdkd/issues/3979))** -- `src/deployment/replacement-name-holder.ts` (`reverseReplacementNewHoldsName`) and `src/deployment/rollback-executor.ts`, with unit tests in `tests/unit/deployment/rollback-reverse-replacement-name-holder.test.ts` and `reverse-replacement-name-holder.test.ts`. When a rollback re-created the old resource of a replacement and the create reported the name as taken, cdkd deleted the NEW resource first to free the name. If the name was actually held by something else -- a resource an earlier failed attempt left behind (re-running `cdkd rollback` after a Kinesis stream's partial create), a replayed create, or a resource made outside the stack -- that deleted a live resource that never held the name, and the re-create collided again. cdkd now deletes the new resource only when its state record shows it holds that name: the same name property, spelled exactly alike except where the service ignores case (IAM, RDS), and the same parent (the event bus of a rule, the database of a Glue table, the cluster of an ECS service), or for a Route 53 record the same DNS name in the same hosted zone. Otherwise, and whenever it cannot tell (no requested name, a redacted one, a type with no known name property such as a nested stack, or a `Type` change between types that do not share names), the operation fails with the colliding name in the message, nothing is deleted, and the journal is kept. The `cdkd deploy --replace` path without an explicit name is not covered yet (#3979).
