- **Reversing a replacement no longer deletes the new resource when something else holds the name the old one needs (issue [#3979](https://github.com/go-to-k/cdkd/issues/3979))** -- `src/deployment/replacement-name-holder.ts` (`reverseReplacementNewHoldsName`) and `src/deployment/rollback-executor.ts`, with unit tests in `tests/unit/deployment/rollback-reverse-replacement-name-holder.test.ts` and `reverse-replacement-name-holder.test.ts`. When a rollback re-created the old resource of a replacement and the create reported the name as taken, cdkd deleted the NEW resource first to free the name. If the name was actually held by something else -- a resource an earlier failed attempt left behind (re-running `cdkd rollback` after a Kinesis stream's partial create), a replayed create, or a resource made outside the stack -- that deleted a live resource that never held the name, and the re-create collided again. cdkd now deletes the new resource only when it can show that the new resource holds that name. An explicit name must match the new resource's recorded name (spelled exactly alike except where the service ignores case, such as IAM and RDS) under the same parent (the event bus of a rule, the database of a Glue table, the cluster of an ECS service), or be named by its physical id. For a Route 53 record, the DNS name and hosted zone must match. A name cdkd generates is proven only through the new resource's physical id, and only where cdkd knows the generated name exactly. IAM roles, users, groups, instance profiles and managed policies, and ELBv2 load balancers and target groups, rewrite even an explicit name before sending it (a stack prefix, a character rewrite). For those, cdkd derives the name this re-create actually sent and accepts only a physical id naming it. Otherwise, and whenever it cannot tell (no name it can derive, a redacted or empty one, a type with no known name property such as a nested stack, or a `Type` change between types cdkd does not know to share names), the operation fails with the colliding name in the message, nothing is deleted, and the journal is kept. If the holder is the new resource itself, deleting it by hand and re-running `cdkd rollback` proceeds. The `cdkd deploy --replace` path without an explicit name is left for a follow-up (#3979).
