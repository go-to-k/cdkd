- **Reversing a replacement no longer deletes the new resource when something else holds the name the old one needs (issue [#3979](https://github.com/go-to-k/cdkd/issues/3979))** -- `src/deployment/replacement-name-holder.ts` (`reverseReplacementNewHoldsName`) and `src/deployment/rollback-executor.ts`. When a rollback's re-create of the old resource reported the name as taken, cdkd deleted the NEW resource first. If something else held the name (a resource an earlier failed attempt left behind, a replayed create, or one made outside the stack), that deleted a live resource and the re-create collided again. cdkd now deletes the new resource only when it can show the new resource holds that name: the same explicit name recorded under the same parent (case ignored only where the service ignores it, such as IAM and RDS), or a physical id naming it; for a Route 53 record, the same DNS name in the same hosted zone. A generated name is proven only through the physical id, and only where cdkd knows it exactly. IAM roles, users, groups, instance profiles and managed policies, and ELBv2 load balancers and target groups rewrite even an explicit name before sending it, so for them only a physical id naming the name this re-create actually sent counts. Otherwise, and whenever cdkd cannot tell, the operation fails naming the colliding name, nothing is deleted, and the journal is kept; if the holder is the new resource itself, deleting it by hand and re-running `cdkd rollback` proceeds. The `cdkd deploy --replace` path without an explicit name is left for a follow-up (#3979).
