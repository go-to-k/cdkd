- **`cdkd deploy`: a DynamoDB table's `TableClass` change in the same deploy as a `BillingMode` or capacity change succeeds (issue [#6995](https://github.com/go-to-k/cdkd/issues/6995))** -- `src/provisioning/providers/dynamodb-table/update-billing.ts`. A `dynamodb.Table` moved to `TableClass.STANDARD_INFREQUENT_ACCESS` and to provisioned capacity (or another capacity) in one edit failed the deploy with `ValidationException` (`TableClass modification must be the only operation in the request`) and rolled back, because cdkd sent both in one `UpdateTable`. cdkd now sends the class change in its own call after the billing call settles, as CloudFormation completes the update. When that second call fails and the update is retried, a change the table already holds (the billing mode and capacity, or the class) is not sent again, so the error names the real cause (for example, DynamoDB's limit of two class changes in 30 days) rather than `The provisioned throughput for the table will not change`. Tests: `tests/unit/provisioning/dynamodb-table-provider-table-class-own-call-6995.test.ts`; integ `dynamodb-tableclass-switch` (`CombinedTable`).
