- **A Glue `CatalogId` change is refused instead of updating the same-named resource in another Data Catalog (issue [#3756](https://github.com/go-to-k/cdkd/issues/3756))** -- `refuseCatalogMove` in `src/provisioning/providers/glue-provider.ts`, called from `GlueProvider.updateDatabase` / `updateTable` and `GlueConnectionProvider.update`; unit tests in `tests/unit/provisioning/providers/glue-provider.test.ts`; phase 2d of the `glue-update-hardening` fixture. Each update sent the template's `CatalogId` while the state record names only the resource, so a changed catalog addressed the same-named database, table or connection in the other catalog. `CatalogId` is not createOnly on `AWS::Glue::Database`, so every such edit took that path; Table and Connection took it when the createOnly lookup degraded. The update now fails before any Glue call with a `ResourceUpdateNotSupportedError` naming both catalogs, and `cdkd deploy --replace` (plus `--force-stateful-recreation` for a table or database) moves the resource. An absent `CatalogId`, the `AWS::AccountId` pseudo parameter and the caller's own account id count as one catalog, so switching a database between them still updates in place (one `sts:GetCallerIdentity` call). `readCurrentState` now carries the recorded `CatalogId` back, so `cdkd drift --revert` updates the entity in the catalog it was read from rather than this account's default one.
