- **A custom resource whose Update answers a new `PhysicalResourceId` now gets a `Delete` for its old id (issue [#6117](https://github.com/go-to-k/cdkd/issues/6117))** -- `src/deployment/deploy-engine/replacement/cleanup-old-id.ts`, `src/deployment/deploy-engine/update-in-place.ts`, `src/provisioning/providers/custom-resource/create-update.ts`, plus a new `custom-resource-physid-replace` integ. Before, cdkd logged `Resource <id> was replaced: <old> -> <new>` and never sent the old id a `Delete`, so whatever the handler created under it was orphaned, and `cdkd destroy` later deleted only the new id. Like CloudFormation's cleanup phase, cdkd now sends the handler `RequestType: Delete` for the old id, with the old properties, once every other change of the deploy succeeded. A failed deploy sends nothing, so its rollback finds the old id as the update left it. Until the Delete is sent the old id is kept in state, so a deploy killed first leaves it for the next deploy or `cdkd destroy`; a record holding a masked `NoEcho` value is not kept, since only the running deploy can re-resolve it. A `Delete` the handler does not complete warns naming the old id and does not fail the deploy; the row counts as partially updated (exit `2` unless `--allow-unaddressed`), as for any replaced resource whose delete is skipped. `UpdateReplacePolicy: Retain` keeps the old id and sends nothing.
