- **A failed IAM user, IAM group, IAM UserToGroupAddition, IAM inline policy or IAM instance profile create, update or delete no longer writes the caller's account id, assumed-role ARN and session name into the persisted deployment events (issue [#2319](https://github.com/go-to-k/cdkd/issues/2319))** -- `src/provisioning/providers/iam-user-group-provider.ts`, `iam-policy-provider.ts`, `iam-instance-profile-provider.ts`, and unit cases. The thrown message quoted AWS's raw text, which names the caller on an access denial, and `deployments/{runId}.jsonl` outlives the run. The message now carries the error class (`AccessDenied. Re-run with --verbose for AWS's own message.`), and AWS's text goes to the debug log, masked through the operation's secret masker; the instance profile, inline policy and UserToGroupAddition delete messages now go through that masker too. A cdkd-authored or transport error keeps its text. The AWS error stays as the `cause`, so an IAM grant that is still propagating is retried as before and a taken user, group or instance profile name still reads as a name collision. A `DeleteUser` that finds the user already gone (`NoSuchEntity`) now reads as already deleted, as CloudFormation treats it, instead of failing the delete.
