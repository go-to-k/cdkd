- **The new Cloud Control abandonment error is refused by every already-deleted classifier, so a delete cdkd stopped watching is never recorded as done (issue [#3236](https://github.com/go-to-k/cdkd/issues/3236))** -- `src/provisioning/wait-abandoned.ts` (new), `src/provisioning/cloud-control-provider.ts`, `src/deployment/deploy-engine.ts`, `src/cli/commands/destroy-runner.ts`. cdkd decides a failed DELETE means the resource is already gone by SUBSTRING-matching the error message, at four sites: the Cloud Control provider's own `delete()` catch, the deploy engine's replacement delete-then-CREATE arm and its template-removal delete arm, and the destroy runner's per-resource delete loop. `CloudControlWaitAbandonedError` -- shipped by the sibling entry dated 2026-09-16 -- says the OPPOSITE, and is deliberately left RETRYABLE for DELETE and UPDATE so the delete can be re-issued, so it carries no non-retryable marker and clears every pre-existing typed guard. Its message interpolates the LOGICAL ID and the last-seen IDENTIFIER, both user- or template-chosen, so a resource named `PageNotFound` would satisfy the needles: destroy would report success and drop the state row over a delete AWS may never have completed, and the replacement arm would create the replacement beside a resource whose delete was still in flight. All four sites test the new `isWaitAbandonedError` first; the replacement arm, which carried no typed guard at all, also gains `isInterruptedWaitError` and `isMarkedNonRetryable`. A marker rather than an exported class, because three of the four cannot import the provider without closing a cycle. `cleanupFailedCreateRemnant` takes the same guard for a sharper reason: its `isNotFoundMessage` is case-INSENSITIVE, so a `getaddrinfo ENOTFOUND ...` cause matches `/not\s*found/i` and would suppress the real "remove it manually" warning over a remnant still holding the name.
