- **`cdkd rollback --revert-failed` now deletes a resource whose CREATE succeeded at AWS and then failed (Kinesis so far) (issue [#1710](https://github.com/go-to-k/cdkd/issues/1710))** -- `src/provisioning/auxiliary-failure.ts`, `src/deployment/deploy-engine/execute.ts`, `src/deployment/{rollback-executor,retry,prior-attempt-scope}.ts`, `src/deployment/rollback-executor/{plan,types}.ts`, `src/provisioning/providers/kinesis-provider.ts`, `src/cli/commands/rollback.ts`, `src/types/rollback-journal.ts`. A provider that failed after its create call returned (a Kinesis stream whose retention or encryption follow-up AWS rejected) left the resource in AWS with no state record, and the failed op was journaled with no physical id, so `--revert-failed` skipped it and a retry collided with the leftover name. A provider now marks the error once its create call has returned (`markCreatedBeforeFailure`); the deploy journals that id with `physicalIdRecoveredFromError` and the template's `DeletionPolicy`, and `--revert-failed` deletes, retains or snapshots it accordingly, only while nothing later owns it: no state resource or rollback-orphan record holds its ids, no newer entry of its type names its id or completed a CREATE, and no later removal superseded it; otherwise it is skipped, warned where it may be untracked. `ProvisioningError.physicalId` is never trusted: providers also set it on a collision with another owner's resource. A retry carries the mark forward. Kinesis is the first provider to mark; it also now refuses a non-numeric `RetentionPeriodHours` or a KMS `StreamEncryption` without a `KeyId` before `CreateStream`, and sends a numeric-string retention as a number; its update refuses a non-numeric retention too. Tests: `tests/unit/deployment/{failed-create-orphan,deploy-engine-rollback-journal,retry-replayed-create-collision-3972}.test.ts`, `tests/unit/provisioning/kinesis-provider-metrics-and-record-size.test.ts`; integ Phase O in `tests/integration/rollback-command/`.
