- **`cdkd local invoke` / `start-api` / `run-task` / `invoke-agentcore` now log in to the pull host for every ECR form, and recognize only hosts AWS serves (issue [#3670](https://github.com/go-to-k/cdkd/issues/3670))** -- `src/local/ecr-puller.ts`, `src/utils/ecr-uri.ts`, their unit tests, `docs/local-run-task.md`. A cross-account pull through the plain `<acct>.dkr.ecr.<region>.<suffix>` host, made on the caller's own credentials (a repository-policy grant, no `--ecr-role-arn`), failed with `no basic auth credentials`: the plain form still logged in to `GetAuthorizationToken`'s `proxyEndpoint`, which names the CALLER's registry. `docker login` now always targets the host `docker pull` uses. Three host shapes AWS does not serve are now refused instead of receiving a login: a dual-stack `on.aws` host outside the `aws` / `aws-us-gov` partitions, a FIPS host outside those partitions (AWS lists `dkr.ecr-fips` endpoints only there), and a service-name label in the region position (`<acct>.dkr.ecr.s3.amazonaws.com`). A region whose PREFIX cdkd does not know yet (a future `nz-north-1`, the way `il-` / `mx-` arrived) is now refused too, until cdkd learns the prefix: `local run-task` pulls such an image anonymously as a public image and logs at debug level that the host looked like ECR, and `local invoke` / `start-api` refuse it as an ECR URI cdkd cannot authenticate against. Upstream counterpart: go-to-k/cdk-local#766.
