- **`AWS::EC2::Instance` with `LaunchTemplate` / `Volumes` now deploys on the SDK path (issue [#5630](https://github.com/go-to-k/cdkd/issues/5630))** -- `src/provisioning/providers/ec2-provider.ts`, the regenerated coverage map, unit tests and the `ec2-instance` integ fixture. Before this change, a template that set either property sent the whole instance through Cloud Control, which is slower and sticky. `LaunchTemplate` is now sent on `RunInstances`; an instance launched from one needs no `ImageId` or `InstanceType` of its own, and cdkd no longer defaults the instance type beside a template. It is create-only, so a change (a new `Version`) replaces the instance, as CloudFormation does. Each `Volumes` entry is attached once the instance runs, so a create declaring `Volumes` waits for `running` even under `--no-wait`. These update behaviors follow what CloudFormation did on a measured throwaway stack: adding an entry attaches the volume, removing one (or the whole property) detaches it, and a `Device` change detaches the volume and attaches it at the new device, all on the same instance. A replacement while a listed volume is still attached to the old instance fails, as it does in CloudFormation. A malformed value is refused before any AWS call. `cdkd drift` reads `Volumes` back from the attached volumes it lists; `LaunchTemplate` is not read back. Resources already recorded as Cloud Control-provisioned stay on Cloud Control. `LicenseSpecifications`, `SsmAssociations` and the other `AWS::EC2::Instance` properties listed on #5630 still route through Cloud Control.
