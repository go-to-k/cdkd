- **A stack lock released during the final acquire attempt no longer fails the command with "Lock exists but could not read lock info" (issue [#4055](https://github.com/go-to-k/cdkd/issues/4055))** -- `src/state/lock-manager.ts`, `docs/troubleshooting.md`, `docs/cli-deploy.md`, `docs/state-management.md`. `acquireLockWithRetry` (used by `cdkd deploy`, `rollback`, `scrub` and `export`'s nested children) read the lock after each failed acquire and, when the holder had released it in between, fell through: on the last attempt the loop ended, a second read also found nothing, and the command failed although one more acquire would have succeeded, telling the user to `force-unlock` a lock that was gone. An empty read after a failed acquire now re-attempts at once without spending a retry, up to 3 times per command so a flapping lock, or a `lock.json` whose body is not a readable lock, cannot loop forever; past that an empty read waits the retry delay like a held lock. The refusal renders the read taken after the last failed acquire instead of reading again, counts the attempts actually made, and when no lock was found says `No lock could be read after the last failed attempt` and asks for a re-run, keeping the `force-unlock` command for a repeat. Tests: `tests/unit/state/lock-acquire-released-race.test.ts`.
