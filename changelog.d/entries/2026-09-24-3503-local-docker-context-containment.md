- **`cdkd local invoke` / `start-api` / `invoke-agentcore` / `start-service` / `start-alb` now REFUSE a Docker asset whose relative `source.directory` escapes the assembly (issue [#3503](https://github.com/go-to-k/cdkd/issues/3503))** -- `src/local/docker-image-builder.ts`, `src/assets/docker-build.ts`, `src/cli/commands/emulator-docker-context.ts`, `src/cli/commands/local-{invoke,start-api,invoke-agentcore,start-service,start-alb}.ts`. These commands build container images through the bundled `cdk-local` engine, which joins `source.directory` onto the manifest directory with no check, so a hand-modified assembly could make any host directory the build context of an image cdkd then runs. `cdkd local run-task` was the only local image build already contained. **Behavior change:** the three direct builds now go through a shim that judges the path with the same `resolveDockerContextDirectory` the deploy path uses, bound by the app's output directory (a `cdk.Stage`'s `../asset.<hash>` still loads), before the engine runs. `start-service` / `start-alb` hand the whole run to the engine, so cdkd checks every Docker asset in every stack's manifest at the strategy's `resolveBoots`, which the engine calls before any build, at startup and on each `--watch` reload (a refused reload keeps the previous replicas serving), bound like the engine's own (climbing from an `--app cdk.out/assembly-<Stage>` to its declaring parent, with a warning). An absolute `source.directory` is judged as the engine joins it, under the manifest directory, and every path is also judged as the kernel resolves it, so `<link>/..` cannot step out. Still not contained: images built inside `cdkd local start-agentcore` and `start-cloudfront`, which cdk-local runs end to end, and the directory a `start-service` / `start-alb` `--watch` soft reload copies ([#3597](https://github.com/go-to-k/cdkd/issues/3597)).
