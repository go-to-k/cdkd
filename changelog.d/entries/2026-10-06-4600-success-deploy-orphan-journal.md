- **A successful deploy now deletes a resource a failed CREATE made before it failed, instead of dropping the rollback journal that is its only record (issue [#4600](https://github.com/go-to-k/cdkd/issues/4600))** -- `src/deployment/deploy-engine/{rollback,deploy-flow}.ts`, `src/deployment/rollback-executor/journaled-orphans.ts`, `src/deployment/nested-child-journal.ts`, `src/state/s3-state-backend.ts`. After #4584 the automatic rollback, `cdkd rollback` and `cdkd destroy` acted on such a journaled resource (Kinesis so far), but a later successful deploy deleted the journal unconditionally, and a top-level deploy deleted each nested stack's journal the same way, leaving the resource in AWS with nothing in cdkd naming it. Now the deploy first deletes it per its journaled `DeletionPolicy` (`Retain` keeps it, `Snapshot` snapshots it), through the #1710 supersede pass and ownership checks; its own resources are judged by physical id against the saved state, so a fix-forward re-creating the same logical id still deletes the orphan. It never deletes one that any other state record in the bucket holds by type and physical id, or while such a record cannot be read. Nested stacks are settled under their own lock against their own record. A delete that fails or is refused keeps the journal reduced to that entry where it can, warns, and is counted with the skipped deletes, so the deploy exits `2` (`--allow-unaddressed` exits `0`); the next successful deploy retries it, and the warning names `cdkd rollback` only once the journal is reduced. Tests: `tests/unit/deployment/{deploy-engine-rollback-journal,deploy-engine-nested-journal,nested-child-journal,journaled-orphans-success}.test.ts`, `tests/unit/state/{s3-state-backend,malformed-resources-bag}.test.ts`; integ Phase O steps O6-O8 in `tests/integration/rollback-command/`.
