- **A successful deploy now deletes a resource a failed CREATE made before it failed, instead of dropping the rollback journal that is its only record (issue [#4600](https://github.com/go-to-k/cdkd/issues/4600))** -- `src/deployment/deploy-engine/{rollback,deploy-flow}.ts`, `src/deployment/rollback-executor/journaled-orphans.ts`, `src/deployment/nested-child-journal.ts`, `src/state/s3-state-backend.ts`. After #4584 the automatic rollback, `cdkd rollback` and `cdkd destroy` acted on such a journaled resource (Kinesis so far), but a later successful deploy deleted the journal unconditionally, and a top-level deploy deleted each nested stack's journal the same way, leaving the resource in AWS with nothing in cdkd naming it. Now the deploy first deletes it per its journaled `DeletionPolicy` (`Retain` keeps it, `Snapshot` snapshots it), through the same supersede pass (the deploy's own completed operations count as newer) and ownership checks against the saved state, and does the same for each nested stack's journal under that stack's lock. A delete that fails keeps the journal reduced to just that entry, warns with a `cdkd rollback` command, and is counted with the skipped deletes, so the deploy exits `2` (`--allow-unaddressed` exits `0`); the next successful deploy retries it. A nested stack whose state cannot be read keeps such an entry rather than deleting it.
