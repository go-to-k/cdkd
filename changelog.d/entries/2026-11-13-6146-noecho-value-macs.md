- **A write-only property fed by a `NoEcho` parameter is re-sent only when the value changed (issue [#6146](https://github.com/go-to-k/cdkd/issues/6146))** -- `src/deployment/noecho-value-macs.ts`, `src/deployment/deploy-engine/{noecho-macs,update/noecho-macs,update/provision-update}.ts`, `src/cli/commands/{bootstrap,bootstrap-noecho-mac-key}.ts`, `src/cli/commands/diff-recursive/noecho-macs.ts`, `ResourceState.noEchoValueMacs` (state schema 17), unit tests, the `noecho-restapi-body-mac` integ fixture and docs. AWS never reports such a property (an RDS `MasterUserPassword`), so every deploy re-sent it, and a REST API `Body` holding a `NoEcho` value was never put again. Now `cdkd bootstrap` creates a per-region HMAC KMS key (`alias/cdkd-noecho-mac`, a least-privilege key policy), and each deploy records a KMS MAC of each `NoEcho` value a property was sent, bound to the stack and the parameter. The next deploy compares: a different MAC sends the property (the `Body` is put); an equal one sends nothing, for a property that reads only `NoEcho` parameters and literals. No MAC (the first deploy after upgrading, after a failed update or a rollback, without the key or `kms:GenerateMac`, an AWS Emulator target) keeps the previous behaviour; a `Body` keeps its skip-and-warn. A stack with no `NoEcho` parameter makes no KMS call; one with them makes one `GenerateMac` per parameter per deploy. A KMS failure never fails a deploy and logs only the error name. `cdkd diff` shows a write-only property whose MAC differs as changed. To turn it on, re-run `cdkd bootstrap` in each region and grant the deploying identity `kms:GenerateMac` on the key. A state holding a MAC is written as schema version 17, which an older cdkd refuses ("Upgrade cdkd"), as a deployer or as a `Fn::GetStackOutput` consumer, until no record holds a MAC; every other state stays version 16.
