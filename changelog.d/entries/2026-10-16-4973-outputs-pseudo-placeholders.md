- **`cdkd diff --recursive --fail` no longer reports a change on an unchanged nested stack in which a child's `Outputs` read a parameter the parent spelled as a literal embedding `{{resolve:...}}` tokens, beside another output reading a sibling parameter that spells the same secret differently through an `Fn::Join` / `Fn::Sub` naming two or more pseudo parameters, e.g. `` `${Aws.REGION}.${Aws.ACCOUNT_ID}.${param.valueAsString}` `` (issue [#4973](https://github.com/go-to-k/cdkd/issues/4973)).** The redaction of a child's outputs could hold at most one pseudo parameter unknown in such an output, so it fell back to the sibling's spelling for the literal parameter across the whole child. It now reads `AWS::Region`, `AWS::Partition`, `AWS::URLSuffix` and (where the child already looks it up, [#4975](https://github.com/go-to-k/cdkd/issues/4975)) `AWS::AccountId` from the values the child's parameter resolution records ([#4962](https://github.com/go-to-k/cdkd/issues/4962)); no AWS call is added. After upgrading, the first deploy of such a stack shows a change on the child resources reading the literal parameter, because their state (and the child's outputs) now record the parameter's own `{{resolve:...}}` spelling instead of the sibling's; the deployed VALUE is unchanged, and a create-only property is replaced once with an identical value. `AWS::StackName`, `AWS::StackId`, and an `AWS::AccountId` the child does not look up, stay unknown. Source: `src/deployment/secret-redaction/{placeholder-positions,nested-stack}.ts`, `src/deployment/intrinsic-resolver/parameter-secrets.ts`.
