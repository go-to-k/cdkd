- **The readers of a resource the update-failure fallback replaces under a new id follow it (issue [#7081](https://github.com/go-to-k/cdkd/issues/7081))** -- `src/deployment/deploy-engine/execute/fallback-replaced-readers.ts` (new), `src/deployment/deploy-engine/execute/{provision-node,lost-children}.ts`, `src/deployment/deploy-engine/update-in-place/replace-fallback.ts`, `src/deployment/deploy-engine/replacement/run-state.ts`. When `--replace` (or Cloud Control's `UnsupportedActionException`, which needs no flag) replaced a resource whose in-place update was rejected, and the replacement got a new physical id -- a generated-name resource on any stack with a `stackInstanceId`, or an AWS-assigned id -- the readers the diff called unchanged were never sent the new id: the deploy exited 0 and they, and their state records, kept naming the deleted resource. They are now promoted when the replacement completes, as a planned replacement's readers are: updated in place where the referencing property is mutable, replaced where it is create-only (their own readers following), with `--force-stateful-recreation` required to replace a stateful one. A re-create under the same id keeps the #4444 handling.
