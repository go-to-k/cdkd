- **The SDK provider restores an `AWS::RDS::DBCluster` from a snapshot, or to a point in time from a source resource id (issue [#5639](https://github.com/go-to-k/cdkd/issues/5639))** -- `src/provisioning/providers/rds/cluster-restore.ts`, `cluster-create.ts`, `rds-provider.ts`, `rds/drift.ts`, the delete and update comments, `src/provisioning/restore-source-guard.ts` and the four deploy-engine replacement paths that call it, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, unit tests, the RDS wire cases, and the `rds-dbcluster-pitr-restore` integ. Before, a cluster declaring `SnapshotIdentifier` or `SourceDbClusterResourceId` routed through Cloud Control. Now a non-empty `SnapshotIdentifier` makes the create a `RestoreDBClusterFromSnapshot` with the members CloudFormation's handler puts on it, after reading the snapshot for its scalability type (shared and public snapshots included; a denied read restores as a standard cluster, as CloudFormation does). A `SourceDbClusterResourceId` makes it a `RestoreDBClusterToPointInTime` naming that id, after reading that cluster's automated backups (a retained Aurora Limitless backup and the encryption combinations CloudFormation refuses are refused). Declaring both point-in-time sources is refused, and a point-in-time source wins over a `SnapshotIdentifier`, as in CloudFormation. Either restore is followed by the same `ModifyDBCluster` CloudFormation sends once the cluster is `available`. A record restored either way deletes no writer instance by name and detaches only from a global cluster AWS lists it in. A delete-first replacement whose `SourceDbClusterResourceId` is the replaced cluster's own resource id is refused before the delete. Resources already deployed through Cloud Control stay there.
