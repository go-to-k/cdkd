- **A cross-account `Fn::GetStackOutput` that the AWS CDK generates is now read through the producer account's CDK lookup role, or refused before the deploy with both remedies (issue [#4808](https://github.com/go-to-k/cdkd/issues/4808))** -- the new `src/deployment/intrinsic-resolver/cdk-cross-account-ref.ts`, `stack-output.ts`, `src/synthesis/assembly-reader.ts` (`StackInfo.lookupRoleArn`), `src/analyzer/cross-stack-deps.ts`, `src/cli/commands/deploy.ts`, `diff.ts`, `diff-recursive.ts`. Such a reference used to fail mid-deploy with "RoleArn must be a literal string" (or, under `@aws-cdk/core:enablePartitionLiterals`, with an `AssumeRole` denial). `cdkd deploy` and `cdkd diff` now recognize it, only for a reference carrying a `RoleArn`: the `RoleArn` is a literal ARN or CDK's exact `Fn::Join` over `AWS::Partition`, and the producer stack in the same assembly declares a role of that name trusting only CloudFormation execution roles. cdkd then assumes the producer artifact's lookup role and reads the producer's state as for any `RoleArn`; the secret refusal still applies. When the producer is not in the assembly, names no lookup role, or the lookup role or state read is denied, cdkd refuses and names `cdk bootstrap --trust-for-lookup <consumer-account>` and a user-written `cdk.Fn.getStackOutput()`; `cdkd deploy` refuses the first two before anything is provisioned when the reference sits in a top-level stack's resource that every deploy resolves; one in a nested stack or a conditional branch is refused when it is resolved. A role you wrote keeps today's behavior, and a reference without `RoleArn` runs none of this.
