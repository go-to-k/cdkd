- **A failed update of a resource deleted outside cdkd now says so, instead of pointing at a rollback that cannot succeed (issue [#6106](https://github.com/go-to-k/cdkd/issues/6106))** -- `src/deployment/deleted-outside-cdkd.ts` (new), `src/deployment/deploy-engine/rollback/settle.ts`, `src/deployment/deploy-engine/execute/rollback-after-failure.ts` and `src/deployment/rollback-executor/replay-failed.ts`, plus a new `update-deleted-outside` integ. Before, when an update failed because its resource had been deleted outside cdkd (in the console, say), the automatic rollback kept the failed operation and printed `Revert it with: cdkd rollback <stack> --revert-failed`. That command re-applies the previous properties through the same update, fails the same way, and then asks for another re-run, without end. Now, after a failed update, cdkd reads the resource; when AWS reports it gone, the deploy names it as deleted outside cdkd and prints the remedy `cdkd drift` gives for such a resource (remove it from the app and deploy, then restore it and deploy again), and it keeps no `--revert-failed` record for it. `cdkd rollback --revert-failed` does the same when its forced revert fails on a resource AWS reports gone: it skips the operation with that warning (exit 2) and drops it from the journal, which also settles journals older releases wrote. A replacement that deleted the old resource itself is not reported this way. Any other read outcome (the resource exists, the read fails, or the type has no read) keeps the previous behavior.
