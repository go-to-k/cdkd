- **A SageMaker domain `VpcId` change is now planned as a replacement, as CloudFormation does, behind `--force-stateful-recreation` (issue [#7126](https://github.com/go-to-k/cdkd/issues/7126))** -- `src/analyzer/replacement-rules/evidence.ts`, `src/analyzer/replacement-rules/spec-replacement-properties.generated.ts`, `src/deployment/deploy-engine/update-replace/preflight.ts`. Before this, the change was sent to Cloud Control in place and refused (`NotUpdatable`, "VpcId change requires replacement"). CloudFormation was measured going to the replacement's create path on a VpcId-only change, where the new domain failed `AlreadyExists` on the `DomainName` it keeps and the stack rolled back: CloudFormation replaces the domain only when `DomainName` changes too. The domain owns its users' home EFS, so the deploy refuses the replacement before any call unless `--force-stateful-recreation` is passed, and the refusal says how CloudFormation behaves. With the flag and the same `DomainName`, cdkd's create-first replacement meets the same `AlreadyExists` and refuses without deleting anything; adding `--replace` deletes the old domain first, and its home EFS and NFS security groups stay behind in the account. A subnet or network-access change within the same VPC still applies in place.
