- **`cdkd local run-task` refuses a container `Command` / `EntryPoint` / health-check element that `Ref`s an `AWS::AppSync::ApiKey`, and passes such a value in `Environment` off the `docker run` command line (issue [#6330](https://github.com/go-to-k/cdkd/issues/6330))** -- `src/local/ecs-task-resolver/{container,cross-stack,volume}.ts`. The argv guard caught a secret read only through `Fn::GetAtt` or a dotted `${Id.Attr}` placeholder of `Fn::Sub`. A `Ref` (CDK's `cfnApiKey.ref`) or a dot-less `${ApiKey}` placeholder resolves to the recorded physical id `<apiId>|<key>`, so before this the plaintext `x-api-key` went on the `docker run` command line, where `ps` and `docker inspect` show it. Such an element is now refused, in the sync pass and the cross-stack post-pass, for any record whose physical id holds a secret, as is an `Fn::GetAtt` of an attribute holding that secret (the ApiKey's `Arn`, which ends in the key). Pseudo parameters, variable-map names and a `Ref` to any other record still resolve; a `${!Literal}` escape is not reported as an ApiKey read. A nested stack output its row records as carrying a child's secret is a secret read too, and a `Host.SourcePath` (which goes on the argv as `-v`) reading such a recorded secret is refused. The refusal names `Environment` as the remedy, but an `Environment` value went on the argv as `-e KEY=<value>`: one that reads a secret from state (a `Ref` like this, or a secret attribute) is now passed, in both passes, as a value-less `-e KEY` with the value in the docker client's environment, as a resolved secret is. A `Secrets` `ValueFrom` reading a secret its record holds (never judged by attribute name: CDK's nested-stack secret ARN output is named `...Secret...Ref`) is dropped with a warning naming only its logical id, since the secrets lookup would print the value it resolved to. Tests: `tests/unit/local/ecs-task-resolver-command-intrinsics.test.ts`.
