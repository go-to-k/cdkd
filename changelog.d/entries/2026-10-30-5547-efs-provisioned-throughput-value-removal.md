- **An `AWS::EFS::FileSystem` update with `ThroughputMode: provisioned` and no `ProvisionedThroughputInMibps` is now refused before any call, as CloudFormation refuses it (issue [#5547](https://github.com/go-to-k/cdkd/issues/5547), umbrella [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/efs-provider.ts` (`updateFileSystem`), `tests/unit/provisioning/efs-provider-throughput-removal.test.ts`, `tests/unit/provisioning/sdk-wire-cases-17.ts` and a refusal phase in the `efs-standalone` integ fixture. Removing only the throughput value while the mode stays provisioned was skipped silently: cdkd sent nothing, the file system kept its old value (and its billing), and no message named it. A live CloudFormation A/B in us-east-1 settled the premise: that update fails with "Throughput value must be specified for provisioned throughput mode." before any EFS mutation (no `UpdateFileSystem` in CloudTrail), alone and beside a tag + lifecycle change, rolls back, and the value stays. A bursting -> provisioned switch with no value fails there too. cdkd now fails the update with the same message and applies none of the resource's other changes; a rollback or drift-revert replay warns instead and leaves the throughput as it is, and a value-less record on both sides does not block unrelated changes. The AWS CDK L2 `FileSystem` already refuses the shape at synth; it is reachable through `CfnFileSystem` or an override.
