- **The automatic rollback, a plain `cdkd rollback` and `cdkd destroy` now delete a resource a failed CREATE made before it failed, instead of dropping its only record (issue [#4584](https://github.com/go-to-k/cdkd/issues/4584))** -- `src/deployment/deploy-engine/{rollback,execute}.ts`, `src/deployment/rollback-executor.ts`, `src/deployment/rollback-executor/{plan,journaled-orphans}.ts`, `src/cli/commands/{rollback,destroy-runner}.ts`, `src/state/{s3-state-backend,malformed-resources-bag}.ts`. Since #1710 such a CREATE (Kinesis so far) is journaled with its physical id, but only `cdkd rollback --revert-failed` acted on it: the automatic rollback left the resource in AWS, a plain `cdkd rollback` popped the entry, and `cdkd destroy` swept the journal with the state, after which nothing in cdkd named it. Now, as CloudFormation's rollback deletes a failed CREATE, the automatic rollback deletes it before reverting the completed operations; a plain `cdkd rollback` replays it as `--revert-failed` does (other failed operations still need the flag); and `cdkd destroy` lists and counts it before the prompt, re-reads the journal under the lock, deletes it before the stack's resources and strips the entry, and never takes the unconfirmed empty-stack path while one is journaled (a journal it cannot read is still warned about and removed with the state). A later successful deploy still drops the journal without deleting it (#4600). Each honours the journaled `DeletionPolicy` (`Retain` keeps it, `Snapshot` snapshots it) and the #1710 ownership checks; a failed delete keeps the record (the full segment, or the state and journal on destroy). `--no-rollback` deletes nothing.
