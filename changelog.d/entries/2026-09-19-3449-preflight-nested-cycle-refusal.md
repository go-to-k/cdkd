- **`cdkd deploy` refuses a cyclic nested-template tree before it starts, not at the nested-stack row (issue [#3449](https://github.com/go-to-k/cdkd/issues/3449))** -- `deploy.ts`, new `src/cli/commands/nested-template-preflight.ts`, tests, `docs/cli-deploy-safety.md`, `nested-stack-deep` integ arm. [#3448](https://github.com/go-to-k/cdkd/pull/3448) made `NestedStackProvider` refuse a cyclic (or absolute-path, too deep, too large) nested-template tree before the first nested level deploys. That is the earliest point the provider owns, but by then the parent stack had been started: its assets were published, its lock was held, and any of its own resources that do not depend on the nested row could already be created and then had to be rolled back. `cdkd deploy` now runs the same walk (`findNestedTemplateTreeDefect`, same rules, same display-safe rendering) right after synthesis, over every stack in the final deploy set including auto-included dependency stacks, and before macro expansion, asset publishing, any lock, any state write and any engine. One malformed stack stops the whole run with exit code 1, under `--dry-run` too; a stack outside the deploy set is not judged. The error is a non-retryable `SynthesisError` ending in `Refusing to start the deploy; nothing has been published or provisioned.` The provider's per-row walk is unchanged and stays as the guard for a nested deploy started by anything other than this command, with its own `NestedStackProvider: ... Refusing to deploy any level of it.` wording. The walk is not seeded with the root template's path (`StackInfo` does not carry it); a child pointing back at the root template is still refused, one lap later in the rendered chain. `cdkd rollback`, `cdkd destroy` and `cdkd state destroy` build a destroy-mode nested context that cannot start a nested deploy, and `cdkd import --migrate-from-cloudformation` recurses over the real (finite) CloudFormation stack tree, so none of them needed the check.
