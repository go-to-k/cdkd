- **`cdkd force-unlock` recovery hints build through the shared pasteable-command gate, so a lock record named like an option or past the stack-ref cap gets no command (issue [#3436](https://github.com/go-to-k/cdkd/issues/3436))** -- `src/state/lock-contention-message.ts`. `buildForceUnlockCommand` kept its own copy of the gate: emptiness and exactness of the name and region plus the recovery flags' own exactness, but no leading-`-` refusal and no cap, so a record named `--state-bucket=attacker` rendered exactly and came out as `cdkd force-unlock '--state-bucket=attacker' ...`, which the shell strips to the flag Commander then parses, and a name longer than 1152 code points was named in full. It now builds through `pasteableCommand` and keeps its SUPPRESS semantics: any value the gate withholds (`empty`, `altered`, `too-long`, `option-shaped`), or an inexact recovery fragment, suppresses the whole command and the message says so, with the two new causes named in the no-command sentence; the region takes the same two refusals. Named commands render byte-for-byte as before. The refusal's head sentence now renders the stack name in `displayIdent`'s boundary instead of inside cdkd's own `'...'` (a plain name prints bare): the paste fence measured the hand-quoted form running when a name carrying a quote was pasted with its sentence.
