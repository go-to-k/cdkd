- **A bare cdkd command uses your AWS profile's region, and keeps finding stacks the old `us-east-1` default created (issue [#2100](https://github.com/go-to-k/cdkd/issues/2100))** -- `src/cli/region-options.ts`, `src/cli/config-loader.ts`, `src/state/s3-state-backend.ts`, `src/synthesis/app-executor.ts`, `src/assets/docker-build.ts`, `src/cli/commands/*.ts`. With no `--region` / `AWS_REGION`, these commands keyed an env-agnostic stack's state, resources and `AWS::Region` by `us-east-1` while their pre-flight clients followed the profile. They now resolve `--region`, `AWS_REGION`, `AWS_DEFAULT_REGION`, the profile's region, then `us-east-1`, as `cdkd bootstrap` / `gc` already did. Compatibility: when the region came from `AWS_DEFAULT_REGION` or the profile, an env-agnostic stack that has state only in `us-east-1` stays there, and cdkd prints `Continuing to use us-east-1 so the existing stack is not duplicated`; a new stack joins it when the app's other stacks are all held, so the app stays in one region. The same hold applies to a force-unlock lock, the exports index (one file per command, the `us-east-1` one while it exists) and a region-less legacy state record (`S3StateBackend.stateExistsOwnedBy`), and the default state bucket also reads `cdkd-state-<account>-us-east-1`, preferred while it holds state; `cdkd state migrate` with no `--region` picks its source the same way. A stack with state in both regions stays in `us-east-1`, and a `us-east-1` legacy bucket that answers 403 never wins over a working one. A region taken from `AWS_DEFAULT_REGION`, which the AWS SDK does not read, is copied into `AWS_REGION` for cdkd's clients but not for the CDK app or an asset's build command. A fresh bare deploy into a profile region without cdkd asset storage creates it or uses the CDK bootstrap assets there. Tests: `tests/unit/cli/*-2100.test.ts` (new), `region-effective`, `config-loader`, `state-migrate`, `s3-state-backend`. Integ: `profile-region-default` (new).
