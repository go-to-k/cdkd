- **A rollback that re-adopts an old resource cdkd cannot prove it created now says so, and an identity read that fails no longer re-adopts (issue [#6655](https://github.com/go-to-k/cdkd/issues/6655))**. When a rollback reverses a replacement whose old resource AWS still reports, it compares an AWS-assigned id (an IAM role's `RoleId`, a table's `TableId`, ...) where one was recorded. Where none can be compared — a type with no such id, a record written before cdkd kept it, a type with no read for it — the old resource is still re-adopted, and one warning line per resource now says cdkd could not prove it is the one it created, naming the type or attribute (no value) and the `cdkd state orphan --resource <logicalId>` way out if it is not this stack's. The line is not counted as a warning, so the rollback's exit code is unchanged. Where an id was recorded but could not be compared (a redacted value, a failed identity read, a read that cannot name the resource), it is no longer re-adopted as proven: a delete that was refused is refused, saying the identity could not be compared (and offering a re-run only when the read failed), and a delete waiting for the cleanup phase is re-adopted, with the same warning line, only while state still lists the old resource as superseded, as for a failed existence read. No extra AWS call. Files: `src/deployment/rollback-executor/replaced-survivor.ts`, `src/deployment/rollback-executor/replay-reverse-replacement.ts`.
