- **A retried create no longer duplicates a KMS key after a follow-up call fails, and a KMS / Cognito / AppSync create that hits a 5xx now reports candidate orphans instead of duplicating silently (issue [#2080](https://github.com/go-to-k/cdkd/issues/2080), Plan C: KMS / Cognito / AppSync)** -- `src/provisioning/providers/{kms,cognito,appsync}-provider.ts`, `src/provisioning/providers/ambiguous-create.ts` (new), `docs/_contents/provider-rules.md`, `docs/_contents/troubleshooting.md`. `CreateKey`, `CreateUserPool` and `CreateGraphqlApi` have no idempotency token, so a retry re-ran them from the top. A failed `EnableKeyRotation` / `DisableKey` after `CreateKey` left a live key behind and minted another; the retry now reuses the key its own response named. These three creates no longer let the AWS SDK retry a 5xx inside one call, where a duplicate was invisible; the 5xx reaches cdkd's retry, which first looks for a user pool or API of the same name, or a key with the same settings, created during the failed attempt (for AppSync, any unrecorded API of that name), and reports each at warn with a read command first. Nothing is adopted and nothing is deleted: a name does not prove which deploy made a resource. A throttle, a 4xx or IAM propagation triggers no lookup. The lookup needs `kms:ListKeys` + `kms:DescribeKey`, `cognito-idp:ListUserPools`, or `appsync:ListGraphqlApis`; without them it warns and the create proceeds. A reset connection or timeout after the send is still retried inside the SDK and not reported (#3978 layer (b)). Tests: `tests/unit/provisioning/{kms,cognito,appsync}-create-retry-2080.test.ts`, `ambiguous-create.test.ts`.
