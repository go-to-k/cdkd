- **A same-name re-create of an IAM role or group refuses an instance profile or user outside the stack still holding it, instead of stripping it (issue [#6808](https://github.com/go-to-k/cdkd/issues/6808))** -- `src/provisioning/stack-own-holders.ts` (new), `src/provisioning/providers/iam-role/delete.ts`, `src/provisioning/providers/iam-user-group/group.ts`, `src/deployment/stack-records-scope.ts` / `src/deployment/rollback-executor.ts` (a replay's view carries the journal's failed ops), `docs/cli-destroy-guards.md`, the `iam-stack-own-holders-6808` / `rollback-journaled-holders-6808` unit suites, and a Phase 5d arm in the `iam-role-prefixed-name-update` integ. The deletes that may strip holders (`stackHoldersStillAttached`: `--recreate-via-*`, `--replace`'s delete-first, the update fallback, a rollback's delete-new-first, a rollback's delete of what the failed run created, and the role provider's old-role delete in a `RoleName` update) removed the role from every instance profile and every user from the group, including ones outside the stack, which only the stack's own holders re-attach afterwards; CloudFormation's delete handler holds no `iam:RemoveRoleFromInstanceProfile` / `iam:RemoveUserFromGroup` and fails with `DeleteConflict`. They now strip only the stack's own holders: the instance profiles whose `Roles` name the role, the users whose `Groups` or a `UserToGroupAddition` name the group, read from the stack's records (plus a replayed journal's failed writes) and matched by the recorded `InstanceProfileId` / `UserId` where one is. Any other holder is refused as on a destroy (#6750), before any holder is removed. With no records to read, nothing is stripped.
