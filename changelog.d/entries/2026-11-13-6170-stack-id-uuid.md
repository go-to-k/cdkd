- **`AWS::StackId` ends in a per-stack UUID on a newly deployed stack (issue [#6170](https://github.com/go-to-k/cdkd/issues/6170))** -- `src/state/stack-id-tail.ts`, `src/state/stack-instance-id.ts`, `src/deployment/intrinsic-resolver/functions/pseudo-parameter.ts`, the deploy, `cdkd diff`, `cdkd import`, `cdkd export` and `cdkd scrub` resolver contexts, state schema v16 (`stackIdFromInstance`), unit tests and the new `stack-id-uuid` and `schema-v15-to-v16-migration` integs. Before, cdkd resolved `AWS::StackId` to `arn:...:stack/<name>/cdkd`, where CloudFormation puts a UUID. The common CDK idiom for a unique name suffix, `Fn.select(4, Fn.split('-', Fn.select(2, Fn.split('/', Aws.STACK_ID))))`, then failed every create with an `{{Fn::Select:4:OutOfBounds}}` name, and its `Fn.select(0, ...)` / `Fn.select(2, Fn.split('/', ...))` forms gave every stack the same `cdkd` suffix. Now a stack whose first deploy runs with this version records `stackIdFromInstance` and its `AWS::StackId` ends in a UUID derived from the stack's instance id: unique per stack, the same on every deploy, and computed without an AWS call. The first deploy's conditions, diff and approval table already show it. A stack deployed before keeps the `cdkd` tail, so nothing already named from it is replaced. State is written as schema v16, which an older cdkd refuses to read.
