- **A managed policy, inline policy, group, role, permissions boundary or security group rule that a cdkd deploy just removed no longer stays in the drift baseline, where an out-of-band re-add of the same grant would never report (issue [#6609](https://github.com/go-to-k/cdkd/issues/6609))** -- `src/provisioning/own-write-removals.ts`, `src/provisioning/settle-own-write-members.ts`, `src/provisioning/sg-own-write-rules.ts`, the IAM role, user, group, managed policy and instance profile providers, the EC2 security group read and update, unit tests, the `iam-sibling-managed-policy-drift` and `drift-sg-sibling-rules` integs. The capture after cdkd's own write settled a list member once every declared entry read back, so a read still showing an entry that write had just detached, deleted, removed or revoked was recorded as the baseline; re-granting it outside cdkd later then matched the baseline. Each removal call that succeeds now notes what it removed (an ARN, a name, a boundary ARN, a rule's identity; never a policy document or a rule description, held in memory only), and the capture re-reads while a removed entry still shows (up to 3 more reads, 3.5 seconds at most, only when the first answer shows one). If it still shows after that, it is left out of the baseline, with a warning that points at `cdkd state refresh-observed`. This includes a template that drops the whole member, a deleted permissions boundary (recorded as none) and the AWS default allow-all egress rule a security group create revokes. An entry the same write put back is never waited on. No such lag was measured (us-east-1); this is a defence that costs nothing when the first read agrees. Drift, import and `state refresh-observed` still take the first answer.
