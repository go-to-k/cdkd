- **`--aws-emulator`: a destroy without the app refuses custom resources up front, and a failed rollback no longer advises a re-run that loops (issues [#6246](https://github.com/go-to-k/cdkd/issues/6246), [#6247](https://github.com/go-to-k/cdkd/issues/6247))** -- `src/cli/commands/destroy-runner/emulator-custom-resources.ts`, `src/cli/commands/destroy/command.ts`, `src/cli/commands/state/destroy.ts`, `src/local/custom-resource-runtime-gate.ts`, `src/local/custom-resource-runtime.ts`, `src/provisioning/providers/custom-resource/dispatch.ts`, `src/provisioning/providers/custom-resource/create-update.ts`, `src/cli/commands/rollback/render.ts` and `src/cli/commands/rollback/replay.ts`. Before, `cdkd state destroy` (or a `cdkd destroy` that did not read the app) sent custom resources' Delete events to AWS Emulator's own Lambda runtime, which fails CDK's own providers, advised `cdkd destroy` from the app only once it was running, and then deleted the handler functions, so that advice skipped every custom resource and left what they manage behind. Now every target stack and the nested stacks under it are checked before the first one is touched, and the run is refused before the prompt (`--yes` included) when one holds custom resources backed by a Lambda function in the run's account, naming `cdkd destroy <stack>` from the app's directory or `--no-local-custom-resources`. And a `cdkd rollback` whose custom resource failed in the emulator's runtime no longer ends with `Re-run with: cdkd rollback ...`, which failed the same way every time; it ends with `Deploy forward with: cdkd deploy <stack>`, as does its up-front warning.
