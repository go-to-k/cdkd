- **`--aws-emulator`: a destroy without the app refuses custom resources up front, and a failed rollback no longer advises a re-run that loops (issues [#6246](https://github.com/go-to-k/cdkd/issues/6246), [#6247](https://github.com/go-to-k/cdkd/issues/6247))** -- `src/cli/commands/destroy-runner/emulator-custom-resources.ts`, `src/cli/commands/destroy-runner/run.ts`, `src/local/custom-resource-runtime-gate.ts`, `src/local/custom-resource-runtime.ts`, `src/provisioning/providers/custom-resource/create-update.ts`, `src/cli/commands/rollback/render.ts` and `src/cli/commands/rollback/replay.ts`. Before, `cdkd state destroy` (or a `cdkd destroy` that did not read the app) under `--aws-emulator` sent custom resources' Delete events to AWS Emulator's own Lambda runtime, which fails CDK's own providers, and printed "run `cdkd destroy --aws-emulator` from the app's directory" only after the run had started; the same run then deleted the handler functions, so that advice skipped every custom resource and left what they manage (for example an `AwsCustomResource`'s SSM parameter) behind. Now the destroy refuses such a stack before the confirmation prompt and before deleting anything, `--yes` included, and names `cdkd destroy <stack>` from the app's directory, or `--no-local-custom-resources` to send the events to the emulator's runtime anyway. And when a custom resource's handler failed in the emulator's runtime during `cdkd rollback` (which never reads the app), the rollback no longer ends with `Re-run with: cdkd rollback ...`, which failed the same way every time; it names a deploy forward from the app (`Deploy forward with: cdkd deploy <stack>`), and its up-front warning says so instead of offering the silence flag.
