- **A replacement or create that names an ELBv2 load balancer or target group after one that already exists is refused before anything changes, and `cdkd import` resolves either by its template `Name` (issue [#3937](https://github.com/go-to-k/cdkd/issues/3937))** -- `src/deployment/replacement-name-holder.ts` (`NAME_ADOPTING_SDK_CREATE_TYPES`, `replacementSentNameMoves`), `src/provisioning/providers/elbv2-provider.ts` (`import()`, `sentElbv2Name`), `docs/_contents/cli-deploy-safety.md`, unit cases and target-group, load-balancer, prefix-flag and plain-create arms in `tests/integration/replacement-rename-onto-holder/`. `CreateLoadBalancer` and `CreateTargetGroup` return the existing resource when one of the requested name has the same settings, so a rename onto it "succeeded", deleted the stack's own resource and recorded the other one for a later `cdkd destroy` to delete; a plain create with an explicit `Name` adopted the same way. The SDK route now looks the name up first, as for the other name-adopting types: a resource found there, or a lookup that fails, fails the deploy with nothing created or deleted. The lookup asks for the name the create sends, stack-name prefix included under `--prefix-user-supplied-names`, and also runs when only that flag changed the sent name; a secret-derived `Name` is masked in the spelling the provider sends. Before, the provider's `import()` reported every ELBv2 load balancer and target group without a `--resource` override as not found, though `docs/_contents/import.md` listed both as resolved by their template name; `cdkd import` looks up the unprefixed name, and a lookup that fails is a failed row.
