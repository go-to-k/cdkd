- **SDK clients built outside `AwsClients` now use explicitly supplied credentials (issue [#3588](https://github.com/go-to-k/cdkd/issues/3588))** -- new `src/utils/ambient-client-defaults.ts` (`ambientClientDefaults`, `credentialFingerprint`), the ~82 client constructions in the SDK providers (DocumentDB and Neptune included), `cloud-control-provider.ts`, the synthesis context providers, `macro-expander.ts`, the asset publishers, `publish-assets.ts` / `state-migrate.ts` and `role-arn.ts`, plus `intrinsic-function-resolver.ts`'s client caches; tests in `tests/unit/utils/ambient-client-defaults{,-fence}.test.ts` and `tests/unit/deployment/intrinsic-cfn-fallback.test.ts`. A library caller that installed `AwsClients` with an explicit `credentials` object had every client cdkd builds for itself -- provider, context-provider and asset-publisher clients, and the source identity of the cross-account `Fn::GetStackOutput` `sts:AssumeRole` hop -- sign with the SDK's default credential chain instead. Those clients now carry the active `AwsClients`' profile and explicit credentials, in `AwsClients`' own precedence. The cross-account credential cache and the resolver's per-region client and CloudFormation-fallback caches are keyed by that identity as well, so a second identity is never served the first one's clients or credentials. CLI runs are unaffected: no command passes explicit credentials. Five files (four held by other open pull requests, plus the `cdkd local` ECR puller, whose caller-identity cache needs the same keying) still build the old shape and follow separately; the resolver's account-identity and dynamic-reference value caches are tracked in [#3660](https://github.com/go-to-k/cdkd/issues/3660).
