- **A 1-3 character secret embedded in a literal no longer reaches `state.json` in plaintext beside a public `ssm` reference, or in a nested stack's record restored by a rollback (issue [#5056](https://github.com/go-to-k/cdkd/issues/5056))** -- `src/deployment/secret-redaction/positions.ts`, `src/deployment/secret-redaction/context.ts`, `src/deployment/rollback-executor/replay-secrets.ts`, `src/deployment/rollback-executor/replay-retry.ts`. Such a secret is below the value scan's 4-character floor, so only its position can redact it. Before, a literal such as `postgres://{{resolve:ssm:/db/host}}:5432/?pin={{resolve:secretsmanager:...}}` was persisted with the pin in plaintext: the position arm refused the whole leaf because the public token has no secret pair. A deploy now persists the secret span as its reference and the public span as its resolved value, where this deploy's own lookup proved the parameter public and the leaf is exactly that rendering; a public value equal to or containing the secret is refused, as is any leaf the value scan would answer differently. A rollback replay now states the same generation claim the deploy does for a provider bag built from the re-resolved journal (a nested stack's `Parameters`), so a short secret embedded there is persisted as its reference. A provider bag no provider vouches for keeps the existing residual, as on the deploy side. Tests: `tests/unit/deployment/secret-redaction-subfloor-5056.test.ts`, `tests/unit/deployment/secret-redaction-context-1940.test.ts`.
