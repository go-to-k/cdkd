- **`AWS::RDS::DBCluster`: a Multi-AZ DB cluster's `DBClusterInstanceClass`, `AllocatedStorage` and `Iops` now deploy on the SDK route (issue [#5639](https://github.com/go-to-k/cdkd/issues/5639))** -- `src/provisioning/providers/rds/cluster-members.ts`. A Multi-AZ DB cluster (engine `mysql` or `postgres`) declares all three, so until now it always went through Cloud Control. Create sends each declared value. An update sends a changed instance class, and sends the declared size and IOPS together when the size, IOPS or `StorageType` changed. It then waits for the change to apply; `--no-wait` skips the wait. A class change counts as applied once the cluster reports the new class and is `available`. A storage change counts once the new size (and, on `io1` / `io2` storage, the IOPS) reads back with no storage change pending. CloudFormation also waits for `available` after a storage-only change; cdkd does not, because RDS can hold `storage-optimization` long after the new size is in place. A removed property sends nothing, so RDS keeps the live value, as CloudFormation's handler does. A size or IOPS that is not a whole number is refused before any call. A rollback or `cdkd drift --revert` never sends a smaller storage size, which RDS cannot apply: it warns and keeps the larger one. `cdkd drift` now reads all three back on a non-Aurora cluster. A DB cluster update now gets at least 90 minutes (the larger of 90 minutes and `--resource-timeout`). RDS applies a Multi-AZ class change to the three instances one at a time, with a failover, and a `db.c6gd.medium` to `large` change was still running after 30 minutes. With `--full-wait`, a storage optimization can take longer still, so raise `--resource-timeout AWS::RDS::DBCluster=<n>h` for one.
