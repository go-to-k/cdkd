- **A rollback that reverses a replacement now re-creates the old resource under the name cdkd would have minted, instead of letting AWS invent one (issue [#3199](https://github.com/go-to-k/cdkd/issues/3199))** -- `src/deployment/rollback-executor.ts`. The `reverse-replacement` replay-CREATE handed the provider the RECORDED property bag, which holds the template's resolved properties and so never carries a name cdkd generated. The three create sites in `DeployEngine` fill a `FALLBACK_NAME_RULES` name before a Cloud Control create; these two replay sites were the fourth and filled nothing, so a Cloud-Control-routed replay re-created under an AWS-random physical name and the restored resource silently stopped matching what the forward path mints. Both sites now run the bag through `applyDefaultNameForFallback` when the registry's ROUTING DECISION -- not the recorded `provisionedBy` hint, which is absent on a pre-v7 record and can disagree via the sticky rule's `sdk-coverage` exemption -- says `cc-api`; an SDK-routed replay is untouched, since its provider mints the name itself. Both rollback entry points already bind `withStackName`, so the replayed name is byte-identical to the forward create's. The fill lands only on the bag handed to `create()`; the state record is still rebuilt from the recorded bag, keeping the "a recorded bag never holds a generated name" invariant the Cloud Control UPDATE path depends on. Reachable whenever a replacement changes the physical id while the recorded bag names nothing -- adding an explicit name to a previously unnamed resource, but also any create-only change on a table type whose physical id is not its name (`AWS::ElasticLoadBalancingV2::TargetGroup` on `Port` / `VpcId`, `AWS::WAFv2::WebACL` on `Scope`) -- and a later resource then fails. A type whose Cloud Control handler requires the name would fail the replay outright, stranding the resource; none is in the table yet.
