- **cdkd now uses path-style S3 URLs when an S3 endpoint override is configured, so custom resources complete against S3 emulators, and `CDKD_CR_S3_ENDPOINT_URL` signs the custom-resource response URL for a separate endpoint (issue [#5745](https://github.com/go-to-k/cdkd/issues/5745))** -- `src/utils/s3-client-defaults.ts`, `src/provisioning/providers/custom-resource-response-endpoint.ts`, `src/cli/program.ts`, every `new S3Client(...)` site, `scripts/check-aws-client-defaults.ts`, and their tests. The AWS SDK for JavaScript v3 honours `AWS_ENDPOINT_URL_S3` / `AWS_ENDPOINT_URL` / a profile `endpoint_url` but kept building virtual-hosted URLs (`http://<bucket>.s3:4566/...`), and it ignores a profile's `s3 = addressing_style`. The pre-signed `ResponseURL` a custom resource's Lambda PUTs its result to was therefore unreachable from the emulator, and the deploy waited until it timed out. cdkd now follows the AWS CLI's rule for every S3 client: path-style when an override is configured (unless `addressing_style = virtual`) or when `addressing_style = path` (config or credentials file, as botocore reads it), and it honours the AWS CDK CLI's `CDK_S3_FORCE_PATH_STYLE` (any non-empty value forces path-style); with none of these, clients are unchanged. Library callers resolve it with the newly exported `resolveS3ClientDefaults()`. `CDKD_CR_S3_ENDPOINT_URL` (modelled on the AWS CDK CLI's `AWS_ENDPOINT_URL_S3_FOR_CLOUDFORMATION`, which serves the CloudFormation template URL) signs only the `ResponseURL` for the endpoint the Lambda can reach; a malformed value fails the custom resource before it is invoked. Docs: `docs/troubleshooting-internals.md`.
