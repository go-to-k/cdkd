- **`cdkd destroy` of a parent stack whose nested child left only resources a failed deploy created now finishes in one run (issue [#4738](https://github.com/go-to-k/cdkd/issues/4738))** -- `src/provisioning/providers/nested-stack-provider.ts`, `src/cli/commands/destroy-runner.ts` (`journaledOrphanSkips` on the result), `src/provisioning/nested-stack-context.ts`, and the new `src/cli/commands/destroy-skip-message.ts` used by `destroy.ts` and `state.ts`. A failed-CREATE resource that the rollback journal alone records, and that cdkd keeps in AWS because nothing proves it is the deploy's own (an SQS queue, for example), keeps no state record. A nested child whose only skips were such resources had already deleted its own state, yet the parent kept its `AWS::CloudFormation::Stack` row and its own state and needed a second destroy. The parent now drops that row and its state in the same run. Those resources still count as skipped, so the run exits 2, and the row's line names how many the child left. The final message of a `cdkd destroy` / `cdkd state destroy` whose every skip is such a resource no longer says "State preserved (the records are kept)": it says the resources were left in AWS and no state records them. When recorded skips sit beside them, only the recorded ones are counted as entries kept in state. A deploy that removes such a nested stack, and a rollback, are unchanged: they keep the row, and their next run finds the child's state gone.
