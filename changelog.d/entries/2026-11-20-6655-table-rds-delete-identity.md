- **A DynamoDB table, RDS DB instance or RDS DB cluster delete refuses a resource that took over the recorded name (issue [#6655](https://github.com/go-to-k/cdkd/issues/6655))**. These deletes address AWS by name (identifier), so a table or database re-created under that name outside cdkd was deleted by a destroy, template removal, replacement or rollback. When the record holds the id AWS minted at create (`TableId` / `DbiResourceId` / `DBClusterResourceId`), the delete first reads the resource once (`DescribeTable` / `DescribeDBInstances` / `DescribeDBClusters`) and compares the id; a difference still there on a re-read 5 s later refuses before any write (no `--remove-protection` flip, no global-cluster detach, no final snapshot, no delete), non-retryable, naming the attribute (no value) and the `cdkd state orphan --resource` remedy, record kept. Unlike CloudFormation, which deletes whatever holds the name, the refusal also covers a DB that took over the identifier in an RDS blue/green switchover or a restore, and a table restored under its name: the message says the recorded one may still exist under another name, and that a replacement you made yourself is adopted with `cdkd import <stack> --resource <logicalId>=<physicalId> --force` (which records its new id) before re-running; otherwise the record is dropped with `cdkd state orphan --resource`. A `--remove-protection` flip an earlier attempt made is not re-enabled by name on a holder cdkd cannot confirm; a warning says so instead. The read replaces the `--remove-protection` observation, the read-replica check and the express-writer read the delete already made. No recorded id (a record written before cdkd recorded it): no read, by-name delete as before. Files: `src/provisioning/providers/dynamodb-table/delete.ts`, `src/provisioning/providers/rds/{instance-delete,cluster-delete}.ts`.
