- **`cdkd local start-service` / `start-alb` / `start-agentcore` now pull FIPS, dual-stack and ISO-partition ECR images (issue [#3655](https://github.com/go-to-k/cdkd/issues/3655))** -- `package.json` (`cdk-local` `^0.149.4` -> `^0.149.6`), `tests/integration/local-start-service/`. These commands pull through cdk-local's own ECR puller, which recognized only the plain `<acct>.dkr.ecr.<region>.amazonaws.com(.cn)` host. An image on `<acct>.dkr.ecr-fips.<region>.<suffix>`, `<acct>.dkr-ecr[-fips].<region>.on.aws` or an ISO / EUSC plain host was treated as a public image and pulled anonymously, which failed with `no basic auth credentials`. The bundled engine now recognizes every form AWS serves (FIPS and dual-stack only in the commercial and GovCloud partitions), always runs `docker login` against the host `docker pull` uses, no longer treats a host whose region label is not a region (`<acct>.dkr.ecr.s3.amazonaws.com`) as ECR, and folds an upper-cased host to lower case before logging in and pulling. Also from the bump (go-to-k/cdk-local#765): a `docker build failed for ...` message from a container-image build (`local invoke` / `start-api` / `invoke-agentcore`, and the engine's own builds) now shows only the first element of `source.executable`, display-safe, in its `(...)`, and a docker or executable spawn error reads `Failed to execute <cmd> (<code>)`. Upstream: go-to-k/cdk-local#766; cdkd's own pull path was fixed in #3651 / #3673.
