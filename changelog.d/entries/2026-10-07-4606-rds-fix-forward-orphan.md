- **A successful fix-forward deploy now deletes the RDS DB cluster or DB instance an earlier failed CREATE left under the same logical id, once live reads prove it is not the new one and is still the one that failed CREATE made (issues [#4606](https://github.com/go-to-k/cdkd/issues/4606), [#4655](https://github.com/go-to-k/cdkd/issues/4655))** -- `src/provisioning/providers/rds-provider.ts`, `src/provisioning/auxiliary-failure.ts`, `src/deployment/deploy-engine/execute.ts`. After `cdkd deploy --no-rollback` failed with an `AWS::RDS::DBCluster` or `AWS::RDS::DBInstance` already created, and the fixed template created a new one under the same logical id with another identifier, the successful deploy warned, named the earlier resource, exited `2` and left it in AWS. `RDSProvider` now implements `isSameResource` and `resourceIdentity`. Both rest on the immutable `DbClusterResourceId` / `DbiResourceId`. Identifiers equal apart from case are the same resource, since RDS identifiers are case-insensitive. The failed CREATE journals the resource id its create call returned, carried on the failure itself, so a describe that cannot run (often the failure) does not cost the orphan its identity; a provider may carry such an id on its created-before-failure mark, and the deploy then journals it without a live read. A resource someone re-created under the identifier, in any case spelling, reads back under another resource id and is kept with a warning. Only the not-found fault name counts as gone. Deleting an earlier resource that is already gone prints one info line. Tests: `tests/unit/provisioning/rds-provider-{same-resource-4606,resource-identity-4655}.test.ts`; new integ `rds-fix-forward-orphan`.
