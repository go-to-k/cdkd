- **`cdkd drift` now compares `AWS::IAM::UserToGroupAddition`, `AWS::CloudWatch::AnomalyDetector` and `AWS::EMR::InstanceFleetConfig`, which were always drift unknown (issue [#6769](https://github.com/go-to-k/cdkd/issues/6769), part of [#6696](https://github.com/go-to-k/cdkd/issues/6696))** -- `src/provisioning/providers/iam-user-group/read-state.ts`, `src/provisioning/providers/cloudwatch-anomaly-detector-provider.ts`, `src/provisioning/providers/emr-instance-fleet-config{-provider.ts,/read-state.ts}`, `src/analyzer/drift-cc-api-deny-list.ts`, `docs/cli-drift.md`, unit tests, and drift arms in the `iam-recreate-reattach`, `cloudwatch-anomaly-detector` and `emr-instance-fleets` integ fixtures. Since #6696 a drift-unknown resource makes a clean run exit 2, so a stack holding `user.addToGroup(...)`, an anomaly detector or a standalone EMR instance fleet exited 2 on every run, and an out-of-band change to them was never reported. Each now has a read-back: the addition lists each recorded user's groups (`ListGroupsForUser`) and reports the recorded users no longer in the group; the detector is found by its recorded metric descriptor (`DescribeAnomalyDetectors`) and its `Configuration` / `MetricCharacteristics` are compared; the fleet is read on its recorded cluster (`ListInstanceFleets`), with its capacities, instance type configs and launch / resize specifications. A detector or fleet AWS no longer has, and an addition whose group is gone, report as deleted. A record whose address holds a redacted or secret-derived value stays drift unknown. The read also runs for the baseline cdkd records after each deploy, like every other read-back. `AWS::EC2::LaunchTemplate` and the two types above leave the Cloud Control deny-list; the launch template, which has no SDK provider, was already read through Cloud Control. `AWS::EMR::InstanceGroupConfig` stays drift unknown for now.
