- **The SDK provider sends `GlobalClusterIdentifier` for `AWS::RDS::DBCluster` (issues [#5639](https://github.com/go-to-k/cdkd/issues/5639), [#5853](https://github.com/go-to-k/cdkd/issues/5853))** -- `src/provisioning/providers/rds-provider.ts`, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, unit tests, the RDS wire cases, a new `rds-aurora` integ arm, and the `cc-final-snapshot-handlers` integ, which now seeds its member onto Cloud Control. Before, a cluster declaring it routed through Cloud Control. The cluster now joins the named global cluster through `CreateDBCluster`. An update follows CloudFormation's update handler: removing the property, or setting it to `""`, detaches the cluster in place with `RemoveFromGlobalCluster` and waits until it has left and is available, even under `--no-wait`; unlike the detach before a delete, it is not refused for deletion protection. Adding it, or naming another global cluster, is refused before any write unless the live cluster is already a member of it (as a CDK `GlobalCluster` created with `SourceDBClusterIdentifier` makes it); joining another one takes a replacement, such as a new `DBClusterIdentifier`. A rollback replay or `cdkd drift --revert` never joins or detaches; it warns and leaves the cluster where it is. A value that is not a string is refused before any call, except on a replayed create, which leaves it out with a warning. The primary of a global cluster that still has other members now fails a detach at once, on an update and before a delete, naming them, where it used to wait out the delete timeout first. `cdkd drift` does not read it back. Resources already deployed through Cloud Control stay there.
