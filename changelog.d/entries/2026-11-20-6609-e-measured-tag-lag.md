- **A DynamoDB table's, a DynamoDB global table replica's or a Secrets Manager secret's tags that a cdkd update just changed no longer leave a drift baseline holding the previous tags, which `cdkd drift --revert` would put back (issue [#6609](https://github.com/go-to-k/cdkd/issues/6609))** -- `src/provisioning/tags-own-write-baseline.ts`, `src/provisioning/providers/dynamodb-table/{read-current-state,table-settings}.ts`, `src/provisioning/providers/dynamodb-table-provider.ts`, `src/provisioning/providers/dynamodb-globaltable/{read,read-support,update}.ts`, `src/provisioning/providers/dynamodb-globaltable-provider.ts`, `src/provisioning/providers/secretsmanager-secret/{read-state,update}.ts`, `src/provisioning/providers/secretsmanager-secret-provider.ts`, unit tests, the `dynamodb-table-policy-baseline`, `dynamodb-globaltable` and `secretsmanager-update-value-source` integs. Right after `TagResource` / `UntagResource`, `ListTagsOfResource` answered the previous tags for up to about 2.5 seconds, and `DescribeSecret` sometimes missed a just-written tag. The deploy recorded that first answer as the `observedProperties` baseline, so `cdkd drift` reported an untouched resource and `drift --revert` restored the old tags. When an update sent a tag call for the resource, the capture after it now re-reads an answer that is not the declared tag set: up to 4 more reads, 7.5 seconds at most, and only when the first answer differs. If the declared tags still do not show, they are recorded with a warning. Tags sent with the create call read back at once and are not re-read. A capture after an update that left the tags alone, drift, import and `state refresh-observed` take the first answer, as before.
