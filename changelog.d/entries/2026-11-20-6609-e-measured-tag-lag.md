- **A DynamoDB table's, a DynamoDB global table replica's or a Secrets Manager secret's tags that a cdkd update just changed no longer leave a drift baseline holding the previous tags, which `cdkd drift --revert` would put back (issue [#6609](https://github.com/go-to-k/cdkd/issues/6609))** -- `src/provisioning/tags-own-write-baseline.ts`, the `dynamodb-table`, `dynamodb-globaltable` and `secretsmanager-secret` providers, `src/cli/commands/drift/baseline-keys.ts`, unit tests, three integs. Right after `TagResource` / `UntagResource`, `ListTagsOfResource` answered the previous tags for up to about 2.5 seconds, and `DescribeSecret` sometimes missed a just-written tag; the deploy recorded that answer as the baseline, so drift reported an untouched resource and `--revert` restored the old tags. When an update sent a tag call, the capture after it now re-reads an answer that does not yet show the tags that call set or removed (up to 4 more reads, 7.5 seconds at most, only when the first answer differs). Tags the update did not touch, such as one added outside the template, are recorded as read. If the written tags still do not show, the newest answer is recorded with them applied, with a warning. Tags sent with the create call, drift, import and `state refresh-observed` take the first answer, as before. A table or secret `Tags` baseline written by an earlier cdkd is not compared while the live tags (`aws:` tags aside) are exactly the declared set; a global table replica's is compared until the next update or `cdkd state refresh-observed`.
