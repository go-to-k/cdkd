- **Commands that never touch a provider start ~270 ms of CPU faster: the SDK provider classes load when a command registers them (issue [#4521](https://github.com/go-to-k/cdkd/issues/4521))** -- `src/provisioning/register-providers.ts`, `src/provisioning/provider-classes.ts`, `src/cli/commands/{deploy,destroy,destroy-runner,diff,drift,import,orphan,rollback,state}.ts`, `src/provisioning/providers/wafv2-arn.ts`, `src/provisioning/providers/wafv2-provider.ts`, `src/deployment/intrinsic-resolver/ref-values.ts`, `scripts/diagnose-schema-refresh.mjs`. Every command module that registers providers is reached statically from the command tree, and each provider module evaluates its `@aws-sdk/client-*` package, so `cdkd --help`, `synth` and `list` evaluated all of them. The classes now load through `loadProviderClasses()` (one dynamic import, once per process), awaited at the start of each command function so registration stays synchronous inside the per-stack AWS client scope; every type is still registered. A helper the intrinsic resolver imported from the WAFv2 provider moved to a leaf module. `cdkd --help`: ~1140 ms to ~870 ms CPU. Tests: `tests/unit/provisioning/lazy-provider-classes.test.ts`.
