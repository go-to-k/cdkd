- **`cdkd scrub` no longer reports a stack CLEAN when a dynamic reference failed to RESOLVE** — a deleted SSM parameter, a secret with no `SecretString`, a missing `JSON_KEY`, a non-JSON secret, or a denied / pending-deletion / undecryptable secret each abandon the whole leaf, because the resolver's token loop stops at the first failing token. A real `{{resolve:secretsmanager:...}}` sitting after it was never fetched and recorded no needle, so a legacy plaintext already in `state.json` survived under `No plaintext secrets found`, exit 0. These are now a counted FINDING rather than a silent `debug` line: the rest of the stack is still scrubbed, **each abandoned record is named in a warning at default verbosity** (the resource, orphan record or output it belongs to), the per-stack and whole-run summaries carry the count, and the run does not report clean — `--dry-run --fail` exits 1, and so does a real run. The detection is POSITIONAL — it asks whether the value being scanned carried a `{{resolve:...}}` at all — not keyed on the error's message text: `sendWithThrottleRetry` rethrows an AWS rejection RAW, so a genuinely deleted parameter arrives as a bare `ParameterNotFound` with none of the resolver's own prose, which a text-keyed predicate missed. **A scan stopped by a TEMPLATE failure is warned but does NOT raise the exit code**: one throw aborts the whole properties bag, and an unresolvable `Ref` / `Fn::GetAtt` or a `Default`-less parameter is not a failure to fetch a reference — scrub resolves with template defaults and takes no `--parameters`, so failing the gate on those could not be cleared. Same for a token whose argument kept an unsubstituted `${...}`: it was never fetchable. Both still warn, because the leaf really was left unscanned. None of these refuse the stack the way a NAMELESS reference does (#2692). Issue #3160; the resolver-side fix is #3181.
