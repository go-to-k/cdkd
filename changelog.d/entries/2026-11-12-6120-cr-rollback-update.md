- **The rollback of a custom resource whose Update moved its physical id sends an `Update`, not a `Create` (issue [#6120](https://github.com/go-to-k/cdkd/issues/6120))** -- `src/deployment/rollback-executor/plan/classify.ts`, `replay-revert.ts`, `replay-failed.ts`, `replay-completed.ts`, new `replay-moved-id-cleanup.ts`, `src/deployment/deploy-engine/execute/provision-node.ts`, `update-in-place.ts`, `src/types/rollback-journal.ts`, plus a rollback phase in the `custom-resource-physid-replace` integ. Before, a failed deploy's rollback of a custom resource whose handler had answered a new `PhysicalResourceId` re-created the old id with a `Create` (which a handler still holding it, for example one whose `Create` refuses an existing name, failed), then deleted the new id. Like CloudFormation, the rollback now sends the NEW id an `Update` with the old properties, records whatever id the handler answers, and sends the id it moved off a `Delete` once the rollback has completed (CloudFormation's `UPDATE_ROLLBACK_COMPLETE_CLEANUP`). Any rollback `Update` (including `cdkd rollback --revert-failed`) whose handler answers a new id now deletes the id it moved off the same way; before, that id was left untracked. The Delete is not sent under `UpdateReplacePolicy: Retain` or `Snapshot`, nor for an id another record names; until it is sent the id is kept in state, so an interrupted or failed one is retried by the next deploy or `cdkd destroy`. The deploy journals the provider's answer on the completed op (`oldPhysicalIdLeftForCleanup`); a journal written by an older cdkd lacks it and keeps the re-create.
