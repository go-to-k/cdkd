- **`AWS::DynamoDB::Table` now SENDS a per-GSI `OnDemandThroughput` change (issue [#3287](https://github.com/go-to-k/cdkd/issues/3287))** -- `src/provisioning/providers/dynamodb-table-provider.ts`, `tests/unit/provisioning/dynamodb-table-provider-cfn-integer.test.ts`, `tests/integration/dynamodb-ondemand/`. `UpdateGlobalSecondaryIndexAction.OnDemandThroughput` exists in the SDK model and NEITHER per-index update arm set it, while `updateHasMember` was set only by the capacity and warm arms -- so a template whose only edit was a live index's ceiling fired no op at all, deployed GREEN and was recorded as applied, losing the edit permanently with nothing warned. Both arms (the same-name `Update` and the adopted-index repair) now carry it through `coerceOnDemandCeilingsForSend`, the reader the other four send sites use, taking the ceiling-member count from four sites to six. The member is REFUSED outright on a PROVISIONED table -- AWS accepts it only on PAY_PER_REQUEST, and it rides the same action as the capacity, so sending it would take a valid capacity edit down with it; the table-level pre-flight refusal cannot see that shape because it keys on the TABLE block. A live-`DescribeTable` idempotency guard withholds an op AWS already applied (the #1630 class, fail-open on anything unreadable), and a block with no surviving GRAMMAR member emits no op rather than an action AWS rejects for carrying only `IndexName`. Removing a ceiling stays a no-op at both positions, tracked as issue [#3373](https://github.com/go-to-k/cdkd/issues/3373). The RECORD side is untouched: an `effectiveProperties` + `canonicalizeDesiredProperties` fold was written for this change and WITHDRAWN, so issue [#3286](https://github.com/go-to-k/cdkd/issues/3286) stays open and now carries the evidence and a revised estimate.
