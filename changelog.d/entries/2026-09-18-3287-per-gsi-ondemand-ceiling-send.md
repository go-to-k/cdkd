- **`AWS::DynamoDB::Table` now SENDS a per-GSI `OnDemandThroughput` change (issue [#3287](https://github.com/go-to-k/cdkd/issues/3287))** -- `src/provisioning/providers/dynamodb-table-provider.ts`, `tests/integration/dynamodb-ondemand/`. `UpdateGlobalSecondaryIndexAction.OnDemandThroughput` exists in the SDK model and NEITHER per-index update arm set it, and `updateHasMember` was set only by the capacity and warm arms -- so a template whose only edit was a live index's ceiling fired no op at all, deployed GREEN, and was recorded as applied: the edit lost permanently with nothing warned. Both arms now carry it through `coerceOnDemandCeilingsForSend`, the reader the other four send sites use. A live-`DescribeTable` idempotency guard withholds an op AWS already applied (#1630); the detector narrows both sides only when NOTHING was dropped, falling back to a RAW compare otherwise so a still-malformed template keeps being announced; and a block with no surviving GRAMMAR member emits no op. One BEHAVIOUR CHANGE: AWS accepts `OnDemandThroughput` only on a PAY_PER_REQUEST table, so a PROVISIONED table declaring a per-index ceiling -- which used to deploy GREEN with it silently ignored -- now has the `UpdateTable` REJECTED, taking co-resident capacity edits with it. Loud beats silently lost; a cdkd-worded pre-flight refusal across all THREE per-index send sites is issue [#3392](https://github.com/go-to-k/cdkd/issues/3392). Removing a ceiling stays a no-op at both positions (issue [#3373](https://github.com/go-to-k/cdkd/issues/3373)), and the RECORD side is untouched: an `effectiveProperties` + `canonicalizeDesiredProperties` fold was written for this change and WITHDRAWN, so issue [#3286](https://github.com/go-to-k/cdkd/issues/3286) stays open with the evidence.
