- **A changed resource that reads another changed resource through an unchanged one now waits for it on an update deploy (issue [#6244](https://github.com/go-to-k/cdkd/issues/6244))** -- `src/deployment/deploy-engine/dependencies.ts` (`nearestMemberDependencies`), `deploy-engine/execute.ts`, `deploy-engine/execute/lost-children.ts`, unit tests. Before, the create/update phase kept only the direct dependencies that were themselves being provisioned, so a chain such as a custom resource -> an unchanged `cr.Provider` framework function -> a changed `onEvent` function lost its only edge: both ends started at the same time, and the custom resource could run the previous handler code while the deploy reported success. cdkd now walks through every unchanged resource to the nearest changed ones behind it (memoized, once per unchanged resource), as CloudFormation orders them. Changed resources with no such chain between them still run in parallel. The re-created children of an update-failure fallback are ordered the same way.
