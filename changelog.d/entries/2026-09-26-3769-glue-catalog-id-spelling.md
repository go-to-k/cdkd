- **Adding your own account id as a Glue Table or Connection `CatalogId` no longer plans a replacement (issue [#3769](https://github.com/go-to-k/cdkd/issues/3769))** -- a new optional `ResourceProvider.createOnlyValuesEquivalent` hook (`src/types/resource.ts`), consulted by `DiffCalculator` (`src/analyzer/diff-calculator.ts`) only where the registry schema's createOnly fallback would plan a replacement, built for both `cdkd deploy` and `cdkd diff` by `makeCreateOnlyEquivalenceFn` (`src/provisioning/canonicalize-properties.ts`) and implemented by `GlueProvider` / `GlueConnectionProvider`; unit tests in `tests/unit/analyzer/`, `tests/unit/provisioning/`, `tests/unit/cli/diff-recursive.test.ts` and `tests/unit/deployment/deploy-engine-effective-properties.test.ts`; phase 2e of the `glue-update-hardening` fixture. `CatalogId` is createOnly on these types and the diff compared raw values, so switching between an absent `CatalogId` and a literal equal to the deploying account's id was planned as a replacement: a Connection was deleted and re-created, and a Table stopped at the stateful guard asking for `--force-stateful-recreation`. Both spellings address the same Data Catalog, so the change is now an in-place update; the deploying account comes from the diff's own `AWS::AccountId` resolution, and without it the replacement stands. A move to another account's catalog is still a replacement.
