- **`cdkd destroy --remove-protection` no longer strips a Cognito user pool's Lambda triggers, advanced security or self-sign-up setting when it turns deletion protection off (issue [#4066](https://github.com/go-to-k/cdkd/issues/4066))** -- `src/provisioning/providers/cognito-provider.ts`, `deletion-protection-compensation.ts`, `docs/cli-destroy.md`, with unit tests in `tests/unit/provisioning/providers/cognito-remove-protection-rmw.test.ts`. Before, the flip-off and the #2204 re-enable sent `UpdateUserPool` with `DeletionProtection` alone, and `UpdateUserPool` resets members a call omits: measured live, `LambdaConfig` triggers, `UserPoolAddOns`, `AutoVerifiedAttributes`, `VerificationMessageTemplate`, `DeviceConfiguration` and `AllowAdminCreateUserOnly` (self sign-up switched on) all reset, so a pool whose delete then failed stayed live without them. On a pool requiring email verification before an attribute update, the bare flip was refused outright, so `--remove-protection` could not delete it. Both writes now send back, from the pool's own `DescribeUserPool`, the settings a call would reset (and nothing measured to survive omission, except a `DEVELOPER` SES email configuration, which is unmeasured), and a pool left live with settings reset after a failed delete is reported at ERROR with what it held. If AWS refuses a write carrying the SES email configuration, it is re-sent once without it, with a warn that the email configuration may have been reset. Only when AWS refuses the echo on validation after that does the flip fall back to the bare write, at warn, and only then may the re-enable too. A pool cdkd cannot read first is no longer flipped blind: its guard stays on, at warn, so `--remove-protection` on a user pool now needs `cognito-idp:DescribeUserPool`. A throttle or server error on the read or the flip retries the whole delete before anything is deleted.
