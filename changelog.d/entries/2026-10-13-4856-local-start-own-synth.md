- **`cdkd local start-agentcore` / `start-cloudfront` / `start-service` / `start-alb` synthesize with cdkd's own synthesizer (issue [#4856](https://github.com/go-to-k/cdkd/issues/4856))** -- `src/cli/commands/local-host-synthesizer.ts` (new), `src/cli/commands/local-start-{agentcore,cloudfront,service,alb}.ts`, `package.json` (cdk-local 0.150.0, which takes a `synthesizer`, go-to-k/cdk-local#787). These four commands synthesized the CDK app through cdk-local's `@aws-cdk/toolkit-lib` synthesizer, the only `cdkd` commands that did. They now use cdkd's synthesizer, as `local invoke` / `start-api` / `run-task` do, on boot and on every `--watch` reload. The stacks these commands pick a target from now include a `cdk.Stage`'s stacks, which cdk-local's synthesizer did not enumerate (go-to-k/cdk-local#746); a stack carrying a CloudFormation macro is expanded, using `--state-bucket` for a template too large to expand inline, and context lookups and `cdk.json` / `cdk.context.json` context resolve as in every other `cdkd` command. A macro-bearing stack is expanded on every `--watch` reload too, which needs credentials and a region. `--verbose` shows the synthesis debug output again, and `--role-arn` is the identity of the synthesis's own AWS calls (macro change set, upload) under `--profile` as well. Tests: `tests/unit/cli/local-host-synthesizer.test.ts`, `tests/unit/cli/local-start-own-synth-wiring.test.ts` (new). Integ: `local-start-agentcore`, `local-start-cloudfront`, `local-start-service`, `local-start-alb`, `local-start-service-watch-fast`, `local-start-alb-from-state`.
