- **The SDK provider sends `AutoMinorVersionUpgrade`, `NetworkType`, the Performance Insights settings and `EnableHttpEndpoint` for `AWS::RDS::DBCluster` (issue [#5639](https://github.com/go-to-k/cdkd/issues/5639))** -- `src/provisioning/providers/rds-provider.ts`, the regenerated property-coverage map, `tests/fixtures/cfn-schemas/_todo-backfill.json`, a new unit file, the RDS wire cases, and a new arm in the `rds-aurora` integ. Before, a cluster declaring any of `AutoMinorVersionUpgrade`, `NetworkType`, `PerformanceInsightsEnabled`, `PerformanceInsightsKmsKeyId`, `PerformanceInsightsRetentionPeriod` or `EnableHttpEndpoint` (a CDK `rds.DatabaseCluster` with `enableDataApi`, for one) routed through Cloud Control. Each now rides `CreateDBCluster` as declared, as CloudFormation sends it. An update sends a changed `AutoMinorVersionUpgrade` or `NetworkType`, and all declared Performance Insights settings when any of them changed; removing one of these leaves the live value, as under CloudFormation. A changed `EnableHttpEndpoint` on an `aurora-mysql` or `aurora-postgresql` cluster turns the Data API on or off with `EnableHttpEndpoint` / `DisableHttpEndpoint` and waits for the cluster to report it (skipped under `--no-wait`); removing a declared `true` turns it off, as CloudFormation does, so the deploying identity needs `rds:EnableHttpEndpoint` / `rds:DisableHttpEndpoint` for that change. `cdkd drift` reads all six back; `cdkd drift` reports a changed Data API setting, but `cdkd drift --revert` only turns it off, never on (its baseline records the live setting, which may have been turned on outside the template); it warns instead. Resources already deployed through Cloud Control stay there.
