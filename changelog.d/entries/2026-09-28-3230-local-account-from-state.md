- **`cdkd local *` now substitutes `${AWS::AccountId}` from the account the stack was read from, so `--from-state --role-arn` no longer names the caller's account (issue [#3230](https://github.com/go-to-k/cdkd/issues/3230))** -- `src/cli/commands/local-invoke.ts` (`resolvePseudoParametersForInvoke`), `local-start-api.ts` (`resolvePseudoParametersForStartApi`), `local-run-task.ts` (`resolveStackAccountId`, `resolvePlaceholderAccount`) and `local-invoke-agentcore.ts` (`resolveStackAccountId`), plus `tests/unit/cli/local-stack-account-source.test.ts`. Each resolver asked STS as the CALLER. Under `--from-state` with `--role-arn` the state record is read as the ROLE, and `ExpectedBucketOwner` pins that bucket to the reader's own account, so an emulated function resolved ARNs, ECR image URIs and the bare `--assume-task-role` ARN for an account its stack does not live in. Under `--from-state` the account is now asked as the state reader (the role when one is published); under `--from-cfn-stack`, or with no state source, it stays the caller's own. `local invoke` / `start-api` / `run-task` also ask through `--profile` now, the identity both state sources read through; before, they asked the default chain while the state was read as the profile. A run without `--role-arn` or `--profile` is unchanged. The container's own credentials are not affected. The `invoke` / `start-api` STS-failure warnings now name `--from-cfn-stack` rather than `--from-state` when that is the source in use.
