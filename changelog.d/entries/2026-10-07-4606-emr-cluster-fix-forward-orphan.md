- **A successful fix-forward deploy now settles the EMR cluster an earlier failed CREATE left under the same logical id (issue [#4606](https://github.com/go-to-k/cdkd/issues/4606))** -- `src/provisioning/providers/emr-cluster-provider.ts`. After `cdkd deploy --no-rollback` failed with an `AWS::EMR::Cluster` that `RunJobFlow` made and the create's own terminate could not stop (a journaled proven orphan) and the fixed template created a new cluster under the same logical id, the successful deploy warned, named the earlier cluster and exited `2`. `EMRClusterProvider` now answers `isSameResource` from the `j-` cluster id: the client must be in the stack's region and the record's cluster must read back live (`STARTING`, `BOOTSTRAPPING`, `RUNNING` or `WAITING`); the earlier cluster is then `different`, so the settle deletes it (terminating a live one) and the deploy exits `0`. Equal ids are `same`; any other id form and a failed read stay `unknown` (the previous warning and exit `2`). An earlier cluster already terminated or gone is named in one info line. `AWS::EMR::InstanceFleetConfig` / `AWS::EMR::InstanceGroupConfig` keep the warning: no EMR call reads a fleet or group by id without its cluster id, and neither has a delete API. Tests: `tests/unit/provisioning/emr-same-resource-4606.test.ts`; integ `emr-cluster` Phase 3b asserts the earlier cluster settled, the new one kept, exit `0`.
