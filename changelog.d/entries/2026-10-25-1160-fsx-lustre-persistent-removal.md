- **`AWS::FSx::FileSystem`: the warning for a removed Lustre persistent or Intelligent-Tiering sub-property now says CloudFormation keeps the value too, on the shapes measured (issue [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/fsx-filesystem-provider.ts`. A CloudFormation A/B on the issue (us-east-1, 2026-10-25) removed each property. Every removal completed in place, with the same file system and the value unchanged: `DailyAutomaticBackupStartTime`, `AutomaticBackupRetentionDays`, `PerUnitStorageThroughput` and `MetadataConfiguration` on `PERSISTENT_2` SSD, alone and all four together, and the first three on `PERSISTENT_1` HDD; `DataReadCacheConfiguration` and `ThroughputCapacity` on `PERSISTENT_2` `INTELLIGENT_TIERING`, each removed alone. cdkd already sent nothing for these removals, so only the warning changes: it now reads `... and keeps its current AWS value, as CloudFormation leaves it; ...`. The four SSD rows get that wording on Lustre SSD and HDD file systems. The two Intelligent-Tiering rows get it only on `PERSISTENT_2` `INTELLIGENT_TIERING`, and only when the property is the deploy's single removal. Every other shape keeps the line that claims nothing about CloudFormation. CloudFormation replaces the file system when `CopyTagsToBackups` is removed. cdkd still refuses that change with its `--replace --force-stateful-recreation` pointer. Tests: `tests/unit/provisioning/providers/fsx-filesystem-provider.test.ts`. The `fsx-lustre` integ gains a `PERSISTENT_2` file system whose four persistent-only settings are removed in the removal phase.
