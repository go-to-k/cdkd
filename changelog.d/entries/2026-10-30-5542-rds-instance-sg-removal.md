- **Removing `VPCSecurityGroups` from an RDS DB instance now moves the instance to its VPC's default security group, as CloudFormation does (issue [#5542](https://github.com/go-to-k/cdkd/issues/5542), umbrella [#1160](https://github.com/go-to-k/cdkd/issues/1160))** -- `src/provisioning/providers/rds-provider.ts`, `tests/unit/provisioning/rds-instance-sg-removal-5542.test.ts`, `tests/integration/rds-dbinstance-backfill/`, `docs/troubleshooting-permissions.md`. Before this change, cdkd sent no security groups when an `AWS::RDS::DBInstance` dropped `VPCSecurityGroups`, so `ModifyDBInstance` kept the removed groups attached, and their ingress open, while the deploy reported success. A real CloudFormation A/B (us-east-1) removed the property from a non-Aurora instance in a VPC, alone and beside another change: both times CloudFormation sent `ModifyDBInstance` with the VPC's `default` security group, and the instance stayed on that group. cdkd now does the same, through the lookup the DB cluster removal already uses (the instance's DB subnet group gives the VPC; `ec2:DescribeSecurityGroups` gives the group named `default`). If the group cannot be found, the update fails before any change and says to declare `VPCSecurityGroups`. The lookup runs only on this removal, and the deploy credentials need `ec2:DescribeSecurityGroups` for it. A warning names the group attached. An empty list is still never sent, and `cdkd drift --revert` does not reset.
